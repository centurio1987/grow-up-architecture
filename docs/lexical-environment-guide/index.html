렉시컬 환경으로 읽는 화살표 함수와 function 함수

두 함수는 변수를 찾는 방법이 같고, this를 얻는 곳만 다릅니다. 명세(ECMA-262)의 단계와 그림으로 그 차이를 보이고, 마지막에는 “전역 화살표 함수가 변수를 많이 참조하면 GC가 힘들지 않을까?”라는 질문을 Node 실측으로 답합니다.

작성 2026-10-28 명세 기준 ECMA-262 2027 초안(2026-10-23판) 실측 Node v22.22.3 · V8 12.4 · macOS arm64

먼저 결론

  1. 렉시컬 환경은 “이름 → 값” 칸을 모은 기록(환경 레코드)과, 바깥 기록을 가리키는 연결([[OuterEnv]])의 묶음입니다. 변수는 이 연결을 안에서 바깥으로 따라가며 찾습니다.
  2. 화살표 함수와 function 함수는 만들어질 때 그 자리의 환경을 [[Environment]] 칸에 똑같이 담습니다. 자기가 만들어진 환경을 기억하는 함수, 곧 클로저로서는 차이가 없습니다.
  3. 차이는 this·arguments·super·new.target을 스스로 갖느냐입니다. function 함수는 부를 때마다 this를 새로 정하고, 화살표 함수는 그 칸이 없어서 바깥 환경의 것을 변수처럼 찾아 씁니다. new로 부를 수 없는 것도 같은 설계에서 나옵니다.
  4. 전역 화살표 함수가 전역 변수를 아무리 많이 참조해도 GC는 그대로 동작합니다. 함수가 붙잡는 것은 환경 하나를 가리키는 연결 하나이고, 전역 환경은 함수가 없어도 끝까지 살아 있으며, 변수에 새 값을 넣으면 옛 값은 회수됩니다. 실측에서 전역 변수 1개를 참조하는 클로저와 50개를 참조하는 클로저는 둘 다 56바이트였습니다.
  5. 실제로 조심할 곳은 함수 안의 환경입니다. 오래 사는 콜백이 큰 값을 참조할 때, 같은 스코프의 클로저들이 컨텍스트를 함께 쓸 때, 직접 eval을 쓸 때 값이 남습니다. 이 셋은 함수 종류와 상관없이 생깁니다.

1. 렉시컬 환경: 이름을 찾는 사슬

코드에 level이라고 적으면 엔진은 그 이름이 가리키는 값을 어딘가에서 찾아야 합니다. 명세는 “이름 → 값” 칸들을 모아 둔 기록을 환경 레코드(Environment Record)라고 부릅니다. 그리고 모든 환경 레코드에 바깥 기록을 가리키는 연결 [[OuterEnv]]를 하나씩 둡니다(ECMA-262 9.1).

렉시컬 환경은 이 둘을 묶어 부르는 말이에요. ES2015 무렵의 명세는 Lexical Environment라는 이름으로 둘을 묶어 정의했고, 지금 판은 환경 레코드가 [[OuterEnv]]를 직접 갖도록 정리했습니다. 이름만 바뀌었고 뜻은 같아요. “렉시컬”은 코드를 쓴 자리로 정해진다는 뜻이어서, 바깥 연결도 코드가 어디에 쓰였는지로 정해집니다.

환경 레코드는 코드 종류에 따라 다섯 가지가 있습니다. 이 가이드에서 자주 나오는 것은 선언적·함수·전역 세 가지입니다.

종류언제 생기나담는 것
선언적 환경 레코드블록 { }, catch 절, for (let …)의 반복마다let·const·class 선언
함수 환경 레코드함수를 부를 때마다 새로매개변수, 지역 변수, this와 new.target 칸. 화살표 함수의 것에는 this 칸이 없습니다.
모듈 환경 레코드ES 모듈마다 하나모듈 최상위 선언, import로 들여온 이름
객체 환경 레코드with 문, 그리고 전역 레코드 안쪽어떤 객체의 속성을 이름처럼 보이게 함
전역 환경 레코드실행 환경(realm)마다 하나. 바깥 연결은 null전역 객체를 감싼 객체 레코드(var, function 선언)와 선언적 레코드(최상위 let·const·class)를 합친 것

이름은 늘 안쪽에서 바깥쪽으로 찾아요. 같은 이름이 여러 층에 있으면 가장 안쪽 것이 먼저 걸리고, null까지 갔는데도 없으면 ReferenceError가 납니다. 명세에서는 ResolveBinding(9.4.2)과 GetIdentifierReference(9.1.2.1)가 이 일을 맡습니다. 아래 그림에서 이름을 눌러 보면 찾는 순서가 보여요.

헷갈리기 쉬운 지점: 바깥 연결은 부른 곳이 아니라 쓴 곳으로 정해집니다
const who = '전역';
function show() { return who; }
function caller() {
  const who = 'caller';
  return show();
}
caller();   // '전역'

show를 caller 안에서 불러도 show의 바깥은 show를 쓴 자리인 전역 환경입니다. 그래서 'caller'가 아니라 '전역'이 나옵니다. 부른 곳의 변수를 보는 방식(동적 스코프)은 JavaScript에 없습니다.

show() 호출 환경 ──[[OuterEnv]]──▶ 전역 환경 { who: '전역', show, caller }
caller() 호출 환경 { who: 'caller' } ──[[OuterEnv]]──▶ 전역 환경
                 ▲
                 show의 사슬에는 들어 있지 않습니다

this만은 부르는 방식에 따라 바뀌는 것처럼 보이는데, 그 이유는 4절에서 다룹니다.

2. 함수는 만들어진 자리의 환경을 기억합니다

함수 객체에는 [[Environment]]라는 내부 칸이 있습니다. 명세의 설명을 옮기면, 함수가 만들어질 때 닫아 둔 환경 레코드이고 함수 코드를 실행할 때 바깥 환경으로 쓰는 칸입니다(10.2, 함수 객체의 내부 칸 표). 함수를 부르면 엔진은 새 함수 환경 레코드를 만들고, 그 [[OuterEnv]]에 [[Environment]] 값을 넣습니다(NewFunctionEnvironment, 9.1.2.4).

그래서 함수를 만든 바깥 함수가 이미 끝났어도, 함수가 살아 있는 한 그 환경에 닿는 길이 남습니다. 자기가 만들어진 환경을 이렇게 들고 다니는 함수를 클로저라고 부릅니다. JavaScript의 함수는 모두 이 칸을 가지므로 모든 함수가 클로저입니다.

아래 실행 화면은 화살표 함수와 function 함수를 같은 바깥 함수 안에서 만들고 차례로 부릅니다. 다음 버튼이나 키보드 →·←로 한 단계씩 넘기면 됩니다.

실행 화면에서 본 것을 정리해 볼게요. 화살표 함수 byArrow와 function 함수 byFunc는 같은 E1을 [[Environment]]로 가졌고, 부를 때 만든 환경의 바깥 연결도 둘 다 E1이었습니다. 그래서 total을 함께 고쳐 12, 14로 이어졌어요. 두 함수가 갈라진 곳은 호출 환경에 this 칸이 있느냐 하나뿐이었습니다.

바깥 함수의 실행 컨텍스트(지금 실행 중인 코드의 작업 공간)가 스택에서 빠진 뒤에도 E1이 남은 것도 눈여겨볼 곳입니다. 환경 레코드의 수명은 실행 컨텍스트가 아니라 “누가 아직 가리키는가”로 정해집니다. 이 점이 7절부터 다룰 GC 이야기의 출발점입니다.

3. 명세에서 두 함수가 갈라지는 곳

두 함수가 같은 방식으로 환경을 기억한다는 것은 명세의 생성 단계에서 바로 보입니다. 아래는 함수 식을 평가하는 두 연산의 단계를 우리말로 줄여 옮긴 것입니다. 색칠한 줄이 서로 다른 곳입니다.

// 화살표 함수 식 (15.3.4 InstantiateArrowFunctionExpression)
1. env ← 지금 실행 컨텍스트의 렉시컬 환경
2. 함수 ← OrdinaryFunctionCreate(…,
          lexical-this, env, …)
3. 이름을 붙이고 돌려준다
// function 식 (15.2.5 InstantiateOrdinaryFunctionExpression)
1. env ← 지금 실행 컨텍스트의 렉시컬 환경
2. 함수 ← OrdinaryFunctionCreate(…,
          non-lexical-this, env, …)
3. 이름을 붙인다
4. MakeConstructor(함수)
5. 돌려준다

두 연산 모두 1번 단계에서 지금 환경을 가져와 2번 단계에서 함수의 [[Environment]]로 넣으니, 환경을 기억하는 방식은 글자 그대로 같습니다. 차이는 둘이에요. 화살표 함수는 lexical-this 표시를 달고 만들어져 [[ThisMode]]가 lexical이 되고, MakeConstructor(10.2.5)를 거치지 않습니다. MakeConstructor를 거치지 않은 함수에는 [[Construct]] 내부 메서드가 없어서 new로 부를 수 없고 prototype 속성도 없어요.

[[ThisMode]] 표시는 함수를 부를 때 세 곳에서 쓰입니다.

  • OrdinaryCallBindThis(10.2.1.2): 호출하면서 this를 묶는 단계입니다. 표시가 lexical이면 아무것도 묶지 않고 바로 끝납니다. strict면 넘겨받은 값을 그대로 쓰고, 엄격 모드가 아닌 함수(global)는 undefined·null을 전역 객체로 바꾸고 원시값은 객체로 감쌉니다.
  • NewFunctionEnvironment(9.1.2.4): 호출 환경을 만들 때 [[ThisBindingStatus]]를 lexical로 둡니다. 이 환경에는 this 칸이 없다는 뜻입니다.
  • FunctionDeclarationInstantiation(10.2.11): 화살표 함수에는 arguments 객체를 만들지 않습니다.
한 줄로 줄이면

화살표 함수는 “this를 다르게 묶는 함수”가 아니라 “this를 묶지 않는 함수”입니다. 묶지 않은 this를 어디서 찾는지가 다음 절의 내용입니다.

4. this는 어디서 오나

본문에서 this를 만나면 엔진은 GetThisEnvironment(9.4.3)로 지금 환경부터 바깥으로 올라가며 this 칸이 있는 첫 환경을 찾습니다. function 함수의 호출 환경에는 this 칸이 있으므로 거기서 멈추고, 그 칸의 값은 함수를 어떻게 불렀는지로 정해집니다.

화살표 함수의 호출 환경과 블록 환경에는 this 칸이 없으므로 엔진은 그곳을 지나칩니다. 그러다 화살표 함수를 쓴 자리를 감싼 함수의 환경에서 멈춥니다. 결국 화살표 함수의 this는 변수와 같은 규칙, 곧 쓴 자리로 정해집니다.

'use strict';
function Outer() {
  const fn = function () { return this; };
  const ar = () => this;
  return { fn, ar };
}
const host = { name: 'host' };
const other = { name: 'other' };
const { fn, ar } = Outer.call(host);   // Outer의 this = host

아래 버튼으로 부르는 방식을 바꿔 보면 function 쪽 결과는 매번 바뀌고 화살표 쪽은 늘 host입니다. Outer를 Outer.call(host)로 불렀으므로 Outer 호출 환경의 this 칸에 host가 들어 있고, ar은 그 칸을 찾아 씁니다.

엄격 모드를 가정했습니다. 엄격 모드가 아닌 function 함수는 그냥 부를 때 this가 undefined 대신 전역 객체가 됩니다.

헷갈리기 쉬운 지점: 객체 리터럴 안의 화살표 메서드
const counter = {
  count: 0,
  inc: () => { this.count++; },   // this는 counter가 아닙니다
};

객체 리터럴의 중괄호는 환경을 만들지 않아서, inc의 바깥은 counter를 쓴 자리가 됩니다. 모듈 최상위라면 그곳의 this가 undefined여서 TypeError가 나고, 일반 스크립트라면 전역 객체의 count를 건드려요. 메서드는 inc() { this.count++; }처럼 메서드 문법으로 씁니다.

5. 그 밖의 차이 한눈에

this 말고도 화살표 함수가 스스로 갖지 않는 것이 몇 가지 더 있습니다. 원리는 모두 같아서, 화살표 함수의 호출 환경에 칸이 없으니 바깥에서 찾거나 아예 쓸 수 없습니다. 마지막 열은 이 가이드를 쓰며 확인한 방법입니다.

“선언 전에 부르기” 줄은 함수 종류보다 선언 방식의 차이입니다. const f = function () {}로 써도 같은 ReferenceError가 납니다. 값을 넣기 전의 let·const 이름을 읽으면 나는 오류이고, 이 구간을 TDZ(일시적 사각지대)라고 부릅니다.

6. 언제 무엇을 쓰나

차이가 this로 모이므로 고르는 기준도 this입니다.

  • 메서드 안의 콜백(map, then, setTimeout 등)에서 바깥 메서드의 this를 그대로 쓰려면 화살표 함수를 씁니다. 예전에 const self = this;나 .bind(this)로 하던 일을 문법이 대신합니다.
  • 객체와 클래스의 메서드, 생성자는 메서드 문법(inc() {})이나 class로 씁니다. 화살표 함수로 쓰면 this가 객체를 가리키지 않고 new도 쓸 수 없습니다.
  • 부르는 쪽이 this로 값을 넘겨주는 콜백(DOM 이벤트 리스너의 요소 등)은 function 함수를 씁니다. 이벤트라면 event.currentTarget을 읽으면 화살표 함수로도 됩니다.
  • 클래스 필드 화살표 함수(handle = () => {})는 this가 고정되는 대신 인스턴스마다 함수 객체가 생깁니다. 인스턴스가 아주 많다면 프로토타입 메서드로 두고, 콜백으로 넘길 때만 bind하는 편이 메모리를 덜 씁니다.

변수를 붙잡는 방식은 두 함수가 같으므로, 메모리를 이유로 둘 중 하나를 고를 일은 없습니다. 다음 절부터 그 이야기를 합니다.

7. GC는 무엇을 보고 지우나

GC(가비지 컬렉션)는 더 쓰지 않을 메모리를 찾아 돌려받는 일입니다. 엔진은 어떤 값을 앞으로 쓸지 알 수 없으므로, 대신 그 값에 닿을 수 있는지를 봅니다. V8 블로그의 Orinoco 설명도 닿을 수 있음을 살아 있음의 대리 지표로 쓴다고 적습니다.

방법은 이렇습니다. 실행 스택과 전역 객체 같은 뿌리(root)에서 출발해 포인터를 따라가며 닿는 객체에 표시를 하고(mark), 표시가 없는 객체를 거둡니다(sweep). V8은 여기에 더해 객체를 새 세대와 옛 세대로 나눕니다. 새 세대는 Scavenger라는 작은 GC로 자주 거두고, 힙 전체는 Mark-Compact라는 큰 GC로 가끔 거둡니다. 표시 작업은 보조 스레드에서 자바스크립트 실행과 함께 진행하기도 합니다.

아래 그림에서 표시와 쓸기를 직접 돌려 볼 수 있습니다. 오른쪽 X와 Y는 서로를 가리키지만 뿌리에서 닿는 길이 없습니다.

참조 개수를 세는 방식(reference counting)이었다면 결과가 달랐을 것입니다. “옛 결과 배열”은 가리키는 곳이 0곳이라 지워지지만, X와 Y는 서로를 하나씩 가리키고 있어 개수가 0이 되지 않아요. 둘은 영원히 남습니다. MDN은 지금의 자바스크립트 엔진 가운데 참조 개수 방식을 쓰는 것은 없고 모두 표시하고 쓸기 방식을 쓴다고 적고 있습니다. 이 가이드의 실측(사례 cycle)에서도 객체와 클로저가 서로 가리키는 순환 구조가 뿌리에서 끊긴 뒤 회수됐어요.

여기서 가져갈 한 가지

이 방식은 객체를 “몇 곳에서 가리키느냐”를 보지 않고 “뿌리에서 닿느냐” 하나만 봅니다. 열 곳에서 가리켜도 뿌리에서 닿지 않으면 거두고, 한 곳에서만 가리켜도 그곳이 뿌리에서 닿으면 남깁니다. 표시는 객체마다 한 번만 하므로, 이미 표시한 객체를 가리키는 연결이 더 있다고 따라갈 일이 늘지도 않습니다.

8. 전역 화살표 함수가 변수를 많이 참조해도 괜찮은 이유

질문을 다시 적으면 다음과 같아요. 화살표 함수를 전역에 두고 그 안에서 렉시컬 환경의 변수를 많이 참조하면, 함수가 그 변수들을 모두 붙잡고 있어서 GC가 제대로 거두지 못할 것 같다는 걱정입니다. 자연스러운 직관이지만 실제로는 문제가 생기지 않습니다. 이유는 네 가지이고, 모두 이 컴퓨터의 Node v22.22.3에서 실측으로 확인했어요.

// 일반 스크립트의 최상위(전역)
let big = loadHugeTable();               // 약 8MB 배열
let a1 = 1, a2 = 2, /* … */ a50 = 50;
const read = () => big.length + a1 + a2 + /* … */ a50;

근거 1. 함수가 붙잡는 것은 변수 50개가 아니라 환경 하나입니다

2절에서 본 대로 함수 객체에는 [[Environment]] 칸이 하나뿐이고, 거기에는 환경 레코드 하나가 들어갑니다. 본문에 이름을 50개 적어도 함수가 이름마다 연결을 따로 만들지 않습니다. 본문의 이름은 실행할 때 환경 사슬에서 찾으라는 코드일 뿐입니다.

실측에서는 전역 변수 1개를 참조하는 화살표 함수와 50개를 참조하는 화살표 함수를 20만 개씩 만들고, 늘어난 힙을 개수로 나눴습니다(사례 closureSize).

클로저 하나가 차지한 힙 (V8 12.4, 20만 개 평균)
전역 변수 1개 참조
56 B
전역 변수 50개 참조
56 B

56바이트는 V8 내부 함수 객체의 크기라 버전과 설정에 따라 달라질 수 있습니다. 같은 버전에서 참조 수와 상관없이 같다는 점이 핵심입니다.

근거 2. 전역 환경은 화살표 함수가 없어도 끝까지 살아 있습니다

전역 환경 레코드는 실행 환경(realm)이 있는 동안 늘 뿌리에서 닿습니다. 전역 변수 big은 read가 있든 없든 전역 환경의 칸에 들어 있으므로 GC가 거두지 않습니다. 그러니 read가 big을 참조한다고 big의 수명이 늘어나지 않습니다.

아래 그림에서 read = null을 눌러 함수를 지워 보면 함수만 회수 대상이 되고 전역 변수는 그대로 남습니다. 값을 살려 두는 것은 함수의 참조가 아니라 전역이라는 자리입니다.

근거 3. 붙잡는 것은 칸이지, 그 칸에 들었던 값이 아닙니다

환경 레코드는 이름마다 칸(바인딩)을 두고, 칸에는 지금 값 하나가 들어 있습니다. 함수는 환경을 가리킬 뿐 값을 따로 복사해 두지 않아요. 그래서 big = null로 칸을 비우면 옛 배열은 뿌리에서 닿는 길을 잃고 회수됩니다. read는 그대로 살아 있습니다. 다음에 부르면 바뀐 값을 볼 뿐이에요. 실측(사례 globalRebind)에서도 read가 살아 있는 상태로 옛 배열이 회수됐습니다.

근거 4. GC는 참조 수를 세지 않고, 이미 표시한 객체는 다시 따라가지 않습니다

7절의 표시 방식에서 전역 환경은 어차피 모든 GC에서 표시되는 객체입니다. 화살표 함수가 더하는 것은 함수 객체 하나와 연결 하나이고, 함수가 변수 50개를 참조한다고 GC가 따라갈 길이 50개 늘어나지 않습니다. 참조 개수 방식이었다면 순환이나 개수 관리가 걱정거리였겠지만, 지금 엔진에는 해당하지 않습니다.

“전역”이 실제로 어떤 환경인지

코드를 어디서 실행하느냐에 따라 최상위 환경이 다릅니다.

  • 브라우저의 일반 <script>: 전역 환경 레코드입니다. var와 function 선언은 전역 객체의 속성이 되고, let·const는 전역 레코드 안의 선언적 레코드에 들어갑니다. V8은 여러 스크립트가 함께 보는 최상위 변수를 언제나 힙에 둡니다(V8 블로그, lazy parsing 편).
  • ES 모듈(<script type="module">, .mjs): 모듈 환경 레코드이고, 바깥 연결이 전역 환경입니다.
  • Node의 CommonJS 파일(.js, .cjs): Node가 파일 내용을 함수로 감싸 실행하므로 최상위가 실은 그 함수의 환경입니다(Node 문서, module wrapper).

어느 경우든 최상위 함수가 붙잡는 것은 그 최상위 환경 하나이고, 그 환경은 보통 프로그램이 끝날 때까지 살아 있습니다. 근거 1~4가 그대로 적용됩니다.

9. 그래도 메모리가 남는 경우

클로저가 메모리와 무관하다는 뜻은 아닙니다. 클로저 때문에 값이 오래 남는 경우는 정해져 있고, 공통점은 전역이 아니라 함수 안의 환경을 오래 붙잡는다는 것입니다. 아래 경우는 모두 화살표 함수와 function 함수에서 똑같이 생깁니다.

9-1. 오래 사는 콜백이 함수 안의 큰 값을 참조할 때

function watch() {
  const big = makeBig();
  setInterval(() => big.length, 60_000);   // 타이머가 살아 있는 동안 big도 남음
}

타이머, 이벤트 리스너, 전역 캐시에 등록한 함수는 등록이 풀릴 때까지 뿌리에서 닿습니다. 그 함수가 big을 참조하면 big도 함께 남아요. 실측(사례 longLivedCallback)에서 등록 중에는 회수되지 않았고, clearInterval 뒤에는 회수됐습니다. 다 쓴 등록은 clearInterval, removeEventListener, AbortController 등으로 풉니다.

9-2. 같은 스코프의 클로저들이 컨텍스트를 함께 쓸 때

명세의 환경 레코드는 그 스코프의 이름을 모두 담습니다. 명세 그대로라면 클로저 하나만 살아 있어도 그 스코프의 변수가 모두 남는 셈입니다. 다만 결과가 달라지지 않는 한 엔진은 이것을 아껴도 됩니다. V8은 안쪽 함수가 참조하는 변수만 힙의 컨텍스트(context)에 싣고, 나머지는 스택에 둡니다(V8 블로그, lazy parsing 편). 실측(사례 unreferencedLocal)에서도 어떤 클로저도 참조하지 않은 big은 바깥 함수가 끝난 뒤 회수됐습니다.

그런데 실측으로 보면 V8 12.4는 이 컨텍스트를 클로저마다 따로 만들지 않고 스코프마다 하나 만들어, 그 스코프의 클로저들이 함께 씁니다. 그래서 버린 클로저 하나가 big을 참조했으면, 살아남은 클로저가 big을 쓰지 않아도 big이 컨텍스트에 남습니다. 아래에서 코드를 바꿔 보며 확인할 수 있습니다.

function 키워드로 바꿔도 결과가 같았습니다(사례 sharedContextFunctionKeyword). 아무 변수도 쓰지 않는 콜백 () => 1을 타이머에 걸어 둔 경우에도, 같은 스코프에 big을 쓰는 클로저가 있으면 big이 남았습니다(사례 sharedContextNoRefs). 해결은 다 쓴 큰 값을 null로 끊거나, 큰 값을 다루는 일을 별도 함수로 떼어 스코프를 나누는 것입니다.

9-3. 직접 eval을 쓸 때

함수 안에서 eval(code)를 직접 부르면 엔진은 code가 어떤 이름을 쓸지 미리 알 수 없습니다. 그래서 그 스코프의 변수를 남겨 둘 수밖에 없습니다. 실측(사례 directEval)에서 아무 클로저도 big을 적지 않았는데, eval을 품은 클로저가 big을 붙잡았고 실제로 eval('big.length')로 읽을 수도 있었습니다.

9-4. 화살표 함수가 this를 쓸 때

화살표 함수가 this를 쓰면 바깥 함수의 this, 곧 메서드를 부른 객체를 붙잡습니다. 안 쓰면 붙잡지 않아요(사례 arrowThis). function 함수에서 const self = this;로 담아 쓰는 것과 같은 결과입니다. 큰 객체의 메서드가 돌려준 화살표 함수를 오래 보관하면 그 객체도 함께 남는다는 점만 기억하면 됩니다.

9-5. 전역에 계속 쌓을 때

전역 쪽에서 메모리가 늘어나는 경우는 클로저와 상관없이 전역에서 닿는 자료가 계속 늘 때입니다. 전역 배열에 핸들러를 계속 넣거나 전역 Map 캐시에 지우지 않고 넣기만 하면, 그 자료는 뿌리에서 닿으므로 남아요. 크기를 제한하고, 키가 객체라면 WeakMap을 씁니다. 8절의 결론은 “전역 화살표 함수의 참조가 값을 더 붙잡지 않는다”이지, “전역에 둔 값이 저절로 사라진다”가 아닙니다.

11. 스스로 확인하기

문제 1. (가)와 (나)에서 화살표 함수의 this는 무엇일까요? 
'use strict';
const counter = {
  count: 0,
  start() {
    setInterval(() => { this.count++; }, 1000);
  },
};
counter.start();          // (가)
const s = counter.start;
s();                      // (나)

(가)는 counter입니다. start를 counter.start()로 불러 start 호출 환경의 this가 counter이고, 화살표 함수는 그 칸을 찾아 씁니다.

(나)는 undefined입니다. start를 그냥 불러 start의 this가 undefined이므로 화살표 함수도 같은 값을 보고, 1초 뒤 this.count++에서 TypeError가 납니다. 화살표 함수의 this는 “바깥 함수가 받은 this”라서 바깥 함수를 어떻게 불렀는지에는 여전히 영향을 받습니다(Node로 확인).

문제 2. 두 코드 가운데 big이 회수되는 쪽은 어디일까요? 
// (가) 전역
let big = makeBig();
const read = () => big.length;
big = null;

// (나) 함수 안
function setup() {
  const big = makeBig();
  const unused = () => big.length;
  setInterval(() => 1, 1000);
}
setup();

(가)가 회수됩니다. read는 big 칸을 가리킬 뿐이고, 그 칸이 null이 되었습니다(근거 3).

(나)는 회수되지 않습니다. 타이머 콜백은 아무것도 참조하지 않지만 unused와 같은 setup의 컨텍스트를 받았고, 그 컨텍스트에 big이 실려 있습니다(9-2, 사례 sharedContextNoRefs). 전역 쪽이 오히려 안전한 경우입니다.

문제 3. 아래 코드에서 메모리가 계속 늘어나는 까닭은 무엇일까요? 
const handlers = [];
function on(fn) { handlers.push(fn); }
for (let i = 0; i < 100_000; i++) on(() => i);

화살표 함수여서가 아니라 전역 배열 handlers에 넣었기 때문입니다. 배열이 뿌리에서 닿으므로 함수 10만 개가 모두 남고, for (let …)은 반복마다 새 환경을 만들므로 각 반복의 i 칸도 함께 남습니다. function 함수로 바꿔도 같습니다. 다 쓴 핸들러는 배열에서 빼야 합니다(9-5).
