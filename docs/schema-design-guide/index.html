서론

개요를 읽는 대신, 설계자가 하는 일을 따라가기

이 책의 목표는 외부 스키마·개념 스키마·내부 스키마라는 이름을 외우는 것이 아니다. 이해관계자의 말을 해석해서 명세를 만들고, 명세가 무엇을 보장하는지 설명하고, 구현 선택을 추가한 뒤 그 선택이 업무 의미를 보존하는지 검증하는 능력을 갖추는 것이다. 그러므로 각 장은 정의를 소개한 다음 곧바로 다음 개념으로 넘어가지 않는다. 동일한 주문이 여러 표현에서 어떻게 보이는지, 그 표현을 얻기 위해 어떤 판단을 했는지를 실제 산출물과 함께 다룬다.

주문 O1은 한 장에서는 고객이 확인하려는 정보이고, 다른 장에서는 식별성과 불변식을 가진 업무 사실이며, 다른 장에서는 세 테이블에 걸친 기록이다. 도메인 객체에서는 상태를 바꾸는 주체이고, HTTP 응답에서는 공개하기로 한 필드들의 집합이다. 같은 대상에 관한 표현이라고 해서 필드 목록도 같아야 하는 것은 아니다. 오히려 무엇을 포함하고 제외했는지 설명할 수 있어야 경계를 이해한 것이다.

표기와 읽는 순서

SC는 시나리오, A는 가정, L은 한계, E는 외부 관점, C는 개념, R은 규칙, U는 유스케이스다. 이 식별자는 문서 장식이 아니라 추적을 위한 주소다. 예를 들어 R03은 “접수 당시 항목을 바꾸지 않는다”는 규칙이며, E01의 접수단가, OrderLine의 가격 스냅샷, order_line.unit_price_krw와 연결된다. 별도 파일의 ID도 본문과 동일하다.

본문의 O1·B1·P1은 긴 UUID를 읽기 쉽게 부르는 별칭이다. HTTP·코드 예제에서는 실제 UUID를 사용한다. 단일 HTML 안에 본문·모든 핵심 명세·예제 코드가 내장되어 있다. 긴 명세의 접힌 영역은 요약으로 대체한 것이 아니라 완전한 원문을 펼쳐 읽을 수 있게 한 것이다. 상단의 “명세 모두 펼치기”와 인쇄 기능도 사용할 수 있다.

용어를 먼저 분리한다

용어이 책의 뜻오해하기 쉬운 구분
외부 스키마특정 이용자가 보는 정보 집합, 그 구조와 의미, 선택·투영·계산 규칙웹 화면의 배치나 HTTP API 전체와 동일하지 않다.
외부 정보 계약외부 스키마에 목적·권한·시점·관련 행위를 보완한 교육용 문서 형식전통적인 3-스키마의 용어보다 넓게 기록한다.
개념 스키마합의한 업무 범위의 대상·동일성·관계·속성·제약을 정의한 의미 모델SQL 테이블 설계도, 모든 서비스의 유일한 전사 객체 모델도 아니다.
행위 명세상태 변화의 입력·사전조건·사후조건·실패·원자성 명세정적인 ERD만으로 표현했다고 간주하지 않는다.
논리 데이터 모델선택한 데이터 모델에서 키·관계·정합성을 표현한 구조이 책에서는 관계형 릴레이션을 사용한다.
내부 스키마DB의 저장 표현과 접근 경로를 구체화한 설계API와 도메인 객체를 담는 “내부 구현 전체”와 구분한다.
실행 가능한 도메인 모델업무 데이터와 행위를 함께 구현한 객체·값·규칙분석 단계의 개념 모델도 domain model이라고 부르므로 문맥을 구분한다.

외부·개념·내부는 관점의 구분이며, 개념·논리·물리는 구체화 수준을 말할 때 쓰는 분류다. 둘을 기계적으로 일대일 대응시키지 않는다. 이 책의 CREATE TABLE은 논리 구조를 DB에 실현하는 선언과 물리 타입 선택을 함께 포함한다. 인덱스 선언은 접근 경로를 정한다. 실제 디스크 페이지 배치까지 애플리케이션 설계자가 완전히 결정하는 것은 아니다. FIPS 184 부록 A2.2의 관점 구분을 참고하되 아래 JSON 형식은 이 책의 교육용 형식이다.

범위 안내

이 책은 지정한 유한한 주문 문제를 끝까지 설계하는 교재다. 결제·재고·배송까지 완성한 상용 주문 시스템이라고 주장하지 않는다. “완성된 산출물”은 명시한 범위에 대해 빈칸 없이 기술했다는 뜻이며, 실제 운영 검증을 통과했다는 뜻과 구별한다.

제1장

사람과 시간이 있는 시나리오를 먼저 만든다

오전 10시, 한 매장에서 빵 주문을 받는다. 구매자 민서는 우유식빵 두 개와 버터스콘 한 개를 고른다. 점원 지훈은 들어온 주문을 보고 처리 여부를 확정한다. 아직 결제도 재고 예약도 하지 않는다. 여기서 “접수”는 주문 의사를 기록했다는 뜻이고, “확정”은 점원이 그 주문을 처리하기로 결정했다는 뜻이다. 이 문장을 생략하면 독자는 확정을 카드 승인이나 재고 확보로 해석할 수 있다.

상품 선택 화면에는 우유식빵 3,000원, 버터스콘 2,000원이 표시된다. 두 상품의 가격 조건을 식별하는 revision은 각각 p1-r7, p2-r3다. revision은 가격 그 자체가 아니다. 이름·판매 가능성·가격 중 계약에 포함한 조건이 변경될 때 달라지는 불투명한 토큰이다. 구매자가 본 조건과 서버가 수락하는 조건이 같은지 확인하기 위해 사용한다.

시나리오 분기

SC03, SC04, SC05는 모두 SC01 직후 상태에서 독립적으로 시작한다. SC03으로 취소한 뒤 SC04로 같은 주문을 확정하는 순서가 아니다. 시나리오의 출발 상태를 쓰지 않으면 예제 자체가 규칙 위반이 된다.

시나리오의 구조적 형식

시나리오 메타 형식
Scenario = {
  id, name, actor,
  assumptions: [AssumptionId],
  before: 관찰 가능한 출발 상태,
  steps: 시간 또는 인과 순서가 있는 자극·응답,
  after: 반드시 성립할 결과,
  mustNot: 성공처럼 보이더라도 허용하지 않을 결과
}

before와 after는 DB 행 목록으로만 작성하지 않는다. 아직 저장 방식을 정하지 않았기 때문이다. “주문이 하나 존재한다”, “같은 접수 결과가 반환된다” 같은 업무 수준의 표현을 사용한다. 뒤의 저장 설계 장에서 이 상태를 실제 행으로 번역한다. 시간은 의미를 분리하기 위한 것이며 시스템의 벽시계만으로 동시 요청의 우선순위를 결정하지 않는다.

독자가 확인할 문제

SC06에서 최초 요청 후 카탈로그 가격이 달라졌다고 해보자. 재시도마다 가격을 다시 검증하면 첫 접수는 성공했는데 두 번째 응답은 가격 오류가 된다. 이것은 “같은 작업의 결과를 확인한다”는 시나리오와 모순된다. 따라서 재시도인지 새 작업인지 구분하는 식별과, 과거 접수 결과를 찾아내는 구조가 필요하다. 여기서 멱등 키와 접수 기록의 필요성이 나온다. 먼저 테이블을 만들고 용도를 찾은 것이 아니다.

제2장

가정과 한계를 검토 가능한 명세로 만든다

가정은 단순한 주의 문구가 아니다. 설계 결론을 지지하는 전제다. “판매자는 모든 주문을 볼 수 있다”는 규칙은 단일 매장 가정 아래에서는 타당할 수 있지만 여러 매장에서는 정보 유출이 된다. “금액은 정수로 계산한다”는 규칙은 KRW 전용·정수 가격이라는 전제가 사라지면 다시 검토해야 한다. 가정의 번호가 변경 영향 분석의 시작점이 되는 이유다.

가정 하나를 해부하기: “현재 가격”의 현재는 언제인가

민서의 화면이 보인 시간, 서버가 카탈로그를 읽은 시간, 주문을 저장한 시간, DB가 COMMIT한 시간은 서로 다르다. A07은 서버가 얻은 일관된 카탈로그 스냅샷을 수락 기준으로 정한다. 기대 revision이 이 값과 같으면 그 스냅샷의 단가를 받아들인다. 읽은 직후 가격이 변경되더라도 이미 선택한 수락 조건을 유지한다. 이 규칙은 의미가 정확하고 구현 가능하지만 “COMMIT 순간 가장 최신 가격”과는 다르다.

만약 사업자가 COMMIT 순간의 최신 가격만 허용한다면 외부 카탈로그와 로컬 DB 사이의 원자성을 어떻게 확보할지 새 문제가 생긴다. 가격을 예약하거나 만료 시간이 있는 견적을 발급받거나 동일 저장 경계에서 잠그는 방식이 후보가 된다. 단순히 DB 격리 수준을 높였다는 이유로 외부 시스템의 가격 변경까지 막지는 못한다. 이 한계를 L03으로 기록한다.

왜 총액 입력을 제외하는가

선택한 수량은 구매자의 의도이므로 입력받아야 한다. 접수단가는 서버가 확인할 카탈로그 조건이므로 구매자가 마음대로 지정해서는 안 된다. 총액은 선택한 항목과 확정 단가로 계산할 값이다. 따라서 요청 DTO에 productId·quantity·expectedOfferRevision만 넣는다. buyerId는 인증 주체에서 가져온다. 이 제외 과정이 API 설계의 중요한 부분이다. 데이터 모델에 필드가 있다는 사실은 클라이언트에게 그 필드를 수정할 권한이 있다는 뜻이 아니다.

제4장

외부 스키마에 하나의 보편적인 JSON 표준이 있다고 가정하지 않는다. SQL VIEW, 데이터 사전, 관계대수, 스키마 언어 등으로 표현할 수 있다. 여기서는 읽는 사람이 선택·투영·계산·권한·시간 의미를 빠뜨리지 않도록 교육용 형식을 정의한다. 형식의 구조와 채워진 결과를 구분해서 읽어야 한다.

E00: 상품 선택 관점의 완성

E00의 한 행은 상품 하나다. productId는 사용자가 선택을 제출할 때 가져갈 식별자이고, offerRevision은 사용자가 본 조건을 검증할 토큰이다. 사용자는 두 값의 내부 구조를 해석하지 않는다. 이름과 가격은 화면 표시를 위한 정보다. E00은 카탈로그 경계가 제공하는 데이터에 대한 계약이며 주문 DB에 상품 테이블을 반드시 만들라는 지시가 아니다.

목록에서 판매 가능한 상품을 골랐더라도 접수 순간에는 판매 불가가 될 수 있다. 그러므로 E00이 보여준 결과는 이후 접수 성공의 보증서가 아니다. U01이 다시 확인할 조건을 사용자에게 제공하는 것이다. 판매 가능성의 변화도 revision을 바꿔야 한다는 A07이 이 흐름을 지지한다.

E01: 구매자 상세의 완성

선택·투영·계산의 의미 정의
selected = σ(id = input.orderId ∧ buyerId = actor.id)(Orders)
lines(o) = sort(lineNo)(OrderLines where orderId = o.id)
lineTotal(l) = l.quantity × l.unitPriceKrw
total(o) = Σ lineTotal(l), l ∈ lines(o)
canCancel(o) = o.state = PLACED
E01 = project(orderId, placedAt, state, version, lines, total, canCancel)
      from selected

이 식에서 canCancel에 소유권 비교가 보이지 않는 이유는 selected 단계에서 이미 본인 주문만 남기기 때문이다. 그러나 취소 명령은 이 결과를 믿고 권한 검사를 생략하지 않는다. 읽기와 쓰기 사이에 상태가 바뀔 수 있고, 공격자는 화면을 거치지 않고 요청할 수 있다. 외부 스키마의 필터와 명령의 권한 전제는 같은 정책을 다른 실행 지점에 적용한다.

E01의 version은 업무 사실을 설명하는 필드라기보다 화면의 판단이 어느 상태를 기준으로 했는지 전달하는 기술 토큰이다. 외부 스키마에 나타나는 모든 필드가 개념 엔터티의 업무 속성이어야 하는 것은 아니다. “개념 스키마 + 외부 계약 실행에 필요한 기술 정책”에서 완성된 표현이 나온다는 점을 여기서 확인할 수 있다.

제5장

페이지네이션을 시나리오로 검증하기

대기 목록이 O1, O2, O3 순서이고 한 페이지 크기가 2라면 첫 응답은 O1·O2와 O2의 (placedAt,id)를 포함한 cursor를 반환한다. 다음 요청은 그 키보다 큰 행을 찾는다. 그 사이 O1이 취소되어도 offset이 당겨져 O3을 건너뛰는 문제는 피할 수 있다. 하지만 모든 문제를 해결한 것은 아니다. 접수시각은 커밋시각이 아니므로, 오래 걸린 새 트랜잭션이 나중에 커밋하면서 이미 지나간 cursor 앞에 나타날 수 있다. 이 페이지 순회에서 보이지 않을 수 있으며 새로고침해야 한다. 이것을 L04로 명시한다.

따라서 E02를 “누락 없이 모든 주문을 정확히 한 번 처리하는 작업 큐”라고 부르면 틀리다. 사람이 조회하는 처리 목록이며, 실제 처리는 조건부 확정 명령이 담당한다. 완전한 작업 배분이 필요하다면 claim·lease·작업 상태·복구 시나리오를 새로 설계해야 한다. 읽기 페이지 계약으로 작업 배분 보장까지 얻을 수는 없다.

조회 결과를 역으로 저장할 수 없는 이유

E01에 totalKrw=8,000이 있다고 해서 totalKrw=7,000으로 수정하는 요청을 허용하면, 어떤 항목의 수량이나 단가를 바꿀지 결정할 수 없다. 합은 여러 원본 조합에서 같은 값이 될 수 있다. E02는 취소 주문을 선택 단계에서 버리므로 E02에 없는 주문이 원본 DB에도 없다고 판단할 수 없다. 이런 변환은 일반적으로 역함수가 없다.

뷰 갱신이 단순한 역변환이 아닌 반례
원본 A: 식빵 2 × 3000 + 스콘 1 × 2000 = 8000
원본 B: 식빵 1 × 3000 + 다른 상품 1 × 5000 = 8000

집계 결과 8000만으로 원본 A와 B를 구별할 수 없다.
따라서 setTotal(7000)는 원본 변경을 유일하게 정의하지 못한다.
반면 CancelOrder(orderId, version)는 상태 변화의 의도를 명시한다.

외부 관점 단계의 검토 질문

각 필드를 하나씩 지우면서 사용자가 목적을 달성할 수 있는지 확인한다. version을 지우면 오래된 화면의 변경 충돌을 명시적으로 처리하기 어렵다. buyerId를 지워도 본인 상세 화면은 여전히 동작한다. productName을 지우면 사람이 주문 항목을 알아보기 어렵다. 필드를 추가하는 것보다, 이처럼 필요성과 공개 범위를 설명하는 것이 좋은 외부 스키마의 기준이다.

제6장

세 외부 관점을 하나의 의미 모델로 통합한다

외부 스키마가 완성되면 세 관점에 반복해서 등장하는 사실을 찾는다. E01의 orderId와 E02의 orderId는 같은 주문을 가리킨다. 두 화면의 접수시각도 같은 사실이다. 반면 E00의 unitPriceKrw는 조회 시점의 상품 조건이고 E01의 unitPriceKrw는 수락한 주문 조건이다. 이름이 같다고 하나의 속성으로 통합해서는 안 된다. 통합의 기준은 문자열 일치가 아니라 대상·시점·규칙의 일치다.

외부 요소통합 판단개념 결과판단 근거

개념의 동일성은 값의 같음과 다르다

민서가 같은 빵을 같은 수량으로 두 번 실제 주문한다면 내용은 같아도 주문은 두 개다. 따라서 “구매자·항목·금액이 같음”을 주문 동일성으로 쓰면 안 된다. 반대로 첫 접수의 응답이 유실돼 같은 요청 키로 다시 보낸 경우에는 네트워크 요청은 두 개지만 주문은 하나다. 업무 대상의 식별과 실행 시도의 식별을 구분해야 한다.

상품도 항목의 식별자가 아니다. P1은 여러 주문에 등장한다. 이 사례에서는 한 주문 안에 같은 상품을 한 번만 허용하지만, 항목 번호는 입력 순서에 따른 발생 식별을 담당한다. 개념적 동일성은 (Order,lineNo)로 잡고, (Order,productId)의 유일성을 별도 규칙으로 둔다. 두 키가 현재 모두 유일하다고 의미까지 같아지는 것은 아니다.

개념 스키마의 일관성은 정의한 범위 안의 의미 일관성이다. 전사 모든 시스템을 하나의 거대한 모델로 묶어야 한다는 뜻이 아니다. 외부 참조가 어디서 오는지와 어떤 사실을 신뢰하는지 계약으로 적는 것으로 경계를 유지할 수 있다.

∀ order : distinct(productId in order.lines)
∀ order : line numbers are exactly {1, 2, …, count(order.lines)}

첫 식의 ∃!는 정확히 하나 존재한다는 뜻이다. 이 문장은 자식의 필수 FK로 상당 부분 실현할 수 있다. 두 번째 식의 최소 1개는 FK가 강제하지 못한다. 아무 자식도 없는 부모는 자식 FK를 위반하지 않기 때문이다. 최대 20개는 이 사례에서 lineNo의 1..20 범위와 주문 내 번호 PK를 함께 사용하면 결과적으로 제한된다. 연속 번호는 그 두 제약만으로 보장되지 않는다. 1번과 3번만 있어도 PK·범위 제약은 통과하므로 생성 규칙이 별도로 필요하다.

타입은 프로그래밍 언어 타입보다 먼저다

Quantity가 integer라는 말만으로는 -1과 0을 제외할 수 없다. UnitPrice가 number라는 말만으로는 원·달러·부동소수점 오차를 구별할 수 없다. 의미 타입은 업무에서 허용하는 값의 집합을 정한다. 구현에서는 그 집합을 표현할 수 있는 DB와 언어 타입을 고른다. 이 책의 상한을 곱하면 합계는 최대 1,980,000,000으로 32비트 부호 정수 안이다. JavaScript Number도 이 범위의 정수를 정확히 표현할 수 있다. 이 결론은 상한 가정에 의존한다.

값 제약과 상태 전이 제약은 다르다

state가 세 문자열 중 하나라는 조건은 정적인 값 제약이다. CONFIRMED에서 CANCELLED로 바꿀 수 없다는 조건은 이전 상태와 이후 상태 사이의 관계다. 최종 행만 보는 CHECK는 두 시점 사이의 규칙 전체를 알 수 없다. state=CONFIRMED,version=2인 행을 state=CANCELLED,version=2로 바꿔도 각 값의 범위와 상태·버전 조합은 유효하다. 따라서 허용 전이는 행위와 쓰기 프로토콜에서 보장해야 한다.

U01 접수의 상세 계약

입력은 BUYER actor, requestKey, 항목 배열이다. 서버가 새 주문 ID와 접수 결정 시각을 만든다. 먼저 요청 형식과 중복 상품을 검사하고 표준화한 요청의 fingerprint를 계산한다. 같은 구매자·키가 성공 접수에 이미 연결되어 있으면 fingerprint를 비교한다. 같으면 기존 영수증을 반환하고, 다르면 키 재사용 충돌이다. 새 키인 경우에만 카탈로그 스냅샷을 확인한다.

이 순서는 의미가 있다. 이미 성공한 접수를 다시 확인하는 요청은 현재 가격과 관계없기 때문이다. 가격 확인 후 재시도 여부를 판단하는 구조는 SC06의 계약을 깨뜨릴 수 있다. 새 접수에서는 모든 상품이 판매 가능하고 기대 revision과 같아야 한다. 수락한 이름·단가·revision을 복사하고 PLACED v1 주문을 만든다. 주문·항목·접수 키 기록은 함께 커밋한다. COMMIT 이전에 성공 응답을 보내지 않는다.

U02와 U03의 상세 계약

U02는 BUYER 역할과 소유권을 요구한다. U03는 SELLER 역할을 요구한다. 둘 다 PLACED와 기대 버전 일치를 요구한다. 성공하면 state가 각각 CANCELLED·CONFIRMED가 되고 version은 2가 된다. 항목, 접수 단가, 접수시각, 접수 영수증은 변하지 않는다. 이 상태 그래프에서 허용되는 상태 변화는 한 번뿐이므로 버전 상한 2가 의미 있게 정해진다. 일반적인 시스템에서 버전이 항상 1 또는 2여야 한다는 규칙은 아니다.

완전한 상태 전이 그래프
ConfirmOrder
        PLACED v1 ───────────────→ CONFIRMED v2
           │                            (terminal)
           │ CancelOrder
           ↓
        CANCELLED v2
          (terminal)

no transition: CONFIRMED -> CANCELLED
no transition: CANCELLED -> CONFIRMED
no replay-success contract for repeated cancel/confirm

같은 취소 요청을 반복하면 상태 변경이 다시 일어나지는 않지만 응답은 최초 200과 반복 409로 다를 수 있다. “상태 효과가 중복되지 않는다”와 “동일 응답을 재생한다”를 구분한다. 생성에는 영수증 재생 계약을 선택했고, 상태 변경에는 오래된 버전을 충돌로 알려 다시 조회하게 하는 계약을 선택했다. 두 연산에 같은 재시도 정책을 강제할 필요는 없다.

내부 스키마를 설계하는 형식과 결정 기록

관계형 구조가 정해져도 PostgreSQL이 어떤 타입과 인덱스를 사용해야 하는지는 아직 정해지지 않았다. Identity는 uuid·text·bigint 중 어떤 표현이든 될 수 있다. 시각은 시간대를 포함한 절대 시점인지 로컬 시각인지 결정해야 한다. 읽기 패턴은 어떤 접근 경로를 만들지 결정하는 입력이다. 이 장은 “내부로 변환한다”는 말을 구체적인 설계 필드로 풀어낸다.

인덱스는 어디서 왔는가

E01은 orderId와 buyerId로 검색하지만 orderId가 이미 PK로 유일하므로 먼저 PK로 행 하나를 찾고 소유권을 확인할 수 있다. E01만을 위해 buyer_id 단독 인덱스를 만들 필연성은 없다. E02는 상태가 PLACED인 주문을 (placed_at,id) 순서로 읽으므로 그 조건의 부분 인덱스가 후보가 된다. 주문을 확정·취소하면 인덱스 대상에서 빠지므로 조회 이득과 함께 갱신 비용도 생긴다.

전체 주문 100만 건, 대기 최대 1만 건이라는 A11은 이 후보를 검토할 이유를 제공한다. 실제로 빠른지는 EXPLAIN (ANALYZE, BUFFERS)와 현실적인 데이터·동시 쓰기 부하로 확인해야 한다. 이 책에 실행계획 결과를 만들어 넣지 않았다. 정렬 키를 고른 논리와 측정하지 않은 성능 주장을 구별해야 한다.

타입 정합성은 세 경계에서 검사한다

quantity=99는 API, 도메인, DB에서 모두 허용해야 한다. quantity=100은 셋 모두 거부해야 한다. DB smallint가 100을 표현할 수 있어도 CHECK가 업무 범위를 제한한다. 이름 길이는 Unicode 코드 포인트 수를 기준으로 하며 예제 JavaScript는 [...name].length를 사용한다. 사용자가 보는 글자 덩어리 수와 코드 포인트 수는 다를 수 있다. 이 사례는 자소 정규화나 유니코드 동치까지 처리하지 않는다.

SQL SUM은 bigint 결과를 반환할 수 있고 드라이버가 문자열로 전달할 수 있다. 최대 금액을 검증한 후 Number로 변환해야 한다. DB에서 숫자였다는 이유로 응답 직렬화까지 같은 타입이라고 가정하면 API의 integer 계약을 깨뜨릴 수 있다. 이런 변환은 어댑터의 책임이며 개념의 금액 뜻 자체가 바뀌는 것은 아니다.

제11장

내부 스키마의 실제 결과물: SQL과 보장 범위

아래 SQL은 빈 PostgreSQL 데이터베이스에 이 사례의 저장 구조를 만드는 완전한 초기 DDL이다. 관계형 계획과 정책 파일을 입력받아 함께 제공한 생성기가 출력한다. 테이블 이름만 보여주고 세부 제약을 생략한 의사코드가 아니다. 다만 실제 PostgreSQL 서버에서 실행한 검증 결과는 별도로 표시하며, 기존 운영 DB의 마이그레이션 스크립트라고 부르지 않는다.

생성된 전체 DDL

schema.sql · 전체 원문 ·

schema.sql
-- Generated from a reviewed relational plan + storage policy. PostgreSQL 18.
-- Not a migration. Application-owned rules are listed in the trace.

CREATE TABLE sales_order (
  id uuid NOT NULL,
  buyer_id uuid NOT NULL,
  placed_at timestamptz(3) NOT NULL,
  state text NOT NULL CHECK (state IN ('PLACED','CONFIRMED','CANCELLED')),
  version smallint NOT NULL CHECK (version BETWEEN 1 AND 2),
  PRIMARY KEY (id),
  CHECK ((state = 'PLACED' AND version = 1) OR (state IN ('CONFIRMED','CANCELLED') AND version = 2))
);

CREATE TABLE order_line (
  order_id uuid NOT NULL,
  line_no smallint NOT NULL CHECK (line_no BETWEEN 1 AND 20),
  product_id uuid NOT NULL,
  product_name varchar(100) NOT NULL CHECK (char_length(product_name) BETWEEN 1 AND 100),
  quantity smallint NOT NULL CHECK (quantity BETWEEN 1 AND 99),
  unit_price_krw integer NOT NULL CHECK (unit_price_krw BETWEEN 0 AND 1000000),
  offer_revision varchar(100) NOT NULL CHECK (offer_revision ~ '^[A-Za-z0-9._-]{1,100}$'),
  PRIMARY KEY (order_id, line_no),
  UNIQUE (order_id, product_id),
  FOREIGN KEY (order_id) REFERENCES sales_order (id)
);

CREATE TABLE order_submission (
  buyer_id uuid NOT NULL,
  request_key uuid NOT NULL,
  request_fingerprint char(64) NOT NULL CHECK (request_fingerprint ~ '^[a-f0-9]{64}$'),
  order_id uuid NOT NULL,
  PRIMARY KEY (buyer_id, request_key),
  UNIQUE (order_id),
  FOREIGN KEY (order_id) REFERENCES sales_order (id) DEFERRABLE INITIALLY DEFERRED
);

CREATE INDEX pending_orders_idx ON sales_order (placed_at, id) WHERE state = 'PLACED';

헤더 테이블을 한 줄씩 읽기

sales_order.id는 주문 동일성을 저장하는 UUID다. buyer_id는 인증된 구매자 식별 참조다. 로컬 buyer 테이블이 없으므로 FK를 만들지 않았다. placed_at은 수락 시점으로 고정된다. state와 version의 개별 값 범위를 제한하고, PLACED에는 1, 종결 상태에는 2라는 조합 CHECK를 둔다. 이 CHECK는 잘못된 스냅샷을 줄이지만, CONFIRMED에서 CANCELLED로의 변경을 기억해서 막는 장치는 아니다.

항목 테이블이 보장하는 것

복합 PK(order_id,line_no)는 같은 주문 안의 번호 중복을 막는다. UNIQUE(order_id,product_id)는 같은 상품을 두 줄로 넣는 입력을 저장 수준에서도 막는다. line_no가 1..20이므로 한 주문에 21개 행은 만들 수 없다. 수량과 단가는 범위 CHECK를 가진다. order_id FK는 존재하지 않는 주문에 항목이 연결되는 것을 막는다. 이 조합에도 항목 0개인 주문은 가능하고, 1·3번만 있는 순서도 가능하다. 제약을 나열하는 대신 각각의 논리적 효과를 따져야 한다.

접수 키 테이블의 지연 FK

order_submission의 PK는 구매자와 요청 키의 쌍이다. 다른 구매자가 같은 요청 키를 쓰는 것은 허용한다. order_id UNIQUE는 하나의 주문에 여러 성공 접수 기록이 연결되는 것을 막는다. 이 예제의 쓰기 프로토콜은 주문을 만들기 전에 키를 선점하므로 order_id FK 검사를 트랜잭션 끝으로 미룬다. DEFERRABLE INITIALLY DEFERRED는 FK 검사를 없애는 것이 아니라 커밋 시점까지 주문 행이 생겨야 한다는 뜻이다. 실패한 트랜잭션은 키 선점까지 롤백한다.

이 FK는 submission.buyer_id와 order.buyer_id가 같은지까지 검사하지 않는다. 응용 생성 경로가 동일한 인증 주체로 두 값을 넣는다는 A08에 의존한다. DB에서도 강제하려면 sales_order의 (id,buyer_id) 유일 제약과 해당 쌍을 참조하는 복합 FK 같은 보완을 설계할 수 있다. 이 책의 기본 DDL은 이 보완을 포함하지 않으며 생성 추적표의 미강제 의무에 남긴다.

제12장

내부 기록을 외부 스키마로 다시 투영한다

외부 스키마와 내부 스키마가 연결된다는 것을 보여주려면 실제 조회 매핑이 있어야 한다. E01은 주문 하나를 선택하고 그 주문의 항목을 번호 순서로 모으며 금액을 합산한다. 쿼리 결과와 API JSON 사이에는 이름·시각·숫자 표현을 변환하는 어댑터가 존재한다. 이 어댑터를 생략하고 테이블 행을 그대로 반환하면 공개 범위가 무너진다.

-- Q01: Buyer detail. $1 order UUID, $2 trusted buyer UUID.
-- One SQL statement gives header, items and amount the same statement snapshot.
SELECT o.id AS order_id, o.placed_at, o.state, o.version,
       (o.state = 'PLACED') AS can_cancel,
       SUM(l.quantity::bigint * l.unit_price_krw) AS total_krw,
       jsonb_agg(jsonb_build_object(
         'lineNo',l.line_no,'productId',l.product_id,'productName',l.product_name,
         'quantity',l.quantity,'unitPriceKrw',l.unit_price_krw,
         'lineTotalKrw',l.quantity::bigint*l.unit_price_krw
       ) ORDER BY l.line_no) AS lines
FROM sales_order o JOIN order_line l ON l.order_id=o.id
WHERE o.id=$1 AND o.buyer_id=$2
GROUP BY o.id;

-- Q02: Seller pending page. Application verifies SELLER first.
-- $1 after time or NULL; $2 after id or NULL; both absent or both present.
-- $3 requested limit 1..100. Read limit+1 to decide whether another page exists.
WITH page AS (
 SELECT id, placed_at, version FROM sales_order
 WHERE state='PLACED'
   AND ($1::timestamptz IS NULL OR (placed_at,id)>($1::timestamptz,$2::uuid))
 ORDER BY placed_at,id LIMIT ($3::integer+1)
)
SELECT p.id AS order_id,p.placed_at,p.version,
       SUM(l.quantity::bigint*l.unit_price_krw) AS total_krw,
       jsonb_agg(jsonb_build_object(
         'lineNo',l.line_no,'productId',l.product_id,'productName',l.product_name,
         'quantity',l.quantity,'unitPriceKrw',l.unit_price_krw,
         'lineTotalKrw',l.quantity::bigint*l.unit_price_krw
       ) ORDER BY l.line_no) AS lines
FROM page p JOIN order_line l ON l.order_id=p.id
GROUP BY p.id,p.placed_at,p.version ORDER BY p.placed_at,p.id;
-- Return the first limit rows. If an extra row exists, encode the last RETURNED
-- row's (placed_at,id) as nextCursor. Otherwise nextCursor=null.
-- Driver bigint SUM may be a string: validate the proven bound before Number conversion.

-- W01: Claim creation key inside the same transaction as Order and OrderLine inserts.
-- $1 buyer UUID, $2 request key, $3 canonical SHA-256 lowercase hex, $4 candidate order UUID.
INSERT INTO order_submission(buyer_id,request_key,request_fingerprint,order_id)
VALUES($1,$2,$3,$4)
ON CONFLICT (buyer_id,request_key) DO NOTHING RETURNING order_id;
-- 1 row: claim won, read catalog snapshot, construct Order, insert header + ALL lines, commit.
-- 0 rows: another committed acceptance owns key. Fetch in a NEW statement below.
-- FK is deferred so candidate order may be inserted later within this transaction.

-- W02: In a fresh READ COMMITTED statement after the key claim returned 0 rows.
SELECT request_fingerprint,order_id FROM order_submission
WHERE buyer_id=$1 AND request_key=$2;
-- Fingerprint differs -> 409 and rollback; same -> load historical receipt and commit.
-- No repricing and no second order. Rollback removes a failed fresh claim.

-- W03: Buyer cancellation. $1 order id; $2 trusted buyer; $3 expectedVersion.
UPDATE sales_order SET state='CANCELLED',version=2
WHERE id=$1 AND buyer_id=$2 AND state='PLACED' AND version=$3
RETURNING id,state,version;
-- 1 row -> success. 0 rows -> no success; ownership-filtered read distinguishes 404/409.

-- W04: Seller confirmation. Role checked by application BEFORE this statement.
UPDATE sales_order SET state='CONFIRMED',version=2
WHERE id=$1 AND state='PLACED' AND version=$2
RETURNING id,state,version;
-- 1 row -> success. 0 -> 404 if absent, otherwise 409. Never retry by removing predicates.

E02는 limit+1을 읽는 이유

클라이언트가 20개를 요구할 때 21개까지 읽어야 뒤에 더 있는지 판단할 수 있다. 21번째가 있으면 첫 20개만 반환하고, 20번째의 정렬 키를 다음 cursor로 만든다. 21번째를 cursor로 쓰면 그 행을 건너뛴다. SQL의 GROUP BY는 이 페이지 후보 주문들에 항목을 붙인 뒤 각각의 금액과 배열을 만든다. 페이지 결과의 모든 주문은 같은 쿼리 스냅샷을 기준으로 PLACED였지만 클라이언트가 클릭할 때도 PLACED라는 보장은 없다.

cursor의 base64url은 암호화나 접근권한이 아니다. 사용자가 디코딩하거나 바꾸더라도 서버는 시각·UUID 형식을 검증하고 SELLER 권한과 상태 필터를 별도로 적용해야 한다. 오프셋·커서 선택은 전송 표현과 조회 정책의 결정이며 주문의 개념적 동일성이 아니다.

외부 스키마는 DB VIEW여야 하는가

반드시 그렇지는 않다. SQL VIEW로 일부 투영을 고정할 수도 있고, 파라미터 쿼리와 응용 어댑터로 제공할 수도 있다. 이 책에서는 actor 기반의 조건과 JSON 조립을 명확하게 보이기 위해 파라미터 SQL을 사용한다. 외부 스키마는 사용자가 보는 데이터의 의미를 정의하는 수준이며 구현 방식은 별도 선택이다.

제13장

접수·재시도·경쟁을 트랜잭션으로 실현한다

DDL은 가능한 저장 상태의 일부를 제한한다. 어떤 순서로 저장하고 어떤 실패에서 롤백할지는 별도 프로토콜이다. SC01과 SC06을 동시에 만족하려면 “키가 없으면 주문 생성”이라는 두 단계 문장만으로는 부족하다. 두 요청이 동시에 “키 없음”을 읽을 수 있기 때문이다. 유일 제약을 가진 키 행 삽입을 경쟁의 판정 지점으로 사용한다.

항목 삽입 중 실패한 경우

키 행과 주문 헤더, 첫 번째 항목까지 삽입하고 두 번째 항목에서 오류가 발생했다고 하자. 성공 응답을 보내지 않고 트랜잭션 전체를 롤백한다. DB 밖에서 발급한 UUID 자체를 되돌릴 필요는 없지만, 그 ID를 성공 주문이라고 알려서는 안 된다. 원자성은 “아무 일도 일어난 적 없다”는 형이상학적 의미가 아니라 이 작업의 영속 상태가 부분 성공으로 남지 않는다는 의미다.

보장의 범위

한 주문 행을 대상으로 한 조건부 변경과 유일 키 선점은 이 사례에 맞는 방법이다. 재고 여러 행의 합계·계좌간 전역 한도·서로 다른 저장소의 원자성까지 자동으로 해결하지는 않는다. 더 넓은 불변식에는 추가 잠금·직렬화·보상 설계가 필요하다.

지원하지 않는 것을 중단하는 것이 왜 중요한가

개념 모델에 다중 통화가 추가되었는데 생성기가 모르는 Money 타입을 text로 대충 바꾸면 문법상 유효한 SQL이 나올 수 있다. 하지만 금액 비교·정렬·계산의 의미가 사라진다. 생성 실패는 불편해도 명시적인 실패다. 아무 경고 없이 규칙을 누락한 성공 출력은 더 위험하다. 이 생성기는 지원하는 타입과 구조를 제한하고, 모르는 입력이나 미결정 책임에서 중단한다.

동시에 이 생성기를 범용 모델 컴파일러라고 과장해서도 안 된다. 임의의 상속·시간 구간·다대다·사용자 수식을 처리하지 않으며, 모든 불변식의 논리적 일관성을 증명하지 않는다. 입력 형식의 지원 영역과 출력의 보장 범위를 명시하는 것이 자동화의 정직한 사용이다. 사람이 모든 정책을 확정한 뒤에는 반복적인 SQL 전사 오류를 줄이는 실질적인 가치가 있다.

  acceptanceReceipt(){return {orderId:this.#data.id,acceptedAt:this.#data.placedAt,acceptedTotalKrw:this.totalKrw};}
  buyerView(actorId){if(uuid(actorId)!==this.#data.buyerId)fail('NOT_FOUND');return {...this.pendingView(),state:this.#data.state,canCancel:this.#data.state==='PLACED'};}
  pendingView(){return {orderId:this.#data.id,placedAt:this.#data.placedAt,version:this.#data.version,lines:this.#data.lines.map(({offerRevision,...l})=>({...l,lineTotalKrw:l.quantity*l.unitPriceKrw})),totalKrw:this.totalKrw};}
}

canonicalRequest는 요청 항목을 명시된 배열 튜플로 표준화한다. 객체 프로퍼티의 입력 순서가 달라도 같은 의미의 요청을 같은 문자열로 만든다. 항목 배열 순서는 lineNo를 결정하므로 의미 있는 차이로 유지한다. UUID는 소문자로 통일한다. 이 문자열의 SHA-256을 응용 어댑터가 계산한다. 해시 충돌 가능성이 사실상 무시할 만큼 작다는 기술 전제를 사용하며, 원문 완전 동일성의 수학적 증명이라고 표현하지 않는다.
복원은 새 주문 생성과 다르다
저장된 CANCELLED v2 주문을 읽을 때 place를 다시 호출하면 PLACED v1이 되어 버린다. 현재 카탈로그를 조회해 다시 단가를 채우면 과거 가격도 바뀐다. rehydrate는 저장 스냅샷의 구조·범위·상태 조합을 검증하되 현재 카탈로그를 참조하지 않는다. 저장값이 잘못되면 조용히 고치지 않고 오류를 내야 데이터 손상을 알아차릴 수 있다. 외부 요청에서 arbitrary snapshot을 받아 rehydrate에 넣는 경로는 제공하지 않는다.
동결이 DB 불변성을 보장하지는 않는다
snapshot과 내부 lines는 동결되어 있으므로 호출자가 quantity를 바꾸어 객체의 규칙을 우회할 수 없다. 하지만 DB 관리자가 SQL로 값을 바꾸는 것은 이 객체가 막을 수 없다. 메모리 안의 불변성, 응용 쓰기 경로의 불변성, 저장소 전체의 불변성을 구분해야 한다. 이 책은 앞의 둘을 설계하고, 세 번째는 A08에 의존하는 제한을 명시한다.
책임을 분리한 취소 흐름
계층별 실행 계약
HTTP adapter:
  validate request shape -> authenticate -> require BUYER
Application service:
  load owned order snapshot (missing or not-owned -> NotFound)
  order = Order.rehydrate(snapshot)
  originalVersion = snapshot.version
  order.cancel(request.expectedVersion)
Repository:
  UPDATE ... WHERE id=? AND buyer_id=?
    AND state='PLACED' AND version=request.expectedVersion
  if affectedRows != 1: return Conflict/NotFound policy
Application service:
  only after commit -> return {orderId, state:'CANCELLED', version:2}

메모리 전이 성공은 저장 성공의 증거가 아니다.
저장 실패한 객체를 성공 응답·캐시·이벤트에 사용하지 않는다.
pendingView와 buyerView는 실행 실습을 위해 같은 파일에 둔 투영 도우미다. 큰 시스템에서는 외부 DTO 조립을 응용 계층 mapper로 분리할 수 있다. 핵심은 저장 필드 전체를 그대로 내보내지 않고 정의한 E01·E02의 구조를 명시적으로 만드는 것이다. pendingView를 호출했다고 SELLER 인증이 수행되지는 않는다. 역할 검사는 응용 계층의 책임이다.
제17장
외부 관점·행위·개념을 API 계약으로 바꾸는 과정
API를 만들 때 입력은 개념 스키마 하나가 아니다. 개념 스키마는 값과 관계의 의미를 제공하고, 외부 스키마는 누가 무엇을 보아야 하는지 제공하며, 행위 명세는 무엇을 요청하고 어떤 결과를 받아야 하는지 제공한다. 여기에 HTTP 경로·상태 코드·인증 방식·재시도 규약이라는 전송 결정을 추가한다. 같은 업무 의미도 HTTP가 아닌 메시지나 CLI로 제공할 수 있으므로 전송 형식은 별도 선택이다.

요청 DTO를 만드는 실제 추론
U01은 사용자 선택을 받으므로 productId·quantity를 입력에 넣는다. 사용자가 본 조건을 확인해야 하므로 expectedOfferRevision을 추가한다. buyerId는 인증에서 가져오므로 제외한다. productName·unitPriceKrw는 서버 스냅샷에서 가져오므로 제외한다. totalKrw와 state는 서버가 산출하므로 제외한다. 이런 식으로 각 필드의 입력 권한을 판정하면 “테이블에 있으니 요청에도 있다”는 잘못된 복사를 피할 수 있다.

응답 구조를 고르는 실제 추론
최초 접수 응답은 주문의 현재 상태 전체가 아니라 역사적 접수 영수증이다. orderId·acceptedAt·acceptedTotalKrw만 포함한다. SC06에서 주문이 이미 확정된 뒤 재시도하더라도 영수증은 변하지 않는다. 현재 상태는 GET 상세로 확인한다. 만약 최초 PLACED 상태 전체를 재생한다면 그 값이 과거 상태임을 응답 의미에 명확히 표시해야 한다. 이 책은 혼동을 줄이기 위해 영수증을 분리했다.

상태 코드 선택은 이 API의 정책이다. 동일한 개념 모델에서 다른 오류 표현을 선택할 수도 있다. 중요한 것은 클라이언트가 무엇을 수정하거나 재시도해야 하는지 구별할 수 있고, 서버가 실제로 이 계약을 구현하는 것이다. security 선언이나 description 문구는 권한 검사 코드의 대체물이 아니다.
API Spec의 구조적 형식
이번 산출물은 임의 JSON 양식이 아니라 OpenAPI 3.1.1을 사용한다. info는 계약의 이름과 버전을, paths는 연산을, parameters·requestBody는 입력을, responses는 결과를, components.schemas는 구조를 정의한다. x-source-ids는 표준 확장 필드를 이용한 추적 정보다. OpenAPI 문법이 표현하지 못하거나 자동 검증하지 않는 교차 필드 규칙은 설명과 서버 검증에 남긴다. 공식 명세를 기준으로 작성했다.
제18장

제20장
API·도메인 모델을 내부 스키마에서 뽑는다는 주장을 평가한다
이 질문은 “가능하다/불가능하다” 하나로 답하면 부정확하다. DB 테이블에서 ORM 클래스를 생성하는 일은 가능하다. 테이블 CRUD API를 생성하는 것도 가능하다. 그러나 그것이 우리가 앞에서 설계한 외부 정보 계약이나 업무 행위를 가진 도메인 모델을 논리적으로 복원했다는 뜻은 아니다. 역변환에 필요한 정보가 저장 구조에 남아 있는지 확인해야 한다.
비유 대신 반례로 증명하기
역함수가 존재하지 않는 이유
저장 구조 S:
  order(id, buyer_id, state)
  state ∈ {PLACED, CONFIRMED, CANCELLED}

업무 모델 M1: PLACED에서만 취소 가능.
업무 모델 M2: CONFIRMED에서도 점원 승인 뒤 취소 가능.
업무 모델 M3: 구매자는 취소 불가, 판매자만 취소 가능.

세 모델 모두 같은 저장 구조 S와 양립한다.
f(M1)=S, f(M2)=S, f(M3)=S가 가능하다.
S만 주어져서는 원래 모델이 무엇인지 유일하게 결정할 수 없다.
정보를 더 넣으면 역공학에 도움이 된다. 트리거가 종결 상태 변경을 막는다면 상태 규칙 일부를 알 수 있다. 저장 프로시저가 소유권을 검사한다면 권한 정책 일부를 알 수 있다. 하지만 프런트엔드와 응용 코드·운영 절차에만 있는 정책도 있을 수 있다. 따라서 스키마만으로 충분하다는 주장 대신 실제로 읽은 근거와 아직 가설인 부분을 구분해야 한다.

개념 + 행위 + 외부 관점API·도메인 설계의 의미적 근거플랫폼·계층·전송·일관성 경계의 선택
DB 중심 API가 정당한 경우
관리용 데이터 브라우저처럼 저장 구조를 그대로 조작하는 것이 명시적인 목적일 수 있다. 이 경우 테이블 CRUD 생성은 목적에 맞는다. 접근권한과 제약을 검증하고 이 API가 DB 구조에 결합된 계약임을 인정하면 된다. 모든 API가 반드시 풍부한 도메인 모델에서 출발해야 한다는 뜻은 아니다. 문제는 CRUD 생성 결과를 업무 유스케이스의 설계까지 자동으로 해결한 것처럼 설명하는 데 있다.
권장하는 의존 관계를 식으로 다시 쓰기
도출의 근거와 추가 결정

DB -> API -> domain으로만 직렬 배치할 이유는 없다.
이미 존재하는 DB에서 시작해야 한다면 위 방향을 억지로 거꾸로 고집할 필요도 없다. 스키마·샘플 데이터·코드에서 개념 후보를 수집하고, 업무 담당자에게 시나리오와 반례를 확인한 뒤 명세를 복원한다. 이것은 역공학과 검증의 반복이며, 기계적으로 확정된 의미 추출과는 다르다.
제21장

변경 1: 확정 후에도 취소 허용
A03과 R02가 바뀐다. 현재 버전 상한 2는 더 이상 맞지 않으며 CONFIRMED v2 → CANCELLED v3 같은 전이를 설계해야 한다. 추가 승인이 필요한지, 점원이 이미 처리한 주문은 어떻게 되는지 새 시나리오를 만든다. Order.cancel의 조건, API 충돌 의미, UPDATE의 허용 상태, DB version 범위·state/version 조합 CHECK가 함께 바뀐다. 접수 영수증은 불변의 최초 수락 사실이므로 바뀌지 않을 수 있다.

변경 5: “DB만으로 모든 규칙을 보장하라”
A08의 단일 쓰기 경로 가정을 줄이려면 불변 항목 UPDATE/DELETE를 차단하고, 종결 상태 간 전이를 검사하고, 트랜잭션 끝의 최소 항목 수를 검증하는 DB 설계가 필요하다. 지연 제약 트리거, 쓰기 함수에 대한 권한 제한, 직접 테이블 권한 회수 등이 후보가 된다. 트리거가 여러 테이블을 확인할 때 동시 삭제·삽입과 잠금 순서를 검토해야 한다. 객체에서 검사했다는 설명을 DB 보장으로 바꿔 부를 수 없다.

제22장
연습 문제와 풀이: 외워서가 아니라 설계해서 답하기
각 문제는 먼저 직접 답한 뒤 풀이를 펼쳐보는 것이 좋다. 정답은 테이블 이름을 맞추는 것이 아니라 의미·가정·추가 결정·검증 사례를 연결하는 것이다. 여러 설계가 가능할 때는 아래 풀이가 하나의 정당화된 선택임을 기억한다.
문제 1. 주문 항목에 상품명을 저장하는 것은 정규화 위반인가?
상품 이름이라는 말만으로 판단할 수 없다. 현재 상품 이름이라면 ProductId가 이름을 결정할 수 있고 중복 저장의 갱신 문제가 생긴다. 여기서는 접수 당시 이름이며 같은 상품도 다른 주문에서 다른 이름으로 수락될 수 있다. 따라서 ProductId만으로 이 역사적 이름이 결정되지 않는다. 주문 항목에 수락 이름을 기록하는 것은 요구 의미를 보존하기 위한 선택이다. 상품 변경 후 조회라는 SC02 반례로 검증한다.


문제 2. FK와 NOT NULL을 넣으면 빈 주문을 막을 수 있는가?
아니다. FK는 존재하는 항목이 유효한 주문을 참조하는지 검사한다. 아무 항목도 없는 주문에는 검사할 자식 FK가 없다. 생성자가 1..20항목을 확인하고 헤더·항목을 한 트랜잭션으로 저장하며 삭제 우회 경로를 막아야 한다. DB 전체 보장이 필요하면 커밋 시점의 자식 수를 검사하는 별도 설계를 추가한다.


문제 3. 같은 요청 키로 항목 순서만 바꾸면 같은 요청인가?
이 계약에서는 아니다. 입력 순서가 lineNo와 출력 순서를 결정하므로 순서도 요청 의미에 포함된다. 순서가 업무적으로 무의미하다고 합의한다면 canonicalization에서 productId 순으로 정렬하는 정책을 선택할 수 있지만, 그때 생성 규칙과 API 설명도 함께 바꿔야 한다. 단순 JSON 문자열 비교 대신 명시적인 표준 표현을 쓰는 이유다.


문제 4. canCancel=true 응답을 받은 뒤 취소가 409라면 버그인가?
반드시 그렇지는 않다. canCancel은 조회 시점의 안내이며 판매자가 그 사이 확정할 수 있다. version을 포함해 변경 명령이 자신의 판단 근거를 전달하고 서버가 다시 검사해야 한다. 반대로 아무 동시 변경도 없는데 409가 나면 상태·버전 전달·저장 매핑을 조사해야 한다. 현재 계약은 버튼의 표시를 미래의 실행 성공 보장으로 정의하지 않았다.


문제 5. 내부 DB의 UUID를 TEXT로 바꾸면 API도 바뀌어야 하는가?
반드시 아니다. TEXT에 동일한 UUID 형식을 저장하고 어댑터가 계약을 유지하면 공개 식별 표현은 바뀌지 않는다. 하지만 DB가 더 이상 UUID 타입 검사를 하지 않으므로 형식 강제 위치가 바뀐다. 내부 표현 변경과 공개 의미 변경을 분리하되, 데이터 검증 책임이 사라지지 않도록 해야 한다.


문제 6. 이미 확정된 주문의 생성 요청을 재시도하면 state=PLACED를 응답해야 하는가?
우리 생성 응답에는 현재 state를 넣지 않는다. orderId·acceptedAt·acceptedTotalKrw라는 역사적 접수 영수증을 재생한다. 현재 상태는 상세 조회로 얻는다. 만약 전체 최초 응답을 캐시하는 계약을 택했다면 과거 응답이라는 의미를 명확히 해야 한다. 이것은 DB에서 저절로 나오는 규칙이 아니라 SC06을 만족하기 위해 선택한 API 정책이다.


문제 7. 항목을 JSON으로 저장하면 개념 스키마가 달라지는가?
같은 Order·OrderLine의 의미와 규칙을 표현한다면 반드시 달라지지는 않는다. 저장 매핑, 제약 강제 방법, 조회·인덱스·동시성 검증이 달라진다. JSON이라서 개념 관계가 없어지는 것도 아니고, 별도 테이블이라서 독립 집합체가 되는 것도 아니다. 같은 의미에 대해 둘 이상의 물리 표현이 가능하다는 반례다.


문제 8. OrderLine이 20개이고 각 수량 99, 단가 1,000,000이면 안전한가?
합은 1,980,000,000으로 32비트 부호 정수 최대값보다 작고 JS 안전 정수 범위 안이다. 하지만 단일 곱·합·DB 반환 타입·JSON 직렬화를 모두 확인해야 한다. 수량 상한을 999로 바꾸면 19,980,000,000이 되어 32비트 합계 열에는 들어가지 않는다. 현재 설계는 총액을 저장하지 않지만 미래 저장 정책과 API 범위도 재검토해야 한다.


문제 9. 도메인 객체 테스트가 통과하면 동시 취소·확정도 안전한가?
아니다. 서로 다른 프로세스의 객체가 모두 PLACED v1을 가지고 있으면 각 객체의 전이는 합법적이다. 저장 시 조건부 UPDATE나 다른 동시성 제어가 없으면 마지막 쓰기가 앞 결과를 덮어쓴다. 객체 단위 테스트와 실제 DB 두 세션 경쟁 테스트는 서로 다른 주장을 검증한다.


문제 10. 판매자 목록에서 모든 주문을 정확히 한 번 처리할 수 있는가?
이 페이지 계약만으로는 안 된다. 목록은 조회할 때마다 변하고 커서 앞에 늦게 커밋한 행이 나타날 수 있다. 처리 성공은 별도 상태 변경의 조건부 저장으로 결정한다. 정확한 작업 배분·재시도·복구가 요구되면 claim과 lease 같은 새로운 업무·기술 시나리오를 설계해야 한다.
종합 실습: 부분 취소를 추가하라
새 시나리오를 “식빵 두 개 중 한 개만 취소한다”로 정하고, 상태와 금액이 무엇을 의미하는지 먼저 적어보라. 기존 항목을 고치는지, 취소량을 별도 기록하는지, 원래 접수금액과 현재 유효금액을 나누는지 결정해야 한다. 결제가 없다는 A02 아래에서도 원래 접수 사실과 변경 이력을 구분할 필요가 생긴다. 각 설계의 E01 결과·개념 규칙·DB 구조·도메인 행위·API 요청을 하나씩 작성해야 완료다.
종합 실습의 풀이 방향
한 선택은 접수 항목을 그대로 두고 CancellationLine을 추가하는 것이다. 취소 수량 합이 접수 수량을 넘지 않는 불변식을 정의하고, 현재 유효수량=접수수량−취소수량으로 계산한다. API는 lineNo와 quantity를 가진 부분 취소 명령을 제공하고, 도메인은 같은 주문 경계에서 잔량을 검사하며, DB는 주문 버전을 비교해 여러 취소가 경쟁해도 합계가 초과하지 않도록 저장한다. 원래 접수 영수증은 여전히 불변이다. 새 개념이 생겼으므로 기존 세 상태만으로 충분한지도 다시 검토한다. 이것은 유일한 해법은 아니지만 원래 사실을 보존한다는 선택과 연결되어 있다.
