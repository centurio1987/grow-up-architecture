헥사고날 포트와 어댑터 구분
Ports & Adapters

헥사고날 아키텍처에서 무엇이 포트이고 무엇이 어댑터인가

구상 서비스, 컨트롤러, 리포지토리 인터페이스가 각각 어느 자리에 속하는지 정리합니다. 판단 기준은 하나입니다. 헥사곤 안쪽인가, 바깥쪽인가.

세 질문에 대한 짧은 답

구상 서비스와 인프라 구상 클래스는 둘 다 어댑터인가?

아닙니다. 인프라 구상 클래스(JpaOrderRepository)는 피주도 어댑터가 맞습니다. 하지만 구상 서비스(OrderService)는 주도 포트를 구현하는 헥사곤 내부, 애플리케이션 코어 자체이고 어댑터가 아닙니다.

컨트롤러는 어디에 해당하나?

주도(Primary/Driving) 어댑터입니다. HTTP 요청을 유스케이스 호출로 번역하는 바깥쪽 부품이며, 메시지 컨슈머·CLI·스케줄러·테스트 코드도 같은 자리에 섭니다.

리포지토리를 도메인이 아니라 구상 서비스가 쓴다면 분류가 달라지나?

달라지지 않습니다. 헥사고날은 애플리케이션 서비스와 도메인 모델을 모두 “헥사곤 안쪽”으로 묶습니다. 안쪽 누군가가 바깥 세계를 부르기 위해 정의한 인터페이스면 사용자가 서비스든 도메인이든 피주도 포트입니다.

한 장으로 보는 배치

구성 요소별 분류

구성 요소위치하는 일분류

1. 구상 서비스는 왜 어댑터가 아닌가

어댑터는 바깥 기술과 코어 사이를 번역하는 부품입니다. 컨트롤러는 HTTP를, JPA 리포지토리는 SQL을 코어의 언어로 바꿉니다. 그래서 어댑터는 교체 대상입니다. REST를 gRPC로, MySQL을 MongoDB로 바꿀 때 어댑터만 갈아 끼웁니다.

OrderService는 번역하지 않습니다. “주문을 받으면 재고를 확인하고, 결제를 요청하고, 주문을 저장한다”는 애플리케이션의 동작 그 자체입니다. 이것을 갈아 끼우면 애플리케이션이 다른 애플리케이션이 됩니다. 주도 포트를 구현한다는 형태가 어댑터와 비슷해 보여도, 구현하는 쪽이 헥사곤 안에 있으므로 코어로 분류합니다.

구분 기준: 그 클래스가 특정 기술(HTTP, JPA, Kafka, SDK)을 import 하는가? 하면 어댑터, 하지 않으면 코어입니다. OrderService가 EntityManager나 HttpServletRequest를 알고 있다면 그 자체가 설계 결함입니다.

2. 컨트롤러는 주도 어댑터

코어를 “주도하는(driving)” 쪽, 즉 먼저 호출을 시작하는 쪽이 주도 측입니다. 컨트롤러는 요청을 받아 PlaceOrderUseCase를 호출하므로 주도 어댑터입니다. 같은 포트에 여러 어댑터가 붙을 수 있습니다. 위 그림처럼 OrderController와 OrderConsumer가 같은 유스케이스를 호출하고, 테스트 코드도 하나의 주도 어댑터로 볼 수 있습니다.

질문에서 정리하신 대로 DIP가 꼭 필요한 곳은 피주도 측입니다. 주도 측은 호출 방향(컨트롤러 → 서비스)과 의존 방향이 이미 안쪽을 향하므로 역전할 것이 없습니다. 주도 포트 인터페이스는 경계를 명시하고 여러 어댑터·테스트가 같은 계약을 쓰게 하는 용도이며, 구현이 하나뿐인 프로젝트에서는 컨트롤러가 구상 서비스를 직접 참조해도 의존 방향 규칙은 깨지지 않습니다.

3. 리포지토리를 서비스가 써도 피주도 포트다

헥사고날 아키텍처는 원래 안과 밖, 두 영역만 구분합니다. 코어 내부를 애플리케이션 서비스와 도메인 모델로 나누는 것은 DDD·클린 아키텍처에서 가져온 추가 구분이고, 포트 분류에는 영향을 주지 않습니다. “secondary port는 도메인이 인프라에 접근하는 인터페이스”라는 정의를 “코어가 바깥에 접근하는 인터페이스”로 넓혀 읽으면 모순이 사라집니다.

실행 흐름은 밖으로 나가지만 소스 의존은 안쪽을 향합니다. DIP가 이 두 방향을 갈라 놓습니다.

실행 흐름 (런타임 호출 순서)
OrderController→ OrderService→ JpaOrderRepository→ DB
소스 코드 의존 (import 방향)
OrderController→ PlaceOrderUseCase← OrderService→ OrderRepository← JpaOrderRepository

도메인 엔티티가 리포지토리를 쓰지 않는 것이 오히려 정상입니다

  • Order 같은 엔티티는 포트 없이 순수한 규칙만 갖는 편이 테스트하기 좋습니다. 저장·조회 같은 I/O 조율은 애플리케이션 서비스의 몫입니다.
  • 도메인 서비스가 포트를 쓰는 경우도 있습니다(예: 환율을 가져오는 ExchangeRateProvider). 그때도 분류는 똑같이 피주도 포트입니다.
  • 포트의 주인은 사용하는 쪽(코어)입니다. 인터페이스 시그니처는 Order, OrderId 같은 도메인 타입으로 쓰고, JPA 엔티티나 ResultSet 같은 기술 타입이 새어 나오면 안 됩니다.

인터페이스를 어느 패키지에 둘까

두 방식 모두 쓰입니다. DDD 쪽에서는 리포지토리를 “애그리거트의 컬렉션”이라는 도메인 개념으로 보고 domain 패키지에 두고, 헥사고날을 엄격히 따르는 쪽(예: Get Your Hands Dirty on Clean Architecture)은 application/port/out에 둡니다. 어느 쪽이든 헥사곤 안에 있고 바깥 어댑터가 그것을 구현한다는 점은 같습니다. 팀 안에서 한 가지로 통일하면 충분합니다.

코드로 보면

order/
├─ adapter/
│  ├─ in/web/OrderController.java             // 주도 어댑터
│  └─ out/persistence/JpaOrderRepository.java  // 피주도 어댑터
├─ application/
│  ├─ port/in/PlaceOrderUseCase.java          // 주도 포트
│  ├─ port/out/OrderRepository.java           // 피주도 포트
│  └─ service/OrderService.java               // 헥사곤 내부 (어댑터 아님)
└─ domain/
   └─ Order.java, Money.java                   // 헥사곤 내부
주도 어댑터 → 주도 포트 
// adapter/in/web
@RestController
class OrderController {
  private final PlaceOrderUseCase placeOrder;

  @PostMapping("/orders")
  OrderResponse place(@RequestBody OrderRequest req) {
    OrderId id = placeOrder.place(req.toCommand());
    return new OrderResponse(id.value());
  }
}
주도 포트 
// application/port/in
public interface PlaceOrderUseCase {
  OrderId place(PlaceOrderCommand command);
}
피주도 포트 
// application/port/out
public interface OrderRepository {
  void save(Order order);
  Optional<Order> findById(OrderId id);
}
코어: 주도 포트를 구현하고 피주도 포트를 사용 
// application/service
@Transactional
class OrderService implements PlaceOrderUseCase {
  private final OrderRepository orders;
  private final PaymentGateway payments;

  public OrderId place(PlaceOrderCommand cmd) {
    Order order = Order.create(cmd.lines()); // 도메인 규칙
    payments.charge(order.total());
    orders.save(order);
    return order.id();
  }
}
피주도 어댑터 → 피주도 포트 
// adapter/out/persistence
@Repository
class JpaOrderRepository implements OrderRepository {
  private final SpringDataOrderJpa jpa;
  private final OrderMapper mapper;

  public void save(Order order) {
    jpa.save(mapper.toEntity(order));
  }
  public Optional<Order> findById(OrderId id) {
    return jpa.findById(id.value()).map(mapper::toDomain);
  }
}

정리

  • 어댑터는 헥사곤 바깥에서 기술을 번역하는 클래스입니다. 컨트롤러는 주도 어댑터, 인프라 구현체는 피주도 어댑터입니다.
  • 구상 서비스는 주도 포트를 구현하지만 헥사곤 안쪽의 애플리케이션 코어이며 어댑터가 아닙니다.
  • 포트는 코어가 소유하는 경계 인터페이스입니다. 코어 안의 누가 쓰든(서비스든 도메인 서비스든) 바깥으로 나가는 인터페이스는 피주도 포트입니다.
  • DIP가 실질적으로 작동하는 곳은 피주도 측입니다. 실행은 밖으로 나가고, 의존은 안으로 들어옵니다.
