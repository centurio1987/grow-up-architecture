## 16장 유스케이스와 사용자 스토리

이 장을 마치면 Cockburn 형식의 유스케이스를 칸별로 원장과 계약에 옮기고, 특히 **최소 보장**과 **성공 보장**을 계약의 사후조건으로 바꿀 수 있어요. 잘게 나뉜 사용자 스토리 묶음에서 공통 개념을 찾아 합치는 방법도 다룹니다.

### 유스케이스: Cockburn의 형식

유스케이스 작성법의 대표 문헌은 Alistair Cockburn의 『Writing Effective Use Cases』(Addison-Wesley, 2000년 10월 출간, 저작권 표기 2001)입니다. 이 책이 말하는 "fully dressed"(빠짐없이 갖춘) 유스케이스의 항목은 위키백과가 책 120쪽을 근거로 다음처럼 나열해요. 책 본문의 템플릿 쪽은 직접 보지 못했고 이 2차 자료로 확인했습니다.

| 항목 | 뜻 |
| --- | --- |
| Title | 능동 동사로 쓴 목표 이름 |
| Primary Actor | 목표를 가진 주 행위자 |
| Goal in Context | 맥락 속의 목표 |
| Scope | 설계 범위(어느 시스템을 다루는가) |
| Level | 목표 수준 |
| Stakeholders and Interests | 이해관계자와 각자의 관심사 |
| Precondition | 시작할 때 이미 참이라고 보는 것 |
| Minimal Guarantees | 어떻게 끝나든 성립하는 것 |
| Success Guarantees | 목표를 이뤘을 때 성립하는 것 |
| Trigger | 시작시키는 사건 |
| Main Success Scenario | 일이 잘 풀리는 주 흐름 |
| Extensions | 주 흐름의 단계마다 갈라지는 조건과 처리 |
| Technology & Data Variations List | 기술·데이터의 변형 |

책의 견본 쪽(출판사 공개 PDF)에는 작성 순서도 있습니다. 범위와 경계에 이름 붙이기, 주 행위자 찾기, 사용자 목표 목록, 바깥쪽 요약 유스케이스, 하나를 골라 펼치기, 이해관계자의 관심사·사전조건·보장 적기, 주 흐름(3~9단계), 확장 조건(시스템이 감지하고 처리해야 하는 것 모두), 확장 처리, 복잡한 흐름은 하위 유스케이스로 빼기, 전체 다시 맞추기 순서예요.

**목표 수준**은 기본으로 요약(summary, `+`), 사용자 목표(user-goal, `!`), 하위 기능(subfunction, `-`) 셋을 씁니다. 사용자 목표 수준이 기본 권장이고, 한 사람이 한 번 앉아서 이루는 목표 정도의 크기예요. 소스에 따라 이보다 위아래 수준을 더 두기도 하는데, 기호 표기는 소스마다 달라서 이 가이드는 세 수준만 씁니다.

### 데이터 정밀도 세 단계

이 가이드에서 특히 쓸모 있는 규칙이 Cockburn의 사전 출판 초안(2000)에 있습니다. 유스케이스 본문에는 데이터의 **별칭**만 쓰라는 규칙이에요. 데이터 기술에도 정밀도 단계를 두는데, 1단계는 별칭, 2단계는 그 별칭에 딸린 필드, 3단계는 필드의 타입·길이·검증입니다. 2·3단계는 유스케이스 밖에 따로 둬요.

```text
1단계 별칭     "예약 정보"                          ← 유스케이스 본문에
2단계 필드     회원번호, 회의실, 시작, 끝             ← 외부 스키마의 열
3단계 형식     시작: 날짜-시각, 30분 경계, 오프셋 필수   ← JSON Schema, 계약의 구조·의미 겹
```

이 규칙은 이 가이드의 층 구분과 잘 맞습니다. 유스케이스는 **행위**를 적는 형식이고, 데이터의 모양은 외부 스키마와 계약이 맡아요. 유스케이스를 받았는데 필드 목록이 없다면 형식이 잘못된 것이 아니라 원래 그런 형식입니다. 필드는 원장의 q로 남겨 따로 묻습니다.

### 유스케이스를 원장과 계약으로 옮기는 규칙

| 유스케이스 항목 | 원장 칸 | 계약에서 |
| --- | --- | --- |
| Title, Goal in Context | C | 연산 이름 |
| Primary Actor | C의 행위자, V의 이용자 | 소비자 |
| Stakeholders and Interests | V, R | 다른 이용자의 외부 스키마, 계약의 품질 겹 |
| Precondition | R | 업무 사전조건 pre (경계에서는 검사하고 실패 응답을 둠) |
| Minimal Guarantees | R | 실패해도 성립하는 post, 실패표의 "상태 변화" 열 |
| Success Guarantees | F, R | 성공 시 post |
| Trigger | C | 연산을 부르는 조건, 또는 이벤트 |
| Main Success Scenario | C, F, V | 연산의 순서, 생기는 사실, 보여 주는 것 |
| Extensions | R, Q | 실패표의 줄 |
| Technology & Data Variations | T, V | 구조·의미 겹 |
| 데이터 별칭 | T | 필드는 q로 물어 외부 스키마에 |

사전조건 줄을 따로 짚겠습니다. Cockburn 형식의 사전조건은 시스템이 이미 참이라고 보고 다시 검사하지 않는 것이라는 해설이 있어요(3자 요약이라 근거가 약합니다). 5장에서 본 Meyer의 사전조건과 같은 태도예요. 그런데 네트워크 경계에서는 사전조건을 어긴 요청이 반드시 들어오므로, 계약에서는 사전조건을 **검사하고 실패 응답을 약속**합니다. 유스케이스의 사전조건을 그대로 옮기되, 경계 계약에서는 실패표에 줄을 하나 더하는 거예요.

최소 보장은 5장에서 "상태 변화 없음"을 실패표에 적어야 한다고 했던 바로 그 자리입니다. 해설에 따르면 최소 보장의 흔한 예가 "시도가 기록된다"예요. 실패한 예약 시도도 기록해야 한다면, 그것은 개념 스키마의 새 사실(예약 시도는 결과와 함께 기록된다)이 됩니다.

### 「틈」의 유스케이스를 계약으로

「틈」의 "회의실을 예약한다"를 fully dressed로 적었다고 합시다.

```text
UC-1 회의실을 예약한다                                   수준: 사용자 목표 (!)
주 행위자     회원
범위          예약 시스템
이해관계자    회원: 원하는 시간에 방을 확보하고 싶다
              다른 회원: 자기 예약이 침해되지 않기를
              회계팀: 확정된 예약만 청구에 쓰고 싶다
사전조건      회원이 앱에 로그인했다
최소 보장     예약이 실패하면 아무 예약도 생기거나 바뀌지 않는다
성공 보장     확정 예약이 생기고 회원이 예약번호를 받는다. 회계팀이 확정을 알 수 있다
트리거        회원이 앱에서 빈 시간을 고르고 예약을 누른다
주 흐름       1. 회원이 회의실·날짜·시작·끝을 고른다
              2. 시스템이 시간 규칙을 확인한다
              3. 시스템이 겹치는 예약이 없음을 확인하고 확정 예약을 만든다
              4. 시스템이 예약번호를 보여 준다
확장          2a. 30분 단위가 아니거나 4시간을 넘는다: 시스템이 규칙을 알려 준다
              3a. 겹치는 확정 예약이 있다: 시스템이 다른 시간을 제안한다
              3b. 회원이 정지 상태다: 시스템이 예약할 수 없다고 알린다
              *a. 응답 전에 연결이 끊긴다: 회원이 다시 시도하면 같은 결과를 받는다
```

이것을 11장의 O1 계약과 나란히 놓으면 대응이 보입니다.

```text
유스케이스                          계약 O1
사전조건 "로그인했다"         →     인증(보안 조건) — 업무 사전조건은 아님
주 흐름 2 "시간 규칙"          →     pre2 30분 경계, 4시간 이하
주 흐름 3 "겹침 없음"          →     inv1, 성공 시 post1
성공 보장 "회계팀이 알 수 있다"  →     post2 E1 발행
최소 보장 "아무것도 안 바뀜"    →     실패표의 "상태 변화: 없음" 열 전체
확장 2a                      →     422 invalid_slot
확장 3a                      →     409 slot_taken
확장 3b                      →     403 member_inactive
확장 *a                      →     Idempotency-Key 재요청 = 같은 응답
```

유스케이스 쪽에 없고 계약에만 있는 것도 보세요. pre3(시작이 지금보다 뒤)는 유스케이스에 없었습니다. 회원이 앱에서 지난 시간을 고를 수 없게 화면이 막아 주니 유스케이스 작성자는 생각하지 않았겠지요. 하지만 API는 화면을 거치지 않은 요청도 받으므로 계약에는 있어야 해요. 유스케이스를 계약으로 옮길 때마다 "화면이 막아 주던 것은 무엇인가"를 묻는 것이 좋습니다.

### 사용자 스토리

사용자 스토리는 요구를 짧은 카드 한 장으로 적는 형식입니다. 흔히 쓰는 "As a … I want … so that …" 틀은 Mike Cohn에 따르면 2000년대 초 영국 Connextra에서 Rachel Davies가 시작했어요. Cohn은 "so that" 절이 꼭 있어야 하는 것은 아니지만 거의 늘 쓴다고 했습니다. Bill Wake는 2003년 좋은 스토리의 조건으로 INVEST(Independent, Negotiable, Valuable, Estimable, Small, Testable)를 들었고, Ron Jeffries는 2001년 스토리를 Card(카드)·Conversation(대화)·Confirmation(확인, 곧 인수 시험)의 3C로 설명했어요.

스토리를 원장으로 옮기는 규칙은 이렇습니다.

| 스토리의 부분 | 원장 칸 | 메모 |
| --- | --- | --- |
| As a (역할) | V의 이용자, C의 행위자 | 같은 역할의 스토리를 모으면 외부 스키마 하나가 보임 |
| I want (원하는 것) | V 또는 C | 보고 싶은 것이면 V, 바꾸고 싶은 것이면 C |
| so that (이유) | 메모, 가끔 R | 그 데이터가 왜 필요한지. 필드를 뺄지 정할 때 근거 |
| 인수 조건 | R, F(예) | 조건 안의 구체적 값은 F의 예, 일반 규칙은 R |
| Conversation에서 나온 말 | Q, T | 카드에 없는 합의는 원장에 적지 않으면 사라짐 |

INVEST의 I(독립)는 스토리끼리 **개념이** 겹치지 않기를 바라는 조건이에요. 그런데 스토리는 일의 단위로 나뉘었을 뿐, 데이터는 서로 겹칩니다. "예약을 만든다"와 "예약을 취소한다"는 독립된 스토리지만 같은 예약을 다뤄요. 그래서 스토리 묶음을 원장으로 옮긴 뒤에는 10장의 뷰 통합이 거의 늘 필요합니다.

### 「틈」의 스토리 묶음

```text
S1  회원으로서, 다가오는 내 예약을 보고 싶다. 하루 일정을 미리 알 수 있도록.
    인수: 확정 예약만 시작순으로 보인다. 취소한 예약은 보이지 않는다.
S2  회원으로서, 예약을 취소하고 싶다. 안 쓰는 시간에 돈을 내지 않도록.
    인수: 시작 1시간 전까지 취소하면 사용 시간에 들어가지 않는다.
          그 뒤에 취소하면 "사용으로 처리됩니다"라는 안내가 먼저 보인다.
S3  청구 담당자로서, 회원별 이번 달 초과 시간을 보고 싶다. 월말 청구를 빨리 끝내도록.
    인수: 초과 시간 = 사용 시간 - 등급의 무료 시간. 음수면 0.
```

옮긴 원장의 일부예요.

| ID | 칸 | 내용 | 출처 |
| --- | --- | --- | --- |
| v3 | V | 회원은 다가오는 자기 확정 예약을 시작순으로 본다 | S1 |
| r6 | R | V1에 취소한 예약은 보이지 않는다 | S1 인수 |
| c2 | C | 회원이 예약을 취소한다 | S2 |
| r4 | R | 시작 1시간 전보다 늦은 취소는 사용으로 셈 | S2 인수 |
| v6 | V | 늦은 취소 전에 회원에게 사용 처리 안내가 보인다 | S2 인수 |
| v7 | V | 청구 담당자는 회원별 월 초과 시간을 본다 | S3 |
| q8 | Q | S1의 "취소한 예약은 보이지 않는다"와 9장 V1(지난 예약도 최근순으로 보임)은 다른가? | S1, 9장 |

q8이 스토리 묶음을 옮길 때 흔히 생기는 충돌이에요. S1은 다가오는 예약만 말했고, 9장의 V1은 지난 예약 목록(Q-V1-b)도 가졌습니다. 둘은 같은 외부 스키마일까요, 다른 외부 스키마일까요? 스토리는 이 질문에 답하지 않으므로 Conversation(대화)으로 확인합니다. v6은 외부 스키마이기도 하지만, "안내가 먼저 보인다"는 순서는 화면 흐름이에요. 계약 O2에는 "늦은 취소 여부를 미리 알 수 있는 필드(V1의 `freeCancellable`)"를 두는 것으로 이어집니다.

### 이 형식들이 빼먹기 쉬운 것

| 빠지기 쉬운 것 | 유스케이스에서 | 사용자 스토리에서 | 채우는 질문 |
| --- | --- | --- | --- |
| 데이터 필드 | 별칭만 있음(원래 그런 형식) | 거의 없음 | "예약 정보에는 무엇이 들어가나요?" |
| 화면이 막아 주던 조건 | 주 흐름에서 빠짐 | 인수 조건에서 빠짐 | "화면을 안 거치고 요청이 오면?" |
| 유스케이스·스토리 사이 공유 데이터 | 각자 따로 적음 | 각자 따로 적음 | "이 둘이 다루는 예약은 같은 것인가요?" |
| 빈도 | 없음 | 없음 | "하루에 몇 번인가요?" |
| 동시성 | 확장에 드물게 | 거의 없음 | "두 사람이 동시에 하면?" |

### 헷갈리기 쉬운 곳

1. 유스케이스 하나가 연산 계약 하나라고 단정하면 안 됩니다. 사용자 목표 수준의 유스케이스는 연산 하나에 가까운 경우가 많지만, 주 흐름 안에 조회와 쓰기가 섞여 있으면 계약이 둘 이상 나와요(UC-1에도 빈 시간 조회 V4와 예약하기 O1이 함께 있습니다).
2. 인수 조건은 규칙과 예가 섞여 있습니다. "시작 1시간 전까지 취소하면 사용 시간에 들어가지 않는다"는 규칙(R)이고, "10:00 시작 예약을 09:10에 취소하면 사용 시간 0"은 예(F)예요. 예가 있으면 17장의 Gherkin처럼 인구로 쓸 수 있습니다.
3. "so that" 절을 버리지 마세요. 필드를 하나 빼야 할 때 "이 필드는 왜 필요했나"를 답해 주는 것이 so that 절입니다. 원장의 메모 칸에 남겨 두면 나중에 근거가 됩니다.

### 잠깐 확인

UC-1의 사전조건 "회원이 앱에 로그인했다"를 계약 O1의 업무 사전조건(pre)으로 옮기지 않은 이유는 무엇일까요?

로그인은 담화 세계의 규칙이 아니라 경계의 **보안 조건**이기 때문이에요. 예약할 수 있는지는 회원이 활동 상태인지(pre1)로 정해지고, 로그인 여부는 요청이 그 회원에게서 왔는지를 확인하는 일입니다. 계약에서는 보안 조건을 따로 적고(OpenAPI의 `security`), 인증이 없을 때의 응답(예: 401)을 실패표에 더합니다. 개념 스키마에는 로그인이 들어가지 않아요.

### 스스로 점검하기

1. UC-1에 확장 "1a. 회원이 고른 회의실이 공사 중이라 막혀 있다"를 더했습니다. 원장과 개념 스키마와 계약에 각각 무엇이 생기나요?
2. 스토리 S3의 인수 조건만으로는 V3 월 청구 명세를 완성할 수 없습니다. 빠진 것을 9장의 시점 질문 가운데 둘로 지적해 보세요.

#### 풀이

1. 원장에 `f`(회의실 ○는 ○일부터 ○일까지 이용 중지다)와 `r`(이용 중지 기간에는 예약할 수 없다)이 생기고, "누가 언제 중지를 거는가"를 묻는 q가 생깁니다. 개념 스키마에는 `F13 회의실 은 [시작, 끝) 동안 이용 중지다`와 제약 `확정 예약 구간은 그 회의실의 이용 중지 기간과 겹치지 않는다`가 더해집니다. 계약 O1에는 새 업무 사전조건과 실패표 줄(예: `409 room_unavailable`, 상태 변화 없음)이 더해집니다. 이미 있는 예약 위에 중지를 걸면 그 예약을 어떻게 할지도 q로 남깁니다.
2. 하나는 "이 값은 지금 값인가, 그때 값인가"입니다. 등급이 달 중간에 바뀌면 무료 시간을 어떻게 셀지(9장의 q4)를 S3이 말하지 않습니다. 다른 하나는 "언제까지의 변경이 반영되어야 하는가"입니다. 월말 23:59의 늦은 취소가 그달 청구에 들어가는지, 청구를 만든 뒤 들어온 노쇼 표시는 어떻게 할지가 빠져 있습니다.

이어지는 실습: P03 동물병원 진료 예약(유스케이스), P04 공유 자전거 대여(사용자 스토리).
