# 제1부 이론 — 넷을 정의합니다

## 1장 층을 나누는 이유: 데이터 독립성

이 장을 마치면 프로그램과 저장 형식이 붙어 있을 때 무엇이 어긋나는지 예로 설명하고, ANSI/SPARC 세 층 구조가 그 문제를 어떻게 나눠 맡기는지 그림으로 그릴 수 있습니다. 데이터 독립성이 무엇을 약속하고 무엇은 약속하지 않는지도 구분하게 됩니다.

### 프로그램과 저장 형식이 붙어 있으면

「틈」이 처음 문을 열었을 때 예약은 파일 하나에 고정 길이 레코드로 쌓였다고 해 봅시다. 한 줄이 예약 하나이고, 몇 번째 글자부터 몇 글자가 무엇인지가 정해져 있습니다.

```text
bookings.dat 한 줄 (22글자)

위치  1-2   3-6    7-14      15-18  19-22
값    R1    0007   20261117  1000   1130
뜻    회의실 회원번호 날짜      시작    끝
```

이 파일을 세 프로그램이 읽습니다. 회원 앱은 3~6번째 글자로 "내 예약"을 고르고, 안내 데스크 출력 프로그램은 7~14번째 글자로 오늘 예약을 고르고, 청구 프로그램은 15~22번째 글자로 사용 시간을 계산합니다. 세 프로그램 모두 **글자 위치**를 알고 있다는 점이 중요해요.

이제 지점이 하나 늘어서 회원번호를 `0007`에서 `G1-0007`처럼 일곱 글자로 바꿔야 한다고 합시다. 회원번호 칸이 세 글자 늘어나면 그 뒤의 날짜·시작·끝이 모두 세 칸씩 뒤로 옮겨집니다. 회원번호를 쓰지 않는 청구 프로그램까지 고쳐야 하는 이유가 여기 있어요.

```text
Before                          After
R1 0007    20261117 1000 1130   R1 G1-0007 20261117 1000 1130
   [3-6]   [7-14]   [15-22]        [3-9]   [10-17]  [18-25]

청구 프로그램이 15-22를 읽으면 → "1000 1130" 대신 "171000 1" 을 읽음
```

여기서 헷갈리기 쉬운 포인트는 "청구 프로그램은 회원번호를 안 쓰니까 영향이 없다"고 생각하는 것입니다. 청구 프로그램이 기대는 것은 회원번호가 아니라 **저장 형식 전체**였습니다. 프로그램이 데이터의 뜻이 아니라 배치에 기대면, 배치를 바꾸는 순간 그 배치를 아는 모든 프로그램이 함께 바뀌어야 합니다.

### ANSI/SPARC의 답: 세 층과 두 사상

이 문제에 대한 고전적인 답이 미국 표준 위원회 ANSI/X3/SPARC 산하 DBMS 연구 그룹의 보고서입니다. 1975년 중간 보고서가 *FDT*(ACM SIGMOD 회보) 7권 2호에 실렸고, 최종 보고서는 D. Tsichritzis와 A. Klug가 엮어 1977년 AFIPS Press에서, 1978년 *Information Systems* 3권 3호에서 나왔습니다. 이 가이드는 두 보고서 원문을 직접 보지 못했습니다. 아래 정의는 같은 연구 그룹의 작업반이 1985년에 낸 후속 보고서 NBS IR 85-3173과 ISO/TR 9007(1987)에서 옮겼습니다.

후속 보고서는 세 층을 이렇게 나눕니다.

| 층 | 무엇을 적는가 | 「틈」에서의 예 |
| --- | --- | --- |
| 외부 스키마 | 특정 응용이 관심을 두는 데이터 객체와, 그것을 응용에 보여 줄 모양 | 회원 앱이 보는 "내 예약" 목록의 항목과 모양 |
| 개념 스키마 | 기업이 관심을 두는 개체·속성·관계와 무결성 제약. 보고서는 이것을 기업의 정보 모델이라고 부릅니다 | 회원·회의실·예약이 있고, 같은 회의실 예약은 겹치지 않는다 |
| 내부 스키마 | 무엇을 어떻게 저장하는가. 저장 구조와 접근 경로 | 예약을 어떤 표에 어떤 열로 두고 어떤 인덱스로 찾는가 |

세 층만 있으면 아직 아무것도 해결되지 않아요. 핵심은 층과 층을 잇는 **사상**입니다. 보고서의 그림에는 외부-개념 사상과 개념-내부 사상이 따로 그려져 있고, 실행할 때는 변환기가 이용자의 요청을 층마다 번역합니다.

```text
회원 앱      데스크 출력      청구
  |             |             |
[외부 V1]    [외부 V2]      [외부 V3]     ← 각자 보는 모양
  \             |             /
   +---- 외부-개념 사상 ------+           ← "V1의 항목은 개념의 무엇에서 오는가"
                |
          [ 개념 스키마 ]                  ← 회원 · 회의실 · 예약 · 겹침 금지
                |
         개념-내부 사상                    ← "개념의 사실을 어떤 구조에 적는가"
                |
          [ 내부 스키마 ]                  ← 저장 구조 · 인덱스
```

이 그림을 앞의 파일 사례에 겹쳐 보면 차이가 분명해집니다. 세 프로그램은 이제 글자 위치를 모릅니다. 각자 자기 외부 스키마의 항목 이름만 압니다. 회원번호가 일곱 글자로 바뀌어도 바뀌는 것은 내부 스키마와 개념-내부 사상이고, 청구 프로그램이 보는 V3는 그대로입니다.

### 데이터 독립성

후속 보고서는 세 층을 두는 목적을 이렇게 요약합니다. 개념 스키마를 효율 고려와 응용별 요구에서 떼어 놓아 기업 모델의 비교적 안정된 기술로 삼는 것, 그리고 그렇게 얻는 유연성을 보고서의 표현으로 "usually called data independence"라고 부른다는 것입니다.

교과서는 보통 데이터 독립성을 둘로 나눕니다. 이 구분은 원전 문장을 직접 확인하지 못했고 교재와 백과사전 수준의 설명으로 확인한 것이라는 점을 밝혀 둡니다.

| 이름 | 무엇이 바뀌어도 | 무엇이 그대로인가 | 바꾸는 곳 |
| --- | --- | --- | --- |
| 물리적 데이터 독립성 | 내부 스키마(저장 구조·인덱스) | 개념 스키마와 외부 스키마 | 개념-내부 사상 |
| 논리적 데이터 독립성 | 개념 스키마(사실 유형을 더하거나 다시 나눔) | 외부 스키마와 그 위의 프로그램 | 외부-개념 사상 |

ISO/TR 9007은 "데이터 독립성"이라는 말을 쓰지 않고 같은 효과를 개념 스키마 시설의 요구로 적습니다. 요구 5는 이용자가 보는 정보 뷰가 바뀌어도 개념 스키마에 영향이 없어야 한다는 것이고, 요구 6은 내부(물리) 표현이 바뀌어도 개념 스키마가 변하지 않게 유지되어야 한다는 것입니다.

SQL 뷰로 논리적 독립성을 직접 보겠습니다. 안내 데스크의 "오늘 일정표"가 처음에는 예약 표 하나에서 나왔다고 합시다.

```sql
-- Before: 예약 표 하나
CREATE VIEW desk_today AS
SELECT room_code, starts_at, ends_at, member_name
FROM booking
WHERE starts_at::date = CURRENT_DATE;
```

나중에 반복 예약이 생기면서 개념 스키마가 바뀌어, 예약(누가 어떤 조건으로)과 예약 회차(언제)를 나눴다고 합시다. 데스크 프로그램은 `desk_today`라는 이름과 네 열만 압니다. 뷰 정의만 다시 쓰면 데스크 프로그램은 한 줄도 바꿀 필요가 없어요.

```sql
-- After: 예약과 예약 회차로 나눔. 데스크가 보는 열은 같다
CREATE OR REPLACE VIEW desk_today AS
SELECT o.room_code, o.starts_at, o.ends_at, b.member_name
FROM booking b
JOIN booking_occurrence o ON o.booking_id = b.booking_id
WHERE o.starts_at::date = CURRENT_DATE;
```

여기서 가장 중요한 줄은 `CREATE OR REPLACE VIEW desk_today` 입니다. 이름과 열 목록이 그대로라서 바깥에서 보면 아무 일도 없었던 셈이에요. 바뀐 것은 뷰 정의, 곧 외부-개념 사상뿐입니다. 뷰 이름이나 열 이름을 함께 바꿨다면 데스크 프로그램도 같이 고쳐야 했을 겁니다.

> 층이 바뀌면 사상을 고치고, 사상을 고쳐서 위층을 지킵니다.

### 사상이 흡수하지 못하는 변경

데이터 독립성을 아무 변경이나 공짜로 숨겨 주는 장치로 읽으면 곤란합니다. 사상이 숨길 수 있는 변경에는 한계가 있어요.

```text
변경                                  사상으로 숨길 수 있는가
------------------------------------  ----------------------------------------
예약 표에 인덱스 추가                    예. 외부·개념 모두 그대로
예약을 두 표로 나눔                      예. 뷰 정의만 바꿈
회원번호를 4자리에서 7자리로             대개 예. 외부에 회원번호를 보이면 아니오
"이용 인원" 사실을 개념에서 지움          아니오. 그것을 보던 외부 스키마는 원천이 없어짐
"끝 시각"의 뜻을 포함에서 불포함으로      아니오. 값은 같아도 뜻이 바뀜
조회가 0.1초에서 3초로 느려짐            구조는 숨겨지지만 이용자는 느낌
```

넷째 줄은 정보 자체가 사라진 경우입니다. 외부 스키마는 개념 스키마에서 파생되므로, 파생할 원천이 없으면 사상을 어떻게 고쳐도 같은 외부 스키마를 만들 수 없어요. 다섯째 줄은 더 까다롭습니다. 데이터 모양이 그대로라서 기계는 아무 이상을 감지하지 못하는데, 11:30에 끝나는 예약 뒤에 11:30 시작 예약을 넣어도 되는지에 대한 답이 바뀝니다. 여섯째 줄의 성능 변화는 구조로는 숨겨지지만 이용자의 기대를 어깁니다.

이 세 경우가 5장에서 계약을 따로 두는 이유입니다. 사상은 구조를 숨기고, 계약은 뜻·품질·변경 절차를 약속합니다.

### CODASYL 하위 스키마에서 SQL 뷰까지

세 층 구조에는 앞선 시도와 뒤이은 구현이 있습니다. 1971년 CODASYL 데이터베이스 작업 그룹(DBTG)의 보고서가 스키마와 **하위 스키마**(subschema, 응용 프로그램마다 보는 부분 스키마) 개념을 들여왔다고 알려져 있습니다. 이 사실은 2차 자료로만 확인했습니다. 1979년 VLDB 학회에서 Clemons는 당시 하위 스키마가 저장 스키마의 레코드 구조를 너무 닮아 데이터 독립성이 약하다고 지적했습니다. 대안으로 내놓은 것은 저장 DB에서 도출하되 모양은 달라도 되는 가상 데이터베이스였어요(초록으로 확인).

관계형 쪽에서는 1970년 Codd의 논문 "A Relational Model of Data for Large Shared Data Banks"가 처음부터 데이터 독립성을 목표로 걸었습니다. Codd는 내부 표현이 바뀌어도 응용 프로그램이 영향을 받지 않아야 한다고 쓰고, 정보의 관점에서 인덱스는 데이터 표현의 중복 구성 요소라고 말합니다. 인덱스를 만들든 없애든 담긴 정보는 같다는 뜻이고, 그래서 인덱스는 내부 스키마의 일입니다.

```text
1970  Codd                관계 모델, 데이터 독립성을 목표로
1971  CODASYL DBTG        스키마 / 하위 스키마
1975  ANSI/SPARC 중간 보고서  외부 · 개념 · 내부 세 층
1977  Tsichritzis·Klug 최종 보고서
1979  Clemons             하위 스키마 비판, 가상 데이터베이스
1987  ISO/TR 9007         개념 스키마와 정보 베이스의 개념·용어
```

세 층 구조는 공식 표준이 되지 못했고, 제품마다 용어를 다르게 구현했다는 평가가 있습니다(2차 자료). 그래도 생각은 남아서 오늘날 SQL 뷰, 테이블과 인덱스의 분리, API 응답 모양과 저장 구조의 분리로 이어지고 있어요.

### 헷갈리기 쉬운 곳

1. 세 층은 DB가 세 개 있다는 뜻이 아닙니다. 데이터는 한 곳에 한 번 저장되고, 세 층은 그 데이터를 기술하는 세 가지 **설명서**예요.
2. 개념 스키마가 꼭 DBMS 안에 들어 있어야 하는 것은 아닙니다. 1970년대 보고서는 DBMS가 개념 스키마를 알아야 한다고 봤지만, 오늘날 실무에서 개념 스키마는 대개 문서나 모델 도구에 있고 DBMS 안에는 내부 스키마와 일부 제약만 있습니다. 이 가이드가 4장에서 테이블 구조를 내부 쪽에 놓는 이유가 여기 있는데, 그 이야기는 4장에서 하겠습니다.
3. 외부 스키마는 화면이 아닙니다. 같은 "내 예약" 외부 스키마를 앱 화면으로도, 문자 메시지로도 보여 줄 수 있습니다. 화면 배치는 외부 스키마를 **표시하는 방식**이지 외부 스키마 자체가 아니에요.

### 잠깐 확인

「틈」에서 예약 표에 `(room_code, starts_at)` 인덱스를 새로 만들었습니다. 바뀌는 스키마는 어느 층이고, 회원 앱은 무엇을 고쳐야 할까요?

바뀌는 것은 내부 스키마뿐입니다. 인덱스는 정보를 더하지 않고 찾는 길만 더하니까요. 회원 앱이 보는 외부 스키마도, 개념 스키마도 그대로이므로 앱은 고칠 것이 없습니다. 다만 조회가 빨라졌다는 효과는 이용자가 느낄 수 있어요. 이것은 구조가 아니라 품질의 변화입니다.

### 스스로 점검하기

1. 고정 길이 파일에서 "날짜" 칸을 8글자(`20261117`)에서 10글자(`2026-11-17`)로 바꿨습니다. 세 층 구조가 있었다면 어느 층과 어느 사상이 바뀌고, 어느 프로그램이 그대로일까요?
2. "회의실마다 수용 인원이 있다"는 사실을 새로 기록하기로 했습니다. 이 변경은 두 독립성 가운데 어느 쪽의 시험대일까요? 기존 외부 스키마 V1·V2·V3는 영향을 받을까요?
3. 사상으로 숨길 수 없는 변경 세 종류를 들고, 각각 「틈」에서의 예를 하나씩 만들어 보세요.

#### 풀이

1. 저장 형식이 바뀌었으므로 내부 스키마와 개념-내부 사상이 바뀝니다. 개념 스키마에서 날짜는 여전히 날짜이고, 세 외부 스키마도 그대로입니다. 그래서 세 프로그램 모두 그대로입니다. 외부 스키마 가운데 날짜를 문자열로 보여 주는 것이 있더라도, 그 문자열 모양은 외부 스키마가 정하는 것이지 저장 형식이 정하는 것이 아닙니다.
2. 개념 스키마에 사실 유형을 하나 더하는 변경이므로 논리적 독립성의 시험대입니다. 기존 외부 스키마는 수용 인원을 쓰지 않으므로, 외부-개념 사상이 그대로 성립하는 한 영향을 받지 않습니다. 수용 인원을 보여 주고 싶은 이용자가 생기면 그때 외부 스키마를 새로 만들거나 늘립니다.
3. 정보가 사라지는 변경(예: 이용 인원 기록을 그만둠), 뜻이 바뀌는 변경(예: 끝 시각을 불포함으로 해석), 품질이 바뀌는 변경(예: 일정표 조회가 크게 느려짐)입니다. 세 경우 모두 5장의 계약에서 다룹니다.
