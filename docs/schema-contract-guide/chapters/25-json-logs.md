## 25장 반정형 로그와 JSON

이 장을 마치면 버전이 섞인 JSON 로그에서 필드 출현 수와 타입을 세어 **모양**별로 묶고, 그 모양들 사이의 변화를 5장의 호환성 유형으로 판정할 수 있어요. 값이 `null`인 것과 필드가 아예 없는 것의 차이를 계약에 적는 법, 로그에서 계약의 진화 이력을 되찾는 법도 익힙니다.

### 로그는 계약의 지층이다

앱이나 서비스가 남긴 JSON 로그는 쓴 쪽 프로그램이 바뀔 때마다 모양이 조금씩 달라집니다. 문서에는 지금 모양만 남아 있어도, 로그에는 지난 모양들이 시간 순서대로 쌓여 있어요. 로그를 읽는 일은 계약이 어떻게 바뀌어 왔는지를 되찾는 일이기도 합니다.

「틈」이 회계 시스템으로 보낸 예약 확정 이벤트를 로그로 남겨 두었다고 해 봅시다. 2025년부터 2026년까지의 여덟 줄이에요(`problems/data/tum-events.jsonl`).

```text
{"type":"booking_confirmed","booking":"B051","member":"M07","room":"R1","start":"2025-03-04 10:00","end":"2025-03-04 11:00"}
{"type":"booking_confirmed","booking":"B052","member":"M12","room":"R2","start":"2025-03-04 14:00","end":"2025-03-04 15:30"}
{"type":"booking_confirmed","booking":"B060","member":"M07","room":"R1","start":"2025-03-11 10:00","end":"2025-03-11 12:00","note":"대표 예약"}
{"event":"booking.confirmed","eventId":"e-1","bookingId":"B210","memberId":"M07","roomCode":"R1","startAt":"2026-01-05T10:00:00+09:00","endAt":"2026-01-05T11:30:00+09:00"}
{"event":"booking.confirmed","eventId":"e-2","bookingId":"B211","memberId":"M31","roomCode":"R3","startAt":"2026-01-05T13:00:00+09:00","endAt":"2026-01-05T14:00:00+09:00"}
{"event":"booking.confirmed","eventId":"e-90","bookingId":"B402","memberId":"M12","roomCode":"R2","startAt":"2026-06-02T09:00:00+09:00","endAt":"2026-06-02T10:30:00+09:00","minutes":90}
{"event":"booking.confirmed","eventId":"e-91","bookingId":"B403","memberId":"M07","roomCode":"R1","startAt":"2026-06-02T01:00:00Z","endAt":"2026-06-02T02:00:00Z","minutes":60}
{"event":"booking.confirmed","eventId":"e-95","bookingId":"B410","memberId":"M44","roomCode":"R3","startAt":"2026-06-03T15:00:00+09:00","endAt":"2026-06-03T16:00:00+09:00","minutes":null}
```

### 절차

```text
1. 줄마다 필드와 타입 세기      어떤 필드가 몇 줄에, 어떤 타입으로
2. 모양으로 묶기               최상위 필드 이름의 집합이 같은 줄끼리
3. 모양에 시간 붙이기           모양마다 가장 이른 줄과 늦은 줄
4. 같은 뜻 맞추기              모양 사이에서 이름만 다른 필드 (booking / bookingId)
5. 값의 뜻 맞추기              시각 표기, 단위, null 과 없음
6. 변화마다 호환성 판정         5장의 BACKWARD · FORWARD · FULL
7. 지금 계약과 정제 규칙 쓰기    앞으로의 모양 + 옛 줄을 읽는 규칙
```

### 1~3단계: 세고, 묶고, 시간 붙이기

`verification/json_profile.py`로 세었습니다(결과는 `verification/tum-events-profile.json`).

```text
필드          나온 줄  없는 줄  타입
type             3       5     string 3
booking          3       5     string 3
member, room, start, end   각각 3줄, string
note             1       7     string 1
event            5       3     string 5
eventId          5       3     string 5
bookingId, memberId, roomCode, startAt, endAt   각각 5줄, string
minutes          3       5     integer 2, null 1
```

어느 필드도 여덟 줄 모두에 나오지 않아요. 여기서 헷갈리기 쉬운 포인트는 여덟 줄 전체를 하나의 스키마로 합치는 것입니다. JSON 샘플에서 스키마를 추론하는 도구 GenSON은 같은 종류의 객체를 합칠 때 속성을 합집합으로 모으고, `required`에는 **모든 객체에 있었던 키만** 넣는다고 문서에 적고 있어요. 이 여덟 줄을 그대로 넣으면 `required`가 비어 버립니다. 모든 줄에 공통인 키가 없으니까요. 문법상으로는 맞는 스키마지만, 아무 객체나 통과시키는 스키마라 설계에는 쓸모가 없습니다.

그래서 먼저 모양으로 묶습니다. 최상위 필드 이름의 집합이 같은 줄끼리 묶으면 네 모양이 나와요.

| 모양 | 필드 | 줄 수 | 시기 |
| --- | --- | --- | --- |
| A | type, booking, member, room, start, end | 2 | 2025-03 |
| A' | A + note | 1 | 2025-03 |
| B | event, eventId, bookingId, memberId, roomCode, startAt, endAt | 2 | 2026-01 |
| B' | B + minutes | 3 | 2026-06 |

Baazizi·Colazzo·Ghelli·Sartiani 등의 연구(EDBT 2017, VLDB Journal 2019)는 JSON 스키마 추론에서 객체를 합치는 기준을 매개변수로 두었다고 알려져 있어요. 종류만 같으면 같은 객체로 보는 기준과, 필드 이름 집합까지 같아야 같은 객체로 보는 기준입니다. 이 내용은 요약 수준으로만 확인했습니다. 종류 기준으로 합치면 여덟 줄이 하나가 되고, 이름 집합 기준으로 합치면 위에서 본 네 모양으로 나뉘어요. 설계에는 뒤의 기준으로 먼저 나눠 보고, 나눈 모양 사이의 관계를 사람이 판단하는 편이 맞습니다.

### 4~5단계: 같은 뜻, 값의 뜻

모양 A와 B는 필드 이름이 하나도 겹치지 않지만, 값을 보면 대응이 보입니다.

```text
A          B            값의 차이
type     → event        "booking_confirmed" → "booking.confirmed"
booking  → bookingId    같음
member   → memberId     같음
room     → roomCode     같음
start    → startAt      "2025-03-04 10:00" → "2026-01-05T10:00:00+09:00"  (시간대 표기가 생김)
end      → endAt        같은 변화
(없음)   → eventId      새로 생김
note     → (없음)       A' 에만 있음
```

이 대응은 값과 이름이 비슷하다는 **관찰**일 뿐입니다. `start`가 정말 `startAt`과 같은 뜻인지(예약 시작인지, 이벤트를 만든 시각인지)는 쓴 쪽 개발자나 문서로 확인해야 해요. 원장에 t로 적고 근거 수준은 관찰로 둡니다.

값의 뜻에서는 세 가지가 걸립니다.

**시간대.** 모양 A의 시각에는 시간대가 없어요. 한국 시간이라고 짐작되지만 관찰일 뿐입니다. 모양 B는 오프셋을 달았는데, 다섯 줄 가운데 한 줄(e-91)은 `Z`(UTC)로 적었어요. `2026-06-02T01:00:00Z`는 한국 시간으로 10:00이니 같은 순간을 다르게 적은 것입니다. 5장의 의미 겹에 "오프셋 필수, `Z`도 같은 순간으로 해석"이 적혀 있었다면 정상이고, 소비자가 `+09:00`만 처리하게 만들어져 있었다면 이 한 줄에서 오류가 납니다.

**새로 생긴 필드.** `minutes`는 2026년 6월부터 나옵니다. 11장 점검 문제 2에서 회계팀이 요청했던 바로 그 필드가 실제로 더해진 흔적이에요. 11장 본문의 E1 명세에는 이 필드가 없으니, 그 명세는 6월 이전 판이라고 보면 됩니다. 예약 길이(분)로 보이고, e-90은 09:00~10:30에 90, e-91은 01:00Z~02:00Z에 60이라 구간과 맞아요. 11장 점검 문제에서 본 대로, 구간에서 계산되는 값이 함께 오면 둘이 어긋날 때 무엇을 믿을지 계약에 적어야 합니다.

**`null`과 없음.** e-95는 `"minutes": null`이고, e-1과 e-2에는 `minutes` 필드가 아예 없어요. 둘은 다른 이야기를 합니다.

```text
필드가 없음          그 필드를 모르는(보내지 않는) 생산자가 쓴 줄
                    e-1, e-2: minutes 가 생기기 전의 줄
값이 null           필드는 아는데 값을 넣지 않은 줄
                    e-95: 계산을 못 했나? 일부러 비웠나?
```

e-95의 `null`은 원장에 q로 남깁니다. "minutes를 null로 보내는 경우는 언제인가요?" 소비자에게 이 차이가 중요한지도 물어요. 둘을 같은 "모름"으로 다뤄도 되는 소비자가 있고, "옛 생산자"와 "계산 실패"를 구분해야 하는 소비자도 있으니까요. 계약에 적지 않으면 소비자마다 다르게 해석합니다.

> 없는 것은 모르는 것이고, null 은 비워 둔 것입니다.

### 6단계: 변화마다 호환성 판정

이제 모양 사이의 변화를 시간 순서대로 놓고 5장의 호환성 유형으로 판정합니다. 판정의 기준은 "필드 이름으로 읽는 소비자"예요.

| 변화 | 무엇이 바뀌었나 | 옛 소비자가 새 줄을 읽음(FORWARD) | 새 소비자가 옛 줄을 읽음(BACKWARD) | 판정 |
| --- | --- | --- | --- | --- |
| A → A' | 선택 필드 note 추가 | 모르는 필드를 무시하면 됨 | note 가 없어도 됨 | 호환(선택 필드라면) |
| A → B | 모든 필드 이름 변경, 시간대 표기, eventId 추가 | 실패: 아는 필드가 하나도 없음 | 실패: 옛 이름을 모름 | 비호환. Semver 로는 MAJOR |
| B → B' | 선택 필드 minutes 추가 | Tolerant Reader 면 그대로 | minutes 가 없어도 됨 | 호환. MINOR |

A → B는 계약을 새로 쓴 것과 같습니다. 이런 변화가 있었다면 그때 옛 소비자는 모두 함께 바뀌었거나, 한동안 두 모양을 함께 읽었어야 해요. 지금 회계 시스템이 2025년 로그를 다시 처리해야 한다면(예: 지난 청구를 다시 계산), 모양 A를 읽는 정제 규칙이 필요합니다.

B → B'는 5장에서 본 "사후조건 강화"예요. 다만 호환인지는 소비자의 검증 방식에 달려 있습니다. 소비자가 JSON Schema를 닫힌 모델(`additionalProperties: false`)로 엄격히 검증했다면, `minutes`가 생긴 순간 e-90부터 실패했을 거예요. 5장에서 본 대로 JSON Schema에는 호환성 규칙이 정의되어 있지 않아서, 판정은 스키마가 열려 있는지 닫혀 있는지에 따라 달라집니다.

### 7단계: 지금 계약과 정제 규칙

로그에서 되찾은 것을 두 가지 문서로 남깁니다.

```text
지금 계약 (E1, 11장의 모양 B')
  필드      eventId, bookingId, memberId, roomCode, startAt, endAt (필수), minutes (선택)
  의미      시각은 오프셋 필수, Z 허용 · 구간 [startAt, endAt) · minutes = 구간의 분, 어긋나면 구간이 기준
            minutes 가 없거나 null 이면 소비자가 구간으로 계산
  진화      선택 필드 추가는 예고 없이 · 소비자는 모르는 필드를 무시

옛 줄을 읽는 정제 규칙 (모양 A, A')
  type booking_confirmed → event booking.confirmed
  booking/member/room → bookingId/memberId/roomCode
  start/end → startAt/endAt, 시간대가 없으면 +09:00 으로 읽음     ← 관찰에 기댄 가정. 확인 필요
  eventId 없음 → bookingId 로 대신 식별 (중복 제거용)
  note → 버림 (회계 계약에 없음)                                  ← 버려도 되는지 확인 필요
```

정제 규칙 가운데 두 줄에 "확인 필요"를 달았습니다. 시간대가 없는 시각을 한국 시간으로 읽는 것과 `note`를 버리는 것은, 로그만으로는 맞는지 알 수 없는 결정이에요. 21장의 원칙대로 이것들은 관찰과 가정이고, 쓴 쪽의 진술을 받아야 확인이 됩니다.

실무 도구 가운데 quicktype의 문서는 이 흐름을 권합니다. 샘플에서 JSON Schema를 먼저 추론하고, 사람이 검토·편집해 저장소에 올린 뒤, 그 스키마에서 코드를 만들라는 거예요. 추론한 스키마를 그대로 쓰지 말고 **검토를 거쳐** 계약으로 만든다는 점이 이 장의 7단계와 같습니다.

### 헷갈리기 쉬운 곳

1. 출현 비율이 낮은 필드를 오류로 보기 쉽습니다. `note`는 여덟 줄 가운데 한 줄에만 나오지만, 쓰는 사람이 드물 뿐인 선택 필드일 수 있어요. 비율은 모양과 시기를 함께 봐야 뜻이 있습니다.
2. 타입이 섞인 필드를 "숫자 또는 null"로 합쳐 버리면 뜻이 사라집니다. `minutes`의 `null`이 언제 나오는지가 계약의 내용이에요. P13에서는 같은 이름의 필드가 정수였다가 배열이 되는 더 까다로운 경우를 봅니다.
3. 로그는 생산자가 보낸 것이지 소비자가 받은 것이 아닙니다. 로그에 줄이 하나 있다고 회계 시스템이 그 이벤트를 처리했다는 뜻은 아니에요. 전달 보장(11장)은 로그만으로 확인할 수 없습니다.

### 잠깐 확인

모양 A와 B 사이의 변화를 지금 와서 FULL 호환으로 만들 방법이 있었을까요?

있었습니다. 한동안 새 이름과 옛 이름을 함께 보냈다면요. 예를 들어 `{"type":…, "event":…, "booking":…, "bookingId":…}`처럼 두 이름을 같은 줄에 담으면, 옛 소비자는 옛 이름을, 새 소비자는 새 이름을 읽습니다. 모든 소비자가 새 이름으로 옮긴 뒤 옛 이름을 지우면, 그 지우는 변화는 이미 아무도 쓰지 않는 필드의 삭제라서 소비자 주도 계약(5장)으로 보면 안전해요. 11장 진화 겹의 "병행" 단계가 바로 이 방법입니다.

### 스스로 점검하기

1. 위 로그에서 모양 B'의 세 줄 가운데 `minutes`가 구간과 맞는지 직접 계산해 보세요. e-95는 무엇으로 계산해야 하나요?
2. 모양 A의 `start`가 사실은 예약을 만든 시각이었다는 답이 왔다고 합시다. 정제 규칙과 원장에서 무엇이 바뀌나요?
3. 회계 시스템이 로그를 처음부터 다시 처리하려 합니다. 중복 제거 키를 무엇으로 해야 할까요? 모양마다 나눠 답해 보세요.

#### 풀이

1. e-90은 09:00~10:30이라 90분이고 `minutes` 90과 같습니다. e-91은 01:00Z~02:00Z라 60분이고 `minutes` 60과 같습니다. e-95는 15:00~16:00이라 구간으로 계산하면 60분입니다. 계약에 "minutes가 null이면 구간으로 계산"이라고 적었으니 소비자는 60을 씁니다.
2. 모양 A에는 예약 구간의 시작이 없고, 예약을 만든 시각과 끝 시각만 있는 셈이 됩니다. `start → startAt` 대응은 틀렸으므로 지우고, `start`는 "생성 시각"으로 따로 옮깁니다. 예약 구간의 시작은 모양 A만으로는 알 수 없게 되므로, 옛 예약의 시작 시각을 다른 자료(예약 DB)에서 찾아야 한다는 q를 남깁니다. 원장의 t(start = startAt)는 관찰이었으므로 기각 기록을 남깁니다.
3. 모양 B와 B'는 `eventId`로 중복을 거릅니다. 모양 A와 A'에는 `eventId`가 없으므로 `booking`(예약번호)으로 거릅니다. 다만 같은 예약에 확정 이벤트가 두 번 정당하게 생길 수 있는지(예: 취소 뒤 다시 확정)를 확인해야 합니다. 그런 일이 있다면 예약번호만으로는 정당한 두 이벤트를 하나로 지워 버립니다.
