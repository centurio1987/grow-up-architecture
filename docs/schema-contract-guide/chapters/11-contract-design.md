## 11장 계약 설계: 연산·실패·진화

이 장을 마치면 경계 목록에서 출발해 연산과 이벤트마다 계약을 다섯 겹으로 쓸 수 있어요. 실패를 종류별로 나눠 응답과 상태 변화를 약속하는 법, 멱등성과 동시성을 계약에 적는 법, 진화 정책과 소비자 주도 계약 시험을 정하는 법까지 다룹니다.

### 절차 한눈에

```text
1. 경계 목록       누구와 누구 사이인가. 동기 호출 / 비동기 이벤트 / 데이터 파일
2. 연산 목록       원장의 C 칸 → 연산 계약 O, 상태 변화 알림 → 이벤트 계약 E
3. 행위 겹         사전·사후조건, 불변식, 실패표, 멱등성, 순서, 동시성
4. 구조·의미 겹    외부 스키마를 붙이고 단위·시간대·코드표·구간의 뜻을 적음
5. 품질 겹         지연, 가용성, 신선도, 보존 기간
6. 진화 겹         무엇이 호환인가(소비자별), 공지와 폐기 절차, 버전 번호
7. 시험            소비자 주도 계약 시험, 제공자 검증
```

### 1~2단계: 경계와 연산

「틈」의 경계는 셋입니다. 각 경계에서 오가는 연산과 이벤트를 원장의 C 칸에서 뽑아요.

| 경계 | 방식 | 계약 | 원장 줄 |
| --- | --- | --- | --- |
| 회원 앱 → 예약 API | 동기 HTTP | O1 예약하기, O2 취소하기, V1·V4 조회 | c1, c2, v3, v4 |
| 데스크 → 예약 API | 동기 HTTP | V2 조회 | v1 |
| 예약 시스템 → 회계 시스템 | 비동기 이벤트 | E1 예약 확정, E2 예약 취소, E3 이용 확정(이용완료·노쇼) | v2, q3 |

E2와 E3은 원장에 직접 적혀 있지 않았어요. q3(회계팀은 확정만 받나, 취소·노쇼도 받나?)에 회계팀이 "사용 분 계산에 필요하니 취소와 노쇼도 보내 달라"고 답했다고 합시다. 그 답이 이벤트 두 개를 더 만들었습니다. 미결 질문 하나가 계약 둘이 되는 일은 흔해요.

### 3단계: 행위 겹

연산마다 5장의 틀로 사전·사후조건과 불변식을 적고, 실패를 표로 정리합니다. 실패표의 열은 네 개를 권해요. 어떤 조건을 어겼는지, 무엇을 돌려주는지, 상태가 바뀌었는지, 다시 시도해도 되는지입니다.

```text
O1 예약하기   POST /bookings
  입력      memberId, roomCode, startAt, endAt, 머리글 Idempotency-Key
  사전조건  pre1 회원이 존재하고 활동 상태          (업무)
           pre2 30분 경계, 끝 > 시작, 4시간 이하     (형식)
           pre3 시작이 지금보다 뒤                    (업무)
  사후조건  post1 성공: 확정 예약 하나가 생기고 예약번호를 돌려줌
           post2 성공: E1 이 같은 트랜잭션 결과에 따라 정확히 한 번 발행 예약됨
  불변식    inv1 확정 예약끼리 같은 회의실이면 구간이 겹치지 않음 (R3)
```

| 실패 | 응답 | 상태 변화 | 다시 시도 |
| --- | --- | --- | --- |
| pre2 위반 | 422 `invalid_slot` | 없음 | 같은 요청으로는 소용없음 |
| pre1 위반(정지·탈퇴) | 403 `member_inactive` | 없음 | 소용없음 |
| pre3 위반 | 422 `starts_in_past` | 없음 | 소용없음 |
| inv1과 충돌 | 409 `slot_taken` | 없음 | 다른 시간으로 |
| 같은 Idempotency-Key, 같은 본문 | 첫 응답을 그대로 | 없음(이미 반영됨) | — |
| 같은 Idempotency-Key, 다른 본문 | 422 `idempotency_key_reused` | 없음 | 새 키로 |
| 일시 장애 | 503 | 없음이 보장됨 | 같은 키로 다시 |

마지막 줄이 중요합니다. 503을 돌려줄 때 "상태 변화 없음이 보장됨"이라고 약속하려면, 예약을 기록하는 트랜잭션이 끝나기 전에만 503을 내야 해요. 기록은 끝났는데 응답을 보내다 끊긴 경우에는 소비자가 결과를 모릅니다. 그래서 소비자는 같은 Idempotency-Key로 다시 보내고, 제공자는 첫 결과를 돌려줘요. 멱등 키가 있어야 "모르는 결과"를 안전하게 다시 물을 수 있습니다.

```text
회원 앱                     예약 API                    DB
  | POST (key=K1) --------▶ |                           |
  |                         | 확정 기록 ---------------▶ | 커밋됨
  |        (응답 중 끊김)  X  |                           |
  | POST (key=K1) 다시 ----▶ |                           |
  |                         | K1 의 첫 결과 찾음 -------▶ |
  | ◀---- 201 B101 (같은 답)  |                           |
```

**동시성**도 행위 겹에 들어갑니다. 두 회원이 같은 회의실의 같은 시간을 거의 동시에 예약하면 어떻게 될까요? 4장의 배제 제약이 있으면 DB가 둘 가운데 하나만 받아들이고, 나머지는 제약 위반으로 실패해요. 계약에는 이렇게 적습니다. "같은 구간을 겹치게 요청한 둘 가운데 먼저 커밋된 하나가 성공하고, 나머지는 409를 받는다. 어느 쪽이 먼저인지는 보장하지 않는다." 순서를 보장하지 않는다는 것까지 적어야, 소비자가 먼저 누른 사람의 예약이 받아들여진다고 기대하지 않습니다.

이벤트 E1의 행위 겹은 다르게 생겼어요.

```text
E1 예약 확정   채널 tum.booking.confirmed
  발행 조건   O1 이 성공해 확정 예약이 커밋되었을 때, 그리고 그때만
  전달       적어도 한 번 (같은 이벤트가 두 번 올 수 있음)
  중복 제거   소비자는 eventId 로 중복을 걸러야 함
  순서       같은 bookingId 의 E1·E2·E3 은 발생 순서대로. 다른 예약끼리는 보장 안 함
```

"발행 조건 … 그리고 그때만"을 지키는 것은 생각보다 어렵습니다. 예약을 DB에 커밋한 뒤 이벤트를 보내다 실패하면 회계는 예약을 모르게 되고, 이벤트를 먼저 보낸 뒤 커밋이 실패하면 없는 예약이 청구돼요. 흔히 쓰는 해법은 예약과 같은 트랜잭션에서 "보낼 이벤트" 행을 함께 기록하고, 별도 과정이 그 행을 읽어 발행하는 방식입니다. 이 결정은 12장의 보장 위치표에 post2를 지키는 자리로 적어요. 그 별도 과정이 실패 뒤 다시 보내면 같은 이벤트가 두 번 갈 수 있으므로, 전달은 "적어도 한 번"이 되고 소비자는 eventId로 중복을 걸러야 합니다. 이렇게 행위 겹의 줄 하나하나가 서로 맞물려 있어요.

### 4단계: 구조와 의미 겹

구조는 9장에서 만든 외부 스키마를 붙이면 됩니다. 의미 겹에는 모양만으로 알 수 없는 것을 적어요.

| 항목 | O1·E1에서 |
| --- | --- |
| 시각 | ISO 8601, 오프셋 필수(`+09:00`). `Z`로 보내도 같은 순간으로 해석 |
| 구간 | `[startAt, endAt)` — 끝 불포함 |
| 단위 | 분 단위 길이는 정수 분. 금액은 원, 정수 |
| 코드표 | `roomCode`는 회의실 코드표(R1, R2, R3)의 값. 코드표는 별도 조회 API로 제공 |
| 식별 | `memberId`는 회원번호. 이메일로 회원을 찾지 않음(10장의 맞추기 결정) |

OpenAPI로 O1의 기계가 읽는 부분을 적으면 다음과 같습니다. 일부만 보입니다.

```yaml
openapi: 3.2.0
info:
  title: 틈 예약 API
  version: 1.0.0
paths:
  /bookings:
    post:
      operationId: createBooking
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          schema: { type: string, maxLength: 64 }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/BookingRequest' }
      responses:
        '201': { description: 확정 예약이 생김 (post1) }
        '403': { description: 회원이 활동 상태가 아님 (pre1), 상태 변화 없음 }
        '409': { description: 겹치는 확정 예약이 있음 (inv1), 상태 변화 없음 }
        '422': { description: 형식 위반 (pre2, pre3) 또는 멱등 키 재사용, 상태 변화 없음 }
components:
  schemas:
    BookingRequest:
      type: object
      required: [memberId, roomCode, startAt, endAt]
      properties:
        memberId: { type: string }
        roomCode: { type: string }
        startAt:  { type: string, format: date-time }
        endAt:    { type: string, format: date-time, description: '끝 불포함' }
```

응답의 `description`에 사전·사후조건 번호를 적은 것을 보세요. 5장에서 본 대로 OpenAPI에는 사후조건을 적는 전용 자리가 보이지 않으므로, 산문 계약과 기계용 명세를 번호로 잇는 거예요. "30분 경계"는 JSON Schema로 표현하기 어려워 산문 계약(pre2)에만 있습니다. 기계용 명세가 계약 전체를 담지 못한다는 점을 이렇게 드러내 두는 편이 낫습니다.

E1은 AsyncAPI 3 꼴로 적을 수 있어요.

```yaml
asyncapi: 3.0.0
info:
  title: 틈 예약 이벤트
  version: 1.0.0
channels:
  bookingConfirmed:
    address: tum.booking.confirmed
    messages:
      bookingConfirmed:
        $ref: '#/components/messages/BookingConfirmed'
operations:
  sendBookingConfirmed:
    action: send
    channel:
      $ref: '#/channels/bookingConfirmed'
components:
  messages:
    BookingConfirmed:
      payload:
        type: object
        required: [eventId, bookingId, memberId, roomCode, startAt, endAt]
        properties:
          eventId:   { type: string }
          bookingId: { type: string }
          memberId:  { type: string }
          roomCode:  { type: string }
          startAt:   { type: string, format: date-time }
          endAt:     { type: string, format: date-time }
```

AsyncAPI 3.0에서 연산을 `send`·`receive`로 적고 채널을 연산과 따로 둔다는 점은 3.0.0 발표 자료에서 확인했습니다. "적어도 한 번 전달"이나 "같은 예약 안에서 순서 보장" 같은 약속을 적는 표준 자리는 이번에 확인하지 못했어요. 그래서 이 약속들은 산문 계약에 적습니다.

### 5단계: 품질 겹

품질 겹은 숫자로 적되, 측정 방법을 함께 적어야 약속이 됩니다.

| 항목 | 약속(가정한 값) | 측정 |
| --- | --- | --- |
| O1 지연 | 요청의 95%가 0.5초 이내 | API 게이트웨이 기록, 월 단위 |
| O1 가용성 | 월 99.5% | 5분 간격 상태 확인 |
| E1 신선도 | 확정 후 1분 이내 발행 | 커밋 시각과 발행 시각의 차 |
| E1 보존 | 채널에 7일 보관 | 브로커 설정 |

데이터 파일을 넘기는 경계라면 ODCS의 SLA 절이 이런 항목을 적는 자리를 줍니다. 조사에서 확인한 SLA 항목 이름에는 지연(latency), 가용성(generalAvailability), 보존(retention), 갱신 주기(frequency), 제공 시각(timeOfAvailability) 같은 것이 있었어요.

### 6단계: 진화 겹

진화 겹은 세 부분으로 씁니다. 무엇을 호환 변경으로 보는지, 호환되지 않는 변경은 어떤 절차로 하는지, 버전 번호를 어떻게 붙이는지예요.

| 변경 | 이 계약에서의 분류 | 근거 |
| --- | --- | --- |
| 응답·이벤트에 선택 필드 추가 | 호환. 예고 없이 가능 | 사후조건 강화. 소비자는 모르는 필드를 무시해야 함(계약에 명시) |
| 요청에 선택 필드 추가 | 호환 | 사전조건 약화 |
| 출력 열거값 추가(예: 상태 `pending`) | 공지 후 호환 | 소비자가 모르는 값을 어떻게 다룰지 미리 약속했을 때만 |
| 요청에 필수 필드 추가 | 비호환 | 사전조건 강화 |
| 출력 필드 삭제·이름 변경 | 비호환 | 사후조건 약화 |
| 값의 뜻 변경(구간, 단위, 시간대) | 비호환 | 의미 겹 변경 |

열거값을 더하는 줄은 따로 짚겠습니다. 출력에 열거값을 하나 더하는 것은 모양으로는 작은 변경이지만, 소비자가 `switch`로 상태를 빠짐없이 나눠 처리하고 있었다면 모르는 값에서 실패해요. 그래서 계약에 "모르는 상태 값은 확정이 아닌 것으로 다룬다" 같은 규칙을 **처음부터** 적어 두면, 나중에 열거값을 더할 길이 열립니다. 호환성은 변경할 때가 아니라 첫 계약을 쓸 때 준비한다는 뜻이에요.

비호환 변경의 절차는 이렇게 적습니다.

```text
1. 공지      변경 내용, 이유, 새 주 버전, 일정 (90일 전, 가정)
2. 병행      옛 버전과 새 버전을 함께 제공. 이벤트라면 두 채널로 함께 발행
3. 사용 측정  옛 버전을 누가 아직 쓰는지 확인 (소비자 계약, 호출 기록)
4. 제거      남은 소비자가 없거나 공지한 날이 되면 제거
```

버전 번호는 Semver를 따라 비호환이면 주 버전을, 호환 기능 추가면 부 버전을 올립니다. 그리고 Semver가 요구하는 대로 **무엇이 공개 API인지** 계약에 선언해요. 「틈」은 계약에 적은 필드와 동작만 공개 API로 선언하고, 순서처럼 약속하지 않은 동작은 바뀔 수 있다고 명시합니다. 5장의 Hyrum 법칙을 생각하면, 약속하지 않은 순서에 기대는 소비자가 생기지 않도록 목록 응답의 순서를 일부러 고정하지 않는 것도 방법이에요.

### 7단계: 시험

마지막으로 계약을 시험할 방법을 정합니다. 계약을 지키는지 확인하는 시험은 양쪽에 있어요.

```text
제공자 쪽   계약의 pre·post·inv 를 시험 사례로: 409 를 내야 하는 겹침 요청, 같은 멱등 키 재요청 ...
소비자 쪽   소비자가 실제로 쓰는 필드와 동작만 적은 소비자 계약 (Pact 의 예시 계약)
연결       제공자 빌드에서 모든 소비자 계약을 다시 보내 확인 (제공자 검증)
배포 판단   소비자·제공자 버전 조합별 검증 결과로 배포 여부 결정 (Pact 의 can-i-deploy)
```

회계 시스템의 소비자 계약을 예시로 적으면 다음과 같아요. Pact 파일의 정확한 형식이 아니라, 담아야 할 내용을 보이려고 줄인 꼴입니다.

```json
{
  "consumer": "회계 시스템",
  "provider": "예약 시스템",
  "messages": [
    {
      "description": "예약 확정 이벤트",
      "contents": {
        "eventId": "e-77", "bookingId": "B101", "memberId": "M07",
        "startAt": "2026-11-17T10:00:00+09:00", "endAt": "2026-11-17T11:30:00+09:00"
      }
    }
  ]
}
```

회계 시스템의 기대에는 `roomCode`가 없습니다. 회계는 회의실을 쓰지 않으니까요. 10장에서 회의실마다 단가를 다르게 매기자는 이야기가 나왔다면, 그 순간 회계의 소비자 계약에 `roomCode`가 들어가고, 예약 시스템은 그 필드를 지울 수 없게 됩니다. 소비자 계약은 이렇게 **지금 누가 무엇에 기대는지**를 보여 줘요.

### 헷갈리기 쉬운 곳

1. 실패 응답을 상태 코드만으로 적으면 부족합니다. 같은 409라도 "다른 시간으로 다시 하면 된다"와 "다시 해도 소용없다"는 소비자가 해야 할 일이 달라요. 실패표의 "상태 변화"와 "다시 시도" 열이 그 차이를 적는 자리입니다.
2. 멱등성은 HTTP 메서드가 정해 주지 않는 경우가 많습니다. RFC 9110이 정한 멱등 메서드는 PUT·DELETE와 안전한 메서드이고, 예약하기 같은 POST는 계약이 따로 정해야 해요.
3. 기계용 명세가 통과했다고 계약이 지켜졌다는 뜻은 아닙니다. 응답이 JSON Schema에 맞더라도 겹치는 예약을 만들었다면 inv1을 어긴 거예요. 행위 겹은 시험 사례로 확인합니다.

### 잠깐 확인

E1 이벤트를 받은 회계 시스템이 같은 eventId를 두 번 받았습니다. 이것은 예약 시스템이 계약을 어긴 것일까요?

아닙니다. E1의 계약은 "적어도 한 번" 전달을 약속했고, 소비자가 eventId로 중복을 거르라고 적었어요. 같은 이벤트가 두 번 오는 것은 계약 안의 일이고, 두 번 처리해서 청구가 두 번 되었다면 소비자 쪽이 계약의 의무를 지키지 않은 것입니다. 거꾸로 이벤트가 한 번도 오지 않았다면 예약 시스템이 post2를 어긴 거예요.

### 스스로 점검하기

1. O2 취소하기의 실패표를 네 열(실패·응답·상태 변화·다시 시도)로 써 보세요. 이미 취소된 예약을 다시 취소하는 경우를 실패로 볼지, 멱등한 성공으로 볼지 정하고 이유를 적어 보세요.
2. 회계팀이 E1에 `minutes`(예약 길이, 분) 필드를 넣어 달라고 합니다. 진화 겹의 표로 분류하고, `startAt`·`endAt`과 어긋날 가능성을 의미 겹에서 어떻게 막을지 적어 보세요.
3. E1의 신선도 약속(1분 이내 발행)을 지키지 못한 날이 있었습니다. 계약에 무엇이 적혀 있어야 이 일을 다룰 수 있을까요?

#### 풀이

1. 예: `pre1 위반(남의 예약이거나 없음) · 404 · 없음 · 소용없음`, `pre2 위반(이미 이용완료·노쇼) · 409 not_cancellable · 없음 · 소용없음`, `일시 장애 · 503 · 없음 보장 · 같은 키로 다시`. 이미 취소된 예약을 다시 취소하는 경우는 멱등한 성공(200, 첫 취소의 결과를 그대로)으로 보는 편이 소비자에게 편합니다. 응답이 끊겨 다시 보낸 취소가 실패로 돌아오면, 소비자는 취소가 되었는지 알 수 없게 되기 때문입니다. 다만 그때 돌려주는 취소 시각은 첫 취소의 시각이어야 R5 계산이 바뀌지 않습니다.
2. 이벤트에 선택 필드를 더하는 것이므로 호환 변경입니다. 다만 `minutes`는 `startAt`·`endAt`에서 계산되는 값이라 둘이 어긋날 수 있습니다. 의미 겹에 "`minutes = (endAt - startAt)`의 분, 끝 불포함 구간 기준"을 적고, 제공자 시험에 둘이 같은지 확인하는 사례를 넣습니다. 어긋났을 때 무엇을 믿을지(구간이 기준)도 적어 둡니다.
3. 측정 방법(커밋 시각과 발행 시각의 차), 달성 기준(예: 그달 이벤트의 99%), 지키지 못했을 때 알리는 절차(누구에게, 얼마 안에)가 있어야 합니다. ODCS의 SLA 항목에 탐지·통지·복구까지 걸리는 시간(timeToDetect, timeToNotify, timeToRepair)을 적는 자리가 있는 것도 같은 이유입니다.
