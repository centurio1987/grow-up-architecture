## 24장 데이터 덤프 프로파일링

이 장을 마치면 데이터 덤프에서 유일 열 조합·함수 종속·포함 종속 후보를 계산하고, 결과를 개념 스키마와 맞춰 "진술을 구할 후보", "우연이라 버릴 것", "사람에게 물을 어긋남"으로 나눌 수 있어요. 근사 종속의 오차를 읽는 법과 이 가이드의 계산 스크립트 쓰는 법도 익힙니다.

### 프로파일링이란

Abedjan·Golab·Naumann의 2015년 조사 논문 「관계형 데이터 프로파일링」은 Johnson의 정의를 인용해, 데이터 프로파일링을 데이터베이스에 대해 작지만 정보가 많은 요약을 만드는 일로 설명합니다. 이 논문은 저자 원고로 직접 읽었어요. 논문은 전통적인 프로파일링 작업을 세 묶음으로 나눕니다.

| 묶음 | 작업 | 「틈」 덤프에서 묻는 것 |
| --- | --- | --- |
| 한 열 | 행 수, 값 길이, 결측, 서로 다른 값의 수, 값 분포, 자료형과 패턴, 도메인 | `room_capacity`에 빈칸이 몇 개인가, `status`의 값은 몇 가지인가 |
| 여러 열 | 상관·연관 규칙, 군집과 이상치, 요약 | 노쇼가 특정 회의실에 몰리는가 |
| 종속 | 유일 열 조합(키 발견), 포함 종속(외래 키 발견), 함수 종속. 각각 조건부·근사 변형 | 무엇이 키인가, 무엇이 무엇을 결정하는가, 어느 열이 다른 표를 가리키는가 |

논문은 분류표에 조건부·근사 변형을 넣어 두었지만, 본문 조사는 정확한(exact) 방법에 집중한다고 밝힙니다. 그리고 21장에서 본 대로, 찾아낸 결과는 주어진 인스턴스에 관한 것일 뿐이라 전문가가 해석해야 한다고 강조해요. 이 장의 계산도 모두 그 전제 위에 있습니다.

### 세 가지 종속

종속 묶음의 세 작업을 「틈」의 예로 정의하겠습니다.

**유일 열 조합**(unique column combination, UCC)은 값의 조합이 모든 행에서 서로 다른 열들입니다. 키 후보예요. 덤프에서 `booking_id`는 열두 행이 모두 달라서 한 열짜리 유일 열 조합입니다.

**함수 종속**(functional dependency, FD) `X → Y`는 X 값이 같은 행끼리 Y 값도 같다는 뜻이에요. 덤프에서 `room_code → room_capacity`가 성립합니다. 회의실 코드가 같으면 정원도 같아요. 논문은 함수 종속이 스키마 정규화에 쓰인다고 정리합니다. 4장과 8장에서 본 갱신 이상을 찾는 근거가 이것이에요.

**포함 종속**(inclusion dependency, IND)은 한 열의 값이 모두 다른 열(대개 다른 표)에도 나타난다는 것입니다. 덤프에 있는 `member_id` 값이 모두 회원 목록 `member_id`에 있다면, 덤프 쪽 `member_id`는 회원 목록을 가리키는 외래 키 후보예요. 논문은 포함 종속이 외래 키의 전제이고 조인 경로를 제안하는 데 쓰인다고 말합니다.

```text
유일 열 조합   booking_id                       → 키 후보
함수 종속      room_code → room_capacity        → 정원은 회의실에 딸린 값 (F3)
포함 종속      덤프.member_id 값들은 모두 회원목록.member_id 에 있다 → 외래 키 후보
```

### 근사 종속과 오차

실제 자료에는 규칙의 예외가 섞여 있습니다. 논문도 그 때문에 조건부·부분·근사 변형을 둔다고 설명해요. **근사 종속**은 몇 행을 빼면 성립하는 종속이고, 얼마나 가까운지를 수로 나타낼 수 있습니다.

이 가이드의 스크립트는 오차를 "종속이 성립하도록 지워야 하는 최소 행 수 ÷ 전체 행 수"로 계산하고, 출력에서는 `g3`라는 이름으로 보여 줘요. 계산법을 작은 예로 보겠습니다.

```text
member_id → grade 를 검사

M07 의 행: 일반, 일반, 상주, 상주       ← 값이 두 가지
M12 의 행: 상주, 상주, 상주             ← 하나
M31 의 행: 일반, 일반, 일반             ← 하나
M44 의 행: 일반, 일반                   ← 하나

M07 을 성립시키려면 다수 값(2개)을 남기고 나머지(2개)를 지워야 함
지울 최소 행 수 = 2,  전체 12행  →  오차 = 2 / 12 ≈ 0.1667
```

M07의 네 행에서 두 값이 2대 2로 맞섰으니, 어느 쪽을 남기든 두 행을 지워야 합니다. 다른 회원은 이미 값이 하나라 지울 것이 없어요. 그래서 전체 오차는 2 ÷ 12입니다.

근사 종속을 처음으로 효율 있게 찾은 알고리즘으로 TANE이 자주 꼽힙니다. Huhtala·Kärkkäinen·Porkka·Toivonen(1999, *The Computer Journal* 42권 2호)의 방법으로, 속성 값에 따라 행을 **분할**해 종속을 빠르게 검사하고, 같은 분할로 근사 종속과 오류·예외 행을 찾기 쉽다고 설명합니다. 이 내용은 저자들의 프로젝트 페이지로 확인했어요. 위 계산에서 M07 행들을 값별로 나눠 본 것이 바로 분할입니다.

### 스크립트로 계산하기

`verification/profile.py`는 표준 라이브러리만 쓰는 작은 프로파일러입니다. 큰 자료에는 맞지 않지만, 실습 자료처럼 수십 행짜리 자료에서 후보를 빠짐없이 보여 줘요.

```bash
# 한 열 통계, 세 열 이하의 최소 유일 열 조합, 왼쪽 한 열의 최소 함수 종속
python3 verification/profile.py problems/data/tum-bookings-dump.csv --max-lhs 1

# 근사 종속 하나의 오차와 어긋난 값
python3 verification/profile.py problems/data/tum-bookings-dump.csv --approx member_id grade

# 포함 종속: 앞 파일의 열 값이 모두 뒤 파일의 열에 있는가
python3 verification/profile.py --ind problems/data/tum-bookings-dump.csv:member_id \
                                     problems/data/tum-members.csv:member_id
```

스크립트는 빈칸을 결측으로 세되, 유일성과 종속을 계산할 때는 빈 문자열 값 하나로 다룹니다. 그래서 정원이 빈 R3의 세 행은 정원 "빈 값"을 공유하는 행으로 계산돼요. SQL의 `NULL`은 서로 같지 않다고 보는 규칙과 다르니, 빈칸이 많은 열의 결과는 따로 확인해야 합니다.

### 「틈」 예약 덤프의 결과

「틈」의 예약 기록에서 뽑았다고 가정한 덤프(`problems/data/tum-bookings-dump.csv`, 12행)로 실제로 계산했습니다. 결과 파일은 `verification/tum-profile.json`(왼쪽 한 열), `tum-profile-lhs2.json`(왼쪽 두 열까지), `tum-approx-member-grade.json`, `tum-ind-member.json`이에요.

```text
열(서로 다른 값 / 빈칸)
booking_id 12/0 · member_id 4/0 · member_name 4/0 · grade 2/0 · room_code 3/0
room_capacity 3/3 · starts_at 11/0 · ends_at 12/0 · status 4/0 · cancelled_at 3/10

세 열 이하의 최소 유일 열 조합 (8개)
booking_id · ends_at · (starts_at, status) · (starts_at, cancelled_at)
(member_id, room_code, status) · (member_id, room_capacity, status)
(member_name, room_code, status) · (member_name, room_capacity, status)

왼쪽 한 열의 최소 함수 종속 (9개)
member_id → member_name        member_name → member_id
room_code → room_capacity      room_capacity → room_code
starts_at → member_id · member_name · grade · room_code · room_capacity

왼쪽 두 열까지의 최소 함수 종속: 13개
근사 종속 member_id → grade: 지울 행 2, 오차 0.1667 (M07 에서 일반 2 · 상주 2)
포함 종속 덤프.member_id → 회원목록.member_id: 성립 안 함, 목록에 없는 값 M44
```

### 결과 읽기: 개념 스키마와 맞추기

이 결과를 그대로 스키마로 옮기면 안 됩니다. 하나씩 개념 스키마와 맞춰 세 갈래로 나눠요.

| 결과 | 개념 스키마와 | 판단 |
| --- | --- | --- |
| `booking_id` 유일 | 예약의 참조 방식(예약번호)과 같음 | 진술 구함(이미 2장에서 정함) |
| `ends_at` 혼자 유일 | 끝 시각이 예약을 식별한다는 규칙은 없음 | 우연. 12행이라 겹치는 끝 시각이 없었을 뿐 |
| `(room_code, starts_at)`는 유일 **아님** | 2장·8장: 취소된 예약과 새 예약이 같은 회의실·시작을 가질 수 있음 | 개념과 맞음. B104(취소)와 B105가 R3 09:00을 공유 |
| `room_code → room_capacity` | F3 회의실은 정원을 가진다 | 진술 구함 |
| `room_capacity → room_code` | 정원이 회의실을 정한다는 규칙은 없음 | 우연. 회의실 셋의 정원이 모두 달랐을 뿐 |
| `member_id → member_name` | F1 회원은 이름을 가진다 | 진술 구함 |
| `member_name → member_id` | 동명이인이 있을 수 있음 | 우연일 가능성. 이름으로 회원을 찾지 않음(8장) |
| `starts_at → …` 다섯 개 | 시작 시각이 회원을 정한다는 규칙은 없음 | 우연. 시작 시각 11가지가 거의 행마다 다름 |
| `member_id → grade` 근사(0.1667) | 등급은 바뀔 수 있음(9장 F2') | 어긋남을 물음. M07의 등급 변경으로 설명됨(21장) |
| 회원 목록에 없는 M44 | 예약은 회원이 한 것(F4) | 어긋남을 물음. 목록이 오래되었나, 탈퇴 회원인가 |

"우연"으로 버린 것들에는 공통점이 있어요. 왼쪽 열의 값이 거의 행마다 달라서 키처럼 행동한다는 점입니다. `starts_at`은 12행에 11가지, `ends_at`은 12가지예요. 21장의 첫 질문(왼쪽 값이 거의 다 다른가)이 이런 후보를 빠르게 거릅니다.

`(room_code, starts_at)`가 유일하지 않다는 결과는 거꾸로 값진 정보예요. 개념 스키마가 예측한 대로 자료가 반례를 보여 줬습니다. 2장에서 논증으로 얻은 결론(예약은 회의실과 시작으로 식별할 수 없다)을 자료가 반증 쪽에서 받쳐 준 셈이에요. 21장에서 말한 대로 자료가 할 수 있는 일은 반증이고, 여기서는 그 반증이 우리 설계를 뒷받침했습니다.

### 헷갈리기 쉬운 곳

1. 프로파일러가 낸 함수 종속 목록을 정규화의 입력으로 그대로 쓰면, 우연 종속 때문에 표가 엉뚱하게 쪼개집니다. `starts_at → member_id`를 따르면 "시작 시각 표"가 생겨요. 먼저 개념 스키마와 맞춰 걸러야 합니다.
2. 유일 열 조합이 여럿 나오면 그중 하나를 기본 키로 고르는 일이 남습니다. 논문도 유일 열 조합을 찾은 뒤 의도된 기본 키를 고르는 것을 별도 단계로 다뤄요. 고르는 기준은 자료가 아니라 2장의 참조 방식(담화 세계에서 무엇으로 알아보는가)입니다.
3. 포함 종속이 성립하지 않는다고 외래 키가 아닌 것은 아닙니다. M44 하나 때문에 성립하지 않았을 뿐, 업무상으로는 외래 키여야 할 가능성이 커요. 반례 소수는 21장의 둘째 갈래(사람에게 물음)로 갑니다.

### 잠깐 확인

덤프의 `cancelled_at`은 12행 가운데 10행이 빈칸입니다. 이 열의 결측 비율 83%는 데이터 품질 문제일까요?

아닙니다. 개념 스키마의 R6(취소 시각을 가진 예약 = 취소 상태인 예약)에 따르면, 취소되지 않은 예약에는 취소 시각이 없어야 해요. 덤프에서 `status`가 `cancelled`인 행은 B104와 B110 두 개이고, 바로 그 두 행에만 `cancelled_at`이 있습니다. 결측 비율만 보면 나빠 보이지만, 규칙과 맞춰 보면 오히려 R6을 지키고 있다는 증거예요. 결측은 비율이 아니라 **규칙과 함께** 읽습니다.

### 스스로 점검하기

1. 덤프에 행을 하나 더해 `ends_at` 혼자 유일 열 조합이라는 결과를 반증해 보세요. 어떤 예약을 더하면 되나요?
2. `member_name → member_id`를 우연으로 판단했습니다. 이 판단을 담당자 진술로 확인하려면 무엇을 물어야 할까요?
3. 회원 목록에 없는 M44에 대해 21장의 결정 세 갈래(제약으로 올림·정제 규칙·모델에서 허용) 가운데 무엇을 고를지, 답이 오기 전과 후로 나눠 적어 보세요.

#### 풀이

1. 이미 있는 예약과 끝 시각이 같은 예약을 더하면 됩니다. 예: `B113, M12, 박도윤, 상주, R3, , 2026-11-17 10:00, 2026-11-17 11:30, confirmed,`. B107과 끝 시각(11-17 11:30)이 같으므로 `ends_at`은 더 이상 유일하지 않습니다. 회의실이 다르므로(R1과 R3) 겹침 금지에는 걸리지 않습니다. 다른 회의실에서 같은 시각에 끝나는 예약은 흔한 일이라, `ends_at`이 키가 아니라는 판단을 뒷받침합니다.
2. "회원 가운데 이름이 같은 분이 있나요? 앞으로 생길 수도 있나요?"를 묻습니다. 지금 없더라도 생길 수 있다는 답이면, 이름으로 회원을 찾는 설계(예: 엑셀의 이름을 회원번호로 바꾸는 정제 규칙)에 동명이인 처리 규칙이 필요합니다.
3. 답이 오기 전에는 모델에서 허용합니다. 예약을 지우지 않고 M44를 "확인 대기" 회원으로 넣어 외래 키를 지키거나, 외래 키를 잠시 걸지 않고 감시 질의로 목록 밖 회원번호를 찾습니다. 답이 "회원 목록이 오래되었다"면 목록을 갱신하고 외래 키를 제약으로 올립니다. 답이 "탈퇴한 회원"이면 10장에서 정한 대로 회원을 지우지 않고 탈퇴 상태로 두므로, 목록에 M44를 탈퇴 상태로 넣고 외래 키를 제약으로 올립니다.
