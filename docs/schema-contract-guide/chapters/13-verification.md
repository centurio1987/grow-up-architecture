## 13장 검증: 인구 왕복과 추적표

이 장을 마치면 설계한 네 산출물이 서로 맞물리는지 세 가지 방법으로 확인할 수 있어요. 원장 줄과 산출물 요소를 잇는 **추적표**, 예제 데이터를 네 표현으로 차례로 옮겨 보는 **인구 왕복**, 규칙마다 반례를 넣어 보는 반례 시험입니다. 「틈」의 SQLite 판을 실제로 실행한 결과로 설명합니다.

### 무엇을 확인하는가

설계가 맞물린다는 것은 몇 가지 질문에 모두 "예"라고 답할 수 있다는 뜻입니다.

```text
1. 원장의 모든 f 가 개념 스키마의 사실 유형이 되었는가
2. 개념 스키마의 모든 사실 유형이 내부 스키마 어딘가에 기록되는가       (4장 조건 1)
3. 외부 스키마의 모든 열에 ← 를 달 수 있는가                            (3장)
4. 모든 제약·파생·계약 조항에 지키는 자리가 있는가                       (보장 위치표)
5. 모든 c 에 연산 계약이 있는가
6. 모든 q 가 답을 받았거나, 가정으로 등록되었는가
7. 예제 데이터를 넣으면 외부 스키마가 기대한 값을 내는가                  (인구 왕복)
8. 규칙을 어기는 데이터를 넣으면 지키는 자리가 거부하는가                 (반례 시험)
```

1~6은 표를 보고 확인하는 정적 검사이고, 7·8은 실제로 실행해 보는 동적 검사예요.

### 추적표

**추적표**는 원장 줄 하나가 네 산출물의 어디에 나타나는지 한 줄로 잇는 표입니다. 「틈」의 일부를 적어 볼게요.

| 원장 | 개념 | 외부 | 계약 | 내부 | 보장 |
| --- | --- | --- | --- | --- | --- |
| f1 예약 사실 | F4·F5·F6·F7 | V1·V2·V4 열 | O1 입력, E1 페이로드 | `booking` | 기본 키·NOT NULL |
| r1 30분·4시간 | R2 | — | O1 pre2 | `CHECK` | DB |
| r2 겹침 금지 | R3 | — | O1 inv1, 409 | `EXCLUDE` (SQLite 판은 트리거) | DB |
| r3 무료·초과 | F8, D2, D3 | V3 | E3 의미 겹 | `grade`, 청구 뷰 | 질의 |
| r4 늦은 취소 | R5, F9, D1 | V1 무료 취소 여부 | O2 post2 | `cancelled_at` | 질의 |
| v1 일정표 | — | V2 | — | 없음(뷰) | — |
| v2 회계 | — | E1~E3 | E1~E3 | `outbox` | 발행 과정 |
| c1 예약하기 | — | — | O1 | `idempotency`, `outbox` | DB + 발행 과정 |
| q1 올림 여부 | D3 | V3 초과 요금 | E3 의미 겹 | 청구 뷰 | **답 대기** |
| q4 월중 등급 변경 | F2', D4 | V3 | — | `member_grade_period` | 가정: 월말 기준 |

표를 채우다 보면 빈칸이 생깁니다. 빈칸은 둘 중 하나예요. 정말로 해당이 없거나(v1 일정표는 계약이 없는 내부 이용자), 설계가 빠뜨렸거나. 빠뜨린 것이면 원장으로 돌아갑니다. q1처럼 답을 기다리는 줄은 **굵게** 표시해서 누가 언제까지 답할지를 따로 관리해요.

q4 줄의 "가정: 월말 기준"은 답을 받지 못한 채 설계를 진행하려고 세운 **가정**입니다. 가정은 원장의 q를 지우지 않고 그대로 둔 채 "어떤 답을 가정했는가, 답이 다르면 무엇이 바뀌는가"를 적어요. 9장에서 본 대로 (나) 월초 기준이 답으로 오면 M07 김하나 회원의 11월 청구가 0원에서 21,000원으로 바뀝니다. 사용 330분에서 무료 120분을 빼면 초과 210분, 30분 단위로 7번, 7 × 3,000원이니까요. 이 숫자를 가정 옆에 적어 두면 답을 서둘러 받아야 할 이유가 보입니다.

### 인구 왕복

**인구 왕복**은 작은 예제 데이터(인구)를 정해 내부 스키마에 넣고, 외부 스키마로 꺼낸 결과가 손으로 계산한 기대값과 같은지 보는 검사입니다. 8장의 인구 검사가 개념 스키마를 시험했다면, 인구 왕복은 개념에서 내부를 거쳐 외부까지 이어지는 사상 전체를 시험해요.

12장의 DDL을 SQLite에서 실행할 수 있게 고친 판으로 실제로 해 봤습니다. 배제 제약 대신 트리거로 겹침을 막았고, 스크립트는 `verification/tum_roundtrip.py`, 결과는 `verification/tum-roundtrip-result.json`에 있어요. Python의 `sqlite3` 모듈(SQLite 3.53.0)로 실행했고, SQLite는 외래 키 검사가 기본으로 꺼져 있어서 `PRAGMA foreign_keys = ON`으로 켰습니다.

인구는 회원 셋, 회의실 셋, 11월 예약 일곱 건입니다.

```text
회원   M07 김하나  일반(11-01~11-14) → 상주(11-15~)
       M12 박도윤  상주
       M31 이서준  일반
등급   일반 무료 120분 · 상주 무료 600분 · 초과 30분당 3,000원
회의실 R1 정원 6 · R2 정원 4 · R3 정원 없음

예약   B101 M07 R1 11-17 10:00-11:30      B105 M31 R1 11-19 13:00-14:00
       B102 M12 R1 11-17 11:30-12:00      B106 M31 R2 11-20 15:00-17:00
       B103 M07 R2 11-17 14:00-16:00      B107 M07 R3 11-21 10:00-12:00
       B104 M31 R3 11-18 09:00-10:00
```

**11월 17일 아침의 일정표(V2).** 모든 예약이 확정인 상태에서 V2를 꺼내면 기대값은 그날 시작하는 확정 예약 셋이고, 회의실·시작순이어야 합니다. 실행 결과도 그랬어요.

```text
회의실 | 시작  | 끝    | 예약자 | 정원
R1     | 10:00 | 11:30 | 김하나 | 6
R1     | 11:30 | 12:00 | 박도윤 | 6
R2     | 14:00 | 16:00 | 김하나 | 4
```

**11월 말의 청구 명세(V3).** 한 달 동안 상태가 바뀌었다고 하고 전이를 넣었습니다. B101·B102·B103·B107은 이용완료, B106은 노쇼, B104는 11-18 08:30에 취소(시작 30분 전이라 늦은 취소), B105는 11-18 20:00에 취소(다음 날 13:00 시작이라 무료 취소)예요. 손으로 계산한 기대값부터 보겠습니다.

```text
M07  B101 90 + B103 120 + B107 120 = 330분   월말 등급 상주(600) → 초과 0
M12  B102 30                       =  30분   상주(600)           → 초과 0
M31  B104 60 (늦은 취소) + B106 120 (노쇼)
     B105 는 셈하지 않음 (무료 취소) = 180분   일반(120)           → 초과 60분
     초과 요금 = 올림(60 / 30) × 3,000 = 2 × 3,000 = 6,000원
```

실행 결과도 같았습니다.

```text
이름   | 등급 | 사용 분 | 무료 분 | 초과 분 | 초과 요금
김하나 | 상주 | 330     | 600     | 0       | 0
박도윤 | 상주 | 30      | 600     | 0       | 0
이서준 | 일반 | 180     | 120     | 60      | 6000
```

기대값을 **먼저** 손으로 계산한 다음 실행해야 한다는 점이 중요해요. 실행 결과를 보고 "그럴듯하다"고 넘어가면, 질의가 틀려도 결과에 맞춰 기대를 고치게 됩니다. M31의 B105가 셈에서 빠진 이유(취소가 시작 1시간 전보다 이름)와 B104가 들어간 이유(1시간 전보다 늦음)를 미리 적어 두었기 때문에, 질의가 R5를 제대로 옮겼는지 확인할 수 있었습니다.

### 반례 시험

**반례 시험**은 규칙마다 그 규칙을 어기는 데이터와 아슬아슬하게 지키는 데이터를 넣어, 지키는 자리가 기대대로 거부하고 받아들이는지 보는 검사입니다. 8장에서 담당자에게 보여 준 반례 인구를 이번에는 DB에 넣어 보는 거예요.

| 사례 | 기대 | 실제 결과 |
| --- | --- | --- |
| R1 10:00-11:30 확정이 있을 때 R1 11:00-12:00 확정 | 거부 | 거부 (R3 트리거) |
| R1 11:30-12:00 확정이 있을 때 R1 12:00-12:30 확정 | 받아들임 | 받아들임 |
| 확정 예약과 겹치는 시간의 취소된 예약 | 받아들임 | 받아들임 |
| 10:15 시작 | 거부 | 거부 (30분 경계 CHECK) |
| 4시간 30분 예약 | 거부 | 거부 (길이 CHECK) |
| 취소 시각 없는 취소 상태 | 거부 | 거부 (R6 CHECK) |
| M07에게 11-20부터 시작하는 일반 등급 기간 추가 | 거부 | 거부 (R8 트리거) |
| 이름 없는 활동 회원 | 거부 | 거부 (R9 CHECK) |
| 이용완료된 B101을 확정으로 되돌림 | 거부 | 거부 (R4 트리거) |
| 없는 회원 M99의 예약 | 거부 | 거부 (외래 키) |

표의 두 번째 줄은 아슬아슬하게 지키는 사례예요. 끝 시각과 다음 시작 시각이 같은 예약은 받아들여져야 합니다. 4장에서 본 `[시작, 끝)`의 뜻이 트리거의 겹침 조건(`b.시작 < 새.끝 AND 새.시작 < b.끝`)에 제대로 옮겨졌는지는 이 사례 하나로 확인돼요. 거부만 시험하면 너무 엄격한 규칙을 놓칩니다.

반례 시험을 짜다가 빈칸도 하나 찾았습니다. SQLite 판의 R3 트리거는 `INSERT`에만 걸려 있어요. 이미 있는 예약의 시작·끝을 `UPDATE`로 바꾸면 겹침을 검사하지 않습니다. 「틈」의 계약에는 예약 시간을 바꾸는 연산이 없지만, DB는 그런 `UPDATE`를 막지 않아요. 이 빈칸을 다루는 길은 둘입니다. `UPDATE`에도 트리거를 거는 것, 아니면 시각 열의 `UPDATE`를 예약 서비스 바깥에서 할 수 없게 권한으로 막고 보장 위치표에 적는 것. PostgreSQL 판의 배제 제약은 `UPDATE`에도 걸리므로 이 문제가 없습니다. 같은 개념 규칙이라도 내부 스키마 판마다 보장 범위가 다를 수 있다는 예예요.

### 계약 시험

마지막은 계약입니다. 11장에서 본 대로 계약 시험은 양쪽에서 해요.

```text
제공자 시험    O1 실패표의 줄마다 사례 하나
              (409 겹침, 422 형식, 403 비활동, 같은 멱등 키 재요청은 같은 응답 ...)
소비자 계약    회계 시스템이 E1 에서 쓰는 필드: eventId, bookingId, memberId, startAt, endAt
제공자 검증    예약 시스템 빌드에서 회계의 소비자 계약을 재생해 확인
```

이 저장소에서는 계약 시험을 실행하지 않았습니다. HTTP 서버와 이벤트 브로커가 없기 때문이에요. 그래서 이 절의 내용은 시험을 어떻게 짤지까지이고, 실행 결과는 없습니다. 검증을 보고할 때는 이처럼 무엇을 실행했고 무엇을 실행하지 않았는지를 나눠 적어야 해요.

| 검사 | 실행 여부 | 근거 |
| --- | --- | --- |
| 추적표(정적) | 손으로 함 | 이 장의 표 |
| 인구 왕복 V2·V3 | 실행함 (SQLite 3.53.0) | `verification/tum-roundtrip-result.json` |
| 반례 시험 10건 | 실행함 (SQLite 3.53.0) | 같은 파일 |
| PostgreSQL DDL | 실행 안 함 | 이 환경에 PostgreSQL 없음 |
| 계약 시험 | 실행 안 함 | HTTP 서버·브로커 없음 |

### 헷갈리기 쉬운 곳

1. 인구 왕복이 통과했다고 설계가 옳은 것은 아닙니다. 인구가 다루지 않은 경우(월중 등급 변경을 월초 기준으로 계산하는 경우, 30분 미만 초과의 올림)는 여전히 열려 있어요. 인구 왕복은 "이 인구에 대해서는 사상이 맞다"까지만 보여 줍니다. 21장에서 볼 "자료는 반증만 할 수 있다"와 같은 이야기예요.
2. 추적표는 한 번 만들고 끝나는 문서가 아닙니다. 원장에 줄이 더해지거나 계약이 바뀔 때마다 갱신해야 해요. 갱신하지 않은 추적표는 오히려 틀린 안심을 줍니다.
3. 반례 시험은 거부만 보면 반쪽입니다. 받아들여야 할 경계 사례(이어지는 예약, 취소된 예약의 겹침)를 함께 넣어야 규칙이 너무 엄격해진 것을 잡을 수 있어요.

### 잠깐 확인

q1(초과 요금 올림 여부)에 회계팀이 "내림"이라고 답했다고 합시다. 인구 왕복의 어느 값이 바뀔까요?

바뀌는 값은 없습니다. 이 인구에서 초과가 있는 회원은 M31 하나이고, 초과 60분은 30으로 나누어떨어지기 때문이에요. 올림이든 내림이든 2 × 3,000 = 6,000원입니다. q1의 답을 시험하려면 초과가 30의 배수가 아닌 사례가 필요해요. 그런 사례를 만들 수 있는지는 점검 문제 1에서 따져 보겠습니다.

### 스스로 점검하기

1. 위 인구에 q1을 시험할 예약 하나를 더해 보세요. 누구의 어떤 예약을 더하면 초과가 30의 배수가 아니게 되는지, 그때 올림과 내림의 기대값을 각각 계산해 보세요.
2. 추적표에 "t2 노쇼" 줄을 더해 보세요. 노쇼 판정 주체(q2)가 아직 정해지지 않았다면, 보장 열에 무엇을 적어야 할까요?
3. R3 트리거의 `UPDATE` 빈칸을 막는 트리거를 직접 써 보세요. `INSERT` 트리거와 무엇이 달라야 하나요?

#### 풀이

1. 만들 수 없습니다. 단계로 보면 이렇습니다. 먼저, R2에 따라 예약의 시작과 끝이 모두 30분 경계이므로 예약 길이는 30분의 배수입니다. 이어서 D1의 사용 분은 그런 길이들의 합이라 역시 30의 배수입니다. 그리고 무료 분은 120과 600으로 둘 다 30의 배수입니다. 마지막으로, 30의 배수에서 30의 배수를 빼면 30의 배수이고, 0과 견준 큰 쪽(max)도 30의 배수입니다. 따라서 지금 규칙에서 초과 분은 늘 30의 배수이고, 올림과 내림은 언제나 같은 값을 냅니다. 원장에는 "q1: 현재 규칙에서는 결과에 영향 없음. 예약 단위(R2)나 무료 분(F8)이 30의 배수가 아니게 바뀌면 다시 물음"이라고 적고 닫을 수 있습니다. 인구를 만들어 보려다가 그 인구가 불가능하다는 것을 알게 되는 것도 검증의 결과입니다.
2. `t2 노쇼 · F7 상태 값 · V1 상태 열 · E3 · booking.status = 'no_show' · 보장: 판정 주체 미정(q2)`. 판정이 정해지지 않았으므로 누가 `no_show`로 바꾸는지가 빈칸입니다. 보장 열에 "q2 답 전까지는 데스크가 수동으로 표시(가정)"처럼 가정을 적고, 가정이 틀렸을 때 바뀌는 것(예: 자동 판정이면 배치 작업과 그 계약)을 함께 적습니다.
3. 예시입니다.

```sql
CREATE TRIGGER r3_no_overlap_upd BEFORE UPDATE OF room_code, starts_at, ends_at, status ON booking
WHEN NEW.status = 'confirmed' AND EXISTS (
  SELECT 1 FROM booking b
  WHERE b.booking_id <> NEW.booking_id
    AND b.room_code = NEW.room_code AND b.status = 'confirmed'
    AND b.starts_at < NEW.ends_at AND NEW.starts_at < b.ends_at)
BEGIN SELECT RAISE(ABORT, 'R3 확정 예약 겹침'); END;
```

`INSERT` 트리거와 달리 `b.booking_id <> NEW.booking_id`가 있어야 합니다. 없으면 고치려는 예약이 자기 자신의 옛 행과 겹친다고 판단해 모든 수정을 거부합니다.
