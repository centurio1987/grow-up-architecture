## 18장 이벤트 스토밍 보드

이 장을 마치면 이벤트 스토밍 보드의 스티커를 종류별로 원장과 산출물에 옮길 수 있어요. 도메인 이벤트는 상태 변화 사실과 이벤트 계약으로, 명령은 연산 계약으로, 읽기 모델은 외부 스키마로, 집합체는 불변식을 지키는 범위로 갑니다. 보드가 거의 늘 빠뜨리는 것(속성, 식별, 빈도)을 채우는 질문도 다룹니다.

### 이벤트 스토밍이란

이벤트 스토밍은 Alberto Brandolini가 2013년 11월 블로그 글 「Introducing Event Storming」에서 소개한 워크숍 형식입니다. 그는 이것을 복잡한 업무 도메인을 빠르게 탐색하는 워크숍이라고 불렀고, 표기법이 아주 단순하다는 점을 강조했어요. 넓은 벽에 색 스티커를 붙여 가며, 도메인에서 일어난 일을 시간순으로 늘어놓는 방식입니다.

2013년 글에 적힌 진행 순서는 이렇습니다. 알맞은 사람들을 부르고 모델링 공간을 넉넉히 마련한 뒤 도메인 이벤트를 찾습니다. 그다음 이벤트가 어디서 왔는지(명령이나 외부 트리거)를 찾고, 마지막으로 집합체(aggregate)를 찾아요. 하위 도메인, bounded context, 핵심 인수 시험, 핵심 읽기 모델 스케치는 선택 목표로 들었습니다. eventstorming.com은 이 워크숍을 큰 그림(Big Picture), 프로세스 모델링(Process Modelling), 소프트웨어 설계(Software Design) 세 층위로 나눠 소개해요.

### 스티커 색: 원문과 지금의 관행

스티커 색에는 정본이 없습니다. 2013년 원문과 지금 흔히 쓰는 범례가 서로 다르고, 특히 보라색의 뜻이 달라요. 이 가이드는 둘을 나란히 적고, 색보다 **종류**로 옮깁니다.

| 종류 | 2013년 원문 | 지금 흔한 범례(2차 자료) |
| --- | --- | --- |
| 도메인 이벤트 | 주황 | 주황 |
| 명령 | 파랑 | 파랑 |
| 외부 시스템·시간 트리거 | 보라 | 외부 시스템은 분홍 |
| 정책("~하면 ~한다") | — | 보라 |
| 행위자·페르소나 | 연노랑(선택) | 작은 노랑 |
| 집합체 | (찾는 단계가 있음) | 노란 큰 직사각형 |
| 읽기 모델 | (선택 목표) | 초록 |
| 핫스팟(문제·질문) | — | 빨강 또는 진보라, 45도 기울여 붙임 |

지금 범례는 SAP가 정리한 DDD 자료 모음(2차 자료)에서 옮겼습니다. 여러 자료가 워크숍마다 범례를 벽에 붙여 두라고 권하는 것도 색이 이렇게 갈리기 때문이에요. 보드 사진을 받았다면 먼저 그 워크숍의 범례를 찾으세요. 보라 스티커가 외부 트리거인지 정책인지에 따라 원장의 칸이 달라집니다.

### 원장과 산출물로 옮기는 규칙

스티커 종류마다 가는 곳은 아래 표와 같아요. 이 대응은 이 가이드의 정리이고, 특히 집합체를 불변식의 범위로 읽는 것은 해석이라는 점을 밝혀 둡니다.

| 스티커 | 원장 칸 | 산출물 |
| --- | --- | --- |
| 도메인 이벤트(과거형) | F, C의 결과 | 개념 스키마의 상태 변화 사실, 이벤트 계약 E의 후보 |
| 명령 | C | 연산 계약 O |
| 행위자 | C의 행위자, V의 이용자 | 소비자, 이용자 목록 |
| 정책 | R | "이벤트 X가 생기면 명령 Y를 부른다"는 반응 규칙. 계약의 발행·구독 |
| 읽기 모델 | V | 외부 스키마 |
| 집합체 | R | 한 트랜잭션 안에서 함께 지켜야 하는 불변식의 범위 → 보장 위치표 |
| 외부 시스템 | V, C | 경계, 계약 |
| 핫스팟 | Q | 미결 질문 |

이벤트가 과거형이라는 점이 중요해요. "예약이 확정됨"은 이미 일어난 일이라서, 그 이벤트가 생겼다는 것은 곧 담화 세계에 사실 하나가 생겼다는 뜻입니다. 그래서 이벤트 하나에서 원장 줄이 둘 나와요. 하나는 상태가 바뀌었다는 사실(F), 다른 하나는 그것을 다른 이용자에게 알리는 이벤트 계약 후보(V 또는 C)입니다. 다른 팀이 그 이벤트를 받아야 한다면 계약이 되고, 같은 시스템 안의 일이면 계약 없이 끝나요.

### 「틈」의 보드

「틈」에서 프로세스 모델링 수준의 워크숍을 했다고 합시다. 보드를 시간순으로 글자로 옮기면 이렇게 됩니다. 이 워크숍은 지금 흔한 범례를 썼어요.

```text
[행위자 회원]  [명령 예약하기]   → [이벤트 예약이 확정됨]  → [정책 확정되면 회계에 알린다] → [외부 회계 시스템]
                  |
          [핫스팟 동시에 같은 시간을 누르면?]

[행위자 회원]  [명령 취소하기]   → [이벤트 예약이 취소됨]  → [정책 취소되면 회계에 알린다]
                                  [핫스팟 늦은 취소인지 누가 계산?]

[정책 시작 15분 뒤 입실 표시가 없으면 노쇼로 표시한다] → [명령 노쇼 표시] → [이벤트 노쇼로 표시됨]
          [핫스팟 입실 표시는 누가? 출입 기록은 안 씀]

[행위자 데스크] [명령 이용 완료 표시] → [이벤트 이용이 완료됨]

[행위자 청구 담당] [명령 월 마감하기] → [이벤트 월 청구가 마감됨]   (중요 이벤트: 이 뒤로 그달 예약은 바뀌면 안 됨)

[읽기 모델 오늘 일정표]  [읽기 모델 내 예약]  [읽기 모델 월 청구 명세]
[집합체 회의실 일정]  — 겹침 금지를 지키는 곳
```

원장으로 옮긴 일부입니다. 근거 수준은 모두 진술(워크숍 참석자 여럿)이에요.

| ID | 칸 | 내용 | 출처(스티커) |
| --- | --- | --- | --- |
| c1 | C | 회원이 예약한다 | 명령 예약하기 |
| f12 | F | 예약이 확정되었다(언제, 누가, 어느 방, 어느 구간) | 이벤트 예약이 확정됨 |
| r10 | R | 예약이 확정되면 회계에 알린다 | 정책 |
| r11 | R | 시작 15분 뒤 입실 표시가 없으면 노쇼로 표시한다 | 정책 |
| c5 | C | 청구 담당이 월 마감을 한다 | 명령 월 마감하기 |
| r12 | R | 월 마감 뒤에는 그달 예약의 상태를 바꿀 수 없다 | 중요 이벤트의 메모 |
| v1 | V | 데스크는 오늘 일정표를 본다 | 읽기 모델 |
| r3 | R | 같은 회의실 확정 예약은 겹치지 않는다(회의실 일정에서 지킴) | 집합체 회의실 일정 |
| q10 | Q | 두 회원이 동시에 같은 시간을 누르면? | 핫스팟 |
| q2 | Q | 입실 표시는 누가, 무엇으로 하나? | 핫스팟 |

### 보드에서 산출물로

몇 가지를 더 짚겠습니다.

**이벤트가 새 사실 유형을 낳습니다.** 예약이 확정됨이라는 이벤트에는 언제 확정됐는지가 붙어요. 그런데 8장의 개념 스키마에는 예약이 **확정된 시각**을 적는 사실 유형이 없었습니다. 예약 상태(F7)는 지금 상태만 말하니까요. 이벤트 스토밍 보드를 옮기면 상태가 바뀐 시각들이 자연스럽게 원장에 들어옵니다. 청구나 분쟁 처리에 그 시각이 필요한지 물어서, 필요하면 개념 스키마에 `예약 은 확정 시각 을 가진다` 같은 사실 유형을 더해요.

**정책은 반응 규칙이고, 경계를 넘으면 계약이 됩니다.** r10 "확정되면 회계에 알린다"는 11장의 post2(E1을 발행 예약함)와 같은 내용이에요. 정책이 같은 시스템 안에서 명령을 부르는 경우(r11 노쇼 표시)라면 내부 설계의 일이지만, 다른 팀 시스템으로 이어지면 이벤트 계약의 발행 조건이 됩니다.

**집합체는 불변식을 지키는 범위를 정합니다.** 보드에 회의실 일정이라는 집합체가 붙은 데는 이유가 있어요. 겹침 금지(R3)는 예약 하나만 보고는 지킬 수 없고, 같은 회의실의 예약 여럿을 함께 봐야 지킬 수 있습니다. 만약 집합체를 예약 하나로 잡았다면, 그 불변식을 지키는 곳이 집합체 바깥으로 나가야 해요. 4장에서 R3을 DB의 배제 제약으로 지키기로 한 것이 바로 그 바깥 자리입니다. 집합체를 무엇으로 잡든 보장 위치표에 R3을 지키는 자리가 하나 있어야 해요.

```text
집합체 = 예약 하나         → R3 은 집합체 밖에서: DB 배제 제약 (4장)
집합체 = 회의실 일정        → R3 은 집합체 안에서: 회의실 일정을 바꾸는 쓰기를 한 번에 하나씩
둘 다 가능. 고른 것을 보장 위치표에 적는다.
```

**중요 이벤트는 시점 경계입니다.** "월 청구가 마감됨" 뒤로 그달 예약이 바뀌면 안 된다는 r12는, 9장에서 본 "과거를 다시 조회하면 같은 답이 나와야 하는가"에 대한 답이에요. 마감 뒤의 늦은 노쇼 표시를 어떻게 할지(거절할지, 다음 달 조정으로 넘길지)를 q로 남깁니다.

**읽기 모델은 외부 스키마의 이름만 줍니다.** 보드의 초록 스티커 "오늘 일정표"에는 대개 열이 없어요. 9장의 절차로 다섯 항목을 채워야 합니다.

### 이 형식이 빼먹기 쉬운 것

| 빠지기 쉬운 것 | 이유 | 채우는 질문 |
| --- | --- | --- |
| 속성 | 스티커에는 이벤트 이름만 씀 | "이 이벤트가 일어났을 때 무엇을 알아야 하나요?" (페이로드) |
| 식별 | 이름은 있지만 무엇으로 부르는지 없음 | "어떤 예약이 취소되었는지 무엇으로 알죠?" |
| 빈도와 규모 | 보드는 흐름만 보여 줌 | "이 명령은 하루에 몇 번?" |
| 실패 흐름 | 일이 잘 풀리는 흐름 위주 | 명령마다 "거절되면 어떤 이벤트가?" (예: 예약이 거절됨을 남길지) |
| 시간에 따른 규칙 | 정책에 시각이 있어도 기준이 없음 | "15분은 예약 시작 기준인가요, 입실 예정 기준인가요?" |

### 헷갈리기 쉬운 곳

1. 모든 이벤트가 이벤트 계약이 되지는 않습니다. "이용이 완료됨"을 회계가 받아야 한다면 E3이 되지만, 데스크 화면만 바꾸는 이벤트라면 같은 시스템 안의 상태 변화일 뿐이에요. 경계를 넘는지가 기준입니다.
2. 명령이 거절되었다는 것도 사실일 수 있습니다. 보드에 "예약이 거절됨" 같은 이벤트가 없다면, 거절을 기록할 필요가 없다는 뜻인지 아무도 생각하지 않았다는 뜻인지 물어야 해요. 16장의 최소 보장 "시도가 기록된다"와 같은 질문입니다.
3. 보라 스티커를 색만 보고 옮기지 않습니다. 원문 범례면 외부 트리거, 지금 범례면 정책이에요. 범례를 확인하지 못했다면 스티커의 글을 보고 "~하면 ~한다" 꼴이면 정책으로, 시스템 이름이면 외부로 옮기고 q에 범례 확인을 남깁니다.

### 잠깐 확인

핫스팟 q10 "두 회원이 동시에 같은 시간을 누르면?"에 답하려면 산출물의 어디를 봐야 할까요?

계약 O1의 행위 겹(동시성)과 보장 위치표의 R3 줄입니다. 11장에서 "같은 구간을 겹치게 요청한 둘 가운데 먼저 커밋된 하나가 성공하고 나머지는 409를 받으며, 어느 쪽이 먼저인지는 보장하지 않는다"고 적었고, 4장에서 그것을 DB 배제 제약이 지키게 했어요. 핫스팟은 워크숍에서 나온 질문이고, 그 답은 계약과 보장 위치표에 적힙니다. 원장의 q10 옆에 "O1 동시성, R3 보장 위치"를 적고 닫습니다.

### 스스로 점검하기

1. 「틈」 보드의 "예약이 취소됨" 이벤트에 들어가야 할 페이로드를 정해 보세요. 회계가 늦은 취소인지 직접 계산하게 할지, 예약 시스템이 계산해서 보낼지에 따라 무엇이 달라지나요?
2. 정책 r11(시작 15분 뒤 입실 표시가 없으면 노쇼)을 보장 위치표의 한 줄로 적어 보세요. 지키는 자리가 DB일 수 있을까요?

#### 풀이

1. 최소한 예약번호, 회원번호, 시작, 끝, 취소 시각이 필요합니다. 회계가 직접 계산하게 하면 시작과 취소 시각을 모두 보내고, 늦은 취소 규칙(R5와 17장의 q9 경계)을 계약의 의미 겹에 적어 양쪽이 같은 식을 쓰게 해야 합니다. 예약 시스템이 계산해서 보내면 `countsAsUsage: true/false` 같은 필드를 더하고, 계산 규칙은 예약 시스템 쪽에만 둡니다. 뒤의 방식이 규칙을 한 곳에 두므로 어긋날 위험이 적지만, 회계가 근거를 확인하려면 시작과 취소 시각도 함께 받는 편이 좋습니다.
2. 예: `r11 노쇼 판정 · 지키는 자리: 예약 서비스의 주기 작업(5분마다) · 방법: 시작 + 15분이 지났고 입실 표시가 없는 확정 예약을 노쇼로 바꾸고 E3 발행 · 감시: 하루 한 번 시작 + 1시간이 지난 확정 예약이 남아 있는지 질의`. DB 제약은 값이 바뀔 때만 검사하고 시각이 지나는 것만으로는 아무 일도 하지 않으므로 지키는 자리가 될 수 없습니다. 정해진 간격으로 실행되는 주기 작업이 맡습니다. 입실 표시를 누가 하는지(q2)는 여전히 답을 기다립니다.

이어지는 실습: P06 온라인 강의 수강 신청(이벤트 스토밍 보드).
