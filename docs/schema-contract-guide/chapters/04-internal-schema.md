## 4장 내부 스키마: 저장과 접근의 선택

이 장을 마치면 내부 스키마를 논리 구조와 물리 선택 두 부분으로 나눠 적고, 개념-내부 사상이 뜻을 지키는지 네 조건으로 확인할 수 있어요. 인덱스·분할·비정규화 같은 결정이 **작업 부하**에서 나온다는 것도 「틈」의 예로 보이게 됩니다.

### 정의와 이 가이드가 그은 경계

1985년 ANSI/SPARC 후속 보고서는 내부 스키마가 무엇을 어떻게 저장하는지 규정한다고 말합니다. 효율을 반영한 저장 구조의 추상 모델이고, 표현 방식과 접근 경로가 여기에 들어가요.

1970년대 보고서는 DBMS가 개념 스키마를 직접 알고, 내부 스키마는 그 아래 저장 구조를 맡는 그림을 그렸습니다. 오늘날의 관계형 DBMS는 개념 스키마를 따로 갖고 있지 않아요. DBMS가 아는 것은 테이블·열·키·제약·인덱스입니다. 그러면 테이블 구조는 개념 쪽일까요, 내부 쪽일까요?

이 가이드는 테이블 구조를 **내부 쪽**에 둡니다. 이유는 하나예요. 같은 개념 스키마를 여러 테이블 구조로 실현할 수 있고, 그중 하나를 고르는 일은 구현 선택이기 때문입니다.

```text
개념 스키마 (하나)
  예약 은 상태 에 있다 · 상태 전이는 확정 → 취소|이용완료|노쇼
          |
          +--▶ 구조 A: booking 표에 status 열 하나 (현재 상태만)
          +--▶ 구조 B: booking 표 + booking_event 표 (상태가 바뀔 때마다 한 줄)
          +--▶ 구조 C: 상태별로 표를 나눔 (confirmed_booking, cancelled_booking, ...)
```

셋 모두 같은 개념 사실을 기록할 수 있습니다. B는 상태가 바뀐 때를 모두 남기고, A는 지금 상태만 남겨요. 어느 쪽이 맞는지는 개념 스키마가 아니라 질의 빈도와 보관 요구가 정합니다. 그래서 이 가이드의 내부 스키마는 두 층으로 적어요.

| 부분 | 담는 것 | 주로 적는 곳 |
| --- | --- | --- |
| 논리 구조 | 테이블, 열, 기본 키·외래 키, 검사 제약 | `CREATE TABLE` |
| 물리 선택 | 자료형 세부, 인덱스, 분할, 실체화 뷰, 저장 매개변수 | `CREATE INDEX`, `PARTITION BY`, 운영 설정 |

ER 모델을 만든 Chen도 1976년 논문에서 데이터 관점을 네 층으로 나눴습니다. 머릿속의 개체·관계 정보, 정보 구조, 접근 경로와 무관한 데이터 구조, 접근 경로에 의존하는 데이터 구조예요. 이 가이드의 논리 구조는 Chen이 말한 접근 경로와 무관한 층, 물리 선택은 접근 경로에 의존하는 층에 가깝습니다. 다만 Chen의 네 층과 ANSI/SPARC 세 층은 나누는 기준이 다릅니다. 세 층은 누구의 관점인지로 나누고, Chen의 네 층은 얼마나 구체적인지로 나눠요.

### 사상이 뜻을 지키는가: 네 조건

ISO/TR 9007은 개념 스키마의 역할 가운데 하나로, 여러 데이터 표현 사이를 옮길 때 뜻이 보존되게 하는 것을 듭니다. 개념-내부 사상이 뜻을 지키는지 확인하려면 다음 네 가지를 보면 됩니다. 원전의 조건이 아니라 이 가이드가 점검용으로 정리한 목록이에요.

```text
1. 기록   모든 기본 사실 유형이 내부 스키마 어딘가에 기록되는가
2. 식별   개념의 참조 방식이 저장된 키로 옮겨지는가
3. 단일   같은 사실이 두 곳에 있다면, 누가 둘을 맞추는지 정해져 있는가
4. 보장   모든 제약에 그것을 지키는 자리가 있는가
```

1번을 어기면 정보가 사라지고, 2번을 어기면 같은 대상을 다른 대상으로 착각하게 됩니다. 3번을 어기면 두 곳의 값이 어긋나요. 4번을 어기면 규칙을 어긴 상태가 그대로 저장됩니다. 4번이 특히 손이 많이 가서 따로 표를 만듭니다.

### 보장 위치표

「틈」의 제약마다 어디서 지킬지 정해 보겠습니다. 이 표를 **보장 위치표**라고 부를게요. 이 가이드가 만든 이름입니다.

| 규칙 | 지키는 자리 | 방법 |
| --- | --- | --- |
| R1 회원마다 이름 하나, 예약마다 회원·회의실·시각·상태 하나 | DB | `NOT NULL`, 열 하나에 값 하나 |
| R2 끝 > 시작, 30분 단위, 4시간 이하 | DB | `CHECK` |
| R3 확정 예약은 같은 회의실에서 겹치지 않음 | DB | 배제 제약(`EXCLUDE`) |
| R4 상태 전이는 확정에서만 | 응용의 단일 쓰기 경로 + DB 트리거 | 전이표 검사 |
| R5 시작 1시간 전보다 늦은 취소는 사용으로 셈 | 응용 | 취소 시각을 기록하고 청구 집계에서 계산 |
| D1·D2 월 사용 분·초과 분 | 질의 | 청구용 뷰 |

R3은 일반 `UNIQUE`로는 지킬 수 없어요. 같은 값이 두 번 나오는 것을 막는 게 아니라 구간이 **겹치는** 것을 막아야 하니까요. PostgreSQL은 이런 규칙을 위해 배제 제약을 제공합니다.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- text 열의 = 를 GiST 에서 쓰려고

CREATE TABLE booking (
  booking_id   text        PRIMARY KEY,                       -- 참조 방식: 예약번호
  member_id    text        NOT NULL REFERENCES member(member_id),
  room_code    text        NOT NULL REFERENCES room(room_code),
  starts_at    timestamptz NOT NULL,
  ends_at      timestamptz NOT NULL,
  status       text        NOT NULL
               CHECK (status IN ('confirmed', 'cancelled', 'used', 'no_show')),
  cancelled_at timestamptz,
  CHECK (ends_at > starts_at),                                -- R2
  CHECK (ends_at - starts_at <= interval '4 hours'),          -- R2
  CHECK (extract(epoch FROM starts_at)::bigint % 1800 = 0
         AND extract(epoch FROM ends_at)::bigint % 1800 = 0),  -- R2: 30분(1800초) 경계
  CHECK ((status = 'cancelled') = (cancelled_at IS NOT NULL)),
  EXCLUDE USING gist (
    room_code WITH =,
    tstzrange(starts_at, ends_at) WITH &&                     -- R3
  ) WHERE (status = 'confirmed')
);
```

여기서 가장 중요한 줄은 `tstzrange(starts_at, ends_at) WITH &&` 입니다. `tstzrange`는 기본으로 시작을 포함하고 끝을 포함하지 않는 구간 `[시작, 끝)`을 만들어요. 그래서 10:00-11:30 예약 뒤에 11:30-12:00 예약을 넣어도 겹치지 않습니다. 1장에서 "끝 시각을 포함으로 볼지 불포함으로 볼지"가 뜻의 변경이라고 했지요. 그 결정이 바로 이 한 줄에 들어 있습니다. 구간을 `'[]'`로 바꾸면 같은 데이터가 갑자기 규칙 위반이 됩니다.

> 개념 스키마의 한 문장이 DDL의 한 줄이 되기도 하고, 응용 코드 한 곳이 되기도 합니다. 어느 쪽이든 표에 적어 둡니다.

이 DDL은 이 저장소 환경에 PostgreSQL이 없어서 실제로 실행해 보지 못했습니다. 배제 제약에 `WHERE`를 붙이는 문법과 `btree_gist` 확장은 PostgreSQL 공식 문서에 근거해 썼어요. 실습 풀이의 DDL은 SQLite에서 실행할 수 있는 부분을 실제로 실행했고, 그 결과는 `verification/`에 있습니다.

R5처럼 DB 제약으로 쓰기 어려운 규칙도 있습니다. "시작 1시간 전보다 늦은"은 취소하는 **순간의 시각**에 달려 있어서, 저장된 값만 보는 `CHECK`로는 표현이 어색해요. 이런 규칙은 취소 시각을 기록해 두고(`cancelled_at`), 청구를 계산할 때 응용이나 질의가 판정하게 합니다. 지키는 자리가 DB가 아니라는 사실을 표에 적어 두는 것, 그것이 2장의 100% 원칙을 내부 스키마에서 이어 가는 방법입니다.

### 작업 부하가 물리 선택을 정한다

물리 선택은 무엇을 근거로 할까요? Ramakrishnan·Gehrke의 교재 『Database Management Systems』(3판) 물리 설계 장의 강의 슬라이드는 이렇게 말합니다. "We must begin by understanding the workload." 가장 중요한 질의와 그 빈도, 가장 중요한 갱신과 그 빈도, 각각의 성능 목표가 입력이라는 거예요.

Codd도 1970년 논문에서 같은 방향을 가리켰습니다. 정보의 관점에서 인덱스는 중복된 구성 요소라고 했어요. 인덱스가 있으면 질의는 빨라지고 삽입·삭제는 느려집니다. 그래서 이용 패턴이 바뀌면 인덱스를 만들고 없앨 수 있어야 한다는 거예요. 인덱스는 정보를 더하지 않고, 작업 부하에 맞춰 넣고 빼는 도구라는 뜻입니다.

「틈」의 작업 부하를 표로 적어 보겠습니다. 빈도는 설명을 위해 **가정한 값**입니다.

| 번호 | 무엇 | 빈도(가정) | 조건과 순서 | 목표(가정) |
| --- | --- | --- | --- | --- |
| W1 | 회원의 다가오는 예약 조회 | 하루 300회 | `member_id = ? AND starts_at >= now()` 시작순 | 0.2초 이내 |
| W2 | 예약하기 | 하루 60회 | 같은 회의실·겹치는 구간이 있는지 | 0.5초 이내 |
| W3 | 오늘 일정표 | 하루 50회 | 오늘 시작하는 확정 예약, 회의실·시작순 | 0.5초 이내 |
| W4 | 월 청구 집계 | 월 1회 | 한 달 치 예약 전부 | 1분 이내 |

표를 보고 결정을 내립니다. 결정마다 근거가 된 작업 부하 줄과 비용을 같이 적어요.

```text
[결정] IX1 B-tree 인덱스 (member_id, starts_at)
  근거   W1: 선두 열이 같음 조건, 둘째 열이 범위 조건이라 다중 열 인덱스에 맞음
  비용   예약을 쓸 때마다 인덱스도 갱신 (W2 하루 60회, 작음)

[결정] IX2 배제 제약이 만드는 GiST 인덱스를 W2 에 그대로 씀
  근거   W2 의 겹침 검사와 R3 이 같은 조건
  비용   추가 없음 (제약이 이미 만듦)

[결정] IX3 W3 용 인덱스는 따로 만들지 않음
  근거   오늘 예약은 수십 건. IX2 의 GiST 인덱스나 순차 탐색으로 충분하다고 봄
  재검토 예약이 하루 수천 건을 넘거나 W3 목표를 못 맞추면

[결정] PT1 분할하지 않음
  근거   한 해 예약이 2만여 건(하루 60건 가정). PostgreSQL 문서는 분할의 이득이
         대개 테이블이 아주 클 때만 있고, 경험칙으로 테이블이 서버 메모리보다
         클 때라고 함
  재검토 보관 기간 정책이 생겨 오래된 예약을 한꺼번에 지워야 할 때
```

IX1은 PostgreSQL 문서의 다중 열 인덱스 설명과 맞습니다. 선두 열의 같음 조건과 그다음 열의 범위 조건이 탐색 범위를 줄인다고 하고, 다중 열 인덱스는 아껴 쓰라고도 권해요. PT1의 근거로 든 경험칙도 같은 문서의 분할 절에 있습니다.

여기서 헷갈리기 쉬운 포인트는 자주 쓰는 열에는 일단 인덱스를 걸고 보는 습관입니다. 인덱스 하나하나가 쓰기 비용을 더합니다. PostgreSQL 문서도 인덱스를 테이블과 계속 맞춰야 하므로 데이터 조작에 부담이 더해진다고 적어요. 작업 부하 표의 어느 줄에도 기대지 않는 인덱스는 비용만 남깁니다.

### 정규화와 비정규화

논리 구조를 고를 때 오래 쓰여 온 기준이 정규형입니다. 연표와 뜻을 간단히 정리하면 아래와 같아요. 2NF 이후의 정의와 연표는 교재·백과사전 수준의 2차 자료로 확인했습니다.

| 정규형 | 처음 나온 곳 | 요지 |
| --- | --- | --- |
| 1NF | Codd 1970 | 칸에 집합이나 중첩 구조를 넣지 않음 |
| 2NF, 3NF | Codd 1971 보고서(1972 단행본 재수록) | 키가 아닌 속성이 키 전체에, 키에만 종속 |
| BCNF | Boyce·Codd 1974 | 자명하지 않은 함수 종속의 왼쪽은 모두 슈퍼키 |
| 4NF | Fagin 1977 | 자명하지 않은 다치 종속의 왼쪽도 모두 슈퍼키 |

정규형이 막는 것은 **갱신 이상**이에요. 「틈」에서 예약 표에 회원 이름을 함께 넣었다고 해 봅시다.

```text
booking (비정규화한 경우)
booking_id  member_id  member_name  room_code  starts_at
B101        M07        김하나        R1         11-17 10:00
B105        M07        김하나        R2         11-18 14:00
B120        M07        김하나        R1         11-20 09:00

김하나 회원이 이름을 "김하늘"로 바꿈
→ 세 줄을 모두 고쳐야 함. 하나라도 빠뜨리면 같은 회원이 두 이름을 가짐
```

member_id → member_name 이라는 함수 종속이 있는데, member_id가 이 표의 키가 아니어서 생기는 문제입니다. 회원 이름을 회원 표에만 두면 고칠 곳이 한 곳이 돼요.

그렇다면 비정규화는 언제 할까요? Ramakrishnan·Gehrke는 질의가 충분히 중요하고, 인덱스나 다른 3NF 구조로는 성능을 얻을 수 없을 때만 고려하라고 합니다. 이 가이드는 여기에 조건을 하나 더 붙여요. 비정규화로 같은 사실이 두 곳에 생기면, 앞의 네 조건 가운데 3번(단일)에 따라 **누가 둘을 맞추는지**를 보장 위치표에 적어야 합니다. 적지 않은 비정규화는 어긋남을 예약해 둔 것과 같아요.

### 헷갈리기 쉬운 곳

1. 내부 스키마 = DDL이라고 보면 빠지는 것이 생깁니다. "예약 쓰기는 예약 서비스 한 곳에서만 한다" 같은 결정은 DDL에 나타나지 않지만, R4를 지키는 자리이므로 내부 설계에 속해요. 보장 위치표가 그런 결정을 담는 그릇입니다.
2. 인덱스가 규칙을 지킨다고 생각하기 쉽습니다. 일반 인덱스는 찾는 길을 만들 뿐 규칙을 지키지 않아요. 규칙을 지키는 것은 `UNIQUE`나 `EXCLUDE` 같은 **제약**이고, 제약이 내부적으로 인덱스를 쓸 뿐입니다.
3. 내부 스키마도 이용자에게 보일 수 있습니다. 회계 시스템이 예약 표를 직접 읽는다면, 그 순간 예약 표의 열 이름이 회계 시스템의 외부 스키마가 되어 버려요. 그러면 내부 스키마를 바꿀 자유가 사라집니다. 실습 P14(철물점 재고)가 바로 이런 경우입니다.

### 잠깐 확인

W1 조회가 느려서 `booking` 표에 회원 이름 열을 더하자는 제안이 나왔습니다. 받아들여야 할까요?

먼저 W1이 무엇 때문에 느린지 봐야 합니다. W1은 회원 자신의 예약을 보는 조회라서 회원 이름은 한 번만 가져오면 되고, 조인 비용도 작아요. 느린 원인은 이름 조인보다 `(member_id, starts_at)` 인덱스가 없는 쪽일 가능성이 큽니다. 인덱스로 해결된다면 비정규화는 하지 않아요. 그래도 비정규화를 한다면, 회원 이름이 바뀔 때 예약 표의 이름을 누가 고치는지를 보장 위치표에 적어야 합니다.

### 스스로 점검하기

1. 「틈」에 "회의실별 월 가동률"을 매일 아침 경영 보고서로 보여 주자는 요구가 생겼습니다. 작업 부하 표에 줄 하나를 더하고, 실체화 뷰를 쓸지 결정 기록 형식으로 적어 보세요.
2. 상태 이력을 남겨야 한다는 요구가 생겨 구조 A를 구조 B로 바꾸려 합니다. 네 조건(기록·식별·단일·보장) 가운데 특히 신경 써야 할 것은 무엇이고 왜인가요?
3. 배제 제약의 구간을 `tstzrange(starts_at, ends_at, '[]')`로 쓰면 어떤 예약이 거부될까요? 구체적인 두 예약으로 보여 주세요.

#### 풀이

1. 작업 부하에 `W5 회의실별 월 가동률 · 매일 아침 1회 · 이번 달 예약 전부 회의실별 합계 · 1초 이내(가정)`를 더합니다. 결정은 예를 들어 이렇게 적습니다. `[결정] MV1 실체화 뷰를 만들지 않음 · 근거: 한 달 예약이 2천 건 안팎이라 매번 집계해도 W5 목표 안 · 재검토: 집계가 목표를 넘을 때`. 반대로 실체화 뷰를 만든다면 갱신 주기(매일 새벽)와 신선도(아침 보고서는 전날까지)를 함께 적어야 합니다. PostgreSQL의 실체화 뷰는 `REFRESH`를 해야 바뀌기 때문입니다.
2. 3번 단일입니다. 구조 B에서 현재 상태를 `booking.status`에도 두고 `booking_event`의 마지막 줄에도 두면 같은 사실이 두 곳에 생깁니다. 상태를 바꾸는 쓰기가 두 곳을 같은 트랜잭션에서 함께 바꾸게 하거나, 현재 상태를 이벤트 표에서 계산하고 `status` 열을 없애야 합니다. 어느 쪽을 골랐는지 보장 위치표에 적습니다.
3. 끝을 포함하는 구간이 되므로 R1 10:00-11:30 확정 예약이 있을 때 R1 11:30-12:00 예약이 거부됩니다. 두 구간이 11:30 한 점에서 겹치기 때문입니다. 업무상으로는 이어지는 예약이 정상이므로, 개념 스키마의 R3이 "끝 시각은 다음 예약의 시작 시각과 같아도 된다"는 뜻을 담고 있다면 `'[)'`가 맞습니다.
