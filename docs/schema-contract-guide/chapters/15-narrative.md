## 15장 서사 시나리오와 도메인 스토리

이 장을 마치면 사람과 시간이 나오는 이야기(서사 시나리오)와 그림 문장으로 된 도메인 스토리를 원장으로 옮길 수 있어요. 이야기 형식이 특히 잘 빠뜨리는 것(대안 흐름, 수량, 식별)을 질문으로 바꾸는 방법도 익힙니다.

### 두 형식

**서사 시나리오**는 특정한 사람이 특정한 때에 무엇을 하는지 이야기로 적은 글입니다. 콘셉트 문서 안에 "11월 17일 아침, 김하나 씨는…" 같은 단락으로 들어 있는 경우가 많아요. 정해진 표준 형식은 없고, 이 가이드에서는 등장인물·시각·사건·결과가 있는 이야기를 모두 서사 시나리오로 부릅니다. 사람과 시간이 있다는 점이 중요해요. 7장에서 F 칸은 구체적일수록 좋다고 했는데, 서사 시나리오는 처음부터 구체적인 값을 줍니다.

**도메인 스토리텔링**은 Stefan Hofer와 Henning Schwentner가 2021년 책 『Domain Storytelling』(Addison-Wesley)에서 정리한 방법입니다. 출간일은 소스마다 9월과 10월로 다르게 적혀 있어요. 출판사 발췌로 확인한 그림 언어는 다섯 요소로 되어 있습니다.

| 요소 | 그리는 법 | 「틈」의 예 |
| --- | --- | --- |
| 행위자 | 사람이나 역할(막대 인물), 시스템도 가능 | 회원, 데스크 직원, 예약 시스템 |
| 작업 객체 | 활동이 다루는 것(문서·물건·디지털 객체) | 예약, 일정표, 회의실 |
| 활동 | 행위자와 작업 객체를 잇는 화살표와 동사 | 만든다, 출력한다, 안내한다 |
| 순번 | 화살표에 붙인 번호. 이야기의 순서 | ①, ②, ③ |
| 주석 | 짧은 맥락 메모 | "상주 회원은 무료 10시간" |

책이 든 문장 예는 "Cashier suggests available seats to moviegoer."예요. 행위자(cashier)·활동(suggests)·작업 객체(seats)·다른 행위자(moviegoer)가 한 문장에 들어 있습니다. 발췌에 따르면 도메인 스토리에는 "만약"이나 "또는"이 없어요. 중요한 대안은 따로 스토리를 만들고, 먼저 보이는 것이 일이 잘 풀리는 흐름입니다.

### 원장으로 옮기는 규칙

두 형식 모두 "누가 무엇을 언제 했다"가 기본 단위라서 옮기는 규칙이 비슷합니다.

| 씨앗의 요소 | 원장 칸 | 메모 |
| --- | --- | --- |
| 등장인물·행위자 | C의 행위자, V의 이용자 | 사람 이름은 역할로 바꿔 적음(김하나 씨 → 회원) |
| 시스템 행위자 | C의 행위자, 경계 후보 | 다른 팀 시스템이면 계약 후보 |
| 작업 객체·명사 | T, F의 개체 후보 | 이름이 같은지 다른지 용어 칸에서 맞춤 |
| 활동·사건 동사 | C, 또는 F(완료된 사건) | "예약했다"는 F, "예약한다"는 C |
| 시각·날짜·순번 | F의 값, C의 순서 | 시각이 있으면 시간대도 물음 |
| "~해야", "~못 한다", "~까지만" | R | 근거 수준은 진술 |
| 보는 장면("화면에 뜬다", "출력한다") | V | 무엇을 보는지, 누가 보는지 |
| 주석, 괄호 안 설명 | R 또는 Q | 규칙인지 예외인지 모르면 Q |

활동 동사를 C로 적을지 F로 적을지는 시제로 가르면 편합니다. 이야기 속에서 이미 일어난 일("예약을 마쳤다")은 그 결과로 남는 사실(F)이고, 이야기가 보여 주는 행동("예약 버튼을 누른다")은 연산(C)이에요. 대개 둘 다 적습니다. 연산이 있으면 그 연산이 남기는 사실도 있기 마련이니까요.

### 「틈」으로 해 보기

콘셉트 문서에 아래 단락이 들어 있었다고 합시다. 문장 번호를 붙였습니다.

```text
s1 11월 17일 화요일 아침 9시, 데스크의 이지원 씨는 그날 일정표를 출력한다.
s2 일정표에는 R1 10시~11시 반 김하나, R1 11시 반~12시 박도윤, R2 2시~4시 김하나가 있다.
s3 10시 5분 전, 김하나 씨의 손님 두 명이 데스크에 와서 김하나 씨의 회의실을 묻는다.
s4 이지원 씨는 일정표를 보고 R1로 안내한다.
s5 김하나 씨는 회의가 길어질 것 같아 10시 40분에 앱에서 R1을 12시까지 늘리려 하지만,
   11시 반부터 박도윤 씨 예약이 있어 늘리지 못한다.
s6 대신 R3이 비어 있어 11시 반~12시를 R3으로 새로 예약한다.
```

같은 장면을 도메인 스토리 문장으로 쓰면 이렇게 됩니다. "만약"이 없도록 늘리기에 실패한 흐름은 따로 떼었어요.

```text
스토리 A (늘리기가 안 되는 날)
  ① 데스크 직원이 일정표를 출력한다
  ② 손님이 데스크 직원에게 회원의 회의실을 묻는다
  ③ 데스크 직원이 일정표를 보고 손님을 회의실로 안내한다
  ④ 회원이 예약 시스템에 예약 연장을 요청한다
  ⑤ 예약 시스템이 회원에게 연장 불가를 알린다      (주석: 다음 예약과 겹침)
  ⑥ 회원이 예약 시스템에 다른 회의실 예약을 만든다
```

원장으로 옮기면 다음과 같습니다. 근거 수준은 모두 진술이에요.

| ID | 칸 | 내용 | 출처 |
| --- | --- | --- | --- |
| v1 | V | 데스크 직원은 아침에 오늘 일정표를 출력해 본다 | s1, ① |
| f1 | F | 2026-11-17 R1 10:00~11:30 김하나 예약이 있다 | s2 |
| f2 | F | 2026-11-17 R1 11:30~12:00 박도윤 예약이 있다 | s2 |
| v5 | V | 데스크 직원은 손님에게 회원 이름으로 회의실을 찾아 준다 | s3, ②③ |
| c3 | C | 회원이 자기 예약의 끝 시각을 늘린다(연장) | s5, ④ |
| r1 | R | 연장한 구간이 다음 확정 예약과 겹치면 연장할 수 없다 | s5, ⑤ |
| c1 | C | 회원이 새 예약을 만든다 | s6, ⑥ |
| q1 | Q | 연장은 기존 예약의 끝을 바꾸는가, 새 예약을 이어 붙이는가? | s5 |
| q2 | Q | 일정표를 출력한 뒤 생긴 예약(s6의 R3)을 데스크는 어떻게 아는가? | s1, s6 |
| q3 | Q | 손님이 회원 이름을 말하지 않으면 데스크는 무엇으로 찾는가? | s3 |

이 단락에서 새로 나온 것이 둘 있습니다. 하나는 c3 **연장**이라는 연산이에요. 7장의 콘셉트 메모에는 없던 연산입니다. 연장이 기존 예약의 끝 시각을 바꾸는 것이라면, 13장에서 찾은 빈칸(예약 시간을 `UPDATE`로 바꾸는 경로에 겹침 검사가 없음)이 곧장 실제 문제가 됩니다. 다른 하나는 v5, 손님이 회원 이름으로 회의실을 찾는 장면이에요. V2 일정표에 예약자 이름이 있어야 하는 이유가 이 장면에서 나옵니다.

개념 스키마 조각으로 옮기면 이렇게 됩니다.

```text
[연산 후보] O3 연장하기(예약번호, 새 끝 시각)
  pre   예약이 확정, 새 끝 > 지금 끝, 새 끝 - 시작 ≤ 240분 (R2)
  post  예약의 끝 시각이 새 끝으로 바뀜          ← q1 답이 "바꾼다"일 때
  inv   R3 (겹침 금지) — 바뀐 구간으로 다시 검사
  실패  inv1 충돌 → 409 slot_taken (상태 변화 없음)
```

연장이 기존 예약을 바꾸는 것인지, 새 예약을 잇는 것인지(q1)에 따라 청구도 달라집니다. 새 예약을 잇는다면 예약 두 건이 생기고, 늦은 취소 규칙(R5)도 예약마다 따로 적용되니까요. 서사 하나가 연산 하나와 질문 셋을 낳았어요.

### 이야기 형식이 빼먹기 쉬운 것

이야기는 대개 일이 잘 풀리는 하루를 보여 줍니다. 그래서 빠지는 것에 일정한 무늬가 있어요. 빠진 것을 찾는 질문을 함께 적어 둡니다.

| 빠지기 쉬운 것 | 찾는 질문 | 「틈」에서 |
| --- | --- | --- |
| 대안 흐름 | 이 장면에서 일이 틀어지면 어떻게 되나요? | 손님이 회원 이름을 모르면? (q3) |
| 수량과 상한 | 몇 개까지 되나요? 최대 얼마인가요? | 연장은 몇 번까지? 총 4시간 상한은 연장에도? |
| 식별 | 그것을 무엇으로 부르나요? 같은 이름이 둘이면? | 동명 회원 둘이면 손님 안내는? |
| 시간대·시점 | 그 시각은 언제 기준인가요? 그 뒤에 바뀌면? | 출력 뒤 생긴 예약 (q2) |
| 빈도 | 이런 일이 하루에 몇 번 있나요? | 연장 요청 빈도 |
| 지워지는 것 | 이 기록은 언제까지 남나요? | 연장 이력을 남기는가 |

도메인 스토리는 "만약"을 쓰지 않으므로, 대안 흐름은 **스토리를 하나 더 그려 달라고** 요청하는 방식으로 얻습니다. "연장이 되는 날의 스토리도 그려 볼까요?" 같은 식이에요. 스토리가 둘이 되면 두 스토리의 차이가 곧 규칙(r1)이 됩니다.

### 헷갈리기 쉬운 곳

1. 이야기 속 사람 이름을 원장에 그대로 옮기면 안 됩니다. "김하나 씨"는 회원이라는 역할의 한 예예요. F 칸에는 예로 남기되(f1의 김하나), C와 V 칸에는 역할로 적습니다. 이야기 속 김하나 씨가 상주 회원이라서 생긴 일이라면, 그 사실(등급)도 F로 따로 적어야 합니다.
2. 이야기의 순서가 규칙의 순서는 아닙니다. s1에서 일정표를 9시에 출력했다고 해서 "일정표는 9시에 출력해야 한다"는 규칙이 생기지는 않아요. 그런 규칙이 있는지는 q로 묻습니다.
3. 도메인 스토리의 작업 객체가 모두 개체 유형이 되는 것도 아닙니다. "일정표"는 작업 객체지만 개념 스키마의 개체가 아니라 외부 스키마(V2)예요. 작업 객체를 옮길 때마다 "이것은 담화 세계의 사물인가, 사물을 보여 주는 문서인가"를 묻습니다.

### 잠깐 확인

s5의 "11시 반부터 박도윤 씨 예약이 있어 늘리지 못한다"는 원장의 어느 칸에 무엇으로 적었고, 그것은 개념 스키마의 어떤 기존 규칙과 같은가요?

r1로 적었고, 개념 스키마의 R3(확정 예약끼리 같은 회의실이면 구간이 겹치지 않음)과 같은 규칙입니다. 새 규칙이 아니라, 기존 규칙이 연장이라는 새 연산에도 걸린다는 것을 이야기가 보여 준 거예요. 원장에는 r1을 적되 "R3과 같음"을 메모로 붙여, 13장 추적표에서 한 줄로 이어지게 합니다.

### 스스로 점검하기

1. 스토리 A와 짝이 되는 "연장이 되는 날"의 스토리 B를 순번 문장으로 써 보세요. 두 스토리의 차이에서 무엇이 규칙으로 나오나요?
2. q2(출력 뒤 생긴 예약)에 데스크 직원이 "점심때 한 번 더 출력해요"라고 답했다고 합시다. 이 답을 원장에 어떻게 반영하고, V2의 다섯 항목 가운데 무엇이 바뀌나요?

#### 풀이

1. 예시입니다. ① 회원이 예약 시스템에 예약 연장을 요청한다 ② 예약 시스템이 연장한 예약을 회원에게 보여 준다 ③ 예약 시스템이 회계 시스템에 예약이 바뀌었음을 알린다. 스토리 A의 ⑤와 B의 ②가 갈리는 조건(다음 확정 예약과 겹치는가)이 r1이고, B의 ③에서 새 이벤트(예약 변경)가 나옵니다. 이 이벤트는 11장에서 정한 E1~E3에 없던 것이라, 회계 시스템과 맺은 계약에 더할지 q로 남깁니다.
2. 원장에 `v1` 줄을 고쳐 "하루 두 번(아침·점심) 출력"으로 적고, C 칸 빈도에도 반영합니다(근거: 데스크 진술). V2의 갱신 항목은 그대로 읽기 전용이지만, "모양"에 출력 시각을 찍는 칸을 더하는 것을 권합니다. 종이를 본 사람이 그 일정표가 언제 기준인지 알 수 있어야 하기 때문입니다. 출력 사이에 생긴 예약을 데스크가 놓칠 수 있다는 점은 V2의 시점 한계로 기록합니다.

이어지는 실습: P02 작은 도서관 상호대차(서사 시나리오).
