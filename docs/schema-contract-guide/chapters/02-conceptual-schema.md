## 2장 개념 스키마: 담화 세계에 관해 참인 것

이 장을 마치면 개념 스키마에 넣을 것과 뺄 것을 두 원칙(100% 원칙, 개념화 원칙)으로 가를 수 있어요. 개념 스키마를 이루는 부품(개체 유형·사실 유형·제약·파생 규칙)을 이름으로 부르고, 「틈」의 개념 스키마를 글자 표기로 적을 수 있게 됩니다.

### 출발점: 담화 세계

개념 스키마를 정의하려면 먼저 "무엇에 관한" 스키마인지 정해야 합니다. ISO/TR 9007(1987, 「개념 스키마와 정보 베이스의 개념과 용어」)은 그 대상을 **담화 세계**(universe of discourse)라고 부릅니다. 실제 세계든 가정한 세계든 관심을 두고 기술하기로 고른 부분이고, 거기에는 이미 있었던 것, 지금 있는 것, 앞으로 있을 것이 모두 들어갑니다. TR 9007은 재고처럼 구체적인 것, 조직 구조처럼 추상적인 것, 이상한 나라의 앨리스처럼 지어낸 것도 담화 세계가 될 수 있다고 예를 듭니다.

담화 세계는 **고르는 것**이라는 점이 중요해요. 「틈」의 예약 시스템이라면 경계를 이렇게 그을 수 있습니다.

```text
          담화 세계에 넣음                 넣지 않음
  +------------------------------+   +-------------------------+
  | 회원, 회원 등급                 |   | 출입 카드와 출입 기록       |
  | 회의실, 수용 인원               |   | 전기 요금, 청소 일정        |
  | 예약, 예약 시간, 예약 상태       |   | 회원의 회사 정보            |
  | 월 무료 시간, 초과 요금         |   | 실제 결제와 환불(회계 쪽)    |
  +------------------------------+   +-------------------------+
```

오른쪽에 있는 것들이 현실에 없다는 뜻이 아닙니다. 이 시스템이 알 책임을 지지 않기로 했다는 뜻이에요. 결제를 오른쪽에 둔 결정은 나중에 5장의 계약에서 다시 나옵니다. 예약 시스템이 결제를 모른다면, 결제를 아는 시스템과 무엇을 주고받을지 약속해야 하니까요.

### 개념 스키마와 정보 베이스

TR 9007은 담화 세계에 관해 시스템이 아는 것을 두 부분으로 나눕니다.

- **개념 스키마**: 담화 세계가 놓일 수 있는 상태들의 기술입니다. 분류·규칙·법칙 같은 일반적인 것을 적습니다.
- **정보 베이스**: 어느 시점이나 기간에 담화 세계에 실제로 있다고 인식된 구체적 대상과 상태의 기술입니다.

둘을 나란히 놓으면 이렇게 됩니다.

```text
개념 스키마 (일반 규칙)                  정보 베이스 (지금의 사실들)
-------------------------------------    -----------------------------------
회원은 회원번호로 식별된다                 회원 M07 의 이름은 "김하나"
회원마다 이름은 하나다                     회원 M12 의 이름은 "박도윤"
회의실은 코드로 식별된다                   회의실 R1 의 수용 인원은 6
같은 회의실의 확정 예약은 겹치지 않는다      예약 B101: M07, R1, 10:00-11:30, 확정
예약 상태는 확정 → 취소·이용완료·노쇼       예약 B102: M12, R1, 11:30-12:00, 확정
```

왼쪽은 "무엇이 가능한가"를, 오른쪽은 "무엇이 실제인가"를 적습니다. TR 9007의 표현을 빌리면 개념 스키마의 일반 규칙은 정보 베이스에 일어날 수 있는 일과 없는 일을 통제합니다. 예약 B103으로 M12가 R1을 11:00부터 잡으려 하면, 왼쪽 넷째 줄이 오른쪽 B101과 맞부딪혀 그 상태를 허락하지 않아요.

여기서 헷갈리기 쉬운 포인트는 개념 스키마를 테이블 설계도로 읽는 것입니다. 개념 스키마에는 테이블도 열도 없습니다. 들어가는 것은 사물의 종류, 사물에 관해 말하는 문장의 종류, 그 문장들이 지킬 규칙입니다. 테이블은 그것을 저장하는 여러 방법 가운데 하나이고, 4장의 내부 스키마에서 고릅니다.

### 무엇을 넣는가: 100% 원칙

TR 9007은 개념 스키마에 담을 내용에 관해 원칙 두 개를 내겁니다. 먼저 **100% 원칙**입니다. 담화 세계의 관련 있는 일반적 측면, 정적이든 동적이든, 곧 모든 규칙과 법칙을 개념 스키마에 기술해야 한다는 원칙이에요. TR 9007은 여기에 한 문장을 더 붙입니다. 다른 곳, 특히 응용 프로그램에만 적힌 규칙을 시스템이 지키지 못해도 정보 시스템은 그 책임을 지지 않는다는 것입니다.

이 덧붙인 문장이 실무에서 큰 뜻을 가집니다. 「틈」의 겹침 금지 규칙이 회원 앱의 화면 코드에만 들어 있다고 해 봅시다.

```text
규칙이 있는 곳            안내 데스크가 직접 예약을 넣으면?
----------------------   ------------------------------------
회원 앱 화면 코드에만      검사가 없음 → 겹친 예약이 들어감
개념 스키마에 적음         어디서 넣든 같은 규칙을 지켜야 함을 모두가 앎
```

규칙이 앱 코드에만 있으면, 데스크 프로그램처럼 다른 길로 들어온 쓰기는 그 규칙을 모릅니다. 100% 원칙은 규칙을 **어디서 지킬지**를 정하는 원칙이 아니라, 규칙을 **어디에 적을지**를 정하는 원칙이에요. 적는 곳은 개념 스키마 하나이고, 지키는 곳은 여럿일 수 있습니다. 지키는 곳을 고르는 일은 4장과 12장의 "보장 위치표"에서 다룹니다.

### 무엇을 빼는가: 개념화 원칙

다른 하나는 **개념화 원칙**입니다. 개념 스키마에는 개념적으로 관련 있는 측면만 넣습니다. TR 9007은 빼야 할 것을 구체적으로 듭니다. 외부·내부 데이터 표현의 모든 측면, 물리적 데이터 조직과 접근, 그리고 메시지 형식이나 자료 구조처럼 특정 외부 이용자에게 보이는 표현입니다.

「틈」에서 나올 법한 문장으로 연습해 봅시다.

| 문장 | 개념 스키마에? | 이유 |
| --- | --- | --- |
| 같은 회의실의 확정 예약은 시간이 겹치지 않는다 | 넣음 | 담화 세계의 규칙 |
| 예약 길이는 4시간을 넘지 않는다 | 넣음 | 담화 세계의 규칙 |
| 시작 시각은 `2026-11-17T10:00:00+09:00` 꼴의 문자열이다 | 뺌 | 외부 표현 |
| 앱 응답의 필드 이름은 `startAt` 이다 | 뺌 | 메시지 형식 |
| 예약 표에 회의실 코드 인덱스를 둔다 | 뺌 | 물리적 접근 |
| 회원번호는 `M` 다음 숫자 두 자리다 | 경우에 따라 | 회원이 이 번호를 실제로 쓰면 담화 세계의 식별 방식, 시스템만 쓰면 내부 표현 |

마지막 줄이 가장 까다롭습니다. 회원이 카운터에서 "M07입니다"라고 말한다면, 회원번호는 담화 세계에서 회원을 알아보는 방법이므로 개념 스키마에 들어갑니다. 반대로 DB가 행마다 붙이는 일련번호를 아무도 입으로 말하지 않는다면, 그것은 저장의 편의일 뿐이라 내부 스키마의 일이에요. 같은 모양의 값이라도 **담화 세계의 누가 그것을 쓰는가**로 갈립니다.

> 바깥에서 어떻게 보이는지와 안에서 어떻게 저장하는지는 빼고, 무엇이 참인지만 남깁니다.

### 개념 스키마의 부품

개념 스키마를 적는 표기법은 ER(개체-관계) 모델, ORM(객체-역할 모델링), UML 클래스 도식 등 여럿입니다. 표기는 달라도 담는 부품은 비슷해요. 이 가이드는 사실 중심의 ORM 쪽 용어를 기본으로 쓰고, ER 용어를 옆에 둡니다.

| 부품 | 뜻 | 「틈」의 예 | ER에서 가까운 말 |
| --- | --- | --- | --- |
| 개체 유형 | 따로 알아볼 수 있는 사물의 종류 | 회원, 회의실, 예약 | 개체 집합 |
| 값 유형 | 그 자체로 뜻이 정해진 값의 종류 | 이름 문자열, 시각, 분, 원 | 값 집합 |
| 참조 방식 | 개체 하나를 값으로 가리키는 방법 | 회원은 회원번호로 | 키 |
| 사실 유형 | 개체·값에 관해 말할 수 있는 문장의 틀 | 회원은 이름을 가진다 | 속성, 관계 |
| 제약 | 사실들이 지켜야 하는 규칙 | 회원마다 이름은 하나 | 카디널리티, 무결성 제약 |
| 파생 규칙 | 다른 사실에서 계산되는 사실 | 이달 사용 분 = 이용완료 예약 길이의 합 | 파생 속성 |

ER 모델을 처음 제안한 Peter Chen의 1976년 논문은 속성을 개체 집합에서 값 집합으로 가는 **함수**로 정의하고, 속성과 값 집합은 이름이 같더라도 다른 개념이라고 강조합니다. 「틈」으로 말하면 "회원의 이름"(속성)과 "사람 이름 문자열"(값 집합)은 다릅니다. 같은 문자열 집합을 "회원의 이름"과 "보호자의 이름"이 함께 쓸 수 있어요. Chen은 관계에도 속성이 붙는다고 했습니다. 예약 시간 구간은 회원 속성도 회의실 속성도 아닙니다. 회원과 회의실을 잇는 예약에 붙는 값이에요.

이제 「틈」의 개념 스키마를 글자 표기로 적어 보겠습니다. 이 표기는 이 가이드에서 계속 씁니다.

```text
[개체] 회원        참조: 회원번호 (예: M07)
[개체] 회의실      참조: 회의실 코드 (예: R1)
[개체] 예약        참조: 예약번호 (예: B101)
[값]   이름, 등급{일반, 상주}, 시각, 분, 원, 상태{확정, 취소, 이용완료, 노쇼}

[사실] F1  회원 은 이름 을 가진다
[사실] F2  회원 은 등급 에 속한다
[사실] F3  회의실 은 수용 인원 을 가진다
[사실] F4  예약 은 회원 이 한 것이다
[사실] F5  예약 은 회의실 을 잡는다
[사실] F6  예약 은 시작 시각 과 끝 시각 을 가진다
[사실] F7  예약 은 상태 에 있다
[사실] F8  등급 은 월 무료 분 을 가진다

[제약] R1  F1·F2·F4·F5·F6·F7: 각 개체마다 정확히 하나        (유일 + 필수)
[제약] R2  F6: 끝 > 시작, 둘 다 30분 단위, 길이 ≤ 240분
[제약] R3  확정 상태인 두 예약이 같은 회의실을 잡으면 시간 구간이 겹치지 않는다
[제약] R4  상태 전이는 확정 → 취소 | 이용완료 | 노쇼 만 허용
[제약] R5  시작 1시간 전보다 늦게 한 취소는 이용한 것으로 셈한다 (1시간 전까지는 무료)

[파생] D1  회원의 월 사용 분 = 그 달 이용완료·노쇼 예약과 R5에 걸린 취소 예약의 길이 합
[파생] D2  초과 분 = max(0, 월 사용 분 - 등급의 월 무료 분)
```

R1부터 R3은 어느 한 순간의 상태를 다루는 **정적 규칙**이고, R4와 R5는 상태가 바뀌는 방식을 다루는 **동적 규칙**입니다. 100% 원칙이 정적 측면과 동적 측면을 함께 든 이유가 이것이에요. 상태 전이 규칙을 빠뜨리면 "이용완료된 예약을 다시 확정으로 되돌린다" 같은 변화가 허용되는지 아무도 답할 수 없습니다.

### 동일성: 같은 것을 같은 것으로 알아보기

참조 방식을 고르는 일은 생각보다 어렵습니다. 예약번호를 붙이지 않고 회의실과 시작 시각만으로 예약을 알아본다고 해 봅시다. 겹침 금지 규칙이 있으니 확정 예약끼리는 회의실과 시작 시각이 같을 수 없어요. 그러면 이 둘을 참조 방식으로 써도 될까요?

```text
10:02  B101  M07  R1  10:00-11:30  확정
10:05  B101  M07  R1  10:00-11:30  취소      ← M07이 취소
10:06  ????  M12  R1  10:00-11:00  확정      ← M12가 같은 시간을 잡음

(회의실, 시작) = (R1, 10:00) 인 예약이 둘 → 하나는 취소, 하나는 확정
```

취소된 예약도 담화 세계에 남아 있다는 점이 문제입니다. 담화 세계에는 지금 있는 것뿐 아니라 이미 있었던 것도 들어간다고 했지요. 청구에는 취소 기록이 필요하므로 취소된 B101을 지울 수 없고, 그러면 (R1, 10:00)이 두 예약을 가리킵니다. 그래서 예약에는 시간이 지나도 바뀌지 않는 자기만의 참조 방식, 예약번호가 필요합니다. 회원들이 문의할 때 예약번호를 말한다면 이것은 개념 스키마의 참조 방식이에요.

TR 9007은 사물과 사물의 기술을 섞지 말라고 경고합니다. 회의실 R1이라는 방과 `R1`이라는 두 글자는 다른 것입니다. 회의실 코드를 `R1`에서 `A-101`로 바꿔도 방은 그대로예요. 참조 방식을 바꾸는 일은 이름표를 바꾸는 일이고, 사물을 바꾸는 일이 아닙니다.

### 하나의 개념 스키마인가, 여럿인가

TR 9007은 개념 스키마를 데이터베이스에 담길 수 있는 정보 내용의 유일한 중심 기술로 봅니다. 반면 도메인 주도 설계(DDD)는 큰 시스템을 여러 **경계 지어진 맥락**(bounded context)으로 나누고 맥락마다 자기 모델을 두라고 권합니다. Martin Fowler는 Eric Evans를 인용해, 큰 시스템 전체를 하나의 통합 모델로 묶는 것은 실현 가능하지도 비용 효율적이지도 않다고 정리했어요.

둘은 정면으로 부딪히는 것처럼 보이지만, 이 가이드는 이렇게 읽습니다. 원전이 직접 한 말은 아니에요. 두 원전을 나란히 놓고 이 가이드가 내린 결론입니다.

```text
TR 9007: 개념 스키마는 "고른 담화 세계"에 관한 유일한 기술
DDD   : 맥락마다 모델이 하나

→ 맥락 하나 = 담화 세계 하나를 고른 것
→ 맥락 안에서는 개념 스키마가 하나 (TR 9007을 그대로 따름)
→ 맥락 사이에는 개념 스키마를 합치지 않고 계약으로 잇는다 (5장)
```

「틈」에서 예약 맥락의 "회원"은 예약할 수 있는 사람이고, 회계 맥락의 "회원"은 청구서를 받는 계약 당사자입니다. 둘을 억지로 하나의 회원으로 합치면 어느 쪽에도 맞지 않는 속성 목록이 생겨요. 예약 맥락은 자기 회원을, 회계 맥락은 자기 회원을 두고, 둘 사이에는 "확정된 예약" 이벤트라는 계약을 둡니다.

### 합의된 뜻: Helsinki 원칙과 용어집

TR 9007은 1978년 헬싱키 회의에서 정한 원칙 하나를 앞머리에 둡니다. 의미 있는 말 주고받기는 미리 합의된 의미·구문 규칙이 있어야 가능하다는 **Helsinki 원칙**입니다. 개념 스키마의 낱말은 담화 세계 사람들이 합의한 뜻으로 읽혀야 한다는 이야기예요.

실무에서 이 원칙은 용어집으로 나타납니다. 「틈」에서 "이용 시간"이 예약한 시간인지 실제로 방에 있던 시간인지 합의되어 있지 않으면, 청구 담당자와 회원은 같은 낱말로 다른 것을 말합니다.

```text
t1  예약 시간   예약에 적힌 시작~끝. 실제 입퇴실과 무관
t2  이용 시간   이 시스템은 다루지 않음 (출입 기록은 담화 세계 밖)
t3  노쇼       시작 후 15분 안에 입실 확인이 없던 확정 예약      ← 담당자 확인 필요
```

t3의 "입실 확인"은 출입 기록을 쓰지 않는다는 t2와 충돌할 수 있습니다. 이런 충돌을 발견하는 일 자체가 용어집을 쓰는 이유예요. 7장의 추출 원장에서 용어 칸(T)이 첫째 칸인 것도 이 때문입니다.

### 잠깐 확인

"회원 앱은 예약 목록을 시작 시각 오름차순으로 보여 준다." 이 문장은 개념 스키마에 들어갈까요?

들어가지 않습니다. 정렬 순서는 특정 외부 이용자에게 보여 주는 방식이라 외부 스키마의 일이에요. 같은 예약 사실을 안내 데스크는 회의실 순으로 볼 수도 있습니다. 개념 스키마는 예약에 시작 시각이 있다는 사실(F6)까지만 적습니다.

### 스스로 점검하기

1. 「틈」에 "회의실마다 화이트보드가 있는지"를 기록하기로 했습니다. 개념 스키마에 무엇을 더해야 하나요? 사실 유형과 필요한 제약을 표기법대로 적어 보세요.
2. 앱 개발자가 "예약 겹침 검사는 앱 서버에서 하니까 개념 스키마에 R3을 적을 필요가 없다"고 합니다. 100% 원칙으로 반론해 보세요.
3. 회의실 코드를 `R1`·`R2`·`R3`에서 층과 호수를 담은 `3F-01`·`3F-02`·`4F-01`로 바꾸려 합니다. 개념 스키마에서 바뀌는 것과 바뀌지 않는 것을 나눠 보세요.

#### 풀이

1. 사실 유형 `F12 회의실 은 화이트보드 여부 를 가진다`를 더하고, 값 유형 `여부{있음, 없음}`과 제약 `회의실마다 정확히 하나`를 둡니다. "있는 회의실만 기록한다"는 단항 사실 `회의실 은 화이트보드가 있다`로 적어도 되는데, 그때는 기록이 없는 것이 "없음"인지 "아직 모름"인지 따로 정해야 합니다.
2. 100% 원칙은 규칙을 어디서 검사하든 개념 스키마에 적으라고 요구합니다. 앱 서버에서만 검사하면 안내 데스크 프로그램이나 일괄 입력처럼 다른 길로 들어온 쓰기는 그 규칙을 모르고, TR 9007의 표현대로 정보 시스템은 그 규칙을 지키지 못한 책임을 지지 않습니다. 검사 위치는 앱 서버로 정하더라도 규칙은 개념 스키마에 적어 모든 쓰기 경로가 알게 해야 합니다.
3. 바뀌는 것은 회의실의 참조 방식에 쓰는 값의 모양입니다. 회의실이라는 개체 유형, 수용 인원 같은 사실 유형, 겹침 금지 같은 제약은 바뀌지 않습니다. 코드에 층 정보가 들어간다고 해서 "회의실은 층에 있다"는 사실을 코드 글자로만 표현하면, 코드를 다시 바꿀 때 층 정보가 사라집니다. 층이 담화 세계에서 의미가 있다면 `회의실 은 층 에 있다`를 별도 사실 유형으로 두는 편이 낫습니다.
