## 3장 외부 스키마: 한 이용자가 보는 세계

이 장을 마치면 외부 스키마를 개념 스키마에서 **파생 규칙**으로 정의하고, 이용자·내용·모양·파생 규칙·갱신 의미의 다섯 항목으로 적을 수 있어요. 읽기만 하는 외부 스키마와 쓰기도 받는 외부 스키마가 왜 설계 난이도가 다른지, 그 이유인 뷰 갱신 문제도 예로 설명하게 됩니다.

### 정의

1985년 ANSI/SPARC 후속 보고서(NBS IR 85-3173)는 외부 수준에 외부 뷰가 여럿 있다고 말합니다. 각 뷰는 특정 응용이 관심을 두는 개체·속성·관계를 나타내는 데이터 객체의 모음이고, 뷰마다 그 객체를 응용에 어떤 모양으로 보여 줄지 기술한 외부 스키마가 붙어요. ISO/TR 9007은 한 걸음 더 나아가, 각 외부 스키마는 공통의 개념 스키마에서 **파생된다**고 적습니다.

"파생된다"는 말에 이 장의 내용이 다 들어 있습니다. 외부 스키마는 개념 스키마와 따로 설계하는 두 번째 모델이 아니에요. 개념 스키마에 이미 있는 사실을 골라 계산하고 모양을 바꾼 결과입니다.

```text
개념 스키마의 사실들                     외부 스키마 V2 "오늘 일정표" (안내 데스크)
--------------------------              -----------------------------------------
F1 회원 은 이름 을 가진다           +    회의실 | 시작  | 끝    | 예약자 | 정원
F3 회의실 은 수용 인원 을 가진다     |    R1     | 10:00 | 11:30 | 김하나 | 6
F4 예약 은 회원 이 한 것이다        +-▶  R1     | 11:30 | 12:00 | 박도윤 | 6
F5 예약 은 회의실 을 잡는다         |    R2     | 14:00 | 16:00 | 김하나 | 4
F6 예약 은 시작·끝 을 가진다        |
F7 예약 은 상태 에 있다            +    (확정만, 오늘만, 회의실·시작 순)
```

### 외부 스키마에 적는 다섯 항목

이 가이드는 외부 스키마 하나를 다섯 항목으로 적습니다. 원전의 정의(내용과 모양)에 이용자·파생 규칙·갱신 의미를 더한 교육용 형식입니다.

| 항목 | 묻는 것 | V2 오늘 일정표 |
| --- | --- | --- |
| 이용자 | 누가 보는가, 무엇을 하려고 | 안내 데스크 직원. 손님에게 방을 안내 |
| 내용 | 개념 스키마의 어떤 사실을 고르는가 | F1, F3, F4, F5, F6, F7 |
| 모양 | 이름·구조·단위·순서·표기 | 한 행 = 예약 하나. 시각은 `HH:MM`. 회의실·시작 순 |
| 파생 규칙 | 개념 사실에서 어떻게 만드는가 | 확정이고 시작 날짜가 오늘인 예약을 고르고, 회원 이름과 회의실 정원을 붙임 |
| 갱신 의미 | 이 모양으로 쓰기를 받는가, 받으면 무엇이 바뀌는가 | 읽기 전용 |

글자 표기로는 이렇게 씁니다.

```text
[외부] V2 오늘 일정표                 이용자: 안내 데스크
  행      오늘 시작하는 확정 예약 하나
  열      회의실 ← F5 · 시작 ← F6 · 끝 ← F6 · 예약자 ← F4 → F1 · 정원 ← F5 → F3
  고르기   F7 = 확정, F6.시작의 날짜 = 오늘
  순서     회의실, 시작
  가림     회원번호와 등급은 보이지 않음
  갱신     읽기 전용
```

`←` 오른쪽이 그 열이 어느 사실에서 오는지를 가리킵니다. "예약자 ← F4 → F1"은 F4로 예약의 회원을 찾고, F1로 그 회원의 이름을 가져온다는 뜻이에요. 이 표기는 13장의 추적표에서 그대로 쓰입니다. 외부 스키마의 모든 열에 이 화살표를 달 수 있어야 하고, 달 수 없는 열이 있다면 개념 스키마에 빠진 사실이 있다는 신호입니다.

### 파생 규칙에 쓰는 연산

외부 스키마를 만들 때 쓰는 연산은 몇 가지로 정리됩니다. 관계 대수의 연산에 표시에 가까운 연산 몇 개를 더한 목록이에요.

| 연산 | 하는 일 | 「틈」의 예 |
| --- | --- | --- |
| 고르기 | 조건에 맞는 사실만 남김 | 확정 예약만, 오늘 예약만 |
| 뽑기(투영) | 필요한 항목만 남김 | 회원 등급은 빼고 이름만 |
| 잇기 | 다른 사실을 붙임 | 예약에 회원 이름을 붙임 |
| 계산 | 새 값을 만듦 | 초과 분 = 사용 분 - 무료 분 |
| 이름 바꾸기 | 이용자의 말로 바꿈 | 회의실 코드 → "방" |
| 모양 바꾸기 | 평평하게 펴거나 묶음 | 회원 하나 아래 예약 목록을 묶음 |
| 가리기 | 권한 없는 사실을 빼거나 흐림 | 다른 회원의 이름을 "예약됨"으로 |

마지막 줄의 가리기를 보면 외부 스키마가 보안과도 이어져 있다는 것을 알 수 있어요. 관계형 DB에서 뷰를 처음 다룬 문헌으로 꼽히는 Chamberlin·Gray·Traiger의 1975년 논문 제목도 「관계형 데이터베이스의 뷰, 권한, 잠금」이었어요. 이 논문 정보는 2차 자료로 확인했습니다. 회원 앱 "회의실 현황" 화면에 다른 회원 예약을 보여 줄 때 예약자는 가리고 시간만 보여 준다면, 그것은 외부 스키마를 설계하며 내린 결정입니다.

SQL에서 외부 스키마를 만드는 가장 직접적인 도구는 뷰예요. V2를 SQL 뷰로 쓰면 이렇습니다.

```sql
CREATE VIEW desk_today AS
SELECT b.room_code       AS 회의실,
       b.starts_at::time AS 시작,
       b.ends_at::time   AS 끝,
       m.name            AS 예약자,
       r.capacity        AS 정원
FROM booking b
JOIN member m ON m.member_id = b.member_id
JOIN room   r ON r.room_code = b.room_code
WHERE b.status = 'confirmed'
  AND b.starts_at::date = CURRENT_DATE;
```

정렬(`ORDER BY`)은 뷰 정의에 넣지 않았습니다. 뷰 안의 정렬은 바깥 질의에서 보장되지 않으니까요. 외부 스키마의 "순서" 항목은 이 뷰를 읽는 질의나 화면 쪽에서 지킵니다. 외부 스키마의 항목 하나하나를 어느 장치가 지키는지 정해야 한다는 것, 이것이 12장 보장 위치표의 출발점이에요.

### 뷰 갱신 문제: 읽기는 쉽고 쓰기는 어렵다

Bancilhon과 Spyratos는 1981년 논문 「관계형 뷰의 갱신 의미」(*ACM TODS* 6권 4호)를 뷰의 정의로 시작합니다. "A view is a query definition named and stored." 뷰는 이름 붙여 저장한 질의이고, 데이터베이스 상태를 뷰 상태로 옮기는 사상입니다.

읽을 때는 이 사상을 앞으로 적용하면 됩니다. 문제는 쓸 때예요. 이용자가 뷰의 한 행을 바꾸면, 그 변경을 데이터베이스의 변경으로 거꾸로 옮겨야 합니다. 그런데 바뀐 뷰를 만들어 내는 데이터베이스 상태가 보통 **여러 개**라서, 어느 것을 고를지 정해야 해요. 이것이 뷰 갱신 문제입니다. 두 가지 예로 보겠습니다.

첫 번째는 정보가 빠진 뷰입니다. 회원 앱에 "회의실 현황" V4가 있고, 누가 예약했는지는 가리고 회의실·시작·끝만 보여 준다고 합시다. 누군가 V4에 `(R3, 15:00, 16:00)` 한 행을 넣으려 하면 어떻게 될까요?

```text
V4 = 뽑기[회의실, 시작, 끝] (확정 예약)

V4에 넣으려는 행: R3 15:00-16:00
데이터베이스에서 가능한 번역:
  (a) 예약 B201: M07, R3, 15:00-16:00, 확정
  (b) 예약 B201: M12, R3, 15:00-16:00, 확정
  (c) 예약 B201: M31, R3, 15:00-16:00, 확정
  ... 회원 수만큼

→ 어느 회원의 예약인지 V4만으로는 정할 수 없음
```

두 번째는 잇기 뷰의 **부수 효과**입니다. 청구 담당자가 보는 V5가 예약마다 회원 이름과 등급, 등급의 무료 분을 붙여 보여 준다고 합시다.

```text
V5 = 잇기(예약, 회원, 등급)

예약   회원 이름  등급  무료 분
B101  김하나    일반  120
B105  김하나    일반  120
B110  박도윤    상주  600

청구 담당자가 B101 줄의 등급을 "상주"로 바꿈
→ 번역: 회원 M07(김하나)의 등급을 상주로
→ 결과: B105 줄의 등급도 상주로 바뀜   ← 고치지 않은 줄이 바뀜
```

B101 줄 하나만 고쳤는데 B105 줄까지 바뀌었어요. 등급은 예약이 아니라 회원에 딸린 값이라서, 같은 회원이 나오는 줄이 모두 함께 바뀝니다. 이용자 입장에서는 놀라운 결과입니다. 2012년 Guagliardo·Franconi의 기술 보고서도 같은 꼴의 예를 듭니다. 잇기 뷰에 한 행을 넣으면 기존 행과 이어져 넣지 않은 행이 뷰에 함께 나타난다는 예예요.

Bancilhon·Spyratos의 답은 **보완 뷰**(complement)라는 개념입니다. 원래 뷰와 합치면 데이터베이스 전체를 다시 계산해 낼 수 있는 또 하나의 뷰예요. 뷰를 갱신하는 동안 보완 뷰를 그대로 두는 번역만 허용하면 번역이 하나로 정해집니다. 논문의 주된 결과는, 갱신 집합이 번역기를 가질 필요충분조건이 "보완 뷰를 고정한 채 번역할 수 있다"는 것이라는 점이에요.

```text
V1 "내 예약" (회원 M07 에게)  = 고르기[회원 = M07] (예약)
V1의 보완 뷰                 = 고르기[회원 ≠ M07] (예약)

V1 + 보완 = 예약 전체 → 데이터베이스를 되찾을 수 있음
V1에서 B101의 끝을 11:00으로 고침 + 보완(다른 회원의 예약)은 그대로
→ 번역이 하나로 정해짐: 예약 B101의 끝 = 11:00
```

V1은 쓰기를 받아도 되는 외부 스키마이고, V4와 V5는 그대로는 쓰기를 받기 어려운 외부 스키마입니다. 둘을 가르는 것은 "이 뷰에서 받은 변경을 데이터베이스의 변경 하나로 정할 수 있는가"예요. 다만 논문은 번역을 찾는 계산 방법까지 주지는 않았습니다.

### DBMS가 정해 둔 규칙: 자동 갱신 가능한 뷰

실제 DBMS는 이 문제를 단순한 규칙으로 좁혀 둡니다. PostgreSQL 공식 문서(CREATE VIEW)는 뷰가 다음 조건을 모두 만족할 때만 자동으로 갱신을 받는다고 적어요.

| 조건 | V1 내 예약 | V4 회의실 현황 | V5 청구용 |
| --- | --- | --- | --- |
| FROM에 테이블(또는 갱신 가능한 뷰)이 정확히 하나 | 예 | 예 | 아니오(셋을 이음) |
| 최상위에 WITH·DISTINCT·GROUP BY·HAVING·LIMIT·OFFSET 없음 | 예 | 예 | 예 |
| 최상위에 UNION·INTERSECT·EXCEPT 없음 | 예 | 예 | 예 |
| 선택 목록에 집계·윈도·집합 반환 함수 없음 | 예 | 예 | 예 |

V4는 표 하나에서 나왔으므로 자동 갱신 조건은 만족합니다. 그렇다고 V4로 예약을 넣어도 되는 것은 아니에요. PostgreSQL은 열 단위로 판단해서 V4에 없는 회원 열을 NULL이나 기본값으로 채우려 할 것이고, 회원이 필수라면 그 삽입은 실패합니다. DBMS의 규칙은 "번역이 기계적으로 하나로 정해지는가"를 보고, "그 번역이 업무상 맞는가"는 보지 않습니다. 업무상 맞는지는 설계자가 정해요.

여기에 쓰는 장치가 `WITH CHECK OPTION`입니다. 이 옵션을 단 뷰는, 넣거나 고친 결과가 그 뷰에 더는 보이지 않게 되는 변경을 거부해요.

```sql
CREATE VIEW my_bookings AS
SELECT booking_id, room_code, starts_at, ends_at, status, member_id
FROM booking
WHERE member_id = current_setting('app.member_id')
WITH CHECK OPTION;

-- M07로 접속해서 자기 예약의 회원을 M12로 바꾸려 하면
UPDATE my_bookings SET member_id = 'M12' WHERE booking_id = 'B101';
-- → 거부됨: 바뀐 행이 my_bookings 조건을 만족하지 않음
```

자동 갱신이 안 되는 뷰(V5처럼 여러 표를 잇는 뷰)는 INSTEAD OF 트리거로 "이 뷰의 갱신을 무엇으로 바꿀지"를 직접 써 줄 수 있습니다. PostgreSQL 문서 부록에 있는 SQL 표준 대응표를 보면, 표준 선택 기능 가운데 잇기·합집합 뷰 갱신(T111)은 지원하지 않는다고 나와 있어요.

여기서 얻는 결론이 이 장에서 가장 중요합니다.

> 읽는 외부 스키마는 파생 규칙으로 끝나고, 쓰는 외부 스키마는 갱신 의미를 따로 정해야 합니다.

갱신 의미란 이 모양으로 받은 변경을 개념 사실 가운데 무엇의 변경으로 옮길지를 말합니다. 외부 스키마의 다섯째 항목이면서 5장 계약의 행위 겹에 들어갈 내용이에요.

### 오늘날 외부 스키마에 해당하는 것들

1970년대의 외부 스키마는 같은 DBMS를 쓰는 응용 프로그램의 하위 스키마였습니다. 오늘날 비슷한 자리에 있는 것은 HTTP API의 응답 모양, GraphQL 스키마, 읽기 전용 모델, 이벤트의 페이로드 같은 것들이에요. 다만 이것들을 "외부 스키마"라고 부르는 문헌은 이번 조사에서 찾지 못했습니다. 아래 표는 이 가이드의 해석이고, 해석을 받치는 근거를 함께 적었습니다.

| 오늘의 형식 | 외부 스키마로 보는 근거 | 외부 스키마를 넘는 부분 |
| --- | --- | --- |
| REST 자원의 표현 | Fielding(2000)은 자원을 개체 집합에 대한 개념적 사상으로, 표현을 바이트열과 메타데이터로 나눔. 개념과 모양의 구분과 닮음 | 연산(GET·PUT 등), 상태 코드, 캐시 규칙 |
| GraphQL 스키마 | 명세(2021-10판)는 타입 시스템이 서비스의 능력을 기술하고, 응답은 클라이언트가 요청한 것만 담는다고 함. 이용자마다 고르는 뷰와 닮음 | 변경(mutation), 오류, 권한 |
| CQRS 읽기 모델 | Microsoft의 CQRS 패턴 문서는 읽기와 쓰기의 데이터 표현이 흔히 다르다고 하고, 읽기 모델을 실체화 뷰로 둘 수 있다고 함 | 쓰기 모델과의 결과적 일관성 |
| BFF(Backends for Frontends) | Sam Newman(2015)은 사용자 경험 하나에 백엔드 하나를 둔다고 함. 이용자마다 외부 스키마를 두는 구조와 닮음 | 그 자체로 서비스이므로 배포·운영 |
| 이벤트 페이로드, 데이터 파일 | ISO/TR 9007의 개념화 원칙은 메시지 형식을 외부 이용자 표현의 예로 듦 | 전달 보장, 순서, 보존 기간 |

CQRS는 뷰 갱신 문제와 흥미롭게 이어집니다. CQRS는 읽기 모델로 쓰기를 받지 않고, 쓰기는 "예약하기" 같은 **명령**으로 따로 받아요. 외부 스키마를 읽기 전용으로 두고 갱신 의미를 명령 쪽에 몰아 적는 설계라고 볼 수 있습니다. 앞에서 V4·V5에 쓰기를 받지 않기로 한 판단과 같은 방향이에요. 이 연결도 이 가이드의 해석입니다. Fowler는 CQRS가 대부분의 시스템에는 위험한 복잡성을 더한다고 경고했으니, 읽기 모델을 따로 저장하는 것까지 따라 할 필요는 없습니다.

Pat Helland의 2005년 논문 「바깥의 데이터와 안쪽의 데이터」는 이 표 전체를 한 문장으로 받쳐 줍니다. 서비스는 다른 서비스가 쓰도록 다듬은 데이터의 부분집합을 바깥으로 내보내고, 안쪽 데이터는 서비스의 로직을 거쳐서만 접근된다는 것이에요. 바깥으로 나간 부분집합이 이 가이드의 외부 스키마이고, 그것을 바꾸지 않겠다는 약속이 계약입니다.

### 헷갈리기 쉬운 곳

OpenAPI 문서 한 벌 전체를 외부 스키마로 보는 것은 지나칩니다. OpenAPI 문서의 `components.schemas`와 응답 본문 정의는 외부 스키마에 해당하지만, 경로와 연산, 오류 응답, 보안 방식, 버전은 "어떻게 주고받고 무엇을 약속하는가"를 적은 계약 쪽 내용이에요.

```text
OpenAPI 문서
+------------------------------------------+
| paths: /bookings  POST, GET              |  ← 계약(연산)
|   responses: 201, 409, 422               |  ← 계약(실패)
| components.schemas.Booking               |  ← 외부 스키마(모양)
| security: bearerAuth                     |  ← 계약(조건)
| info.version: 1.4.0                      |  ← 계약(진화)
+------------------------------------------+
```

또 하나, 외부 스키마가 개념 스키마의 **부분집합**이기만 한 것도 아닙니다. 초과 분처럼 개념 스키마에 파생 규칙으로만 있는 값을 외부 스키마가 실제 열로 보여 줄 수 있고, 회원 아래에 예약 목록을 묶은 중첩 구조처럼 개념 스키마에 없는 모양을 만들 수도 있어요. 외부 스키마에 없어야 하는 것은 개념 스키마에서 파생할 수 없는 **사실**뿐입니다.

### 잠깐 확인

회원 앱의 "내 예약" V1에 "남은 무료 시간"을 보여 주려 합니다. 개념 스키마에 무엇이 있어야 할까요?

등급의 월 무료 분(F8), 회원의 등급(F2), 그리고 월 사용 분을 계산하는 파생 규칙 D1이 있어야 합니다. 남은 무료 시간 = 무료 분 - 사용 분이라는 계산은 외부 스키마의 파생 규칙에 적으면 돼요. 이 셋 가운데 하나라도 없으면 V1의 그 열에 `←` 화살표를 달 수 없습니다.

### 스스로 점검하기

1. 청구 담당자를 위한 외부 스키마 V3 "월 청구 명세"를 다섯 항목 표기로 적어 보세요. 행은 회원 한 명, 열은 회원 이름·등급·사용 분·무료 분·초과 분입니다.
2. V3로 쓰기를 받을 수 있을까요? 청구 담당자가 초과 분을 0으로 고치는 경우를 들어 뷰 갱신 문제로 설명해 보세요.
3. 회의실 현황 V4에서 다른 회원의 예약자 이름을 "예약됨"으로 가리려 합니다. 이 가림을 SQL 뷰 하나로 쓸 때 어떤 정보가 필요한가요?

#### 풀이

1. 다음처럼 적을 수 있습니다.

```text
[외부] V3 월 청구 명세               이용자: 청구 담당자
  행      해당 월에 사용 분이 있는 회원 한 명
  열      회원 이름 ← F1 · 등급 ← F2 · 사용 분 ← D1 · 무료 분 ← F2 → F8 · 초과 분 ← D2
  고르기   D1 > 0, 월 = 청구 대상 월
  순서     회원 이름
  가림     없음 (청구 담당자는 모든 회원을 봄)
  갱신     읽기 전용
```

2. 받기 어렵습니다. 초과 분은 D2로 계산되는 값이라서, 0으로 만들려면 사용 분을 줄이거나 무료 분을 늘리거나 예약 일부를 취소로 바꾸는 등 여러 번역이 가능합니다. 어느 것을 골라도 이용자가 고치지 않은 다른 값(사용 분, 다른 달의 무료 분)이 바뀝니다. 청구를 깎아 주는 일이 업무상 필요하다면 V3에서 직접 고치게 하지 말고 "청구 조정"이라는 별도 사실 유형과 그것을 만드는 연산을 개념 스키마와 계약에 두는 편이 맞습니다.
3. 지금 접속한 회원이 누구인지가 필요합니다. 예를 들어 `CASE WHEN b.member_id = current_setting('app.member_id') THEN m.name ELSE '예약됨' END`처럼 접속한 회원과 예약의 회원을 견줍니다. 이 정보는 개념 스키마의 사실이 아니라 실행 맥락이므로, 외부 스키마의 "이용자" 항목과 "가림" 항목에 그 의존을 적어 둡니다.
