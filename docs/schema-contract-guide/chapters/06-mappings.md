## 6장 넷을 잇는 사상과 추적

이 장을 마치면 한 사실이 네 산출물에서 각각 어떤 모양인지 따라가고, 두 사상과 계약이 걸리는 자리를 한 장의 그림으로 그릴 수 있어요. 자주 섞이는 용어 쌍(외부·개념·내부와 개념·논리·물리, 개념 스키마와 도메인 모델 등)을 구분하는 것도 이 장의 몫입니다.

### 한 예약을 네 표현으로 따라가기

예약 B101 하나를 골라 네 산출물에서 차례로 보겠습니다. 같은 대상인데 모양이 전부 달라요.

```text
[개념 스키마의 사실]
  F4 예약 B101 은 회원 M07 이 한 것이다
  F5 예약 B101 은 회의실 R1 을 잡는다
  F6 예약 B101 은 2026-11-17 10:00 부터 11:30 까지다
  F7 예약 B101 은 확정 상태에 있다

[내부 스키마의 행]  booking
  booking_id | member_id | room_code | starts_at              | ends_at                | status
  B101       | M07       | R1        | 2026-11-17 10:00+09    | 2026-11-17 11:30+09    | confirmed

[외부 스키마 V2 오늘 일정표의 행]
  회의실 R1 | 시작 10:00 | 끝 11:30 | 예약자 김하나 | 정원 6

[계약 E1 "예약 확정" 이벤트의 한 건]
  {"eventId":"e-77","type":"booking.confirmed","bookingId":"B101",
   "memberId":"M07","roomCode":"R1",
   "startAt":"2026-11-17T10:00:00+09:00","endAt":"2026-11-17T11:30:00+09:00"}
```

넷을 견주어 보면 무엇이 어디서 왔는지 보입니다. 외부 스키마에 보이는 "예약자 김하나"는 개념 사실 F4와 F1을 이어서 만든 값이고, 내부 행에는 회원 이름이 없어요. 이벤트에는 회원 이름이 없고 회원번호만 있습니다. 회계 시스템이 회원 이름을 필요로 하지 않는다는 판단이 계약에 들어간 거예요. 상태는 내부에서 `confirmed`, 외부 V2에서는 고르기 조건으로 사라졌고, 이벤트에서는 `type`에 녹아 있습니다.

### 두 사상과 계약이 걸리는 자리

이제 전체 그림을 그릴 수 있습니다.

```text
                 씨앗(콘셉트·요구·엑셀·로그 ...)
                          |  추출 규칙 (7장, 14~26장)
                          ▼
                     [ 추출 원장 ]  T F V C R Q
                          |  설계 절차 (8~12장)
                          ▼
+-------------+   외부-개념 사상   +---------------+   개념-내부 사상   +-------------+
| 외부 스키마   | ◀---------------  | 개념 스키마      | --------------▶ | 내부 스키마   |
| V1 V2 V3 E1 |   (파생 규칙)       | 사실·제약·파생   |   (저장 규칙)      | 표·키·인덱스  |
+-------------+                   +---------------+                   +-------------+
      |                                                                     |
 [ 계약 ]  경계마다: 구조·의미·행위·품질·진화                         [ 보장 위치표 ]
      |                                                                     |
      +---------------------- 추적표 (13장) ----------------------------------+
```

이 그림에서 사상은 둘입니다. 외부-개념 사상은 3장의 파생 규칙이고, 개념-내부 사상은 4장의 저장 규칙이에요. 계약은 사상이 아닙니다. 외부 스키마가 경계를 넘을 때 그 경계에 붙는 약속이에요. 맨 아래 추적표는 원장의 한 줄이 네 산출물의 어디에 나타나는지 이어 주는 표이고, 13장에서 자세히 만듭니다.

개념-내부 사상도 외부-개념 사상처럼 표로 적을 수 있어요.

| 개념 | 내부 | 비고 |
| --- | --- | --- |
| [개체] 회원(회원번호) | `member.member_id` 기본 키 | 참조 방식이 키로 |
| F1 회원은 이름을 가진다 | `member.name NOT NULL` | 필수 + 하나 |
| F4 예약은 회원이 한 것이다 | `booking.member_id NOT NULL REFERENCES member` | 1:N의 N쪽에 외래 키 |
| F6 예약은 시작·끝을 가진다 | `booking.starts_at`, `booking.ends_at` | 구간은 `[시작, 끝)` |
| R3 겹침 금지 | `EXCLUDE USING gist (...) WHERE status = 'confirmed'` | DB가 지킴 |
| R5 늦은 취소는 사용으로 셈 | `booking.cancelled_at` + 청구 질의 | 응용이 지킴 |

### 자주 섞이는 용어 쌍

이 분야에는 비슷한 이름이 많아서, 같은 낱말을 서로 다른 뜻으로 쓰는 대화가 흔합니다. 이 가이드에서 쓰는 뜻을 표로 정리해 둘게요.

| 쌍 | 차이 | 이 가이드에서는 |
| --- | --- | --- |
| 외부·개념·내부 vs 개념·논리·물리 | 앞의 셋은 **누구의 관점인가**로, 뒤의 셋은 **얼마나 구체적인가**로 나눔 | 개념 스키마 = 개념 모델. 내부 스키마 = 논리 모델 + 물리 모델 |
| 개념 스키마 vs 도메인 모델 | 개념 스키마는 사실과 규칙의 구현 독립 기술. DDD의 도메인 모델은 흔히 행위를 가진 코드까지 포함 | 개념 스키마를 먼저 쓰고, 도메인 모델은 그것을 구현하는 선택의 하나로 봄 |
| 외부 스키마 vs 계약 vs API 명세 | 외부 스키마는 모양과 파생, 계약은 약속, API 명세는 둘의 기계가 읽는 부분 | 3장·5장의 구분 |
| 내부 스키마 vs DDL | DDL은 내부 스키마의 대부분을 적지만 단일 쓰기 경로 같은 결정은 못 적음 | 보장 위치표로 보충 |
| 스키마 vs 인스턴스 | TR 9007의 개념 스키마와 정보 베이스. 일반 규칙과 지금의 사실 | 설계할 때는 인스턴스(예제 데이터)를 늘 함께 씀 |
| 개념 스키마 하나 vs 맥락마다 | TR 9007은 유일한 중심 기술, DDD는 맥락마다 모델 | 맥락 하나 = 담화 세계 하나. 맥락 사이는 계약 |

다섯째 줄에 한 가지를 덧붙이면, 스키마와 인스턴스를 떼어 놓는 관행을 비판하는 연구도 있습니다. Partridge 외(2025, arXiv 프리프린트)는 개념 모델링이 정보 베이스를 떼어 내고 스키마만 남긴 흐름을 "schema turn"이라 부르며 그 분리가 근본적이지 않다고 주장해요. 이 가이드는 그 논쟁에 판정을 내리지 않습니다. 다만 설계 과정에서는 인스턴스를 스키마와 늘 함께 다룹니다. 8장의 인구 검사와 13장의 인구 왕복이 그 방법이에요.

### 문장을 넷으로 가르기

마지막으로 손을 움직여 봅시다. 아래 문장이 개념 스키마·외부 스키마·내부 스키마·계약 가운데 어디에 속하는지 가려 보세요. 둘 이상에 걸치는 문장도 있습니다.

```text
(가) 회원은 한 달에 등급별 무료 시간을 받는다
(나) 일정표에서 회원번호는 보이지 않는다
(다) booking 표의 (member_id, starts_at) 에 인덱스를 둔다
(라) 예약 확정 이벤트는 확정 후 1분 안에 발행한다
(마) endAt 은 그 시각을 포함하지 않는다
(바) 예약 쓰기는 예약 서비스 한 곳에서만 한다
(사) 필드를 지울 때는 90일 전에 공지한다
(아) 예약 목록은 시작 시각순으로 돌려준다
```

#### 풀이

| 문장 | 속하는 곳 | 이유 |
| --- | --- | --- |
| (가) | 개념 | 담화 세계의 규칙(F8, D1, D2) |
| (나) | 외부 | 특정 이용자에게 보이는 범위(V2의 가림) |
| (다) | 내부 | 접근 경로. 정보를 더하지 않음 |
| (라) | 계약 | 품질 겹(신선도) |
| (마) | 개념 + 계약 | 구간의 뜻은 담화 세계의 규칙이고, 이벤트 소비자에게는 의미 겹의 약속 |
| (바) | 내부 | R4를 지키는 자리를 정한 결정(보장 위치표) |
| (사) | 계약 | 진화 겹 |
| (아) | 외부, 계약에 올리면 계약 | 순서는 외부 스키마의 모양. 계약에 적지 않고 늘 그렇게 돌려주면 실제 계약이 됨(5장 Hyrum 법칙) |

### 제1부를 마치며

제1부에서 네 가지를 정의했습니다. 제2부부터는 이 정의를 외우는 데서 멈추지 않고 실제로 쓰는 단계예요. 어떤 자료가 오든 같은 절차로 네 산출물을 만들 수 있도록, 7장에서 설계의 흐름과 추출 원장부터 정합니다.

### 스스로 점검하기

1. 「틈」에 "회원이 예약에 손님 이름을 적을 수 있다"는 기능이 생겼습니다. 이 사실이 네 산출물에 각각 어떤 모양으로 나타날지 B101을 따라간 앞의 그림처럼 적어 보세요. 회계 시스템 이벤트에 손님 이름을 넣을지도 정해 보세요.
2. 팀 회의에서 "개념 모델은 이미 ERD로 그렸으니 개념 스키마는 끝났다"는 말이 나왔습니다. 이 말에서 빠진 것을 2장과 6장의 내용으로 지적해 보세요.

#### 풀이

1. 개념에 `F11 예약 은 손님 이름 을 가진다`(선택, 여럿일 수 있음)를 더합니다. 여럿이면 내부에는 `booking_guest(booking_id, guest_name)` 표를 두고, 하나뿐이면 `booking.guest_name` 열로 둡니다. 안내 데스크 V2에는 손님 이름 열을 더하면 손님 안내에 쓸 수 있습니다. 회계 이벤트에는 넣지 않는 편이 낫습니다. 청구에 쓰이지 않는 개인 정보를 다른 팀 시스템으로 보내면 그 팀이 보관·삭제 책임까지 지게 되고, 계약의 품질 겹(보존 기간)도 늘어나기 때문입니다.
2. ERD는 개체와 관계를 그리지만, 겹침 금지(R3) 같은 제약, 상태 전이(R4) 같은 동적 규칙, 늦은 취소(R5)와 파생 규칙(D1·D2)은 기본 ERD 표기에 잘 나타나지 않습니다. 100% 원칙은 이런 규칙까지 모두 개념 스키마에 적으라고 요구합니다. 또 ERD에 테이블 이름과 외래 키 열이 그려져 있다면, 그것은 개념화 원칙이 빼라고 한 내부 표현이 섞인 것입니다.
