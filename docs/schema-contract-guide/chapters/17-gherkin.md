## 17장 Gherkin과 예시 명세

이 장을 마치면 Gherkin 시나리오의 `Given`·`When`·`Then`을 각각 원장의 칸으로 옮기고, `Examples` 표를 8장 CSDP의 인구로 바로 쓸 수 있어요. 예시 표에 경계값과 반례를 넣어 규칙의 빈틈을 찾는 방법도 익힙니다.

### Gherkin의 낱말

Gherkin은 Cucumber 같은 도구가 읽는 시나리오 언어입니다. Cucumber 공식 참조 문서의 주요 낱말을 정리하면 이래요.

| 낱말 | 뜻(공식 문서 요지) |
| --- | --- |
| `Feature` | 소프트웨어의 기능 하나에 이름을 붙이고 시나리오를 묶음. 파일마다 하나 |
| `Rule` | 업무 규칙 하나를 보여 주는 시나리오들을 묶음 |
| `Scenario` (`Example`) | 단계들로 된 구체적인 예 하나 |
| `Given` | 시스템의 처음 맥락을 기술 |
| `When` | 사건이나 행동을 기술 |
| `Then` | 기대하는 결과를 기술 |
| `And`, `But` | 앞 단계와 같은 종류를 이음 |
| `Background` | 모든 시나리오 앞에 공통으로 오는 `Given` |
| `Scenario Outline` + `Examples` | 같은 시나리오를 값만 바꿔 여러 번. 표의 행마다 한 번 실행 |

Given/When/Then 꼴은 Dan North가 2006년 글 「Introducing BDD」에서 처음 맥락·사건·결과로 쓴 것이 널리 퍼졌습니다. Gojko Adzic의 『Specification by Example』(Manning, 2011)은 이런 구체적인 예를 요구 명세 자체로 쓰는 방법을 정리한 책이에요.

### 원장으로 옮기는 규칙

Gherkin은 이 가이드의 산출물과 대응이 특히 깔끔합니다. 세 낱말이 각각 상태·연산·결과를 가리키기 때문이에요.

| Gherkin | 원장 칸 | 산출물에서 |
| --- | --- | --- |
| `Feature` 이름 | C 묶음, T | 연산 계약의 묶음, 용어 |
| `Rule` | R | 개념 스키마의 제약 |
| `Background`, `Given` | F (인구) | 개념 스키마의 인구, 계약의 사전 상태 |
| `When` | C | 연산 계약 O |
| `Then` (상태가 바뀜) | F, R | 사후조건 post |
| `Then` (무엇이 보임) | V | 외부 스키마 |
| `Then` (거절됨, 오류) | R | 실패표의 줄 |
| `Examples` 표 | F (인구 여러 줄) | CSDP 1·2단계의 인구, 반례 시험 |

마지막 줄이 이 형식의 가장 큰 장점이에요. 8장의 CSDP는 1단계에서 익숙한 예를 기본 사실로 바꾸고 2단계에서 인구로 검사했지요. `Examples` 표는 그 인구가 이미 표 모양으로 적혀 있는 셈입니다. 표의 열은 사실 유형의 역할, 행은 인구 한 줄이에요.

### 「틈」으로 해 보기

「틈」의 늦은 취소 규칙을 Gherkin으로 적은 기획 문서가 왔다고 합시다.

```gherkin
Feature: 예약 취소와 사용 시간

  Rule: 시작 1시간 전보다 늦게 취소하면 사용으로 셈한다

    Background:
      Given 회원 M31 은 일반 등급이다

    Scenario Outline: 취소 시각에 따라 사용 시간이 달라진다
      Given M31 의 확정 예약이 R1 에 <시작> 부터 60분 있다
      When M31 이 <취소 시각> 에 그 예약을 취소한다
      Then 예약은 취소 상태가 된다
      And 그 예약은 사용 시간에 <셈> 

      Examples:
        | 시작  | 취소 시각 | 셈        |
        | 10:00 | 08:30     | 들어가지 않는다 |
        | 10:00 | 09:30     | 들어간다    |
        | 10:00 | 09:59     | 들어간다    |
```

원장으로 옮기면 이렇게 됩니다.

| ID | 칸 | 내용 | 출처 |
| --- | --- | --- | --- |
| r4 | R | 시작 1시간 전보다 늦은 취소는 사용으로 셈 | Rule |
| f9 | F | 회원 M31은 일반 등급 | Background |
| f10 | F | M31의 R1 10:00~11:00 확정 예약 (예약번호는 시나리오에 없음) | Given |
| c2 | C | 회원이 예약을 취소한다 | When |
| f11 | F | 그 예약의 취소 시각은 08:30 / 09:30 / 09:59 | Examples |
| r7 | R | 취소하면 상태가 취소가 된다 | Then |

`Examples`의 세 줄은 바로 인구 검사가 됩니다. 8장의 D1(늦은 취소의 셈)을 이 세 줄에 적용해 보면 08:30은 10:00보다 90분 앞이라 들어가지 않고, 09:30(30분 앞)과 09:59(1분 앞)는 들어가요. 표와 같습니다.

### 경계값과 반례를 더하기

예시 표는 쓴 사람이 떠올린 줄만 담고 있어요. 그래서 설계자가 할 일은 **표에 줄을 더하는 것**입니다. 규칙의 경계에 있는 값과, 규칙이 다루지 않는 값을 넣어 담당자에게 결과를 물어요. 8장에서 반례 인구를 들이밀던 것과 같은 방법입니다.

```text
더한 줄                     기대 결과          담당자에게
| 10:00 | 09:00 |           ?                 정확히 1시간 전은?
| 10:00 | 10:10 |           ?                 시작한 뒤에도 취소할 수 있나?
| 10:00 | 전날 23:00 |       들어가지 않는다     (확인용)
```

09:00 줄은 경계값이에요. 7장의 콘셉트 메모는 "시작 1시간 전까지는 그냥 취소할 수 있는데"라고 했습니다. 우리말의 "까지"는 보통 그 시각을 포함하므로, 8장의 D1은 `취소 시각 > 시작 - 1시간`으로 적어 09:00 취소를 무료로 셉니다. 13장의 SQLite 질의도 같은 조건(`cancelled_at > datetime(starts_at, '-60 minutes')`)을 써요. 그런데 처음 표의 세 줄로는 이 경계를 시험하지 못합니다. D1을 `≥`로 잘못 적었더라도 08:30·09:30·09:59 세 줄은 모두 같은 결과를 내니까요. 경계값 줄을 넣어야 D1이 메모의 읽기를 제대로 옮겼는지 확인할 수 있어요. 그리고 "까지"를 포함으로 읽은 것도 설계자의 해석이라, 원장에 q로 남겨 담당자에게 확인받습니다.

```text
q9  정확히 시작 1시간 전(예: 10:00 예약을 09:00에) 취소하면 무료인가?
    "까지"를 포함으로 읽으면 무료 → D1 은 "취소 시각 > 시작 - 1시간" (8장·13장의 식)
    사용으로 센다는 답이 오면   → D1 과 13장 질의를 "≥" 로 바꿈
```

10:10 줄은 규칙이 다루지 않던 경우입니다. 시작한 뒤의 취소를 허용할지는 R4(상태 전이)의 문제예요. 지금 R4는 확정에서 취소로 가는 것을 시각과 상관없이 허용합니다. 이용 중에 "취소"를 누르는 것이 무슨 뜻인지(남은 시간을 돌려받나, 그냥 기록인가) 정해야 하고, 정해지기 전까지는 q로 둡니다. Then을 거절로 정하면 그 줄은 O2 실패표의 한 줄이 돼요.

> 예시 표에 줄을 하나 더할 때마다 담당자에게 질문 하나가 생깁니다.

### 이 형식이 빼먹기 쉬운 것

| 빠지기 쉬운 것 | 이유 | 채우는 질문 |
| --- | --- | --- |
| 식별자 | Given이 "M31의 예약이 있다"처럼 식별 없이 씀 | "이 예약은 무엇으로 부르나요?" |
| 예에 없는 값 | 표는 떠올린 줄만 담음 | 경계값·반례 줄을 더해 결과를 물음 |
| 용어 정의 | 시나리오가 낱말을 정의하지 않고 씀 | "'사용 시간'은 예약 시간인가요, 머문 시간인가요?" |
| 빈도와 규모 | 시나리오는 한 건만 다룸 | "이런 취소가 하루에 몇 건인가요?" |
| 동시성 | 한 시나리오 안에는 행위자가 하나 | "두 회원이 동시에 같은 시간을 예약하면?" |

### 헷갈리기 쉬운 곳

1. `Then`의 문장이 화면 표시인지 상태 변화인지 구분해야 합니다. "예약은 취소 상태가 된다"는 사후조건이고, "'취소되었습니다'가 보인다"는 외부 스키마나 표시의 일이에요. 둘이 한 `Then`에 섞여 있으면 원장에서 둘로 나눕니다.
2. `Examples` 표의 값이 모두 규칙은 아닙니다. 표의 08:30은 예일 뿐이고, 규칙은 Rule에 있어요. 표에서 규칙을 끌어내려면 8장처럼 일반형을 적고, 그 일반형이 표의 모든 줄을 설명하는지 확인합니다.
3. Gherkin 파일이 시험으로 자동 실행된다고 해서 계약이 완성된 것은 아닙니다. 시나리오는 예를 시험할 뿐이라, 예와 예 사이의 값(09:00)은 시험되지 않아요. 13장에서 본 인구 왕복의 한계와 같습니다.

### 잠깐 확인

Background의 "회원 M31은 일반 등급이다"는 이 Feature의 모든 시나리오에 필요한 사실일까요?

이 Feature에서는 꼭 필요하지 않습니다. 늦은 취소가 사용으로 셈되는지는 등급과 상관이 없고, 등급은 사용 시간이 **얼마나 청구되는지**에만 영향을 주니까요. 시나리오에 필요 없는 Given이 Background에 있으면, 읽는 사람은 등급이 규칙에 관련 있다고 오해할 수 있어요. 원장에는 옮기되, 이 Rule과는 관련이 없다는 메모를 붙입니다.

### 스스로 점검하기

1. 위 Feature에 "노쇼도 사용으로 셈한다"는 Rule을 더하는 Scenario를 Given/When/Then으로 써 보세요. When에 올 연산은 무엇이고, 누가 그 연산을 하나요?
2. q9의 답이 "정확히 1시간 전 취소도 사용으로 셈"으로 왔다고 합시다. 13장 인구 왕복의 결과가 바뀌는 예약이 있나요? 인구의 B104와 B105를 기준으로 답해 보세요.

#### 풀이

1. 예시입니다. `Given M31 의 확정 예약이 R2 에 15:00 부터 120분 있다` / `When 데스크 직원이 15:15 에 그 예약을 노쇼로 표시한다` / `Then 예약은 노쇼 상태가 된다` / `And 그 예약은 사용 시간에 들어간다`. When의 연산은 "노쇼 표시"이고, 7장 원장의 q2(노쇼는 누가 판정하나)에 따라 행위자가 정해집니다. 데스크 직원이 표시한다면 새 연산 계약(O4 노쇼 표시)이 생기고, 15분 기준은 15장의 질문처럼 확인을 받아야 합니다.
2. 바뀌지 않습니다. B104는 09:00 시작을 08:30에 취소했으니 시작 30분 전이라 어느 읽기로도 사용으로 셈합니다. B105는 다음 날 13:00 시작을 전날 20:00에 취소했으니 17시간 앞이라 어느 읽기로도 무료입니다. 인구에 정확히 1시간 전 취소가 없어서, 13장의 결과는 q9의 답과 상관없이 같습니다. q9를 시험하려면 그런 예약을 인구에 더해야 합니다.
