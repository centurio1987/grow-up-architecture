## 5장 계약: 경계에서 지키는 약속

이 장을 마치면 계약을 사전조건·사후조건·불변식으로 적고, 구조·의미·행위·품질·진화의 다섯 겹으로 빠짐없이 채울 수 있어요. 제공자 계약과 소비자 주도 계약의 차이를 설명하고, 어떤 변경이 호환되고 어떤 변경이 호환되지 않는지 근거를 들어 가르게 됩니다.

### 왜 세 층에 계약을 더하는가

1장의 데이터 독립성은 **안쪽에 주는 자유**였습니다. 내부 스키마를 바꿔도, 개념 스키마를 다시 나눠도, 사상만 고치면 바깥은 그대로였지요. 이 자유에는 전제가 하나 있어요. 바깥에서 보는 외부 스키마만큼은 그대로 있어야 한다는 것입니다.

외부 스키마를 보는 쪽이 같은 팀의 프로그램이라면, 외부 스키마를 바꿀 때 그 프로그램도 같이 고치면 됩니다. 「틈」의 회계 시스템처럼 다른 팀이 만든 시스템이라면 이야기가 달라져요. 예약 시스템 팀은 회계 시스템을 고칠 수 없습니다. 외부 스키마를 바꾸려면 상대 팀이 준비될 때까지 기다리거나, 바꾸지 않겠다고 미리 약속해야 해요.

```text
          같은 팀의 이용자                     다른 팀의 이용자
   +-----------------------+         +----------------------------+
   | 외부 스키마를 바꾸면      |         | 외부 스키마를 바꾸면           |
   | → 이용자도 같이 고침      |         | → 상대가 준비될 때까지 못 바꿈  |
   +-----------------------+         +----------------------------+
              자유                        약속이 필요 = 계약
```

Pat Helland는 2005년 논문에서 서비스 바깥으로 나가는 데이터와 안쪽에 머무는 데이터를 나눴습니다. 바깥으로 나간 데이터는 메시지 형식과 업무 의미가 잘 정의되어야 하고, 안쪽 데이터는 서비스 로직을 거쳐서만 접근된다는 구분이에요. Eric Evans가 도메인 주도 설계를 정리한 『DDD Reference』(2015)도 서비스마다 계약을 정의하라고 합니다. 여기서 계약은 서비스와 주고받는 상호작용에 관한 단언의 집합이에요. 이 가이드는 이 생각을 이어받아 계약을 넷째 산출물로 둡니다.

> 안쪽의 자유는 바깥에 한 약속으로 얻습니다.

### 정의

이 가이드는 계약을 이렇게 정의합니다.

> 계약은 경계 하나에서 제공자가 소비자에게 하는 약속의 묶음입니다. 무엇을 받는지, 무엇을 돌려주는지, 언제나 무엇이 참인지, 어떻게 실패하는지, 어느 품질로 제공하는지, 어떻게 바뀌는지를 적습니다.

"경계 하나"가 중요합니다. 계약은 시스템 전체에 하나가 아니라 경계마다 하나씩 있어요. 「틈」에는 회원 앱과 예약 API 사이에 하나, 예약 시스템과 회계 시스템 사이에 하나가 있습니다.

### Meyer의 계약: 의무와 이익

계약이라는 말을 소프트웨어 설계에 들여온 사람은 Bertrand Meyer입니다. 1986년 기술 보고서에서 시작해 1992년 *IEEE Computer* 논문 「Design by Contract 적용하기」와 1997년 『Object-Oriented Software Construction』 2판으로 정리했어요. 1986년 보고서는 서지 정보만 확인했고, 핵심 내용은 1992년 논문과 Eiffel 공식 문서에서 확인했습니다.

Meyer의 출발점은 사람 사이의 계약입니다. 두 당사자가 있고, 각자 이익을 기대하며 그 대가로 의무를 져요. 한쪽의 의무는 대개 다른 쪽의 이익이고요. 1992년 논문은 택배를 예로 듭니다. 고객은 정해진 크기와 무게 안의 소포와 요금을 내야 하고(의무), 정해진 시간 안에 배달받습니다(이익). 택배사는 시간 안에 배달해야 하고(의무), 너무 크거나 무겁거나 요금을 안 낸 소포는 받지 않아도 됩니다(이익).

「틈」의 예약하기를 같은 표로 적어 보겠습니다.

| 당사자 | 의무 | 이익 |
| --- | --- | --- |
| 소비자(회원 앱) | 회원번호·회의실·시작·끝을 보냄. 시각은 30분 경계, 길이는 4시간 이하 | 성공하면 확정 예약을 얻고, 그 시간에 그 회의실을 겹쳐 잡은 사람이 없다는 보장을 받음 |
| 제공자(예약 API) | 겹침이 없으면 확정 예약을 기록하고 예약번호를 돌려줌. 회계 시스템에 확정 사실을 알림 | 형식에 어긋난 요청은 처리하지 않아도 됨 |

Meyer는 이것을 세 가지 단언으로 적었습니다.

```text
사전조건 (require)   호출하기 전에 소비자가 참으로 만들어야 하는 것
사후조건 (ensure)    사전조건이 참이었다면, 끝났을 때 제공자가 참으로 만드는 것
불변식   (invariant)  호출 전후에 언제나 참인 것

예약하기(회원, 회의실, 시작, 끝)
  사전조건  pre1 회원이 존재하고 정지 상태가 아님
           pre2 시작·끝이 30분 경계, 끝 > 시작, 끝 - 시작 ≤ 4시간
           pre3 시작이 지금보다 뒤
  사후조건  post1 성공이면: 상태가 확정인 새 예약 하나가 생기고, 그 예약번호를 돌려줌
           post2 성공이면: 회계 시스템으로 "예약 확정" 이벤트 하나가 나감
  불변식    inv1 같은 회의실의 확정 예약끼리는 시간이 겹치지 않음
```

이 표기는 1969년 Hoare가 프로그램의 정당성을 따지려고 쓴 `P {Q} R`, 곧 Q를 시작하기 전에 P가 참이면 Q가 끝났을 때 R이 참이라는 꼴과 같은 모양입니다. 1992년 논문은 불변식 개념이 Hoare의 1972년 연구에서 왔다고 적어요.

위반했을 때 책임이 누구에게 있는지도 계약이 정합니다. Eiffel 공식 문서는 사전조건 위반은 호출한 쪽(소비자)의 버그이고, 사후조건이나 불변식 위반은 제공자의 버그라고 정리해요. 계약이 빠짐없이 적혀 있다면 계약에 없는 조건을 상대에게 요구할 수 없다는 원칙(No Hidden Clauses)도 1992년 논문에 있습니다.

### 네트워크 경계에서는 실패도 약속이다

Meyer의 계약을 HTTP API에 그대로 옮기면 한 군데가 어긋납니다. Eiffel에서는 사전조건을 지키는 것이 호출자의 책임이라서, 루틴 몸체가 사전조건을 다시 검사하지 않아요. 그런데 API는 누가 어떤 요청을 보낼지 통제할 수 없습니다. 사전조건을 어긴 요청이 **반드시** 들어옵니다.

그래서 이 가이드는 API 계약에서 사전조건을 두 갈래로 나눠 적습니다. Meyer의 원래 틀을 경계에 맞게 고친 것이라 원전의 구분은 아니에요.

```text
업무 사전조건  이 조건이 아니면 요청이 업무상 뜻이 없음        예: pre1 회원이 정지 상태가 아님
형식 사전조건  이 조건이 아니면 요청을 해석할 수 없음          예: pre2 30분 경계, 4시간 이하

→ 둘 다 제공자가 검사하고, 어겼을 때 돌려줄 응답을 계약에 적는다
   pre1 위반 → 403 member_suspended (상태 변화 없음)
   pre2 위반 → 422 invalid_slot     (상태 변화 없음)
   inv1 충돌 → 409 slot_taken       (상태 변화 없음)
```

"상태 변화 없음"을 함께 적는 것이 중요해요. 실패했을 때 무엇이 바뀌지 않았는지도 소비자가 기대는 사실입니다. Cockburn의 유스케이스 형식에 있는 **최소 보장**(어떻게 끝나든 성립하는 것)이 바로 이 자리에 해당하고, 16장에서 다시 만납니다.

### 계약의 다섯 겹

이제 계약에 무엇을 적어야 빠짐이 없는지 정리하겠습니다. 이 가이드는 다섯 겹으로 나눠요. 원전에서 온 목록이 아니라, 앞의 Meyer의 단언과 아래에서 볼 명세 형식들이 담는 내용을 묶은 교육용 분류입니다.

| 겹 | 묻는 것 | 「틈」 예약하기 API의 예 |
| --- | --- | --- |
| 구조 | 어떤 모양을 주고받는가 | 요청 `{memberId, roomCode, startAt, endAt}`, 응답 `{bookingId, status}` |
| 의미 | 각 값이 무엇을 뜻하는가 | `endAt`은 불포함. 시각은 오프셋을 단 ISO 8601. `roomCode`는 회의실 코드표의 값 |
| 행위 | 사전·사후조건, 불변식, 실패, 멱등성, 순서 | pre1~pre3, post1~post2, inv1. 실패 응답 셋. 같은 `Idempotency-Key`로 다시 보내면 같은 결과 |
| 품질 | 얼마나 빠르고, 얼마나 자주 쓸 수 있고, 얼마나 신선한가 | 응답 0.5초 이내(가정), 이벤트는 확정 뒤 1분 안에 발행(가정) |
| 진화 | 어떻게 바뀌고, 바뀌기 전에 무엇을 알리는가 | 필드 추가는 예고 없이 가능. 필드 삭제·뜻 변경은 새 주 버전, 90일 전 공지(가정) |

3장의 외부 스키마는 이 가운데 **구조**와 **의미**의 상당 부분을 이미 담고 있어요. 계약은 외부 스키마를 감싸고 행위·품질·진화를 더한 것이라고 보면 됩니다.

```text
+--------------------------------------------------+
| 계약                                              |
|   +------------------------------+               |
|   | 외부 스키마  (구조 · 의미)       |  행위 · 품질 · 진화 |
|   +------------------------------+               |
+--------------------------------------------------+
```

### 명세 형식은 계약의 어디를 적는가

계약을 기계가 읽는 형태로 적는 형식이 여럿 있습니다. 조회 시점(2026-11-17) 기준 버전과 각 형식이 다섯 겹 가운데 어디를 주로 적는지 표로 정리합니다.

| 형식 | 버전(조회 시점) | 주로 적는 겹 | 비고 |
| --- | --- | --- | --- |
| OpenAPI | 3.2.1 (2026-09-10) | 구조, 행위 일부(연산·응답 코드·보안) | HTTP API의 언어 중립 인터페이스 |
| JSON Schema | 2020-12 | 구조, 의미 일부(형식·열거·범위) | 문서가 어떤 모양이어야 하는지 단언. 진화 규칙은 없음 |
| AsyncAPI | 3.1.0 (2026-01-31) | 구조, 행위 일부(채널·보내기/받기) | 메시지 기반 API |
| Arazzo | 1.1.0 (2026-05-17) | 행위(호출 순서) | 여러 호출의 순서와 의존 |
| ODCS | v3.2.0 (2026-09-08, 연도는 2차 자료) | 구조, 품질(품질 규칙·SLA), 진화 일부(상태·버전) | 데이터 계약 표준 |
| Pact 계약 파일 | — | 구조·행위의 예 | 소비자 테스트에서 생기는 예시 계약 |

열람한 범위에서 OpenAPI와 AsyncAPI 명세에는 연산마다 사후조건이나 멱등성을 적는 표준 필드가 보이지 않았습니다. 명세 전문을 다 읽지는 못했으므로 "없다"고 단정하지는 않을게요. 멱등성은 HTTP 의미론에 일부 들어 있습니다. RFC 9110은 PUT·DELETE와 안전한 메서드(GET·HEAD 등)를 멱등이라고 정합니다. POST로 만드는 예약하기는 멱등이 아니므로, 같은 요청을 다시 보냈을 때 어떻게 되는지는 계약에 따로 적어야 해요. 「틈」은 `Idempotency-Key` 머리글로 같은 키의 재요청에 첫 결과를 돌려주기로 했습니다.

ODCS(Open Data Contract Standard)는 LF AI & Data 재단 산하 Bitol 프로젝트의 데이터 계약 표준입니다. 문서 목차에 스키마, 데이터 품질, 서비스 수준 합의(SLA), 팀과 역할 같은 절이 있어서, API 명세가 잘 다루지 않는 품질 겹을 적기에 좋아요. SLA 항목에는 지연(latency), 가용성, 보존 기간, 갱신 주기 같은 것이 있습니다. 비슷한 목적의 Data Contract Specification은 ODCS v3.1.0이 나오면서 폐기되었다고 그 저장소에 공지되어 있습니다.

### 누가 계약을 정하는가: 제공자 계약과 소비자 주도 계약

계약은 제공자가 일방적으로 정하는 것일까요? Ian Robinson은 2006년 글 「소비자 주도 계약: 서비스 진화 패턴」에서 세 가지를 나눴습니다.

| 이름 | 무엇인가 | 성격 |
| --- | --- | --- |
| 제공자 계약 | 제공자가 내놓는 기능 전체(스키마, 인터페이스, 정책, 품질 특성) | 닫혀 있고, 하나이며, 권위가 있음 |
| 소비자 계약 | 소비자 한 명이 제공자에게 기대하는 것 | 열려 있고, 불완전하며, 여럿 |
| 소비자 주도 계약 | 지금 있는 소비자 계약들을 합한 데서 나온 제공자 계약 | 지금의 소비자들에 대해서는 닫혀 있고 완전함 |

차이가 실제로 문제가 되는 때는 변경할 때입니다. 제공자 계약만 보면 응답에서 필드 하나를 지우는 것은 언제나 깨는 변경이에요. 그런데 소비자 계약을 모아 보니 아무도 그 필드를 쓰지 않는다면, 지금의 소비자 주도 계약은 그 필드를 담고 있지 않습니다. 지워도 되는 거예요.

```text
제공자 계약:  bookingId, status, roomCode, startAt, endAt, createdAt
회원 앱이 씀:  bookingId, status, startAt, endAt
회계 시스템이 씀: bookingId, roomCode, startAt, endAt

소비자 주도 계약 = 합집합 = bookingId, status, roomCode, startAt, endAt
→ createdAt 은 지금 아무도 쓰지 않음 → 지워도 지금의 소비자는 그대로
```

Robinson은 소비자가 응답 전체를 엄격하게 검증하면 제공자가 무엇 하나만 바꿔도 함께 배포해야 한다고 지적하고, 자기가 쓰는 부분만 검증하라고 권했어요. Martin Fowler는 2011년 같은 생각을 **Tolerant Reader**라고 불렀습니다. 필요한 필드만 읽고 나머지는 무시하며 구조에 대한 가정을 최소로 하는 소비자입니다.

이 생각을 도구로 만든 것이 Pact입니다. Pact 공식 문서의 흐름은 이래요.

```text
1. 소비자 테스트   소비자가 기대하는 요청과 최소한의 응답을 적고, 모의 제공자로 시험
2. 계약 파일 생성   테스트가 통과하면 pact 파일(JSON)이 나옴 = 소비자 계약
3. 제공자 검증     기록된 요청을 실제 제공자에 다시 보내, 응답이 최소 기대를 채우는지 확인
4. 배포 판단       소비자·제공자 버전 조합별 검증 결과를 보고 배포해도 되는지 판단(can-i-deploy)
```

Pact는 계약을 예시로 적기 때문에, 소비자가 실제로 쓰는 것만 계약에 들어갑니다. 제공자는 아무도 쓰지 않는 동작을 바꿀 수 있어요.

### 계약은 어떻게 바뀌는가: 호환성

계약을 바꿀 때 묻는 질문은 하나예요. 이미 있는 상대가 그대로 동작하는가? 이벤트와 메시지 쪽에서 이 질문을 가장 체계적으로 정리한 문서가 Confluent Schema Registry의 호환성 유형입니다. 기본값은 BACKWARD예요.

| 유형 | 뜻 | 먼저 올릴 쪽 |
| --- | --- | --- |
| BACKWARD | 새 스키마를 쓰는 소비자가 바로 앞 스키마로 쓴 데이터를 읽을 수 있음 | 소비자 |
| FORWARD | 새 스키마로 쓴 데이터를 바로 앞 스키마의 소비자가 읽을 수 있음 | 생산자 |
| FULL | 바로 앞 스키마와 양쪽 모두 | 어느 쪽이든 따로 |
| *_TRANSITIVE | 바로 앞 하나가 아니라 등록된 모든 이전 버전과 | 위와 같음 |
| NONE | 검사하지 않음 | 주의 |

형식마다 "무엇이 호환되는가"를 판정하는 규칙이 다릅니다.

- **Avro**는 이름으로 필드를 맞춥니다. 읽는 쪽 스키마에 없는 필드는 무시하고, 쓴 쪽에 없는 필드는 읽는 쪽 기본값을 쓰며, 기본값이 없으면 오류예요(Avro 1.12.0 명세). 그래서 기본값이 있는 필드를 더하거나 빼는 변경이 양쪽으로 호환됩니다.
- **Protocol Buffers**는 필드 **번호**가 정체성입니다. 공식 문서는 기존 필드의 번호를 바꾸는 것이 안전하지 않다고 하고, 지운 필드의 번호를 다시 쓰지 말라고 해요. 다시 쓰면 해독이 모호해지고 데이터 손상이나 개인정보 노출로 이어질 수 있습니다. 지운 번호와 이름은 `reserved`로 막아 둡니다.
- **JSON Schema**에는 호환성 규칙이 정의되어 있지 않습니다. Confluent 문서가 직접 그렇게 적어요. 판정은 스키마가 모르는 필드를 허용하는 열린 모델(`additionalProperties` 기본값 true)인지, 막는 닫힌 모델인지에 따라 달라집니다.

버전 번호로 변경의 종류를 알리는 관례가 Semantic Versioning 2.0.0입니다. 호환되지 않는 API 변경은 MAJOR, 하위 호환인 기능 추가는 MINOR, 하위 호환인 버그 수정은 PATCH를 올려요. 그리고 Semver는 **공개 API를 선언해야** 한다고 요구합니다. 무엇이 공개 API인지 선언하지 않으면 무엇이 깨는 변경인지도 정할 수 없으니까요.

### 호환성을 계약의 말로 다시 읽기

Meyer는 하위 클래스가 부모의 루틴을 다시 정의할 때의 규칙도 정했습니다. Eiffel 공식 문서에 따르면 다시 정의한 사전조건은 원래보다 약하거나 같아야 하고, 사후조건은 원래보다 강하거나 같아야 해요. 부모를 기대하고 호출하던 쪽이 자식을 받아도 놀라지 않게 하는 규칙입니다.

이 규칙은 계약의 진화에 그대로 들어맞습니다. 새 버전을 옛 버전의 "하위 유형"으로 보면, 옛 버전을 기대하던 소비자가 놀라지 않는 변경은 **사전조건을 약하게**(더 많이 받음) 하거나 **사후조건을 강하게**(더 많이 약속함) 하는 변경이에요. 이 연결은 원전이 한 말이 아니라 이 가이드가 두 원전을 이어서 읽은 것입니다.

| 변경 | 계약의 말로 | 옛 소비자는? |
| --- | --- | --- |
| 응답에 `confirmedAt` 필드 추가 | 사후조건 강화 | Tolerant Reader라면 그대로. 닫힌 모델로 엄격히 검증하면 실패 |
| 요청의 `note` 필드를 선택으로 허용 | 사전조건 약화 | 그대로 (안 보내던 소비자는 계속 안 보내면 됨) |
| 요청의 `attendees` 필드를 필수로 | 사전조건 강화 | 실패 (옛 요청에는 없음) |
| 응답에서 `roomCode` 삭제 | 사후조건 약화 | 그 필드를 쓰던 소비자는 실패 |

여기서 헷갈리기 쉬운 포인트가 하나 있습니다. 같은 변경이 방향에 따라 약화도 되고 강화도 돼요. 예약 단위를 30분에서 15분으로 풀었다고 해 봅시다.

```text
예약 단위 30분 → 15분으로 완화

요청 쪽에서 보면   사전조건 약화 → 옛 회원 앱은 30분 단위로 계속 보냄 → 그대로
이벤트 쪽에서 보면 사후조건 약화 → "모든 예약은 30분 경계"를 믿던 회계 시스템이
                                 10:15 시작 예약을 받음 → 요금 계산이 어긋날 수 있음
```

요청을 보내는 쪽에게는 호환되는 변경이, 결과를 읽는 쪽에게는 호환되지 않는 변경이 됩니다. Confluent의 BACKWARD와 FORWARD가 따로 있는 것도 같은 이유예요. 그래서 계약의 진화 겹에는 "누구에게 호환되는가"를 소비자별로 적어야 합니다.

### 너그럽게 받기의 대가: Postel 법칙과 RFC 9413

호환성을 이야기할 때 자주 인용되는 원칙이 Postel 법칙(robustness principle)입니다. 1980년 TCP 명세 RFC 761에 실렸고(RFC 9413은 가장 이른 형태를 같은 해의 RFC 760에서 찾습니다), 1989년 RFC 1122에서는 받을 때는 너그럽게, 보낼 때는 보수적으로라는 꼴로 다시 적혔어요. 앞의 Tolerant Reader도 이 원칙을 인용합니다.

2023년 IAB(인터넷 아키텍처 위원회)의 RFC 9413 「견고한 프로토콜 유지하기」는 이 원칙의 부작용을 짚습니다. 잘못된 입력을 조용히 받아 주면 그 결함이 실제 표준처럼 굳고, 새 구현은 기존 구현의 버그까지 맞춰야 하게 된다는 것이에요. RFC 9413의 처방은 명세를 발행한 뒤에도 계속 유지보수하는 것, 그리고 명세가 뒷받침한다면 명시되지 않은 입력에 분명한 오류를 내는 쪽을 택하는 것입니다.

두 문서를 함께 놓으면 경계마다 다른 태도가 나옵니다. 이 정리는 이 가이드의 판단이에요.

```text
읽는 쪽(소비자)    모르는 필드는 무시한다 (Tolerant Reader)
받는 쪽(제공자)    계약에 없는 입력은 분명한 오류로 돌려준다 (RFC 9413)
                 "알아서 고쳐 받기"는 하지 않는다 → 그 버릇이 실제 계약이 된다
```

### 선언하지 않아도 생기는 계약: Hyrum 법칙

마지막으로, 계약은 적은 것보다 넓어지기 쉽습니다. Hyrum 법칙(hyrumslaw.com)은 API 이용자가 충분히 많으면 계약에 무엇을 약속했든 "all observable behaviors of your system will be depended on by somebody"라고 말해요.

「틈」의 예약 목록 API가 계약에는 순서를 약속하지 않았지만 늘 시작 시각순으로 돌려줬다고 해 봅시다. 회계 팀은 그 순서를 믿고 첫 줄을 그달 첫 예약으로 처리했습니다. 내부 스키마를 바꾸다 순서가 달라지면, 계약을 어긴 사람은 없는데 회계 시스템이 틀린 값을 냅니다.

```text
선언한 계약       bookingId, status, roomCode, startAt, endAt  (순서는 약속 안 함)
관찰된 의존       + 시작 시각순 정렬  + 빈 목록일 때 [] (null 아님)  + 응답 0.3초 안팎
------------------------------------------------------------------
실제 계약         선언한 계약 + 관찰된 의존
```

이 가이드는 선언한 계약에 관찰된 의존을 더한 것을 **실제 계약**이라고 부릅니다. 실제 계약은 문서에 없으니 찾아내야 해요. 26장에서 오래된 DB를 역공학할 때 질의 기록으로 실제 계약을 복원하는 방법을 다룹니다. 처방은 두 가지입니다. 기대도 되는 것은 계약에 올려 선언하고, 기대면 안 되는 것은 일부러 흔들어(예: 순서를 무작위로) 의존이 생기지 않게 하는 거예요.

### 헷갈리기 쉬운 곳

1. 계약은 명세 파일이 아닙니다. OpenAPI 파일은 계약 가운데 기계가 읽을 수 있는 부분이고, 의미·품질·진화 정책은 대개 산문으로 따로 적어야 해요. 파일만 보고 계약이 완성되었다고 여기면 다섯 겹 가운데 셋이 빕니다.
2. 계약은 외부 스키마와 같지 않습니다. 외부 스키마가 "무엇을 어떤 모양으로 보는가"라면, 계약은 "무엇을 언제까지 어떻게 지키는가"예요. 같은 외부 스키마에 계약이 둘일 수도 있습니다. 내부 대시보드에는 언제든 바뀔 수 있다는 계약을, 협력사 API에는 90일 전 공지 계약을 붙이는 식으로요.
3. 계약이 있다고 데이터 독립성이 사라지지는 않습니다. 계약은 바깥을 고정하고, 그 덕분에 안쪽(개념 스키마의 나눔, 내부 스키마)은 사상을 고쳐 가며 바꿀 수 있어요.

### 잠깐 확인

회계 팀이 "예약 확정" 이벤트에 회원 등급도 넣어 달라고 요청했습니다. 등급을 선택 필드로 추가하는 것은 어떤 변경이고, 누구를 먼저 올려야 할까요?

생산자(예약 시스템) 쪽에서 보면 사후조건을 강하게 하는 변경입니다. 기본값이 있는 선택 필드를 더하는 것이라 Avro라면 앞뒤 양쪽으로 호환되고, 옛 소비자가 Tolerant Reader라면 새 필드를 무시해요. 생산자를 먼저 올려도 됩니다. 다만 회계 시스템이 닫힌 모델로 엄격히 검증한다면 새 필드 때문에 실패하므로, 그때는 소비자를 먼저 올려야 합니다. 어느 경우인지 확인하는 것이 소비자 주도 계약 시험의 역할이에요.

### 스스로 점검하기

1. 「틈」의 취소하기 연산에 대해 사전조건·사후조건·불변식을 적고, 실패 응답과 상태 변화 없음을 함께 적어 보세요. R5(시작 1시간 전보다 늦은 취소는 사용으로 셈)를 어디에 적을지도 정해 보세요.
2. 예약 확정 이벤트의 `endAt` 뜻을 "불포함"에서 "포함"으로 바꾸려 합니다. 다섯 겹 가운데 어디가 바뀌고, Semver로는 무엇을 올려야 할까요? 필드 이름과 모양은 그대로라는 점에 주의하세요.
3. 예약 목록 API가 빈 결과에 `null`을 돌려주다가 `[]`로 바꾸려 합니다. 선언한 계약에 빈 결과의 모양이 적혀 있지 않았다면, 이 변경은 안전할까요? Hyrum 법칙으로 설명해 보세요.

#### 풀이

1. 예를 들어 이렇게 적습니다.

```text
취소하기(회원, 예약번호)
  사전조건  pre1 예약이 존재하고 그 회원의 것   pre2 예약 상태가 확정
  사후조건  post1 예약 상태가 취소, 취소 시각이 기록됨
           post2 취소 시각이 시작 1시간 전보다 늦으면 그 예약은 사용 분에 셈(R5)
           post3 회계 시스템으로 "예약 취소" 이벤트(사용 분 포함 여부 포함)가 나감
  불변식    inv1 그대로
  실패      pre1 위반 → 404 (상태 변화 없음), pre2 위반 → 409 not_cancellable (상태 변화 없음)
```

R5는 개념 스키마에 적힌 규칙이면서, 취소하기 계약에서는 사후조건 post2로, 이벤트에서는 의미 겹으로 다시 적힙니다. 회계 시스템이 사용 분을 직접 계산한다면, 계산 규칙이 계약에 들어가야 양쪽 계산이 어긋나지 않습니다.

2. 모양(구조 겹)은 그대로이고 뜻(의미 겹)이 바뀝니다. 같은 값이 다른 뜻이 되므로, 옛 소비자는 오류 없이 틀린 계산을 하게 됩니다. 호환되지 않는 변경이라 MAJOR를 올려야 하고, 가능하면 필드 이름을 바꿔(`endAtInclusive`처럼) 옛 소비자가 모르는 채 새 뜻을 받지 않게 하는 편이 안전합니다.

3. 안전하다고 단정할 수 없습니다. 선언한 계약에는 없었더라도, 소비자가 `null`을 보고 "결과 없음"을 판단하도록 만들었다면 그것은 관찰된 의존이고 실제 계약의 일부입니다. Hyrum 법칙이 말하는 상황이 바로 이것입니다. 소비자를 확인하거나(소비자 주도 계약 시험), 바꾸기 전에 빈 결과의 모양을 계약에 선언하고 공지해야 합니다.
