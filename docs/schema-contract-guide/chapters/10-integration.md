## 10장 관점 통합과 스키마 품질

이 장을 마치면 서로 다른 이용자나 씨앗에서 나온 부분 스키마를 네 단계(사전 통합·비교·맞추기·병합과 재구성)로 합칠 수 있어요. 이름 충돌과 구조 충돌을 예로 찾아내고, 합친 결과를 품질 기준으로 점검하게 됩니다.

### 왜 통합이 필요한가

8장에서는 일정표와 청구 명세라는 두 사례로 개념 스키마를 만들었어요. 실제 프로젝트에서는 사례가 훨씬 많고, 사례마다 담당자가 다릅니다. 회원 앱 담당, 안내 데스크, 회계팀이 각자 자기 말로 자기 관점을 설명하면, 관점마다 작은 개념 스키마가 하나씩 생겨요. 이것을 하나로 합치는 일이 **뷰 통합**입니다.

Batini·Lenzerini·Navathe의 1986년 조사 논문 「데이터베이스 스키마 통합 방법론 비교 분석」(*ACM Computing Surveys* 18권 4호)은 스키마 통합을 기존 또는 제안된 데이터베이스의 스키마를 전역 통합 스키마로 합치는 일로 정의하고, 두 맥락을 나눕니다. 설계할 때 여러 이용자 관점을 합치는 뷰 통합과, 이미 있는 여러 데이터베이스를 합치는 데이터베이스 통합이에요. 이 장은 뷰 통합을 다루고, 데이터베이스 통합은 26장 역공학에서 조금 다룹니다.

### 통합의 네 단계

논문은 열두 가지 방법론을 비교한 뒤 통합의 공통 단계를 넷으로 정리합니다.

```text
1. 사전 통합     무엇을, 어떤 순서로 합칠지 정함. 우선순위(예: 회계 관점 우선)
                 전략: 이진(둘씩, 사다리꼴·균형) / n항(한 번에, 반복)
2. 비교          개념끼리 대응을 찾고 충돌을 찾음. 스키마 사이의 관계도 발견
3. 맞추기        충돌을 풀어 합칠 수 있게 고침 (이름 바꾸기, 구조 변환 ...)
4. 병합과 재구성  겹쳐서 중간 스키마를 만들고, 품질 기준에 맞게 다시 짬
```

논문은 3단계에 대해 충돌을 자동으로 푸는 것은 대개 불가능하며 설계자·이용자와 주고받아야 한다고 분명히 적어요. 충돌의 상당수는 업무의 뜻을 정하는 문제라서 기계가 대신할 수 없기 때문입니다.

「틈」의 세 관점에서 나온 부분 스키마를 가져와 보겠습니다.

```text
[앱 관점 A]                       [데스크 관점 B]                  [회계 관점 C]
회원(회원번호)                      방(방 이름)                      고객(이메일)
  - 이름, 등급                       - 정원                           - 이름, 요금제
회의실(코드)                        예약(시간대)                      요금제
예약(예약번호)                        - 손님, 이용 시간                  - 월 무료 시간, 초과 단가
  - 회원, 회의실, 시작, 끝, 상태                                     사용 내역
                                                                    - 고객, 공간, 사용 분, 월
```

### 2단계: 충돌 찾기

논문은 충돌을 크게 이름 충돌과 구조 충돌로 나눕니다.

**이름 충돌**에는 두 가지가 있어요. **동음이의어**는 같은 이름이 서로 다른 개념을 가리키는 경우이고, **이음동의어**는 같은 개념이 다른 이름으로 불리는 경우입니다. 논문의 예로는 EQUIPMENT가 한쪽에서는 기계만, 다른 쪽에서는 가구까지 가리키는 것이 동음이의어이고, CLIENT와 CUSTOMER가 이음동의어예요. 논문은 동음이의어는 같은 이름끼리 견줘 찾을 수 있지만 이음동의어는 바깥 정보가 있어야 찾을 수 있다고 덧붙입니다.

```text
이음동의어  A 회의실 = B 방 = C 공간                 → 같은 것을 셋이 다르게 부름
           A 회원 / C 고객                          → 같은가? 아직 모름 (아래 키 충돌)
           A 등급 / C 요금제                         → 같은가? (아래 유형 충돌)
동음이의어  B 이용 시간 = 실제로 방에 있던 시간
           C 사용 분   = 예약에 적힌 시간           → "이용"과 "사용"이 다른 것을 가리킴
```

**구조 충돌**은 같은 개념을 서로 다른 모델 구성 요소나 제약으로 표현해서 생깁니다. 논문은 네 가지를 들어요.

| 종류 | 뜻 | 「틈」의 예 |
| --- | --- | --- |
| 유형 충돌 | 같은 개념이 한쪽은 개체, 다른 쪽은 속성 | A는 등급을 회원의 속성으로, C는 요금제를 무료 시간·단가를 가진 개체로 봄 |
| 종속 충돌 | 개념 사이 관계의 다중성이 다름 | A는 회원-등급 1:1(지금 등급), C는 월별 요금제 이력이 있어 사실상 시간에 따른 1:N |
| 키 충돌 | 같은 개념에 다른 식별자 | A 회원번호 vs C 이메일 |
| 행위 충돌 | 넣기·지우기 정책이 다름 | 회원이 탈퇴하면 A는 미래 예약을 취소하고 회원을 지움, C는 지난 사용 내역을 5년 보관해야 함 |

### 3단계: 맞추기

충돌마다 어떻게 맞출지 정합니다. 대부분 담당자에게 물어서 정해요.

```text
이음동의어   회의실 / 방 / 공간         → "회의실"로 통일. 용어집 t4 에 동의어로 방·공간 기록
동음이의어   이용 시간 / 사용 분         → "예약 시간"(예약에 적힌 구간)과
                                        "재실 시간"(실제 있던 시간)으로 나눔.
                                        재실 시간은 담화 세계 밖(출입 기록 없음)으로 확인
유형 충돌    등급 속성 / 요금제 개체     → 개체로 맞춤: 등급(이름, 월 무료 분, 초과 단가)
종속 충돌    1:1 / 시간에 따른 1:N       → 이력으로 맞춤: F2'(9장의 등급 기간)
키 충돌      회원번호 / 이메일           → 회원번호를 참조 방식으로, 이메일은 속성(바뀔 수 있음)
                                        C와 주고받을 때는 회원번호를 쓰기로 계약에 적음
행위 충돌    탈퇴 시 삭제 / 5년 보관      → 회원은 지우지 않고 "탈퇴" 상태로. 개인 정보 일부는 지움
```

키 충돌을 푸는 방식에 주목해 보세요. 이메일은 회원이 바꿀 수 있어서 참조 방식으로 부적합합니다. 2장에서 본 대로 참조 방식은 시간이 지나도 바뀌지 않아야 하니까요. 그런데 C(회계)는 이미 이메일로 고객을 찾고 있습니다. 회계 시스템은 다른 팀의 것이라 예약 시스템이 바꿀 수 없어요. 그래서 결정을 **계약**에 적습니다. "예약 확정 이벤트는 회원번호를 담고, 회계 시스템은 회원번호로 고객을 찾는다." 통합의 결정이 개념 스키마에만 머물지 않고 경계의 계약까지 이어지는 경우예요.

행위 충돌도 비슷합니다. "회원을 지운다"와 "5년 보관한다"는 같은 담화 세계에서 함께 참일 수 없어요. 맞추는 방법은 "회원"을 지우지 않고 상태를 두는 것이었습니다. 그런데 개인 정보를 지워야 한다는 요구가 따로 있다면, 회원에 관한 사실 유형마다 무엇을 지우고 무엇을 남길지 정해야 해요. 이 결정은 계약의 품질 겹(보존 기간)에도 들어갑니다.

### 4단계: 병합과 재구성

맞춘 스키마를 겹치면 중간 통합 스키마가 나옵니다. 논문이 든 예에서는 한쪽 스키마의 Book과 다른 쪽 Publication을 겹친 뒤, Book을 Publication의 부분집합으로 두고 공통 속성을 Publication으로 옮겨요. 「틈」에서는 이런 결과가 나옵니다.

```text
[개체] 회원(회원번호)          ← A 회원 + C 고객
         이름 · 이메일 · 상태{활동, 탈퇴}
[개체] 등급(등급 이름)          ← A 등급 + C 요금제
         월 무료 분 · 초과 단가(30분당)
[사실] F2' 회원 은 [시작일, 종료일) 동안 등급 에 속했다      ← 종속 충돌 해소
[개체] 회의실(회의실 코드)      ← A 회의실 + B 방 + C 공간
         정원(선택)
[개체] 예약(예약번호)           ← A 예약 + B 예약
         회원 · 회의실 · 시작 · 끝 · 상태 · 취소 시각(선택)
[사실] F11 예약 은 손님 이름 을 가진다 (여럿, 선택)         ← B에서 옴
[파생] D1 사용 분 (월, 회원)      ← C 사용 내역은 저장하지 않고 파생으로
```

C의 "사용 내역"이 개체가 아니라 파생 규칙 D1이 된 것을 보세요. 사용 분은 예약에서 계산되므로, 따로 저장하면 2장의 원칙에서 본 중복이 생깁니다. 이처럼 병합 뒤 다시 짜는 일을 논문은 **재구성**이라 부르고, 그 기준으로 셋을 듭니다. 통합 스키마가 모든 구성 스키마의 개념을 올바르게 담아야 한다는 완전성과 정확성, 둘 이상에 있던 개념이 한 번만 나타나야 한다는 **최소성**, 같은 내용을 담는 여러 표현 가운데 가장 이해하기 쉬운 것을 골라야 한다는 이해 용이성이에요.

논문은 통합 과정에서 어느 구성 스키마에도 없던 관계가 발견될 수 있다고도 말합니다. 「틈」에서는 회계 관점의 "공간"과 앱 관점의 "회의실"을 맞추다가, 회계는 회의실마다 단가를 다르게 매기고 싶어 한다는 사실이 나왔다고 해 봅시다. 어느 관점에도 "회의실은 초과 단가를 가진다"는 없었어요. 원장에 q를 더하고, 확인을 받으면 사실 유형을 더합니다.

| 점검 | 질문 | 「틈」에서 확인 |
| --- | --- | --- |
| 완전성 | 원장의 모든 f·r이 스키마 어딘가에 있는가? 모든 v의 열에 화살표를 달 수 있는가? | 손님 이름(F11), 등급 이력(F2') 반영 |
| 적절성 | 스키마에 원장 어디에도 근거가 없는 요소가 있는가? | 회의실 층 정보: 근거 없음 → 뺌 |
| 정확성 | 각 요소가 표기법의 정의대로 쓰였고, 요구를 바르게 옮겼는가? | 노쇼를 상태로 둔 것은 q2 답 전까지 잠정 |
| 최소성 | 다른 요소에서 계산되는 것을 따로 두지 않았는가? | 사용 내역을 D1로 바꿈 |
| 이해 용이성 | 담당자가 이 스키마를 읽고 자기 업무를 알아보는가? | 용어집의 이름(회의실, 예약 시간) 그대로 씀 |

Batini의 강의록은 완전성과 적절성을 확인하는 방법도 줍니다. 요구 문서의 명사와 동사에 표시를 하고, 하나하나가 스키마의 어느 요소에 대응하는지 보는 거예요. 대응이 없는 명사·동사는 완전성의 구멍이고, 대응하는 문장이 없는 스키마 요소는 적절성의 문제입니다. 원장을 쓰고 있다면 이 확인은 원장 줄과 스키마 요소를 잇는 일과 같아요. 13장의 추적표가 바로 그 일을 합니다.

Batini 강의록은 최소성에 관해 단서를 하나 답니다. 중복을 개념 설계에서 반드시 없앨 필요는 없고, 확인해서 표시해 두라는 것이에요. 논리 설계에서는 중복이 특정 질의를 빠르게 할 수도 있으니까요. 이 가이드의 방식으로 말하면, 개념 스키마에는 파생 규칙으로 적고, 저장할지는 12장에서 작업 부하를 보고 정합니다.

### 헷갈리기 쉬운 곳

1. 통합은 합집합이 아닙니다. 세 관점의 요소를 모두 모아 놓기만 하면 회의실·방·공간이 따로 있는 스키마가 나와요. 맞추기를 거쳐야 같은 것이 하나가 됩니다.
2. 모든 관점을 하나로 합쳐야 하는 것도 아닙니다. 회계 관점 C는 다른 팀의 맥락이에요. 2장에서 본 대로 맥락이 다르면 개념 스키마를 합치지 않고 계약으로 잇는 선택이 있습니다. 「틈」에서는 C를 예약 맥락의 스키마에 합치지 않고, 맞추기에서 정한 것(회원번호로 찾기, 사용 분의 계산 규칙)을 계약 E1에 적는 쪽을 택할 수도 있어요. 이때 통합의 산출물은 하나의 스키마가 아니라 스키마 하나와 계약 하나입니다.
3. 충돌을 발견하면 바로 고치고 싶어지지만, 기록이 먼저입니다. 어떤 충돌을 어떻게 맞췄는지 남기지 않으면, 나중에 "왜 이메일이 키가 아니냐"는 질문에 답할 수 없어요.

### 잠깐 확인

데스크 관점 B의 "예약(시간대)"는 시간대로 예약을 식별합니다. 이것은 어떤 충돌이고 어떻게 맞춰야 할까요?

키 충돌입니다. A는 예약번호로, B는 회의실과 시간대로 예약을 알아봅니다. 2장과 8장에서 본 대로 취소된 예약과 새 예약이 같은 회의실·같은 시간대를 가질 수 있으므로 시간대는 참조 방식이 될 수 없어요. 예약번호를 참조 방식으로 하고, 데스크 화면(V2)에서는 예약번호를 보여 주지 않더라도 내부적으로는 예약번호로 찾게 맞춥니다.

### 스스로 점검하기

1. 회원 앱 관점 A에 "즐겨찾는 회의실"이 있고, 데스크 관점 B에 "자주 오는 손님"이 있다고 합시다. 둘이 같은 개념인지, 이름 충돌인지, 서로 상관없는지 판단하는 데 필요한 질문을 적어 보세요.
2. 행위 충돌(탈퇴 시 삭제와 5년 보관)을 맞춘 결과를 사실 유형마다 "탈퇴 시 지움 / 남김"으로 나눠 보세요(F1 이름, 이메일, F2' 등급 이력, F4 예약의 회원).
3. 이진 사다리꼴 전략으로 A·B·C를 합친다면 어떤 순서가 좋을까요? 사전 통합 단계의 우선순위(회계 관점 우선)를 고려해 이유를 적어 보세요.

#### 풀이

1. "즐겨찾는 회의실은 회원이 직접 표시하나요, 이용 횟수로 계산하나요?", "자주 오는 손님은 회원인가요, 회원이 데려오는 손님인가요?"를 묻습니다. 앞은 저장되는 사실인지 파생인지를, 뒤는 손님이 회원과 같은 개체인지를 가립니다. 손님이 회원이 아니고 둘 다 저장되는 표시라면 서로 상관없는 개념이고, 둘 다 이용 기록에서 계산한다면 같은 꼴의 파생 규칙 둘입니다.
2. 예를 들면 이렇습니다. 이름과 이메일은 지우거나 알아볼 수 없게 바꿈(개인 정보), F2' 등급 이력은 남김(청구 근거), F4 예약의 회원은 회원번호로 남김(회원번호만으로는 개인을 알 수 없게 이름·이메일을 지웠다는 전제). 이 결정은 법적 보관 의무와 개인정보 처리 방침에 따라 달라지므로, 근거 수준은 "확인"을 받아야 합니다.
3. 회계 관점이 우선이면 C를 기준으로 삼고, C와 가장 많이 겹치는 A를 먼저 합친 뒤(회원·등급·예약의 키와 유형 충돌이 여기서 대부분 풀림), 그 결과에 B를 합칩니다. B는 주로 이름 충돌(방, 이용 시간)과 손님 이름을 더하므로 마지막에 합쳐도 앞의 결정을 크게 바꾸지 않습니다.
