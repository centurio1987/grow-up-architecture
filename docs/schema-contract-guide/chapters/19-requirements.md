## 19장 요구사항 문장: ISO/IEC/IEEE 29148과 EARS

이 장을 마치면 "~해야 한다" 꼴의 요구사항 문장을 패턴별로 갈라 원장과 계약에 옮길 수 있어요. EARS의 다섯 패턴이 각각 불변식·사후조건·상태 의존 규칙·실패표·선택 필드로 이어지는 길을 익히고, 좋은 요구사항의 특성으로 문장을 먼저 손보는 방법도 다룹니다.

### 좋은 요구사항의 특성

ISO/IEC/IEEE 29148:2018은 요구공학 과정과 산출물에 관한 국제 표준입니다. 표준 원문은 유료라 이번에 직접 보지 못했고, 아래 아홉 특성은 표준을 인용한 2024년 arXiv 논문(2차 자료)에서 옮겼어요. 표준 목차에서는 개별 요구가 갖출 특성, 요구 집합이 갖출 특성, 요구를 쓰는 언어의 기준을 서로 다른 절에서 다룬다고 합니다.

| 특성 | 요지 | 이 가이드에서 이어지는 점검 |
| --- | --- | --- |
| Appropriate | 추상화 수준이 알맞고 구현 세부가 없음 | 개념화 원칙(2장) |
| Complete | 이해에 필요한 정보가 다 있음 | 원장의 q가 남아 있지 않은가 |
| Conforming | 승인된 틀을 따름 | EARS 패턴을 따르는가 |
| Correct | 필요를 바르게 나타냄 | 근거 수준이 확인인가 |
| Feasible | 제약 안에서 실현 가능 | 보장 위치표에 자리가 있는가 |
| Necessary | 빼면 결함이 생기는 것 | 적절성(10장) |
| Singular | 한 가지만 말함 | 원장 한 줄에 하나("그리고" 검사) |
| Unambiguous | 해석이 하나뿐 | 용어(T 칸) |
| Verifiable | 증명하거나 잴 수 있음 | 반례 시험, 품질 겹의 측정 방법 |

SWEBOK을 바탕으로 한 강의 사이트(역시 2차 자료)는 조동사마다 무게가 다르다는 것도 정리합니다. `shall`은 지켜야 하는 요구, `will`은 사실이나 목적의 진술, `should`는 바람직한 목표, `may`는 허용이에요. 문장 틀로는 [조건] [주어] [동작] [대상] [제약]을 듭니다. 이 가이드는 우리말로 옮길 때 `shall`을 "해야 한다", `should`를 "하는 것이 좋다", `may`를 "해도 된다"로 씁니다. 원장에 옮길 때 `should`로 적힌 문장은 R이 아니라 **바람**이라서, 근거 수준과 상관없이 "확인 필요"를 붙여요. 꼭 지켜야 하는지 물어야 하니까요.

### EARS: 다섯 패턴

EARS(Easy Approach to Requirements Syntax)는 Alistair Mavin 등이 Rolls-Royce에서 항공기 엔진 제어 시스템의 규정을 분석하다 만들어 2009년 IEEE 요구공학 학회(RE'09)에서 처음 발표한 문장 틀입니다. 일반 구조는 "While <사전 상태>, when <트리거>, the <시스템> shall <반응>"이고 절의 순서가 고정되어 있어요. Mavin의 공식 사이트는 패턴을 여섯으로 나열하고 위키백과는 기본 다섯에 조합형을 더한 것으로 설명하는데, 같은 내용을 다르게 센 것으로 보입니다.

| 패턴 | 키워드 | 틀 |
| --- | --- | --- |
| Ubiquitous | (없음) | 시스템은 ~해야 한다 |
| Event-driven | When | ~하면, 시스템은 ~해야 한다 |
| State-driven | While | ~인 동안, 시스템은 ~해야 한다 |
| Unwanted behaviour | If ... then | 만약 ~하면, 그때 시스템은 ~해야 한다 |
| Optional feature | Where | ~가 있는 경우, 시스템은 ~해야 한다 |
| Complex | 조합 | ~인 동안, ~하면, 시스템은 ~해야 한다 |

### 패턴마다 가는 곳

EARS 패턴은 이 가이드의 산출물과 놀랄 만큼 잘 맞습니다. 패턴의 키워드가 곧 "언제 참이어야 하는가"를 말해 주기 때문이에요. 아래 대응은 이 가이드의 정리입니다.

| 패턴 | 원장 칸 | 산출물 |
| --- | --- | --- |
| Ubiquitous | R | 개념 스키마의 제약, 계약의 불변식 inv |
| Event-driven (When) | C, R | 연산의 사후조건 post, 이벤트 계약의 발행 조건 |
| State-driven (While) | R | 상태에 따라 달라지는 제약, 업무 사전조건 pre |
| Unwanted (If-then) | R | 실패표의 한 줄(실패·응답·상태 변화·다시 시도) |
| Optional (Where) | F, V | 선택 사실 유형(필수 아님), 외부 스키마의 선택 열, 계약의 선택 필드 |
| Complex | 위의 조합 | 상태 조건이 붙은 사후조건 등 |

Unwanted 패턴이 특히 반가운 패턴이에요. 11장의 실패표는 줄마다 "어떤 조건을 어겼는가, 무엇을 돌려주는가"를 적었는데, If-then 문장은 그 두 칸을 이미 채워서 줍니다. 상태 변화와 다시 시도 칸만 물어서 채우면 돼요.

### 「틈」의 요구사항 명세

「틈」의 요구사항 명세에서 일부를 EARS 꼴로 옮겨 왔다고 합시다.

```text
REQ-01 (Ubiquitous)  예약 시스템은 같은 회의실의 확정 예약 구간이 서로 겹치지 않게 유지해야 한다.
REQ-02 (When)        회원이 예약을 요청하면, 예약 시스템은 겹치는 확정 예약이 없을 때
                   확정 예약을 만들고 예약번호를 돌려줘야 한다.
REQ-03 (When)        예약이 확정되면, 예약 시스템은 1분 안에 회계 시스템에 확정 이벤트를 보내야 한다.
REQ-04 (While)       회원이 정지 상태인 동안, 예약 시스템은 그 회원의 새 예약 요청을 거절해야 한다.
REQ-05 (While)       그달 청구가 마감된 동안, 예약 시스템은 그달 예약의 상태 변경을 거절해야 한다.
REQ-06 (If-then)     만약 요청한 시각이 30분 경계가 아니면, 그때 예약 시스템은 요청을 거절하고
                   invalid_slot 을 돌려줘야 한다.
REQ-07 (If-then)     만약 요청한 구간이 다른 확정 예약과 겹치면, 그때 예약 시스템은 요청을 거절하고
                   slot_taken 을 돌려줘야 한다.
REQ-08 (Where)       회의실에 화상 회의 장비가 있는 경우, 예약 시스템은 예약할 때 장비 사용 여부를
                   고르게 해야 한다.
REQ-09 (should)      예약 시스템은 예약 요청에 빠르게 응답하는 것이 좋다.
```

`REQ-` 번호는 명세 원문의 번호입니다. 원장의 출처 칸에는 이 번호를 그대로 써요.

옮기면 이렇게 됩니다.

| 요구 | 원장 | 산출물 |
| --- | --- | --- |
| REQ-01 | r2 | R3, O1의 inv1 |
| REQ-02 | c1, r2 | O1의 post1 |
| REQ-03 | r10 | O1의 post2, E1의 발행 조건과 품질 겹(1분) |
| REQ-04 | r13 | O1의 pre1, 실패표 `403 member_inactive` |
| REQ-05 | r12 | O2·노쇼 표시의 pre(마감 안 된 달), 실패표 줄 하나 더 |
| REQ-06 | r1 | O1의 pre2, 실패표 `422 invalid_slot` |
| REQ-07 | r2 | 실패표 `409 slot_taken` |
| REQ-08 | f13, v8, q11 | 선택 사실 유형, V의 선택 열, O1의 선택 필드 |
| REQ-09 | q12 | 잴 수 없으므로 원장에는 질문으로 |

REQ-05는 18장의 이벤트 스토밍에서 "중요 이벤트"로 나왔던 월 마감 규칙과 같은 내용이에요. 형식이 달라도 같은 규칙이 나오면 원장의 출처 칸에 두 출처를 함께 적어 둡니다. 13장의 추적표에서 한 줄로 이어 붙이기 쉬워져요.

REQ-08은 Where 패턴입니다. 장비가 **있는** 회의실에만 해당하므로, 개념 스키마에는 필수가 아닌 사실 유형이 두 개 생겨요.

```text
[사실] F14 회의실 은 화상 장비 를 가진다          (필수 아님. 장비가 없으면 기록 없음)
[사실] F15 예약 은 화상 장비 사용 여부 를 가진다   (필수 아님)
[제약] R14 F15 를 가진 예약의 회의실은 F14 를 가진다    (집합 비교: 부분집합)
```

R14는 8장 6단계의 집합 비교 제약이에요. 장비 없는 방에서 장비 사용을 고를 수는 없다는 뜻입니다. REQ-08 문장에는 R14가 직접 적혀 있지 않았지만, Where 절의 조건("장비가 있는 경우")을 거꾸로 읽으면 나와요. 계약 O1에서는 `videoConference` 같은 선택 필드가 되고, 장비 없는 방에 `true`를 보내면 실패표 줄이 하나 더 생깁니다.

REQ-09는 29148의 특성으로 보면 Verifiable(잴 수 있음)이 아닙니다. "빠르게"가 얼마인지 없으니까요. 또 `should`라서 꼭 지켜야 하는지도 모릅니다. 원장에는 R로 적지 않고 q로 적어 "몇 초 안에, 몇 퍼센트의 요청이, 무엇으로 재나요?"를 물어요. 답이 오면 11장 품질 겹의 표(요청의 95%가 0.5초 이내, 게이트웨이 기록으로 측정) 같은 꼴로 바꿉니다.

### 이 형식이 빼먹기 쉬운 것

| 빠지기 쉬운 것 | 이유 | 채우는 질문 |
| --- | --- | --- |
| 데이터의 구조 | 문장은 반응을 말하고 데이터 모양은 말하지 않음 | "예약번호를 돌려줄 때 함께 무엇을 돌려주나요?" |
| 문장 사이의 공유 개념 | 문장마다 따로 씀 | "REQ-04의 '정지 상태'와 다른 곳의 '휴면'은 같나요?" |
| 상태 변화 없음 | If-then은 거절만 말함 | "거절할 때 아무것도 바뀌지 않나요? 시도는 기록하나요?" |
| 경계값 | 수치는 있지만 경계 포함 여부가 없음 | "정확히 30분이면? 정확히 1분이면?" |
| 왜 | 요구는 이유를 적지 않음 | "이 규칙은 누구의 어떤 문제를 막나요?" |

### 헷갈리기 쉬운 곳

1. When과 While을 섞어 읽으면 규칙의 종류가 바뀝니다. When은 사건이 일어나는 **순간**의 반응이고(사후조건), While은 상태가 이어지는 **동안** 늘 참이어야 하는 것이에요(상태 의존 제약). REQ-04를 "회원이 정지되면 예약을 거절한다"로 바꿔 쓰면, 정지되는 순간 한 번만 거절하는 것처럼 읽힐 수 있습니다.
2. If-then의 "거절"은 상태 변화 없음을 약속하지 않습니다. 거절하면서도 시도 기록이나 경고 집계를 남길 수 있어요. 실패표의 상태 변화 칸은 따로 물어 채웁니다.
3. 요구사항 명세가 승인 문서라도 원장의 근거 수준을 무조건 확인으로 올리지는 않습니다. `should` 문장은 바람이고, 숫자가 없는 품질 문장은 잴 수 없어요. 승인된 것은 문서이고, 문장 하나하나의 뜻이 확정된 것은 아닙니다.

### 잠깐 확인

REQ-03 "예약이 확정되면, 1분 안에 회계 시스템에 확정 이벤트를 보내야 한다"는 계약의 다섯 겹 가운데 어디에 들어가나요?

두 겹에 나뉘어 들어갑니다. "확정되면 보낸다"는 행위 겹(E1의 발행 조건, O1의 post2)이고, "1분 안에"는 품질 겹(신선도)이에요. 품질 겹에는 측정 방법(커밋 시각과 발행 시각의 차)과 달성 기준(예: 그달 이벤트의 99%)을 함께 적어야 약속이 됩니다. REQ-03에는 측정 방법이 없으므로 원장에 q를 하나 남겨요.

### 스스로 점검하기

1. 다음 문장을 EARS 패턴 하나로 고쳐 쓰고, 고친 문장이 29148의 어느 특성을 새로 갖추었는지 적어 보세요. "시스템은 늦은 취소를 적절히 처리해야 한다."
2. REQ-05(마감된 달의 상태 변경 거절)를 실패표의 한 줄로 쓰고, 마감 뒤 들어온 노쇼 표시를 다음 달 조정으로 넘긴다는 답을 받았을 때 바뀌는 것을 적어 보세요.

#### 풀이

1. 예: "회원이 시작 1시간 전보다 늦게 예약을 취소하면, 예약 시스템은 그 예약을 사용 시간에 포함해야 한다."(When 패턴) "적절히"를 구체적인 반응으로 바꿔 Unambiguous(해석이 하나)와 Verifiable(시험 가능)을 갖추었습니다. 다만 "1시간 전보다 늦게"의 경계(정확히 1시간 전 취소가 무료인지, 17장의 q9)가 남아 있으므로 완전히 Unambiguous하려면 경계를 함께 적어야 합니다.
2. `REQ-05 위반(마감된 달의 예약) · 409 month_closed · 상태 변화 없음 · 소용없음(조정 요청으로)`. 다음 달 조정으로 넘긴다는 답이 오면, 노쇼 표시 연산은 거절 대신 "조정 기록"이라는 새 사실(마감된 달의 예약에 대한 사후 조정, 반영 월)을 만들고 성공해야 합니다. 그러면 실패표 줄은 노쇼 표시에서 빠지고, 개념 스키마에 `조정 은 예약 과 반영 월 을 가진다` 같은 사실 유형이, 청구 파생 규칙에 조정분이 더해집니다.
