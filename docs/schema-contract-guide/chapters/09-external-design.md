## 9장 외부 스키마 설계와 갱신 의미

이 장을 마치면 이용자 목록에서 출발해 외부 스키마를 다섯 항목으로 설계하고, 각 열을 개념 스키마에 이어 붙일 수 있어요. 쓰기를 받을지, 받는다면 무엇으로 번역할지 정하는 **갱신 의미** 결정표와, 외부 스키마에 숨어 있는 **시점** 문제도 다룹니다.

### 절차 한눈에

3장에서 외부 스키마가 무엇인지 정의했으니, 여기서는 만드는 순서를 정합니다.

```text
1. 이용자 목록      역할 × 목적
2. 보기 요구 모으기  원장의 V 칸
3. 질의 목록        조건 · 순서 · 묶음 · 얼마나 자주
4. 다섯 항목 쓰기    이용자 · 내용 · 모양 · 파생 규칙 · 갱신 의미
5. 열마다 ← 달기    개념 스키마의 어느 사실·파생에서 오는가
6. 갱신 의미 정하기  읽기 전용 / 쓰기 받음 / 명령으로 분리
7. 가림과 시점      누구에게 무엇을 가리는가, 언제 기준인가
```

### 1~3단계: 이용자, 보기 요구, 질의

외부 스키마는 화면마다 하나가 아니라 **이용자와 목적의 짝**마다 하나입니다. 같은 사람이라도 목적이 다르면 보는 것이 달라요. 「틈」의 이용자 목록은 이렇습니다.

| 이용자 | 목적 | 원장 줄 | 외부 스키마 |
| --- | --- | --- | --- |
| 회원 | 내 예약을 확인·관리 | v3(새로 추가) | V1 내 예약 |
| 회원 | 빈 시간을 찾아 예약 | v4(새로 추가) | V4 회의실 현황 |
| 안내 데스크 | 손님을 방으로 안내 | v1 | V2 오늘 일정표 |
| 청구 담당자 | 월말 청구 | (원장에 없음 → 추가) | V3 월 청구 명세 |
| 회계 시스템 | 청구 처리 | v2 | E1 예약 확정 이벤트 |

7장의 원장에는 v1·v2만 있었어요. 이용자 목록을 만들다 보니 회원 쪽 보기 요구가 원장에 빠져 있었다는 것을 알게 됐습니다. 콘셉트 메모가 회원 앱 화면을 따로 말하지 않았기 때문이에요. 이렇게 이용자 목록은 원장의 빈칸을 찾는 도구이기도 합니다. 찾은 줄은 원장에 더하고 근거 수준을 "진술 필요"로 둡니다.

다음으로 외부 스키마마다 질의를 적습니다. 질의는 조건·순서·묶음·빈도로 적어요. 빈도는 12장 작업 부하 표로 그대로 넘어갑니다.

```text
V1 내 예약
  Q-V1-a  내 다가오는 확정 예약, 시작순                 하루 300회(가정)
  Q-V1-b  내 지난 예약, 최근순, 20건씩                   하루 30회(가정)
V4 회의실 현황
  Q-V4-a  특정 날짜의 회의실별 확정 예약 구간 (예약자 가림) 하루 200회(가정)
```

### 4~5단계: 다섯 항목과 화살표

V1 "내 예약"을 다섯 항목으로 써 보겠습니다. 3장의 V2와 같은 표기예요.

```text
[외부] V1 내 예약                       이용자: 회원 본인
  행      그 회원의 예약 하나
  열      예약번호 ← 예약(참조) · 회의실 ← F5 · 시작 ← F6 · 끝 ← F6 · 상태 ← F7
          · 취소 가능 여부 ← F7 + F6 + 지금 시각   (확정이고 시작 전이면 가능)
          · 무료로 취소 가능 여부 ← F6 + 지금 시각 (시작 1시간 전까지면 가능, R5)
  고르기   F4 = 접속한 회원
  순서     다가오는 것은 시작순, 지난 것은 최근순
  가림     없음 (본인 예약만 보이므로)
  갱신     직접 쓰기 없음. 취소는 명령 "취소하기"(O2)로
```

화살표를 다는 5단계에서 두 가지를 발견할 수 있습니다. 하나는 "취소 가능 여부"처럼 **지금 시각**에 기대는 열이에요. 지금 시각은 개념 스키마의 사실이 아니라 질의할 때 주어지는 값입니다. 외부 스키마는 개념 사실과 질의 시점의 맥락을 함께 써서 값을 만들 수 있고, 그 의존을 화살표에 적어 둬요.

다른 하나는 화살표를 달 수 없는 열입니다. 회원이 앱에서 "이 예약에 메모 남기기"를 원한다는 요구가 있었다면, 메모 열에는 화살표를 달 곳이 없어요. 개념 스키마에 "예약은 메모를 가진다"가 없으니까요. 이럴 때 외부 스키마에서 메모를 빼거나, 원장에 f를 더해 개념 스키마로 돌아갑니다. 어느 쪽이든 외부 스키마 혼자 새 사실을 만들어 내지는 않아요.

외부 스키마를 JSON으로 내보낸다면 모양 항목을 JSON Schema(2020-12)로 적을 수 있습니다. 모양의 일부만 보입니다.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.invalid/tum/v1-my-booking.json",
  "type": "object",
  "required": ["bookingId", "roomCode", "startAt", "endAt", "status", "cancellable"],
  "properties": {
    "bookingId":   { "type": "string", "pattern": "^B[0-9]+$" },
    "roomCode":    { "type": "string" },
    "startAt":     { "type": "string", "format": "date-time" },
    "endAt":       { "type": "string", "format": "date-time",
                     "description": "이 시각을 포함하지 않음 ([startAt, endAt))" },
    "status":      { "enum": ["confirmed", "cancelled", "used", "no_show"] },
    "cancellable": { "type": "boolean" },
    "freeCancellable": { "type": "boolean" }
  }
}
```

`endAt`의 `description`에 구간의 뜻을 적었습니다. JSON Schema는 이 값이 포함인지 불포함인지 검증하지 못해요. 그래도 뜻을 적는 자리를 스키마 안에 두면, 5장 계약의 의미 겹이 모양 옆에 붙어 다닙니다. `additionalProperties`를 적지 않았으니 이 스키마는 모르는 필드를 허용하는 열린 모델이에요. 5장에서 본 대로 이 선택이 나중의 호환성 판정을 좌우합니다.

### 6단계: 갱신 의미 정하기

3장의 뷰 갱신 문제를 설계 규칙으로 바꾸면 다음 결정표가 됩니다. 이 표는 3장의 예와 PostgreSQL의 자동 갱신 규칙을 바탕으로 이 가이드가 정리한 권고예요.

| 외부 스키마의 꼴 | 쓰기를 받을 때 생기는 일 | 권고 |
| --- | --- | --- |
| 고르기만 함 (V1처럼) | 보완 뷰가 분명해 번역이 하나로 정해짐 | 받을 수 있음. 보이지 않게 되는 변경은 막음(`WITH CHECK OPTION`과 같은 효과) |
| 뽑기로 필수 사실이 빠짐 (V4처럼) | 빠진 값을 정할 수 없음 | 받지 않음. 또는 빠진 값을 맥락(접속한 회원)으로 채운다는 규칙을 명시 |
| 여러 사실을 이음 (V5처럼) | 고치지 않은 행이 함께 바뀌는 부수 효과 | 받지 않음. 바꾸려는 사실마다 명령을 둠 |
| 계산 열 (초과 분) | 번역이 여럿 | 받지 않음. 조정이 필요하면 조정 사실과 명령을 둠 |
| 묶음·중첩 | 묶음 안의 변경이 어느 사실의 변경인지 모호 | 명령으로 분리 |

표를 보면 대부분 "명령으로 분리"로 끝납니다. 이 가이드는 외부 스키마를 읽기 전용으로 두고, 변경은 원장의 C 칸에서 나온 **명령**(예약하기, 취소하기)으로 받는 쪽을 기본으로 권해요. 3장에서 본 CQRS의 방향과 같습니다. 그 대신 명령마다 11장의 계약을 씁니다.

```text
읽기   V1 내 예약          ← 파생 규칙만 있으면 됨
쓰기   O1 예약하기(...)     ← 계약: 사전·사후조건, 실패, 멱등
       O2 취소하기(...)     ← 계약
```

### 7단계: 가림과 시점

**가림**은 3장에서 봤으니 시점을 보겠습니다. 외부 스키마에는 늘 "언제 기준"이 숨어 있어요. V3 월 청구 명세의 "등급" 열을 예로 들어 봅시다.

```text
M07 김하나의 등급 이력
  11-01 ~ 11-14  일반 (무료 120분)
  11-15 ~        상주 (무료 600분)

V3 11월 청구 명세에서 M07의 무료 분은?
  (가) 월말 기준 등급 → 600분
  (나) 월초 기준 등급 → 120분
  (다) 날수로 나눔    → 120 × 14/30 + 600 × 16/30 = 56 + 320 = 376분
```

(가)·(나)·(다) 가운데 어느 것이 맞는지는 담화 세계의 규칙이에요. 외부 스키마 설계자가 정할 일이 아니라 원장의 q4(등급이 달 중간에 바뀌면?)에 대한 답으로 정해집니다. 그리고 어느 답이든 공통된 결과가 하나 있어요. 등급이 바뀐 날짜를 알아야 합니다. 그런데 지금 개념 스키마의 F2(회원은 등급에 속한다)는 **지금의** 등급만 적어요.

외부 스키마의 시점 요구가 개념 스키마를 키우는 경우입니다. 1장의 논리적 데이터 독립성은 개념이 바뀌어도 외부를 지키는 방향이었는데, 여기서는 거꾸로 외부의 요구가 개념을 바꿉니다. 둘은 모순이 아니에요. 외부 스키마는 개념 스키마에서 **파생**되므로, 파생할 원천이 없으면 원천을 늘려야 합니다.

```text
Before  F2  회원 은 등급 에 속한다                        (지금 등급 하나)
After   F2' 회원 은 [시작일, 종료일) 동안 등급 에 속했다     (이력)
        R8  한 회원의 등급 기간은 겹치지 않는다
        D4  어느 날의 등급 = 그 날을 포함하는 기간의 등급
```

외부 스키마를 설계하며 시점을 묻는 질문은 몇 가지로 정리됩니다.

| 질문 | 「틈」의 예 |
| --- | --- |
| 이 값은 지금 값인가, 그때 값인가? | 청구서의 등급은 청구 대상 월의 값인가 |
| 과거를 다시 조회하면 같은 답이 나와야 하는가? | 10월 청구서를 12월에 다시 뽑으면 같아야 하는가 |
| 언제까지의 변경이 반영되어야 하는가? | 월말 23:59 취소가 그달 청구에 들어가는가 |
| 외부 스키마를 받아 간 쪽이 그 값을 보관하는가? | 회계 시스템은 이벤트를 받아 자기 DB에 저장하는가 |

표의 두 번째 질문에 "예"라고 답한다면 V3는 단순한 뷰가 아니라 **발행된 문서**입니다. 회원 이름이 나중에 바뀌어도 이미 보낸 10월 청구서는 바뀌면 안 되니까요. 이럴 때는 청구서를 낼 때 값을 따로 기록해 두어야 합니다. 그 기록은 개념 스키마에 새 사실(청구서는 발행 시점 회원 이름을 담는다)로 들어가요.

### 헷갈리기 쉬운 곳

1. 화면 하나 = 외부 스키마 하나가 아닙니다. 회원 앱의 "홈" 화면이 다가오는 예약 세 건과 이번 달 남은 무료 시간을 함께 보여 준다면, 그 화면은 V1과 V3의 일부를 함께 씁니다. 외부 스키마는 이용자와 목적으로 묶고, 화면은 그것을 조합해 보여 줘요.
2. 외부 스키마마다 개념 스키마를 고치는 것은 위험합니다. 시점 문제처럼 원천이 없을 때만 개념으로 돌아가고, 모양만 다른 요구(정렬, 이름, 묶음)는 외부 스키마 안에서 해결합니다.
3. 읽기 전용이라고 계약이 필요 없는 것은 아닙니다. 다른 팀이 읽는 외부 스키마라면 구조·의미·품질·진화 겹이 모두 필요해요. 빠지는 것은 행위 겹의 쓰기 부분뿐입니다.

### 잠깐 확인

V4 회의실 현황에서 회원이 빈 칸을 눌러 바로 예약하게 하고 싶습니다. V4가 쓰기를 받아야 할까요?

받지 않아도 됩니다. 화면에서 빈 칸을 누르는 것은 예약하기 명령(O1)을 회의실·시작·끝을 채운 채 부르는 것이에요. V4는 읽기 전용으로 두고, 화면이 V4로 빈 시간을 보여 준 뒤 O1을 부릅니다. 그 사이에 다른 회원이 같은 시간을 잡으면 O1이 409로 실패하는데, 이 경우를 O1의 계약이 이미 적고 있어요.

### 스스로 점검하기

1. 회원 앱 "홈" 화면(다가오는 예약 세 건, 이번 달 남은 무료 시간)에 필요한 외부 스키마 요소를 V1·V3에서 골라 적고, 남은 무료 시간 열의 화살표를 적어 보세요.
2. 매니저가 데스크 일정표(V2)에서 손님 이름을 직접 고칠 수 있게 해 달라고 합니다. 6장 점검 문제의 `booking_guest`를 쓴다고 할 때, V2가 쓰기를 받게 할지 명령으로 분리할지 결정표로 판단해 보세요.
3. q4의 답이 "(가) 월말 기준 등급"으로 정해졌다면, F2'(등급 이력)는 여전히 필요할까요?

#### 풀이

1. V1에서 다가오는 확정 예약 세 건(예약번호·회의실·시작·끝), V3에서 무료 분과 사용 분을 씁니다. `남은 무료 시간 ← F8(등급의 무료 분) - D1(이번 달 사용 분)`이고, 등급은 F2(또는 이력이 있다면 D4의 오늘 등급)에서 옵니다. 음수가 되면 0으로 보이게 할지도 모양 항목에 적습니다.
2. V2는 예약·회원·회의실을 이은 외부 스키마라서, 손님 이름 칸을 고치는 쓰기를 받으면 어느 사실을 바꾸는지 따져야 합니다. 손님 이름이 예약에 딸린 사실(booking_guest)이라면 번역은 하나로 정해지지만, V2의 다른 열(예약자 이름)까지 고칠 수 있게 열어 두면 부수 효과가 생깁니다. 결정표에 따라 V2는 읽기 전용으로 두고 "손님 이름 고치기" 명령을 따로 두는 편이 안전합니다.
3. 필요합니다. 월말 기준이라도 12월에 10월 청구서를 다시 뽑으려면 10월 말의 등급을 알아야 하고, 지금 등급만 있으면 그 값을 잃습니다. 과거 청구서를 다시 뽑을 일이 없다고 확인되면, 청구서를 낼 때 등급을 함께 기록하는 방식으로 이력 없이 갈 수도 있습니다. 어느 쪽이든 원장에 결정과 근거를 남깁니다.
