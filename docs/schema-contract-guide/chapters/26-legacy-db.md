## 26장 오래된 DB 역공학

이 장을 마치면 설명서 없는 오래된 DB에서 선언된 구조와 **선언되지 않은 구조**를 찾아 개념 스키마로 되살릴 수 있어요. 질의 기록에서 그 DB를 읽는 바깥 프로그램들의 **실제 계약**을 복원하고, 구조를 바꾸는 동안 그들을 지키는 방법도 다룹니다.

### 상황: 문서 없는 DB와 바깥 이용자

「틈」은 지금의 예약 시스템 전에 패키지 예약 프로그램을 썼다고 해 봅시다. 프로그램을 만든 회사는 문을 닫았고 문서는 없어요. 남은 것은 DB와, 회계팀이 매달 그 DB에서 직접 사용 내역을 뽑던 질의 하나입니다.

```sql
CREATE TABLE MEM (
  MEM_CD  CHAR(4) PRIMARY KEY,     -- 예: N001, S002
  NM      VARCHAR(20),
  TEL     VARCHAR(20),
  DEL_YN  CHAR(1)
);
CREATE TABLE RSV (
  RSV_NO  INTEGER PRIMARY KEY,
  MEM_CD  CHAR(4),
  ROOM    CHAR(2),                 -- 01, 02, 03
  YMD     CHAR(8),                 -- 20250304
  FR      CHAR(4),                 -- 1000
  TO_     CHAR(4),                 -- 1130
  ST      CHAR(1),
  ETC     VARCHAR(100)
);
CREATE TABLE CD (GRP VARCHAR(10), CD VARCHAR(5), NM VARCHAR(20));
-- 외래 키 선언 없음
```

```text
[회계팀 월말 질의, 매달 1회]
SELECT MEM_CD, YMD, FR, TO_ FROM RSV WHERE ST IN ('3','4') AND YMD LIKE ? || '%'
```

4장의 "헷갈리기 쉬운 곳" 3번에서 경고한 상황이 이것이에요. 바깥 프로그램이 내부 표를 직접 읽으면, 그 순간 내부 표의 열 이름과 값이 그 프로그램의 외부 스키마가 되어 버립니다.

### 두 단계: 구조를 꺼내고, 뜻을 되살린다

Hainaut와 동료들은 1993년 ER 학회 논문에서 데이터베이스 역공학(database reverse engineering, DBRE)을 두 단계로 나눴다고 알려져 있습니다. 먼저 특정 DBMS에 묶인 데이터 구조를 **추출**하고, 그다음 스키마 변환으로 그 구조의 뜻을 되살리는 **개념화**를 한다는 거예요. 1996년 논문은 데이터 구조와 무결성 제약이 선언되지 않은 채 절차 코드나 화면 동작으로 구현되는 일이 많다고 지적합니다. 그런 암묵 구조를 찾는 기법, 특히 가장 흔한 암묵 구조인 외래 키를 찾는 기법을 다뤘다고 해요. Chiang·Barron·Storey(1994, *Data & Knowledge Engineering* 12권 2호)는 스키마 분석과 데이터 인스턴스 분석을 함께 써서 EER(확장 ER) 모델을 뽑는 방법을 냈다고 알려져 있습니다. 세 편 모두 이번 조사에서는 서지와 요약 수준으로만 확인했어요.

이 장은 두 단계를 이렇게 나눠 씁니다.

```text
1. 추출
   1a. 선언된 구조 읽기       DDL: 표, 열, 타입, 기본 키, (있다면) 외래 키·검사 제약
   1b. 암묵 구조 찾기         이름 규칙 · 자료 분석(24장) · 질의와 코드 분석 · 화면과 보고서
2. 개념화
   2a. 최적화·편의 구조 걷어 내기   반복 열, 코드에 박은 뜻, 여러 용도의 칸
   2b. 뜻 되살리기                 담당자 진술로 t·r 확인 → 개념 스키마
   2c. 바깥 이용자의 실제 계약 복원  질의 기록 → 지킬 것 목록
```

### 암묵 구조의 종류와 찾는 법

1b에서 찾을 암묵 구조를 종류별로 정리했습니다. 「틈」의 옛 DB와, 실습 P14 철물점 DB에서 실제로 나오는 것들이에요.

| 암묵 구조 | 「틈」 옛 DB | 찾는 법 |
| --- | --- | --- |
| 선언 안 된 외래 키 | `RSV.MEM_CD` → `MEM.MEM_CD` | 이름이 같은 열을 찾고, 포함 종속을 검사(24장) |
| 코드 표 하나에 여러 묶음 | `CD`에 예약 상태(`GRP='RSV_ST'`)와 회원 구분이 함께 | `SELECT DISTINCT GRP FROM CD`로 묶음을 세고, 묶음마다 값 유형 하나 |
| 코드값의 뜻 | `ST`의 `1`~`4` | 코드 표와 질의를 맞춰 봄. 회계 질의가 `3`·`4`를 고름 |
| 코드에 박은 뜻 | `MEM_CD` 첫 글자 N·S가 일반·상주 | 첫 글자별로 다른 열(구분)과 맞는지 셈. P14에서는 품목 코드 앞 두 글자 |
| 여러 용도의 칸 | `ETC`에 손님 이름, 취소 사유, "BLOCK" | 값의 패턴을 셈(`LIKE '손님:%'` 등). P14에서는 `MEMO` |
| 논리 삭제 | `DEL_YN = 'Y'`인 회원 | 이 열로 거르는 질의가 있는지 질의 기록에서 확인 |
| 형식에 숨은 뜻 | `YMD` 여덟 글자, `FR`·`TO_` 네 글자 | 값이 모두 그 꼴인지 셈. 시간대 없음 → 한국 시간으로 추정(관찰) |
| 반복 열 | (없음) | P14의 `PRICE1`·`PRICE2`·`PRICE3` |

암묵 외래 키를 찾는 질의는 단순합니다.

```sql
-- RSV.MEM_CD 가운데 MEM 에 없는 값: 0 이면 외래 키 후보, 몇 개면 21장의 둘째 갈래
SELECT DISTINCT MEM_CD FROM RSV
WHERE MEM_CD IS NOT NULL AND MEM_CD NOT IN (SELECT MEM_CD FROM MEM);
```

21장의 원칙은 여기서도 그대로입니다. 고아 값이 없다는 것은 관찰이고, 고아 값이 몇 개 있다는 것은 질문이에요. P14에서는 재고 표에만 있는 품목 하나와 입출고 표에만 있는 거래처 하나가 나옵니다.

### 코드에 박은 뜻이 위험한 이유

암묵 구조 가운데 가장 조심할 것은 **식별자에 박은 뜻**입니다. 「틈」의 옛 DB는 회원 코드의 첫 글자로 등급을 나타냈어요. N001은 일반 회원, S002는 상주 회원입니다.

```text
2025-03  김하나 = N001 (일반)
2026-11  김하나가 상주로 바뀜 → 코드를 S00? 로 바꿔야 하나?

바꾸면   RSV 의 옛 예약 MEM_CD 를 모두 고쳐야 함. 회계팀 자료의 N001 과 이어지지 않음
안 바꾸면 "첫 글자 = 등급" 이 더는 참이 아님. 첫 글자로 등급을 읽던 질의가 틀린 답을 냄
```

2장에서 참조 방식은 시간이 지나도 바뀌지 않아야 한다고 했지요. 바뀔 수 있는 값(등급)을 참조 방식(회원 코드)에 넣으면, 그 값이 바뀌는 날 둘 중 하나를 포기해야 합니다. 개념화(2a) 단계에서는 이 뜻을 코드에서 떼어 별도 사실 유형(F2 회원은 등급에 속한다)으로 옮기고, 코드는 그냥 이름표로 둡니다. 옛 코드의 첫 글자가 지금 등급과 맞는지는 자료로 셀 수 있는데, P14에서 품목 코드 앞 두 글자와 대분류가 여덟 품목 가운데 일곱에서만 맞는 것을 확인합니다.

### 질의 기록에서 실제 계약 복원하기

2c는 이 장에서 가장 중요한 단계입니다. 5장의 Hyrum 법칙을 떠올려 보세요. 이용자가 많으면, 약속했든 안 했든 관찰 가능한 모든 동작에 누군가 기댑니다. 오래된 DB는 계약을 선언한 적이 없으니, 바깥 프로그램이 기대는 것이 곧 **실제 계약**의 전부예요. 그것을 찾는 가장 좋은 자료가 질의 기록입니다.

회계팀의 질의 한 줄을 실제 계약으로 풀어 보겠습니다.

```text
SELECT MEM_CD, YMD, FR, TO_ FROM RSV WHERE ST IN ('3','4') AND YMD LIKE ? || '%'

지켜야 할 것
  표와 열 이름       RSV, MEM_CD, YMD, FR, TO_, ST    (이름을 바꾸면 질의가 실패)
  값의 꼴           YMD 는 'YYYYMMDD' (월 앞부분 LIKE 로 거름) · FR·TO_ 는 'HHMM'
  코드값의 뜻        ST '3' = 이용, '4' = 노쇼         (코드를 바꾸면 조용히 틀린 답)
  고르는 범위        ST 가 3·4 인 행만 = 청구 대상
```

마지막 줄에서 흥미로운 사실이 하나 나옵니다. 회계 질의는 상태가 이용(3)과 노쇼(4)인 예약만 고르고, 취소(2)는 고르지 않아요. 그런데 7장의 콘셉트 메모는 "시작 1시간 전까지는 그냥 취소할 수 있는데, 그 뒤에 취소하면 쓴 걸로 쳐요"(r4)라고 했습니다. 질의 기록이 보여 주는 실제 청구 방식과 매니저가 말한 규칙이 다릅니다. 둘 가운데 하나가 틀렸거나, 늦은 취소를 이용(3)으로 바꿔 적는 관행이 있었을 수 있어요.

```text
q15 늦은 취소는 옛 DB 에서 ST 를 무엇으로 적었나요? 취소(2)였다면 회계는 늦은 취소를 청구하지 않은 것
    → 매니저 진술(r4)과 실제 청구가 다름. 어느 쪽이 업무 규칙인가요?
```

질의 기록은 사람이 말한 규칙이 시스템에서 실제로 어떻게 처리되었는지를 보여 주는 **관찰**입니다. 21장의 말로는, 진술(r4)을 반증할 수도 있는 자료예요. 실제 계약을 복원하다가 업무 규칙의 모순을 찾는 일은 드물지 않습니다.

### 바꾸는 동안 바깥 이용자를 지키기

이제 옛 DB를 새 구조로 옮긴다고 합시다. 회계 프로그램은 다른 팀의 것이라 당장 고칠 수 없어요. 1장에서 본 데이터 독립성을 이번에는 **거꾸로** 씁니다. 1장에서는 바깥을 그대로 둔 채 안쪽을 바꾸려고 뷰를 썼지요. 여기서도 같아요. 새 구조를 만들고, 옛 표와 **같은 이름·같은 열·같은 값의 꼴**을 내주는 뷰를 둡니다.

```sql
-- 새 구조(12장의 booking)에서 옛 RSV 모양을 내주는 호환 뷰
CREATE VIEW RSV AS
SELECT b.legacy_no                              AS RSV_NO,
       m.legacy_code                            AS MEM_CD,
       r.legacy_room                            AS ROOM,
       to_char(b.starts_at, 'YYYYMMDD')         AS YMD,
       to_char(b.starts_at, 'HH24MI')           AS FR,
       to_char(b.ends_at,   'HH24MI')           AS TO_,
       CASE b.status WHEN 'confirmed' THEN '1' WHEN 'cancelled' THEN '2'
                     WHEN 'used' THEN '3' ELSE '4' END AS ST,
       NULL                                     AS ETC
FROM booking b JOIN member m USING (member_id) JOIN room r USING (room_code);
```

옛 번호를 이어 쓰려고, 옮길 때 12장의 `booking`·`member`·`room` 표에 옛 번호 열(`legacy_no`·`legacy_code`·`legacy_room`)을 더했다고 가정했어요. 이 뷰는 PostgreSQL 문법이고 이 장에서는 실행하지 않았습니다. 같은 방법을 실습 P14에서 SQLite로 실제로 실행해, 회계 프로그램의 질의가 열 개 날짜 모두 옛 DB와 같은 결과를 내는 것을 확인했어요(`verification/part4-ddl-result.json`).

호환 뷰는 끝이 아니라 시작입니다. 11장의 진화 절차대로 이어 가요.

```text
1. 호환 뷰로 옮김          회계 프로그램은 바뀐 것을 모름
2. 계약을 선언             지금까지의 실제 계약을 문서로: 표·열·꼴·코드값의 뜻
3. 새 계약을 제안          E3 이용 확정 이벤트(11장) 같은 정식 경계
4. 병행                   호환 뷰와 새 이벤트를 함께 제공
5. 사용 측정과 제거         회계 프로그램이 새 경계로 옮긴 것을 확인한 뒤 호환 뷰 제거
```

호환 뷰를 둔다는 결정에는 비용이 따릅니다. 옛 코드값(`ST`의 `1`~`4`)과 옛 꼴(`YMD`)을 새 구조가 계속 만들어 내야 하고, 옛 DB에 없던 사실(예: 등급 이력)은 뷰로 보여 줄 수 없어요. 그래서 호환 뷰는 기한을 정해 두고, 그 기한을 계약의 진화 겹에 적습니다.

### 헷갈리기 쉬운 곳

1. 역공학의 결과를 옛 DB의 복제로 만들면 안 됩니다. 옛 DB의 구조는 그때의 최적화와 편의가 섞인 내부 스키마예요. 2a 단계에서 그것을 걷어 내고 개념 스키마로 올라가야, 새 내부 스키마를 다시 고를 수 있습니다.
2. 질의 기록에 나오지 않는다고 아무도 안 쓰는 것은 아닙니다. 기록 기간이 짧으면 연말에만 실행되는 질의를 놓쳐요. 기록 기간을 원장의 출처에 적고, "1년에 한 번 쓰는 것이 있나요?"를 묻습니다.
3. 호환 뷰가 같은 열을 내준다고 같은 결과가 나오는 것은 아닙니다. 값의 꼴(앞의 0, 공백, 빈 문자열과 NULL의 차이)까지 같아야 해요. P14의 호환 뷰가 거래처가 없는 행에 `NULL`이 아니라 빈 문자열을 내주는 이유가 이것입니다. 옛 표가 빈 문자열을 썼고, 회계 프로그램이 그 값에 기댔을 수 있으니까요.

### 잠깐 확인

옛 DB의 `ETC` 칸에 "BLOCK"이라는 값이 몇 줄 있습니다. 회원 코드는 대표의 것이고, 시간대는 늘 평일 저녁이에요. 이것은 무엇일 가능성이 크고, 원장에 어떻게 적어야 할까요?

대표가 정기 회의 시간을 막아 두려고 넣은 **차단 예약**일 가능성이 큽니다. 그러나 자료만 보고 확정할 수는 없어요. 원장에 `t ETC='BLOCK': 대표의 평일 저녁 예약에만 나옴 · 근거: 관찰`과 `q 차단 예약은 청구 대상인가요? 겹침 금지를 지키나요? 회원이 아닌 운영 목적의 예약인가요?`를 적습니다. 답에 따라 개념 스키마에 "예약의 목적{회원 이용, 운영 차단}" 같은 사실 유형이 생길 수 있습니다.

### 스스로 점검하기

1. 「틈」의 옛 DB에서 `MEM.DEL_YN = 'Y'`인 회원의 예약이 `RSV`에 남아 있습니다. 회계 질의는 `DEL_YN`을 보지 않아요. 실제 계약과 개념 스키마에서 각각 무엇을 정해야 할까요?
2. 호환 뷰 `RSV`의 `ETC`를 `NULL`로 내준 것은 어떤 위험이 있나요? 질의 기록으로 무엇을 확인해야 하나요?
3. 옛 DB의 `CD` 표에서 `GRP = 'RSV_ST'`의 코드가 `1`~`5`로 다섯 개인데, `RSV.ST`에는 `1`~`4`만 나옵니다. 21장의 세 갈래로 다뤄 보세요.

#### 풀이

1. 실제 계약 쪽에서는 "탈퇴(논리 삭제)한 회원의 지난 예약도 회계 질의 결과에 나온다"가 지켜야 할 동작입니다. 회계가 탈퇴 회원의 지난 사용분도 청구해 왔다면, 호환 뷰도 그 행을 내줘야 합니다. 개념 스키마 쪽에서는 10장에서 맞춘 대로 회원을 지우지 않고 "탈퇴" 상태로 두고, 탈퇴 회원의 예약이 청구 대상인지를 확인받아 규칙으로 적습니다.
2. 회계 질의는 `ETC`를 읽지 않으므로 이 질의에는 영향이 없습니다. 하지만 다른 바깥 프로그램(예: 데스크의 오래된 출력 프로그램)이 `ETC`에서 손님 이름을 읽고 있었다면, 그 프로그램은 오류 없이 빈 값을 받게 됩니다. 질의 기록 전체에서 `ETC`를 읽는 질의가 있는지 확인하고, 있다면 새 구조의 손님 이름(F11)에서 같은 꼴("손님:" 접두어)로 만들어 내줘야 합니다.
3. 코드 5에 해당하는 행이 자료에 없다는 것은 반례가 없는 것이 아니라 **값이 쓰이지 않은 것**입니다. 코드 5의 이름(`CD.NM`)을 보고, 쓰이지 않는 상태인지(예: "대기") 앞으로 쓰일 상태인지 담당자에게 묻습니다. 쓰이지 않았다면 개념 스키마의 상태 값에 넣지 않고 기각 기록을 남기며, 새 구조로 옮긴 뒤 그 코드가 다시 나타나면 감시 질의로 잡습니다.
