# 서론

## 이 가이드로 할 수 있게 되는 것

이 가이드는 데이터 설계에서 오래 쓰여 온 세 낱말, 외부 스키마·개념 스키마·내부 스키마에 **계약**을 더한 네 가지를 정의하고, 실제 자료에서 그 넷을 설계하는 방법을 다룹니다. 다 읽고 실습까지 마치면 다음 네 가지를 할 수 있습니다.

1. 어떤 문장이나 산출물이 넷 가운데 어디에 속하는지 근거를 들어 가릴 수 있습니다. "예약은 겹치지 않는다"는 개념 스키마의 규칙이고, "응답의 `startAt` 필드는 ISO 8601 문자열이다"는 외부 표현이며, "예약 표에 회의실 번호 인덱스를 둔다"는 내부 선택이고, "필드를 지우려면 90일 전에 알린다"는 계약 조항입니다. 이런 구분을 손으로 할 수 있게 됩니다.
2. 콘셉트 문서, 시나리오, 유스케이스, 사용자 스토리, Gherkin 시나리오, 이벤트 스토밍 보드, 요구사항 문장, 종이 양식처럼 **형식이 있는 자료**에서 네 산출물을 만들 수 있습니다.
3. 메신저 대화, 손으로 만든 엑셀, 데이터 덤프, 버전이 섞인 로그, 설명서 없는 오래된 DB처럼 **형식이 없거나 거친 자료**에서도 같은 산출물을 만들되, 자료가 증명하지 못하는 것을 질문 목록으로 따로 남길 수 있습니다.
4. 만든 결과가 서로 맞물리는지 예제 데이터와 추적표로 확인할 수 있습니다.

## 네 산출물을 한 장에 놓으면

먼저 전체 지도를 보여 드리겠습니다. 낱말 뜻은 아직 몰라도 괜찮아요. 장을 하나씩 지날 때마다 이 그림으로 돌아와 지금 어디를 보고 있는지 확인하시면 됩니다.

```text
   이용자 A        이용자 B         다른 팀의 시스템
      |               |                    |
+-----------+   +-----------+     +------------------+
| 외부 스키마 |   | 외부 스키마 |     | 외부 스키마        |
|    V1     |   |    V2     |     |    V3            |
+-----------+   +-----------+     +------------------+
      |               |            [ 계약: 바꾸지 않겠다는 약속 ]
      +-------+-------+--------------------+
              |   외부-개념 사상 (파생 규칙)
              ▼
     +---------------------+
     |     개념 스키마        |   담화 세계에 관해 참이어야 하는 것
     +---------------------+
              |   개념-내부 사상 (저장 방법)
              ▼
     +---------------------+
     |     내부 스키마        |   어떤 구조로 저장하고 어떻게 찾는가
     +---------------------+
```

가운데의 개념 스키마는 "무엇이 참인가"를 적습니다. 위쪽의 외부 스키마는 이용자마다 "무엇을 어떤 모양으로 보는가"를 적고, 아래쪽 내부 스키마는 "어떻게 저장하고 찾는가"를 적습니다. 세 층을 잇는 화살표가 **사상**(mapping, 한 층에서 쓰는 표현을 다른 층 표현으로 옮기는 규칙)이에요. 이 구조는 1970년대 ANSI/X3/SPARC 연구 그룹의 보고서에서 나왔습니다.

오른쪽 위에 걸린 **계약**은 원래 세 층 구조에 없던 말이에요. 이 가이드가 넷째 산출물로 넣었습니다. 세 층 구조가 나오던 때의 이용자는 대개 같은 DBMS 안의 응용 프로그램이었습니다. 지금은 외부 스키마가 HTTP API·이벤트·데이터 파일의 모양으로 조직 밖까지 나갑니다. 밖으로 나간 외부 스키마는 제공하는 쪽 혼자서는 못 바꿉니다. 그래서 무엇을 언제까지 지키고 바꿀 때는 어떤 절차를 거치는지 적은 약속이 따로 있어야 해요. 그 약속이 계약입니다.

> 개념 스키마는 참인 것, 외부 스키마는 보이는 것, 내부 스키마는 저장된 것, 계약은 지키겠다고 한 것입니다.

## 이 가이드의 짜임

가이드는 다섯 부로 나뉩니다. 앞 부의 질문에 답해야 뒤 부의 질문이 성립하도록 순서를 잡았습니다.

| 부 | 묻는 것 | 장 |
| --- | --- | --- |
| 제1부 이론 | 넷은 각각 무엇인가 | 1~6장 |
| 제2부 설계 방법 | 무엇을 어떤 순서로 정하는가 | 7~13장 |
| 제3부 형식이 있는 씨앗 | 이 형식의 자료로는 어떻게 시작하는가 | 14~20장 |
| 제4부 거친 자료 | 형식이 없는 자료로는 어떻게 시작하는가 | 21~26장 |
| 제5부 실습 | 직접 설계해 봅니다 | 문제 15개와 풀이 |

여기서 **씨앗**은 설계를 시작할 때 처음 받은 자료예요. 콘셉트 문서일 수도, 엑셀 파일일 수도 있습니다.

제3부와 제4부를 따로 쓰지 않고 한 방법으로 묶기 위해, 이 가이드는 **추출 원장**이라는 중간 표를 씁니다. 어떤 씨앗이든 먼저 이 표의 여섯 칸(용어·사실·보기 요구·연산·규칙·미결 질문)으로 옮기고, 원장부터 뒤는 같은 절차로 설계합니다. 씨앗 형식마다 달라지는 것은 "원장으로 옮기는 규칙"뿐이에요. 원장은 7장에서 자세히 다룹니다.

```text
유스케이스 --+
엑셀 장부 ---+--▶ 추출 원장 --▶ 개념 · 외부 · 계약 · 내부
메신저 대화 --+    (형식별 규칙)    (공통 절차)
```

## 읽는 경로

처음부터 끝까지 읽으셔도 되고, 상황에 맞는 경로를 골라도 됩니다.

| 지금 상황 | 권하는 경로 |
| --- | --- |
| 이 낱말들을 처음 정리하려는 경우 | 1~6장 → 7~8장 → P01·P02 |
| 요구사항 문서를 받아 설계해야 하는 경우 | 6장 → 7~13장 → 14장 → 자기 자료 형식의 장(15~20장) → 해당 실습 |
| 엑셀이나 DB 덤프만 받은 경우 | 6장 → 7장 → 21장 → 자료 형식의 장(22~26장) → P10~P14 |
| API를 공개하거나 바꿔야 하는 경우 | 3장, 5장, 11장 → P13·P14 |

## 표기 약속

이 가이드에서 자주 쓰는 표기를 미리 정해 둡니다.

- 원장의 여섯 칸은 대문자 머리글자로 부릅니다. `T` 용어, `F` 사실, `V` 보기 요구, `C` 연산, `R` 규칙, `Q` 미결 질문이에요. 원장의 **줄**은 소문자 머리글자와 번호로 씁니다. `f3`은 원장의 셋째 사실 줄입니다. 원장은 씨앗마다 하나씩 생기므로 줄 번호는 그 원장 안에서만 뜻이 있어요. 7장에서 만드는 「틈」 콘셉트 메모의 원장을 2부 내내 이어 쓰고, 14~26장의 작은 예는 각자 다른 씨앗에서 원장을 새로 뽑습니다. 다른 장의 원장 줄을 가리킬 때는 "7장 원장의 q4"처럼 장을 붙입니다.
- 설계한 산출물의 요소는 대문자 번호로 씁니다. 개념 스키마의 사실 유형은 `F1`, 제약은 `R1`, 파생 규칙은 `D1`, 외부 스키마는 `V1`, 계약을 맺는 연산은 `O1`, 이벤트는 `E1`, 작업 부하 줄은 `W1`이에요. 계약 안의 사전조건·사후조건·불변식은 `pre1`·`post1`·`inv1`, 내부 스키마의 결정은 `IX1`(인덱스)·`PT1`(분할)·`MV1`(실체화 뷰)로 씁니다. 원장 줄 `r2`가 다듬어져 개념 스키마의 제약 `R3`이 되는 식이라, 같은 규칙이라도 원장과 산출물에서 번호가 다를 수 있습니다.
- 근거 수준은 세 단계로 표시합니다. **관찰**은 자료에서 보인 것, **진술**은 누군가 그렇다고 말한 것, **확인**은 업무 책임자가 규칙으로 승인한 것입니다.
- 도식은 글자로 그립니다. `+--+` 상자, `→`와 `▼` 화살표, `|` 연결선을 씁니다.
- 원전을 인용할 때는 원문을 짧게 따옴표로 옮기고 어디서 왔는지 밝힙니다. 원문을 직접 보지 못하고 다른 문헌의 인용으로만 확인한 내용은 그렇다고 적습니다.

이 가이드가 새로 만든 말과 원전에서 온 말을 섞지 않도록 아래처럼 나눠 둡니다.

| 원전에서 온 말 | 이 가이드가 만든 교육용 형식 |
| --- | --- |
| 외부·개념·내부 스키마, 사상, 데이터 독립성(ANSI/SPARC) | 추출 원장과 여섯 칸 |
| 담화 세계, 100% 원칙, 개념화 원칙(ISO/TR 9007) | 근거 수준(관찰·진술·확인) |
| 기본 사실, 인구 검사, CSDP(Halpin) | 계약의 다섯 겹(구조·의미·행위·품질·진화) |
| 뷰 통합과 충돌 분류(Batini·Lenzerini·Navathe) | 보장 위치표 |
| 사전조건·사후조건·불변식(Meyer) | 실제 계약(선언한 계약 + 관찰된 의존) |

## 이웃 가이드

이 저장소에는 같은 주제를 다른 방향에서 다룬 가이드가 두 편 있습니다. 「시나리오에서 스키마와 구현까지」(`docs/schema-design-guide`)는 단일 매장의 주문 사례 하나를 시나리오부터 API까지 끝까지 따라갑니다. 「DB 스키마 설계 학습 가이드」(`docs/db-schema-guide`)는 저장 여부 판단과 물리 설계를 깊게 봅니다. 이 가이드는 사례 하나를 끝까지 파고들기보다, 정의와 방법을 먼저 정하고 여러 형식의 자료에 되풀이해 적용해요. 한 사례를 처음부터 끝까지 보고 싶으시면 이웃 가이드를 같이 읽어 보세요.

## 이어지는 예: 공유 오피스 「틈」의 회의실 예약

제1부와 제2부는 하나의 작은 사례를 계속 씁니다. 회원 서른 명 남짓의 공유 오피스 「틈」에는 회의실이 셋 있습니다. 회원은 앱으로 회의실을 30분 단위로 예약하고, 안내 데스크 직원은 오늘의 일정표를 보며 손님을 안내하고, 월말에는 청구 담당자가 무료 시간을 넘긴 사용분을 청구합니다. 청구는 다른 팀이 만든 회계 시스템에서 처리해요. 그래서 예약 시스템은 "예약이 확정되었다"는 소식을 그쪽으로 보내야 합니다.

```text
 회원(앱)            안내 데스크            회계 시스템(다른 팀)
 "내 예약"           "오늘 일정표"          "확정된 예약 이벤트"
    \                   |                    /
     +---------- 예약 시스템 ----------------+
              회의실 3개 · 회원 30여 명
```

작은 사례인데도 네 산출물이 모두 필요해요. 같은 회의실의 예약 시간이 겹치면 안 된다는 규칙은 개념 스키마에 들어가야 하고, 회원·안내 데스크·회계 시스템은 서로 다른 외부 스키마를 보며, 회계 시스템과는 계약을 맺어야 하고, 겹침 금지를 DB가 어떻게 지킬지는 내부 스키마에서 정해야 합니다. 실습 문제는 일부러 다른 도메인을 골랐습니다.
