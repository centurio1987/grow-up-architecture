## C. 계약 명세 양식

5장의 다섯 겹과 11장의 설계 절차를 양식으로 정리했습니다. 연산 계약(O)과 이벤트 계약(E)에 같은 양식을 쓰고, 해당하지 않는 칸은 왜 해당하지 않는지 한 줄로 적어요. 빈칸으로 두면 빠뜨린 것인지 해당이 없는 것인지 구분되지 않으니까요.

### 계약 한 벌의 양식

```text
[계약] ○○ (O 또는 E 번호)
  머리
    경계        제공자 ○○ → 소비자 ○○ (동기 호출 / 비동기 이벤트 / 데이터 파일)
    판·상태      1.0.0 · 초안 / 운영 / 폐기 예정
    원장 줄      c○, v○, r○ ...
  구조 겹
    외부 스키마  V○ 또는 페이로드 정의를 가리킴 (기계용 명세 경로)
    입력         ○○
    출력         ○○
  의미 겹
    시각        표기, 시간대, 구간의 포함·불포함
    단위        길이·금액·수량의 단위, 정수 여부
    코드표      값이 어느 코드표에서 오는가, 모르는 값은 어떻게 다루나
    식별        어떤 번호로 무엇을 가리키나
  행위 겹
    사전조건     pre1 (업무) ... pre2 (형식) ...
    사후조건     post1 성공이면 ... post2 ...
    불변식       inv1 ...
    실패         아래 실패표
    멱등성       같은 요청을 다시 보내면 ...
    순서        무엇의 순서를 보장하고 무엇은 보장하지 않나
    동시성       같은 자원을 동시에 바꾸면 ...
    전달        (이벤트) 적어도 한 번 / 많아야 한 번, 중복 제거 방법
  품질 겹
    아래 품질표
  진화 겹
    공개 API    계약에 들어가는 것과 들어가지 않는 것(약속하지 않는 동작)
    호환 분류    아래 진화 정책표
    비호환 절차  공지 → 병행 → 사용 측정 → 제거
    판 번호      Semantic Versioning 규칙
  시험
    제공자 시험  실패표 줄마다 사례 하나, pre·post·inv 마다 사례 하나
    소비자 계약  누가 무엇을 쓰는가 (아래 양식)
```

### 실패표

| 실패 | 응답 | 상태 변화 | 다시 시도 |
| --- | --- | --- | --- |
| pre○ 위반 (업무) | 코드와 이름 | 없음 / 있음(무엇이) | 소용없음 / 같은 키로 / 다른 값으로 |
| pre○ 위반 (형식) |  |  |  |
| inv○ 과 충돌 |  |  |  |
| 같은 멱등 키, 같은 본문 | 첫 응답 그대로 |  | — |
| 같은 멱등 키, 다른 본문 |  |  |  |
| 일시 장애 |  | 없음이 보장되는가? |  |

"상태 변화"와 "다시 시도" 열은 비우지 않습니다. 같은 응답 코드라도 소비자가 해야 할 일이 다르기 때문이에요(11장).

### 품질표

| 항목 | 약속 | 측정 방법 | 지키지 못했을 때 |
| --- | --- | --- | --- |
| 지연 | 예: 요청의 95%가 0.5초 이내 | 어디서, 어떤 주기로 재는가 | 누구에게 얼마 안에 알리는가 |
| 가용성 |  |  |  |
| 신선도 | 예: 확정 후 1분 이내 발행 |  |  |
| 보존 | 예: 7일 보관 |  |  |

데이터 파일을 넘기는 경계라면 ODCS(Open Data Contract Standard)의 SLA 항목(지연, 가용성, 보존 기간, 갱신 주기, 제공 시각, 탐지·통지·복구 시간 등)을 표의 행으로 그대로 써도 됩니다.

### 진화 정책표

| 변경 | 분류 | 소비자별로 다를 때 | 절차 |
| --- | --- | --- | --- |
| 출력에 선택 필드 추가 | 호환(사후조건 강화) | 닫힌 모델로 엄격히 검증하는 소비자에게는 비호환 | 예고 없이 |
| 입력에 선택 필드 추가 | 호환(사전조건 약화) |  | 예고 없이 |
| 출력 열거값 추가 | 모르는 값 처리 규칙을 미리 약속했을 때만 호환 |  | 공지 후 |
| 입력에 필수 필드 추가 | 비호환(사전조건 강화) |  | 주 판 |
| 출력 필드 삭제·이름 변경 | 비호환(사후조건 약화) | 그 필드를 쓰지 않는 소비자에게는 무해(소비자 계약으로 확인) | 주 판 |
| 값의 뜻 변경(구간·단위·시간대) | 비호환(의미 겹) |  | 주 판, 가능하면 새 이름 |
| 입력 허용 범위 넓힘 | 요청 쪽엔 호환, 결과를 읽는 쪽엔 비호환일 수 있음 | 5장의 15분 단위 예 | 소비자별로 |

### 소비자 계약 양식

```text
[소비자 계약] 소비자 ○○ → 제공자 ○○ · 계약 ○○
  쓰는 필드      ○○, ○○, ○○
  쓰는 동작      예: 같은 bookingId 의 이벤트는 순서대로 온다고 믿음
  모르는 필드     무시함 (Tolerant Reader) / 검증 실패로 봄
  모르는 열거값   ○○로 다룸
  확인 방법      예시 상호작용(Pact 의 pact 파일 같은 것)과 제공자 검증
  담당·연락       ○○
```

"쓰는 동작" 칸이 중요합니다. 선언하지 않은 동작에 기대고 있다면 여기 적혀야 해요. 제공자는 이 칸을 모아 실제 계약(선언한 계약 + 관찰된 의존)을 알 수 있습니다(5장 Hyrum 법칙).

### 채운 예: 「틈」의 E1 예약 확정

11장의 내용을 양식에 옮긴 모습입니다. 품질 값은 가정입니다.

```text
[계약] E1 예약 확정
  머리   예약 시스템 → 회계 시스템 · 비동기 이벤트(채널 tum.booking.confirmed) · 1.0.0 운영 · v2, q3
  구조   eventId, bookingId, memberId, roomCode, startAt, endAt (AsyncAPI 3 문서)
  의미   시각은 오프셋이 있는 ISO 8601. 구간 [startAt, endAt). memberId 는 회원번호(이메일 아님)
  행위   발행 조건: O1 이 커밋되었을 때, 그리고 그때만 (예약과 같은 트랜잭션에서 outbox 에 기록)
         전달: 적어도 한 번. 소비자는 eventId 로 중복 제거
         순서: 같은 bookingId 의 E1·E2·E3 은 발생 순서대로. 다른 예약끼리는 보장 안 함
  품질   확정 후 1분 이내 발행(가정) · 채널 보관 7일(가정)
  진화   선택 필드 추가는 예고 없이. 필드 삭제·뜻 변경은 주 판, 90일 전 공지(가정)
  시험   제공자: 커밋 실패 시 발행 없음, 재발행 시 같은 eventId
         소비자 계약(회계): eventId, bookingId, memberId, startAt, endAt 을 씀. roomCode 는 쓰지 않음
```
