## P01 네 산출물 가르기 — 문장 15개

| 난이도 | 씨앗 형식 | 중심 산출물 | 연결 장 |
| --- | --- | --- | --- |
| 하 | 문장 15개 분류 | 넷의 경계 | 1~6 |

### 상황

여러 회사의 설계 회의록에서 한 문장씩 뽑아 왔습니다. 회의에서는 이 문장들이 모두 스키마 이야기라며 한데 섞여 논의됐어요. 문장마다 개념 스키마·외부 스키마·내부 스키마·계약 가운데 어디에 적어야 하는지 가려 주세요. 둘 이상에 걸치는 문장도 있고, 넷 어디에도 들어가지 않는 문장도 있습니다.

### 주어진 자료

```text
(1)  [병원] 환자 한 명은 같은 시각에 두 진료실에 예약될 수 없다.
(2)  [병원] 예약 목록 화면에서 오늘 예약은 노란색 바탕으로 보여 준다.
(3)  [물류] 출고 지시 API에 같은 requestId 로 다시 보내면 처음 응답을 그대로 돌려준다.
(4)  [물류] shipment 표의 (warehouse_id, shipped_at) 에 B-tree 인덱스를 둔다.
(5)  [은행] 이체의 상태는 접수 → 처리 중 → 완료 | 실패 로만 바뀐다.
(6)  [은행] 잔액 조회 API 응답의 95%는 200ms 안에 돌아온다.
(7)  [은행] 이체 이벤트의 amount 는 원 단위 정수이며 소수점이 없다.
(8)  [물류] 배송 조회 응답 JSON 의 출고 시각 필드 이름은 shippedAt 이다.
(9)  [물류] 배송 기록은 5년 보관한 뒤 지운다.
(10) [게임] 플레이어 이름은 모든 서버를 통틀어 유일하다.
(11) [학교] 성적 이벤트의 score 를 100점 만점에서 4.5 만점으로 바꾸기 90일 전에 공지한다.
(12) [학교] 학생 표를 학년별로 나눠 저장한다 (PARTITION BY LIST).
(13) [학교] 담임 교사는 자기 반 학생의 보호자 연락처만 볼 수 있다.
(14) [병원] 예약 목록 API 는 지금까지 늘 예약 시각순으로 돌려줬다. 명세에는 순서가 없다.
          원무과 정산 프로그램은 첫 줄을 그날 첫 예약으로 처리한다.
(15) [게임] 전투 기록은 하루 평균 120만 건 쓰이고, 조회는 그 1% 정도다.
```

### 과제

1. 문장마다 **개념 / 외부 / 내부 / 계약 / 둘 이상 / 어디에도 아님** 가운데 하나를 고르고, 이유를 한 문장으로 적으세요.
2. "둘 이상"으로 고른 문장은 어느 부분이 어느 산출물로 가는지 나눠 적으세요.
3. 다음 두 경우를 가려 보세요. (가) 문장의 내용을 바꿔도 사상만 고치면 바깥 이용자가 모르는 문장, (나) 바꾸려면 계약의 진화 절차(공지·병행·제거)를 거쳐야 하는 문장. 문장 번호로 답하세요(1장 데이터 독립성, 5장 진화 겹).
4. (14)는 지금 어떤 상태이고, 어떻게 정리해야 하나요? 두 가지 정리 방법을 적으세요.

### 실마리

문장마다 네 질문을 차례로 던져 보세요.

```text
가. 담화 세계에 관해 참이어야 하는 규칙·사실인가?          → 개념 (2장)
나. 특정 이용자가 보는 모양·범위·순서·이름인가?             → 외부 (3장)
다. 무엇을 어떤 구조로 저장하고 어떻게 찾는가인가?           → 내부 (4장)
라. 경계 너머 상대에게 지키겠다고 한 약속인가?              → 계약 (5장)
    다섯 겹: 구조 · 의미 · 행위 · 품질 · 진화
```

넷 모두 "아니오"라면, 그 문장은 산출물이 아니라 산출물을 만드는 **입력**이거나 산출물을 **표시하는 방식**일 수 있어요.

### 풀이

#### 1. 분류

| 번호 | 답 | 이유 | 걸리는 원칙 |
| --- | --- | --- | --- |
| (1) | 개념 | 환자·진료실·예약 사이의 규칙. 어느 화면, 어느 저장 방식과도 무관 | 100% 원칙 |
| (2) | 어디에도 아님 | 외부 스키마를 화면에 **표시하는 방식**. 같은 "오늘 예약" 외부 스키마를 문자 메시지로도 보낼 수 있음 | 1장 "외부 스키마는 화면이 아니다" |
| (3) | 계약 | 행위 겹의 멱등성 약속 | 계약 다섯 겹(행위) |
| (4) | 내부 | 접근 경로. 정보를 더하지 않음 | 물리적 데이터 독립성 |
| (5) | 개념 | 상태가 바뀌는 방식에 관한 동적 규칙 | 100% 원칙(정적·동적 모두) |
| (6) | 계약 | 품질 겹(지연). 측정 방법이 함께 있어야 약속이 됨 | 계약 다섯 겹(품질) |
| (7) | 둘 이상 | 외부(값의 모양: 정수)와 계약(의미: 원 단위) | 계약 다섯 겹(구조·의미) |
| (8) | 외부 | 메시지 형식, 곧 특정 이용자에게 보이는 이름 | 개념화 원칙(메시지 형식은 개념에서 뺌) |
| (9) | 둘 이상 | 개념(기록은 5년 뒤 없어진다는 업무·법적 규칙)과 계약(이 데이터를 받는 쪽에 약속하는 보존 기간) | 100% 원칙, 계약 다섯 겹(품질) |
| (10) | 개념 | 플레이어를 이름으로 알아볼 수 있다는 유일성 제약 | 100% 원칙 |
| (11) | 계약 | 진화 겹. 값의 뜻이 바뀌는 변경의 공지 절차 | 계약 다섯 겹(진화), Semver의 주 버전 |
| (12) | 내부 | 저장 구조의 선택. 학생에 관한 사실은 그대로 | 물리적 데이터 독립성 |
| (13) | 둘 이상 | 개념(누가 어떤 정보를 볼 수 있는가라는 보안 규칙)과 외부(담임 교사 관점에서 다른 반 연락처를 가림) | 1985년 ANSI/SPARC 후속 보고서는 개념 스키마에 무결성·보안 제약이 들어간다고 적음 |
| (14) | 계약(실제 계약) | 선언하지 않았지만 소비자가 기대고 있는 동작 | Hyrum 법칙 |
| (15) | 어디에도 아님 | 작업 부하. 내부 스키마를 정하는 **입력**이지 스키마 자체가 아님 | 4장 "작업 부하가 물리 선택을 정한다" |

#### 2. 둘 이상인 문장 나누기

```text
(7)  외부   amount: integer (모양)
     계약   의미 겹: "원 단위, 소수점 없음, 음수 없음(가정)"
            → 단위를 바꾸면 모양은 그대로인데 뜻이 바뀌는 변경이 됨

(9)  개념   "배송 기록은 기록 후 5년이 지나면 담화 세계에서 사라진다" (동적 규칙)
     계약   품질 겹: "이 데이터를 받는 쪽에도 5년 보존, 그 뒤 삭제 통지"
     (내부) 지우는 방법(월 단위 분할을 떼어 내기 등)은 내부의 일. 문장 자체에는 없음

(13) 개념   보안 규칙 "담임 교사는 자기 반 학생의 보호자 연락처를 볼 수 있다"
     외부   담임 교사용 외부 스키마의 가림 항목: 다른 반 학생의 연락처는 빼거나 흐림
```

(13)에서 헷갈리기 쉬운 포인트는 "보이는 범위"이니 외부만으로 끝난다고 보는 것입니다. 가림을 외부 스키마에만 적으면, 같은 연락처를 다른 길(예: 일괄 내보내기)로 읽을 때 그 규칙을 모르게 돼요. 2장의 100% 원칙과 같은 이유로, 규칙은 개념 쪽에 적고 외부 스키마는 그 규칙을 지키는 자리 하나로 봅니다.

#### 3. 사상으로 숨기는 변경과 진화 절차가 필요한 변경

```text
(가) 사상만 고치면 바깥이 모름     (4) 인덱스 · (12) 분할
                                 → 내부만 바뀜. 응답 속도가 달라질 수는 있음(품질 겹)

(나) 진화 절차가 필요함            (3) 멱등 동작 · (6) 지연 약속 · (7) 단위
                                 · (8) 필드 이름 · (9) 보존 기간의 계약 부분
                                 · (11) 점수 체계 · (14) 순서(실제 계약)
```

(8)은 외부 스키마인데 (나)에 들어갔습니다. 외부 스키마도 경계를 넘어 다른 팀이 읽는다면, 필드 이름을 바꾸는 것은 출력 필드를 지우고 새로 만드는 것과 같아 5장의 사후조건 약화에 해당하기 때문이에요. 같은 팀만 쓰는 외부 스키마였다면 (가)에 넣을 수도 있습니다. (1)·(5)·(10)처럼 개념 스키마의 규칙을 바꾸는 일은 (가)·(나) 어느 쪽도 아니에요. 담화 세계의 규칙이 바뀌는 일이라, 담당자의 확인부터 받아야 합니다.

#### 4. (14) 정리하기

지금 (14)의 순서는 선언한 계약에는 없고 관찰된 의존으로만 있는 **실제 계약**입니다. 5장에서 본 Hyrum 법칙 그대로예요. 내부 스키마를 바꾸다 순서가 달라지면 누구도 계약을 어기지 않았는데 정산이 틀립니다. 정리하는 방법은 둘이에요.

```text
방법 A  선언하기   계약 의미 겹에 "예약 목록은 예약 시각 오름차순"을 적고,
                   외부 스키마의 순서 항목과 제공자 시험에 넣는다
방법 B  기대지 않게 하기   원무과 프로그램이 순서 대신 시각 필드로 첫 예약을 고르게 고친다.
                   그 뒤 계약에 "순서는 약속하지 않음"을 명시하고,
                   필요하면 일부러 순서를 섞어 새 의존이 생기지 않게 한다
```

어느 쪽을 고르든, 지금 그 순서에 기대는 소비자가 누구인지 먼저 확인해야 합니다. 11장에서 본 소비자 계약을 모으는 일이 그 확인이에요.

#### 다른 답이 가능한 곳

- (5)를 "둘 이상(개념 + 계약)"으로 볼 수 있습니다. 이체 상태를 API로 보여 준다면, 상태 값과 전이 순서는 계약의 의미 겹에도 적혀야 하니까요. 문장이 "도메인의 규칙"으로만 쓰였다는 점을 보고 개념으로 고른 것이 풀이의 판단입니다.
- (9)에 "내부"를 더해 셋으로 나눠도 됩니다. 다만 문장 자체는 언제 지울지(규칙)를 말할 뿐 어떻게 지울지(저장 방식)는 말하지 않아요.
- (10)을 "개념 + 내부(유일 인덱스)"로 볼 수 있습니다. 유일 인덱스는 그 규칙을 **지키는 자리**이고, 문장은 규칙 자체를 말하므로 풀이는 개념으로 골랐습니다.

#### 흔한 실수

| 실수 | 왜 틀리나 |
| --- | --- |
| (2)를 외부로 고름 | 색은 표시 방식. 외부 스키마는 무엇을 어떤 모양의 정보로 보는가이지 화면 꾸밈이 아님 |
| (4)를 "성능 약속"으로 계약에 넣음 | 인덱스는 수단. 약속은 (6)처럼 측정 가능한 품질로 적어야 함 |
| (14)를 외부로만 고름 | 순서가 외부 스키마의 모양인 것은 맞지만, 소비자가 기대고 있으므로 이미 계약의 문제 |
| (15)를 내부로 고름 | 작업 부하는 내부 설계의 입력. 숫자 자체는 저장 구조가 아님 |
| (8)을 개념으로 고름 | 필드 이름은 메시지 형식. 개념화 원칙이 개념 스키마에서 빼라고 한 것 |
