### 과제

1. 프로파일 요약의 유일 열 조합과 함수 종속을 21장·24장의 세 갈래(진술을 구할 후보 / 우연이라 버릴 것 / 사람에게 물을 어긋남)로 나누세요. 왜 이렇게 많이 나왔는지도 설명합니다.
2. 다음 세 종속의 오차를 계산하고, 어긋난 행이 오류·예외·관행 가운데 무엇인지 판단하세요: `기사코드 → 기사이름`, `송장번호 → 기사코드`, `무게kg → 요금`.
3. 배송 기록의 기사코드가 모두 기사 목록에 있는지(포함 종속) 확인하고, 없는 값을 어떻게 다룰지 결정하세요.
4. 요금 규칙을 자료에서 가설로 세우고 모든 송장에 맞는지 확인하세요. 요금을 저장할지, 계산할지도 정합니다.
5. 개념 스키마와 내부 스키마를 쓰고, 이 자료를 정제 규칙대로 옮겨 넣은 결과를 SQLite로 확인하세요. 점장의 질문("표 하나로 그대로 옮기면?")에 답합니다.

### 실마리

- 송장은 7개뿐입니다. 송장에 딸린 열은 값이 많아야 7가지예요.
- 6012-0002는 배송출발이 두 번 있습니다.
- `김민 준`을 잘 보세요.
- 같은 무게라도 요금이 다른 송장이 있습니다.

#### 1. 프로파일 결과 나누기

28행에 송장 7개라서 우연 종속이 많습니다. 21장에서 본 대로, 값의 종류가 적은 열끼리는 서로를 우연히 "결정"하기 쉬워요. 왼쪽이 한 열인 조합은 13 × 12 = 156개를 검사했고 그 가운데 21개가, 왼쪽이 두 열 이하인 경우 154개가 반례 없이 성립했습니다.

| 결과 | 판단 | 이유 |
| --- | --- | --- |
| 송장번호 → 접수일 … 요금 (8개) | 진술을 구할 후보 | 송장 하나에 딸린 정보. 개념적으로 자연스러움 |
| 우편번호 → 시도 | 진술을 구할 후보 | 주소 체계의 규칙. 다만 우편번호가 5개뿐이라 약한 근거 |
| 받는분 → 요금 | 우연 | 이서연에게 간 두 송장(0001, 0004)이 마침 둘 다 4,000원 |
| 받는분주소 → 송장의 모든 열 (8개) | 우연 | 주소 7개가 모두 달라 송장번호처럼 행동함. 같은 주소로 두 번 보내면 깨짐 |
| 기사코드 → 시도 | 관행일 수 있음 → 물음 | 기사가 늘 한 지역을 맡아 왔음. 담당 구역은 바뀔 수 있음 |
| 기사이름 → 기사코드 | 우연에 가까움 | 동명이인이 없었을 뿐. 오타 "김민 준"도 D01로만 쓰여 성립 |
| 기사이름 → 시도 | 우연 | 위 두 종속에서 따라 나옴 |
| 상태시각 혼자 유일 | 우연 | 28행이 모두 다른 분. 송장이 늘면 같은 분에 상태가 바뀌는 송장이 생김 |
| (송장번호, 기사코드, 상태) 등 세 열 조합 10개 | 우연 | 6012-0002의 배송출발 두 번이 기사가 달라 구별되었을 뿐 |

키 후보로 삼을 만한 것이 프로파일 결과에 **없다**는 점이 중요합니다. 상태 이벤트 하나를 식별하려면 송장번호와 "몇 번째 상태인가"가 필요한데, 그 순번 열이 자료에 없어요. 개념적으로는 (송장번호, 상태시각)도 후보이지만, 한 송장에서 1분 안에 상태가 두 번 바뀔 수 있는지 물어야 합니다.

#### 2. 근사 종속 세 개

```text
기사코드 → 기사이름    지울 행 1 / 28 = 0.0357   D01: 김민준 9행, "김민 준" 1행
송장번호 → 기사코드    지울 행 3 / 28 = 0.1071   6012-0002: D03 4행, D04 2행
                                                6012-0007: D01 2행, D09 1행
무게kg → 요금         지울 행 4 / 28 = 0.1429   1.0kg: 4,000원 4행(서울), 7,000원 4행(제주)
```

판단은 이렇습니다.

| 종속 | 어긋남의 종류 | 근거 | 설계 |
| --- | --- | --- | --- |
| 기사코드 → 기사이름 | 오류 | 띄어쓰기 한 칸. 기사 목록에는 "김민준" | 이름은 기사 목록에만 둠. 상태 이벤트에는 기사코드만(정제: 이름 버림) |
| 송장번호 → 기사코드 | 예외(정상 업무) | 0002는 배송 실패 뒤 다음 날 다른 기사(D04)가 배송. 0007은 집하와 배송 기사가 다름 | 기사는 송장이 아니라 **상태 이벤트**에 딸린 값 |
| 무게kg → 요금 | 규칙이 아님 | 같은 1.0kg이 서울 4,000원, 제주 7,000원 | 요금은 무게만으로 정해지지 않음 → 4번 |

두 번째 판단이 설계를 가장 크게 바꿉니다. 점장의 표는 송장 정보와 기사를 한 줄에 함께 적었는데, 기사는 상태가 바뀔 때마다 달라질 수 있는 값이었어요. 송장 표에 기사 열을 두면 6012-0002에서 두 기사 가운데 하나를 버려야 합니다.

#### 3. 포함 종속

```text
배송 기록.기사코드 의 값이 모두 기사 목록.기사코드 에 있는가 → 아니오, 목록에 없는 값: D09
D09 가 나온 행: 6012-0007 의 집하 (기사이름 칸도 비어 있음)
```

D09는 반례 하나라 21장의 세 갈래 가운데 "사람에게 물음"에 해당합니다. 답이 오기 전에는 **모델에서 허용**해요. 행을 지우면 그 송장의 집하 기록이 사라지고, 다른 기사로 바꾸면 틀린 사실이 생기니까요. 내부 스키마에서는 기사코드를 `NULL`로 두고, 원래 적힌 코드를 `driver_unverified` 열에 옮겨 둡니다.

```text
q  D09 는 누구인가요? 퇴사한 기사, 임시 기사, 다른 대리점 기사 가운데 어느 쪽인가요?
q  기사 목록에 없는 기사가 집하하는 일이 자주 있나요?
```

#### 4. 요금 규칙

`무게kg → 요금`은 성립하지 않지만, 시도를 더한 `(시도, 무게kg) → 요금`은 반례 없이 성립합니다(지울 행 0). 시도 가운데 요금이 다른 것은 제주뿐이라는 점을 보고 가설을 세웠어요.

```text
가설  2kg 이하 4,000원 · 5kg 이하 5,000원 · 10kg 이하 6,000원 · 제주는 3,000원 추가
검사  송장 7개 가운데 7개가 가설과 같음 (verification/p12-fee-rule.json)
      0001 서울 1.0 → 4,000 · 0002 부산 3.5 → 5,000 · 0003 제주 1.0 → 4,000 + 3,000 = 7,000
      0004 경기 2.0 → 4,000 · 0005 서울 6.0 → 6,000 · 0006 부산 4.8 → 5,000 · 0007 서울 0.8 → 4,000
```

일곱 송장이 모두 맞았지만 이 가설은 **관찰**입니다. 10kg을 넘는 송장, 제주 말고 다른 섬, 2kg과 5kg 경계의 정확한 처리(2.0kg이 4,000원인 것은 "2kg 이하"와 맞음)는 자료로 확인되지 않은 범위예요. 점장에게 요금표를 받아 확인해야 합니다.

요금은 계산하지 않고 **저장**합니다. 요금표는 바뀔 수 있고, 송장의 요금은 접수할 때 그때의 요금표로 받은 금액이라는 사실이에요. 내일 요금표가 바뀌어도 어제 접수한 송장의 요금은 그대로여야 합니다. 9장의 "발행된 청구서"와 같은 이유입니다. 요금표 가설은 접수할 때 요금을 계산하는 규칙(계약의 사전조건이나 응용의 계산)으로 쓰고, 저장된 요금과 어긋나는 송장이 생기면 감시 질의로 잡아요.

#### 5. 개념 스키마와 내부 스키마

```text
[개체] 송장(송장번호) · 기사(기사코드) · 우편번호(번호)
[사실] F1 송장 은 접수일, 보내는분, 받는분, 받는분주소, 우편번호, 무게, 요금 을 가진다
[사실] F2 우편번호 는 시도 에 있다                       (진술 필요)
[사실] F3 기사 는 이름, 담당구역, 입사일 을 가진다
[사실] F4 송장 은 순번 n 번째 상태 이벤트 를 가진다: 상태, 시각, 기사(선택)
[제약] R1 상태 값 {집하, 간선상차, 배송출발, 배송실패, 배송완료, 반송}
[제약] R2 상태 이벤트의 기사는 기사 목록에 있다 — 확인 대기 값은 예외로 허용
[미결] 상태 전이 규칙(배송실패 뒤에는 배송출발만?), 한 송장 안 같은 분의 두 상태 가능 여부
```

```sql
CREATE TABLE zip (zip TEXT PRIMARY KEY, sido TEXT NOT NULL);
CREATE TABLE driver (
  driver_code TEXT PRIMARY KEY, name TEXT NOT NULL, area TEXT NOT NULL, hired_on TEXT NOT NULL
);
CREATE TABLE parcel (
  waybill TEXT PRIMARY KEY,
  received_on TEXT NOT NULL,
  sender TEXT NOT NULL,
  receiver TEXT NOT NULL,
  receiver_addr TEXT NOT NULL,
  zip TEXT NOT NULL REFERENCES zip(zip),
  weight_kg REAL NOT NULL CHECK (weight_kg > 0),
  fee INTEGER NOT NULL CHECK (fee > 0)
);
CREATE TABLE parcel_event (
  waybill TEXT NOT NULL REFERENCES parcel(waybill),
  seq INTEGER NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('집하','간선상차','배송출발','배송실패','배송완료','반송')),
  at TEXT NOT NULL,
  driver_code TEXT REFERENCES driver(driver_code),
  driver_unverified TEXT,
  PRIMARY KEY (waybill, seq)

```

정제 규칙은 넷입니다.

```text
1. 송장 정보는 송장마다 한 번만 옮김
2. 기사 이름은 버리고 기사코드만 옮김 (이름은 기사 목록에서)
3. 우편번호와 시도는 우편번호 표로
4. 목록에 없는 기사코드는 NULL 로 두고 원래 코드를 driver_unverified 에
```

외래 키를 켠 SQLite(3.53.0)에 옮겨 넣은 결과예요.

```text
송장 7행 · 상태 이벤트 28행 · 우편번호 5행
외래 키로 거부된 이벤트 1행 → 6012-0007 의 1번(집하), 원래 코드 D09 → 확인 대기로 옮김
배송출발이 두 번인 송장: 6012-0002
기사 목록의 D01 이름: 김민준 ("김민 준" 은 옮기지 않음)
```

점장의 질문에 답하면 이렇습니다. 표 하나로 그대로 옮기면 송장 정보가 상태마다 되풀이되어, 받는 분 주소를 고칠 때 네 줄을 함께 고쳐야 합니다(갱신 이상). 기사 이름의 오타는 계속 생기고, D09 같은 값을 걸러 낼 자리도 없어요. 표를 넷으로 나누면 28줄이 송장 7행과 이벤트 28행이 되고, 고칠 곳은 한 곳씩이 됩니다.

#### 다른 답이 가능한 곳

- 상태 이벤트의 키를 (송장번호, 상태시각)으로 둘 수도 있습니다. 한 송장에서 같은 분에 상태가 두 번 바뀌지 않는다고 확인되면 순번이 필요 없습니다.
- 시도를 송장에 그대로 두는 설계도 가능합니다. 우편번호 체계를 믿지 못하거나(한 우편번호가 두 시도에 걸치는 경우), 접수할 때 적힌 시도를 그대로 남겨야 한다면 송장의 사실로 둡니다.
- D09를 기사 목록에 "확인 대기 기사"로 넣는 방법도 있습니다. 그러면 외래 키는 늘 성립하지만, 기사 목록에 사실이 아닌 행이 생깁니다. 어느 쪽이든 원장에 이유를 남깁니다.

#### 흔한 실수

- 프로파일러가 낸 함수 종속 154개를 정규화 입력으로 그대로 쓰는 것. 받는분주소 → 송장번호를 따르면 주소가 키인 표가 생깁니다.
- 상태시각을 기본 키로 고르는 것. 이 자료에서만 유일합니다.
- 기사를 송장의 속성으로 두는 것. 6012-0002의 두 기사 가운데 하나를 잃습니다.
- D09 행을 지우는 것. 집하 기록이 사라집니다.
- 요금을 무게로 계산하는 열로 바꾸는 것. 요금표가 바뀌면 지난 송장의 요금이 바뀝니다.

#### 채점 기준

| 항목 | 기준 |
| --- | --- |
| 프로파일 해석 | 우연 종속과 우연 키를 이유와 함께 가려냄. 키 후보가 자료에 없다는 것을 알아챔 |
| 근사 종속 | 세 오차를 맞게 계산(1/28, 3/28, 4/28)하고 오류·예외·규칙 아님을 구별함 |

| 요금 | (시도, 무게) 가설을 세우고 7개 송장으로 확인하되 관찰로 둠. 요금을 저장하는 이유를 댐 |
| 스키마 | 기사를 상태 이벤트에 둠. DDL이 실행되고 옮긴 결과(7·28·5, 거부 1)가 맞음 |
