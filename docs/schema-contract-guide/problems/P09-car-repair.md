## P09 자동차 정비소 — 세 부서의 관점

| 난이도 | 씨앗 형식 | 중심 산출물 | 연결 장 |
| --- | --- | --- | --- |
| 상 | 세 부서의 관점 메모와 양식 | 관점 통합 | 10 |

### 상황

정비사 열두 명이 일하는 「바른정비」는 부서마다 따로 쓰던 엑셀과 종이 양식을 하나의 시스템으로 옮기려 합니다. 접수 데스크, 정비 작업장, 회계 담당이 각자 자기 업무를 메모로 설명하고 지금 쓰는 양식을 한 장씩 내주었어요. 세 관점을 하나의 개념 스키마로 통합해 주세요. 회계는 나중에 외부 회계 패키지로 옮길 가능성이 있어서, 회계 관점을 끝까지 합칠지 경계로 남길지도 판단해야 합니다.

### 과제

1. **사전 통합.** 세 관점을 합칠 순서와 우선순위를 정하고 이유를 적으세요(10장 사전 통합, 이진·n항 전략).
2. **비교.** 이름 충돌과 구조 충돌을 모두 찾아 표로 적으세요. 열은 종류·관련 요소·근거(자료 줄 번호)입니다. 구조 충돌은 유형·종속·키·행위 네 종류가 모두 들어 있습니다. 어느 관점에도 없지만 통합해야 알 수 있는 스키마 사이 관계도 찾아보세요.
3. **맞추기.** 충돌마다 맞추는 결정과 근거를 적고, 담당자에게 물어야 할 것은 q로 남기세요.
4. **병합과 재구성.** 통합 개념 스키마를 2장의 글자 표기로 적으세요.
5. **품질 점검.** 10장의 점검 표(완전성·적절성·정확성·최소성·이해 용이성)로 결과를 점검하세요.
6. **경계.** 회계를 외부 회계 패키지로 옮긴다고 할 때, 통합 스키마에서 무엇을 떼어 내고 경계에 어떤 계약을 두어야 하는지 다섯 겹으로 요약하세요.

### 실마리

- 같은 낱말이 부서마다 다른 단위로 쓰이는 곳이 있습니다. 숫자 옆의 단위를 보세요.
- "작업"이라는 말이 세 자료에서 같은 크기의 일을 가리키는지 확인하세요.
- 차와 손님을 각 부서가 무엇으로 찾는지 표로 나란히 놓아 보세요.
- 청구서 합계 214,000원을 공임과 부품으로 나눠 다시 계산해 보세요. 계산하려면 어느 관점에도 없는 사실 하나가 필요합니다.

### 풀이

#### 1. 사전 통합

이진 사다리꼴 전략으로 `(A 접수 + B 정비) + C 회계` 순서를 권합니다.

```text
1단계  A + B   둘 다 "맡긴 차 한 대의 한 번 수리"를 다룸. 차·접수·작업이 크게 겹침
               → 키 충돌(차량번호/차대번호)과 유형 충돌(차종/모델)이 여기서 대부분 풀림
2단계  (A+B) + C   C는 돈과 보관을 다룸. 거래처·청구·단가가 새로 들어옴
우선순위  행위 충돌은 C 우선 (법적 보관 의무 C6), 식별은 B 우선 (번호판이 바뀐다는 B1)
```

A와 B를 먼저 합치는 이유는 둘의 겹침이 가장 크기 때문이에요. 겹침이 큰 둘을 먼저 합치면, 나머지 하나를 합칠 때는 새 개념만 더하면 됩니다. 우선순위를 충돌 종류마다 따로 정한 것도 주목해 보세요. 한 관점이 모든 충돌에서 앞서는 것이 아니라, 근거가 가장 강한 관점이 그 종류의 충돌에서 앞섭니다.

#### 2. 비교: 충돌 표

| 번호 | 종류 | 관련 요소 | 근거 |
| --- | --- | --- | --- |
| k1 | 이음동의어 | A "고객"(손님) / C "거래처" 가운데 개인 거래처 | A2, C1 |
| k2 | 이음동의어 | A 차량번호 / B 차량번호(참고) / C 차량번호 — 같은 말이지만 B에서는 식별자가 아니라 참고 값 | A1, B1 |
| k3 | 동음이의어 | "공임": B는 시간(1.5 = 한 시간 반), C는 금액(원) | B3, C4 |
| k4 | 동음이의어 | "작업": A는 접수 한 건 전체("작업이 다 끝나면"), B는 지시서 안의 한 줄 | A7, B2 |
| k5 | 유형 충돌 | A 차종은 차의 자유 문자열 속성, B 모델은 제조사·모델·연식을 가진 개체 | A5, B5 |
| k6 | 종속 충돌 | A는 접수 하나에 청구 금액 하나(1:1), C는 청구서 하나에 여러 접수(법인 월말 일괄, N:1) | A7, C2 |
| k7 | 키 충돌 | 차: A 차량번호 / B 차대번호 | A1, B1 |
| k8 | 키 충돌 | 손님: A 휴대폰 / C 거래처 코드 | A2, C1 |
| k9 | 행위 충돌 | 접수 취소 시 A는 삭제, B는 작업 시작 후 삭제 불가(취소 표시), C는 출장비가 있으면 5년 보관 | A6, B6, C6 |
| k10 | 종속 충돌 | 청구받는 쪽: A·B는 손님=차 주인을 전제, C는 사고 수리에서 보험사로 청구 | A4, C3 |

스키마 사이 관계도 두 가지 찾을 수 있어요.

```text
x1  정비사 → 등급 → 시간당 단가
    C4 는 "정비사 등급별 단가"를 말하지만, 정비사의 등급은 A·B·C 어디에도 기록되지 않음.
    B 는 작업마다 정비사 이름만, C 는 등급별 단가만 가짐.
    검산: W-2207 의 공임 1.0 + 0.5 = 1.5시간. 청구서 공임액 90,000원.
          A급이면 1.5 × 60,000 = 90,000원 → 맞음.  B급이면 1.5 × 45,000 = 67,500원 → 안 맞음.
          → 김정우 정비사는 A급이라고 추정되지만, 이것은 계산에서 나온 관찰일 뿐 확인이 필요

x2  보험 접수번호가 있는 접수 → 청구 거래처는 보험사
    A4 는 보험 접수번호를 적기만 하고, C3 는 보험사로 청구한다고만 함.
    "보험 접수번호가 있으면 청구 대상이 바뀐다"는 연결은 둘을 합쳐야 보임
```

x1의 검산에서 부품액도 확인해 두면 좋습니다. 합계 214,000원에서 공임 90,000원을 빼면 부품 124,000원이에요. 부품 단가표는 자료에 없으므로 이 124,000원이 두 부품(BP-2019F, BO-DOT4)의 단가 합과 맞는지는 확인할 수 없습니다. 이것도 q로 남깁니다.

#### 3. 맞추기

| 충돌 | 결정 | 근거·남는 질문 |
| --- | --- | --- |
| k1 고객 / 거래처 | **고객**(차를 맡긴 사람)과 **거래처**(청구를 받는 쪽)를 따로 둠. 개인 고객은 거래처 하나와 이어짐 | k10 때문에 둘이 같다고 볼 수 없음 |
| k2·k7 차량번호 / 차대번호 | 차의 참조 방식은 차대번호. 차량번호는 "차는 어느 기간에 어떤 번호판을 달았다"는 사실로 | B1(번호판이 바뀜). 2장: 참조 방식은 시간이 지나도 바뀌지 않아야 함 |
| k3 공임 | "공임 시간"(시간, 0.5 단위)과 "공임액"(원)으로 이름을 나눔. 용어집 t 에 기록 | q: 공임 시간은 0.5 단위만 쓰나? |
| k4 작업 | "수리 건"(접수 한 건)과 "작업 항목"(지시서 한 줄)으로 나눔 | A7의 "작업"은 수리 건 |
| k5 차종 / 모델 | 개체 "모델"(제조사·모델명·연식)로 맞춤. 접수 때 자유 문자열은 "고객이 말한 차종"이라는 메모 값으로 남김 | B5: 연식마다 부품이 다름 |
| k6 청구 1:1 / N:1 | 청구서 하나에 수리 건 여럿(N:1)으로 맞춤. A7의 "청구 금액"은 수리 건마다 계산되는 파생 값 | C2 |
| k8 휴대폰 / 거래처 코드 | 고객은 고객 번호(새로 만듦)로 식별. 휴대폰은 바뀔 수 있는 속성. 거래처는 거래처 코드 | q: 고객 번호를 새로 만들어도 되는가? 접수 데스크는 휴대폰으로 찾는 습관이 있음 |
| k9 행위 | 수리 건은 지우지 않고 상태(접수, 작업 중, 완료, 취소)를 둠. 출장비가 있는 취소 건은 5년 보관 | C6(법적 보관)이 앞섬. A6의 "지운다"는 화면에서 안 보이게 하는 것으로 바꿈 |
| k10 청구 대상 | 수리 건마다 청구 거래처를 둠. 보험 접수번호가 있으면 보험사 거래처(x2) | q: 보험이 일부만 내고 나머지를 고객이 내는 경우가 있나? |
| x1 정비사 등급 | 개체 "정비사"에 등급 사실을 둠. 등급별 시간당 단가는 개체 "정비사 등급"에 | q: 등급이 바뀌면 과거 청구는 그때 등급으로? |

k9을 맞춘 방식은 본문 10장의 회원 탈퇴 사례와 같습니다. "지운다"와 "보관한다"가 함께 참일 수 없을 때, 지우지 않고 상태를 두는 쪽으로 맞추고, A의 "지운다"는 업무상 바라는 효과(접수 화면에서 안 보이기)를 외부 스키마의 고르기 조건으로 옮겨요.

#### 4. 병합과 재구성

```text
[개체] 고객(고객 번호)            이름 · 휴대폰
[개체] 거래처(거래처 코드)        이름 · 구분{개인, 법인, 보험사}
[개체] 차(차대번호)               모델
[개체] 모델(제조사, 모델명, 연식)  ← k5
[개체] 수리 건(접수번호)          고객 · 차 · 접수일 · 주행거리 · 증상 · 예상 출고일
                                 · 보험 접수번호(선택) · 청구 거래처 · 상태
[개체] 작업 항목(지시서 번호, 줄 번호)
[개체] 정비사(정비사 번호)         이름 · 등급                       ← x1
[개체] 정비사 등급(등급)           시간당 단가
[개체] 부품(부품번호)              단가
[개체] 청구서(청구번호)            거래처 · 청구월

[사실] F1  차 는 [시작일, 종료일) 동안 차량번호 를 달았다               ← k2·k7
[사실] F2  고객 은 거래처 와 이어진다 (개인 고객만, 선택)                ← k1
[사실] F3  작업 항목 은 수리 건 에 속한다
[사실] F4  작업 항목 은 정비사 가 맡는다 · 공임 시간 을 가진다          ← k3
[사실] F5  작업 항목 은 부품 을 수량 만큼 쓴다
[사실] F6  수리 건 은 청구서 에 실린다 (N:1, 선택)                      ← k6
[사실] F7  수리 건 은 출장비 를 가진다 (선택)

[제약] R1  한 차의 번호판 기간은 겹치지 않는다
[제약] R2  보험 접수번호가 있는 수리 건의 청구 거래처는 구분이 보험사다        ← x2 (확인 필요)
[제약] R3  수리 건의 청구 거래처와 그 수리 건이 실린 청구서의 거래처는 같다
[제약] R4  작업 항목이 하나라도 시작된 수리 건은 지울 수 없다 (상태로만)      ← k9
[제약] R5  출장비가 있는 취소 수리 건은 5년 보관한다                        ← k9

[파생] D1  공임액 = 공임 시간 × 맡은 정비사 등급의 시간당 단가                ← k3, x1
[파생] D2  부품액 = 작업 항목이 쓴 부품마다 단가 × 수량의 합
[파생] D3  수리 건의 청구 금액 = 그 수리 건 작업 항목들의 D1 + D2 (+ 출장비)   ← A7
[파생] D4  청구서 합계 = 실린 수리 건들의 D3 합
```

재구성에서 바뀐 것이 셋 있습니다. A7의 "청구 금액" 칸은 저장된 값이 아니라 D3이 됐어요. C의 청구서 행에 있던 "공임액·부품액"도 D1·D2로 계산합니다. 같은 값을 접수증과 청구서에 따로 적으면 10장의 최소성에 어긋나니까요. 그리고 차량번호는 차의 속성이 아니라 기간이 있는 사실 F1이 됐습니다.

#### 5. 품질 점검

| 점검 | 질문 | 결과 |
| --- | --- | --- |
| 완전성 | 세 자료의 모든 칸에 대응하는 요소가 있는가 | 있음. 접수증의 "차종"은 수리 건의 메모 값으로. 청구서의 "작업 내용"(브레이크 정비)은 작업 항목 이름들의 요약이라 파생(외부 스키마의 계산 열)으로 봄 |
| 적절성 | 근거 없는 요소가 있는가 | 고객 번호는 자료에 없음. k8 의 맞추기 결정으로 만든 것이므로 q 로 확인 대기 |
| 정확성 | 요구를 바르게 옮겼는가 | R2 는 x2 에서 끌어낸 것이라 진술조차 없음(관찰도 아닌 추론). 확인 전까지 제약으로 걸지 않음 |
| 최소성 | 계산되는 값을 따로 두지 않았는가 | 청구 금액·공임액·부품액을 파생으로 바꿈 |
| 이해 용이성 | 담당자가 알아보는가 | "공임 시간"과 "공임액"이 각 부서 말과 어긋나지 않음을 용어집으로 확인 필요 |

정확성 줄을 보세요. R2는 두 관점을 합치면서 떠오른 연결이라, 7장의 근거 수준으로 치면 관찰도 진술도 아닌 **설계자의 추론**입니다. 이런 줄은 원장에 q로 두고 회계 담당자에게 확인받은 뒤에야 제약으로 올립니다.

#### 6. 회계를 경계로 남길 때

회계를 외부 패키지로 옮긴다면, 2장의 맥락 구분대로 회계 맥락의 개념(거래처, 청구서, 단가로 금액 계산)은 정비소 스키마에서 떼어 내고 경계에 계약을 둡니다.

```text
떼어 내는 것   거래처, 청구서, F6, R3, D4 (청구서 묶기는 회계 패키지가 함)
남기는 것      고객, 차, 수리 건, 작업 항목, 정비사, 부품, F1~F5, F7, D1~D3
               (청구 금액 계산은 정비소가 하고, 금액을 넘김)
경계           E1 "수리 건 완료" 이벤트, E2 "수리 건 취소(출장비 있음)" 이벤트
```

| 겹 | E1 수리 건 완료 |
| --- | --- |
| 구조 | 접수번호, 고객 번호, 청구 거래처 코드, 차대번호, 완료일, 공임액, 부품액, 출장비, 청구 금액, 작업 항목 목록(이름, 공임 시간) |
| 의미 | 금액은 원·정수·부가세 포함 여부 명시(q). 공임 시간은 시간 단위 0.5 간격. 거래처 코드는 회계 패키지의 코드표 값. 차량번호가 아니라 차대번호로 차를 가리킴 |
| 행위 | 수리 건이 완료 상태가 될 때만, 적어도 한 번 발행. 소비자는 접수번호로 중복 제거. 같은 수리 건의 완료·취소는 발생 순서대로 |
| 품질 | 완료 후 10분 안에 발행(가정). 이벤트 보관 30일(가정) |
| 진화 | 선택 필드 추가는 호환. 금액의 뜻(부가세 포함 여부) 변경은 주 버전. 거래처 코드 체계는 회계 패키지가 정하므로 그쪽 변경 공지를 받아야 함 |

진화 줄의 마지막 문장이 중요합니다. 거래처 코드는 회계 패키지의 것이므로, 이 계약에서는 정비소가 소비자 입장이 돼요. 한 경계에서 두 방향의 약속이 함께 있는 셈이고, 거래처 코드표를 받아 오는 쪽은 Tolerant Reader로 읽는 것이 안전합니다.

#### 다른 답이 가능한 곳

- 사전 통합에서 n항 한 번에(one-shot) 합쳐도 됩니다. 자료가 세 장뿐이라 부담이 크지 않아요. 다만 충돌을 기록하는 일이 한꺼번에 몰립니다.
- k8에서 고객 번호를 새로 만들지 않고 휴대폰을 참조 방식으로 남길 수도 있습니다. 휴대폰이 바뀔 때 고객이 둘로 갈리는 위험을 받아들인다는 결정과 그 근거(접수 데스크의 습관, 작은 규모)를 적었다면 맞는 답입니다.
- 6번에서 청구 금액 계산까지 회계 패키지로 넘기고, 정비소는 공임 시간·정비사 등급·부품 수량만 보내는 경계도 가능합니다. 그때는 등급별 단가가 회계 쪽 사실이 되고, 계약의 구조 겹이 달라져요.
