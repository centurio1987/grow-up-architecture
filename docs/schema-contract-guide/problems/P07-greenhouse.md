## P07 스마트 온실 경보 — EARS 요구사항

| 난이도 | 씨앗 형식 | 중심 산출물 | 연결 장 |
| --- | --- | --- | --- |
| 중 | 요구사항 문장(EARS) | 계약, 내부 스키마 | 11, 12, 19 |

### 상황

딸기 농장이 온실 세 동에 센서를 달고 관제 시스템을 만듭니다. 센서 값은 농장에 설치한 게이트웨이(다른 업체 제품)가 모아 관제 시스템으로 보내요. 발주처가 EARS 꼴로 쓴 요구사항 명세를 보냈습니다. 센서 측정 메시지의 계약과, 측정값을 저장하는 내부 스키마를 설계합니다.

### 주어진 자료

```text
시설   온실 3동(G1·G2·G3), 동마다 센서 12개(온도 4 · 습도 4 · CO2 4)

GH-01 관제 시스템은 온실마다 온도·습도·CO2 센서 값을 60초마다 기록해야 한다.
GH-02 센서 측정값이 들어오면, 관제 시스템은 그 값을 측정 시각과 함께 저장해야 한다.
GH-03 한 온도 센서의 값이 5회 연속 35.0℃를 넘으면, 관제 시스템은 그 온실에 고온 경보를 내야 한다.
GH-04 만약 한 센서에서 3분 동안 값이 들어오지 않으면, 그때 관제 시스템은 센서 끊김 경보를 내야 한다.
GH-05 경보가 확인되지 않은 동안, 관제 시스템은 30분마다 같은 경보를 다시 보내야 한다.
GH-06 관리자가 경보를 확인하면, 관제 시스템은 확인한 사람과 시각을 기록하고 다시 보내기를 멈춰야 한다.
GH-07 환기창이 수동 모드인 동안, 관제 시스템은 환기창을 자동으로 열거나 닫지 않아야 한다.
GH-08 환기창이 자동 모드인 동안, 고온 경보가 나면, 관제 시스템은 그 온실의 환기창을 열어야 한다.
GH-09 문자 알림을 신청한 관리자인 경우, 관제 시스템은 경보를 문자로도 보내야 한다.
GH-10 만약 측정값이 센서의 측정 범위(온도 -20~60℃)를 벗어나면, 그때 관제 시스템은 그 값을
      저장하되 이상값으로 표시하고 경보 판정에 쓰지 않아야 한다.
GH-11 관제 시스템은 원시 측정값을 90일 동안 보관해야 한다.
GH-12 관제 시스템은 5분 평균값을 2년 동안 보관해야 한다.
GH-13 관제 시스템은 대시보드에 최근 24시간 그래프를 보여 주는 것이 좋다.
GH-14 관제 시스템은 경보를 빠르게 보내야 한다.

게이트웨이가 보내는 메시지 한 건(업체 문서의 예)
{"sensor":"T-03","greenhouse":"G2","kind":"temp","value":35.6,"unit":"C",
 "measuredAt":"2026-11-17T10:02:00+09:00","seq":18231}

업체 문서의 한 줄: "네트워크가 끊기면 게이트웨이가 쌓아 두었다가 다시 이어질 때 한꺼번에 보냅니다."

T-03(G2 온도 센서)의 10:00부터 1분 간격 값 (- 는 수신 없음)
10:00 34.8 · 10:01 35.2 · 10:02 35.6 · 10:03 36.0 · 10:04 34.9 · 10:05 35.3 · 10:06 35.4
10:07 35.8 · 10:08 36.1 · 10:09 36.4 · 10:10 36.2 · 10:11 - · 10:12 - · 10:13 - · 10:14 - · 10:15 35.9
```

### 과제

1. 문장마다 EARS 패턴을 적고, 19장의 대응표에 따라 원장 칸과 산출물을 정하세요. 29148 특성으로 문제가 있는 문장은 고쳐 쓰거나 질문으로 바꾸세요.
2. 게이트웨이 → 관제 시스템의 센서 측정 메시지 계약 E1을 다섯 겹으로 쓰세요. 업체 문서의 "한꺼번에 보냅니다"가 행위 겹에 무엇을 요구하는지 보이세요.
3. 측정값 저장의 작업 부하와 규모를 계산하고, 내부 스키마(표, 키, 인덱스, 분할, 5분 평균, 보관)를 결정 기록과 함께 쓰세요.
4. GH-03·GH-04·GH-05·GH-10을 지키는 자리를 보장 위치표로 적으세요.
5. T-03의 값으로 고온 경보와 센서 끊김 경보가 각각 언제 나는지 계산하세요. 끊겼던 값이 10:16에 한꺼번에 들어온다면 무엇이 달라지는지도 적으세요.

### 실마리

- GH-03의 "5회 연속"은 값이 **도착한** 순서일까요, **측정된** 순서일까요?
- GH-11·GH-12는 Ubiquitous 문장이지만 DB 제약으로는 지킬 수 없습니다.
- 규모 계산에는 바이트 수가 필요하지만 자료에 없습니다. 가정이라고 밝히고 쓰세요.

#### 2. 센서 측정 메시지 계약 E1

이 경계에서 메시지를 만드는 쪽은 게이트웨이(다른 업체)이고, 받는 쪽은 관제 시스템입니다. 우리가 게이트웨이를 고칠 수 없으므로, 계약은 업체 문서에서 확인한 것과 우리가 요구하는 것을 나눠 적어요.

| 겹 | 내용 | 출처 |
| --- | --- | --- |
| 구조 | `sensor`, `greenhouse`, `kind{temp, humidity, co2}`, `value`(수), `unit`, `measuredAt`(오프셋 있는 ISO 8601), `seq`(정수) — 모두 필수 | 업체 예시 + 우리 요구 |
| 의미 | `value`의 단위는 `unit`이 정함(온도 C, 습도 %, CO2 ppm). `measuredAt`은 센서가 잰 시각이지 보낸 시각이 아님. `seq`는 센서마다 1씩 늘어나는 번호 | q4로 확인 |
| 행위 | 전달은 적어도 한 번. 끊겼다가 이어지면 쌓인 메시지가 한꺼번에, 늦게 옴. 관제는 `(sensor, seq)`로 중복을 거르고, 판정은 `measuredAt` 순서로 함 | 업체 문서 |
| 품질 | 센서마다 60초 간격 측정(GH-01). 정상일 때 측정 뒤 몇 초 안에 도착하는지는 q5 | GH-01 |
| 진화 | 새 `kind` 값이 생기면 관제는 모르는 값을 저장만 하고 판정에 쓰지 않음. 필드 추가는 무시 | 우리 정책 |

업체 문서의 "한꺼번에 보냅니다"가 행위 겹을 두 가지로 바꿨습니다. 하나는 **늦게 도착하는 값**이에요. 도착 순서와 측정 순서가 다를 수 있으니, GH-03의 "5회 연속"은 `measuredAt` 순서로 세야 합니다. 다른 하나는 **같은 값이 두 번 오는 일**입니다. 다시 보낼 때 이미 받은 것까지 보낼 수 있으니 `(sensor, seq)`로 거르고, 저장 표의 키도 이것으로 맞춰요.

관제 시스템이 내보내는 경보 이벤트 E2도 짧게 적어 둡니다.

```text
E2 경보 발생   채널 greenhouse.alarm
  페이로드   alarmId, greenhouse, kind{high_temp, sensor_lost}, sensor, triggeredAt, basedOn(측정 시각 범위)
  발행 조건  r3 또는 r4 가 성립할 때 한 번. 미확인이면 30분마다 같은 alarmId 로 다시(r5)
  전달       적어도 한 번. 받는 쪽(문자 서비스, 환기창 제어)은 alarmId + 회차로 중복을 거름
```

#### 3. 작업 부하와 내부 스키마

규모는 `verification/p07-greenhouse.py`로 계산했고 결과는 `verification/p07-greenhouse.json`에 있어요.

```text
센서 수           3동 × 12 = 36
하루 원시 행      36 × 24 × 60 = 51,840
90일 원시 행      51,840 × 90 = 4,665,600
하루 5분 평균 행   36 × 24 × 60 / 5 = 10,368
2년 5분 평균 행    10,368 × 730 = 7,568,640
90일 원시 바이트   행 하나를 60바이트로 가정하면 4,665,600 × 60 = 279,936,000 (약 280MB)
```

행 하나의 크기 60바이트는 **가정한 값**입니다. 실제 크기는 PostgreSQL의 행 머리와 열 정렬에 따라 달라지므로, 표를 만든 뒤 재서 고쳐야 해요.

```sql
-- PostgreSQL 문법. 이 저장소 환경에서는 실행하지 못했습니다.
CREATE TABLE reading (
  sensor_id   text        NOT NULL,
  measured_at timestamptz NOT NULL,
  seq         bigint      NOT NULL,
  value       double precision NOT NULL,
  is_outlier  boolean     NOT NULL DEFAULT false,      -- GH-10
  received_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (sensor_id, measured_at)                -- 분할 키(measured_at)를 포함
) PARTITION BY RANGE (measured_at);

CREATE TABLE reading_2026_11 PARTITION OF reading
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE UNIQUE INDEX ux_reading_seq ON reading_2026_11 (sensor_id, seq);   -- 중복 거르기
CREATE INDEX brin_reading_time ON reading_2026_11 USING brin (measured_at);

CREATE TABLE reading_5min (                           -- GH-12, 파생 d1 을 저장
  sensor_id    text        NOT NULL,
  bucket_start timestamptz NOT NULL,
  avg_value    double precision NOT NULL,
  n            integer     NOT NULL CHECK (n BETWEEN 0 AND 5),
  PRIMARY KEY (sensor_id, bucket_start)
);
```

         훨씬 빠르다고 PostgreSQL 문서가 설명함. 분할 키 measured_at 은 대부분 질의의 조건과 같음
  비용   기본 키와 고유 제약에 분할 키가 들어가야 함 → (sensor_id, seq) 고유는 파티션마다만 보장.

  재검토 끊김 빈도를 재 보고

  비용   늦게 도착한 값이 지난 버킷에 들어가면 그 버킷을 다시 계산해야 함

MV1의 근거가 특히 중요합니다. 5분 평균은 개념적으로는 원시값에서 계산되는 파생값이에요. 보통이면 저장하지 않고 파생 규칙으로 둡니다. 그런데 원시값이 90일 뒤에 지워지므로, 91일째부터는 계산할 원천이 사라져요. 1장에서 본 "정보가 사라지는 변경"을 내부 스키마가 스스로 만드는 셈이라, 그 전에 평균을 사실로 굳혀 저장해야 합니다. 파생값이 보관 정책 때문에 저장된 사실로 바뀌는 경우예요.

#### 4. 보장 위치표

| 규칙 | 지키는 자리 | 방법 |
| --- | --- | --- |
| r2 GH-02 저장 | 수신 처리 | 받으면 `(sensor_id, seq)`로 중복을 거른 뒤 넣음 |
| r3 GH-03 고온 | 판정 과정(센서마다 상태를 가짐) | 이상값이 아닌 값을 `measured_at` 순서로 보며 연속 수를 셈 |
| r4 GH-04 끊김 | 주기 작업(30초마다) | 센서마다 마지막 `measured_at`이 3분 넘게 지났는지 |
| r5 GH-05 다시 보내기 | 주기 작업 | 미확인 경보의 마지막 발송이 30분 지났으면 다시 |
| r10 GH-10 이상값 | 수신 처리 + DB | 범위 밖이면 `is_outlier = true`로 넣음. 판정 과정은 `is_outlier` 인 값을 건너뜀 |
| r11 GH-11 보관 | 운영 작업(매월 1일) | 90일이 지난 파티션 분리·삭제 |
| r12 GH-12 평균·보관 | 집계 작업(5분마다) + 운영 작업 | 지난 5분 평균 저장. 늦게 온 값이 있으면 그 버킷 다시 계산 |

r3·r4·r5에 DB가 없는 것을 보세요. 18장에서 본 대로 DB 제약은 값이 바뀔 때만 검사하고, 시각이 지나는 것만으로는 아무 일도 하지 않습니다. "3분 동안 들어오지 않으면"이나 "30분마다"는 시각이 지나야 성립하는 규칙이라 주기 작업이 맡아요. GH-03은 값이 들어올 때 판정하지만, 앞의 값 네 개를 기억해야 하므로 센서마다 상태를 가진 판정 과정이 맡습니다.

#### 5. 경보 계산

`verification/p07-greenhouse.py`가 낸 결과와 손 계산이 같습니다.

```text
시각   값     35.0 초과?   연속 수
10:00  34.8   아니오        0
10:01  35.2   예            1
10:02  35.6   예            2
10:03  36.0   예            3
10:04  34.9   아니오        0      ← 다시 0부터
10:05  35.3   예            1
10:06  35.4   예            2
10:07  35.8   예            3
10:08  36.1   예            4
10:09  36.4   예            5      → 고온 경보 (연속 10:05~10:09)
10:10  36.2   예            6      (이미 경보 중. 새 경보 아님)
10:11  -
10:12  -
10:13  -                           → 마지막 수신 10:10 에서 3분 → 센서 끊김 경보
10:14  -
10:15  35.9
```

10:01~10:03에서 세 번 연속 넘었지만 10:04에 34.9로 내려가 0으로 돌아갔어요. 그래서 고온 경보는 10:09에 납니다. 10:10의 36.2는 연속 6회째인데, 이미 같은 경보가 났으므로 새 경보를 내지 않고 GH-05의 다시 보내기 규칙을 따릅니다. 이 처리는 문장에 없으니 q6("경보가 난 뒤 조건이 계속되면 새 경보인가")으로 확인해요.

끊겼던 10:11~10:14 값이 10:16에 한꺼번에 도착한다면 두 가지가 달라집니다. 먼저 10:13에 이미 센서 끊김 경보가 나갔는데 사실 센서는 값을 재고 있었어요. 끊긴 것은 센서가 아니라 게이트웨이와의 연결이었던 거예요. 경보 이름과 뜻을 "수신 끊김"으로 바로잡거나, 늦게 들어온 값으로 경보를 자동으로 닫는 규칙이 필요합니다. 그리고 늦게 온 값이 35.0을 넘었다면 연속 수가 10:15까지 이어지므로, 판정 과정은 `measured_at` 순서로 다시 세야 해요. 다만 고온 경보는 이미 10:09에 났으니 결과는 바뀌지 않습니다. 반대로 10:09 이전에 끊김이 있었다면, 늦게 온 값 때문에 고온 경보 시각이 **과거로** 정해질 수 있어요. E2의 `triggeredAt`과 실제 발송 시각을 따로 두는 이유입니다.

#### 다른 답이 가능한 곳

- 측정값 키를 `(sensor_id, seq)`로 두고 `measured_at`을 일반 열로 두는 설계도 맞습니다. 다만 월 분할을 하려면 기본 키에 분할 키가 들어가야 하므로, 분할하지 않을 때 더 자연스러워요.
- 분할하지 않고 매일 밤 오래된 행을 지우는 설계도 가능합니다. 규모가 작다면 단순하지만, 하루 51,840행씩 지우는 작업이 표를 흩뜨리고 정리 작업을 늘립니다.
- 시계열 전용 저장소를 쓰는 선택도 있습니다. 그때도 E1 계약, 보장 위치표, 5분 평균을 저장하는 이유는 그대로 적어야 해요.

#### 흔한 실수

- GH-03의 연속을 도착 순서로 세는 것.
- 중복 거르기를 `(sensor_id, measured_at)`로만 하는 것. 센서 시계가 틀어져 같은 시각을 두 번 보내면 다른 값이 겹쳐 버립니다. `seq`가 있으면 그것으로 거릅니다(q4로 `seq`의 뜻을 확인).
- 5분 평균을 파생 규칙으로만 두고 저장하지 않는 것. 90일 뒤에 원천이 사라집니다.
- GH-04·GH-05를 DB 트리거로 지키려는 것.
- 행 크기를 확인 없이 적어 규모를 단정하는 것.
