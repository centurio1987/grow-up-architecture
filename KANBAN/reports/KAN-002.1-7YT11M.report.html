이 카드가 무엇을 끝내려는가

이 글은 칸반 카드 KAN-002.1-7YT11M 을 처음 보시는 분께 드리는 계획 리포트예요. 번호의 KAN-002.1 은 상위 카드 KAN-002 아래 첫 번째 하위 카드라는 뜻이고, 뒤의 7YT11M 은 번호가 겹쳐도 카드를 구별해 주는 고유 문자 여섯 자입니다. 아래에서는 KAN-002.1 로 줄여 부를게요. 상위 카드 KAN-002-4FZX1V 는 새 가이드 계열 「시스템 설계 사례 가이드」 전체를 맡은 루트 카드(부모 없이 맨 위에 있는 카드)입니다. 다 읽고 나면 이 카드가 무엇을 바꾸는지와 어떤 순서로 가는지를 알고, 두 수행안 가운데 하나를 고르실 수 있어요.

지금은 새 계열의 원고를 둘 폴더 이름만 정해져 있습니다. 그 폴더에 원고를 넣어도 확인되는 것이 아직 없어요. 검사기(원고가 규칙대로 쓰였는지 기계로 확인하는 도구 scripts/check-guides.py)가 그 폴더를 모르고, 알려 주더라도 대조할 명세(가이드 한 편이 어떤 절을 어떤 순서로 갖고 절마다 무엇을 써야 하는지 정한 규칙 문서)가 없기 때문입니다. 이 카드가 끝나면 그 폴더에 넣은 원고도 기존 가이드 37편처럼 절 구성과 코드까지 기계로 확인받습니다.

질문: 구현 코드는 TypeScript 한 언어 + 메모리 대역으로 실행 검증하는 방식으로 갈까요? 답변: 세 언어 유지

질문: 저장 위치를 pattern-guide/system-design-guide/, 명세 id 를 system-design-guide 로 할까요? 답변: 그렇게 해

「세 언어 유지」라는 답은 이 카드에 할 일 하나를 남깁니다. 새 계열도 구현 예시를 Java · TypeScript · Rust 세 언어로 싣고 세 언어가 같은 출력을 내야 하니, 명세에 그 규칙이 들어가고 검사기가 세 언어 코드를 컴파일해 실행까지 해 봐야 해요. 그래서 이 카드는 새 폴더의 원고에서 그 검사가 실제로 실행되는 것을 보고 나서야 끝납니다.

무엇이 되면 끝인가

끝났는지는 사람이 판정하지 않고 아래 명령으로 확인해요. 카드 실행 문서(카드마다 전략 · 계획 · 검증을 적어 두는 문서 KANBAN/cards/KAN-002.1-7YT11M.md)의 「검증」 절을 그대로 옮긴 것이라, 저장소 루트에서 복사해 실행하면 됩니다.

PLUGIN=~/.claude/plugins/marketplaces/centurio87-plugins/plugins/authoring-kit
python3 $PLUGIN/scripts/authoring.py lock && python3 $PLUGIN/scripts/authoring.py validate --all
python3 $PLUGIN/scripts/authoring.py resolve --voice ppangtolab-teacher --spec system-design-guide --profile main --frozen
python3 scripts/check-guides.py --all > "$TMPDIR/after.txt"; diff "$TMPDIR/before.txt" "$TMPDIR/after.txt"   # 등록 전 결과(before)와 같아야 한다
python3 scripts/check-guides.py --all --compile --run pattern-guide/system-design-guide/<시험 슬러그>/<시험 슬러그>-guide_v0.0.1.md
  • lock 과 validate --all — 판본 기록(authoring.lock.json, 규칙 파일들의 판본을 고정해 둔 기록)이 지금 규칙 파일과 어긋나지 않는지, 모든 명세가 형식에 맞는지 확인합니다.
  • resolve … --frozen — 새 명세와 문체 규칙을 합쳐 집필 규칙 한 벌을 만들어 봅니다. 판본 기록과 다르면 실패하는 옵션이 붙어 있어요.
  • check-guides.py --all 과 diff — 기존 가이드 전부를 다시 검사해 등록 전 결과와 차이가 있는지 봅니다.
  • --all --compile --run — 시험 초안(검사기를 확인하려고 새 폴더에 잠깐 두었다가 지우는 원고)을 절 구성부터 세 언어 실행까지 검사합니다.

여기서 가장 중요한 줄은 diff 가 있는 줄이에요. before.txt 는 S4 가 등록하기 전에 같은 명령으로 저장해 둔 결과입니다. S4 는 이 카드의 마지막 work 인 등록 마감이고, work 는 실행 문서에서 S1 처럼 번호가 붙는 작업 단위예요. 이 줄에서 차이가 나오면 새 명세 때문에 기존 가이드 37편 가운데 어느 편의 검사 결과가 바뀌었다는 뜻이에요. 그대로 두면 발행된 가이드가 아무 알림 없이 실패 상태로 남습니다.

S4 등록 전   check-guides.py --all --▶ before.txt -+
S4 등록 후   check-guides.py --all --▶ after.txt  ---▶ diff
                                         차이 없음 → 등록을 유지
                                         차이 있음 → 등록을 되돌림

사람이 판정할 항목은 없습니다. 명세에 들어갈 절 구성과 규칙은 준비안(이 계열을 어떻게 쓸지 미리 정리한 문서 pattern-guide/research/system-design-guide-plan-2026-11-13.md)의 3절이 이미 정했어요. 그 대응이 빠짐없는지는 위 명령과, S1(명세 본문을 쓰는 첫 work)이 만드는 대응표로 확인합니다.

왜 이 길인가

왜 이 접근인가

명세의 내용은 이 카드에서 새로 정하지 않아요. 준비안 3절에 한 편의 절 구성 표 · 절마다 지킬 규칙 · 기존 규약에서 가져올 것과 뺄 것이 있고, 5절에 유저와 정한 네 가지가 있습니다. 비교 기준이 되는 기존 명세는 gof-guide 1.4.0 이에요. 이 카드가 고르는 것은 그 내용을 어떤 모양으로 등록하느냐이고, 이 선택은 유저께 따로 여쭙지 않고 아래 이유로 정했습니다.

하나는 절 이름을 뜻이 같으면 기존 것 그대로 쓰는 일이에요. 명세는 절마다 절 id(기계가 읽는 고유 표시)와 헤딩 문구를 정해 두는데, 검사기는 그중 일부를 보고 검사를 켭니다. 시나리오 검사는 절 id detail.scenario 가 있을 때만 켜지고, 세 언어 컴파일 · 실행 검사는 헤딩 「구현」을 찾아 켜져요. 그래서 시나리오 절은 기존 id 를, 구현 절은 기존 헤딩 문구를 그대로 씁니다. 상황 설정 · 실제 사례 · 스스로 점검 · 참고 자료의 기존 id 도 물려받는데, 검사 때문이 아니라 두 계열에서 같은 뜻의 절을 같은 이름으로 부르려는 것이에요. 새 id 는 요구사항 · 규모 추정 · 개념도 · 기술 상세 설명 · 대안 비교 · 요구 충족 확인 표처럼 이 계열에만 있는 절에만 붙입니다.

명세에 정해 두는 것                        검사기가 켜는 검사
절 id  detail.scenario  (시나리오)  --▶  시나리오 개수 · 단계 수
헤딩   「구현」           (구현)      --▶  세 언어 컴파일 · 실행
새로 붙인 id            (요구사항 등) --▶  연결된 기존 검사 없음

버린 대안이 바로 이 반대였어요. 절 이름을 전부 새로 지으면 시나리오 검사와 세 언어 실행 검사가 꺼진 채로 시작합니다. 다시 켜려면 검사기를 고쳐야 하는데 그 일은 이 카드 범위 밖이라, 「세 언어 유지」라는 답을 기계로 확인할 방법이 그동안 없어져요. 물려받는 길에도 대가는 있습니다. 기존 id 에 붙은 검사의 전제까지 함께 오는데, 그 전제가 이 계열과 맞지 않을 때의 일은 「막힐 만한 지점」에서 다룹니다.

다른 하나는 공유 블록에 합류하지 않는 일이에요. 기존 명세 둘(gof-guide 와 analysis-guide)은 공통 규칙 덩어리를 바이트 하나까지 똑같이 두고, 검사기가 둘이 같은지 따로 검사합니다(--spec-shared). 새 명세까지 여기 들어가면 규칙 하나를 고칠 때마다 파일 세 개를 함께 고쳐야 해요. 그래서 필요한 규칙만 골라, 출처인 기존 원칙 번호(PG 번호)를 달아 옮겨 적습니다.

공유 블록에 합류하면 (버린 길)            옮겨 적으면 (고른 길)
gof-guide            +                   gof-guide            + 공유 블록
analysis-guide       | 바이트까지 같음    analysis-guide       + (지금처럼 둘)
system-design-guide  +                   system-design-guide
                                           필요한 규칙만 + 출처 PG 번호
공통 규칙 하나 수정 → 파일 셋 수정         공통 규칙 하나 수정 → 파일 둘 수정

이 길이 내주는 것도 있습니다. 원래 규칙이 바뀌어도 옮겨 적은 쪽은 저절로 따라오지 않아요. 출처 번호가 붙어 있어서 어느 규칙에서 왔는지 찾아갈 수 있을 뿐이고, 따라 고칠지는 그때 따로 정해야 합니다.

나머지는 바로 정해지는 것이에요. 문체(voice, 말투와 설명 장치를 정한 규칙 묶음)는 기존 가이드와 같은 ppangtolab-teacher 이고, 캔버스(집필할 때 채워 넣는 빈 틀)는 기존 캔버스 옆에 둡니다. 집필을 시작하는 입구를 기존 design-pattern-guide 스킬에 붙일지 새 스킬로 만들지는 이 카드에서 정하지 않아요. 같은 상위 카드의 두 번째 하위 카드 KAN-002.2 를 착수할 때 정합니다.

새 폴더 줄을 먼저 넣으면 (버린 길)
paths.json 의 트랙 목록
  system-design-guide 폴더 --▶ system-design-guide 명세   (명세 파일은 아직 없음)
          |
          |  그 폴더에 원고 파일이 하나 생기면
          ▼
검사기: 「spec 이 없습니다」 --▶ 그 자리에서 멈춤

버린 대안이 하나 더 있었어요. 경로 설정 파일(.claude/authoring/paths.json, 폴더마다 어느 명세로 검사할지와 캔버스 위치를 적어 둔 파일)에 새 폴더 줄을 먼저 넣는 길입니다. 이 줄을 트랙이라고 부르는데, 명세 없이 트랙만 있으면 그 폴더에 파일이 생기는 순간 검사기가 위 그림처럼 멈춰요. 그래서 트랙 줄은 명세와 캔버스가 다 갖춰진 뒤 마지막 work 에서 넣습니다.

명세가 먼저, 트랙 줄은 맨 끝.

어떤 순서로

무엇을 어떤 순서로

위 첫 그림은 work 넷이 배치 둘에 어떻게 나뉘는지를 보여 줘요. 배치는 한 세션이 끝까지 해낼 수 있게 work 를 묶은 단위이고, 크기 기준은 시간이 아니라 work 개수(배치당 2개)입니다. 배치 1 에 명세 본문(S1)과 기계 판독 파일(S2), 배치 2 에 캔버스(S3)와 등록 마감(S4)이 들어 있고 네 칸 모두 아직 시작 전이에요. 그림에 없는 것은 이 차례의 이유입니다. 뒤 work 는 앞 work 의 결정을 한 글자도 바꾸지 않고 옮겨 받아요.

S1 은 사람이 읽는 명세 본문(spec.md)을 씁니다. 준비안 3절 표의 절이 전부 명세 절로 대응하고, 기존 규칙을 옮긴 자리마다 출처 원칙 번호가 붙으면 끝이에요. S2 는 그 본문을 검사기와 집필 도구가 읽는 파일(spec.json · template.slots.json)로 옮깁니다. 형식 검사가 통과하고 절 id 가 본문과 하나씩 맞아야 끝나요. S3 은 캔버스를 쓰는데, 헤딩이 S2 의 절 목록과 같고 빈칸 검사(lint_placeholders.py)가 통과하면 끝입니다.

S4 의 시험 초안 (확인한 뒤 지우고, 커밋에 남기지 않음)
pattern-guide/system-design-guide/<시험 슬러그>/<시험 슬러그>-guide_v0.0.1.md
  |- 빠진 필수 절이 있으면    --▶ 오류가 나야 정상
  +- 세 언어 코드 블록        --▶ 컴파일되고 실행되어야 정상

S4 는 등록을 마감해요. 경로 설정 파일에 트랙 줄과 캔버스 위치 줄을 더하고 판본 기록을 갱신한 뒤, 최소 내용과 세 언어 코드만 담은 시험 초안으로 검사기가 명세대로 동작하는지 봅니다. 확인이 끝나면 시험 초안은 지웁니다. 기존 37편의 검사 결과가 등록 전과 같아야 한다는 조건도 이 work 에 붙어 있어요.

잠깐, 확인 하나만 해 볼까요? S2 를 마쳤는데 spec.json 의 원칙 번호 하나가 spec.md 본문의 괄호 번호와 다르다면 S2 는 끝난 걸까요? 끝나지 않았어요. 배치 1 문서가 적은 S2 의 완료 기준이 그 번호가 하나도 어긋나지 않는 것이라, S2 를 다시 해야 합니다. 차례가 이렇게 맞물려 있어서 이 카드에는 동시에 진행할 수 있는 work 가 없어요.

두 가지 수행안

위 두 번째 그림은 두 수행안의 배치를 나란히 놓은 것이에요. 단일 에이전트는 에이전트 하나가 work 를 차례로 하는 방식이고, 오케스트레이션은 메인 에이전트가 워커(일을 나눠 맡는 보조 에이전트)를 띄워 work 를 맡기는 방식입니다. 이 카드에서는 두 안 모두 배치가 둘이고, 배치 안의 차례도 어느 쪽이든 S1 다음 S2, S3 다음 S4 입니다. 여기서 헷갈리기 쉬운 포인트는 오케스트레이션을 고르면 work 가 동시에 진행된다고 읽는 것입니다. 워커를 여럿 띄워도 S2 는 S1 의 결과가 나와야 시작할 수 있어서, 이 카드에서는 동시에 진행되는 work 가 생기지 않아요.

단일 에이전트

에이전트 하나가 배치 1 의 S1 과 S2 를 차례로 하고, 이어서 배치 2 의 S3 과 S4 를 합니다. 배치는 둘이고 동시에 진행되는 work 는 없어요. work 마다 완료 기준을 확인하는 일도 그 에이전트가 work 를 닫을 때 직접 합니다.

얻는 것은 S1 에서 정한 절 id 와 원칙 번호를, 정한 쪽이 그대로 S2 와 S3 으로 옮긴다는 점이에요. 번호를 넘겨주는 단계가 없어서 어긋날 틈이 작습니다. 내주는 것은 쓴 쪽이 자기 결과를 스스로 확인한다는 점이에요. 다른 에이전트가 처음 보는 눈으로 결과를 읽는 단계가 없습니다. 위험은 배치 문서가 낮음으로 적었어요. 한 에이전트가 같은 명세 파일을 처음부터 끝까지 다루기 때문입니다.

오케스트레이션

메인 에이전트가 work 마다 워커를 하나씩 띄웁니다. S1 워커가 명세 본문을 쓰면 메인이 완료 기준을 확인하고, 그 결과를 S2 워커에게 넘겨요. 배치는 둘이고 동시에 진행되는 work 는 없습니다.

얻는 것은 쓴 쪽과 확인하는 쪽이 나뉜다는 점이에요. 메인은 결과를 직접 쓰지 않았으므로 완료 기준을 처음 보는 눈으로 확인합니다. 내주는 것은 S1 에서 정한 절 id 와 원칙 번호를 다른 워커가 받아 옮긴다는 점이에요. 워커는 앞 대화의 맥락을 이어받지 않아서, 메인이 앞 결과를 빠짐없이 넘겨야 합니다. 위험은 배치 문서가 짚었어요. 같은 명세 파일을 두 워커가 따로 다루면 원칙 번호를 서로 다르게 매길 수 있습니다.

추천

추천은 단일 에이전트예요. 오케스트레이션을 쓰는 보통의 이유인 동시 진행이 이 카드에서는 생기지 않고, 번호를 넘겨주는 단계의 위험만 남기 때문입니다. 배치 문서 두 편도 같은 이유로 단일 에이전트를 추천했어요. 오케스트레이션을 고르셔도 배치 수와 차례는 같습니다. 달라지는 것은 메인이 S2 결과의 원칙 번호를 S1 본문과 한 번 더 대조하게 된다는 점이에요. 쓴 쪽과 확인하는 쪽을 나누는 일을 더 중히 여기시면 오케스트레이션이 맞는 선택입니다.

막힐 만한 지점

루트 독립성

위 그림은 루트 독립성 맵이에요. 루트 카드는 저마다 자기 브랜치에서 나란히 진행되므로, 범위(카드가 건드릴 파일 경로 목록)가 겹치는 루트가 둘 있으면 같은 파일을 두 브랜치가 따로 고치게 됩니다. 그래서 착수 전에 겹치는 루트가 있는지 확인해요. 결과는 겹침 없음입니다. 아직 끝나지 않은 루트 카드가 이 카드의 상위 카드 KAN-002-4FZX1V 하나뿐이라 비교할 상대가 없고, 독립성 검사의 겹침 목록도 비어 있어요. 완료된 루트 카드는 브랜치가 이미 병합돼 나란히 진행될 일이 없으므로 비교 대상에서 빠집니다(manage-kanban 스킬의 scripts/kanban.py:5465-5473).

착수한 뒤 여쭐 수 있는 자리

진행하다가 유저께 여쭙고 멈출 수 있는 자리는 두 곳이에요. 하나는 S4 에서 고칠 두 파일, 경로 설정 파일(paths.json)과 판본 기록(authoring.lock.json)입니다. 두 파일에는 다른 작업이 고쳐 두고 아직 커밋하지 않은 수정이 이미 있어요. 그대로 S4 를 커밋하면 아래처럼 됩니다.

paths.json · authoring.lock.json 의 바뀐 내용
  |- 다른 작업이 고쳐 둔 것   (아직 커밋 안 됨)
  +- S4 가 더할 것           (트랙 · 캔버스 줄, 새 명세의 판본 항목)
          |  함께 커밋하면
          ▼
S4 커밋 하나에 두 수정이 섞임 --▶ S4 를 되돌리면 남의 수정도 함께 되돌아감

그래서 S4 는 커밋하기 전에 그 수정이 따로 커밋됐는지 확인하고, 아니면 처분을 여쭙고 멈춰요. 착수 전에 그 작업의 수정을 먼저 커밋해 두시면 이 질문은 생기지 않습니다. 판본 기록에는 확인할 것이 하나 더 있어요. 기록을 갱신하면서 기존 명세의 지문(내용이 바뀌었는지 알아보는 값)까지 바뀌면, 이미 발행된 가이드의 게이트 기록(편마다 품질 채점을 통과했다고 남긴 기록)과 어긋납니다. 새 명세를 더하는 것만으로는 기존 지문이 바뀌지 않아야 하므로, S4 에서 갱신 전후의 기존 지문을 비교해요.

다른 하나는 물려받은 이름에 따라오는 검사의 전제예요. 시나리오 절이 그 예입니다. 기존 규칙의 시나리오 3 「경계를 넘을 때」는 패턴의 규칙을 어기는 경우를 뜻해요.

기존 패턴 가이드                       이 계열
시나리오 3 「경계를 넘을 때」    --▶   시나리오 3 「장애가 날 때」
  패턴의 규칙을 어기는 경우              뜻을 바꿔 옮기고, 바꾼 자리를 대응표에 적음

S1 은 이렇게 뜻을 바꿔 옮기고, 이 계열에 걸리지 않았으면 하는 검사가 있으면 적어 두었다가 S4 의 시험 초안에서 확인해요. 그래도 시험 초안이 이 계열과 맞지 않는 오류를 내면 검사기를 고쳐야 하는데, 그 일은 이 카드 범위 밖입니다. 그때는 여쭌 뒤 별도 work 로 뺍니다.

되돌리는 자리와 예산

여쭙지 않고 되돌리는 자리도 하나 있어요. 「무엇이 되면 끝인가」의 diff 줄이 잡는 경우이고, 그때 S4 는 등록을 되돌립니다.

예산을 넘길 지점은 배치 문서가 따로 짚지 않았습니다. 두 배치 모두 work 가 기준인 2개로 차 있어요. 배치를 착수할 때 그 배치의 마지막 work 를 뒤로 미룰지는 수행하는 쪽이 그 자리에서 정해 기록합니다(배치 문서 4항 「착수 시점 판단」). 되돌리기 어려운 지점은 없습니다. 배치 1 이 만드는 것은 새 명세 폴더 안의 파일뿐이고 아직 아무 데서도 읽지 않아요. 배치 2 도 S4 가 더한 두 줄(트랙 · 캔버스 위치)과 판본 기록 항목을 빼고 S3 의 캔버스 파일을 지우면 등록 전으로 돌아갑니다. 다만 S4 커밋에 남의 수정이 섞이면 이 되돌리기가 남의 수정까지 건드리게 돼요. 커밋 전에 그 수정을 확인하는 일은 되돌리기 쉬운 상태를 지키는 일이기도 합니다.

스스로 점검하기

트랙 줄을 S1 보다 먼저 넣고, 명세가 아직 없는 상태에서 시험 초안을 새 폴더에 두면 어떻게 될까요? 검사기가 「spec 이 없습니다」로 멈춰서 시험 초안을 검사하지 못해요. 그래서 시험 초안은 명세 · 캔버스 · 트랙 줄이 다 갖춰진 S4 에서만 둡니다.

착수 전에 paths.json 과 authoring.lock.json 에 있던 다른 작업의 수정이 이미 커밋돼 있다면, S4 에서 유저께 여쭐 일이 생길까요? 생기지 않습니다. S4 가 커밋 전에 확인하는 것이 바로 그 수정의 커밋 여부이고, 이미 커밋됐다면 S4 커밋에는 이 카드가 더한 수정만 들어가요.

「전략」 원문 펼치기

입력: 준비안 pattern-guide/research/system-design-guide-plan-2026-11-13.md 의 3절(한 편의 절 구성 표 · 절마다 지킬 규칙 · 기존 규약에서 가져올 것과 뺄 것)과 5절(정한 것 넷 — 구현 코드는 Java · TypeScript · Rust 세 언어가 같은 출력을 내는 기존 규약 유지, 위치 pattern-guide/system-design-guide/<슬러그>/, 명세 id system-design-guide, 파일럿 두 편). 기존 명세는 gof-guide 1.4.0 이다.

절 이름은 뜻이 같으면 기존 것을 그대로 쓴다. 검사기가 명세의 절 id 에 묶어 켜는 검사는 시나리오 검사(개수 · 단계 수)다(scripts/check-guides.py:1086, 커밋 e2384dd 기준 — 작업 트리의 검사기는 다른 작업이 고치는 중이라 줄 번호가 움직인다). 세 언어 컴파일 · 실행은 절 id 가 아니라 ### 구현 헤딩 문구로 찾는다(:133 · :1289). 그래서 시나리오 절은 기존 id detail.scenario 를, 구현 절은 기존 헤딩 문구 「구현」을 그대로 쓴다. 나머지 기존 id(example.context · example.impl · example.realworld · selfcheck · refs)는 검사 때문이 아니라 같은 뜻의 절을 두 계열에서 같은 이름으로 부르려고 물려받는다. 상황 설정 표 검사는 분석 패턴 트랙에서만 켜지므로(:1071) example.context 를 물려받아도 이 명세에는 걸리지 않는다. 요구사항 · 규모 추정 · 개념도 · 기술 상세 설명 · 대안 비교 · 요구 충족 확인 표만 새 id 를 쓴다.

공유 블록에 합류하지 않는다. gof-guide 와 analysis-guide 는 공통 규칙 덩어리를 바이트 단위로 같게 두고 --spec-shared 로 검사한다. 셋째 명세가 들어가면 규칙 하나를 고칠 때 세 파일을 함께 고쳐야 한다. 필요한 규칙은 출처 원칙 번호(PG 번호)를 달아 옮겨 적는다.

문체(voice)는 기존 가이드와 같은 ppangtolab-teacher 다. 캔버스는 기존 캔버스 옆(.claude/skills/design-pattern-guide/system-design-guide-canvas.md)에 둔다. 집필 진입을 기존 design-pattern-guide 스킬에 붙일지 새 스킬로 할지는 KAN-002.2 착수 때 정한다.
