# KAN-001-YXTC2C 계획 리포트 — 전체 가이드 재집필

## 이 카드가 끝나면 무엇이 달라지는가

이 글은 칸반 카드 KAN-001-YXTC2C(부모가 없는 최상위 카드라 루트 카드라고 부릅니다)를 처음 보는 분을 위해 썼어요. 다 읽으면 이 카드가 무엇을 바꾸는지와 하위 카드 여섯 장(KAN-001.1부터 KAN-001.6까지, 이 글에서는 .1~.6으로 줄입니다)이 어떤 순서로 도는지를 알고, 두 수행안 중 하나를 고를 수 있습니다. 카드는 지금 진행 중 열에 있어요. work(실행 문서에서 `S1`처럼 번호가 붙는 작업 단위)로 치면 하위 카드 .1~.3은 검토 열에서 유저 판단을 기다리고, .4~.6은 아직 시작 전이에요.

끝나면 달라지는 것은 `pattern-guide/` 아래 패턴 가이드 33편의 골격이에요. GoF(Gang of Four, 『Design Patterns』 저자 넷을 가리키는 관용 표기) 23편과 DDD(Domain-Driven Design, 도메인 주도 설계) 분석 패턴 10편이 같은 명세를 지나 처음부터 다시 쓰입니다. 지금 33편은 9절 템플릿으로 균질하지만, 요청서가 요구한 네 요소 중 셋을 담을 절이 없어요. 개념 전수 정의 · 절차 전수 · 경계와 불변식 비교, 이 셋입니다.

```text
지금 (33편 · 9절 템플릿)                카드 완료 후 (spec 2종의 새 골격)
┌───────────────────────────┐         ┌──────────────────────────────────┐
│ 어떨 때 사용하나            │         │ ## 한눈에 보는 개요                 │
│ 장점과 단점, 한계점         │         │ ## 패턴 자세히 들여다보기            │
│ 정보 표 (활용성 별점)       │  ───▶   │    ### 등장하는 개념과 정의         │
│ Class Diagram             │         │    ### 동작 절차                   │
│ …                         │         │ ## 사용 목적                       │
│                           │         │ ## 패턴의 경계                     │
│ 없음: 개념 전수 정의         │         │    ### 최소 조건 [필수]/[선택]      │
│ 없음: 절차 전수             │         │    ### 비슷한 패턴·안티패턴과의 차이  │
│ 없음: 경계·불변식·차이 비교   │         │ ## 구현 예시 (java → ts → rust)    │
└───────────────────────────┘         │ ## 스스로 점검하기 · ## 참고 자료     │
                                      └──────────────────────────────────┘
```

분석 패턴 쪽은 더 구체적으로 달라져요. 지금 10편은 aggregate(DDD에서 일관성 경계를 이루는 객체 묶음)의 경계를 정하지 않은 채 경계를 암시하는 코드를 싣습니다. 끝난 뒤에는 편마다 상황 설정 표가 먼저 오고, 구현 코드가 그 표와 1:1로 맞아야 해요. 예시 코드는 Java · TypeScript · Rust 세 언어로 실리고 블록마다 컴파일 검사를 지납니다.

루트 독립성부터 말씀드릴게요. 보드에 루트 카드가 이 한 장뿐이라 범위를 비교할 상대가 없습니다. 그래서 확인된 겹침은 없어요. 근거는 독립성 검사 결과가 비어 있고 검사 대상 루트가 이 카드 하나뿐이라는 사실이에요.

## 왜 골격 교체이고 왜 파일럿이 먼저인가

보강으로 끝낼 수 없는 이유는 빠진 절이 셋이기 때문이에요. 절이 없는 자리에 문장을 더하면 편마다 형태가 갈라지고 기준 문서로 쓸 수 없게 됩니다. 그래서 골격을 바꾸고, 규칙의 정본을 스킬 문서 산문에서 authoring-kit(집필 규칙을 층으로 두고 검증하는 플러그인)의 spec(글 종류별 명세)으로 옮겨요. 33편이 같은 게이트를 지나게 하려는 것입니다.

spec은 둘로 갈랐어요. GoF용 `gof-guide`와 분석 패턴용 `analysis-guide`예요. 하나로 합치면 분석 패턴에만 필수인 조건(DDD 준수 · 배경 전제)이 GoF 쪽에서 선택 조건으로 약해지고, 집필 워커가 생략을 스스로 판단하게 됩니다. 최소 조건을 판정하는 기준도 달라요. GoF는 코드 구조를 보고 분석 패턴은 개념적 책임 분리를 봅니다. 버린 대안은 spec 하나에 조건부 절을 두는 것과 spec 셋이었어요.

```text
 규약             파일럿 3편           회고                 확장 30편
 (.2)     ──▶     (.3 S1~S3)    ──▶   (.3 S4)      ──▶     (.4 · .5)
 spec 1.0         Strategy            spec 1.1             GoF 22편
 lock 생성         Account             배치 크기             분석 8편
                  Quantity            실측 확정             같은 게이트 통과
```

순서가 규약 → 파일럿 → 회고 → 확장인 이유는 이래요. 명세는 산출물이 지나가기 전까지 추정이에요. 추정이 틀렸을 때 30편을 이미 썼다면 30편을 고쳐야 하고, 3편만 썼다면 3편과 명세만 고치면 됩니다. 그래서 파일럿 3편(.3)이 확장 30편(.4와 .5)보다 앞에 와요. 계승 대상인 `~/code_test`가 자료구조 가이드를 다시 쓸 때 밟은 선례(그 저장소의 지시 문서 번호로 ORD-006)를 그대로 따른 순서입니다.

> 명세는 산출물로 검증되기 전엔 추정이다. 추정으로 30편을 쓰지 않는다.

```text
Strategy ──▶ gof-guide      : 비교 쌍 State가 분명한 GoF 대표
Account  ──▶ analysis-guide : 회계 배경 확정안을 처음 인용하는 aggregate 편
Quantity ──▶ analysis-guide : 값 객체에서 「상황 설정」 표가 비는지 실측
```

3편을 고른 근거도 각각 있어요. Strategy는 비교 쌍 State가 분명한 GoF 대표이고, Account는 회계 배경 확정안을 실제로 인용해 보는 첫 편이에요. Quantity는 값 객체 계열이라 분석 spec의 상황 설정 표가 값 객체에서도 뜻이 있는지 여기서 실측합니다. 표가 비거나 값이 뻔하면 회고에서 그 표를 조건부로 내리거나 갈래별로 나눠요.

## 하위 카드 여섯 장이 맡는 일과 그 순서

루트의 work 6개는 하위 카드 6장과 하나씩 대응해요. 루트 work S1이 곧 하위 카드 .1이고, 그 카드가 완료 열로 옮겨지는 것이 루트 work의 완료 기준입니다. 하위 카드 안의 work를 다 더하면 48개예요(4 + 6 + 4 + 22 + 9 + 3). 여섯 장은 엄격히 순차입니다.

```text
루트 배치1                                  루트 배치2
.1 리서치·후보 조사                           .4 GoF 22편 재집필
   │ 노트 4건 · 확정안 · 유저 결정 4건             │ 편마다 work 1
   ▼                                           ▼
.2 authoring-kit 정착                        .5 분석 패턴 8편 재집필
   │ spec 2종 · lock · 게이트 · 검사기             │ 회계 3편은 같은 확정안 인용
   ▼                                           ▼
.3 파일럿 3편과 회고          ─────────▶     .6 인덱스 · stale 정리 · 최종 검증
   spec 1.1 · 배치 크기 확정                      HTML 33편 · 검토서
```

앞 세 장은 쓰기 전 준비예요. .1은 33편이 공유할 리서치 노트 4건과 추가 패턴 후보 보고서, 회계 배경 확정안을 만들어 유저 결정 4건을 받습니다. .2는 spec 2종과 lock(규칙 파일의 판본을 고정한 기록), 이해 게이트 · 검사기 · HTML 렌더러 · 진입 스킬을 갖춰요. .3은 그 위에서 3편을 써 보고, 회고에서 spec을 1.1로 고치고 배치 크기를 실측으로 정합니다.

뒤 세 장이 본체예요. .4는 GoF 22편, .5는 분석 패턴 8편을 씁니다. 편마다 work 하나이고, 착수할 때 `resolve --frozen`(규칙 층을 병합하는 명령 `resolve`를 lock과 어긋나면 실패하는 옵션으로 실행)이 통과해야 써요. .6은 인덱스 3종을 새 경로로 맞추고(PATTERNS.md의 GoF 링크 23개가 전부 옛 경로를 가리켜요) HTML 33편을 한 번에 렌더한 뒤, 루트 검증 전부를 돌려 검토서를 냅니다.

편 하나가 지나는 길은 아래 그림이에요. `check-guides`는 .2가 만드는 가이드 검사기(구조 · 컴파일 · 링크를 봅니다)이고, `gate-results.jsonl`은 편마다 게이트 결과를 한 줄씩 쌓는 기록 파일입니다.

```text
편 하나 = work 하나
resolve --frozen ──▶ 집필 ──▶ 이해 게이트 ──▶ 품질 게이트 ──▶ check-guides ──▶ gate-results.jsonl
(lock 불일치면 중단)            (종료코드 0)     (라운드 ≤ 3)     (--all --compile 0)   (1줄 기록)
```

여기서 헷갈리기 쉬운 포인트는 .4 · .5 · .6의 배치 문서가 .1~.3보다 한참 늦게 생겼다는 점이에요. 빠뜨린 게 아닙니다. 배치 크기를 .3 회고에서 실측으로 정했으니, 그 전에 만들면 근거 없는 크기로 자르게 돼요. 그래서 .3의 마지막 work(S4 회고)가 크기를 정하고 세 카드의 배치 문서를 만들었습니다.

## 두 가지 수행안 — 단일 에이전트와 오케스트레이션

공통 전제부터요. 배치는 한 세션이 끝까지 갈 수 있게 work를 묶은 단위이고, "배치 하나 = 세션 예산의 절반"은 work 개수로 정한 기준이에요. 시간 기준이 아닙니다. 기준은 .3 회고가 실측으로 확정한 배치당 work 2개예요(.1~.3은 확정 전 크기로 이미 돌았어요). 루트 배치는 두 안 모두 2개입니다. 배치1(루트 배치 문서 `KAN-001-YXTC2C.batch1.md`)이 .1~.3, 배치2가 .4~.6이에요.

**단일 에이전트(순차)**는 에이전트 하나가 하위 카드 순서대로 세션을 이어요. 하위 배치 합계는 23개입니다(.1 하나, .2 둘, .3 둘, .4 열하나, .5 다섯, .6 둘). 병렬 폭은 1이고 동시 실행은 없어요. 세션 예산 절반 지점에서 배치를 끊고 다음 세션이 이어받습니다. 리스크는 배치가 가장 많은 .4에 몰려요. 배치 종료 3종(실행 문서에 work 완료를 체크하는 `doc-step done` · 되돌아갈 지점을 남기는 git 태그 · 커밋) 중 하나가 빠지면 다음 세션이 diff부터 다시 읽습니다. 얻는 것은 같은 파일을 두 손이 만질 일이 없고, 비교 쌍 가이드를 한 손이 이어 써서 교차 확인이 자연히 된다는 점이에요. 잃는 것은 .4의 22편이 11배치로 순서대로 이어져 카드 하나의 배치가 가장 길게 늘어선다는 점입니다.

```text
단일 에이전트 (.4의 예)                     오케스트레이션 (.4의 예)

b1: S1 S2 S3   → 커밋·태그 → 다음 세션       메인 ─┬─ 워커 A: S1 (Factory Method)
b2: S4 S5 S6   → 커밋·태그 → 다음 세션            ├─ 워커 B: S2 (Abstract Factory)
 ⋮  (절반 지점에서 끊음)                          └─ 워커 C: S3 (Builder)
b7: S19 … S22  → 커밋·태그                   워커는 커밋 안 함 · 파일 겹침 0
                                             메인이 S1→S2→S3 순으로 doc-step done → 커밋 → 태그
                                             배치 끝에 비교 쌍 교차 확인
```

**오케스트레이션(병렬 서브에이전트)**은 메인 에이전트가 하위 카드 안에서 워커 여럿을 동시에 띄워요. 하위 배치 합계는 단일 에이전트와 같은 23개입니다(.1 하나, .2 둘, .3 둘, .4 열하나, .5 다섯, .6 둘). 병렬 폭은 .1이 4, .2의 배치2가 3, .4와 .5가 2이고 .3과 .6은 순차예요. 동시 실행분의 합은 예산 절반 이내로 둡니다. 리스크는 외부 모델 호출에 몰려요. 폭 4에 편당 외부 호출 2회면 동시 8회라 호출 한도에 걸릴 수 있고, 같은 파일을 두 워커가 만지면 충돌합니다. 얻는 것은 .4·.5의 한 배치 안 두 편이 동시에 돌아 기다리는 시간이 줄고, .1 리서치가 소주제 넷으로 나뉘어 한 번에 돈다는 점이에요. 잃는 것은 비교 쌍이 서로의 최종 문장을 못 보니 배치 끝에 메인이 교차 확인해야 하고, 워커는 커밋하지 않으니 메인이 work 순서대로 doc-step done → 커밋 → 태그를 대신 밟아야 한다는 점입니다.

추천은 오케스트레이션이에요. 배치 수는 두 안이 23개로 같지만, .4의 22편과 .5의 8편은 파일이 서로 겹치지 않아 한 배치 안 두 편을 동시에 돌리는 이득이 실제로 있는 자리입니다. 폭은 .3 파일럿이 외부 호출 한도를 실측한 뒤 2로 정했어요. 단일 에이전트를 골라도 되돌리기 규율은 같습니다. 어느 안이든 커밋과 태그는 메인이 work 순서대로 남기니까요.

```text
.1 회계 확정안 ──▶ .2 analysis-guide spec ──▶ .3 파일럿 (그 파이프라인 위에서만)
                                                    │
                                          spec 1.1 · 배치 크기 확정
                                                    ▼
                                    .4 GoF 22편 ──▶ .5 분석 8편 ──▶ .6 (33편이 다 있어야 뜻이 있음)
```

여기서 헷갈리기 쉬운 포인트는 오케스트레이션이 하위 카드 사이도 병렬로 돌린다고 읽는 것이에요. 그렇지 않습니다. .2의 분석 spec에는 .1의 회계 확정안이 들어가야 하고, .3은 .2가 갖춘 파이프라인 위에서만 돌며, .4와 .5는 .3이 고친 spec 1.1로 씁니다. 카드 사이 의존이 이렇게 한 줄이라 어느 안에서도 여섯 장은 순차예요.

> 카드 사이는 줄, 카드 안은 폭.

## 막힐 만한 지점

예산을 넘길 지점은 두 곳이에요. 하나는 .4입니다. 편당 예시 코드가 세 언어라 코드 분량이 전보다 3배이고, 파일럿 세 편이 모두 3라운드를 다 써서 회고가 크기를 2로 내렸어요. 그래서 .4는 11배치예요. 또 하나는 외부 모델 호출 한도예요. 파일럿 세 편 × 3라운드 뒤 codex 한도에 걸렸으니, 한 한도 창에서 크기 2 배치를 두 개 넘게 돌리지 않습니다.

```text
.3 회고의 배치 크기(batch_size_works) 실측
        ├─ 크기 3 유지  ──▶ .4 = 7배치 (3·3·3·3·3·3·4)
        └─ 크기 2로 하향 ──▶ .4 = 11배치   ◀ 채택
```

오케스트레이션이면 한 곳이 더 있어요. 폭 4에 편당 외부 호출 2회면 동시 8회라 외부 모델의 호출 한도에 걸릴 수 있습니다. 그래서 .3에서 실측한 폭을 넘기지 않아요.

되돌리기 어려운 지점은 세 곳이에요. 같은 경로에 덮어쓰는 결정이 하나예요. 파일명이 analyzer(사용자 코드가 패턴에 맞는지 판정하는 기존 스킬 `design-pattern-analyzer`)와 인덱스의 키라서 경로를 바꿀 수 없고, 옛 문장은 복사하지 않습니다. 대신 작업은 루트 워크트리(같은 저장소를 별도 디렉토리에 체크아웃한 작업 공간)에 격리돼 main에는 섞여 보이지 않고, work마다 태그가 남아 그 지점으로 돌아갈 수 있어요.

```text
main ──────────────────────────────────────────── (재집필 중엔 변화 없음)
  └─ 워크트리 KAN-001-YXTC2C
       S1 ──tag──▶ S2 ──tag──▶ S3 ──tag──▶ …       되돌릴 때는 태그 지점으로
       (덮어쓴 33편은 여기에만 있음)                    (경로는 그대로, 내용만 복구)
```

다음은 `lock --update`예요. 규칙 판본을 바꾸는 명령이라 .3 회고 한 자리에서만, 사유를 커밋에 적고 실행합니다. 마지막은 .6의 stale(현 상태와 어긋난 낡은 것) 처분이에요. 4언어 실행 하니스와 `analysis/`는 기본이 유지 + README 표 개정이고, 삭제는 별도 카드로 뺍니다. 삭제는 되돌리기 어렵고 범위가 늘기 때문이에요.

루트 독립성은 첫 절에서 말씀드린 대로 확인된 겹침이 없어요. 루트가 한 장이라 비교 상대가 없기 때문입니다. 대신 카드 밖에서 막힐 것이 둘 있어요. 이해 게이트와 외부 검토는 외부 모델 도구 둘(codex · agy)의 로그인에 묶여 있어서, 미로그인이면 .3에서 어떤 편도 게이트를 통과(PASS)하지 못합니다. 종료코드 2는 통과가 아니에요. 그리고 .1의 유저 결정 4건이 늦으면 .2의 분석 spec이 확정안 없이 만들어져요. 그래서 .1은 확정안과 후보 보고서를 먼저 내밀고, 답을 기다리는 동안 나머지 노트를 씁니다.

## 무엇이 되면 끝인가 — 검증 세 층

검증은 세 층이에요. 결정론적 명령(전부 종료코드 0), work 단위로만 도는 외부 모델 호출, 사람만 판정하는 7건. 실행 위치는 루트 워크트리이고, `PLUGIN`은 authoring-kit 0.3.0의 캐시 경로예요.

```text

2. work 단위 (외부 모델 호출)   comprehension-gate.sh · review-external.sh     편마다 종료코드 0
```
