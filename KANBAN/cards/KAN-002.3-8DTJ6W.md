## 전략
**입력**: 카드 브리프(목적 · 이유 · 목표), 루트 카드 `KAN-002-4FZX1V` 의 전략과 실행 계획(S3 의 완료 기준은 인덱스에 이 계열을 싣는 것), 파일럿 회고 `pattern-guide/research/system-design-pilot-retro-2026-11-15.md` 8절(차례와 집필 전 확인), `KAN-002.2` 검토의 판정 다섯(2026-11-16 문서 전체 승인). 편마다 쓸 출처는 사례 목록 `pattern-guide/research/system-design-cases-2026-11-13.md` 2절의 그 행에서 시작한다. 명세는 `system-design-guide` 1.1.1 이고, 형식의 기준 예시는 두 파일럿 v1.1.0 이다.

**차례는 회고 8절을 그대로 쓴다.** 작은 결정적 시뮬레이션에 맞는 편이 앞이다. IN-01 처리율 제한 → CT-05 결제 · 송금 중복 방지 → CT-03 좌석 선점 → RT-03 대형 그룹 채팅 → AG-03 광고 클릭 집계 → RD-01 타임라인 → RT-08 알림 발송 → AI-01 LLM 채팅 → GE-02 승차 공유 배차 순이고, 시뮬레이션이 어려운 셋(SY-01 실시간 공동 편집 · MD-01 동영상 업로드와 인코딩 · AI-02 RAG)이 맨 뒤다. 앞 편들은 파일럿의 코드 틀(가상 시계 · 사건 순서로 재현하는 경합 · Redis 판정)을 이어 쓴다.

**어려운 셋의 집필 전 확인은 첫 편보다 먼저 한다(S2).** 2026-11-16 `KAN-002.2` 검토에서 유저가 정했다. 각 편 직전에 확인하면 명세가 그 셋에 맞지 않는다는 사실을 아홉 편을 낸 뒤에 알게 되고, 그때 명세를 고치면 아홉 편을 다시 판올림해야 한다. 확인은 편마다 한 언어(TypeScript)로 시험 코드를 써서 세 가지를 본다. 핵심 동작이 사건 순서만으로 결정적으로 재현되는가, 시나리오 셋(기본 · 부하 · 장애, SD9)을 만들 수 있는가, 펜스 하나가 300줄 안에 드는가(SD28)다. 파일럿 1 첫 초안에서 Rust 가 TypeScript 보다 67줄 길었으므로(343 · 276줄, 회고 123행) TypeScript 가 233줄을 넘으면 Rust 로도 잰다. 시험 코드와 결과는 `pattern-guide/research/system-design-precheck-<쓰는 날>.md` 와 같은 이름의 폴더에 커밋해, 다른 세션이 이어받아도 같은 결과를 보게 한다.

**확인을 통과하지 못한 편이 나오면 멈추고 묻는다.** 그 문제를 사례 목록의 같은 계열 2차 후보로 바꿀지 명세(구현 코드 규약)를 고칠지는 확인 결과에 달린 선택이라, 2026-11-16 에 미리 정하지 않았다. 그때 확인 결과를 근거로 두 길을 함께 든다.

**명세는 첫 편 전에 한 번만 고친다(S3).** 명세를 고치면 해석 해시가 바뀌어 발행한 편의 게이트 PASS 가 모두 낡고(`check-guides --gates` 의 「낡은 PASS」), 판본을 올리면 머리말 `spec_version` 이 다른 최신본이 오류가 된다(`scripts/check-guides.py:1157`). 지금은 두 파일럿만 판올림하면 되지만, 12편을 쓴 뒤에는 열네 편이다. S3 에서 고칠 것은 원칙 표의 SD26 칸과 S2 결과가 요구하는 것이다. SD26 칸(`spec.md:366`)은 아직 「결정성 네 규칙」이고 본문(`spec.md:199`)과 `spec.json` 은 다섯 규칙이다. 집필 워커가 읽는 해석 결과에 표와 본문이 함께 실리므로, 그대로 두면 워커가 두 수를 함께 읽는다. 고치면 두 파일럿을 v1.1.1 로 내고 앞 판을 `legacy` 로 바꾼 뒤 게이트를 다시 거친다. 고칠 것이 없으면 S3 은 보류로 둔다. S3 뒤로는 명세를 고정하고(정할 것 2), 쓰다가 나온 명세 문제는 S28 노트에 근거와 함께 쌓는다.

**진입 스킬을 먼저 손본다(S1).** 고칠 곳은 둘이다. 하나는 플러그인 판이다. `.claude/skills/design-pattern-guide/SKILL.md:63` 은 `CLAUDE_PLUGIN_ROOT` 가 있으면 그 판을 먼저 쓴다. 그래서 0.4.2 플러그인 환경에서는 0.4.2 만 보는 다섯 항목 때문에 lock 검사에서 멈춘다(`KAN-002.2` 검토 5번). lock 에 적힌 판(0.3.0)을 쓰게 고친다. 다른 하나는 인덱스다. 같은 스킬 40행이 「이 계열의 인덱스는 카드 `KAN-002.3` 에서 세운다」며 등록을 막아 두었다. 이 계열의 인덱스를 `pattern-guide/system-design-guide/README.md` 로 새로 세워 두 파일럿을 싣고, `.claude/authoring/paths.json` 의 `dirs.index` 목록에 더한다. 그리고 각 편이 발행하면서 제 줄을 넣게 스킬을 고친다. 분석 패턴 계열도 GoF 인덱스(`PATTERNS.md`)와 따로 제 README 를 인덱스로 둔다.

**한 편은 work 둘이다.** 리서치 노트와 집필 · 발행이다. 노트는 사례 목록 그 행의 출처에서 시작해, 파일럿 노트와 같은 절 구성(요구 · 규모 추정 · 개념도와 기술 · 시나리오 · 대안 · 실제 사례 · 구현 메모 · 미해결 질문 · 원문 대조 · 출처)으로 `pattern-guide/research/system-design-<슬러그>-<쓰는 날>.md` 에 쓴다. 파일럿 때는 원문 대조를 집필 단계에서 따로 했고, 그 대조에서 빈틈 셋(V2 의 18M · 80M 충돌, C3 21% 의 뜻, C8 의 90초가 두 뜻)이 늦게 나왔다. 그래서 원문 대조표를 노트 work 의 완료 기준에 넣는다. 집필 · 발행은 `design-pattern-guide` 스킬 절차(사전 확인 → 집필 위임 → 기계 검사 · 품질 게이트 → 발행 · 게이트 기록 · 인덱스)를 그대로 쓴다. 슬러그는 노트 work 에서 정하고, 실행 계획에는 가칭을 적었다.

**마지막은 정리다(S28).** 12편의 펜스 줄 수, 게이트 라운드, S3 뒤 쌓은 명세 문제를 한 노트에 모은다. 명세 개정은 이 카드에서 하지 않고, 그 노트가 다음 개정의 입력이 된다. 카드 이유 칸이 말한 「후속 53건이 따를 예시」가 이 12편과 그 노트다.
