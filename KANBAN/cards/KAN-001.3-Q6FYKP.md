# KAN-001.3-Q6FYKP — 파일럿 3편과 회고

## 전략
<!-- 왜 이 접근인가 · 제약 · 버린 대안. 사람이 자유롭게 편집한다. -->
**루트 요청서 인용**: 가이드 구성 4요소(직관적 개요 / 개념 전수 정의·절차 전수 / 경계·불변식 + 유사 패턴·안티패턴 차이 비교 / 구체적 배경을 전제한 구현 예시, 분석 패턴은 DDD 원칙 준수).

**왜 파일럿인가.** 명세는 산출물로 검증되기 전엔 추정이다(code_test ORD-006 선례: 규약 → 파일럿 → 회고 → 확장). 30편을 틀린 명세로 쓰면 되돌리는 비용이 크다.

**왜 이 3편인가.** Strategy = GoF 대표(비교 쌍 State가 명확). Account = 회계 aggregate 계열(배경 확정안을 실제로 인용해 보는 첫 편). Quantity = 값 객체 계열 — `analysis-guide`의 `상황 설정` MUST 표(root·entity·VO 배정 / 타 aggregate 참조)가 값 객체에서 공회전하는지는 Account만으로 못 본다. 비거나 자명하면 회고에서 `IF-APPLICABLE`로 내리거나 갈래별 표로 나눈다.

**유저 승인 게이트 2건**(S2 완료 시, GoF·분석 한 편씩 본 뒤): ① 존댓말 voice(단정체 → `ppangtolab-teacher`는 33편 톤 변경) ② HTML 탭 화면. 거부 시 voice는 spec `voice.default` 한 줄 교체.

**회고(S4)에서 정하는 것**: spec 1.1(파일럿에서 드러난 결함 되먹임) · voice params(`max_prose_run=2`가 mermaid·코드·표를 끊는 것으로 세는지) · `batch_size_works` 실측(편당 코드가 3언어라 2가 될 수 있다) · `paths.json.exemplars` 3건 · `lock --update`와 사유 커밋 · 파일럿 3편 `resolve --frozen` 재통과 + 재검사 · **.4·.5·.6의 `batch-init`을 확정 크기로 생성**.

### 배치 2관점

- **단일 에이전트(순차)** — 배치: b1 S1–S2 / b2 S3–S4 / 비고: b1 「4. 착수 시점 판단」에서 S1 실측을 보고 S2를 같은 배치에 둘지 정한다
- **오케스트레이션(병렬)** — 배치: **순차 유지** / 비고: 실측이 목적이라 병렬로 돌리면 배치 크기 근거를 잃는다
