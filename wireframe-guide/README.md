# 와이어프레임 명세 가이드

> 한 줄 요약: 와이어프레임은 "그림"이 아니라 **디자인과 개발 사이의 계약서**다. 화면 구조 + 데이터 바인딩 + 상태 + 행동(커맨드)을 한 문서에 담고, 시각 스타일은 일부러 뺀다.
>
> 예시: [`wireframe-spec-example.html`](wireframe-spec-example.html) — 복식부기 "거래 등록" 화면 (도메인 모델은 [Transaction-Account-Entry 모델링](../pattern-guide/consideration/account-transaction-entry-modeling.md)을 따른다)

---

## 1. 좋은 와이어프레임 명세의 구성

| # | 섹션 | 담는 것 | 주 독자 |
| --- | --- | --- | --- |
| 0 | 머리말 | 화면 ID, 에픽·시나리오 ID, 스키마 버전, 리뷰 상태, 입력물·산출물 | 모두 |
| 1 | 읽는 법 | 범례: 회색 = 구조, 색 = 주석, `Entity.attr` = 바인딩 | 모두 |
| 2 | 흐름과 목적 | 진입·이탈 화면, 성공 지표 | 기획·디자인 |
| 3 | 개념 스키마 발췌 | 이 화면이 읽고 쓰는 엔티티·속성·불변식·상태 모델, **UI와 모델이 다른 곳** | 개발 |
| 4 | 와이어프레임 + 번호 주석 | Lo-fi 화면, 상태 전환(빈·입력·오류·진행·완료·권한 없음), 데스크톱/모바일 | 모두 |
| 5 | 데이터 바인딩 표 | UI 요소 ↔ 스키마 속성 ↔ 타입·제약 ↔ 필수 ↔ 기본값 ↔ 요청/응답/파생 | 개발 |
| 6 | 상태 매트릭스 + 규칙 | 영역 × 상태 표, BR별 클라이언트/서버 검증 위치 | 개발·QA |
| 7 | 인터랙션과 커맨드 | 트리거 → 동작 → 커맨드/API → 성공 → 실패 | 개발 |
| 8 | 수용 기준 + 미결정 사항 | Given/When/Then, 스키마로 되돌려 보낼 질문 | QA·기획 |
| 9 | 입력물 | 무엇을 받아 어디에 썼는지 | 기획 |
| 10 | 완료 기준 | 개발 착수 리뷰 전 체크리스트 | 모두 |

핵심 원칙 다섯 가지:

1. **모든 입력 칸은 스키마 속성 하나에 연결되거나 "파생/UI 전용"으로 표시한다.** 연결 안 되는 칸이 있으면 스키마가 빠졌거나 칸이 필요 없는 것이다.
2. **모든 버튼은 커맨드 하나 또는 화면 이동 하나에 연결한다.** 실패 응답(422/409/403…)이 어느 화면 요소로 돌아오는지까지 적는다.
3. **상태는 별도 화면이 아니라 한 화면의 변형으로 정의한다.** 빈·로딩·오류·성공·권한 없음이 빠지면 미완성이다.
4. **색·폰트·아이콘은 넣지 않는다.** 리뷰가 "무엇을 호출하나"에 머물게 하기 위해서다. 색은 주석에만 쓴다.
5. **와이어프레임은 스키마로 질문을 되돌려 보낸다.** 그리다 보면 "행 순서를 저장해야 하나?(→ `position` 필드)" 같은 질문이 반드시 나온다. 이 역류가 와이어프레임의 가장 큰 가치다.

## 2. 필요한 입력물

| 입력물 | 필수 | 없으면 생기는 일 |
| --- | --- | --- |
| 에픽 목표와 성공 지표 | 필수 | 화면이 무엇을 최적화해야 하는지 판단할 근거가 없다 |
| 시나리오 (주 흐름 · 대안 · 예외) | 필수 | 해피 패스만 그려지고 오류·빈 상태가 개발 중에 발견된다 |
| 개념 스키마 (엔티티 · 속성 · 타입 · 카디널리티 · 관계) | 필수 | 필드 누락, 타입 불일치가 API 설계 때 터진다 |
| 핵심 엔티티의 상태 모델 (생애주기) | 필수 | "수정 버튼이 언제 사라지나"를 아무도 답하지 못한다 |
| 비즈니스 규칙 · 불변식 | 필수 | 버튼이 왜 비활성인지 설명할 수 없다 |
| 역할 · 권한 매트릭스 | 필수 | 403이 빈 화면으로 나간다 |
| 커맨드 · 쿼리 목록 (API 초안 수준) | 권장 | 버튼이 무엇을 호출하는지 모른 채 그려진다 |
| 실제 데이터 표본 (값 범위, 최장 문자열, 최대 행 수) | 권장 | 레이아웃이 실제 데이터에서 깨진다 |
| 플랫폼 제약 (브레이크포인트, 접근성, 기존 컴포넌트 이름) | 권장 | 모바일 화면이 나중에 따로 발명된다 |
| 디자인 파운데이션 (그리드, 간격 단위) | 선택 | 없어도 된다. 있으면 프로토타입 전환이 빠르다 |

스타일 가이드(색, 타이포그래피, 아이콘)는 **입력물이 아니라 후행 산출물**이다. 와이어프레임의 컴포넌트 목록이 스타일 가이드의 입력이 된다.

## 3. 제안된 순서에 대한 의견

제안된 순서:

```
에픽 → 컨셉·시나리오 → UI 기획(스타일 가이드) + 프로토타입 → 개념 스키마 → 와이어프레임
```

### 동의하는 부분

- **에픽마다 컨셉과 시나리오를 먼저 정의하는 것**은 맞다. 시나리오가 없으면 와이어프레임은 해피 패스 하나만 그린 그림이 된다.
- **개념 스키마가 와이어프레임의 전제 조건**이라는 판단이 가장 중요한 통찰이다. 많은 팀이 이걸 거꾸로 해서(화면 먼저, 데이터 나중) 개발 단계에서 "이 칸은 어디에 저장하나요?"를 묻는다.

### 다르게 보는 부분

1. **스타일 가이드와 프로토타입은 와이어프레임 뒤에 와야 한다.** 충실도(fidelity)는 낮은 것에서 높은 것으로 올라가야 수정 비용이 싸다. 구조가 검증되기 전에 시각 스타일을 확정하면, 와이어프레임에서 구조가 바뀔 때 스타일 작업이 함께 버려진다. 또 프로토타입을 만들려면 레이아웃을 이미 정해야 하는데, 그 결정이 바로 와이어프레임의 일이다.
   - 예외 1: 시나리오 단계에서 컨셉 자체를 검증하려는 **종이·저충실도 컨셉 프로토타입**은 앞에 와도 좋다. 이건 버리는 것을 전제로 한다.
   - 예외 2: 스타일 가이드 중 **파운데이션**(그리드, 간격 단위, 밀도 원칙, 브랜드 톤)은 병행해도 된다. 컴포넌트 단위 스타일 가이드는 와이어프레임에서 나온 컴포넌트 목록을 받아 만든다.
2. **개념 스키마와 와이어프레임은 직렬이 아니라 왕복이다.** 스키마가 와이어프레임의 입력이지만, 와이어프레임을 그리면서 스키마의 빈틈이 드러난다(예시의 Q3: 행 순서 → `TransactionLeg.position`). "스키마 v0.x → 와이어프레임 → 스키마 v0.x+1"을 한두 번 돌리는 것을 일정에 넣는다.
3. **개념 스키마만으로는 부족하다.** 엔티티·속성·관계 외에 **상태 모델, 비즈니스 규칙, 권한, 커맨드 목록**이 함께 있어야 버튼의 활성 조건과 오류 화면을 그릴 수 있다. 정적 구조(스키마)와 동적 행동(상태·커맨드)을 둘 다 요구하자.

### 권장 순서

```
에픽(목표·지표)
  └▶ 컨셉 · 시나리오 (주 · 대안 · 예외)        ┐
       └▶ 개념 스키마 + 상태 모델 + 규칙 + 권한   │ 1~2회 왕복
            └▶ 와이어프레임 명세 (이 문서) ─────┘ → 스키마 변경 요청
                 ├▶ 클릭 프로토타입 (흐름·사용성 검증)
                 ├▶ API 계약 · 수용 기준 (개발·QA)
                 └▶ 컴포넌트 목록 → 스타일 가이드 → 하이파이 디자인
```

요약하면, 제안된 흐름에서 **"스타일 가이드 + 프로토타입"을 와이어프레임 뒤로 옮기고, 스키마 ↔ 와이어프레임 사이에 왕복 화살표를 추가**하면 된다.
