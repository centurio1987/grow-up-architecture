1읽는 법

회색은 구조만 뜻한다. 색이 들어간 것은 모두 주석이다. 와이어프레임에 색과 폰트를 넣지 않는 이유는 리뷰가 "이 버튼 색이 별로"로 흐르지 않고 "이 버튼은 무엇을 호출하나"에 머물게 하기 위해서다.

구조 요소 (시각 디자인 아님) 4주석 번호 · 오른쪽 목록과 연결 (마우스를 올려 보세요) Transaction.occurredOn개념 스키마 바인딩 BR-01비즈니스 규칙 (§6) SC-02-03시나리오

2화면 흐름과 목적

주 흐름 SC-02-01은 목록 → 등록 → 전기 → 상세다. 불균형 수정(SC-02-03)은 이 화면 안에서 끝나고, 전기된 거래의 취소(SC-02-04)는 수정이 아니라 상쇄 거래 등록으로 이어진다.

3개념 스키마 발췌

이 화면이 읽고 쓰는 부분만 옮겼다. 와이어프레임의 모든 입력 칸은 아래 속성 중 하나에 연결되거나 "파생/UI 전용"으로 표시된다.

Transaction                 «Aggregate Root» · 이 화면이 생성
  id            TransactionId       서버 발급 TX-YYYY-NNNNNN
  occurredOn    LocalDate           BR-05 마감일 이후
  description   String(1..100)
  memo          String(0..500)?
  status        Draft | Posted | Reversed
  legs          TransactionLeg[2..20]   BR-02
  reversalOf    TransactionId?      상쇄 거래일 때만
  불변식  Σ legs.amount = 0      BR-01 · post() 시점

TransactionLeg              «Value Object» · Transaction 내부
  accountId     AccountId           Account를 ID로만 참조
  amount        Money               + 차변 / − 대변

Account                     «Aggregate Root» · 이 화면은 읽기만
  id · code · name · isActive
  type          Asset | Liability | Equity | Revenue | Expense
  ledgers       AccountLedger[]     조회 모델로만 노출

Money                       «Value Object»
  value         Decimal(18,0)       KRW 정수
  currency      KRW                 BR-06 v1 단일 통화

상태 모델

Draftpost()→Postedreverse()→Reversed

Draft만 편집할 수 있다. Posted는 수정·삭제할 수 없고(BR-04), 되돌리려면 부호를 뒤집은 새 거래를 만든다.

UI와 모델이 다른 곳

화면은 차변·대변 두 칸, 모델은 부호 있는 amount 하나다. 회계 담당자에게 익숙한 표기를 지키되 변환 책임은 클라이언트 매퍼에 둔다. 이런 불일치를 명시하는 것이 와이어프레임 명세의 핵심 일이다.

애그리거트 경계

계정 미리보기(주석 9)는 Account 쪽 조회 모델이다. 전기 요청에는 accountId만 실려 가고, 잔액은 Account가 스스로 갱신한다.

4와이어프레임

상태를 바꿔 가며 같은 화면이 어떻게 달라지는지 확인한다. 상태마다 별도 화면을 그리지 않고, 한 화면의 변형으로 정의한다. 주석 번호에 마우스를 올리면 해당 설명이, 설명에 올리면 화면 요소가 강조된다.

8수용 기준과 미결정 사항

수용 기준은 QA가 그대로 테스트 케이스로 옮길 수 있는 문장으로 쓴다. 미결정 사항은 와이어프레임을 그리다가 발견해 기획·스키마로 되돌려 보내는 질문이다.

  1. AC-1GIVEN차변 합계 1,200,000원, 대변 합계 1,109,091원WHEN사용자가 분개를 입력하는 중THEN'전기하기'는 비활성이고 "차변이 90,909원 많습니다"가 보인다
  2. AC-2GIVEN균형이 맞는 초안WHEN'전기하기'를 누르고 서버가 200을 반환THEN상태가 전기됨으로 바뀌고 모든 입력이 읽기 전용이 되며 '상쇄 거래 만들기'가 나타난다
  3. AC-3GIVEN거래일이 마감된 2025-09-30WHEN전기를 요청THEN409 응답에 따라 상단 오류 요약과 거래일 칸 오류가 보이고 나머지 입력값은 유지된다
  4. AC-4GIVEN전기 요청이 진행 중WHEN사용자가 '전기하기'를 다시 누른다THEN요청은 한 번만 서버에 도달한다

9이 명세에 필요한 입력물

와이어프레임을 시작하기 전에 있어야 하는 것과, 없을 때 어디서 문제가 터지는지.

입력물이 문서에서 쓰인 곳없으면
에픽 목표와 성공 지표§2 목적, 클라이언트 선검증 결정화면이 무엇을 최적화해야 하는지 판단할 근거가 없다
시나리오 (주 · 대안 · 예외)§2 흐름, §4 상태 탭해피 패스만 그려지고 오류·빈 상태가 개발 중에 발견된다
개념 스키마 (엔티티 · 속성 · 타입 · 카디널리티 · 관계)§3, §5, 주석의 바인딩 줄필드 누락과 타입 불일치가 API 설계 때 터진다
상태 모델 (생애주기)상태 칩, 읽기 전용 규칙, 상쇄 흐름"수정 버튼이 언제 사라지나"를 아무도 답하지 못한다
비즈니스 규칙 · 불변식§6 BR 표, 비활성 조건과 이유 문구버튼이 왜 비활성인지 사용자에게 설명할 수 없다
역할 · 권한 매트릭스권한 없음 상태403이 빈 화면으로 나간다
커맨드 · 쿼리 목록 (API 초안 수준)§7 인터랙션 표버튼이 무엇을 호출하는지 모른 채 그려진다
실제 데이터 표본 (값 범위, 최장 문자열, 행 수)예시 값, 20행 제한, 금액 칸 폭레이아웃이 실제 데이터에서 깨진다

스타일 가이드(색, 타이포그래피, 아이콘)는 입력물이 아니다. 이 명세의 컴포넌트 목록이 스타일 가이드의 입력이 된다. 다만 그리드, 간격 단위, 기존 컴포넌트 이름 같은 파운데이션은 미리 있으면 좋다.

10완료 기준

이 체크리스트를 모두 채워야 개발 착수 리뷰에 올린다. 마지막 항목은 일부러 하지 않는 일이다.

  • 모든 입력 요소가 스키마 속성 하나에 연결되거나 "파생 · UI 전용"으로 표시됨
  • 모든 버튼이 커맨드/API 하나 또는 화면 이동 하나에 연결됨
  • 빈 · 로딩 · 오류 · 성공 · 권한 없음 상태가 정의됨
  • 각 규칙에 클라이언트와 서버의 검증 위치가 적힘
  • 모바일에서 달라지는 배치가 정의됨
  • 최장 문자열, 최대 행 수, 최대 금액으로 깨지지 않음을 확인
  • 수용 기준이 테스트 가능한 문장으로 쓰임
  • 미결정 사항마다 담당자가 있음
  • 색 · 폰트 · 아이콘 스타일을 정하지 않음 (스타일 가이드의 몫)
