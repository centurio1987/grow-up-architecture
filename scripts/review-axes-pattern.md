1) 패턴 정의의 정확성: 의도·participants·collaborations·최소 조건이 **원전과 어긋나는** 곳.
   GoF(Gamma 외, 1994)·Fowler(Analysis Patterns, 1996)·Evans(DDD, 2003) 중 해당 원전 기준으로,
   참여 역할을 빠뜨리거나 다른 패턴의 역할을 섞은 곳, `[필수]`여야 할 조건이 `[선택]`이거나 그 반대인 곳,
   원전에 없는 제약을 정의처럼 단정한 곳을 구체적으로. 원전 대조가 불확실하면 "추정"으로 표시.
2) 비교의 타당성: 비슷한 패턴·안티패턴과의 **구분 기준이 틀렸거나 독자를 오인으로 이끄는** 곳.
   두 패턴이 실제로는 같은 구조인데 다르다고 한 곳, 기준이 "의도가 다르다"뿐이라 코드에서 가를 수 없는 곳,
   오인 코드 예시가 실제로는 그 패턴을 충족하는 곳, 얻는 것·포기하는 것이 한쪽에만 적힌 곳.
3) 구현과 설명의 일치: 구현 코드가 **본문 설명·최소 조건과 다른** 곳.
   코드가 `[필수]` 조건 하나를 어기는데 본문은 충족한다고 한 곳, 절차 설명의 단계 순서와 코드 호출 순서가 다른 곳,
   클래스 다이어그램의 역할·관계가 코드와 다른 곳, Java·TypeScript·Rust 세 구현이 **서로 다른 상황이나 다른 구조**를
   구현한 곳(한 언어만 조건을 지키거나, 한 언어만 다른 참여 역할을 쓰는 등).
4) DDD 일관성(분석 패턴 가이드 전용): 「상황 설정」 표(bounded context · 불변식의 위치 · root/entity/VO 배정 ·
   다른 aggregate 참조 방식)와 **구현 코드의 경계·참조 방식이 어긋나는** 곳.
   표는 id 참조라 했는데 코드가 다른 aggregate를 객체로 들고 있는 곳, 불변식을 root가 아닌 곳에서 검사하거나
   root를 거치지 않고 child를 바꿀 수 있는 곳, 배경 전제와 다른 소유 관계를 코드가 암시하는 곳.
   GoF 계열 가이드(상황 설정 표가 없는 글)에는 이 축을 적용하지 말고 "4) 해당 없음"이라고 한 줄로만 답할 것.
