# 디자인 패턴 부합도 분석 Skill

이 skill 은 사용자가 작성한 코드를 읽고, 사용자가 의도한 디자인 패턴의 최소 충족 조건과 비교해 부합도를 판정한다.

산출물은 두 개다.
1. **채팅 요약** — 조건별 ✅/⚠️/❌ 와 종합 판정, 최우선 권장 조치 1~2개.
2. **분석 리포트 파일** — `analysis/<pattern>-<filename>-<YYYYMMDD-HHMM>.md` 에 풀 리포트 저장.

## 작성 절차

### 1. 입력 식별
- **대상 파일**: 사용자가 명시한 경로, 첨부 파일, 또는 `python/` `typescript/` `rust/` `java/` 안의 파일 중 사용자가 가리킨 것.
  - 경로 모호하면 `ls` 로 후보를 추려서 사용자에게 한 번 확인.
- **대상 패턴**: 사용자 메시지에서 추출. 명확하지 않으면 짧게 한 번 묻는다.
- **언어**: 파일 확장자로 판정 (`.py` `.ts` `.rs` `.java`). 그 외 확장자면 사용자에게 확인.

### 2. 평가 기준 로드 (우선순위 순)
1. **가이드 문서** — `pattern-guide/design-pattern-guide/<pattern>/<pattern>-guide_v<버전>.md` (`paths.json` 의 `dirs.content` · `dirs.tracks`) 가 있으면 그 문서의 **최소 조건 절**(아래 「최소 조건 절 찾기」)을 평가 기준으로 사용한다. (가장 우선)
   - `<pattern>` 은 영문 패턴명의 kebab-case 폴더다. Singleton → `singleton/`, Factory Method → `factory-method/`, Chain of Responsibility → `chain-of-responsibility/`. 폴더 안에 `<pattern>-guide_v<semver>.md` 가 여러 개면 **버전이 가장 높은 것**을 쓴다.
   - 머리말 `status: legacy` 인 파일은 구 골격이라 기준으로 쓰지 않는다 — 그런 경우 내장 checklist 로 내려간다.
2. **사용자가 제시한 기준 문서** — 그 문서의 최소 조건 절을 사용한다. 사용자가 기준 문서를 명시적으로 지정했으면 1보다 앞선다 — 지정했다는 것 자체가 기본 경로를 쓰지 말라는 뜻이다.
3. **내장 checklist** — 위 두 가지 모두 없으면 같은 폴더의 `checklist.md` 의 해당 패턴 항목을, 항목이 없으면 그 문서의 「그 외 패턴에 대한 일반 원칙」을 사용한다.

평가 기준의 출처(파일 경로 또는 "내장 checklist.md")를 리포트 메타에 반드시 명시한다. 사용자가 지정한 문서면 경로 뒤에 `(사용자 지정)` 을 붙인다.

**분석 패턴은 이 스킬의 판정 대상이 아니다.** `pattern-guide/ddd-analysis-pattern-guide/` (Account · Transaction · Quantity 등) 가이드의 최소 조건은 개념적 책임 분리와 모델 불변식을 기준으로 쓰여 있어, 코드 구조로 ✅/❌ 를 매길 수 없다. 사용자가 분석 패턴을 대면 그 사실을 알리고 멈춘다. `checklist.md` 의 일반 원칙으로 대신 판정하지 않는다.

#### 최소 조건 절 찾기
- 헤딩 레벨과 무관하게(`##` 또는 `###`) 헤딩 텍스트가 `디자인 패턴을 충족하는 최소 조건` 인 줄을 찾는다. 새 골격 가이드는 `### `(`## 패턴의 경계` 아래), 구 골격 가이드는 `## ` 다. `#` 로 시작하지 않는 줄(본문 속 언급·링크)은 헤딩이 아니다.
- 절은 **찾은 헤딩과 같거나 더 높은 레벨의 다음 헤딩** 직전에서 끝난다. `###` 로 찾았으면 다음 `###` 또는 `##` 가 끝이다.
- 조건은 그 절의 **최상위** 목록 항목이다(들여쓴 하위 항목은 그 조건의 설명이다). 절 안 하위 헤딩(예: 구 가이드의 `### 흔히 오해하는 지점`) 아래 목록은 조건이 아니다 — 판정 해설의 참고로만 쓴다.
- **절 안의 산문 문단도 읽는다.** 목록만 뽑고 문단을 버리면 저자가 절 안에 적어 둔 판정 지침을 통째로 놓친다. 특히 절 끝의 **채점 순서 문단**(「`[필수]` 는 하나만 빠져도 판정이 끝나므로 1번부터 차례로 봅니다…」로 시작한다 — GoF 최신본 24편 중 12편에 있다)에는 **어느 조건을 먼저 보면 빨리 끝나는지**와 **필수를 다 갖춰도 판정이 안 끝나는 경우**가 적혀 있다.
- 그 문단이 **「다만 필수 N 을 다 갖췄다고 판정이 끝나는 것은 아닙니다」** 라고 말하면 **5단계가 강제된다.** 이어지는 문장이 어느 패턴을 함께 보라는 지시이므로 그 패턴을 경쟁 후보에 넣는다. 예: Abstract Factory 편은 「쓰는 쪽이 생성 연산을 순서대로 부르며 결과를 쌓아 가는 모양이라면 비교 절의 기준으로 Builder 쪽인지 함께 봐야 해요」라고 적는다.

#### 비교 절 찾기 — 동시 통과를 가릴 때만 쓴다

헤딩 텍스트가 `비슷한 패턴·안티패턴과의 차이` 인 줄을 찾는다(새 골격 가이드는 `### `, `## 패턴의 경계` 아래). 절의 끝을 정하는 규칙은 최소 조건 절과 같다.

**이 절은 평가 기준이 아니다** — 조건별 채점에는 쓰지 않는다. 5단계에서 **동시 통과가 났을 때만** 꺼낸다. 구 골격 가이드나 `checklist.md` 에는 이 절이 없고, 그때는 5단계의 표만 쓴다.

#### 필수 / 선택 판별
1. **`[필수]` / `[선택]` 표기** — 각 조건 문구 앞(번호·불릿 기호와 굵게 표시 `**` 를 뺀 첫 토큰)의 `[필수]` / `[선택]` 표기를 따른다. 새 골격 가이드는 모든 조건에 이 표기가 있다. 표기가 있는 문서에 표기 없는 조건이 섞여 있으면 그 조건은 `[필수]` 로 보고, 리포트 메타에 표기 누락을 적는다.
2. **fallback — 표기가 하나도 없는 문서**(구 골격 가이드 · `checklist.md`) — 기존 규칙을 그대로 쓴다. 조건 문구의 `(선택)` 같은 표기를 따르고, 그런 표기도 없으면 첫 3개 조건을 필수로 본다. 이 fallback 을 썼으면 리포트 메타의 평가 기준 출처 옆에 적는다.

### 3. 정적 분석
Read 도구로 대상 파일을 읽고, 각 최소 조건마다 다음을 수행한다.

- **조건 진술**: 기준 문서의 원문을 그대로 인용.
- **판정**: ✅ 충족 / ⚠️ 부분 충족 / ❌ 미충족 / ❓ 판정 불가 — 4값 중 하나.
- **근거 인용**: 파일 경로 + 라인 범위 + 5~12 라인의 코드 발췌.
- **해설**: 왜 그렇게 판정했는지 1~3 문장. 미충족이면 무엇이 빠졌는지 구체적으로.

판정이 흔들리는 경우 (코드 단편만으로 판단이 어려움) 는 반드시 ❓ 로 처리하고 "판정 보류" 사유를 적는다. 추측으로 ❌ 를 남발하지 않는다.

추가로 `checklist.md` 의 **자동 시그널** 패턴(정규식·키워드)을 grep 으로 확인해 1차 시그널을 빠르게 잡는다. 단, 시그널 부재만으로 미충족 판정을 내리지 않는다 — 실제 코드 의미를 확인한다.

#### 조건이 말하는 참여자를 먼저 정하고, 조건마다 갈아 끼우지 않는다

조건은 「Adaptee」·「동료」·「서브시스템」처럼 **참여자를 가리키는 말**로 쓰여 있는데, **그것이 코드의 어느 클래스인지를 정하는 방법은 어느 문면에도 없다.** 그래서 가운데 클래스가 이웃을 여럿 들면 **조건마다 편한 이웃을 골라 대어 서로 배타적인 조건 둘을 동시에 만족시킬 수 있다.**

1. **먼저 참여자를 고정한다.** 조건을 하나라도 채점하기 전에, 그 패턴의 참여자 이름마다 **코드의 어느 클래스가 그것인지** 정하고 리포트에 적는다.
   - **감싸는 패턴**(Adapter·Decorator·Proxy)은 「Client 의 요청을 실제로 수행하는 대상」하나를 고른다. 찾는 방법은 Client 가 부르는 연산의 본문을 따라가 **반환값이 어디서 나오는지** 보는 것이다. `inner: Notifier`(Decorator 2번용)와 `legacy: LegacyStamper`(Adapter 3번용)를 함께 든 클래스 하나가 Adapter `[필수]` 넷과 Decorator `[필수]` 다섯을 모두 통과했다(2026-09-30 코드 확인).
   - **생성 패턴**(Factory Method·Abstract Factory·Builder·Prototype)은 **생성 연산을 선언한 타입**을 Creator·Factory 로 고정한다. 생성 연산과 제품을 쓰는 상위 로직이 **다른 타입에 갈라져 있는 코드**가 있고(2026-09-30 실측: `ReportKit` 이 생성 연산을, `ReportWriter` 가 상위 로직을 가졌다), 어느 쪽을 잡느냐에 따라 **경로가 갈린다** — 생성 연산 쪽을 잡으면 「상위 로직이 무엇을 하면 안 되는가」를 묻는 조건들이 「해당 없음」이 되어 5단계로 가고, 상위 로직 쪽을 잡으면 그 조건들이 ❌ 라 「패턴 아님」으로 즉시 끝난다. 생성 연산 쪽으로 고정하는 것은 그 조건들이 **Creator 를 두고 하는 말**이고 Creator 를 정하는 것은 생성 연산이기 때문이다.
   - **가운데 객체 패턴**(Mediator·Facade)은 가운데 클래스가 참조로 든 이웃을 **한 집합으로 본다.** 이웃을 「가운데를 아는 쪽」과 「모르는 쪽」으로 쪼개면 Facade 3번은 뒤쪽만 보고 참, Mediator 2번은 앞쪽만 보고 참이 된다 — 그 쪼개기 하나로 두 패턴이 동시에 통과했다(2026-09-30 코드 확인).
2. 고정한 뒤에는 **모든 조건을 그 집합에 대해** 읽는다. **조건마다 다른 참여자를 대는 판정은 무효다.** 조건이 「~가 A 를 모른다」이면 집합의 **전부**가 몰라야 하고, 「~가 A 를 안다」이면 집합의 **전부**가 알아야 한다. 일부만 그렇다면 그 조건은 ❌ 이고, 나뉘는 경계가 어디인지 리포트에 적는다.
3. 참여자로 안 고른 참조는 **「부차 참조」** 로 적고 무슨 일을 하는지 한 줄 쓴다. 부차 참조가 인터페이스 변환을 하고 있으면 그것은 **안쪽에 다른 패턴이 겹쳐 있다는 신호**다 — 두 패턴이 겹친 것이지 한 패턴의 조건을 두 번 만족한 것이 아니다. 그때는 겹친 사실을 그대로 보고한다.

#### 잴 대상이 없어서 참이 된 조건은 ✅ 가 아니라 「해당 없음」이다

조건 가운데 **「~하는 코드가 없습니다」** 꼴이 많다(예: Factory Method 3번 「제품을 쓰는 메서드 안에 구체 제품 클래스를 만드는 코드가 없고…」). 이런 조건은 **그 코드가 놓일 자리 자체가 없으면** 위반 사례가 없다는 이유로 참이 된다 — 논리학에서 말하는 공허한 참이다. 실제로 정통 Abstract Factory 의 구체 팩토리에는 제품을 쓰는 상위 로직이 아예 없어서 Factory Method 3·5번이 잴 것 없이 통과한다(2026-09-30 코드 확인). Factory Method 가이드의 비교 절도 「3번은 이 자리에서 잴 것이 없습니다」라고 같은 자리를 짚는다.

1. 조건이 금지하는 코드가 놓일 **자리 자체가 없으면** ✅ 가 아니라 **「해당 없음」** 으로 적는다. 자리가 있는데 위반이 없으면 그때가 ✅ 다. 둘을 가르는 물음은 「이 조건을 어길 수 있는 코드를 이 클래스에 넣을 수 있는가」이다.
2. **`[필수]` 에 「해당 없음」이 하나라도 있으면 그 패턴으로 확정하지 않는다.** 5단계 경쟁 후보 대조를 반드시 밟고, 대조가 안 갈리면 보류한다. 「위반 사례가 없다」를 「충족」으로 읽는 것이 다른 패턴의 코드를 이 패턴으로 올리는 가장 흔한 길이다.
3. 리포트의 그 조건 칸에 **왜 잴 대상이 없는지** 한 줄로 적는다(예: 「이 클래스에 제품을 쓰는 메서드가 없다」).

#### 선언된 타입이 아니라 가리키는 대상을 본다

조건이 「필드·인자에 그 추상 타입이 적혀 있다」처럼 **선언 모양**을 묻는 경우가 있다. 선언은 두 줄로 만들 수 있어서, 그대로 채점하면 **자기 자신을 그 타입의 필드에 담는 것만으로 통과**한다 — Factory Method 코드에 팩토리 인터페이스 선언과 `this` 를 담는 필드 두 줄을 더했더니 Abstract Factory `[필수]` 다섯이 전부 통과했다(2026-09-30 코드 확인).

그래서 선언을 확인한 뒤 **그 참조가 실행 중에 무엇을 가리키는지**까지 본다. 생성자·초기화 코드에서 그 필드에 무엇이 들어가는지 따라가, `this` 나 자기 자신이면 「별개 객체」를 요구하는 조건은 충족이 아니다. 따라갈 수 없으면 ❓ 이고, 리포트에 무엇을 못 따라갔는지 적는다.

#### 이름에 기대는 조건은 구조로 다시 읽는다

조건 문면이 **특정 식별자 이름의 유무**를 묻는 경우가 있다. 예컨대 Visitor 조건 3번은 「원소 클래스에는 그 연산의 이름이 없습니다」라고 적는다. 이름은 바꾸기가 쉬워서 문면 그대로 채점하면 **구조가 전혀 다른 코드가 이름만 맞춰 통과한다** — 실제로 Bridge 계열 `Shape.draw(DrawingApi)` 가 연산 이름을 `accept` 로 바꾸자 Visitor 의 `[필수]` 셋을 전부 통과했다(2026-09-29 확인).

1. 조건이 이름의 유무나 일치를 묻고 있으면 **이름 의존 조건**으로 표시하고, 리포트의 그 조건 칸에도 적는다.
2. 판정은 이름이 아니라 **그 이름이 가리키는 구조 관계**로 한다 — 누가 누구를 부르는지, 무엇이 어느 타입에 선언돼 있는지, 인자와 반환의 타입이 무엇인지. **이름이 달라도 구조가 같으면 충족**이고, **이름이 같아도 구조가 다르면 미충족**이다.
3. **타입 이름을 찾는 조건은 그 타입이 구현·상속한 타입까지 본다.** 「서브시스템 클래스의 필드·인자 어디에도 Facade 타입이 없다」 같은 조건은 가운데 클래스가 인터페이스를 하나 구현하고 이웃이 **그 인터페이스를 들면** 구체 클래스 이름이 코드 어디에도 안 나와 통과한다(2026-09-30 코드 확인). 두 가이드가 `[선택]` 으로 추상 중재자·추상 Facade 를 허용하므로 이 우회는 정당한 설계이기도 하다 — 그러므로 **이름이 아니라 그 이름이 가리키는 타입 계층 전체**로 찾는다.
4. 이름 의존 조건의 ✅ 는 **단독 근거로 쓰지 않는다.** 그것만으로 패턴을 확정하지 말고 같은 편의 다른 `[필수]` 조건이나 비교 절이 함께 받치는지 본다. 받치는 것이 없으면 ❓ 로 내리고 사유를 적는다.

### 4. (선택) 안전한 실행 검증

다음 조건이 **모두** 충족될 때만 코드를 실행한다.

- 파일이 자기-완결적 진입점을 가짐 (`if __name__ == "__main__"`, `main()`, `fn main()`, `public static void main`).
- 네트워크 호출, 파일 시스템 변경, 외부 명령(subprocess/exec) 호출이 없음.
- 프로젝트의 `Makefile` 에 해당 패턴/파일에 대응하는 타깃이 존재 (`make py PATTERN=...` 등).

실행은 **프로젝트 루트에서** 다음 명령을 사용한다. 경로를 절대 경로로 박지 않는다 — 이 레포는 워크트리마다 다른 자리에 체크아웃된다.
- Python: `make py PATTERN={module}`
- TypeScript: `make ts PATTERN={basename}`
- Rust: `make rs PATTERN={example_name}`
- Java: `make java PATTERN={ClassName}`

이 `make` 진입점은 **연습 하니스**(`python/` · `typescript/` · `rust/` · `java/`)의 것이다. 가이드 예시 코드는 편마다 그 폴더 안에 있고 `scripts/check-guides.py --compile --run` 이 따로 돌린다 — 분석 대상이 가이드 폴더의 파일이면 `Makefile` 타깃이 없으므로 실행 단계를 생략한다.

실행 출력은 리포트의 "테스트 / 동작 검증" 섹션에 발췌 첨부한다. 출력이 조건(예: Singleton 의 인스턴스 동일성)을 입증/반증하는지 한 줄로 결론짓는다.

위 조건 중 하나라도 안 맞으면 실행 단계를 생략하고 "정적 분석만 수행" 으로 표기한다.

### 5. 경쟁 후보 대조 — 동시 통과 검사

**최소 조건을 다 통과한 것은 「이 패턴이다」가 아니라 「이 패턴일 수 있다」이다.** 서로 다른 두 패턴이 같은 코드에서 `[필수]` 를 전부 만족하는 일이 실제로 있다. 두 패턴의 구조가 같다는 것은 **원전 수준의 사실**이라 조건 문면을 고쳐서는 못 푼다 — 문면을 좁히면 그 패턴의 정당한 변형이 탈락하고, 넓히면 남의 패턴이 들어온다.

이 검사를 안 하면 **먼저 물어본 쪽이 이긴다.** 사용자가 「이 코드 State 맞아?」라고 물으면 Strategy 코드가 State 로 승인되고, 「Strategy 맞아?」라고 물었으면 같은 코드가 Strategy 로 승인된다. 같은 코드에 두 답을 내주는 것이다.

`[필수]` 에 ❌·⚠️ 가 없을 때 이 단계를 밟는다 — **「해당 없음」이 섞여 있어도 밟는다.** 오히려 그때가 가장 위험하다(3단계 「잴 대상이 없어서 참이 된 조건」). 하나라도 ❌·⚠️ 면 그 패턴이 아니거나 변형이므로 대조할 것이 없다.

**1) 경쟁 후보를 세운다.**
- 기준 문서에 비교 절(2단계 「비교 절 찾기」)이 있으면 그 절이 이름을 대는 것 가운데 **채점할 최소 조건 절을 가진 발행된 편**이 후보다. 새 골격 가이드의 비교 절은 `**<이름> 와의 차이.** 구분 기준은 …입니다.` 꼴로 갈래를 열므로 그 굵은 머리에서 이름을 뽑고, 그 이름의 폴더가 있는지 2단계의 경로 규약으로 확인한다.
  > **「GoF 패턴」으로 한정하지 않는다**(2026-09-30 정정). 이 저장소에는 GoF 23편에 없으면서 최소 조건 절을 가진 발행본이 있다 — Specification·Dependency Injection·Null Object 가 그렇고, Specification 편은 스스로 「GoF 의 어느 칸에도 들어가지 않아요」라고 적는다. 「GoF 패턴만 후보」로 적으면 **배제 이유(「최소 조건 절을 갖지 않으므로」)가 그 셋에는 거짓**이 되어 규칙과 이유가 서로 다른 답을 낸다. 실제로 배제하려는 것은 안티패턴·관용구이므로, **배제 이유를 그대로 판정 기준으로 쓴다.**
- **채점할 최소 조건 절이 없는 갈래는 후보가 아니다.** 같은 절이 안티패턴·관용구와의 차이도 다룬다(예: 「열거형 + `switch` 와의 차이」 · 「통제 없는 위임 래퍼와의 차이」 · 「망라적 패턴 매칭과의 차이」). 그것들은 열어 채점할 문서가 없으므로 2)를 밟지 않는다 — 대신 **해설과 권장 조치에 쓴다.**
- 아래 「동시 통과가 확인된 쌍」 표에 이 패턴이 있으면 그 상대를 후보에 넣는다. 표에 있는 상대는 **비교 절이 이름을 안 대도** 반드시 본다.
- **비교 절이 이름을 안 대는 데는 이유가 있을 수 있다 — 발행 순서다.** 뒤에 나온 편은 앞 편을 이름 대지만 앞 편은 뒤 편을 댈 수 없다(앞 편이 발행될 때 뒤 편이 없었다). 그래서 **사용자가 댄 패턴보다 늦게 발행된 편 가운데 그 패턴을 비교 절에서 다루는 것이 있으면 그것도 후보다.** 「다룬다」는 **비교 절의 굵은 갈래 머리(`**<이름> 와의 차이.**`)에 그 이름이 있다**는 뜻이다 — 본문 어디에든 이름이 나오는 것으로 세면 안 된다(2026-09-30 실측: 굵은 머리로 세면 열 편, 본문 전체로 세면 열한 편으로 갈렸다). 찾는 방법은 인덱스(`dirs.index`)의 편들을 훑는 것이고 `date` 머리말로 발행 순서를 안다.
- 구 골격 가이드나 `checklist.md` 로 판정 중이면 비교 절이 없으므로 표만 쓴다.

**2) 후보의 `[필수]` 도 채점한다.** 후보 패턴의 가이드를 열어 2·3단계와 같은 방법으로 최소 조건 절을 읽고 같은 코드를 채점한다. 후보의 `[선택]` 은 안 본다.

**후보가 많아지는 것은 과잉이 아니라 사실이다.** 남들이 자주 대조 상대로 삼는 패턴일수록 후보가 많다 — 2026-09-30 실측에서 Strategy 로 물었을 때 후보가 **열 편**이었고 그중 넷이 실제로 동시 통과했다. 줄이지 말고 **값싼 것부터** 본다: ① 동시 통과 표에 오른 상대(갈리는 자리가 이미 적혀 있어 대조가 가장 싸다) → ② 사용자가 댄 패턴의 비교 절이 이름을 대는 편 → ③ 발행 순서 규칙으로 데려온 편. **조기 종료는 하지 않는다** — 뒤쪽 후보에서 동시 통과가 나온 것이 실측이다(넷 중 셋이 ③에서만 나왔다).

**후보 쪽 조건에도 3단계의 「해당 없음」이 그대로 적용된다.** 후보의 `[필수]` 에 ❌ 는 없고 「해당 없음」이 섞였으면, 그 후보는 **탈락이 아니라 「판정할 수 없음」** 이다. 4)로 떨어뜨리지 말고 3)의 비교 절 대조로 넘기되, 리포트에 **어느 조건을 왜 잴 수 없었는지** 적는다. 잴 수 없었다는 사실이 곧 그 후보가 아니라는 뜻은 아니다.

**3) 후보도 전부 ✅ 면 동시 통과다.** 사용자가 댄 패턴의 **비교 절**에서 그 후보를 다루는 문단을 찾아 거기 적힌 기준으로 가른다.

**거기서 못 찾으면 후보 쪽 비교 절도 본다.** 발행 순서 때문에 가르는 문장이 한쪽에만 있는 일이 있다 — 2026-09-30 실측에서 Strategy 편(2026-09-21 발행)이 Specification 을 이름 대지 못했고, 가르는 문장은 Specification 편(2026-09-30 발행) 쪽에만 있었다. 후보 쪽 문장을 쓸 때는 **어느 편의 어느 절에서 가져왔는지 리포트에 밝힌다.**
- 비교 절이 **갈라 주면** 그 판정을 종합 판정으로 쓰고, 리포트에 **비교 절의 어느 문장으로 갈랐는지 원문을 인용**한다. 갈래마다 「구분 기준은 …입니다」에 이어 **코드에서 어디를 보는지**가 적혀 있으므로, 그 자리를 실제로 읽고 판정한다 — 기준 문장만 인용하고 코드를 안 보면 인용이 판정을 대신한 것이 된다.
- 비교 절이 **후보 쪽을 답으로 지정하면** 종합 판정은 **「<사용자가 댄 패턴> 아님 — 비교 절의 기준으로 <후보>」** 다. 「패턴 아님」 행(필수 중 ❌ 가 하나 이상)과 다르다 — 여기서는 `[필수]` 가 다 통과했고 **비교 절이 다른 이름을 골라 준 것**이다. 2026-09-30 실측: 정통 Abstract Factory 코드를 Factory Method 로 물었을 때가 이 경우였다.
- 비교 절이 **둘 다 맞다고 적으면** 종합 판정은 **「동시 통과 — 둘 다 맞음」** 이고, 그때는 **보류가 아니다.** 이 프로젝트의 발행본 여럿이 그렇게 적는다 — 예컨대 Specification 편은 「필수 넷을 전부 만족하면서 동시에 다른 패턴이기도 한 코드가 있고, 그것은 이 조건들의 결함이 아닙니다」라고 쓰고, 어느 이름을 쓸지는 「그 객체가 도메인에서 무엇으로 불리는가」로 넘긴다. **정답을 「못 갈랐다」로 적지 않는다.** 리포트에는 두 이름과 그 문장을 함께 싣고, 도메인 이름을 고르는 일은 사용자에게 넘긴다.
- 비교 절이 **못 가르고 어느 쪽인지도 적지 않으면** 종합 판정은 **「동시 통과 — 판정 보류」** 다. 둘 다 통과했다는 사실과 각각의 조건별 결과를 함께 보고하고, 무엇을 더 알아야 가릴 수 있는지(설계 의도·변경 이력·호출하는 쪽 코드처럼 이 파일 밖의 정보) 적는다. **사용자가 먼저 댄 쪽을 답으로 고르지 않는다.**

**3-1) 동시 통과한 후보가 여럿이고 답이 갈리면 이렇게 묶는다.** 후보마다 비교 절의 답이 다를 수 있다 — 2026-09-30 실측에서 넷이 동시 통과했는데 둘(Bridge·Decorator)은 비교 절이 **사용자가 댄 패턴을 지정**했고 둘(Specification·의존성 주입)은 **둘 다 맞다**고 적었다.

- **사용자가 댄 패턴을 지정한 후보는 이름 후보에서 뺀다.** 그 편이 「이 코드는 내 쪽이 아니라 그쪽이다」라고 적은 것이므로 이름 다툼이 끝난 자리다. 다만 **동시 통과했다는 사실과 그 편의 지정 문장은 리포트에 남긴다** — 겹침이 실재했고 무엇이 갈랐는지가 다음 사람에게 필요하다.
- **둘 다 맞다고 적은 후보는 이름 후보로 남긴다.** 종합 판정은 「동시 통과 — 둘 다 맞음」이고 남은 이름을 전부 싣는다.
- **하나라도 「판정 보류」가 있으면 전체가 보류다.** 가르지 못한 상대가 있는데 다른 상대로 이름을 정하면 가르지 못한 쪽을 덮는 것이 된다.

**4) 후보가 하나라도 ❌ 면 동시 통과가 아니다.** 종합 판정을 그대로 쓰되, 리포트의 「경쟁 후보 대조」 칸에 **어느 후보를 무슨 조건으로 떨어뜨렸는지** 한 줄씩 적는다. 대조한 기록이 남아야 다음 사람이 같은 의심을 다시 하지 않는다.

#### 동시 통과가 확인된 쌍

아래는 **두 패턴의 `[필수]` 를 전부 만족하는 코드가 실제로 지어진** 쌍이다. 「서는 모양」은 그 코드가 어떤 생김새였는지이고, 「갈리는 자리」는 그 둘을 실제로 가르는 지점이다 — 동시 통과가 났을 때 비교 절에서 먼저 찾아볼 곳이기도 하다.

| 쌍 | 방향 | 동시 통과가 서는 모양 | 갈리는 자리 |
| --- | --- | --- | --- |
| **Strategy ↔ State** | Strategy → State | 구현 객체를 갈아 끼우는 설치 연산(setter)을 Context 에 둔 Strategy | 다음에 쓸 구현 객체를 **요청 처리의 결과로** 정하는가(State), 바깥이 골라 주는가(Strategy) |
| **Factory Method ↔ Abstract Factory** | 양방향 | ① 정통 AF — 구체 팩토리에 제품을 쓰는 상위 로직이 없어 FM 3·5번이 **잴 대상 없이** 참 ② 정통 FM + 두 줄 — 팩토리 인터페이스를 선언하고 `this` 를 그 타입 필드에 담으면 AF 다섯 통과 | 제품을 쓰는 상위 로직과 생성 연산이 **같은 타입에 선언돼 있는가**(FM), 생성만 하는 **별개 객체**를 받아 쓰는가(AF). 필드 선언이 아니라 그 참조가 **`this` 인지 다른 객체인지**를 본다 |
| **Adapter ↔ Proxy** | 양방향 | 전송 채널·RPC 를 감싼 래퍼. 마셜링 코드가 그대로 「이름·인자·반환의 변환」(Adapter 1·3번)이자 「원격」(Proxy 3번)이다. **한 클래스가 여덟 조건을 하나도 안 걸리고 통과한다** | 감싼 참조가 **Subject 를 구현하는 대상 자체인가**(Proxy), **인터페이스가 다른 남인가**(Adapter). Proxy 2번의 면책 구절(「참조가 처음부터 대상 자체일 필요는 없어요」)이 이 검사를 무르게 하므로, **Client 의 요청을 실제로 수행하는 대상**을 고정하고 그것의 타입을 본다 |
| **Decorator ↔ Proxy** | 양방향 | 잠금·참조 수를 관리하는 래퍼. 모든 호출을 전달하므로 Decorator 3번을 안 건드리면서, Proxy 3번 목록의 **「참조 수와 잠금 관리」** 에 그대로 든다 | **대상에 닿지 않는 요청이 하나라도 있는가, 또는 닿는 시점을 대리자가 정하는가**(Proxy 편 비교 절). 뒷구절이 어느 `[필수]` 에도 없으므로 비교 절에서 가져와야 한다 |
| **Adapter ↔ Decorator** | 양방향 · **참조를 둘 들 때만** | `inner: Component`(Decorator 2번용)와 `legacy: Adaptee`(Adapter 3번용)를 함께 든 래퍼. 참조 하나뿐인 순수 어댑터·순수 데코레이터는 타입 검사가 막는다 | 3단계 「감싼 대상을 먼저 하나로 고정한다」로 먼저 걸러진다. 고정한 뒤에는 **그 대상의 인터페이스가 Target 과 같은지**(Decorator) **다른지**(Adapter) 하나로 갈린다 |
| **Builder ↔ Abstract Factory** | 양방향 · **막는 조건이 하나도 없다** | ① 종결 연산을 둘 두고 계열마다 구체 빌더를 둔 Builder → AF 다섯 통과 ② 반환 없는 부분 연산을 함께 둔 팩토리 → Builder 넷 통과. 정통 팩토리는 부분 연산이 **0개**라 Builder 2번이 잴 대상 없이 참이 된다 | **생성 연산이 앞선 호출에 기대는가.** 같은 연산을 두 번 불러 답이 같으면 팩토리, 그 사이 호출에 따라 달라지면 빌더. **Abstract Factory 편 최소 조건 절이 이 대조를 직접 지시한다** — 「쓰는 쪽이 생성 연산을 순서대로 부르며 결과를 쌓아 가는 모양이라면 비교 절의 기준으로 Builder 쪽인지 함께 봐야 해요」 |
| **Mediator ↔ Facade** | 양방향 | 가운데 클래스가 추상 타입(`SeatFormMediator`·`BookingHub`)을 구현하고 이웃이 **그것을** 들면 구체 이름이 코드 어디에도 안 나온다. 그 위에 이웃을 「가운데를 아는 쪽」과 「모르는 쪽」으로 쪼개면 Facade 3번은 뒤쪽만, Mediator 2번은 앞쪽만 보고 각각 참이 된다 | 3단계 「참여자를 먼저 정하고 조건마다 갈아 끼우지 않는다」로 먼저 걸러진다. 고정한 뒤에는 **가운데가 든 이웃 전부가 가운데 타입(그것이 구현한 인터페이스 포함)을 드는가**(Mediator) **하나도 안 드는가**(Facade) 하나로 갈린다 |
| **Strategy ↔ Specification** | 양방향 | 판정이 참·거짓을 돌려주는 술어 객체. 원전이 Hard Coded Specification 을 「specification 을 Strategy 로 다루는 것」이라 적으므로 **원전이 인정하는 겹침**이다. 2026-09-30 실측: `specification/code/ContainerAssignment.java` 가 두 편의 `[필수]` 를 전부 만족한다 | **판정 연산이 돌려주는 것이 후보에 대한 참·거짓인가, 그 밖의 값인가.** 불리언이면 **둘 다 맞고**, 어느 이름을 쓸지는 그 객체가 도메인에서 무엇으로 불리는가로 고른다(Specification 편 비교 절). Strategy 편은 2026-09-21 발행이라 이 상대를 이름 대지 못한다 — 가르는 문장은 **후보 쪽에만** 있다 |
| **Strategy ↔ Bridge** | Strategy 쪽에서 봄 | 같은 코드(`ContainerAssignment.java`)가 Bridge `[필수]` 셋도 통과한다 | **Bridge 편이 Strategy 를 지정한다** — 위임하는 쪽에 하위 타입이 자라는가(Bridge), 고르는 분기를 안쪽에 두면 안 되는가(Strategy), 짝이 1:1 인가(Strategy). 셋이 같은 답을 낸다 |
| **Strategy ↔ Decorator** | Strategy 쪽에서 봄 | 같은 코드의 조합 노드(`NotSpec`)를 떼어 보면 층이 감싸는 모양이라 Decorator `[필수]` 다섯을 통과한다 | **Decorator 편이 Strategy 를 지정한다** — 「데코레이터는 대상을 밖에서 감싸고, 스트래티지는 대상이 안에서 들고 있어요」. Client 가 부르는 대상이 누구인지를 본다 |
| **Strategy ↔ Dependency Injection** | 양방향 | 협력 타입이 하나이고 그 구현들이 같은 계산의 대안이면 두 조건 묶음이 함께 선다 | **둘 다 맞다** — DI 편 비교 절이 「협력 타입이 하나이고 그 구현들이 같은 계산의 대안이면 두 이름이 다 맞고」라고 적는다. 갈리는 것은 든 협력 타입이 하나인가 여럿이고 각자 다른 일을 맡는가다 |
| **Visitor ↔ Bridge 계열** | Bridge → Visitor | 이름 의존. `Shape.draw(DrawingApi)` 에서 연산 이름만 `accept` 로 바꾸면 Visitor 조건 셋을 통과한다 | 3단계 「이름에 기대는 조건은 구조로 다시 읽는다」. 연산 집합이 **원소 타입 여럿에 걸쳐 있는가**(Visitor), **한 가지 일의 대안인가** |

**가장 위험한 것은 Adapter ↔ Proxy 다.** HTTP 클라이언트나 외부 SDK 를 감싸 우리 인터페이스로 내미는 클래스는 실무 저장소에 가장 흔한 래퍼인데, 마셜링을 하는 순간 두 패턴의 `[필수]` 여덟 개가 **모두** 통과한다.

**그다음이 Builder ↔ Abstract Factory 다.** 위 쌍들은 어느 한 방향이나 어느 한 종류에서는 막히는데, 이 쌍은 **`[필수]` 만으로는 아예 갈라지지 않는다** — 양방향 모두 막는 조건이 하나도 없다. 그래서 이 쌍에서는 5단계를 건너뛰면 답이 반드시 틀린다.

**표의 열두 쌍 가운데 아홉이 양방향이다.** 나머지 셋은 한쪽 편이 상대를 지정해 이름 다툼이 끝난 자리이고, 그래도 표에 두는 것은 **겹침이 실재해서 대조를 건너뛰면 안 되기 때문**이다. 「이 패턴의 조건을 다 만족하니 이 패턴이다」가 일반적으로 성립하지 않는다는 뜻이고, 그것이 5단계를 선택이 아니라 절차로 둔 이유다.

**표에 없는 쌍이 동시 통과로 확인되면 여기에 줄을 더한다.** 확인은 조건 문면 대조만으로 하지 않는다 — 두 패턴의 `[필수]` 를 전부 만족하면서 **컴파일되고 실행되는 코드**를 실제로 지어야 한 줄이 선다.

### 6. 종합 판정

조건별 결과를 다음 규칙으로 묶는다.

| 결과 분포 | 종합 판정 |
| --- | --- |
| 모든 필수 조건이 ✅ | **정통 패턴** |
| 필수 조건은 모두 ✅, 선택 조건만 ⚠️/❌ | **정통 패턴 (선택 조건 보강 권장)** |
| 필수 조건 중 1개가 ⚠️ 이고 나머지 ✅ | **변형 패턴** |
| 필수 조건 중 ❌ 가 1개 이상 | **패턴 아님** |
| ❓ 가 핵심 조건에 포함 | **판정 보류** — 추가 정보 요청 |
| 필수 조건에 「해당 없음」(잴 대상 없음)이 1개 이상 | 5단계를 반드시 밟음 — 대조가 안 갈리면 **판정 보류** |
| 필수 모두 ✅ + 경쟁 후보도 필수 모두 ✅ + 비교 절이 갈라 줌 | 비교 절의 판정을 따름 — **근거 문장 인용 필수** |
| 필수 모두 ✅ + 경쟁 후보도 필수 모두 ✅ + 비교 절이 후보 쪽을 지정 | **「<댄 패턴> 아님 — 비교 절의 기준으로 <후보>」** |
| 필수 모두 ✅ + 경쟁 후보도 필수 모두 ✅ + 비교 절이 둘 다 맞다고 적음 | **동시 통과 — 둘 다 맞음** (보류가 아니다) |
| 필수 모두 ✅ + 경쟁 후보도 필수 모두 ✅ + 비교 절이 못 가름 | **동시 통과 — 판정 보류** |

"필수"와 "선택"의 구분은 2단계 「필수 / 선택 판별」을 따른다. 표의 "핵심 조건"은 필수 조건이다. 아래 두 행은 5단계를 거친 결과이고, **위 행들보다 우선한다** — 필수가 모두 ✅ 라고 해서 5단계를 건너뛰고 「정통 패턴」으로 끝내지 않는다.

- **`[필수]` 조건이 코드에서 충족되지 않으면 그 조건은 ❌ 다.** 부분적으로만 드러나면 ⚠️, 코드 단편만으로 판단할 수 없으면 ❓ 다.
- **`[선택]` 조건의 ⚠️/❌ 는 종합 판정을 깎지 않는다.** 조건별 평가에는 판정을 그대로 적되, 종합 판정은 필수 조건만으로 정하고 선택 조건 미충족은 「권장 조치」에만 올린다(표의 "정통 패턴 (선택 조건 보강 권장)" 행). `[선택]` 조건의 ❓ 는 판정 보류 사유가 아니다.

### 7. 리포트 작성

같은 폴더의 `report-template.md` 의 구조를 그대로 따른다. 파일명 규칙:

```
analysis/<pattern>-<filename_stem>-<YYYYMMDD-HHMM>.md
```

예: `analysis/singleton-singleton-20260529-1430.md`

`analysis/` 디렉토리가 없으면 만든다.

### 8. 채팅 요약 출력

다음 형식으로 짧게:

```
[패턴명] {파일경로}
종합 판정: {정통/변형/아님/보류/동시 통과 — 둘 다 맞음/동시 통과 — 판정 보류/<댄 패턴> 아님 — 비교 절의 기준으로 <후보>}
조건: ✅ N개 / ⚠️ M개 / ❌ K개 / ❓ L개
선택 조건 미충족: {조건 번호·제목, 없으면 "없음"} — 종합 판정에 반영하지 않음
경쟁 후보: {대조한 패턴명과 결과 — 예 "State 도 필수 전부 통과(동시 통과)" · "Proxy 는 조건 3 미충족으로 탈락" · 5단계를 안 밟았으면 "해당 없음"}
최우선 조치: {한 줄}

리포트: analysis/...md
```

**동시 통과로 보류했으면 채팅 요약에서 그 사실을 먼저 말한다.** 「판정 보류」만 적고 사유를 리포트에 묻어 두면, 사용자는 보류를 「분석기가 못 읽었다」로 읽고 넘어간다. 두 패턴 다 통과했다는 것과 무엇이 있어야 가릴 수 있는지를 한 줄로 낸다.

리포트 파일 경로를 채팅에 알린다(위 요약의 `리포트:` 줄).

## 톤 & 스타일

- 한국어. 패턴/역할 용어는 영문 원어 병기.
- 추측 금지. 코드에 없는 사실을 단정하지 않는다. 보이지 않으면 ❓.
- "이 코드는 좋다/나쁘다" 류의 가치 평가는 피하고, "조건 N 미충족: 이유" 처럼 사실 기반 서술.
- 권장 조치는 항상 before/after 짝 코드로 보여준다.

## 하지 말 것

- 평가 기준을 임의로 새로 만들지 않는다. 반드시 (1) 가이드 문서·사용자가 지정한 기준 문서 또는 (2) 내장 `checklist.md` 에서 가져온다.
- 코드를 실행할 때 "안전한 실행 조건" 4개를 1개라도 어기지 않는다.
- ❌ 판정만 잔뜩 나열하지 말고, 정확히 어떤 라인의 어떤 코드가 어떤 조건을 어떻게 위반하는지 짝지어 적는다.
- 사용자가 작성한 코드를 마음대로 고치지 않는다. 권장 조치 코드 스니펫은 리포트 안에만 둔다.
- **`[필수]` 가 전부 ✅ 라고 5단계를 건너뛰지 않는다.** 최소 조건은 후보 자격이지 패턴 확정이 아니다.
- **동시 통과가 났을 때 사용자가 먼저 댄 패턴을 답으로 고르지 않는다.** 가르는 근거는 비교 절에서 가져오고, 없으면 보류한다.
