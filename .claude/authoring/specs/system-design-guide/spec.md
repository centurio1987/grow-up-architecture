## 이 글은 무엇인가

**문제 하나**를 두고, 그 문제를 가장 잘 푸는 시스템 아키텍처를 보이는 가이드다.
패턴 가이드(`gof-guide` · `analysis-guide`)가 해법 하나를 단위로 쓰는 것과 방향이 반대다 — 여기서는 요구 하나가 단위이고, 해법은 그 요구를 푸는 부품으로 등장한다.

유저 원문(2026-11-13)이 필수로 정한 네 요소가 몸통이 된다.

1. 시각화된 시스템 개념도 → `diagram`
2. 시스템의 시나리오 설명 → `detail.scenario`
3. 개념도에 포함된 기술의 상세 설명 → `tech.item`
4. 주요 구현 코드 → `example.context` · `example.impl`

여기에 「최적」을 판단할 수 있게 하는 절 둘이 앞뒤로 붙는다. **요구 수치가 없으면 최적을 판단할 수 없고, 다른 구조와 견주지 않으면 왜 최적인지 보이지 않기 때문이다.**

- 앞: `requirements`(문제와 요구사항) · `estimation`(규모 추정)
- 뒤: `alternatives`(대안 비교 — 후보 · 결정 · 전환점) · `fit`(요구 충족 확인)

```text
문제와 요구사항 ─▶ 규모 추정 ─▶ 시스템 개념도 ─▶ 시나리오로 따라가기 ─▶ 기술 상세 설명 ─▶ 대안 비교 ─────────▶ 구현 코드 ─────────▶ 요구 충족 확인 ─▶ 실제 사례 ─▶ 스스로 점검 ─▶ 참고 자료
(수치로 고정)   (수치 → 부하)  (상자 = 실행 단위)  (시나리오 1 기본 흐름       (상자마다 네 칸)    (후보 → 결정 → 전환점) (상황 설정 → 세 언어)  (요구 행 ↔ 단계 ↔ 출력)  (조건부)
                                                  시나리오 2 부하가 몰릴 때
                                                  시나리오 3 장애가 날 때)
```

순서의 이유는 하나다. **이름은 움직이는 것을 본 뒤에 정의한다**(`gof-guide` 가 개념 정리를 시나리오 뒤에 둔 것과 같은 원칙). 개념도가 상자를 보여 주고, 시나리오가 그 상자들이 일하는 모습을 보여 준 다음에 기술 설명이 상자 하나하나를 푼다.
대안 비교는 기술을 알아야 견줄 수 있으므로 기술 설명 뒤에 오고, 요구 충족 확인은 실행 출력을 가리키므로 구현 뒤에 온다.

컨테이너 절 넷 — `## 시나리오로 따라가기`(`detail`) · `## 기술 상세 설명`(`tech`) · `## 대안 비교`(`alternatives`) · `## 구현 코드`(`example`) — 은 자기 본문 없이 하위 `###` 절만 담는다.

### 「최적」을 다루는 세 규칙

이 명세의 절 대부분이 이 셋을 지키려고 있다.

1. **요구를 수치로 고정한다**(SD3). 동시 접속 수 · 지연 상한 · 허용 오차 · 가용성을 숫자로 적는다. "지연 없이"는 "입장 후 N초 안에 화면 숫자에 반영"처럼 바꿔 적는다.
2. **후보 구조를 같은 기준으로 견준다**(SD16 · SD17). 기준은 지연 · 처리량 · 정확도 · 비용 · 운영 부담 · 장애가 번지는 범위 가운데 그 문제에 걸리는 것이다. 빠진 기준이 없는지는 AWS Well-Architected 의 여섯 기둥(운영 우수성 · 보안 · 신뢰성 · 성능 효율 · 비용 최적화 · 지속 가능성)을 점검표로 하나씩 확인한다.
3. **전환점을 적는다**(SD19). 고른 구조가 어느 수치를 넘거나 어떤 요구가 바뀌면 최적이 아닌지를 적는다. 독자가 자기 문제의 수치를 넣어 다른 답을 고를 수 있어야 가이드가 한 사례를 넘어 쓰인다.

### 기존 규약에서 무엇이 어디로 갔나

`gof-guide` 1.4.0 의 절을 기준으로 옮긴 자리를 적는다. 옮긴 규칙은 원칙 목록에서 `← PGn` 으로 출처를 단다.

| `gof-guide` 자리 | 이 명세의 자리 | 무엇이 바뀌었나 |
| --- | --- | --- |
| `title` 패턴 — 부제 | `title` 문제 — 한 줄 해답 | 부제가 패턴의 비결이 아니라 고른 구조의 비결이다 |
| `overview` 개요 | `requirements` 첫 문단 + `diagram` | 문제 상황 · 해결의 직관은 요구사항 첫 문단이, 전후 그림은 개념도가 맡는다 |
| `detail.scenario` 시나리오 | `detail.scenario` (같은 id · 같은 검사) | 종류 셋이 고정이다 — 기본 흐름 · 부하가 몰릴 때 · 장애가 날 때. 패턴의 「경계를 넘을 때」는 「장애가 날 때」로 뜻을 바꿔 옮겼다 |
| `detail.terms` 개념 정리 + 클래스 도식 | `tech.item` 기술 상세 설명 + `diagram` | 역할 정의가 구성 요소 설명이 되고, 정의 ↔ 클래스 도식 1:1 이 기술 항목 ↔ 개념도 상자 1:1 이 된다 |
| `purpose` 사용 목적 | `requirements` + `alternatives.switch` | "어떤 단서에서 꺼내는가"는 요구 수치와 전환점이 대신 답한다 |
| `boundary.minimum` 최소 조건 | **없음** → `fit` 요구 충족 확인 | analyzer 가 읽을 판정 기준이 이 계열에는 없다. 그 자리에서 "이 구조가 요구를 만족하는가"를 시나리오와 실행 출력으로 보인다 |
| `boundary.compare` 비교 | `alternatives.candidates` | 비교 대상이 패턴이 아니라 후보 구조다. 얻는 것과 포기하는 것은 그대로 |
| `example.context` · `example.impl` | 같은 id · 같은 헤딩 | 펜스 규약을 그대로 쓰고, 세 언어 출력을 같게 만드는 결정성 규칙(SD26)을 더했다 |
| `example.realworld` 실제 라이브러리에서 | `example.realworld` `## 실제 사례` | 라이브러리 API 매핑이 기업 사례 매핑이 된다. 조건부는 그대로 |
| `selfcheck` · `refs` | 같음 | 점검 문제의 종류와 참고 자료 순서가 이 계열에 맞게 바뀌었다 |

## 절별 작성법

### 제목 (`title`)

`# {문제} — {한 줄 해답}`. `{문제}` 는 사례 목록의 문제 이름이고, `{한 줄 해답}` 은 이 가이드가 고른 구조의 **비결을 한 구절로** 예고한다(SD2).

- 좋은 예: `# 라이브 동시 시청자 수 — 세는 곳은 에지에, 보내는 일은 1초에 한 번`
- 나쁜 예: `# 라이브 시청자 수 시스템 설계 가이드` — 분류명과 "가이드"로 채웠다.

### 문제와 요구사항 (`requirements`)

이 절만 읽고 닫아도 "누가 무엇을 겪는 문제이고, 무엇이 되면 풀린 것인가"를 들고 나가게 쓴다.

1. **첫 문단 — 문제 상황.** 누가 무엇을 보거나 하려는가를 구체 상황 하나로. 순진한 구조로 만들면 어디서 아픈가를 한 문장 붙인다.
2. **기능 요구** — 사용자가 할 수 있어야 하는 일 셋 안팎. 범위를 넓히는 요구(통계 화면 · 관리자 기능)는 넣지 않는다.
3. **비기능 요구 표** — 열은 `항목 · 수치 · 근거` 다(SD3).
   - 근거 칸은 셋 중 하나다 — 출처 링크(공개 사례 · 공식 문서), `계산`(다른 행에서 셈한 값), `이 가이드의 가정`(왜 그 값으로 잡았는지 한 구절).
   - "빠르게" · "지연 없이" · "대규모" · "안정적으로" 같은 말이 수치 없이 남으면 미흡이다. 지연은 측정 지연과 전달 지연처럼 갈래가 있으면 갈래마다 행을 둔다.
   - 정확도 요구를 반드시 한 행 둔다. 정확해야 하는가(한 건도 틀리면 안 됨), 근사로 충분한가(허용 오차 몇 %)가 구조 선택을 가장 크게 가르기 때문이다.
4. **다루지 않는 것** — 이 가이드가 일부러 범위 밖에 둔 것 1개 이상(SD4). 범위 밖을 적지 않으면 독자는 빠진 것을 실수로 읽는다.

### 규모 추정 (`estimation`)

요구 수치에서 **부하**를 계산한다 — 초당 요청 · 동시 연결 · 저장량 · 대역폭 가운데 이 문제에 걸리는 것.

- 결과 수치마다 **계산식**을 보인다(SD5). `1,000만 명 ÷ 30초 = 초당 약 33만 건` 처럼 입력 · 연산 · 결과가 한 줄에 보인다. 입력 수치는 요구사항 표의 행이나 출처에서 온다.
- **이 계산이 구조를 어떻게 바꾸는가**를 한 문단으로 적는다(SD6). 추정은 숫자를 늘어놓는 일이 아니라 순진한 구조를 배제하는 근거다 — "입장마다 전원에게 보내면 초당 8.3×10¹⁰ 건이라 이 구조는 처음부터 후보에서 빠진다".
- 저장소 한 대의 처리량 같은 **비교 기준 수치**는 출처를 단다. 벤치마크 수치는 측정 조건(파이프라인 여부 · 기계)을 함께 적고 한도로 쓰지 않는다.
- 수치의 출신을 구분한다(SD40) — 출처에서 온 값 · 계산한 값 · 가정한 값이 섞이면 독자가 어느 숫자를 믿을지 모른다.

### 시스템 개념도 (`diagram`)

시스템 전체를 **그림 한 장**으로 보인다(SD7).

- 수준은 C4 모델의 Container 수준이다. 상자 하나가 **실행 단위 하나**(브라우저 · 에지 서버 · 집계 서비스 · Redis 같은 저장소)이고, 화살표마다 **통신 방식과 빈도**(`SSE · 1초마다` · `HTTP POST · 30초마다`)를 적는다.
- 클러스터링 · 부하 분산 · 장애 조치 같은 배포 세부는 개념도에 넣지 않는다. 시나리오가 배포 세부에 기대면(부하 분산이 연결을 나눔 · 복제본이 승격됨) 경로 그림에는 그 부분을 그리고, 정식 설명은 그것과 관련된 기술 항목 안의 한 문단으로 둔다(SD8 · SD12, 1.1.0). 두 파일럿이 모두 이 자리를 찾지 못해 헤맸다.
- viz 카탈로그의 C4 Container(`VT-110`) 또는 Cloud Architecture(`VT-115`)로 `diagrams/` 에 그린다. 도식 규약은 아래 「공통 규약」을 따른다.
- **상자 이름과 기술 상세 설명의 항목이 1:1 이다**(SD8). 그림에 있는데 설명이 없는 상자, 설명은 있는데 그림에 없는 구성 요소가 있으면 미흡이다. 배포 세부를 관련된 기술 항목 안의 문단으로 설명하는 것은 「그림에 없는 구성 요소」로 치지 않는다(1.1.0).
- 그림 바로 아래에 한 문단으로 데이터가 거쳐 가는 주된 경로를 적는다. 상자마다의 설명은 기술 상세 설명이 한다.

### 시나리오 (`detail.scenario`) — 가이드의 중심

**가이드의 주요 내용은 시나리오를 따라간다**(← PG32). 개념도의 상자들이 요청 하나를 어떻게 넘겨받는지를 단계로 보인다.

- 헤딩은 `### 시나리오 n — 제목` 이고 **셋**이다. 번호는 1부터 연속이고 종류가 고정이다(SD9).
- **제목은 그 시나리오에서 일어나는 일을 한 구절로** 쓴다(SD41 ← PG38). 종류 이름(「기본 흐름」 · 「부하가 몰릴 때」 · 「장애가 날 때」)만 옮긴 제목은 미흡이다. 시나리오 3 이면 멈춘 구성 요소나 잃은 메시지와 그 결과를 제목에 쓴다(예: 「집계 노드가 멈추면 화면의 숫자가 어디서 굳는가」). 검사기(`scenario-title`)는 gof 계열의 틀 문구 `규칙을 어기` · `구조를 어기` 만 막으므로, 종류 이름만 옮긴 제목은 채점이 잡는다.
  1. **기본 흐름** — 부하와 장애가 없는 조건에서 요청 하나가 들어와 화면 · 저장소까지 끝나는 길. 평상시가 없는 문제(정각 오픈 같은)면 첫 요청 하나의 길이다(1.1.0).
  2. **부하가 몰릴 때** — 규모 추정의 수치를 넘기는 상황(평소의 10배 · 정각 오픈 · 재접속 폭주). 어느 상자가 그 부하를 받아내고, 무엇이 조절되며, 무엇은 바뀌지 않는가.
  3. **장애가 날 때** — 구성 요소 하나를 멈추거나 메시지 하나를 잃게 한다. 어느 단계에서 무엇이 어긋나고, 사용자는 무엇을 보며, 어떻게 회복되는가. 정합성이 걸린 문제면 "틀린 값이 남는 경로"를 반드시 보인다.
- 시나리오 하나의 모양은 셋으로 고정이다(← PG32 · PG5).
  1. **상황 한 문단** — 무엇이 들어오고 무엇이 나와야 하는가. **구체 값**으로(사람 수 · 초 · 남은 수량 · 시각).
  2. **번호 단계 3개 이상** — 한 단계 = 어느 상자가 무엇을 하는가 **+ 왜**(왜 그 상자가 그 일을 맡는가, 또는 순서를 바꾸면 무엇이 어긋나는가)(SD10). 들여쓰기 없는 `1.` 목록으로 쓴다 — 검사기가 그것을 단계로 센다.
  3. **이 시나리오가 보여 준 것 한 문단** — 어떤 요구가 어떻게 충족되었거나 어떤 위험이 보였는가. 여기서 나온 사실이 `fit` 표로 간다.
- **경로 그림**을 시나리오마다 하나 둔다(SD11). C4 Dynamic(`VT-113`, 번호가 붙은 협력) 또는 Sequence(`VT-108`)로 그리거나 ```text 도식으로 둔다. 상자 이름은 개념도와 같다. 그림이 단계 서술을 대신하지는 않는다. 경로 그림은 개념도 상자 가운데 그 시나리오에 나오는 것만 그려도 되고, 한 상자를 인스턴스 여럿(에지 a · b · c, Redis 주 · 복제)으로 나눠도 된다. 이때도 이름은 개념도와 같게 둔다(1.1.0).
- **처음 쓰는 이름은 그 자리에서 한 구절로 소개한다**(SD12 ← PG3). 구성 요소 · 기술 이름만이 아니라 약어와 명령도 본문에 처음 나오는 자리에서 푼다. 규모 추정의 식에 들어가는 명령(예: 요청 하나가 쓰는 Redis 명령의 개수)도 그 식보다 앞에서 푼다(1.1.0). 정식 설명은 `tech.item` 이 맡고, 개념도 밖 배포 세부는 관련된 기술 항목 안의 문단이 맡는다.
- **도메인은 하나다**(SD13 ← PG35). 시나리오가 고른 값과 등장 요소를 `example.context` · `example.impl` 이 그대로 이어받는다.

### 기술 상세 설명 (`tech.item`)

개념도의 상자마다 `### 구성 요소 — {이름}` 절 하나를 둔다. `{이름}` 은 개념도 상자의 이름과 글자까지 같다(SD8).

- 항목마다 **네 칸**을 이 순서로 쓴다(SD14).
  1. **무엇인가** — 그 기술 · 구성 요소를 처음 보는 사람이 알아들을 정의 한두 문장과 예.
  2. **이 시스템에서 맡는 일** — 시나리오의 어느 단계에서 무엇을 받고 무엇을 내보내는가.
  3. **왜 이 기술인가** — 같은 자리에 올 수 있는 다른 기술 하나 이상과 견준 이유. "널리 쓰인다"는 이유가 아니다. 견준 기술도 가진 성질은 고른 이유가 되지 않는다. 가르는 성질이 공개 수치로 확인되지 않으면 그렇다고 밝히고 (판단)으로 둔다. 회사가 썼다는 사실은 이유 뒤에 붙는 선례이지 이유가 아니다(SD38, 1.1.0).
  4. **설정값과 한계** — 이 가이드가 고른 값(주기 · 만료 시간 · 파티션 수)과 그 값을 고른 이유, 그 기술이 보장하지 않는 것(at-most-once · 비동기 복제 · 근사 오차).
- 제품의 동작과 보장을 단정하면 **공식 문서 출처**를 단다(SD15 ← PG24). "Redis Pub/Sub 은 구독자가 끊기면 메시지를 잃는다"는 출처 없이 쓰지 않는다.
- **본문은 바깥 문서 없이 읽힌다**(← PG30). 이 문제에 필요한 만큼은 그 자리에서 푼다. 여러 편이 같은 기술을 깊게 다뤄야 하면 그 일반론은 참고 문서(`reference-note`)로 빼고 내부 링크로 잇는다.
- 그 기술을 다룬 패턴 가이드가 발행돼 있으면(예: Retry · Circuit Breaker) 링크하고, 이 사례에 필요한 만큼만 설명한다.
- 실제 배포에 쓰는 조각(Redis 명령 · 설정 파일 · 응답 헤더)은 이 절에 싣는다. 정보 문자열에 `no-compile` 을 붙여 실행 검증 대상이 아님을 표시한다(SD30 ← PG14).

### 대안 비교 (`alternatives`)

**이 요구에서 왜 이 구조가 최적인가**를 견주어 보인다. 하위 절 셋이 고정이다.

#### 후보 구조 비교 (`alternatives.candidates`)

- 후보는 이 가이드가 고른 구조를 포함해 **2개 이상**이다(SD16 ← PG11). 순진한 구조(폴링 · 행 하나 잠금)를 후보에 넣으면 규모 추정과 바로 이어진다.
- 후보마다 **같은 기준**으로 견준다 — 위 「최적을 다루는 세 규칙」의 기준 가운데 이 문제에 걸리는 것. 후보마다 **얻는 것과 포기하는 것**을 적는다(SD17 ← PG13).
- 표로 시작하되 표로 끝내지 않는다. **가장 헷갈리는 한 쌍**은 산문과 수치로 푼다(SD20).
- 공개 사례가 같은 문제를 단계별로 고쳐 온 기록이 있으면(예: 한 회사가 구조를 세 번 바꾼 과정) 시간 순서로 쓴다. 각 단계에서 무엇이 아팠는지가 곧 후보를 가르는 기준이 된다.

#### 결정 (`alternatives.decision`)

ADR(Architecture Decision Record, 결정 기록)의 세 칸을 빌려 **맥락 · 결정 · 결과**로 닫는다(SD18).

```text
맥락: 어떤 요구 수치에서 고르는가 (요구사항 표의 행을 가리킨다)
결정: 무엇을 골랐는가 (후보 하나)
결과: 얻는 것 · 포기하는 것 · 새로 생기는 일(운영 · 감시)
```

- 버린 안을 「더 느리다 · 더 위험하다」로 버릴 때는, 이 글의 모형에서 그것이 실제로 더 나쁜지 먼저 확인한다. 모형으로 가를 수 없으면 확인된 근거와 (판단)을 나눠 적는다(SD18, 1.1.0). 파일럿 2 가 Lua 를 「다른 일을 모두 막는다」로 버렸다가, 모형에서는 명령 둘도 같은 시간 Redis 를 쓴다는 지적을 받았다.

#### 전환점 (`alternatives.switch`)

고른 구조가 **최적이 아니게 되는 조건**을 1개 이상 적는다(SD19). 조건은 수치(동시 접속이 몇을 넘으면 · 허용 오차가 몇 % 아래로 내려가면)나 요구 변화(정산에 쓰이게 되면)로 쓴다. 그때 어느 후보로 옮기는지도 함께 적는다.

### 구현 코드 (`example`)

#### 상황 설정 (`example.context`)

구현 펜스보다 앞에서 **시나리오의 도메인과 값을 코드 크기로 고정**한다(SD21 ← PG15).

- 실제 구성 요소가 코드에서 무엇으로 바뀌는지 **대역 매핑 표**를 둔다 — `실제 구성 요소 · 코드의 타입 · 대역이 흉내 내는 것 · 흉내 내지 않는 것`. 예: `Redis` → `MemoryStore`(정렬 집합 · 만료) · 네트워크 지연과 복제는 흉내 내지 않음.
- 시간은 **가상 시계**로 흘린다. 코드가 어떤 사건을 몇 초에 일으키는지(입장 · 하트비트 끊김 · 노드 정지)를 목록으로 적는다.
- 이 코드가 시나리오 몇 번을 재현하는지 적는다. 세 시나리오를 다 재현하지 않아도 되지만, 재현하지 않은 시나리오는 `fit` 에서 "실행 밖"으로 표시된다.

#### 구현 — 펜스 규약 (`example.impl`)

`### 구현` 은 **컴파일 검사를 받는 유일한 절**이다. 아래 규약은 `commands.compile` · `commands.run` 이 기계로 검사한다.

1. **펜스는 정확히 3개, 순서는 `java` → `typescript` → `rust`**, 사이에 산문 · 헤딩이 없다(SD22 ← PG16). HTML 파생본에서는 렌더러가 세 펜스를 탭 묶음 하나로 만든다.
2. **자기완결** — 펜스 하나를 파일 하나로 저장해 단독 컴파일된다. 기준은 Java 21 · TypeScript strict · Rust 2021 edition 이다. 생략 표기(`...`)와 빈 펜스는 실패다(SD23 ← PG17).
3. **표준 라이브러리만** — 외부 crate · npm 패키지 · Maven 의존은 0이다(SD24 ← PG18). 그래서 외부 시스템은 메모리 대역으로 둔다.
4. **같은 상황을 세 언어로** — `example.context` 의 시나리오를 같은 타입 이름으로 세 번 구현하고, 셋 모두 진입점(Java `main` · TypeScript 최상위 호출 · Rust `fn main`)을 갖는다(SD25 ← PG19).
5. **세 언어의 출력이 글자 단위로 같다**(SD26). 시스템 시뮬레이션은 패턴 예제보다 이 조건에 쉽게 걸리므로 다섯 규칙을 지킨다.
   - **맵 순회 순서에 기대지 않는다.** Java `HashMap` 은 순서를 정하지 않고, Rust `HashMap` 은 실행마다 순서가 바뀌며, JavaScript `Map` 은 넣은 순서를 지킨다. 출력하기 전에 키로 정렬한다.
   - **표준 난수 생성기를 쓰지 않는다.** 언어마다 수열이 다르다. 무작위가 필요하면 같은 식의 의사난수 생성기(예: 선형 합동 생성기)를 세 언어에 직접 구현하고 씨앗을 고정한다.
   - **스레드와 실제 시계를 쓰지 않는다.** Rust 표준 라이브러리에는 비동기 실행기가 없으므로, 단일 스레드에서 가상 시계의 사건을 시각 순으로 처리하는 모양이 세 언어 모두에 맞는다. 같은 시각의 사건은 정해 둔 순서(예: 사건 번호)로 처리한다.
   - **실수를 그대로 찍지 않는다.** 같은 1.0 을 Java 는 `1.0`, TypeScript 와 Rust 는 `1` 로 찍는다. 정수로 셈하거나 자릿수를 고정한 문자열로 출력한다.
   - **경합은 사건 순서로 재현한다**(1.1.0). 두 요청이 같은 값을 다투는 상황은 스레드 대신 「A 확인 → B 확인 → A 차감 → B 차감」처럼 사건을 끼워 넣은 차례로 만든다. 네트워크 왕복이 요구(응답 시간 · 전달 지연)에 걸리면 왕복을 사건으로 넣는다 — 넣지 않으면 그 요구는 `fit` 에서 실행 밖이 된다. 파일럿 2 는 이 방법으로 확인 후 차감 구조의 과발급을 결정적으로 재현했다.
6. **예시 코드의 정본은 `code/` 의 실행 파일이다**(SD27 ← PG29). `code/<공개클래스>.java` · `code/main.ts` · `code/main.rs` 와 `code/expected-output.txt` 를 두고, 본문 펜스는 그 파일과 글자 단위로 같다. 실행 출력 펜스는 `### 상황 설정` 의 끝에 둔다. 이 계열은 해설이 `### 구현` 안에 있으므로, 해설 뒤에 두어도 구현 절 안이라 검사기가 네 번째 컴파일 대상 펜스로 센다(1.0.1). **본문의 수치는 실행에서 온다.**
7. **분량은 언어당 250줄 안팎을 목표로 하고 300줄을 넘지 않는다**(SD28 ← PG28, 1.1.0 · 1.1.1). 줄 수는 본문 펜스에 적힌 그대로 센다. 서식 도구(rustfmt · Prettier)의 기본 출력은 요구하지 않는다 — 파일럿 두 편의 Rust 를 rustfmt 기본값으로 정리하면 369 · 415줄, `use_small_heuristics = "Max"` 로도 331 · 391줄이다(1.1.1 실측). 대신 **한 줄에는 문장 하나만** 둔다. 짧은 `if` · `for` 본문이나 한 문장짜리 메서드를 한 줄에 쓰는 것은 되지만, 세미콜론으로 문장 여럿을 한 줄에 잇지 않는다. 300을 넘으면 시나리오를 줄이기 전에 출력과 대역의 군더더기를 먼저 줄인다. 파일럿 두 편의 첫 초안은 258~343줄이었다(파일럿 회고 5절).
8. **해설은 세 펜스 뒤에 한 번, 줄 포인팅으로 쓴다**(SD29 ← PG20 · PG34). "시나리오 1 의 3단계는 Java n행 · TypeScript n행 · Rust n행" 처럼 시나리오 단계 ↔ 코드 줄로 쓰고, 언어 차이는 그 뒤에 짧게 붙인다. 해설 안에는 펜스를 두지 않는다 — `### 구현` 안의 펜스는 출력용 `text` 펜스까지 컴파일 대상으로 세어지므로, 줄 대응은 표로 쓴다(1.1.0).
9. **코드를 바꿔 실행한 실험은 표시한다**(SD43, 1.1.0). 본문이 정본 코드와 다른 실행 결과를 쓰면(기준값을 바꾸면 · 사건 하나를 빼면), 무엇을 바꿨는지 그 자리에 적고 실제로 실행해 얻은 값만 쓴다. 정본 실행의 출력과 섞지 않고, 실험 때문에 `code/` 를 바꾸지 않는다. 파일럿 1 은 바꾼 값을 틀리게 적은 문장으로 두 라운드 연속 걸렸다.

### 요구 충족 확인 (`fit`)

`boundary.minimum` 이 있던 자리다. **이 구조가 요구를 만족하는가**를 표 하나로 보인다(SD31).

| 요구(요구사항 표의 행) | 충족을 보이는 자리 | 확인한 것 |
| --- | --- | --- |
| 입장 측정 지연 3초 | 시나리오 1 의 1~4단계 | `t=2.3s join conn=1201 edge=a` → `t=3.5s total=1201 actual=1201` 로 1.2초 |
| 전달 지연 1초 | 시나리오 1 의 5 · 6단계 | 실행 밖 — 가상 시계가 네트워크 지연을 0 으로 둠. 경로의 구조와 출처 사례로 보임 |
| 동시 시청자 1,000만 명 | 규모 추정 [4] · [5] · [6] | 실행 밖 — 계산으로 보임. 메모리 대역의 에지 3대로는 1,000만 연결을 재현할 수 없음 |

위 예시는 파일럿 1(`live-viewer-count` v1.0.0)의 표에서 세 행을 줄여 옮긴 것이다(1.1.0 — 1.0.x 의 예시는 열람에 실패한 출처와 실제와 무관한 출력 줄을 들었다).

- 요구사항 표의 **비기능 행이 전부** 이 표에 나온다. 빠진 요구가 있으면 미흡이다.
- 셋째 칸은 실행 출력의 줄이거나, 실행으로 확인할 수 없는 요구면 `실행 밖 — ` 뒤에 무엇으로 보였는지(계산 · 출처)를 적는다. 실행 밖을 숨기지 않는다 — 메모리 대역으로는 1,000만 연결을 재현할 수 없고, 그 사실을 표가 말해야 한다.
- 코드를 바꿔 실행한 결과(SD43)를 근거로 쓰면 셋째 칸에 `실행 밖 — 변형 실행(바꾼 것: …)` 으로 적고 정본 출력의 줄과 섞지 않는다(1.1.0).
- **지연 요구와 정확도 요구는 다른 행으로** 둔다. 정확도는 지연이 끝난 뒤의 값으로 적는다(예: 「입장 · 이탈이 멎고 3초 뒤 오차 1% 이내」) — 한 행에 섞으면 숫자가 늦게 따라오는 동안의 차이가 오차로 읽힌다(1.1.0).

### 실제 사례 (`example.realworld`) — 조건부

**출처 링크로 확인한 기업 사례가 있을 때만** 쓴다(SD32 ← PG21).

- 사례마다 회사 엔지니어링 글 · 발표 · 논문 · 공식 문서 링크를 단다. 표로 쓰면 행마다 그 칸에 단다(1.1.0). 링크로 확인하지 못한 사례는 싣지 않는다.
- 사례의 **무엇이 이 가이드 구조의 어느 상자 · 어느 단계에 해당하는가**를 매핑한다. 이름만 대고 넘어가지 않는다.
- 2차 자료(재게시 · 기사 · 요약)로만 확인한 사례는 2차 자료라고 밝힌다. 개발자 포럼의 사용자 증언은 "사용자 관찰"로만 쓴다.
- 한 글 안에서 수치가 어긋나는 사례(같은 행사의 시청자 수를 두 값으로 적는 등)는 그 수치를 인용하지 않거나 두 값을 함께 적는다.
- 확인된 사례가 하나도 없으면 절을 헤딩째 지운다(아래 조건부 절 규칙).

### 스스로 점검하기 (`selfcheck`)

본문을 정독해야 풀리는 문제 2~3개로 마무리한다(SD39). 다음 종류를 섞는다.

1. **수치 바꾸기** — 요구 수치 하나를 바꾸면(동시 접속 100배 · 허용 오차 0%) 고른 구조가 그대로 맞는가, 어느 후보로 옮기는가. 전환점을 실제로 써 보게 한다.
2. **구성 요소 멈추기** — 상자 하나가 멈추거나 메시지를 잃으면 시나리오의 어느 단계에서 무엇이 어긋나는가.
3. **순서 바꾸기** — 시나리오의 두 단계를 바꾸면(커밋 전에 잠금을 풀면 · 복제본에서 읽으면) 무엇이 조용히 틀리는가.

**문제마다 풀이를 둔다**(SD42 ← PG36). 문제는 들여쓰기 없는 번호 목록(`1. …`)이나 굵은 번호 문단(`**1. 수치 바꾸기.** …`)으로 쓰고, 그 문제 바로 뒤에 `> 풀이 — ` 로 시작하는 인용 블록을 둔다(번호 목록 안이면 들여 쓴 `   > 풀이 — `). 풀이에는 **답과 그 답을 낸 본문 자리**(시나리오 n 의 k단계 · 규모 추정의 식 · 전환점 · 요구 충족 확인 표의 행)를 함께 적고, 수치가 답이면 실행이나 손 검산으로 확인한 값만 쓴다. HTML 렌더러가 풀이 블록을 접어 두므로 먼저 풀어 볼 기회는 남는다. 검사기(`selfcheck`)가 문제 수와 풀이 수를 맞춰 본다.

### 참고 자료 (`refs`)

- **1차 자료를 앞에** 둔다 — 기업 엔지니어링 글 · 논문 · 공식 문서. 2차 자료는 뒤에, 2차라고 밝혀 둔다(SD36 ← PG25).
- 본문에서 출처로 단 링크는 **전부** 여기에 다시 모은다. 리서치 노트에만 있고 본문이 쓰지 않은 출처는 올리지 않는다. 검사기(`refs-links`)가 본문의 http · https 링크가 이 절에 있는지 견준다.
- 항목마다 그 자료가 **본문의 무엇을 뒷받침하는지** 한 구절과 게시일을 붙인다. 게시일을 확인하지 못했으면 `게시일 확인 안 함` 으로 적는다.
- 본문이 링크한 패턴 가이드 · 참고 문서도 여기에 올린다.

### 도식 — viz 컴포넌트로 저작한다 (← `gof-guide` 공통 블록)

도식은 본문에 문법으로 그리지 않는다. **가이드 폴더의 `diagrams/` 에 React 컴포넌트로 쓰고**, 렌더한 이미지를 본문이 가리킨다.

- 본문은 `![대체 텍스트](diagrams/<name>.png)` 로 싣는다. 대체 텍스트는 그 그림이 말하는 **주장 한 줄**이다.
- ` ```mermaid ` 펜스는 쓰지 않는다 — 검사기가 막는다.
- 도식 소스 머리에 `@relation` 과 `@viz-type VT-…`(카탈로그), 그 그림의 **주장**과 **출처**를 적는다. `bun run scripts/lint-diagrams.ts` 가 선언과 관계 어휘를 검사한다.
- 이 계열에서 쓰는 유형은 주로 넷이다 — C4 Container(`VT-110`, 개념도) · Cloud Architecture(`VT-115`, 개념도) · C4 Dynamic(`VT-113`, 시나리오 경로) · Sequence(`VT-108`, 시나리오 경로).
- C4 템플릿(`C4ContainerDiagram` · `C4DynamicDiagram`)을 `data` 로만 넘기면 화살표 이름(`label` · `technology`)이 그려지지 않는다(도식 패키지 0.3.0). children 방식으로 상자와 화살표를 직접 그려 화살표마다 통신 방식을 단다(SD7, 1.1.0). 파일럿 두 편의 `diagrams/_*-layout.tsx` 가 그 예다.
- 색 · 타이포는 `viz/style-guide` 토큰에서만 온다. 리터럴 색을 쓰면 검사가 막는다.
- ```text 도식은 개념 직후의 작은 그림(전후 비교 · 계산 흐름)에 쓴다. 개념도는 ```text 로 대신하지 않는다(SD7). 시나리오 경로 그림은 ```text 도식도 허용한다(SD11).

### 산출 위치와 버저닝 (← `gof-guide` 공통 블록)

가이드 한 편이 **폴더 하나**를 갖는다.

```text
pattern-guide/system-design-guide/<슬러그>/     ← 슬러그는 kebab-case(예: live-viewer-count)
  <슬러그>-guide_v<major>.<minor>.<patch>.md      ← 본문(최신은 버전이 가장 높은 파일)
  <슬러그>-guide_v<major>.<minor>.<patch>.html    ← 렌더 산출물
  code/      ← 세 언어 실행 파일과 기대 출력
  diagrams/  ← 도식 소스와 렌더 이미지
```

- **머리말** 에 `pattern` · `slug` · `spec` · `spec_version` · `version` · `status` · `date` 를 둔다. 이 계열에서 `pattern` 은 **다루는 문제의 이름**이다 — 검사기 계약상 키 이름을 그대로 쓴다. 사례 목록의 후보 ID 를 `case: RT-01` 로 함께 적는다.
- `status` 는 `draft`(집필 · 게이트 중) · `published`(게이트 통과) 다.
- **버전을 올리는 기준** — `major` 는 골격이 바뀔 때, `minor` 는 내용이 늘거나 줄 때(절 보완 · 코드 교체 · 도식 추가), `patch` 는 뜻이 바뀌지 않는 정정이다.
- **`status: draft` 인 동안에는 같은 파일을 고친다.** 통과한 뒤의 변경만 새 버전 파일을 만든다. 이전 버전 파일은 지우지 않는다.
- **최신을 가리킨다** — 인덱스 · 기준 예시 · 다른 가이드의 상호 링크는 최신 파일명을 쓴다. `check-guides --pointers` 가 낡은 포인터를 잡는다.
- 머리말 `spec_version` 이 현재 명세 version 과 다르면 검사가 실패한다.

### 리서치 노트를 입력으로 쓰는 법 (← `gof-guide` 공통 블록, 대응표는 이 계열에 맞게 바꿈)

집필 입력은 `paths.json` 의 `dirs.research` 에 있는 **사례 리서치 노트**다(예: `live-viewer-count-2026-11-13.md`). 노트의 항목은 가이드의 정해진 자리로 간다.

```text
노트 항목                                 가이드 절
──────────────────────────────────────    ─────────────────────────────────────
요구사항 근거("지연 없이"를 숫자로)       →  requirements 의 비기능 표 · 근거 칸
규모 추정 계산                           →  estimation
개념도 · 기술 설명 근거(판정 · 집계 · 전달) →  diagram · tech.item 의 네 칸
반례와 장애                              →  detail.scenario 의 시나리오 2 · 3
대안 비교 후보 구조와 전환점(판단)        →  alternatives
실제 사례 대응표                          →  example.realworld
구현 코드 메모                           →  example.context · example.impl
미해결 질문                              →  집필 전에 읽는다 — 본문에서 단정하지 않는다
```

- **노트는 입력이지 검색 금지가 아니다.** 집필 중 새 근거가 필요하면 추가로 조사한다. 노트에 없는 사실을 본문에 쓰면 그 자리에 출처를 달고 `refs` 에도 올린다(SD35 ← PG24).
- 노트의 「(판단)」 표시는 출처로 확정된 사실이 아니다. 본문에 옮길 때도 이 가이드의 판단이라는 것이 보이게 쓴다.
- 노트의 수치는 요약 도구로 읽은 값일 수 있다. **본문에 수치를 인용하기 전에 원문과 대조한다**(SD40). 대조는 수치 문자열만 보지 않는다(1.1.0). 같은 글 안의 다른 값(같은 행사의 시청자 수를 두 값으로 적는 등), 원문 문장의 대상(댓글에 대한 제한인지 전달 전체인지), 동사의 강도(감당하도록 만들었다 · 다뤘다 · 예상한다)를 함께 본다. 다른 값이 있으면 두 값을 함께 적거나 쓰지 않는다. 파일럿 두 편의 1라운드 미흡 가운데 다섯이 이것이었다.
- 「미해결 질문」에 걸린 사실은 본문에서 단정하지 않는다.

### 출처를 다루는 법 — 본문은 출처 없이 읽힌다 (← PG30 · PG31)

- **출처의 위치 지시자**(`그림 n` · `§n.n` · `n장 「…」` · "그 글의 X 절")는 `(근거: …)` 괄호와 `## 참고 자료` 에서만 쓴다(SD37). 검사기(`self-contained`)가 본문에서 잡는다.
- **권위 인용은 설명이 아니다**(SD38). "Netflix 도 그렇게 한다", "Discord 가 그 방식을 골랐다"는 근거 표시일 뿐이다. 그 선택이 **왜** 이 문제에서 맞는지 — 수치 · 반례 · 절차 — 가 본문에 따로 있어야 한다.
- 기업 사례의 이름과 제품 이름은 쓴다. 막는 것은 위치 지시자와 "그 회사가 그랬다"로 끝나는 설명이다.

### 조건부 절 규칙 (← PG23)

`sections[]` 에서 `required: false` 이고 `condition` 이 있는 절이 조건부다(이 명세에서는 `example.realworld` 하나).

- 조건에 해당하지 않으면 **절을 헤딩째 지운다**(SD34). 본문에 "해당 없음" 같은 집필 메타를 남기지 않는다. 생략 사유는 품질 게이트 보고에만 한 줄로 남긴다.
- 캔버스의 조건 블록 표식(`@if` · `@end`) · 집필 지시(`@write`) · 슬롯은 최종본에서 전부 없앤다.
- 조건부가 아닌 절은 지울 수 없다.

### 채점 규약 — 채점자마다 달라지지 않게 고정한 것 (← `gof-guide` 공통 블록)

- **산문 연속 상한(voice V1)** 은 `golden.py measure <가이드> --spec system-design-guide --project . --voice ppangtolab-teacher` 의 `voice_compliance.max_prose_run_without_visual` 이 2 이하인지로 판정한다.
- **사실 주장은 채점이 검증한다.** 본문이 출처 · 실행 결과 · 계산에 대해 단정한 자리는 채점자가 원문과 대조하거나 다시 계산해 참 · 거짓을 가른다. 외부 모델 비평(외부 검토)은 쓰지 않는다(2026-09-20 유저 결정).
- **공통 루브릭의 H축(이해 게이트)은 판정하지 않는다**(해당없음). `commands.comprehension_gate` 가 없다고 미흡으로 치지 않는다 — 기존 명세 1.2.0 · 1.3.0 의 유저 결정이고(커밋 `131b95c`), 이 명세도 따른다.
- **기계와 채점의 분담** — 헤딩(SD1) · 시나리오 개수 · 번호 · 단계 수(SD9 의 일부) · 펜스 규약과 세 언어 출력(SD22 · SD23 · SD25 · SD26 · SD27) · 위치 지시자(SD37) · 근거 괄호 대조는 **검사기**가 판정한다. 시나리오 종류 셋 · 단계의 "왜" · 개념도와 기술 항목의 1:1 · 대안 비교 · 전환점 · 요구 충족 표의 빠짐 · 수치의 출신은 **채점**이 판정한다.
- **근거 없는 평가 수치를 싣지 않는다**(SD33 ← PG22). 난이도 별점 · "실무 활용도 높음" 같은 측정되지 않은 값은 본문 어디에도 없다.
