# 분석 패턴 가이드 — 항목별 작성 방법

> **층: L2 (글 명세)** · 적용 voice: `ppangtolab-teacher` · 캔버스: `paths.json` 의 `templates.analysis-guide-canvas` · 산출 위치: `dirs.analysis`
> 출처: 구 `template.md`·구 `SKILL.md`·구 가이드(`account-pattern.md`)·DDD 인덱스 README 비고 역추출 + code_test `ds-guide` 계승 +
> 루트 카드 KAN-001-YXTC2C 「전략」 절(결정 11건·새 골격·analysis-guide 차이·코드 검사 계약) + 유저 요청서.
> 문체(존댓말·도식·산문 연속 상한·기억법 등)는 voice 소유라 여기 쓰지 않는다.

## 이 글은 무엇인가

Fowler *Analysis Patterns* 의 분석 패턴 **하나를 DDD 원칙을 지키는 모델로 설명하는 독립 가이드**다.
골격은 `gof-guide` 와 같고, 유저 요청서가 분석 패턴에만 붙인 요구가 이 트랙을 따로 세웠다.

> "분석 패턴의 경우, 반드시 DDD 원칙을 준수해야 한다. 또한, 오해가 없도록, 구체적인 배경을 전제해야 한다.
> 예를 들어, transaction과 account 패턴을 설명할 때 entry는 transaction이 가지고 있을 수도 있고, account가 가질 수도 있으며
> 홀로 존재할 수도 있고, 혹은 별도 entity로 존재하나 account entity에 그에 대한 VO를 가지고 있을 수도 있다.
> 그래서 정확한 상황 설정이 중요하다." — 유저 요청서

```text
개요 ─▶ 자세히 들여다보기 ─▶ 사용 목적 ─▶ 경계 ─────────────▶ 구현 예시 ───────────────────────────▶ 스스로 점검 ─▶ 참고 자료
        (개념과 정의                     (최소 조건            (상황 설정 + MUST 표
         → 동작 절차)                     → 차이)               → 구현(java·typescript·rust, 표와 1:1)
                                                               → 상황이 달라지면 · 조건부
                                                               → 실제 사례 · 조건부)
```

컨테이너 절 셋 — `## 패턴 자세히 들여다보기`(`detail`) · `## 패턴의 경계`(`boundary`) · `## 구현 예시`(`example`) — 은
자기 본문 없이 하위 `###` 절만 담는다. 헤딩 바로 아래에 도입 산문을 길게 두지 않는다.

### 왜 트랙이 따로 있는가

구 가이드는 aggregate 경계를 정의하지 않은 채 **경계를 암시하는 코드**를 실었다 —
`account-pattern.md` 의 `Account { List<Entry> }`, `transaction-pattern.md` 의 `e.account.post()`,
`posting-rule-pattern.md` 의 Account 객체 인자. 같은 Entry 가 네 곳에 소속될 수 있으므로,
상황을 먼저 못 박지 않은 코드는 독자마다 다른 모델로 읽힌다. 그래서 이 트랙은 **상황 설정 표를 MUST 로** 두고
구현이 그 표를 1:1로 따르게 한다.

이 전용 규칙을 한 spec 의 조건부 항목으로 두면 GoF 쪽에서 IF-APPLICABLE 로 약해지고 워커가 "정당한 생략"을
스스로 판단하게 된다. 최소 조건의 판정 기준도 다르다(코드 구조 / 개념적 책임 분리). 그래서 spec 을 둘로 나눴다(루트 카드 결정 1).

### `gof-guide` 와 무엇이 다른가

| 절 | `gof-guide` | `analysis-guide` |
| --- | --- | --- |
| `detail.terms` | 원전 participants 를 센다 | **분석 층위 개념만** 센다. DDD 전술 분류는 매기지 않는다 |
| `boundary.minimum` 판정 기준 | 코드 구조 | **개념적 책임 분리 + 모델 불변식** |
| `example.context` | 도메인·요구 전제 | 도메인·요구 전제 + **MUST 표 4행** |
| `example.impl` | 같은 상황을 세 언어로 | + **표와 1:1**, **aggregate 간 객체 참조 0** |
| `example.alternatives` | 없음 | `### 상황이 달라지면` (조건부, 회계 계열은 사실상 필수) |
| `example.realworld` 헤딩 | `### 실제 라이브러리에서` | `### 실제 사례` |

### 구 양식(9섹션)에서 무엇이 어디로 갔나

`gof-guide` 와 같다(루트 카드 결정 11). 다만 구 가이드의 "사례를 통한 예시" 코드는 **경계를 정하지 않은 코드**라
구현의 재료로 쓰지 않는다 — 사실(개념·불변식) 확인용으로만 읽는다.

| 구 절 | 새 자리 |
| --- | --- |
| 한 줄 요약 · 분류 · 다른 이름 | `overview` |
| 상세 설명 | `overview` + `detail.terms` + `detail.procedure` |
| `## 디자인 패턴을 충족하는 최소 조건` | `### 디자인 패턴을 충족하는 최소 조건` (문구 유지, `[필수]`/`[선택]`) |
| 흔히 오해하는 지점 · 장점과 단점, 한계점 | `boundary.compare` |
| 사례를 통한 예시 | `example.context` + `example.impl` + `example.alternatives` + `example.realworld` |
| 어떨 때 사용하나 | `purpose` |
| 정보 표 | **삭제** |
| Class Diagram | `detail.terms` 정의 직후 |
| 참고 자료 | `refs` |

공통 규칙은 아래 공유 블록에, 분석 트랙에만 걸리는 규칙은 그 뒤 「분석 트랙 전용 작성법」에 있다.

## 공통 작성법 — 두 트랙이 같이 쓰는 규칙

> 이 블록은 `gof-guide` 와 `analysis-guide` 두 `spec.md` 에 **바이트 단위로 같게** 들어 있다.
> 한쪽만 고치지 않는다. 고칠 때는 두 파일을 함께 고치고 공유 블록 동일성 검사를 돌린다.
> 트랙마다 다른 규칙은 이 블록 밖, 각 `spec.md` 의 트랙 전용 절에 있다.
> 괄호 안의 `PG` 코드는 `spec.json` 의 `principles[]` 다 — 게이트는 그 문장으로 채점한다.

### 리서치 노트를 입력으로 쓰는 법

집필 입력은 둘이다. `paths.json` 의 `dirs.research` 에 있는 **리서치 노트**와, 같은 경로에 덮어쓸 **기존 가이드**.

노트는 패턴마다 한 절이고, 각 항목은 가이드의 정해진 자리로 간다.

```text
노트 항목                               가이드 절
────────────────────────────────────    ─────────────────────────────────────
주장 · 원전 위치(장·절)               →  overview · refs
participants 대응 / 분석 개념         →  detail.terms
collaborations 대응                   →  detail.procedure
비교 대상 2개 이상과 그 근거          →  boundary.compare
실제 사용처(출처 확인분)              →  example.realworld
미해결 질문                           →  집필 전에 읽는다 — 본문에서 단정하지 않는다
```

- **노트는 입력이지 검색 금지가 아니다.** 집필 중 새 비교 대상이나 구현 쟁점이 나오면 추가로 조사한다.
- 노트에 없는 사실(원전 인용·API 동작·역사·사용처)을 본문에 새로 쓰면 **그 자리에 출처를 달고 `refs` 에도 올린다**(PG24).
- 추가 조사 결과는 노트의 「미해결 질문」에 되먹인다. 여러 워커가 병렬로 쓸 때는 한 노트를 동시에 고치지 않도록 게이트 보고에 적어 두고 메인이 옮긴다.
- 「미해결 질문」에 걸린 사실은 본문에서 단정하지 않는다. 출처를 찾아 해소하거나 본문에서 뺀다.
- **기존 가이드는 사실 확인용 입력이다. 문장을 옮기지 않는다.** 목소리와 골격이 바뀌었으므로 다시 쓴다.
  기존 가이드에만 있고 노트에 없는 주장은 출처를 확인한 뒤에만 쓴다.

### 제목 + 부제 (`title`)

`# {패턴} — {직관을 담은 부제}`. `{패턴}` 자리는 원전의 패턴 이름이다.
부제는 이 패턴의 **비결을 한 구절로** 예고한다. 분류명이나 "가이드" 같은 낱말로 채우지 않는다.

### 한눈에 보는 개요 (`overview`)

이 절만 읽고 닫아도 "무엇을 풀려고 무엇을 하는 패턴인가"를 들고 나가게 쓴다. 네 가지가 모두 있어야 한다(PG2).

1. **문제** — 패턴 없이 쓰면 무엇이 어디서 아픈가. 구체 상황 하나로 보인다.
2. **해결의 직관** — 그 아픔을 패턴이 어떤 한 수로 없애는가.
3. **그림 1개** — 문제 → 해결의 전후가 한눈에 보이게(```text 도식 또는 mermaid).
4. **분류 · 함께 쓰는 패턴 한 줄** — 분류(GoF 는 생성·구조·행위, 분석 패턴은 원전의 장 범주)와 자주 함께 쓰는 패턴을 한 줄에.

- 정의·절차·코드는 여기서 풀지 않는다. 뒤 절이 한다.
- 활용성 별점·학습 난이도 같은 **평가 수치를 싣지 않는다**(PG22). 측정된 적 없는 값이다. 본문 어디에서도 같다.

### 등장하는 개념과 정의 (`detail.terms`)

**이 패턴에 등장하는 개념을 빠짐없이 정의한다**(PG3). 이름만 나열하면 미흡이다.

- 개념마다 **무엇을 책임지는가 · 누구와 협력하는가**를 적는다.
- 판정 기준은 "뒤에서 튀어나오는 이름"이다. 개요·절차·경계·구현 어디에서든 역할이나 개념 이름이 쓰이면 이 절에 정의가 있어야 한다.
- 무엇을 "개념"으로 세는가는 트랙마다 다르다 — 트랙 전용 절을 본다.
- 정의 목록 **바로 뒤에 mermaid `classDiagram` 1개**를 둔다(PG4). 그림의 클래스 이름과 정의 목록의 이름은 1:1이다.
  정의에 없는 클래스가 그림에 있거나, 정의한 이름이 그림에 없으면 미흡이다.

### 동작 절차 (`detail.procedure`)

역할들이 **어떤 순서로 협력해 요청 하나를 처리하는가**를 번호 단계로 쓴다(PG5).

- 한 단계 = 한 협력(누가 누구에게 무엇을 넘기는가).
- **단계마다 "왜"를 붙인다.** 왜 그 역할이 그 일을 맡는가, 또는 순서를 바꾸면 무엇이 깨지는가. 이유 없는 단계가 하나라도 있으면 미흡이다.
- 절차가 갈라지면(처리할지 넘길지, 생성할지 재사용할지) 갈래마다 단계를 따로 적는다. "경우에 따라"로 뭉개지 않는다.
- mermaid `sequenceDiagram` 이나 ```text 도식을 곁들여도 된다. 그림이 단계 서술을 대신하지는 않는다.

### 사용 목적 (`purpose`)

**어떤 단서가 보일 때 이 패턴을 꺼내는가**를 쓴다. 가이드의 실전 가치가 대부분 여기서 나온다 —
구조는 검색하면 나오지만 "언제 꺼내야 하는가"는 잘 안 나온다.

- 단서를 **구체 상황으로 2개 이상** 적는다(PG6). 좋은 단서는 코드나 요구에서 **관찰되는 것**이다.
  - 나쁜 예: "유연성이 필요할 때", "확장성을 높이고 싶을 때" — 관찰할 것이 없다.
  - 좋은 예: "같은 `switch` 가 세 곳에 복제돼 있고, 결제 수단이 하나 늘 때마다 셋을 함께 고친다."
- **쓰지 말아야 할 경우를 1개 이상**, 쓰면 무엇을 잃는지와 함께 적는다(PG7).
- 비슷한 단서에서 다른 패턴을 고르게 되는 경우는 여기서 한 줄로 예고만 하고, 차이는 `boundary.compare` 에서 푼다.

### 디자인 패턴을 충족하는 최소 조건 (`boundary.minimum`)

"어떤 코드·모델을 이 패턴이라고 불러도 되는가"의 판정 기준이다.
**이 헤딩 문자열은 design-pattern-analyzer 가 기준을 읽어 가는 계약이다 — 한 글자도 바꾸지 않는다**(PG1).

- 조건마다 **맨 앞에 `[필수]` 또는 `[선택]`** 을 붙이고, `[필수]` 는 1개 이상이다(PG8).
  analyzer 는 `[필수]` 미충족을 "패턴 아님" 쪽으로, `[선택]` 미충족을 보강 권장으로 다룬다.
  그러니 **빠지면 그 패턴이 아니게 되는 것만 `[필수]`** 다.
- `[필수]` 조건마다 **그 조건이 빠지면 무엇이 되는가**를 구체 반례로 붙인다(PG9) — 비슷한 패턴, 안티패턴, 또는 그냥 분기문.
  조건을 선언만 하고 넘어가면 미흡이다.
- 패턴이 항상 유지해야 하는 **불변식은 이 절의 조건 항목으로 올린다**(PG10). 산문 속에 "항상 ~해야 한다"로 묻어 두면 analyzer 가 못 읽는다.
- 조건의 **판정 기준이 무엇인가**(코드 구조인가, 개념적 책임 분리인가)는 트랙마다 다르다 — 트랙 전용 절을 본다.

형식 예:

```text
1. [필수] <조건 이름> — <판정 기준 한 문장>
   빠지면: <무엇이 되는가 — 반례>
2. [선택] <조건 이름> — <판정 기준 한 문장>
```

### 비슷한 패턴·안티패턴과의 차이 (`boundary.compare`)

패턴은 여러 방식으로 구현될 수 있어서, 경계는 **이웃과의 차이**로 드러난다.

- 비교 대상은 **2개 이상**이다(PG11). 구조가 닮은 패턴, 같은 단서에서 떠오르는 패턴, 이 패턴으로 오해받는 안티패턴 중에서 고른다.
  리서치 노트의 비교 대상과 트랙 전용 절의 필수 포함 대상을 먼저 확인한다.
- **차이점 위주**다(PG12). 대상마다 **구분 기준 한 문장을 먼저** 둔다. "의도가 다르다"로 끝내지 않고,
  코드나 모델에서 확인할 수 있는 기준으로 쓴다 — 예: "교체를 누가 결정하는가: 클라이언트(Strategy) / 상태 객체 자신(State)".
  공통점 나열로 분량을 채우지 않는다.
- 대상마다 **이 패턴을 고르면 무엇을 얻고 무엇을 포기하는가**를 적는다(PG13).
  구 양식의 「장점과 단점, 한계점」은 여기로 흡수됐다. 장단점을 따로 목록으로 늘어놓지 않고 비교의 맥락에서 쓴다.
- 이 패턴처럼 보이지만 아닌 **오인 코드**를 보일 때는 펜스 정보 문자열에 `no-compile` 을 단다(PG14).
  `### 구현` 밖의 펜스는 컴파일 검사 대상이 아니고, 이 표식이 "일부러 보인 반례"라는 신호다.

  ````text
  ```java no-compile
  // 분기를 메서드로 뽑았을 뿐, 교체 지점이 없다
  ```
  ````

- 대상이 셋 이상이면 요약 표(대상 · 구분 기준 · 얻는 것 · 포기하는 것)로 모아도 된다. 다만 표로 끝내지 않는다 —
  가장 헷갈리는 한 쌍은 산문과 코드로 풀어 준다.

### 구현 — 펜스 규약 (`example.impl`)

`### 구현` 은 **컴파일 검사를 받는 유일한 절**이다. 아래 규약은 `commands.compile` 이 기계로 검사한다.
컴파일은 하한일 뿐 정확성 검증이 아니다 — 코드가 본문 주장과 맞는지는 품질 게이트와 외부 검토가 본다.

1. **펜스는 정확히 3개, 순서는 `java` → `typescript` → `rust`**(PG16). 다른 언어, 추가 펜스, `no-compile` 표식은 이 절에 두지 않는다.
2. **세 펜스는 사이에 산문·헤딩 없이 연달아 둔다**(PG16). md 에서는 나열로 읽히고,
   HTML 파생본에서는 렌더러가 세 펜스를 탭 묶음 하나로 만든다. 그래서 본문에 "위 탭에서" 같은 화면 지시어를 쓰지 않는다.
3. **자기완결**(PG17). 펜스 하나를 그대로 파일 하나로 저장해 단독 컴파일돼야 한다.
   기준은 Java 21 · TypeScript strict 모드 · Rust 2021 edition 이다.
   - 다른 펜스나 외부 파일의 타입을 가정하지 않는다.
   - import·use 를 빠뜨리지 않는다.
   - `...` 같은 생략 표기를 쓰지 않는다. 빈 펜스는 실패다.
4. **표준 라이브러리만**(PG18). 외부 crate·npm 패키지·Maven 의존은 0이다.
5. **같은 상황을 세 언어로**(PG19). `example.context` 의 시나리오 하나를 같은 역할·타입 이름으로 세 번 구현한다.
   - 언어 관용 차이는 허용한다 — Java `interface` / TypeScript `interface`·`type` / Rust `trait`.
   - 언어마다 다른 도메인·다른 시나리오면 미흡이다.
   - 세 펜스 모두 시나리오를 실제로 호출하는 진입점을 갖는다 — Java `main` · TypeScript 최상위 호출 · Rust `fn main`.
6. **해설은 세 펜스 뒤에 한 번**(PG20). 핵심 라인을 짚을 때는 세 언어의 대응 줄을 함께 가리킨다.
   같은 해설을 언어마다 세 번 반복하지 않는다. 예시 타입 ↔ 역할 매핑이 `example.context` 에 없으면 여기서 한다(PG15).

### 실제 사용처 (`example.realworld`)

조건부 절이다. **출처 링크로 확인한 사용처가 있을 때만** 쓴다(PG21). 헤딩 문구는 트랙마다 다르니 `sections[]` 를 따른다.

- 사용처마다 공식 문서·소스 저장소·원문 링크를 단다. 링크로 확인하지 못한 사용처는 싣지 않는다.
  "많은 프레임워크가 쓴다" 같은 무출처 서술도 같은 취급이다. 이 규칙은 개요·비교 등 다른 절에서 사용처를 언급할 때도 같다.
- 사용처의 **무엇이 패턴의 어느 역할·개념인가**를 매핑한다. 이름만 대고 넘어가지 않는다.
- 사용처 코드 조각은 `### 구현` 밖이라 컴파일 검사 대상이 아니다. 필요한 만큼만 짧게 싣는다.
- 확인된 사용처가 하나도 없으면 **절을 헤딩째 지운다**(아래 조건부 절 규칙).

### 스스로 점검하기 (`selfcheck`)

본문을 정독해야 풀리는 문제로 마무리한다. 다음 종류를 섞는다.

1. **경계 판정 문제** — 짧은 코드나 모델을 주고 `boundary.minimum` 의 조건을 적용해 이 패턴인지 판정하게 한다(PG26).
2. **비교 판별 문제** — 비슷한 두 패턴 중 어느 쪽인지, 구분 기준을 근거로 고르게 한다.
3. **책임·순서 문제** — 절차의 두 단계를 바꾸거나 한 역할의 책임을 다른 역할로 옮기면 무엇이 조용히 깨지는지 추적하게 한다.

문제 속 코드에는 `no-compile` 을 달지 않는다(PG14) — 표식이 답을 흘린다.

### 참고 자료 (`refs`)

- **원전을 맨 앞에**, 장·절(또는 쪽)까지 적는다(PG25).
- 본문에서 출처로 단 링크는 **전부** 여기에 다시 모은다. 리서치 노트에만 있고 본문이 쓰지 않은 출처는 올리지 않는다.
- 항목마다 그 자료가 **본문의 무엇을 뒷받침하는지** 한 구절을 붙인다.

### 조건부 절 규칙

`sections[]` 에서 `required: false` 이고 `condition` 이 있는 절이 조건부다.

- 조건에 해당하지 않으면 **절을 헤딩째 지운다**(PG23). 본문에 "해당 없음"·"이 절은 생략한다" 같은 집필 메타를 남기지 않는다.
- 생략 사유는 **품질 게이트 보고에만** 한 줄로 남긴다.
- 캔버스의 조건 블록 표식(`@if` · `@end` 주석)·집필 지시(`@write` 주석)·슬롯은 절을 남기든 지우든 최종본에서 전부 없앤다.
- 조건부가 아닌 절은 지울 수 없다. 쓸 내용이 없어 보이면 리서치가 모자란 것이다.

## 분석 트랙 전용 작성법

### 등장하는 개념과 정의 — 분석 층위만 센다 (AG1)

- **분석 층위 개념**은 패턴이 모델링하는 도메인 개념과 그 관계다. 예: Account 패턴이면 Account · Entry 와 둘의 연관·다중도.
- **DDD 전술 분류(Entity · Value Object · Aggregate)를 여기서 매기지 않는다.** 같은 개념이 상황에 따라 다른 분류가 되기 때문이다 —
  요청서의 Entry 예가 그 증거다. 분류는 `example.context` 의 표가 한다.
- 정의 직후의 `classDiagram` 도 개념 모델(연관·다중도)로 그린다. `<<Entity>>`·`<<ValueObject>>` 같은 전술 분류 스테레오타입을 달지 않는다.

### 최소 조건 — 개념적 책임 분리와 모델 불변식으로 판정한다 (AG2)

- 조건은 **"어떤 개념이 무엇을 책임지는가"** 와 **"모델이 항상 지키는 불변식"** 으로 쓴다.
- 특정 클래스 구조·필드 배치·상속·컬렉션 소유를 조건으로 삼지 않는다. 같은 패턴도 aggregate 배정에 따라 코드 구조가 달라진다.
- 나쁜 예: "`[필수]` Account 가 Entry 목록을 필드로 갖는다" — 여러 배정 중 하나를 패턴의 조건으로 굳혔다.
- 좋은 예: "`[필수]` 잔액은 항목들로 설명된다 — 어느 시점의 잔액도 그 시점까지 기록된 항목의 합과 같다.
  빠지면: 잔액이 왜 그 값인지 답할 수 없는 단일 잔액 필드가 된다."

### 상황 설정 (`example.context`) — MUST 표 (AG3 · AG4 · AG5)

표 앞에서 `gof-guide` 와 같은 직무를 먼저 한다 — 도메인 하나와 요구 전제, 예시 타입 ↔ 개념 매핑(PG15).
그다음 **아래 표를 그대로** 싣는다. 헤더와 행 라벨의 문구·순서를 바꾸지 않는다(AG3).

```text
| 항목 | 이 가이드의 설정 |
| --- | --- |
| bounded context | <한 줄 — 이 모델이 의미를 갖는 경계> |
| 불변식의 위치 | <어떤 불변식을 어느 aggregate root 가 지키는가> |
| root·entity·VO 배정 | <개념마다 root / entity / VO 중 하나, 어느 aggregate 소속인가> |
| 타 aggregate 참조 방식 | <id 참조 — 무엇이 무엇을 어떤 id 로 가리키는가> |
```

- 행은 **정확히 4개**, 빈 칸 없음. `bounded context` 칸은 한 줄이다.
- `타 aggregate 참조 방식` 은 **id 참조**다(AG5). 다른 aggregate 를 객체로 들고 있는 배정은 이 트랙에서 쓰지 않는다.
- 불변식의 위치는 `boundary.minimum` 에 올린 불변식 조건과 이어져야 한다 — 조건에 있는 불변식이 표에서 주인 없이 떠 있으면 안 된다.

> **잠정 규칙 — DDD 전술 용어 한 줄 정의 (AG4)**
> 표 안에서 처음 쓰는 DDD 전술 용어(Bounded Context · Aggregate · Aggregate Root · Entity · Value Object 등)는
> **표 셀 안 괄호나 표 바로 아래 목록에서 한 줄로** 정의한다.
> 이 규칙은 잠정이다. 유저가 "DDD 전술 용어 기준선 문서" 신설을 결정하면(루트 카드 결정 8, 리서치 후보 보고) 한 줄 정의는
> 그 문서로의 링크로 대체하고 이 spec 을 개정한다.

#### 회계 계열 — 배경 확정안 인용 (AG9)

**Account · Transaction · Posting Rule** 세 편은 `example.context` 에서 **회계 배경 확정안**을 링크로 인용한다.
확정안은 `paths.json` 의 `dirs.research` 아래 `accounting-context.md` 이고, 유저가 확정한 bounded context · aggregate 경계와 일관성 요구 ·
root/entity/VO 배정 · 참조 방식을 담는다. 이 세 편의 표 네 칸은 **확정안과 어긋나지 않아야 한다.**

- 세 편에만 적용하고, 세 편에는 예외 없이 적용한다. 확정안 없이 쓰면 consideration 두 문서 중 하나와 반드시 모순된다.
- 확정안에 없는 경계 결정을 새로 해야 하면 본문에서 정하지 않는다 — 게이트 보고에 올리고 멈춘다.

#### 값 객체 계열 — 1.0 에서는 MUST 유지

**Quantity · Range · Measurement · Observation** 에서는 표의 aggregate 관련 칸이 비거나 자명해질 수 있다.
1.0 에서는 MUST 를 유지한다 — 칸을 비우지 말고, 그 개념이 어느 aggregate 에 참여하는지(참여하는 aggregate 를 이 가이드가 정하지 않는다면 그 사실과 이유)를 적는다.
**파일럿 Quantity 로 실측해 1.1 에서 처분한다**(유지 / IF-APPLICABLE / 갈래별 표).

### 구현 (`example.impl`) — 표와 1:1 (AG6 · AG7 · AG8)

공통 펜스 규약(PG16~PG20)에 더해 세 가지가 걸린다.

1. **표와 1:1**(AG6).
   - aggregate root 타입은 표가 root 로 배정한 개념뿐이다.
   - entity 는 식별자를 갖는다. VO 는 식별자 없이 불변이고, 같음을 값으로 판단한다.
   - `불변식의 위치` 칸이 가리킨 root 의 메서드가 그 불변식을 **실제로 검사한다**. 표에는 있는데 코드가 검사하지 않으면 미흡이다.
2. **aggregate 간 객체 참조 0**(AG7).
   - aggregate 로 배정된 타입의 필드와 메서드 시그니처에 **다른 aggregate 의 타입이 나오지 않는다.** 다른 aggregate 는 id 타입(예: `AccountId`)으로만 가리킨다.
   - 여러 aggregate 를 함께 다루는 흐름은 aggregate 밖(시나리오 진입점이나 서비스 함수)이 id 로 찾아 조립한다.
   - 구 가이드의 `Entry(Account account, …)`, `e.account.post(…)` 가 정확히 금지 대상이다.
3. **root 경유 변경**(AG8). aggregate 안의 entity·VO 는 root 의 메서드로만 바뀐다.
   root 밖으로 가변 컬렉션이나 child 의 상태 변경 메서드를 노출하지 않는다 — 읽기용으로 내보낼 때는 복사본이나 읽기 전용 뷰로.

### 상황이 달라지면 (`example.alternatives`) — 조건부 (AG10 · AG11)

**조건**: 이 패턴의 개념을 aggregate 로 묶는 경계 선택지가 둘 이상 성립할 때. 해당 없으면 헤딩째 지운다(공통 조건부 절 규칙).

상황이 바뀌면 경계가 어떻게 바뀌는지를 **상황 · 경계 · 이유** 세 열의 표로 보인다(AG10).

- **이 가이드가 고른 경계도 한 행으로** 넣는다. 그래야 다른 행과 나란히 비교된다.
- `상황` 칸은 그 경계가 맞는 업무 조건(일관성 요구 · 동시 처리 · 조회 방식 등), `경계` 칸은 누가 root 이고 무엇이 누구 안에 있는가,
  `이유` 칸은 그 조건에서 그 경계가 지키는 불변식이나 치르는 비용이다.

**회계 계열(Account · Transaction · Posting Rule)은 사실상 필수**이고, 요청서가 든 **Entry 소속 네 가지가 각각 한 행**이 된다(AG11).

```text
| 상황 | 경계 | 이유 |
| --- | --- | --- |
| … | Entry 를 Transaction 이 가진다 | … |
| … | Entry 를 Account 가 가진다 | … |
| … | Entry 가 홀로 존재한다 | … |
| … | Entry 는 별도 entity 로 존재하고, Account 가 그에 대한 VO 를 가진다 | … |
```

회계 계열의 `이유` 칸은 배경 확정안의 일관성 요구 항목(차변·대변 균형 · 중복 전기 방지 · 취소/정정 · 동시 처리 · 파생 잔액의 지연 허용)에 기대어 쓴다.

### 실제 사례 (`example.realworld`) — 조건부 (AG12)

- 분석 패턴의 사례는 라이브러리 API 보다 **시스템 · 표준 · 공개 문서**인 경우가 많다. 출처 링크로 확인한 것만 싣는다(PG21).
- 사례마다 그 시스템·문서의 **어느 개념이 패턴의 어느 개념에 대응하는가**를 매핑한다.
- 확인된 사례가 없으면 절을 헤딩째 지운다.
