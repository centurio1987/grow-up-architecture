# GoF 디자인 패턴 가이드 — 항목별 작성 방법

> **층: L2 (글 명세)** · 적용 voice: `ppangtolab-teacher` · 캔버스: `paths.json` 의 `templates.gof-guide-canvas` · 산출 위치: `dirs.content`/<계열>/<패턴>/
> 출처: 구 `template.md`·구 `SKILL.md`·구 가이드(`strategy-pattern.md`) 역추출 + code_test `ds-guide` 계승 +
> 루트 카드 KAN-001-YXTC2C 「전략」 절(결정 11건·새 골격·코드 검사 계약·HTML 버전) + 유저 요청서.
> 문체(존댓말·도식·산문 연속 상한·기억법 등)는 voice 소유라 여기 쓰지 않는다.

## 이 글은 무엇인가

GoF 23 패턴 중 **하나를 다루는 독립 가이드**다. 유저 요청서가 정한 네 요소가 `##` 절이 된다.

1. 패턴의 핵심을 직관적으로 이해할 수 있는 개요 → `overview`
2. 등장 개념 전수 정의 · 절차 전수 설명과 그 이유 → `detail.terms` · `detail.procedure`
3. 패턴의 경계 · 불변식 · 비슷한 패턴/안티패턴과의 차이 → `boundary.minimum` · `boundary.compare`
4. 실제 구현 예시 → `example.context` · `example.impl` · `example.realworld`

여기에 code_test `ds-guide` 의 "언제 이걸 꺼내야 하는가"(`when.clue`)를 계승한 `purpose`,
voice 가 요구하는 `selfcheck`, L0 evidence 가 요구하는 `refs` 가 붙는다.

```text
개요 ─▶ 자세히 들여다보기 ─▶ 사용 목적 ─▶ 경계 ─────────────▶ 구현 예시 ──────────────────────▶ 스스로 점검 ─▶ 참고 자료
        (개념과 정의                     (최소 조건            (상황 설정
         → 동작 절차)                     → 차이)               → 구현(java·typescript·rust)
                                                               → 실제 라이브러리에서 · 조건부)
```

컨테이너 절 셋 — `## 패턴 자세히 들여다보기`(`detail`) · `## 패턴의 경계`(`boundary`) · `## 구현 예시`(`example`) — 은
자기 본문 없이 하위 `###` 절만 담는다. 헤딩 바로 아래에 도입 산문을 길게 두지 않는다.

### 구 양식(9섹션)에서 무엇이 어디로 갔나

기존 가이드를 입력으로 읽을 때 대응표로 쓴다(루트 카드 결정 11).

| 구 절 | 새 자리 | 비고 |
| --- | --- | --- |
| 한 줄 요약 · 분류 · 다른 이름 | `overview` | 분류는 개요 마지막 한 줄로 |
| 상세 설명 | `overview` + `detail.terms` + `detail.procedure` | 의도·문제·해결은 개요, 용어는 정의 절, 협력은 절차 절 |
| `## 디자인 패턴을 충족하는 최소 조건` | `### 디자인 패턴을 충족하는 최소 조건` | 문구 유지, 레벨만 `###`. 조건마다 `[필수]`/`[선택]` |
| 흔히 오해하는 지점 | `boundary.compare` | |
| 사례를 통한 예시 | `example.context` + `example.impl` + `example.realworld` | 예시 1개를 세 언어로 |
| 어떨 때 사용하나 · 사용하면 안 되는 경우 | `purpose` | |
| 장점과 단점, 한계점 | `boundary.compare` 에 흡수 | 비교 맥락의 "얻는 것 / 포기하는 것" 으로 |
| 정보 표 | **삭제** | 활용성 별점·학습 난이도는 근거 없는 수치 |
| Class Diagram · 역할 설명 | `detail.terms` 정의 직후 | |
| 참고 자료 | `refs` | |

`analysis-guide` 와는 골격이 같고, 개념을 세는 기준·최소 조건의 판정 기준·상황 설정 표·조건부 절 하나가 다르다.
공통 규칙은 아래 공유 블록에, GoF 트랙에만 걸리는 규칙은 그 뒤 「GoF 트랙 전용 작성법」에 있다.

## 공통 작성법 — 두 트랙이 같이 쓰는 규칙

> 이 블록은 `gof-guide` 와 `analysis-guide` 두 `spec.md` 에 **바이트 단위로 같게** 들어 있다.
> 한쪽만 고치지 않는다. 고칠 때는 두 파일을 함께 고치고 공유 블록 동일성 검사를 돌린다.
> 트랙마다 다른 규칙은 이 블록 밖, 각 `spec.md` 의 트랙 전용 절에 있다.
> 괄호 안의 `PG` 코드는 `spec.json` 의 `principles[]` 다 — 게이트는 그 문장으로 채점한다.

### 도식 — viz 컴포넌트로 저작한다

도식은 본문에 문법으로 그리지 않는다. **가이드 폴더의 `diagrams/` 에 React 컴포넌트로 쓰고**, 렌더한 이미지를 본문이 가리킨다.

```text
pattern-guide/<계열>/<패턴>/diagrams/
  <Name>.tsx        ← 도식 소스(머리에 @relation · @viz-type · 주장 · 출처를 적는다)
  <name>.png        ← bun run scripts/render-viz.ts 가 구운 이미지
```

- 본문은 `![대체 텍스트](diagrams/<name>.png)` 로 싣는다. 대체 텍스트는 그 그림이 말하는 **주장 한 줄**이다.
- ` ```mermaid ` 펜스는 쓰지 않는다 — 검사기가 막는다.
- 도식 소스 머리에 `@relation`(branch · linear · cycle · layered · matrix · compare · quantity · relate 여덟 중 하나)과
  `@viz-type VT-…`(카탈로그 87종), 그 그림의 **주장**과 **출처**를 적는다. `bun run scripts/lint-diagrams.ts` 가 그 선언과 관계 어휘를 검사한다.
- 색·타이포는 `viz/style-guide` 토큰에서만 온다. 리터럴 색을 쓰면 검사가 막는다.
- 렌더는 실제 브라우저 마운트다(`scripts/render-viz.ts`). 페인트·폰트·기하 가드가 붙어 있어 무채색이거나 화살촉이 어긋난 그림은 비-0 으로 끝난다.
- HTML 발행본은 그 이미지를 data URI 로 박는다 — 파일·외부 요청이 0 이다.

### 산출 위치와 버저닝

가이드 한 편이 **폴더 하나**를 갖는다. 그 폴더에 본문·렌더된 HTML·예시 코드·도식이 함께 산다.

```text
pattern-guide/<계열>/<패턴>/          ← 계열은 paths.json 의 dirs.tracks, 패턴은 kebab-case 슬러그
  <패턴>-guide_v<major>.<minor>.<patch>.md     ← 본문(최신은 버전이 가장 높은 파일)
  <패턴>-guide_v<major>.<minor>.<patch>.html   ← 렌더 산출물
  code/      ← 예시 코드 실행 파일과 기대 출력
  diagrams/  ← 도식 소스와 렌더 이미지
```

- **머리말(frontmatter)** 에 `pattern` · `slug` · `spec` · `spec_version` · `version` · `status` · `date` 를 둔다.
  `status` 는 `draft`(집필·게이트 중) · `published`(게이트 통과) · `legacy`(구 골격, 검사 대상 밖)다.
- **버전을 올리는 기준** — `major` 는 골격이 바뀔 때(명세의 절 구성이 바뀌거나 명세 major 가 올라 다시 쓸 때),
  `minor` 는 내용이 늘거나 줄 때(절 보완 · 코드 교체 · 도식 추가), `patch` 는 뜻이 바뀌지 않는 정정(오탈자 · 근거 줄 · 링크).
- **`status: draft` 인 동안에는 같은 파일을 고친다.** 게이트를 통과해 `published` 가 된 뒤의 변경만 새 버전 파일을 만든다 —
  통과한 적 없는 초안을 판본으로 쌓으면 이력이 아니라 잡음이다.
- **이전 버전 파일은 지우지 않는다.** 같은 폴더에 남겨 불변 이력으로 둔다. 되돌리기는 새 버전을 쓰는 일이지 옛 파일을 고치는 일이 아니다.
- **최신을 가리킨다** — 인덱스·기준 예시(`paths.json` 의 `exemplars`)·분석 스킬·다른 가이드의 상호 링크는 모두 최신 파일명을 쓴다.
  새 버전을 발행하면 그 자리들을 같이 고친다. `check-guides --pointers` 가 낡은 포인터를 잡는다.
- **명세 판본과의 관계** — 머리말 `spec_version` 이 현재 명세 version 과 다르면 검사가 실패한다. 명세가 올라가면 그 판본으로 다시 쓰고 가이드 버전도 올린다.

### 리서치 노트를 입력으로 쓰는 법

집필 입력은 둘이다. `paths.json` 의 `dirs.research` 에 있는 **리서치 노트**와, 같은 경로에 덮어쓸 **기존 가이드**.

노트는 패턴마다 한 절이고, 각 항목은 가이드의 정해진 자리로 간다.

```text
노트 항목                               가이드 절
────────────────────────────────────    ─────────────────────────────────────
주장 · 원전 위치(장·절)               →  overview · refs
participants 대응 / 분석 개념         →  detail.terms
collaborations 대응                   →  detail.procedure
비교 대상 2개 이상과 그 근거          →  boundary.compare
실제 사용처(출처 확인분)              →  example.realworld
미해결 질문                           →  집필 전에 읽는다 — 본문에서 단정하지 않는다
```

- **노트는 입력이지 검색 금지가 아니다.** 집필 중 새 비교 대상이나 구현 쟁점이 나오면 추가로 조사한다.
- 노트에 없는 사실(원전 인용·API 동작·역사·사용처)을 본문에 새로 쓰면 **그 자리에 출처를 달고 `refs` 에도 올린다**(PG24).
- 추가 조사 결과는 노트의 「미해결 질문」에 되먹인다. 여러 워커가 병렬로 쓸 때는 한 노트를 동시에 고치지 않도록 게이트 보고에 적어 두고 메인이 옮긴다.
- 「미해결 질문」에 걸린 사실은 본문에서 단정하지 않는다. 출처를 찾아 해소하거나 본문에서 뺀다.
- **기존 가이드는 사실 확인용 입력이다. 문장을 옮기지 않는다.** 목소리와 골격이 바뀌었으므로 다시 쓴다.
  기존 가이드에만 있고 노트에 없는 주장은 출처를 확인한 뒤에만 쓴다.

### 제목 + 부제 (`title`)

`# {패턴} — {직관을 담은 부제}`. `{패턴}` 자리는 원전의 패턴 이름이다.
부제는 이 패턴의 **비결을 한 구절로** 예고한다. 분류명이나 "가이드" 같은 낱말로 채우지 않는다.

### 한눈에 보는 개요 (`overview`)

이 절만 읽고 닫아도 "무엇을 풀려고 무엇을 하는 패턴인가"를 들고 나가게 쓴다. 네 가지가 모두 있어야 한다(PG2).

1. **문제** — 패턴 없이 쓰면 무엇이 어디서 아픈가. 구체 상황 하나로 보인다.
2. **해결의 직관** — 그 아픔을 패턴이 어떤 한 수로 없애는가.
3. **그림 1개** — 문제 → 해결의 전후가 한눈에 보이게(```text 도식 또는 viz 도식 이미지).
4. **분류 · 함께 쓰는 패턴 한 줄** — 분류(GoF 는 생성·구조·행위, 분석 패턴은 원전의 장 범주)와 자주 함께 쓰는 패턴을 한 줄에.

- 정의·절차·코드는 여기서 풀지 않는다. 뒤 절이 한다.
- 활용성 별점·학습 난이도 같은 **평가 수치를 싣지 않는다**(PG22). 측정된 적 없는 값이다. 본문 어디에서도 같다.

### 등장하는 개념과 정의 (`detail.terms`)

**이 패턴에 등장하는 개념을 빠짐없이 정의한다**(PG3). 이름만 나열하면 미흡이다.

- 개념마다 **무엇을 책임지는가 · 누구와 협력하는가**를 적는다.
- 판정 기준은 "뒤에서 튀어나오는 이름"이다. 개요·절차·경계·구현 어디에서든 역할이나 개념 이름이 쓰이면 이 절에 정의가 있어야 한다.
- 무엇을 "개념"으로 세는가는 트랙마다 다르다 — 트랙 전용 절을 본다.
- 정의 목록 **바로 뒤에 클래스 구조 도식 1개**를 둔다(PG4) — `diagrams/` 의 컴포넌트를 렌더한 이미지다. 그림의 클래스 이름과 정의 목록의 이름은 1:1이다.
  정의에 없는 클래스가 그림에 있거나, 정의한 이름이 그림에 없으면 미흡이다.

### 동작 절차 (`detail.procedure`)

역할들이 **어떤 순서로 협력해 요청 하나를 처리하는가**를 번호 단계로 쓴다(PG5).

- 한 단계 = 한 협력(누가 누구에게 무엇을 넘기는가).
- **단계마다 "왜"를 붙인다.** 왜 그 역할이 그 일을 맡는가, 또는 순서를 바꾸면 무엇이 깨지는가. 이유 없는 단계가 하나라도 있으면 미흡이다.
- 절차가 갈라지면(처리할지 넘길지, 생성할지 재사용할지) 갈래마다 단계를 따로 적는다. "경우에 따라"로 뭉개지 않는다.
- 순서 도식(`diagrams/` 의 생명선 도식)이나 ```text 도식을 곁들여도 된다. 그림이 단계 서술을 대신하지는 않는다.

### 사용 목적 (`purpose`)

**어떤 단서가 보일 때 이 패턴을 꺼내는가**를 쓴다. 가이드의 실전 가치가 대부분 여기서 나온다 —
구조는 검색하면 나오지만 "언제 꺼내야 하는가"는 잘 안 나온다.

- 단서를 **구체 상황으로 2개 이상** 적는다(PG6). 좋은 단서는 코드나 요구에서 **관찰되는 것**이다.
  - 나쁜 예: "유연성이 필요할 때", "확장성을 높이고 싶을 때" — 관찰할 것이 없다.
  - 좋은 예: "같은 `switch` 가 세 곳에 복제돼 있고, 결제 수단이 하나 늘 때마다 셋을 함께 고친다."
- **쓰지 말아야 할 경우를 1개 이상**, 쓰면 무엇을 잃는지와 함께 적는다(PG7).
- 비슷한 단서에서 다른 패턴을 고르게 되는 경우는 여기서 한 줄로 예고만 하고, 차이는 `boundary.compare` 에서 푼다.

### 디자인 패턴을 충족하는 최소 조건 (`boundary.minimum`)

"어떤 코드·모델을 이 패턴이라고 불러도 되는가"의 판정 기준이다.
**이 헤딩 문자열은 design-pattern-analyzer 가 기준을 읽어 가는 계약이다 — 한 글자도 바꾸지 않는다**(PG1).

- 조건마다 **맨 앞에 `[필수]` 또는 `[선택]`** 을 붙이고, `[필수]` 는 1개 이상이다(PG8).
  analyzer 는 `[필수]` 미충족을 "패턴 아님" 쪽으로, `[선택]` 미충족을 보강 권장으로 다룬다.
  그러니 **빠지면 그 패턴이 아니게 되는 것만 `[필수]`** 다.
- `[필수]` 조건마다 **그 조건이 빠지면 무엇이 되는가**를 구체 반례로 붙인다(PG9) — 비슷한 패턴, 안티패턴, 또는 그냥 분기문.
  조건을 선언만 하고 넘어가면 미흡이다.
- `[필수]` 조건마다 **`(근거: …)` 괄호로 원전의 자리**를 댄다(PG27). 괄호는 **그 조건의 본체 줄이나 `빠지면:` 줄**에 단다 — 하위 항목에 달면 검사가 막는다.
  원전은 GoF 원서(의도·활용성·구조·참여자·협력·결과·구현·예제 코드), Fowler *Analysis Patterns*, 저자가 공개한 보충 자료(martinfowler.com 의 eaaDev·apsupp),
  DDD 원전(Evans · Vernon)이다. 빈 근거와 이 목록 밖을 가리키는 근거는 검사에서 실패한다.
  원전이 "흔한 규칙"·"구현 선택지"로 적은 것과 **이 가이드 예제가 정한 정책은 `[필수]` 로 올리지 않고 `[선택]` 에 둔다.**
  이유는 트랙마다 다르다 — GoF 트랙은 analyzer 가 `[필수]` 미충족을 "패턴 아님"으로 읽어 원전 기준으로는 그 패턴인 코드를 오판하기 때문이고(GG3),
  분석 트랙은 analyzer 의 판정 대상이 아니라서, 원전이 인정하는 모델을 이 가이드의 예제 정책으로 밀어내는 것 자체가 원전 충실성 위반이기 때문이다(AG2).
  `[선택]` 조건의 근거는 원전이어도 되고 `(근거: 이 가이드의 정책 — <이유>)` 여도 된다.
- 패턴이 항상 유지해야 하는 **불변식은 이 절의 조건 항목으로 올린다**(PG10). 산문 속에 "항상 ~해야 한다"로 묻어 두면 analyzer 가 못 읽는다.
- 조건의 **판정 기준이 무엇인가**(코드 구조인가, 개념적 책임 분리인가)는 트랙마다 다르다 — 트랙 전용 절을 본다.

형식 예:

```text
1. [필수] <조건 이름> — <판정 기준 한 문장> (근거: <원전의 자리>)
   빠지면: <무엇이 되는가 — 반례>
2. [선택] <조건 이름> — <판정 기준 한 문장> (근거: <원전의 자리, 또는 이 가이드의 정책 — 이유>)
```

### 비슷한 패턴·안티패턴과의 차이 (`boundary.compare`)

패턴은 여러 방식으로 구현될 수 있어서, 경계는 **이웃과의 차이**로 드러난다.

- 비교 대상은 **2개 이상**이다(PG11). 구조가 닮은 패턴, 같은 단서에서 떠오르는 패턴, 이 패턴으로 오해받는 안티패턴 중에서 고른다.
  리서치 노트의 비교 대상과 트랙 전용 절의 필수 포함 대상을 먼저 확인한다.
- **차이점 위주**다(PG12). 대상마다 **구분 기준 한 문장을 먼저** 둔다. "의도가 다르다"로 끝내지 않고,
  코드나 모델에서 확인할 수 있는 기준으로 쓴다 — 예: "교체를 누가 결정하는가: 클라이언트(Strategy) / 상태 객체 자신(State)".
  공통점 나열로 분량을 채우지 않는다.
- 대상마다 **이 패턴을 고르면 무엇을 얻고 무엇을 포기하는가**를 적는다(PG13).
  구 양식의 「장점과 단점, 한계점」은 여기로 흡수됐다. 장단점을 따로 목록으로 늘어놓지 않고 비교의 맥락에서 쓴다.
- 이 패턴처럼 보이지만 아닌 **오인 코드**를 보일 때는 펜스 정보 문자열에 `no-compile` 을 단다(PG14).
  `### 구현` 밖의 펜스는 컴파일 검사 대상이 아니고, 이 표식이 "일부러 보인 반례"라는 신호다.

  ````text
  ```java no-compile
  // 분기를 메서드로 뽑았을 뿐, 교체 지점이 없다
  ```
  ````

- 대상이 셋 이상이면 요약 표(대상 · 구분 기준 · 얻는 것 · 포기하는 것)로 모아도 된다. 다만 표로 끝내지 않는다 —
  가장 헷갈리는 한 쌍은 산문과 코드로 풀어 준다.

### 구현 — 펜스 규약 (`example.impl`)

`### 구현` 은 **컴파일 검사를 받는 유일한 절**이다. 아래 규약은 `commands.compile` 이 기계로 검사한다.
컴파일은 하한일 뿐 정확성 검증이 아니다 — 코드가 본문 주장과 맞는지는 품질 게이트와 외부 검토가 본다.

1. **펜스는 정확히 3개, 순서는 `java` → `typescript` → `rust`**(PG16). 다른 언어, 추가 펜스, `no-compile` 표식은 이 절에 두지 않는다.
2. **세 펜스는 사이에 산문·헤딩 없이 연달아 둔다**(PG16). md 에서는 나열로 읽히고,
   HTML 파생본에서는 렌더러가 세 펜스를 탭 묶음 하나로 만든다. 그래서 본문에 "위 탭에서" 같은 화면 지시어를 쓰지 않는다.
3. **자기완결**(PG17). 펜스 하나를 그대로 파일 하나로 저장해 단독 컴파일돼야 한다.
   기준은 Java 21 · TypeScript strict 모드 · Rust 2021 edition 이다.
   - 다른 펜스나 외부 파일의 타입을 가정하지 않는다.
   - import·use 를 빠뜨리지 않는다.
   - `...` 같은 생략 표기를 쓰지 않는다. 빈 펜스는 실패다.
4. **표준 라이브러리만**(PG18). 외부 crate·npm 패키지·Maven 의존은 0이다.
5. **같은 상황을 세 언어로**(PG19). `example.context` 의 시나리오 하나를 같은 역할·타입 이름으로 세 번 구현한다.
   - 언어 관용 차이는 허용한다 — Java `interface` / TypeScript `interface`·`type` / Rust `trait`.
   - 언어마다 다른 도메인·다른 시나리오면 미흡이다.
   - 세 펜스 모두 시나리오를 실제로 호출하는 진입점을 갖는다 — Java `main` · TypeScript 최상위 호출 · Rust `fn main`.
6. **해설은 세 펜스 뒤에 한 번**(PG20). 핵심 라인을 짚을 때는 세 언어의 대응 줄을 함께 가리킨다.
   같은 해설을 언어마다 세 번 반복하지 않는다. 예시 타입 ↔ 역할 매핑이 `example.context` 에 없으면 여기서 한다(PG15).
7. **예시 코드의 정본은 `code/` 의 실행 파일**(PG29). 가이드 폴더 안에 `code/<공개클래스>.java` · `code/main.ts` · `code/main.rs` 와
   실행 결과를 담은 `code/expected-output.txt` 를 둔다. 본문 펜스는 그 파일에서 그대로 가져오고, 본문이 보이는 실행 출력도
   `expected-output.txt` 와 글자 단위로 같은 펜스로 싣는다.
   **그 출력 펜스는 `### 구현` 밖에 둔다** — 그 절은 언어 펜스 셋만 허용하므로(규약 1), 출력은 `### 상황 설정` 의
   "이 시나리오가 무엇을 내는가" 자리나 구현 절 뒤 해설에 둔다. `commands.run` 이 세 언어를 컴파일·실행해 셋이 같은 출력을 내는지,
   본문 펜스와 코드 파일이 같은지, 출력이 기대 파일과 같은지 검사한다 — **본문의 수치는 실행에서 온다.**
8. **분량은 언어당 250줄 이하**(PG28). 넘으면 시나리오를 줄인다 — 코드가 본문을 압도하면 독자가 해설과 코드를 오가다 놓친다.
   파일럿 실측: Account 1라운드(Java 286 · TypeScript 270 · Rust 337줄)는 채점에서 "지금 코드 길이는 이해에 방해가 된다"는 의견을 받았고, 2라운드(203 · 201 · 230줄)는 "방해가 되지 않는다"로 바뀌었다.

### 실제 사용처 (`example.realworld`)

조건부 절이다. **출처 링크로 확인한 사용처가 있을 때만** 쓴다(PG21). 헤딩 문구는 트랙마다 다르니 `sections[]` 를 따른다.

- 사용처마다 공식 문서·소스 저장소·원문 링크를 단다. 링크로 확인하지 못한 사용처는 싣지 않는다.
  "많은 프레임워크가 쓴다" 같은 무출처 서술도 같은 취급이다. 이 규칙은 개요·비교 등 다른 절에서 사용처를 언급할 때도 같다.
- 사용처의 **무엇이 패턴의 어느 역할·개념인가**를 매핑한다. 이름만 대고 넘어가지 않는다.
- 사용처 코드 조각은 `### 구현` 밖이라 컴파일 검사 대상이 아니다. 필요한 만큼만 짧게 싣는다.
- 확인된 사용처가 하나도 없으면 **절을 헤딩째 지운다**(아래 조건부 절 규칙).

### 스스로 점검하기 (`selfcheck`)

본문을 정독해야 풀리는 문제로 마무리한다. 다음 종류를 섞는다.

1. **경계 판정 문제** — 짧은 코드나 모델을 주고 `boundary.minimum` 의 조건을 적용해 이 패턴인지 판정하게 한다(PG26).
2. **비교 판별 문제** — 비슷한 두 패턴 중 어느 쪽인지, 구분 기준을 근거로 고르게 한다.
3. **책임·순서 문제** — 절차의 두 단계를 바꾸거나 한 역할의 책임을 다른 역할로 옮기면 무엇이 조용히 깨지는지 추적하게 한다.

문제 속 코드에는 `no-compile` 을 달지 않는다(PG14) — 표식이 답을 흘린다.

### 참고 자료 (`refs`)

- **원전을 맨 앞에**, 장·절(또는 쪽)까지 적는다(PG25).
- 본문에서 출처로 단 링크는 **전부** 여기에 다시 모은다. 리서치 노트에만 있고 본문이 쓰지 않은 출처는 올리지 않는다.
- 항목마다 그 자료가 **본문의 무엇을 뒷받침하는지** 한 구절을 붙인다.

### 조건부 절 규칙

`sections[]` 에서 `required: false` 이고 `condition` 이 있는 절이 조건부다.

- 조건에 해당하지 않으면 **절을 헤딩째 지운다**(PG23). 본문에 "해당 없음"·"이 절은 생략한다" 같은 집필 메타를 남기지 않는다.
- 생략 사유는 **품질 게이트 보고에만** 한 줄로 남긴다.
- 캔버스의 조건 블록 표식(`@if` · `@end` 주석)·집필 지시(`@write` 주석)·슬롯은 절을 남기든 지우든 최종본에서 전부 없앤다.
- 조건부가 아닌 절은 지울 수 없다. 쓸 내용이 없어 보이면 리서치가 모자란 것이다.
### 채점 규약 — 채점자마다 달라지지 않게 고정한 것

- **산문 연속 상한(voice V1)** 은 `golden.py measure <가이드> --spec <id> --project . --voice ppangtolab-teacher` 가 내는
  `voice_compliance.max_prose_run_without_visual` 이 2 이하인지로 판정한다. 채점자가 손으로 세면 도식·표·코드를 끊는 것으로 치는지가 갈렸다(파일럿).
- **마지막 라운드의 외부 검토는 채점 입력이다.** 외부 검토가 채점보다 늦게 끝나면 채점을 닫지 않고 그 지적(코드·본문 대조로
  결정되는 것)을 확인해 판정에 넣는다. 파일럿 Quantity·Account 3라운드에서 외부 검토가 채점보다 늦게 끝나 채점에 들어가지 않았다.

## GoF 트랙 전용 작성법

### 등장하는 개념과 정의 — participants 를 센다 (GG1)

- GoF 원전의 해당 패턴 **Participants 에 나오는 역할을 전부** 정의한다. 리서치 노트의 participants 대응과 대조해 빠진 역할이 없는지 확인한다.
- 원전 목록에 Client 가 없더라도 절차·구현에 Client 가 등장하면 정의한다(PG3).
- **역할 이름**(Strategy, ConcreteStrategy, Context)으로 정의한다. 예시 도메인의 타입 이름(`DiscountPolicy`)은 정의 대상이 아니라
  `example.context`·`example.impl` 에서 역할에 매핑하는 대상이다.

### 동작 절차 — collaborations 를 옮긴다 (GG2)

- 원전 **Collaborations 에 나오는 상호작용을 전부** 단계로 옮긴다. 원전이 한 문장으로 묶은 협력도 주고받는 쪽이 둘 이상이면 단계를 나눈다.

### 최소 조건 — 코드 구조로 판정한다 (GG3)

analyzer 가 사용자의 코드를 이 조건으로 판정한다. 그래서 조건은 **코드에서 관찰 가능한 구조**로 쓴다.

- 쓸 수 있는 관찰 대상: 타입 선언(공통 인터페이스가 있는가) · 참조 보유(누가 어떤 타입을 필드로 갖는가) ·
  호출 방향(누가 누구를 부르는가) · 생성 위치(누가 구체 타입을 만드는가).
- 나쁜 예: "`[필수]` 알고리즘을 유연하게 교체할 수 있다" — 코드에서 무엇을 보면 되는지가 없다.
- 좋은 예: "`[필수]` Context 는 구체 전략 타입을 참조하지 않는다 — 필드와 생성자 인자의 타입이 전략 인터페이스다.
  빠지면: Context 안에 구체 전략 생성이 박혀, 교체하려면 Context 를 고쳐야 하는 단순 위임이 된다."
- 세 언어의 관용 차이(Java interface / TypeScript 구조적 타입 / Rust trait·클로저)에서도 **같은 판정이 나오게** 조건을 쓴다.
  특정 언어 문법(`implements`, `impl Trait for`)을 조건 문구에 박지 않는다.

### 비교 — 인덱스의 빠른 비교 페어를 빠뜨리지 않는다 (GG4)

PATTERNS.md 「빠른 비교가 자주 필요한 페어」에 이 패턴이 들어 있으면 그 페어의 **상대 전부**가 비교 대상에 들어간다.
작성 시점(2026-09)의 페어는 아래와 같다. 인덱스가 바뀌면 인덱스를 따른다.

- Factory Method ↔ Abstract Factory
- Strategy ↔ State
- Adapter ↔ Decorator ↔ Proxy
- Builder ↔ Abstract Factory
- Mediator ↔ Facade

페어에 없는 패턴도 비교 대상 2개 이상(PG11)은 그대로 걸린다.

### 상황 설정 (`example.context`)

구현 펜스보다 앞에서 **도메인 하나와 요구 전제**를 적는다(PG15).

- 무엇이 변하는가(교체·추가되는 축)와 무엇이 고정인가, 시나리오가 무엇을 받아 무엇을 내는가.
- 예시 타입 이름이 어느 역할인지 매핑한다. 짧은 목록이나 2열 표(예시 타입 · 역할)면 충분하다.
- 세 언어 **표준 라이브러리만으로 구현할 수 있는 크기**로 잡는다(PG18). DB·HTTP 같은 외부 시스템은 메모리 안의 대역으로 둔다 —
  컴파일 검사가 펜스 하나 = 파일 하나 기준이다.

### 실제 라이브러리에서 (`example.realworld`) — 조건부 (GG5)

- 표준 라이브러리 또는 널리 쓰이는 프레임워크의 **실제 타입·메서드 이름**을 대고, 그것이 패턴의 어느 역할인지 매핑한다.
  예: "`java.util.Comparator` 가 Strategy, 그것을 인자로 받는 `List.sort` 가 Context" — 링크는 해당 API 문서.
- 링크로 확인한 사용처가 없으면 절을 헤딩째 지운다(공통 조건부 절 규칙).
