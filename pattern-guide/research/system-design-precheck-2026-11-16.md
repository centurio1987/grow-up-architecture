## 3. 편마다 확인한 것

### SY-01 실시간 공동 편집 — 중앙 서버 OT

시험 코드는 중앙 서버 OT(운영 변환)입니다. 서버가 편집의 순서를 정하고, 늦게 도착한 편집을 앞선 편집 뒤로 옮깁니다(`transform`). 클라이언트는 보낸 뒤 확인을 기다리는 편집 하나와 아직 보내지 않은 편집 목록을 갖고, 받은 편집을 그 둘에 맞춰 옮깁니다. 연결은 방향마다 차례를 지키고, 끊긴 동안 보낸 것은 다시 이어진 뒤에 차례대로 도착합니다.

```
[1] 기본 흐름 — A 가 Hi 를 치고, B 가 받은 뒤 ! 를 붙인다
  t=300ms B 화면="Hi"
  서버="Hi!" A="Hi!" B="Hi!" · 서로 다른 문서 1개
[2] 동시 편집 40건 · 변환 없이 그대로 적용
  서버="yyzzlyzyzyyzzzyyzzyzyzyyoy zworld" A="yyzzlyzlyyyzzzyyzzyyzyzzy yzyorld" B="yyzzzyzzyyyzzzzzyyyyyloy ywzorzld" C="zyzzyyzzzyyzzylyzyyyzz zwyorzylyd" D="yyzzyzzzzzzyyzzyyyzloyyzzy yworld" E="yylzyzzzyyzyzzyyzyzyyzyzyyzozrzld" · 서로 다른 문서 6개
[2] 동시 편집 40건 · OT 변환
  서버="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" A="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" B="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" C="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" D="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" E="zyzyzyzyylzzyyzyzy yzywzyozrzzyzlyd" · 서로 다른 문서 1개
[3] 연결 끊김 — C 가 t=100~1600ms 동안 끊긴 채 세 번 고친다
  t=1000ms C 화면="#raft!" · 서버=">draf"
  서버=">#raf!" A=">#raf!" B=">#raf!" C=">#raf!" · 서로 다른 문서 1개
```

- **부하**는 「같은 문장을 다섯 명이 동시에 40번 고친다」로 보였습니다. 변환 없이 적용하면 서버와 다섯 클라이언트가 여섯 가지 문서로 갈라지고, OT 로는 하나로 모입니다. 파일럿 2 가 한 실행 안에서 「확인 뒤 차감」의 과발급과 원자 판정의 0건을 나란히 보인 것과 같은 꼴입니다.
- **장애**는 「1.5초 끊긴 채 편집하고 다시 이어진다」입니다. 끊긴 동안 C 의 화면과 서버가 다르고, 이어진 뒤 네 쪽이 같은 문서가 됩니다. 같은 자리에 들어간 두 글자(`>` · `#`)는 site 이름이 작은 쪽이 왼쪽에 놓입니다.
- **집필 때 정할 것**: 시험 코드는 OT 만 보입니다. CRDT(충돌 없이 합쳐지는 자료형)와 디자인 도구의 속성 단위 LWW(마지막 쓰기 우선)는 대안 비교 절에서 다룰지, 코드로도 견줄지를 리서치 노트 단계에서 정합니다. 견주면 줄 수가 늘어나므로 그때 다시 잽니다. 부하 시나리오는 동시 편집 수만 보이고 서버 처리량은 다루지 않습니다.

### MD-01 동영상 업로드와 인코딩 — 분할 업로드 · 작업 그래프 · 점유 만료

인코딩 자체는 시뮬레이션하지 않습니다. 조각 하나를 올리는 시간(2초), 원본 1초를 화질별로 인코딩하는 데 드는 워커 시간(480p 0.5초 · 720p 1초 · 1080p 2초), 작업 점유 만료(300초)는 모두 가정값입니다. 업로드가 끝나면 60초 구간 × 화질마다 인코딩 작업을 만들고, 한 화질의 구간이 다 모이면 그 화질의 패키징 작업을 만듭니다(작업 그래프, DAG). 480p 패키징이 끝나면 재생할 수 있습니다.

```
[1] 기본 흐름 — 10분 · 400MB 영상 하나, 워커 6대, 480p 먼저
  업로드 끝 t=100s · 480p 재생 가능 t=162s · 세 화질 모두 t=492s
[2] 부하 — 영상 8편이 10초 간격으로 올라오고, 워커는 6대
  들어온 차례 · 업로드 뒤 재생 가능까지 평균 2737.0s · 최대 2762s · 마지막 완료 t=2982s
  480p 먼저    · 업로드 뒤 재생 가능까지 평균 204.3s · 최대 352s · 마지막 완료 t=2968s
[3] 장애 — 21번째 조각에서 연결이 끊기고, 워커 2번이 t=150s 에 잡은 작업에서 600초 멈춘다
  처음부터 다시   · 보낸 조각 71개(전체 50개) · 업로드 끝 t=152s
  빠진 조각만 다시 · 보낸 조각 51개(전체 50개) · 업로드 끝 t=112s
  점유 만료 300s 뒤 다른 워커가 이어받음 · 완료 보고 34번 · 저장 33번(작업 33개) · 세 화질 모두 t=524s
```

- 손으로 셈한 값과 맞습니다. 기본 흐름의 480p 는 구간 10개 × 30초를 워커 6대가 두 번에 나눠 60초, 업로드 끝(100초) 뒤 패키징 2초를 더해 162초입니다. 처음부터 다시 올리면 21개(0~20번, 20번은 사라짐)에 50개를 더해 71개, 빠진 것만 다시 올리면 50개에 사라진 1개를 더해 51개입니다.
- **부하**에서 작업 차례만 바꿔도 재생 가능까지의 평균이 2737.0초에서 204.3초로 줄고, 마지막 완료 시각은 거의 같습니다(2982 · 2968초). 「인코딩 자체를 시뮬레이션할 수 없다」는 걱정과 달리, 이 편의 핵심인 배치 결정은 시간 가정값만으로 재현됩니다.
- **장애**의 「완료 보고 34번 · 저장 33번」은 멈췄던 워커가 늦게 끝내도 같은 결과를 두 번 저장하지 않는다는 것(멱등 저장)을 보입니다.
- **집필 때 정할 것**: 가정값 넷은 본문에서 가정임을 밝히고, 실제 값의 출처를 리서치 노트에서 찾습니다(SD40, 수치의 출신 구분). 적응형 비트레이트 재생(플레이어가 화질을 바꾸는 쪽)과 CDN 전달은 시험 코드에 없습니다. 기술 설명 절에서 다룰지, 시나리오에 넣을지는 노트 단계에서 정합니다.

### AI-02 문서 검색 증강 생성(RAG) — 하이브리드 검색 · 권한 필터 · 재순위

임베딩 모델 대신 낱말을 개념 번호로 바꾸는 표를, 재순위 모델 대신 질문 개념과의 겹침 비율을 씁니다(결정적 대역). 키워드 검색은 두 글자 조각(바이그램) 단위의 BM25 를 줄인 꼴이고, 두 검색의 순위는 RRF(순위 역수 합)로 합칩니다. 재순위 점수가 0.5 아래인 조각은 근거로 쓰지 않습니다.

```
[1] 기본 흐름 — 같은 질문도 볼 수 있는 문서에 따라 근거가 다르다
  eng 팀 「비밀 키 교체 주기는?」 → D1#0(1.00) D1#1(0.67)
  security 팀 「비밀 키 교체 주기는?」 → D5#0(1.00) D5#1(1.00)
  eng 팀 · 상위 3개를 먼저 뽑고 권한으로 거름 → D1#0(1.00)
  security 팀 「보안 사고 기록은 얼마나 보관하나」 · 조각에 제목 안 붙임 → 근거 없음
  security 팀 「보안 사고 기록은 얼마나 보관하나」 · 조각에 제목 붙임   → D2#1(0.80)
[2] 부하 — 질문이 10ms 마다 하나씩 2초 동안 200건, 재순위 서버 1대
  재순위 후보 20개 · 응답 지연 중앙값 3040ms · 95% 5740ms · 최대 6010ms
  재순위 후보  4개 · 응답 지연 중앙값 8ms · 95% 8ms · 최대 8ms
  후보 4개로 줄였을 때 eng 팀 「비밀 키 교체 주기는?」 → D1#0(1.00) D1#1(0.67)
[3] 장애 — 벡터 색인이 내려가 키워드 검색만 남는다
  eng 팀 「API 키 교체」 · 둘 다 → D1#0(1.00) D1#1(1.00) · 키워드만 → D1#0(1.00) D1#1(1.00)
  eng 팀 「비밀값 갱신 간격」 · 둘 다 → D1#0(1.00) D1#1(0.67) · 키워드만 → 근거 없음
```

- **기본**에서 권한을 먼저 거르면 eng 팀은 자기 문서 두 조각을 받고, 상위 3개를 먼저 뽑은 뒤 거르면 security 문서가 자리를 차지해 한 조각만 남습니다. 조각에 문서 제목을 붙이면 「접속 기록은 1년 동안 보관한다」가 보안 사고 문서의 것이라는 정보가 조각에 함께 들어가 재순위 점수가 0.4 에서 0.8 로 올라 근거가 됩니다.
- **부하**는 재순위 서버의 대기열 계산입니다. 질문은 1초에 100건 들어옵니다. 후보 하나에 2ms(가정)이면 후보 20개는 한 건에 40ms 라 1초에 25건밖에 못 받아 대기열이 쌓이고, 후보 4개는 한 건에 8ms 라 125건을 받아 쌓이지 않습니다.
- **장애**에서 키워드만 남으면 낱말이 같은 질문은 그대로 찾고, 뜻만 같은 질문(「비밀값 갱신 간격」)은 근거를 잃습니다.
- **집필 때 정할 것**: 점수(0.80 등)는 대역의 값이지 실제 모델의 값이 아니므로 본문에서 그렇게 밝힙니다. 부하 시나리오는 다른 두 편보다 얕습니다(대기열 산수 하나). 노트 단계에서 실제 서비스의 재순위 지연 · 후보 수 근거를 찾아, 시나리오를 그 수치로 다시 짤지 정합니다. 근거 문서가 빨리 바뀌는 분야라 노트에 대조 날짜를 꼭 적습니다(회고 8절).

## 4. 이 확인이 보지 않은 것

- 세 언어 가운데 TypeScript 하나만 썼습니다. Java · Rust 의 줄 수와 세 언어 출력의 글자 단위 일치(SD26)는 집필 때 검사기가 봅니다.
- 시나리오 셋이 「만들어진다」는 것만 봤고, 그것이 본문의 요구 충족 표를 다 채우는지는 리서치 노트에서 요구를 정한 뒤에 압니다.
- 출처 대조는 하지 않았습니다. 시험 코드의 수치는 모두 가정값입니다.
