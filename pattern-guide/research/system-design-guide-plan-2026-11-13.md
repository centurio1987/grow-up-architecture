## 결론

가이드 한 편은 **문제 하나**를 다룹니다. 요청하신 네 요소(시스템 개념도 · 시나리오 · 기술 상세 설명 · 구현 코드)를 그 순서대로 몸통에 두고,
앞에 「요구사항과 규모 추정」을, 기술 설명 뒤에 「대안 비교」를 덧붙이는 구성을 권합니다.
"최적"은 요구 수치가 정해져야 판단할 수 있고 다른 구조와 견줘 봐야 드러나기 때문에, 두 절이 없으면 가이드가 고른 구조가 왜 최적인지 보여 줄 자리가 없어요.

파일럿은 두 편을 권합니다. 요청 예시인 **라이브 동시 시청자 수**는 근사값이 허용되고 같은 값을 많은 화면에 뿌리는 문제입니다.
여기에 정반대 성격인 **선착순 쿠폰 발급**(값이 정확해야 하고 남은 수량을 두고 요청이 경합하는 문제)을 짝으로 두면,
한쪽 성격에만 맞는 명세로 후보 75건을 쓰는 일을 막을 수 있습니다.

5절의 결정 네 가지는 2026-11-13 에 모두 정했습니다. 구현 코드는 기존과 같은 세 언어 규약을 유지하고, 저장 위치는 `pattern-guide/system-design-guide/<슬러그>/` · 명세 id 는 `system-design-guide` 이며, 파일럿은 위 두 편이고, 진행은 칸반 카드로 관리합니다.

## 1. 패턴 가이드와 무엇이 다른가

지금 저장소의 37편은 **해법 하나**가 단위입니다. Strategy 편은 "이 해법이 어떤 문제들을 푸는가"를 씁니다.
이번 가이드는 방향이 반대입니다. **문제 하나**를 두고 "어떤 해법을 어떻게 조합해야 이 문제가 가장 잘 풀리는가"를 씁니다.

11월 6일 확장 조사가 제안한 `architecture-guide` 트랙(Retry · Circuit Breaker · Outbox 같은 분산 패턴 한 편씩)과도 단위가 다릅니다.
두 계열은 서로를 가리키는 관계가 됩니다. 사례 가이드의 기술 설명 절은 그 패턴들을 부품으로 쓰고,
패턴 가이드의 「실제 사용처」 절은 사례 가이드를 예로 들 수 있습니다. 어느 쪽도 다른 쪽을 먼저 써야 하는 선행 조건은 아닙니다.

| 비교 기준 | 패턴 가이드(현행 37편) | 사례 가이드(이번) |
| --- | --- | --- |
| 한 편의 단위 | 해법(패턴) 하나 | 문제(요구) 하나 |
| 판정 질문 | 이 코드가 이 패턴인가 | 이 구조가 이 요구를 만족하는가 |
| 몸통 | 시나리오 → 개념 정리 → 최소 조건 | 개념도 → 시나리오 → 기술 설명 → 대안 비교 |
| 코드 | 패턴 구조를 보이는 세 언어 예제 | 시스템의 핵심 경로를 재현하는 세 언어 실행 예제(같은 출력 규약) |
| 연결 | analyzer 가 최소 조건을 읽음 | analyzer 대상 아님 |

## 2. "최적"을 어떻게 다룰 것인가

"최적의 아키텍처"는 요구 없이 정해지지 않습니다. 시청자 1천 명인 방송이라면 DB 행 하나를 5초마다 읽어도 충분합니다.
시청자 1천만 명이라면 같은 방식으로는 행 하나에 초당 200만 번의 읽기가 몰립니다(1천만 ÷ 5초).
그래서 가이드는 세 가지를 지킵니다.

1. **요구를 수치로 고정합니다.** 동시 접속 수 · 갱신 지연 상한 · 허용 오차 · 가용성 목표를 숫자로 적고, 그 숫자에서 부하를 계산합니다.
   "지연 없이" 같은 말은 "입장 후 N초 안에 화면 숫자에 반영"처럼 바꿔 적습니다.
2. **후보 구조를 같은 기준으로 견줍니다.** 후보는 2개 이상이고, 기준은 지연 · 처리량 · 정확도 · 비용 · 운영 부담 · 장애가 번지는 범위 가운데 그 문제에 걸리는 것입니다.
   기준 목록을 빠짐없이 훑을 때는 AWS Well-Architected 의 여섯 기둥(운영 우수성 · 보안 · 신뢰성 · 성능 효율 · 비용 최적화 · 지속 가능성)을 점검표로 씁니다.
   AWS 도 이 틀을 "결정의 장단점을 이해하는 도구"로 소개합니다([기둥](https://docs.aws.amazon.com/wellarchitected/latest/framework/the-pillars-of-the-framework.html) · [소개](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)).
3. **전환점을 적습니다.** 고른 구조가 어느 수치를 넘거나 어떤 요구가 바뀌면 더 이상 최적이 아닌지를 적습니다.
   독자가 자기 문제의 수치를 넣어 다른 답을 고를 수 있어야 가이드가 한 사례를 넘어 쓰입니다.

## 3. 한 편의 절 구성 (초안)

요청하신 네 요소의 순서(개념도 → 시나리오 → 기술 설명 → 코드)는 기존 명세의 원칙과도 맞습니다.
기존 명세는 "이름은 움직이는 것을 본 뒤에 정의한다"는 이유로 개념 정리를 시나리오 뒤에 둡니다(`gof-guide/spec.md` 시나리오 절).
기술 설명을 시나리오 뒤에 두면 독자는 상자가 실제로 일하는 모습을 본 뒤에 그 상자의 설명을 읽게 됩니다.

앞에 붙인 「요구사항 → 규모 추정 → 개념도」 순서는 널리 쓰이는 설계 절차들과 같은 방향입니다. 견준 자료는 아래와 같습니다.

| 자료 | 순서 | 이 구성안에 가져온 것 |

| 1 | 문제와 요구사항 | 기능 요구, 비기능 요구 수치, 이 가이드가 다루지 않는 범위 | |
| 2 | 규모 추정 | 요구 수치에서 초당 요청 · 연결 수 · 저장량 · 대역폭을 계산. 계산식을 보입니다 | |

| 5 | 기술 상세 설명 | 개념도 상자마다: 무엇인가 · 이 시스템에서 맡는 일 · 왜 이 기술인가 · 설정값과 한계 | 기술 설명 |
| 6 | 대안 비교 | 후보 구조 2개 이상을 같은 기준으로 비교, 고른 구조의 전환점 | |
| 7 | 구현 코드 | 핵심 경로의 실행 예제와 줄 단위 해설 | 구현 코드 |

| 9 | 스스로 점검 · 참고 자료 | 풀이가 있는 문제 2~3개, 본문이 단 출처 전부 | |

각 절에서 지킬 규칙의 초안입니다.

- **개념도**는 C4 모델의 Container 수준(배포 단위와 그 사이 통신)을 기본으로 합니다. 저장소의 viz 카탈로그에 C4 Container(VT-110)와 Cloud Architecture(VT-115)가 있어 기존 렌더 경로로 그릴 수 있습니다.
  상자 하나는 실행 단위 하나(브라우저 · 에지 서버 · 집계 서비스 · Redis)이고, 화살표마다 통신 방식(WebSocket · HTTP · pub/sub)과 빈도를 적습니다.
- **시나리오**는 기존 명세의 시나리오 규칙(구체 값의 상황 한 문단 · 번호 단계마다 "왜" · 보여 준 것 한 문단)을 그대로 씁니다.
  경로 그림은 C4 Dynamic(VT-113, 번호가 붙은 협력)이나 Sequence(VT-108)로 그립니다. 시나리오 2·3 은 요구 수치를 넘기거나 구성 요소 하나를 멈춰 보고 무엇이 어긋나는지를 보입니다.
- **기술 상세 설명**은 이 문제에 필요한 만큼을 본문에서 풉니다(본문은 바깥 문서 없이 읽혀야 한다는 기존 원칙 PG30). 여러 편이 같은 기술을 깊게 다뤄야 하면 그 내용을 공용 참고 문서로 빼고 링크합니다.
- **대안 비교**는 표로 시작하되 표로 끝내지 않습니다. 가장 헷갈리는 한 쌍(예: 하트비트 집계와 연결 수 집계)은 산문과 수치로 풉니다.
  절의 끝은 ADR 의 세 칸을 빌려 "맥락(어떤 요구 수치에서) · 결정(무엇을 골랐나) · 결과(얻는 것과 포기하는 것)"로 닫고, 이어서 전환점을 적습니다.
- **구현 코드**는 기존 가이드와 같은 세 언어 규약을 따릅니다(2026-11-13 결정). `### 구현` 절에 Java · TypeScript · Rust 펜스 셋을 두고, 세 언어가 글자 단위로 같은 출력을 내는지 `check-guides --run` 이 검사합니다(기존 원칙 PG16~PG19 · PG29).
  검사기는 `### 구현` 헤딩을 찾아 펜스를 컴파일하고 실행하므로(`scripts/check-guides.py:133` · `:1289`, 커밋 `e2384dd` 기준), 구현 코드 절은 기존 가이드처럼 `## 구현 코드` 아래에 `### 상황 설정` · `### 구현` 하위 절을 둡니다.
  외부 시스템(Redis · 메시지 브로커 · 네트워크)은 표준 라이브러리로 만든 메모리 대역으로 두고, 시간은 가상 시계로 흘립니다. 실제 배포 조각(Redis 명령 · SSE 응답 헤더)은 기술 설명 절에 싣고 컴파일 대상이 아님을 표시합니다.
  세 언어의 출력을 같게 만들려면 아래를 지킵니다(판단, 파일럿 1 에서 검증합니다).
  - 맵을 순회하는 순서가 언어마다 다릅니다. Java `HashMap` 은 순서를 정하지 않고, Rust `HashMap` 은 실행마다 순서가 바뀌며, JavaScript `Map` 은 넣은 순서를 지킵니다. 출력하기 전에 키로 정렬합니다.
  - 무작위가 필요하면 같은 식의 의사난수 생성기(예: 선형 합동 생성기)를 세 언어에 직접 구현합니다. 표준 난수 생성기는 언어마다 수열이 다릅니다.
  - 스레드와 실제 시계를 쓰지 않습니다. Rust 표준 라이브러리에는 비동기 실행기가 없으므로, 단일 스레드에서 가상 시계의 사건을 시각 순으로 처리하는 모양이 세 언어 모두에 맞습니다.
  - 실수를 그대로 찍지 않습니다. 같은 1.0 을 Java 는 `1.0`, TypeScript 와 Rust 는 `1` 로 찍습니다. 정수나 자릿수를 고정한 문자열로 출력합니다.
- 위험: 언어당 250줄 상한(기존 원칙 PG28) 안에 에지 노드 · 집계기 · pub/sub 대역 · 가상 시계가 다 들어가는지는 확인 안 함입니다. 파일럿 1 에서 재 보고, 넘치면 시나리오를 줄일지 상한을 바꿀지를 그때 정합니다.
- 기존 규약에서 그대로 가져올 것: 한 편이 폴더 하나 · semver 버전 파일 · 머리말 · viz 도식(mermaid 금지) · 출처 규칙 · 평가 수치 금지 · 점검 문제와 풀이.
- 기존 규약에서 뺄 것: 「디자인 패턴을 충족하는 최소 조건」 절과 analyzer 계약. 그 자리는 「요구 충족 확인 표」(요구 수치마다 어느 시나리오의 어느 단계가 충족을 보이는가)로 대신하기를 권합니다.

## 4. 파일럿 두 편

| 파일럿 | 성격 | 이 편이 명세에서 검증하는 것 |
| --- | --- | --- |
| 라이브 동시 시청자 수 | 근사 허용 · 같은 값을 많은 화면에 뿌림(fan-out) · 갱신 주기 조절 | 규모 추정이 구조 선택을 바꾸는가, 개념도와 기술 설명이 1:1 로 맞는가, 실시간 전달 코드를 검증할 수 있는가 |

파일럿 1 의 근거는 [파일럿 리서치 노트](live-viewer-count-2026-11-13.md)에 모았습니다.
파일럿 2 는 리서치 노트를 아직 만들지 않았습니다. 재료는 [사례 목록](system-design-cases-2026-11-13.md)의 C5 · C13 · C14 · C15 · C16 이고, 실패 사례(배민의 복제 지연 초과 당첨, 올리브영의 미발급)까지 있어 시나리오 3 을 바로 채울 수 있습니다.
플래시 세일(CT-02)이나 티켓 예매(CT-03)보다 이 문제를 먼저 두는 이유는 사례 목록 3절에 적었습니다.

## 5. 정해 주셔야 할 것

추천을 먼저 적었습니다. 앞의 것이 정해져야 뒤의 것이 의미가 있는 순서입니다.

1. **구현 코드의 언어와 검증 방식 — 정함(2026-11-13)**
   - 결정: 기존 가이드와 같은 Java · TypeScript · Rust 세 언어 동일 출력 규약을 유지합니다. 답변 원문은 "세 언어 유지"입니다.
   - 검토했던 다른 길: TypeScript 한 언어(분량이 3분의 1) / docker compose 로 실제 Redis · Kafka 를 띄우는 예제(현실적이지만 검사 자동화와 재현 비용이 큼).
   - 적용 방식과 위험은 3절 「구현 코드」 항목에 적었습니다.
2. **저장 위치와 명세 이름 — 정함(2026-11-13)**: `pattern-guide/system-design-guide/<슬러그>/`, 명세 id `system-design-guide`. 질문은 "저장 위치를 pattern-guide/system-design-guide/, 명세 id 를 system-design-guide 로 할까요?"였고 답변 원문은 "그렇게 해"입니다.
   기존 `paths.json` 의 `dirs.tracks` 에 `"system-design-guide": "system-design-guide"` 한 줄을 더하는 방식이라 검사기 · 렌더러 경로 규약을 그대로 씁니다. 이 줄은 명세를 등록할 때 함께 넣습니다. 명세 없이 트랙만 있으면 그 폴더에 파일이 생기는 순간 검사기가 "spec 이 없습니다"로 멈추기 때문입니다(`scripts/check-guides.py:368-371`, 커밋 `e2384dd` 기준).
   검사기 코드를 읽어 확인한 것은 셋입니다. 트랙 목록을 `paths.json` 에서 읽고(`scripts/check-guides.py:258-271`), 최소 조건 같은 절별 검사는 명세에 그 절이 있을 때만 돌며(`:1063-1065`), 세 언어 컴파일 · 실행은 `### 구현` 헤딩으로 찾습니다(`:133`). 줄 번호는 검사기가 마지막으로 커밋된 `e2384dd` 기준입니다. 작업 트리의 검사기는 다른 작업이 고치는 중이라 줄 번호가 이 세션 안에서도 바뀌었습니다(같은 주석 줄이 1136행에서 1197행으로 밀림).
   그래서 트랙 한 줄과 명세 등록만으로 기존 검사가 붙습니다. 새 트랙으로 검사기를 실제로 돌려 보지는 않았습니다(확인 안 함). 명세를 등록한 뒤 파일럿 초안으로 돌려 봅니다.
3. **파일럿 사례 — 정함(2026-11-13)**: 4절의 두 편(RT-01 라이브 동시 시청자 수 · CT-01 선착순 쿠폰 발급).
4. **진행 관리 — 정함(2026-11-13)**: 칸반 루트 카드 하나에 하위 카드 셋(명세 등록 · 파일럿 두 편과 회고 · 1차 12편)을 둡니다.
   3·4 는 질문 "남은 두 결정(파일럿 두 편, 칸반 카드로 관리)을 추천대로 정할까요?"에 대한 답변 "추천대로"로 정했습니다.
