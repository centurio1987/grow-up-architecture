# 패턴 가이드 확장 집필 전략

- 작성일: 2026-11-06
- 성격: 조사에 근거한 **집필 제안과 실행 순서**. 새 가이드의 발행·새 명세의 적용 완료를 뜻하지 않는다.
- 근거: [56개 후보 조사서](pattern-expansion-research-2026-11-06.md), [현행 인덱스](../../PATTERNS.md), [집필 진입 스킬](../../.agents/skills/design-pattern-guide/SKILL.md), [현행 경로·명령 바인딩](../../.claude/authoring/paths.json).

## 1. 전략의 핵심

현재 37편은 객체 설계와 업무 개념 모델링에 집중되어 있다. 다음 확장은 **애플리케이션의 경계 → 분산 호출의 실패 → 데이터와 메시지 일관성 → 운영·이행**으로 이어지는 학습 흐름을 만든다. 사진의 8개를 사전처럼 나열하면 Saga와 Event Sourcing의 선행 지식이 빠지므로, 함께 필요한 패턴을 먼저 배치한다.

조사 후보 56건 중 **P0 12건을 첫 집필 묶음**, P1 21건을 후속 후보, P2 15건을 후순위로 둔다. 나머지 8건은 기초 4건과 다른 편에 흡수할 변형 4건이다. 우선순위는 보편적인 중요도나 사용 빈도의 점수가 아니라 **현재 저장소를 확장하는 순서에 대한 판단**이다.

첫 묶음의 목표는 12편을 빨리 추가하는 것이 아니라, 시스템 경계를 다루는 가이드를 검증할 수 있는 집필 체계를 만드는 것이다. Circuit Breaker와 Transactional Outbox 두 편을 파일럿으로 삼아 각각 상태 전이와 영속화·재시작 검증을 확인한다. 규약이 맞지 않으면 파일럿에서 수정하고 다음 묶음으로 넘어간다.

## 2. 채택과 분류 원칙

### 패턴을 독립 편으로 만드는 조건

1. 반복되는 문제와 해결 책임을 1차 자료에서 확인한다.
2. 기존 편과의 차이를 적용 경계·보장·포기하는 성질로 설명할 수 있다.
3. 정상 사례와 실패/변화 사례가 독립적으로 존재한다.
4. 최소 조건을 코드 구조 또는 관찰 가능한 시스템 성질로 판정할 수 있다.
5. 실패를 재현하는 실행 예제 또는 배포 검증이 가능하다. 설명만으로 실제 운영 보장을 주장하지 않는다.

이 조건을 충족하지 못하면 참고 개념·비교 절·구현 변형으로 수록한다. 별칭은 독립 패턴으로 세지 않는다. 반대로 구조가 비슷하다는 이유만으로 서로 다른 목적의 패턴을 합치지 않는다.

### 트랙 제안

| 트랙 / 명세 | 대상 | 판정 단위 | 처리 |
| --- | --- | --- | --- |
| 기존 `gof-guide` | 객체 설계 | 객체 역할·의존 방향·행위 | 기존 26편 유지 |
| 기존 `analysis-guide` | 업무 개념 모델 | 개념 책임·불변식 | 기존 11편 유지 |
| 제안 `architecture-guide` | API·분산 데이터·메시징·회복·배포·이행·영속성 | 경계·실행 경로·실패 조건·관찰 결과 | 신규 트랙으로 시작하고 분야는 메타데이터로 구분 |

제안 물리 경로는 `pattern-guide/architecture-pattern-guide/<slug>/`다. 이 경로와 `architecture-guide`는 **아직 등록되지 않았다**. 처음부터 여섯 종류의 명세를 만들지 않고 공통 명세 하나에 검증 프로필을 붙인다. 영속성 편도 우선 이 명세를 사용하되 파일럿 결과로 분리가 필요한지 판단한다.

Service Mesh는 여러 패턴을 조합하는 아키텍처 접근이며, Timeout은 기법 성격이 강하다. 메타데이터에 `kind: pattern | architecture | technique | concept`를 구분한다. 목록을 모두 같은 추상화 수준의 GoF 패턴이라고 부르지 않는다.

## 3. 선행 참고 문서와 공통 예제

기존 DDD 전술 용어·회계·GoF 참고 문서를 재사용한다. 새 참고 문서는 아래 네 개념군을 권고한다. 후보 카탈로그의 ‘기초 4건’과 문서 수가 같아야 하는 것은 아니다. 참고 문서는 개별 패턴명이 아니라 **개념군** 단위다.

| 제안 참고 문서 | 범위 | 먼저 필요한 편 |
| --- | --- | --- |
| 분산 호출과 실패 | 프로세스/네트워크 경계, 부분 실패, Timeout/Deadline, 취소, 재시도 예산 | Retry, Circuit Breaker, API Gateway |
| 메시지 전달과 멱등성 | 명령/이벤트, ack, 재전달, 순서 범위, Correlation ID, 업무 키, 중복 제거 | Idempotent Consumer, Outbox, Saga |
| 트랜잭션 경계와 일관성 | 로컬 ACID, 소유권, 원자성/격리, 최종 일관성, 보상과 rollback | Database per Service, Outbox, Saga, CQRS |
| 이벤트 상태와 파생 모델 | Domain Event/통합 이벤트, 원천/파생 상태, projection, replay, schema version | CQRS, Event Sourcing |

배포 기초와 Service Registry는 Sidecar·Mesh·Discovery 편 착수 시 필요 범위를 확인해 별도 참고 문서로 분리하거나 공통 문서에 포함한다. 아직 없는 참고 문서 경로를 실제 링크처럼 가이드에 넣지 않는다.

**공통 도메인:** 주문·결제 승인·재고 예약을 권고한다. 정상 주문, 재고 부족, 결제 응답 유실, 메시지 중복, 발행 프로세스 재시작을 같은 용어로 설명한다. 각 편은 자기완결이어야 하므로 앞 편의 코드를 모두 실행해야 다음 편이 돌아가는 구조는 피한다.

기존 회계 예제는 수정하지 않는다. Saga의 ‘결제 승인 취소’와 Account의 ‘역분개’는 현실에서 연결될 수 있어도 같은 연산이라고 가정하지 않는다. 예제의 업무 규칙·예약 만료·취소 가능 시점·중복 요청 식별 범위는 공통 리서치 노트에 먼저 확정한다.

## 4. 첫 12편의 집필 순서와 완료 조건

아래 순서는 **실제 집필 순서**다. 독자에게 제시할 목차 순서는 뒤에서 다르게 구성한다. 선수 지식은 참고 문서로 먼저 확보해 순환 의존을 피한다.

| 순서 | 후보 ID / 편 | 선행 산출물 | 정상·실패 시나리오 / 핵심 검증 |
| --- | --- | --- | --- |
| 1 | R02 Retry | 호출·메시지 기초 | 한시적 실패 후 성공 / 영구 오류와 예산 소진. 제한 횟수·총 대기 예산·재시도 가능 오류를 검사 |
| 2 | A03 Circuit Breaker — 파일럿 1 | Retry, 가상 시계 | 정상 호출 / 임계값 도달→차단→복구 탐색. Open 중 원격 호출 수 0, Half-open 동시 탐색 제한을 검사 |
| 3 | D01 Database per Service | DDD·일관성 기초 | 서비스 소유 데이터 갱신 / 타 서비스의 직접 쓰기 거절. 같은 DB 서버에서도 논리 소유권을 검증 |
| 4 | D03 Idempotent Consumer | 메시지·트랜잭션 기초 | 첫 처리 / 같은 메시지 재전달·동시 도착·재시작. 중복 기록과 업무 효과의 원자성을 검사 |
| 5 | D02 Transactional Outbox — 파일럿 2 | 3·4 | 업무 변경과 Outbox 커밋 / 커밋 뒤 발행 전 중단·발행 뒤 표시 전 중단. 재시작 후 누락 방지와 중복 소비 처리를 검사 |
| 6 | A04 Saga | 3·4·5 | 모든 단계 성공 / 재고 실패·보상 재시도·보상 불가능. 상태를 영속화하고 최종 성공/보상 완료/개입 필요를 구분 |
| 7 | A05 CQRS | 파생 모델 기초 | 쓰기 모델 갱신 후 조회 / projection 지연·재전달. 갱신 버전과 조회 버전을 표시하고 동일 DB 변형도 설명 |
| 8 | A06 Event Sourcing | 7, 이벤트 기초 | 기록→재생 / 오래된 이벤트·중복 명령·스냅숏 이후 재생. 전체 재생과 스냅숏 재생의 상태 일치, 외부 효과 재실행 방지를 검사 |
| 9 | A01 API Gateway | 호출 기초·1·2 | 경로별 요청 전달 / 하위 서비스 지연·실패. 라우팅·오류 계약·인증 책임의 경계를 검증 |
| 10 | R05 Cache-Aside | 저장/파생 상태 개념 | miss→저장소 조회→cache hit / 갱신과 읽기의 경합·만료. 낡은 값이 허용되는 범위와 무효화 정책을 검증 |
| 11 | A07 Strangler Fig | 9, 데이터 소유권 | 기능 일부 이관 / 이관 중 실패·복귀. 기능별 라우팅, 데이터 쓰기 주체, 구 기능 제거 조건을 검사 |
| 12 | A08 Sidecar | 배포 기초 | 별도 구성요소로 보조 기능 제공 / 보조 프로세스 중단·종료. 프로세스 경계·건강 상태·종료 처리를 실행으로 확인 |

파일럿 1 종료 후 상태 전이·가상 시계 규약을 확정한다. 파일럿 2 종료 후 영속화·재시작·중복 전달 규약을 확정한다. 12편은 발행 가능한 완성본 기준이다. 규약·참고 문서·실험 환경 구축은 별도 작업으로 집계한다. 기존 37편이 유지되고 12편이 모두 발행될 때 **49편**이 된다.

사진의 Service Mesh는 누락하지 않고 P1의 첫 운영 종합 편으로 둔다. Gateway·Sidecar·호출 실패를 설명한 뒤 집필해야 구성요소 이름만 나열하는 문서가 되지 않는다. 따라서 사진 8개 중 첫 묶음은 7개, 다음 묶음에 Mesh 1개다.

## 6. 새 집필 규약의 구체안

### 공통 본문 골격

기존의 개요 → 시나리오 → 개념 정리 → 사용 목적 → 최소 조건·비교 → 구현 → 자기 점검 → 참고 자료 흐름을 계승한다. 다음 내용을 `architecture-guide`에서 추가한다.

- 상황 설정: 배포 단위, 데이터 소유자, 호출/메시지 방향, 트랜잭션 범위, 신뢰 경계.
- 시나리오: 정상 흐름 하나 + 실패/변화 흐름 하나 이상. 데이터 일관성 패턴에는 중단·재시작 흐름 추가.
- 보장: 정상 조건과 장애 가정을 함께 쓰고, 보장하지 않는 성질과 운영자의 개입 지점을 명시.
- 최소 조건: 각 `[필수]` 조건에 코드·설정·검증 사례 ID를 연결. 구현 제품명을 패턴의 필수 조건으로 만들지 않음.
- 비용: 지연·자원·운영 부담을 비교하되 실행하지 않은 처리량 수치는 만들지 않음.
- 도식: 정적 배치 + 시간 순서/상태 전이. 기존 React 도식·이미지 렌더·잘림 확인 규칙 계승.
- 운영: timeout/retry 한도, 관측 신호, 실패 후 복구/수동 처리, 버전 및 재현 명령.

### 실행 예제의 세 프로필 — 제안이며 현재 검사기에는 없음

| 프로필 | 적합한 편 | 필수 증거 |
| --- | --- | --- |
| `model` | Retry, Circuit Breaker 등 | Java/TypeScript/Rust의 결정적 모델과 동일 기대 출력. 시계·난수·스케줄을 제어 |
| `system` | Outbox, Saga, Event Sourcing 등 | 세 언어 핵심 모델 + 대표 통합 실험 하나. 실제 영속 저장·프로세스 중단·재시작 결과와 업무 불변식 |
| `deployment` | Sidecar, Service Mesh 등 | 최소 앱과 버전을 고정한 배포 설정. 실제 트래픽·정책·수명주기 검증. 동일 구조의 앱을 세 언어로 복제할지는 필요성으로 판정 |

기존 두 명세의 세 언어 계약은 유지한다. 신규 명세에서만 프로필별 요구를 정의한다. 메모리 예제의 성공으로 DB 원자성·네트워크 보안·분산 격리를 입증했다고 쓰지 않는다. 실제 환경 실행이 필요한데 불가능하면 그 편은 실험 미완료 초안으로 남긴다.

분산 실험은 로그 순서가 매번 같지 않다. 타임스탬프와 요청 ID를 무작정 지운 뒤 텍스트만 비교하지 않는다. 결정적 모델에는 기존 출력 일치를 적용하고, 실제 실험에는 **최종 상태·중복 효과 수·재처리 가능성·시간 한도**처럼 의미가 있는 assertion을 사용한다. 순서 자체가 보장 대상이면 aggregate/partition별 순서를 별도로 검증한다.

### 패턴별로 금지할 과도한 일반화

| 주제 | 가이드가 피해야 할 단정 |
| --- | --- |
| CQRS | DB 두 개·비동기 처리·Event Sourcing이 필수 |
| Event Sourcing | 이벤트 로그만 있으면 해당, 감사 로그와 같음, 모든 업무에 적용해야 함 |
| Saga | ACID rollback과 동일, 보상하면 항상 과거 상태로 복원, 격리 문제 없음 |
| Outbox | 중복이 없어짐, 소비까지 exactly-once 보장 |
| Retry | 모든 오류에 반복하면 안정성이 좋아짐 |
| Circuit Breaker | fallback 필수, 차단 기능만으로 모든 자원 고갈 해결 |
| Service Mesh | Sidecar 필수, 애플리케이션의 업무 멱등성을 대신 해결 |
| Strangler Fig | 신버전으로 트래픽 비율만 바꾸면 이행 완료 |

이 경계의 사실 근거는 조사서 S06~S14와 개별 패턴 자료에 연결한다. 집필 시 각 최소 조건의 근거를 다시 대조한다.

## 7. 저장소 적용 작업과 순서

이번 작업에서는 아래를 실행 계획으로만 작성했다. 실제 규약 변경과 가이드 집필은 이 문서를 기준으로 별도 작업 단위로 진행한다.

| 단계 | 변경 대상 | 완료 조건 |
| --- | --- | --- |
| E0 기준선 | `candidates.md`의 결정 기록과 신규 후보 원장 | 추천·채택·집필 중·발행을 구분. 날짜·후보 ID·spec·근거·대체한 판단을 기록 |
| E1 명세 | `.claude/authoring/specs/architecture-guide/` 및 캔버스 | 필수 절, 최소 조건, 실행 프로필, 품질 루브릭 확정 |
| E2 바인딩 | `.claude/authoring/paths.json`, 가이드 진입 스킬 | 신규 트랙·캔버스·명령을 연결. `.agents` 쪽 진입 파일과 불일치 여부 확인 |
| E3 검사 | `scripts/check-guides.py`, 렌더러·분석 스킬 연동 | 신규 프로필 검사 추가, 기존 두 트랙 회귀 검사. 실제 지원 전에는 명세 등록만으로 완료 처리하지 않음 |
| E4 규약 고정 | authoring lock 및 resolve | 규약 개정 사유 기록 후 의도적으로 갱신. frozen resolve 성공 |
| E5 기초·파일럿 | 참고 문서, Circuit Breaker, Outbox | 정상/실패/재시작 증거와 품질 게이트 통과 |
| E6 본집필 | 12편의 나머지, 인덱스·HTML·게이트 기록 | 편별 기계 검사→품질 게이트→발행. 필요 참고 문서를 함께 발행 |
| E7 확장 판단 | P1 묶음과 P2 처분 | 파일럿의 실제 소요 작업·결함을 보고 범위를 재조정 |

현행 검사기는 트랙 일부를 설정으로 읽지만 `mode_run`은 Java·TypeScript·Rust 파일과 동일 출력을 요구한다. 또 공유 규약 검사는 기존 두 명세를 명시적으로 순회한다. **트랙 한 줄 추가만으로 새 검증 프로필이 지원된다고 볼 수 없다.** 렌더러·포인터·게이트 집계·analyzer의 spec 처리까지 점검해야 한다.

가이드 진입 스킬은 기존 트리 밖 새 패턴에 대해 `candidates.md`의 결정에 spec이 있어야 한다고 규정한다. 이번 문서의 P0는 권고이므로 승인된 발행 결정으로 위장해 기록하지 않는다. 착수 작업에서 적용 범위를 확정하면 후보 ID별 명세 배정을 결정 절에 반영한다.

## 8. 편별 작업 카드와 품질 게이트

각 작업 카드는 다음 내용을 가진다.

- 후보 ID·정규 이름·별칭·분류·spec·실행 프로필.
- 현재 처분과 근거: 신규 발견 / 기존 언급 / 과거 제외 재평가.
- 원전·공식 구현 자료의 확인 범위와 미해결 질문.
- 기존 가이드와의 차이, 사전 지식, 기본/실패/복구 시나리오.
- `[필수]` 조건별 증거 표: 주장 → 코드/설정 → 실행 검사 → 결과.
- 본문·예제·도식·HTML·게이트 기록의 경로와 완료 상태.

진행 상태는 `수집 → 근거 확인 → 채택 → 집필 → 검증 → 발행`으로 구분한다. ‘기계 검사 통과’와 ‘품질 게이트 통과’도 별개다. 기존 스킬의 최대 3라운드·자동 통과 금지·발행본 포인터·참고 문서 serves 역참조 규칙을 계승한다. 실제 가이드 검증에 외부 모델 비평 단계를 임의로 추가하지 않는다.

최초 완료 기준은 후보 56건의 이름을 모두 문서로 만드는 것이 아니라 다음과 같다.

1. 새 명세와 실행 프로필이 실제 검사기에 연결됨.
2. 기존 가이드 검증이 유지됨.
3. 파일럿 두 편이 장애·재시작 증거를 포함해 통과함.
4. 첫 묶음 12편이 각각 발행 상태와 인덱스·HTML·게이트 기록을 가짐.
5. 후속 21건의 우선순위가 파일럿 결과로 재검토됨.

기간은 지금 단정하지 않는다. 파일럿에서 원전 조사·참고 문서·예제·실험 환경·게이트 수정 시간을 따로 기록하고, 그 결과로 이후 묶음의 예상 작업량을 잡는다.

## 9. 독자용 목차와 발견 경로

집필 순서와 달리 독자용 목차는 문제 중심으로 제공한다.

| 독자의 질문 | 안내할 편 |
| --- | --- |
| 서비스를 어떻게 나누고 어디로 요청을 보내나? | Database per Service → API Gateway → 후속 분해·ACL |
| 느리거나 실패하는 의존성은 어떻게 다루나? | Retry → Circuit Breaker → 후속 Bulkhead·Rate Limiting |
| DB 변경과 메시지 발행은 어떻게 함께 지키나? | Idempotent Consumer → Outbox → Saga |
| 읽기와 쓰기 요구가 다르면 어떻게 하나? | CQRS → Event Sourcing, Cache-Aside와 비교 |
| 구 시스템과 공통 운영 기능은 어떻게 분리하나? | Strangler Fig → Sidecar → Service Mesh |

새 편이 발행되면 `PATTERNS.md`에 아키텍처 계열과 비교 쌍을 **수동 삽입**한다. 미발행 후보를 가이드 링크로 등록하지 않는다. README의 편 수·트랙 안내는 실제 발행 상태에서 갱신한다. 외부 자료를 추가로 발견하면 ‘출처에 있는 이름인가’만 확인하지 말고 기존 후보와의 의도·보장 차이를 적어 중복을 막는다.
