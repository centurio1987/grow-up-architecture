한눈에 보는 개요

작은 상점의 알림 발송 코드를 하나 떠올려 봅시다. 주문이 나가면 고객에게 문자 한 통을 보내는 클래스가 있고, 하는 일은 받은 본문을 발송망에 넘기는 것 하나뿐이에요. 그런데 요구가 하나씩 붙습니다. 이번 달부터 모든 알림 끝에 상점 서명이 들어가야 하고, 감사 때문에 보낸 건마다 일련번호가 영수증에 찍혀야 하고, 법무팀은 본문에 긴 숫자가 그대로 나가지 않게 가려 달라고 해요.

문제는 이 셋이 늘 함께 붙지 않는다는 데 있습니다. 마케팅 알림에는 서명만, 배송 알림에는 서명과 감사 번호가, 환불 알림에는 셋 다 붙어요. 조합마다 클래스를 만들면 몇 개가 필요한지 세어 봅시다.

책임 3개를 클래스로 굳힐 때 필요한 클래스 수

  켜고 끄는 조합만 세면            2³ = 8개
  붙는 순서도 결과를 바꾼다면       ₃P₀+₃P₁+₃P₂+₃P₃ = 1+3+6+6 = 16개
  책임이 하나 늘어 4개가 되면       조합만 16개, 순서까지 세면 65개

순서까지 세야 하는 이유는 시나리오 2 가 실제로 보여 줍니다. 서명에 담당자 전화번호가 들어 있어서, 숫자를 가리는 일을 서명보다 먼저 하느냐 나중에 하느냐로 고객에게 나가는 문자가 달라져요.

Decorator 의 해법은 책임 하나를 원래와 똑같은 인터페이스를 가진 층으로 만들어, 대상을 감싸 두는 것입니다. 층은 자기 일을 한 뒤 안쪽으로 요청을 그대로 넘기고, 안쪽은 자기를 누가 감쌌는지 모릅니다. 조합은 클래스가 아니라 객체를 조립할 때 정해져요.

Before : 조합마다 클래스를 만든다

  SmsNotifier
  SignedSmsNotifier                  ← 서명만
  SignedAuditedSmsNotifier           ← 서명 + 감사
  MaskedSignedAuditedSmsNotifier     ← 셋 다
  AuditedSignedSmsNotifier           ← 순서가 다른 같은 셋 … 클래스가 계속 늘어난다

After : 책임 하나가 층 하나가 되고, 조합은 조립할 때 고른다

  new AuditNotifier( new SignatureNotifier( sms ) )              ← 배송 알림
  new SignatureNotifier( new MaskingNotifier( sms ) )            ← 마스킹이 서명까지 덮는 구성
  new MaskingNotifier( new SignatureNotifier( sms ) )            ← 같은 셋, 다른 순서, 다른 결과
                       ↑ 층은 전부 같은 인터페이스라 아무 자리에나 들어간다

분류는 구조 패턴이고, 대상을 감싸는 방식만 쓰므로 객체 범위에만 실려요. 다른 이름은 Wrapper 입니다(근거: GoF Decorator 절 Also Known As — GoF 는 Gang of Four 의 줄임말로, 1994년에 나온 Design Patterns 의 저자 네 명을 함께 부르는 이름). 함께 쓰는 패턴은 Adapter · Proxy 입니다.

이 글은 시나리오 셋을 따라갑니다. 알림 한 통이 두 겹을 지나 나갔다 돌아오는 길, 새 요구가 들어올 때 무엇이 바뀌고 무엇은 안 바뀌는가, 조합을 상속으로 굳히거나 참조에 구체 타입을 적거나 전달을 끊거나 객체 동일성에 기대면 어디서 막히고 무엇이 어긋나는가. 끝까지 읽으면 어떤 코드를 Decorator 라고 불러도 되는지 필수 조건 다섯으로 판정할 수 있고, Adapter·Proxy 와도 물음 셋으로 구분할 수 있게 됩니다.

시나리오 1 — 알림 한 통이 두 겹을 지나 나갔다 돌아오는 길

주문 BOOK-042 가 발송됐고, 고객에게 알림 한 통이 나가야 합니다. 실제로 보내는 일은 이미 SmsNotifier 가 하고 있어요. 이번 건에는 상점 서명이 붙어야 하고, 감사 기록을 위해 영수증 끝에 일련번호도 찍혀야 합니다. 들어가는 값은 발송 데스크가 만든 본문 order BOOK-042 shipped today 하나이고, 나와야 하는 값은 영수증 sent[order BOOK-042 shipped today -- Bbangto Store CS 010-1234-5678]+audit#1 입니다. 이 장면에는 다섯이 등장해요. 알림을 시키는 ShipmentDesk(패턴에서는 Client 라고 부르는 역할), 알림을 보내는 연산 모양 Notifier(Component), 실제로 보내는 SmsNotifier(ConcreteComponent), 그리고 사이에 놓인 두 층 AuditNotifier 와 SignatureNotifier(ConcreteDecorator)입니다. 이름은 여기서 한 구절씩만 소개하고 정식 정의는 개념 정리에서 해요.

  1. ShipmentDesk 가 Notifier 의 send(...) 를 부릅니다. 발송 데스크가 아는 타입은 Notifier 하나뿐이고, 자기가 받은 것이 감싸지 않은 SmsNotifier 인지 두 겹이 감긴 물건인지 모릅니다. 모르는 편이 나은 이유는 조합이 자주 바뀌기 때문이에요. 발송 데스크가 층의 개수를 알면 마케팅 알림과 환불 알림마다 발송 데스크 코드가 달라집니다.
  2. 바깥 층 AuditNotifier 가 전달하기 전에 자기 일을 합니다. 받은 횟수를 하나 올려 1 로 만들어요. 이 일을 전달 앞에 두는 이유는 세는 대상이 "요청이 들어왔다"는 사실이기 때문입니다. 뒤로 옮기면 안쪽에서 발송이 실패해 예외가 나갈 때 그 요청은 숫자에 잡히지 않고, 감사 기록에 빠진 부분이 생깁니다.
  3. AuditNotifier 가 자기가 가지고 있는 Notifier 참조로 요청을 그대로 전달합니다. 이 참조에 무엇이 들어 있는지는 모릅니다. 필드에 적힌 타입이 Notifier 라서 구체 클래스를 물어볼 방법이 없고, 물어볼 필요도 없어요. 실제로 지금 들어 있는 것은 감싸지 않은 발송기가 아니라 또 다른 데코레이터인데, 바깥 층은 이 사실을 끝까지 모릅니다.
  4. 안쪽 층 SignatureNotifier 도 전달하기 전에 자기 일을 합니다. 본문 끝에 서명 -- Bbangto Store CS 010-1234-5678 을 이어 붙이고, 그렇게 길어진 본문으로 다시 안쪽에 전달해요. 서명을 전달 앞에 두는 이유는 서명이 고객에게 실제로 나가는 본문 안에 들어 있어야 하기 때문입니다. 뒤로 옮겨 영수증에만 붙이면 기록에는 서명이 보이는데 고객이 받은 문자에는 없습니다.
  5. SmsNotifier 가 본문을 보관함에 넣고 영수증 sent[...] 를 돌려줍니다. 이 층에서 되돌아 나오는 이유는 여기가 유일하게 남에게 넘길 대상을 가지고 있지 않은 층이기 때문이에요. 데코레이터들은 전부 다음 층을 필드로 가지고 있지만 이 클래스는 가진 것이 없고, 그래서 요청이 여기서 끝나고 답이 돌아갑니다.
  6. 영수증이 SignatureNotifier 를 지나 그대로 올라갑니다. 이 층에는 전달 뒤에 할 일이 없어요. 추가 책임이 앞과 뒤 어느 한쪽에만 있어도 되기 때문이고, 비어 있는 뒤쪽을 억지로 채울 이유는 없습니다.
  7. AuditNotifier 가 전달한 뒤에 자기 일을 합니다. 올라온 영수증 끝에 +audit#1 을 붙여요. 이 일이 뒤에 있어야 하는 이유는 붙일 대상이 안쪽이 만들어 준 영수증이라서입니다. 전달 앞으로 옮기면 아직 없는 문자열에 이어 붙이는 셈이 됩니다.
  8. ShipmentDesk 가 영수증 문자열 하나를 결과로 받습니다. 몇 겹을 지났는지, 어느 층이 무엇을 더했는지는 그 문자열 어디에도 타입으로 남아 있지 않아요. 발송 데스크가 보는 것은 Notifier 가 약속한 반환 하나입니다.
단계   부르는 쪽 → 받는 쪽            본문                                     영수증
 1     Client → Component(바깥 층)   "order BOOK-042 shipped today"           (8단계에서 받음)
 2     Audit  → (자기 안)             그대로                                    —  횟수 0 → 1
 3     Audit  → 다음 층               그대로                                    —
 4     Sign   → (자기 안)             본문 + " -- Bbangto Store CS 010-1234-5678"
 5     Sign   → SmsNotifier           위의 긴 본문                              "sent[…]"
 6     Sign   → Audit                 —                                        그대로 올려보냄
 7     Audit  → (자기 안)             —                                        "sent[…]" + "+audit#1"
 8     Audit  → Client                —                                        "sent[…]+audit#1" 전체

잠깐, 확인 하나만 해 볼까요? 3단계에서 AuditNotifier 가 가지고 있는 참조의 타입이 Notifier 가 아니라 SmsNotifier 였다면, 위 표에서 무엇이 달라질까요?

표의 1·2·7·8 단계는 그대로입니다. 사라지는 것은 서명 층이 맡던 4단계와 6단계이고, 3단계의 전달은 곧장 SmsNotifier 로 갑니다. 필드가 SmsNotifier 면 그 자리에 SignatureNotifier 를 넣을 수 없어서, 감사 층은 발송기를 직접 감싸는 것 말고는 할 수 있는 일이 없습니다. 그러면 층이 하나밖에 못 쌓이고, 이 패턴이 조합을 다루려고 존재하는 이유가 사라져요. 시나리오 3 의 2단계가 이것을 세 언어의 컴파일 오류로 확인합니다.

AuditNotifier 의 참조 필드에 적힌 타입이 정하는 것

  Notifier inner      →  Audit( Signature( Sms ) )   그 자리에 층이 또 들어간다
  SmsNotifier inner   →  Audit( Sms )                발송기 말고는 못 들어간다

이 시나리오가 보여 준 것은 전달이 재귀로 일어난다는 사실과 추가 책임이 붙는 자리가 둘이라는 사실입니다. 바깥 층은 자기가 넘긴 상대가 또 다른 층인지 감싸지 않은 발송기인지 구별하지 못하고(3단계), 그래서 같은 과정이 안쪽 끝까지 되풀이돼요(4·5단계). 책임은 전달 앞(2·4단계)이나 뒤(7단계) 어디에든 붙고, 한쪽은 비어도 됩니다(6단계). 그동안 Client 가 보는 인터페이스는 하나입니다. Notifier 뿐이에요(1·8단계).

시나리오 2 — 개인정보를 가리라는 요구가 들어올 때

법무팀에서 요구가 내려왔습니다. 알림 본문에 네 자리 이상 이어진 숫자가 그대로 나가면 안 된다는 것이고, 시행일은 다음 주예요. 지금 운영 중인 알림 구성은 여럿이라 전부 한꺼번에 바꿀 수는 없고, 우선 배송 알림부터 적용해야 합니다. 품목 코드 BOOK-042 의 042 는 세 자리라 그대로 나가야 하고, 서명 안의 010-1234-5678 은 010-****-**** 가 돼야 해요.

  1. MaskingNotifier 클래스를 하나 새로 씁니다. 구현하는 연산 모양은 시나리오 1 이 쓴 Notifier 그대로예요. 여기서 sendMasked 같은 새 이름을 만들면 안 되는 이유는, 그 순간 이 클래스가 기존 층들과 겹쳐 쌓일 수 없는 물건이 되기 때문입니다. 층끼리 서로를 받아 주는 것은 셋 다 같은 인터페이스를 구현하고 있어서지 이름이 비슷해서가 아니에요.
  2. 조립 코드에서 층 하나를 끼웁니다. 바뀌는 곳은 객체를 엮는 그 줄 하나고, SmsNotifier·SignatureNotifier·AuditNotifier·ShipmentDesk 는 한 글자도 안 바뀌어요. 이것이 가능한 이유는 데코레이터가 가지는 참조의 타입이 구체 클래스가 아니라 Notifier 이기 때문입니다. 그 자리는 Notifier 를 구현한 무엇이든 받으므로 새 층이 끼어들 틈이 이미 있어요.
  3. 어느 자리에 끼우느냐로 고객이 받는 문자가 달라집니다. 서명 층을 바깥에 두면(SignatureNotifier(MaskingNotifier(sms))) 서명이 먼저 붙고 그 결과가 마스킹 층을 지나므로 서명 속 전화번호까지 가려집니다. 마스킹 층을 바깥에 두면(MaskingNotifier(SignatureNotifier(sms))) 마스킹이 먼저 끝난 뒤에 서명이 붙으므로 전화번호가 그대로 나가요. 직접 실행하면 앞은 … CS 010-****-****, 뒤는 … CS 010-1234-5678 로 끝납니다. 왜 이렇게 되는지는 시나리오 1 의 2·4단계에 이미 나와 있어요. 바깥 층의 전 처리는 안쪽 층이 아직 더하지 않은 본문에만 적용됩니다.
  4. 같은 층을 두 번 겹칠 수도 있습니다. SignatureNotifier(SignatureNotifier(sms)) 는 서명이 두 번 붙은 본문을 내보내고, 이것도 컴파일되고 돌아가요. 되는 이유는 3단계와 같습니다. 참조 타입이 추상이라 데코레이터는 자기와 같은 종류도 받아요. 만약 서명을 상속으로 붙였다면 서명을 두 번 붙이는 하위 클래스를 따로 새로 써야 합니다. 한 클래스가 같은 상위 클래스를 두 번 상속할 수는 없으니까요.

여기서 헷갈리기 쉬운 포인트는 층을 쌓는 순서가 아무래도 좋다고 믿는 것입니다. 3단계의 두 결과가 보여 주듯 순서는 결과를 바꿔요. 그리고 이것은 구현을 잘못해서 생긴 사고가 아니라 이 패턴을 쓰면 따라오는 성질입니다. 층마다 자기 일을 하는 시점이 전달의 앞뒤로 나뉘는 이상, 어떤 층은 다른 층이 만든 결과 위에서 일하고 어떤 층은 그 전에 일해요. 그래서 조립 코드는 "무엇을 켤 것인가" 뿐 아니라 "어떤 순서로 켤 것인가"까지 정하는 자리가 되고, 그 줄은 아무 데나 흩어 두면 안 되는 줄이 됩니다(refactoring.guru — Decorator 도 순서에 의존하지 않게 데코레이터를 짜기가 어렵다는 점을 이 패턴의 단점으로 듭니다).

이 시나리오가 보여 준 것은 변화의 범위와 그 대가입니다. 책임이 하나 늘 때 바뀌는 곳은 새 클래스 하나와 조립 코드 한 줄이고, 기존 층과 Client 는 그대로예요(1·2단계). 참조 타입이 추상이라는 한 가지 덕분에 새 층을 아무 자리에나 끼워 넣을 수 있고, 같은 층을 두 번 겹칠 수도 있습니다(2·4단계). 대신 대가가 있습니다. 조합의 순서가 뜻을 갖게 되고, 그 뜻을 아는 코드는 조립하는 곳 한 군데로 모여요(3단계).

시나리오 3 — 상속으로 굳힌 조합 · 구체 타입 참조 · 끊긴 전달 · 객체 동일성은 어디서 막히고 무엇이 어긋나는가

같은 알림 코드를 네 사람이 각자 다르게 손봅니다. 한 사람은 조합을 클래스로 굳히려 하고, 한 사람은 참조 필드에 구체 타입을 적고, 한 사람은 가릴 것이 있으면 아예 안 보내게 고치고, 한 사람은 발송기별 설정을 맵에 담아 관리해요. 넷을 차례로 따라가되, 두 번째 수정에는 진단을 읽는 단계를 하나 더 붙입니다. 언어마다 컴파일러가 막아 주는 정도가 다르거든요. 그래서 단계는 다섯이에요. 아래 진단은 javac 21.0.11 · tsc 5.9.3 · rustc 1.95.0 으로 실제로 컴파일해 받은 것이고, 옮기면서 무엇을 지웠는지는 각 줄에 적었습니다.

  1. 첫 사람이 조합을 클래스 이름으로 굳힙니다. SignedAuditedSmsNotifier extends SmsNotifier 를 만들고 그 안에서 서명과 감사 번호를 함께 처리해요. 지금 당장은 돌아갑니다. 문제가 생기는 지점은 두 번째 조합이 필요해질 때인데, 개요에서 센 것처럼 책임 셋이면 순서를 따져 클래스가 열여섯 개까지 갈 수 있어요. 그리고 개수보다 무거운 문제가 따로 있습니다. 상속으로 붙인 책임은 런타임에 뗄 수 없어요. 같은 객체를 두고 이번 발송에만 감사 번호를 빼는 일이 불가능하고, 시나리오 2 의 4단계처럼 같은 책임을 두 번 붙이는 것도 안 됩니다.

이 시나리오가 보여 준 것은 규칙 넷을 어길 때 나타나는 결과의 차이입니다. 조합을 클래스로 굳히면(1단계) 당장은 돌아가지만 조합이 늘 때마다 클래스가 늘고, 무엇보다 런타임에 뗄 수 없게 돼요. 참조 필드에 구체 타입을 적으면 겹쳐 쌓기가 컴파일에서 막히는데(2단계), 컴파일러가 막아 주는 정도는 언어마다 다릅니다(3단계). 전달을 끊거나(4단계) 객체 동일성에 기대면(5단계) 아무 도구도 잡아 주지 않아요. 컴파일러가 잡는 규칙과 사람이 지켜야 하는 규칙을 구분해 두는 것이 이 시나리오의 소득입니다.

개념 정리

시나리오에 나온 역할 다섯을 정식으로 정의합니다. 앞의 넷은 GoF 가 이 패턴의 참여자로 적은 역할이고, Client 는 예시에 등장하므로 함께 답니다(근거: GoF Decorator 절 Participants·Collaborations).

  • Component — 장식되는 쪽과 장식하는 쪽이 함께 구현하는 연산 모양입니다. 이 인터페이스가 이 패턴의 축약된 계약이에요. Client 는 이것만 보고, 데코레이터는 이것을 구현하면서 동시에 이것을 필드로 가집니다. 구현하는 타입과 필드의 타입이 같기 때문에 층이 층을 감쌀 수 있어요. 알림 예에서는 send(body) 하나를 선언한 Notifier 가 Component 입니다.
  • ConcreteComponent — 장식이 붙기 전의 알맹이입니다. 이 패턴에서 유일하게 다음 층을 가지고 있지 않은 구현체이고, 그래서 요청이 여기서 멈추고 답이 되돌아갑니다(시나리오 1 의 5단계). 알림 예에서는 본문을 보관함에 넣고 영수증을 돌려주는 SmsNotifier 예요.
  • Decorator — Component 를 구현하면서 Component 참조를 하나 가지고, 받은 요청을 그 참조로 넘기는 역할입니다. 넘기는 일만 하고 더하는 일은 하지 않아요. 구체 데코레이터들이 되풀이해 쓰는 전달 코드를 한 곳에 모아 두는 자리라, 책임이 하나뿐이면 두지 않아도 됩니다. 알림 예에서는 NotifierDecorator 가 이 역할이에요. 다만 이 예시의 구체 층 셋은 모두 send 를 자기 것으로 덮어써서 이 클래스의 전달 코드는 실제로 실행되지 않고, 셋이 함께 물려받아 쓰는 것은 참조 필드와 그것을 받는 생성자입니다. 시나리오 1 의 6단계에서 영수증을 손대지 않고 올려보낸 것은 서명 층 자신의 전달 줄이에요.
  • ConcreteDecorator — 전달의 앞이나 뒤에 실제 책임을 더하는 쪽입니다. 앞에만 더해도 되고 뒤에만 더해도 되며(시나리오 1 의 4·6·7단계), Component 에 없는 연산이나 상태를 자기 것으로 가질 수도 있어요. 알림 예에서는 서명을 붙이는 SignatureNotifier, 숫자를 가리는 MaskingNotifier, 횟수를 세고 영수증에 번호를 붙이는 AuditNotifier 셋입니다.
  • Client — Component 타입으로만 대상을 받아 쓰는 쪽입니다. 몇 겹이 감겨 있는지, 어떤 순서로 감겨 있는지 모르고, 알 필요도 없어요(시나리오 1 의 1·8단계). 알림 예에서는 본문을 만들어 send 를 부르는 ShipmentDesk 가 Client 입니다. 조합을 고르는 일은 이 역할이 아니라 객체를 엮는 조립 코드가 맡아요. 뒤의 비교 절에서 「조합을 Client 가 고른다」고 할 때의 Client 는 패턴 바깥에서 층을 엮어 쓰는 쪽을 넓게 가리키는 말이고, 이 예시에서는 main 의 조립 코드가 그 자리입니다.

그림에서 Decorator 칸으로 들어가고 나가는 선을 봐 두세요. 위로는 Component 를 구현한다는 선이 있고, 옆으로는 Component 를 하나 갖는다는 선이 있습니다. 한 칸이 같은 타입과 이 두 관계를 함께 맺는다는 것이 이 패턴의 모양이고, 그래서 데코레이터가 데코레이터를 감싸도 타입이 맞아요. ConcreteDecorator 칸 안의 addedBehavior() 는 Component 에 없는 추가 연산인데, 이것을 두어도 되는지는 최소 조건 6번에서 다룹니다.

감싼 뒤에도 인터페이스가 같으면, 감싼 것을 다시 감쌀 수 있다.

사용 목적

Decorator 가 필요하다는 단서는 클래스 이름과 설정 코드에서 먼저 보입니다. 셋을 코드에서 무엇을 보면 되는지 표로 먼저 보고 차례로 봅시다.

단서코드에서 관찰되는 것확인 방법
1. 조합형 클래스 이름형용사가 둘 이상 붙은 구현 클래스가 여럿클래스 이름에서 공통 접미사를 뗀 나머지를 세어 봄
2. 대상마다 다른 조합같은 인터페이스를 쓰는 지점마다 켜는 것이 다름설정 파일이나 조립 코드에서 분기 개수를 셈
3. 런타임 착탈·상속 불가기능을 켜고 끄는 플래그가 구현체 안에 박혀 있거나, 대상 클래스가 final플래그 이름으로 검색하거나 상속 가능 여부를 확인

단서 1 — 클래스 이름이 책임을 이어 붙인 꼴로 자라고 있습니다

BufferedEncryptedFileStream 이나 SignedAuditedSmsNotifier 처럼 형용사가 쌓인 이름이 저장소에 생기기 시작하면, 조합을 타입으로 굳히고 있다는 신호예요. 개요에서 센 것처럼 책임 셋이면 순서를 따져 클래스가 열여섯 개까지 가고 넷이면 예순다섯 개까지 갑니다. 이름으로 검색되는 단서라 가장 알아보기 쉬워요.

클래스 이름에서 형용사를 떼어 보면
────────────────────────────────────────────────────────
SignedSmsNotifier                Signed
SignedAuditedSmsNotifier         Signed + Audited
MaskedSignedSmsNotifier          Masked + Signed
AuditedMaskedSmsNotifier         Audited + Masked      ← 순서만 다른 같은 둘
   떼어 낸 형용사 하나하나가 층 하나가 될 후보다

단서 2 — 같은 인터페이스 위에 더하고 싶은 것이 여럿이고, 켜고 끄는 조합이 대상마다 다릅니다

로깅·재시도·캐싱·계측·마스킹처럼 본래 일과 나란히 붙는 것들이에요. 이 단서가 중요한 이유는 조합이 대상마다 다르다는 조건에 있습니다. 모든 대상에 늘 같은 셋이 붙는다면 그냥 한 클래스 안에서 처리하는 편이 간단하고, 층을 나눠도 얻는 것이 없어요. 배송 알림에는 둘, 환불 알림에는 셋이 붙는 시나리오 2 의 상황이 이 단서입니다.

단서 3 — 붙였다 뗄 수 있어야 하거나, 서브클래싱할 수 없습니다

어떤 계정만 잠시 상세 로깅을 켜야 한다면 그 책임은 런타임에 붙고 떨어져야 하고, 상속으로는 안 돼요(근거: GoF Decorator 절 Intent — 이 패턴이 겨냥하는 것이 책임을 동적으로 덧붙이는 일이고, 확장 수단으로서 서브클래싱의 대안이라는 점입니다). 대상 클래스가 final 이거나 라이브러리가 감춰 둔 타입이면 아예 상속이 막혀 있기도 합니다.

쓰지 말아야 할 경우

비슷한 단서에서 다른 패턴을 고르게 되는 경우가 셋 있습니다. 감싼 뒤 제공하는 인터페이스가 달라지면 Adapter 를, 끼어드는 목적이 접근 통제면 Proxy 를, 바꿔야 하는 것이 겉이 아니라 안에서 실행되는 알고리즘이면 Strategy 를 먼저 검토하세요. 차이는 다음 절에서 풉니다. 그리고 아래 상황에서는 층을 쌓으면 얻는 것보다 잃는 것이 큽니다.

쓰지 말아야 할 상황쓰면 잃는 것
코드가 객체 동일성에 기대고 있음(참조 비교, 객체를 키로 쓰는 맵)장식한 객체로는 원본을 찾지 못합니다. 시나리오 3 의 5단계가 그 상태이고, 이 제약은 구현으로 우회할 수 없어요
Component 인터페이스에 연산이 많음데코레이터마다 전달 메서드를 전부 써야 하고, 하나를 빠뜨리면 그 연산만 장식을 건너뛰는 상태가 됩니다. 컴파일러가 추상 클래스로 잡아 주지 않는 언어에서는 조용히 지나가요
스택 가운데의 한 겹만 떼어 내야 함층은 바깥에서 안으로 한 방향으로만 엮여 있어 가운데를 빼려면 전체를 다시 조립해야 합니다(refactoring.guru — Decorator)
바꿔야 하는 것이 대상 안에서 실행되는 알고리즘겉을 감싸는 것으로는 대상이 내부에서 고르는 계산을 바꿀 수 없습니다. 그 자리는 Strategy 가 맡아요

패턴의 경계

디자인 패턴을 충족하는 최소 조건

어떤 코드를 Decorator 라고 불러도 되는지 가르는 기준입니다. [필수] 가 하나라도 빠지면 Decorator 가 아니고, [선택] 은 갖추면 좋거나 상황에 따라 고르는 구조예요. 조건은 언어와 상관없이 코드에서 확인할 수 있는 모양(타입 선언·참조 보유·호출 방향·생성 위치)으로 적었고, 조건마다 그것을 보여 준 시나리오의 단계를 가리킵니다.

  1. [필수] 감싼 결과가 Component 인터페이스를 빠짐없이 제공 — 데코레이터가 Component 를 구현해 그 연산을 하나도 빼지 않고, Client 는 장식 여부를 모른 채 Component 타입으로만 씁니다. 시나리오 1 의 1·8단계 (근거: GoF Decorator 절 Participants — Decorator 는 Component 의 인터페이스를 따르는 인터페이스를 정의한다 / Related Patterns — 데코레이터는 객체의 책임만 바꾸고 인터페이스는 바꾸지 않는다)
    • 빠지면: 제공하는 연산이 대상의 것과 달라지면 그것은 변환이고 Adapter 입니다. 특히 빼는 쪽을 조심하세요. 연산 하나를 감춰 버리면 그 대상 자리에 더 이상 들어갈 수 없어 겹쳐 쌓기가 그 자리에서 끝납니다.
    • 경계 사례: 연산을 더하는 것은 이 조건을 어기지 않습니다(조건 6번).
  2. [필수] Component 자체를 타입으로 하는 참조 하나 — 데코레이터가 Component 참조를 하나 가지고, 필드에 적힌 그 타입이 구체 클래스가 아니라 Component 라서 그 자리에 또 다른 데코레이터가 들어갑니다. 시나리오 2 의 2단계 (근거: GoF Decorator 절 Participants — Decorator 는 Component 객체에 대한 참조를 유지한다 / GoF Discussion of Structural Patterns — 객체의 전체 기능을 컴파일 시점에 정할 수 없는 상황을 다루므로 재귀 합성이 이 패턴의 전제다)
    • 코드에 나타나는 모양: 필드에 적힌 타입이 추상입니다. 시나리오 2 의 2단계가 조립 코드 한 줄만 고쳐 끝난 것도 이 덕분이에요.
    • 빠지면: 필드 타입이 SmsNotifier 면 다른 데코레이터를 그 자리에 넣을 수 없습니다. 세 언어 모두 컴파일이 막고, 층은 한 겹에서 끝나요. 시나리오 3 의 2단계가 이 조건을 어긴 자리예요.
  3. [필수] 받은 요청을 그 참조로 전달 — 데코레이터는 받은 요청을 참조로 넘기고 추가 책임은 전달의 앞이나 뒤에 붙이며, 어떤 호출도 대상에 전달되지 않고 끝나는 일이 없습니다. 시나리오 1 의 2~7단계 (근거: GoF Decorator 절 Collaborations — Decorator 는 요청을 자기가 참조하는 Component 객체에 전달하고, 전달 전후에 추가 연산을 선택적으로 수행한다)
    • 확인하는 법: 이 글의 예시는 감사 층을 거쳐 두 번, 감싸지 않고 한 번 보낸 요청 셋이 모두 발송기까지 전달돼 발송기의 발송 횟수가 3 입니다(직접 실행해 확인).
    • 빠지면: 조건을 보고 전달을 멈추는 층은 Chain of Responsibility 쪽입니다. 시나리오 3 의 4단계가 그 모양이고, 바깥 층이 이미 한 일과 안쪽에서 일어나지 않은 일이 어긋납니다.
    • 절대형으로 읽는 근거: 원전은 전달이 일어난다는 것까지 적고 「끊지 않는다」를 따로 명시하지는 않아요. 이 조건을 절대형으로 읽는 근거는 refactoring.guru — Decorator 가 데코레이터에게는 요청 흐름을 끊을 권한이 없다고 적은 자리에서 왔습니다.
  4. [필수] 감쌀 대상을 밖에서 받음 — 데코레이터가 대상을 자기 안에서 만들지 않고 생성자나 설정 메서드로 받아, 무엇을 어떤 순서로 감쌀지 정하는 곳이 데코레이터 바깥에 있습니다. 시나리오 2 의 2·3단계 (근거: GoF Decorator 절 Intent — 책임을 객체에 동적으로 덧붙인다 / Consequences — 정적 상속보다 유연해 실행 중에 책임을 붙였다 뗐다 할 수 있고 같은 속성을 두 번 붙일 수도 있다)
    • 빠지면: 데코레이터가 대상을 스스로 만들어 가지고 있으면 조합을 고르는 권한이 그 안으로 들어갑니다. 대상의 생성과 수명을 래퍼가 관리하는 것은 Proxy 쪽 성질이에요.
  5. [필수] 감싼 대상과 같은 객체가 아님, 그 동일성에 기대지 않는 Client — 장식된 객체는 감싼 대상과 같은 객체가 아니고, Client 코드가 그 동일성에 기대지 않습니다. 시나리오 3 의 5단계 (근거: GoF Decorator 절 Consequences — 데코레이터는 투명한 외피이지만 컴포넌트와 동일한 객체는 아니므로 객체 동일성에 의존해서는 안 된다)
    • 코드에 나타나는 모양: 참조 비교가 거짓이고, 대상을 키로 찾는 맵이나 == 검사에 장식된 객체가 끼어들지 않습니다.
    • 빠지면: 장식하기 전의 객체로 등록한 설정·잠금·구독을 장식한 객체가 찾지 못합니다. 타입은 맞고 컴파일도 통과하므로 실행 중에야 나타나요.
  6. [선택] Component 에 없는 공개 연산이나 상태를 더함 — ConcreteDecorator 가 Component 에 없는 공개 연산이나 상태를 더하되, Component 가 선언한 연산은 빼거나 바꾸지 않습니다. 시나리오 1 의 2단계 (근거: 이 가이드의 결정 — 아래 「추가 연산을 두어도 되는가」 참고)
    • 경계 사례: 조건 1번이 막는 것은 연산을 빼거나 바꾸는 일이지 더하는 일이 아니에요. 다만 Client 가 그 연산을 부르는 순간 조건 1번의 뒷부분(Client 가 Component 타입으로만 쓴다)이 성립하지 않습니다.
    • 이 글의 예: AuditNotifier 가 count() 를 갖는 것이 이 경우인데, 그것을 부르는 쪽은 Client 인 ShipmentDesk 가 아니라 층을 엮는 조립 코드예요. 감사 층으로 두 번 보낸 뒤 부르면 2 가 나오고(직접 실행해 확인), 시나리오 1 의 2단계에서 센 숫자를 밖에서 읽으려면 이 연산이 필요합니다.
  7. [선택] 전달만 하는 추상 Decorator 클래스 — 구체 데코레이터가 여럿이면 전달 코드를 한 곳에 모으는 클래스를 따로 두고, 책임이 하나뿐이면 두지 않아도 됩니다. 시나리오 1 의 6단계 (근거: GoF Decorator 절 Implementation — 책임을 하나만 붙이는 경우에는 추상 Decorator 클래스를 생략할 수 있다)
    • 이 글의 예: NotifierDecorator 가 이 클래스입니다. 구체 층 셋이 모두 send 를 덮어써서 여기 모인 것은 전달 코드보다 참조 필드와 생성자예요. 시나리오 1 의 6단계에서 영수증을 그대로 올려보낸 것은 서명 층 자신의 전달 줄입니다.
  8. [선택] 같은 종류의 데코레이터를 두 번 이상 겹침 — 참조 타입이 추상이라 데코레이터가 자기와 같은 종류도 받습니다. 시나리오 2 의 4단계 (근거: GoF Decorator 절 Consequences — 같은 속성을 두 번 덧붙이는 구성이 가능하다는 점을 정적 상속과 대비해 적고 있다)
  9. [선택] 런타임에 층을 붙였다 떼는 API(Application Programming Interface, 바깥에서 부르라고 열어 둔 연산 묶음) — 조립을 한 번만 하지 않고 운영 중에 바꿉니다. 시나리오 2 의 2단계
    • 경계 사례: 시나리오 2 의 2단계에서 조립 코드가 하는 일을 실행 중에 하는 것이고, 이 가이드의 예시 코드는 조립을 시작할 때 한 번만 해서 이 항목을 쓰지 않았습니다.

추가 연산을 두어도 되는가. 조건 6번은 판정이 달라질 수 있는 자리라 근거를 따로 적습니다. GoF 는 관련 패턴을 견주는 대목에서 데코레이터가 객체의 책임을 바꾸지 인터페이스를 바꾸지는 않는다고 적어요. 이 문장의 상대는 Adapter 입니다. Adapter 는 감싼 대상 자리에 다른 인터페이스를 갖다 놓아서 원래 Client 가 못 쓰게 되고, Decorator 는 그렇지 않다는 대비예요. 그러니까 이 문장이 금지하는 것은 인터페이스를 갈아 끼우는 일이지 그 위에 하나를 더하는 일이 아닙니다. 실제로 refactoring.guru 는 데코레이터를 거쳐 접근하는 인터페이스가 같거나 확장된다고 적고 있고요(refactoring.guru — Decorator).

그 문장이 금지하는 것과 금지하지 않는 것

  Component 를 다른 인터페이스로 갈아 끼운다   → 금지. 그건 Adapter 다
  Component 위에 연산을 하나 추가한다          → 금지 아님. 선언된 연산은 그대로 남는다

코드에서 차이가 나는 지점도 같은 쪽을 가리킵니다. 연산을 빼면 장식된 객체를 Component 자리에 넣지 못하므로 조건 1번이 곧바로 성립하지 않아요. 연산을 더하면 Component 가 선언한 것은 전부 그대로 있으므로 아무 자리에도 못 들어가는 일이 생기지 않습니다. 선언된 타입만 보면 더한 쪽은 여전히 Component 이고, 빼는 일은 애초에 타입 수준에서 불가능해요.

다만 비용이 없지는 않습니다. 추가 연산을 쓰려는 Client 는 그 데코레이터의 구체 타입을 알아야 하고, 그 순간 조건 2번이 주는 이득에서 빠져요. 알림 예가 그렇습니다. audited.count() 를 부르려면 AuditNotifier 타입 변수가 필요하고, 그래서 그 변수는 감사 층을 다시 무언가로 감싸는 순간 쓸모가 없어집니다. 바깥 층이 제공하는 것은 Notifier 뿐이니까요.

추가 연산이 있는 층을 다시 감싸면

  AuditNotifier audited = new AuditNotifier(sms);
  audited.count()                                  ← 부를 수 있다
  Notifier outer = new SignatureNotifier(audited);
  outer.count()                                    ← 없다. 바깥이 제공하는 인터페이스는 Notifier 뿐

그래서 이 가이드는 추가 연산을 허용하되 필수가 아닌 것으로 둡니다. 감사·계측처럼 바깥에서 읽어야 하는 값이 있으면 두되, 그 층은 스택의 맨 바깥에 놓거나 값을 따로 모으는 객체에 넘기는 편이 낫다는 것까지가 이 조건의 내용이에요.

정리하면 이 자리에서 잣대는 둘로 나뉩니다. 어떤 패턴인지는 선언된 타입으로 판정하고, 대상 자리에 그대로 넣을 수 있는지는 Client 가 무엇에 기대는가로 가릅니다. 앞엣것이 조건 1번의 앞부분이고 뒤엣것이 뒷부분이에요. 보호 프록시가 실행 중에 요청을 거부해도 물음 1 의 판정이 달라지지 않는 것도 같은 이유입니다 — 거부는 선언된 타입에서 연산을 빼지 않으니까요.

잣대 둘

  어떤 패턴인가          ← 선언된 타입으로 판정            (조건 1번 앞부분)
  그 자리에 넣어도 되나   ← Client 가 무엇에 기대는가       (조건 1번 뒷부분)

감쌌다는 사실은 셋 모두에 있다. 다른 것은 감싼 뒤에 제공하는 인터페이스와, 끼어드는 목적이다.

비슷한 패턴·안티패턴과의 차이

Decorator 와 구조가 닮았거나 같은 단서에서 떠오르는 대상 여섯을 비교합니다. Adapter·Proxy 는 Decorator 와 구조가 거의 같아 셋을 함께 가르는 기준을 먼저 세우고, 그다음 Composite·Strategy·Chain of Responsibility, 마지막으로 상속으로 기능을 더하는 방식을 봅니다.

Adapter 와의 차이

구분 기준은 감싼 결과가 제공하는 인터페이스가 감싼 대상의 것과 같은지입니다. 알림 예에서 SignatureNotifier 는 Notifier 를 감싸 Notifier 를 제공해요. 인터페이스가 그대로라서 발송 데스크는 자기가 받은 것이 층인지 감싸지 않은 발송기인지 몰랐고(시나리오 1 의 1단계), 같은 이유로 층 위에 층을 겹칠 수 있었습니다(시나리오 2 의 4단계). 만약 발송망 회사가 준 SDK 를 감싸 Notifier 를 제공하는 클래스를 쓴다면 그건 다릅니다. 감싼 것과 제공하는 것이 다른 인터페이스니까요.

Adapter  : 발송망 SDK  ──감쌈──▶  Notifier 를 제공한다    인터페이스가 바뀜   → 변환
Decorator: Notifier    ──감쌈──▶  Notifier 를 제공한다    인터페이스가 그대로 → 책임 추가

Decorator 를 고르면 감싼 것을 다시 감쌀 수 있는 재귀 합성을 얻고, 어휘가 맞지 않는 두 쪽을 잇는 일을 포기합니다. 데코레이터가 놓일 수 있는 자리는 애초에 인터페이스가 맞아떨어지는 곳뿐이에요. 두 일이 한 스택 안에 함께 있는 구성도 자연스럽습니다. 발송망 SDK 를 어댑터로 감싸 Notifier 로 만들어 두면, 그 위에 서명 층과 감사 층을 더할 수 있어요. 순서가 그 반대일 수는 없습니다. 어댑터가 감싸야 하는 것은 SDK 인데 데코레이터가 제공하는 것은 Notifier 니까요.

                 ↑ 여기에 Proxy 도 같은 층으로 들어갈 수 있다

Proxy 와의 차이

구분 기준은 인터페이스가 같으면서 끼어드는 목적이 책임 추가인지 접근 통제인지입니다. 접근 통제라는 말은 넓어 보이지만 코드에서 보이는 모양은 좁아요. 대상을 첫 호출까지 만들지 않거나(지연 생성), 권한을 확인해 어떤 호출은 넘기지 않거나(보호), 다른 주소 공간으로 보내거나(원격), 참조 수·잠금·쓸 때 복사를 관리합니다. 데코레이터에는 이 중 어느 것도 없어요. 데코레이터는 받은 요청을 전부 넘기고, 넘기는 길의 앞뒤에 일을 더할 뿐입니다(시나리오 1 의 2·4·7단계).

같은 인터페이스를 유지하는 두 래퍼

Proxy     : if (권한 없음) 거부       ← 어떤 호출은 대상에 전달되지 않는다
            if (아직 없음) 만들어 둠   ← 대상의 생성·수명을 래퍼가 관리한다
Decorator : before(); 대상 호출; after()   ← 모든 호출이 대상에 전달되고, 앞뒤에 일이 붙는다

코드에서 이 둘을 가르는 표식이 둘 더 있습니다. 하나는 대상이 어디서 오는가예요. 데코레이터는 감쌀 것을 밖에서 받고(최소 조건 4번), 프록시는 대상을 스스로 만들어 관리하는 경우가 많습니다. 다른 하나는 층의 개수입니다. 데코레이터는 겹쳐 쌓으려고 있으니 두 겹 세 겹이 예사이고, 프록시는 대상과의 한 관계에 집중해 보통 한 겹이에요.

경계 사례가 하나 있습니다. 보호 프록시가 일부 연산을 거부하면 실제로 쓸 수 있는 연산이 대상의 부분집합이 되어, 인터페이스가 같다는 판정이 맞지 않는 것처럼 보여요. 이때도 선언된 타입은 같습니다. 거부는 실행 중에 일어나지 시그니처에서 빠지는 것이 아니니까요(근거: GoF Proxy 절 Related Patterns). 그래서 물음 1 은 실행 결과가 아니라 선언된 타입으로 판정하고, 그런 래퍼는 물음 2 로 내려가 접근 통제를 이유로 Proxy 가 됩니다.

보호 프록시가 어떤 연산을 거부할 때

  선언된 타입   감싼 대상의 연산이 전부 그대로 있다   → 물음 1 은 "같다"
  실행 중      어떤 호출은 대상에 전달되지 않는다     → 물음 2 에서 Proxy

최소 조건 6번이 다룬 추가 연산이 물음 1 에서 걸리지 않는 것도 같은 규칙이에요. 선언된 타입에 Component 의 연산이 전부 있으면 같은 인터페이스입니다. Decorator 를 고르면 모든 호출이 대상에 전달된다는 보장을 얻고, 대상의 생성과 수명을 관리하는 일을 포기합니다.

Composite 와의 차이

구분 기준은 참조가 하나인지 여럿인지, 그리고 목적이 집계인지 책임 추가인지입니다. 두 패턴 모두 같은 인터페이스를 구현한 객체를 필드로 가지고 요청을 넘기므로 클래스 모양이 닮았어요. 자식이 하나뿐인 컴포지트를 상상하면 구조는 거의 같아집니다(근거: GoF Decorator 절 Related Patterns — 데코레이터를 자식 하나짜리 컴포지트로 볼 수 있으나 목적이 다르다). 다른 점은 왜 그 참조를 드느냐예요. 컴포지트는 여러 개를 하나처럼 다루려고 자식을 모으고, 데코레이터는 한 대상 위에 일을 더하려고 하나만 가집니다. 시나리오 2 의 4단계에서 서명 층을 두 번 겹친 것도 자식이 둘이 된 것이 아니라 층이 두 겹이 된 것이에요. Decorator 를 고르면 한 대상에 책임을 겹겹이 쌓는 구성을 얻고, 여러 대상을 하나로 묶어 다루는 집계를 포기합니다.

Strategy 와의 차이

구분 기준은 바꾸는 것이 대상의 겉인지, 대상 안에서 실행되는 계산인지입니다(근거: GoF Decorator 절 Implementation — 데코레이터는 객체의 겉을 바꾸고 스트래티지는 속을 바꾼다). 코드에서는 화살표 방향으로 보입니다. 데코레이터는 대상을 밖에서 감싸고, 스트래티지는 대상이 안에서 가지고 있어요.

Decorator : Client ──▶ [ 층 ] ──▶ [ 대상 ]        층이 대상을 감싼다. 대상은 층을 모른다
Strategy  : Client ──▶ [ 대상 ( 전략 ) ]          대상이 전략을 가지고 있다. 대상이 부른다

알림 예로 옮겨 봅시다. 서명 문구를 나라별로 다르게 만들고 싶다면 그건 SignatureNotifier 안에서 고르는 계산이니 스트래티지 자리예요. 반면 서명을 붙일지 말지 자체를 켜고 끄는 것은 층을 넣느냐 빼느냐의 문제라 데코레이터입니다. Decorator 를 고르면 대상 코드를 건드리지 않고 밖에서 기능을 더하는 것을 얻고, 대상 안의 알고리즘을 갈아 끼우는 일을 포기합니다. 데코레이터는 대상이 내부에서 무엇을 계산하는지 볼 수 없으니까요.

Chain of Responsibility 와의 차이

구분 기준은 층이 전달을 멈출 수 있는가입니다. 구조는 거의 같아요. 같은 인터페이스를 구현한 객체들이 다음을 하나씩 가지고 한 줄로 이어져 있으니까요. 다른 점은 권한입니다. 책임 연쇄의 핸들러는 자기가 처리할 수 있으면 거기서 끝내는 것이 정상 동작이고, 데코레이터는 그 권한이 없어요(refactoring.guru — Decorator 의 관계 설명이 데코레이터가 요청 흐름을 끊지 않는다는 점으로 둘을 가릅니다). 시나리오 3 의 4단계가 그 선을 넘은 코드였고, 넘은 결과 바깥 감사 층의 기록이 실제 발송과 어긋났습니다. Decorator 를 고르면 요청이 반드시 끝까지 전달된다는 보장을 얻고, 어느 층에서 처리를 끝내는 흐름을 포기합니다.

// 데코레이터로 보이지만 전달을 멈춘다 — 이 층은 Chain of Responsibility 쪽이다
final class BlockingNotifier extends NotifierDecorator {
    BlockingNotifier(Notifier inner) {
        super(inner);
    }

    @Override
    public String send(String body) {
        if (body.matches(".*\\d{4}.*")) {
            return "blocked";          // inner.send 가 불리지 않는다
        }
        return inner.send(body);
    }
}

상속으로 기능 더하기와의 차이

구분 기준은 기능이 클래스 정의에 붙는지, 실행 중의 객체에 붙는지입니다. 시나리오 3 의 1단계가 상속 쪽이었어요. 그 코드는 지금 돌아가고, 층이 없어 스택도 얕습니다. 대신 조합이 늘 때마다 클래스가 늘고, 무엇보다 런타임에 뗄 수 없어요. 이 차이가 쓸모 있는 것은 실행 중에 조합이 달라지는 경우뿐입니다. 모든 알림에 늘 같은 셋이 붙는다면 상속이나 한 클래스가 더 간단해요. Decorator 를 고르면 조합과 순서를 런타임에 고르는 것과 같은 책임을 두 번 붙이는 자유를 얻고, 층이 없는 단순함을 포기합니다. 객체 수가 늘고, 오류를 쫓을 때 스택 트레이스가 층의 수만큼 깊어져요.

이름이 같아 헷갈리는 것이 하나 더 있습니다. TypeScript 나 Python 의 @ 문법도 decorator 라고 부르는데, 그쪽은 클래스나 멤버의 정의에 붙는 언어 기능이에요(TypeScript 5.0 릴리스 노트). 이 글이 다루는 것은 실행 중의 객체를 다른 객체로 감싸는 설계 구조라, 같은 낱말을 쓸 뿐 다른 물건입니다. 둘의 차이가 나타나는 자리는 시나리오 2 의 3단계예요. 언어 문법으로는 같은 클래스의 인스턴스마다 다른 순서로 기능을 더할 수 없습니다.

import java.util.ArrayList;
import java.util.List;

/** Component — 알림을 내보내는 연산 모양. 돌려주는 값은 발송 영수증이다. */
interface Notifier {
    String send(String body);
}

/** ConcreteComponent — 실제로 내보내는 쪽. 외부 발송망 대신 메모리 안 보관함을 쓴다. */
final class SmsNotifier implements Notifier {
    private final List<String> outbox = new ArrayList<>();

    @Override
    public String send(String body) {
        outbox.add(body);
        return "sent[" + body + "]";
    }

    int delivered() {
        return outbox.size();
    }
}

/** Decorator — Component 참조를 들고 받은 요청을 그대로 전달한다. */
abstract class NotifierDecorator implements Notifier {
    protected final Notifier inner;

    protected NotifierDecorator(Notifier inner) {
        this.inner = inner;
    }

    @Override
    public String send(String body) {
        return inner.send(body);
    }
}

/** ConcreteDecorator — 전달하기 전에 서명을 덧붙인다. */
final class SignatureNotifier extends NotifierDecorator {
    static final String SIGNATURE = " -- Bbangto Store CS 010-1234-5678";

    SignatureNotifier(Notifier inner) {
        super(inner);
    }

    @Override
    public String send(String body) {
        return inner.send(body + SIGNATURE);
    }
}

/** ConcreteDecorator — 전달하기 전에 네 자리 이상 이어진 숫자를 가린다. */
final class MaskingNotifier extends NotifierDecorator {
    MaskingNotifier(Notifier inner) {
        super(inner);
    }

    @Override
    public String send(String body) {
        return inner.send(mask(body));
    }

    private static String mask(String text) {
        StringBuilder out = new StringBuilder();
        int i = 0;
        while (i < text.length()) {
            if (!Character.isDigit(text.charAt(i))) {
                out.append(text.charAt(i));
                i++;
                continue;
            }
            int j = i;
            while (j < text.length() && Character.isDigit(text.charAt(j))) {
                j++;
            }
            String run = text.substring(i, j);
            out.append(run.length() >= 4 ? "*".repeat(run.length()) : run);
            i = j;
        }
        return out.toString();
    }
}

        return calls;

use std::cell::Cell;

/// Component — 알림을 내보내는 연산 모양. 돌려주는 값은 발송 영수증이다.
trait Notifier {
    fn send(&self, body: &str) -> String;
}

/// ConcreteComponent — 실제로 내보내는 쪽. 외부 발송망 대신 메모리 안 보관함을 쓴다.
struct SmsNotifier {
    outbox: Cell<usize>,
}

impl SmsNotifier {
    fn new() -> Self {
        Self { outbox: Cell::new(0) }
    }

    fn delivered(&self) -> usize {
        self.outbox.get()
    }
}

impl Notifier for SmsNotifier {
    fn send(&self, body: &str) -> String {
        self.outbox.set(self.outbox.get() + 1);
        format!("sent[{body}]")
    }
}

const SIGNATURE: &str = " -- Bbangto Store CS 010-1234-5678";

/// ConcreteDecorator — 전달하기 전에 서명을 덧붙인다.
/// Rust 에는 추상 클래스가 없어 전달 기본 구현을 물려줄 자리가 없다. 각 데코레이터가 직접 전달한다.
struct SignatureNotifier<'a> {
    inner: &'a dyn Notifier,
}

impl<'a> SignatureNotifier<'a> {
    fn new(inner: &'a dyn Notifier) -> Self {
        Self { inner }
    }
}

impl Notifier for SignatureNotifier<'_> {
    fn send(&self, body: &str) -> String {
        self.inner.send(&format!("{body}{SIGNATURE}"))
    }
}

/// ConcreteDecorator — 전달하기 전에 네 자리 이상 이어진 숫자를 가린다.
struct MaskingNotifier<'a> {
    inner: &'a dyn Notifier,
}

impl<'a> MaskingNotifier<'a> {
    fn new(inner: &'a dyn Notifier) -> Self {
        Self { inner }
    }

    fn mask(text: &str) -> String {
        let chars: Vec<char> = text.chars().collect();
        let mut out = String::new();
        let mut i = 0;
        while i < chars.len() {
            if !chars[i].is_ascii_digit() {
                out.push(chars[i]);
                i += 1;
                continue;
            }
            let mut j = i;
            while j < chars.len() && chars[j].is_ascii_digit() {
                j += 1;
            }
            if j - i >= 4 {
                out.push_str(&"*".repeat(j - i));
            } else {
                out.extend(&chars[i..j]);
            }
            i = j;
        }
        out
    }
}

impl Notifier for MaskingNotifier<'_> {
    fn send(&self, body: &str) -> String {
        self.inner.send(&MaskingNotifier::mask(body))
    }
}

/// ConcreteDecorator — 전달한 뒤 영수증에 감사 번호를 붙이고, 받은 횟수를 센다.
struct AuditNotifier<'a> {
    inner: &'a dyn Notifier,
    calls: Cell<u32>,
}

impl<'a> AuditNotifier<'a> {
    fn new(inner: &'a dyn Notifier) -> Self {
        Self { inner, calls: Cell::new(0) }
    }

    /// Component 에 없는 추가 연산 — 이것을 부르는 쪽은 AuditNotifier 라는 구체 타입을 알아야 한다.
    fn count(&self) -> u32 {
        self.calls.get()
    }
}

impl Notifier for AuditNotifier<'_> {
    fn send(&self, body: &str) -> String {
        self.calls.set(self.calls.get() + 1);
        format!("{}+audit#{}", self.inner.send(body), self.calls.get())
    }
}

/// Client — Notifier 만 알고, 몇 겹이 감겨 있는지 모른다.
struct ShipmentDesk<'a> {
    notifier: &'a dyn Notifier,
}

impl<'a> ShipmentDesk<'a> {
    fn new(notifier: &'a dyn Notifier) -> Self {
        Self { notifier }
    }

    fn ship(&self, sku: &str) -> String {
        self.notifier.send(&format!("order {sku} shipped today"))
    }
}

가장 중요한 줄은 Java 95행 · TypeScript 84행 · Rust 111행입니다. 한 줄 안에 전달과 후 연산이 함께 들어 있어서, 이 줄을 읽으면 데코레이터가 무엇을 하는 물건인지가 그대로 보여요. inner.send(body) 를 부르고 그 결과에 +audit#n 을 잇습니다. 이 줄이 맡는 것이 최소 조건 3번이에요. 이 줄에서 inner.send(body) 를 빼고 고정 문자열을 돌려주면 어떻게 될까요. 세 언어 모두 컴파일이 통과합니다. 직접 고쳐 실행해 보니 javac 21.0.11 과 tsc 5.9.3 은 종료 코드 0 에 메시지가 한 줄도 없었고, rustc 1.95.0 은 쓰이지 않게 된 인자와 필드를 경고 두 건으로 알릴 뿐 오류는 0 건이었어요. 그러고도 프로그램은 돌아가고, 출력 2·3번 줄이 발송되지 않은 값으로 바뀌며 4번 줄은 audit count 2, sms deliveries 1 이 됩니다. 감사 층은 두 번 셌는데 발송기에는 감싸지 않고 보낸 한 건만 남은 거예요. 어긴 것은 최소 조건 3번 하나인데 그것을 말해 주는 도구가 없는 셈이고, 시나리오 3 의 4단계가 말한 고장이 바로 이 모양이에요.

언어 차이는 셋만 짚습니다. Java 와 TypeScript 는 추상 클래스 NotifierDecorator 가 참조 필드와 전달 기본 구현을 물려주는데(이 예시는 연산이 send 하나라 구체 층 셋이 모두 그것을 덮어써 직접 전달합니다), Rust 에는 클래스 상속이 없어 세 층이 참조 필드부터 각자 두고 impl Notifier 안에서 직접 전달합니다. 최소 조건 7번이 말한 「추상 Decorator 클래스를 생략한 구성」이에요. TypeScript 는 타입을 이름이 아니라 멤버 모양으로 견주기 때문에, 참조 필드에 구체 클래스를 적었을 때 컴파일러가 막아 주는지가 대상 클래스의 멤버에 따라 달라집니다(시나리오 3 의 3단계). Rust 는 소유권 때문에 층이 대상을 참조로 가지고 수명 표기를 달며, 참조 뒤에서 횟수를 세려고 Cell(std::cell::Cell — 공유 참조를 통해서도 값을 바꿀 수 있게 해 주는 표준 라이브러리 타입)을 씁니다.

FilterInputStream 계열은 이 패턴의 역할 넷이 클래스 계층으로 그대로 나타난 드문 경우예요. 감싼 스트림을 필드로 가지고 모든 연산을 그리로 넘기는 클래스가 하나 있고, 버퍼링이나 자료형 읽기 같은 책임은 그것을 상속한 클래스들이 맡습니다. 층이 겹친다는 것도 실제로 확인할 수 있어요. 바이트 배열을 버퍼 층으로 감싸고 그 위에 자료형 읽기 층을 더한 다음 정수를 읽어 보면 이렇게 나옵니다.

byte[] raw = {0, 0, 0, 7, 65, 66};
DataInputStream stacked = new DataInputStream(new BufferedInputStream(new ByteArrayInputStream(raw)));

stacked instanceof InputStream   →  true    두 겹을 감싸고도 타입은 InputStream 그대로
stacked.readInt()                →  7       요청이 두 층을 지나 맨 안쪽 배열까지 전달됐다

Collections 의 래퍼들은 판정이 나뉘는 자리라 물음 셋을 실제로 적용해 볼 만합니다. synchronizedList 는 모든 연산을 대상에 그대로 넘기면서 잠금이라는 책임을 더하니 물음 1 도 물음 2 도 Decorator 쪽이에요. 반면 unmodifiableList 는 같은 판정을 받지 않습니다. 직접 실행해 보면 이렇습니다.

List<String> backing = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(backing);

view 의 선언 타입      →  List                          물음 1 은 "같다" — 연산이 빠진 것이 아니다
view.add("c")          →  UnsupportedOperationException  물음 2 — 어떤 호출은 대상에 전달되지 않는다
backing.add("c") 뒤    →  view = [a, b, c]               대상을 복사하지 않고 그대로 들여다본다

선언된 타입만 보면 List 그대로라 물음 1 에서는 구분되지 않아요. 구분되는 곳은 물음 2 입니다. 이 래퍼가 하는 일은 책임을 더하는 것이 아니라 쓰기 연산을 막는 것이고, 그건 접근 통제니까요. 그래서 이 가이드는 unmodifiableList 를 보호 프록시로 읽습니다. refactoring.guru 는 synchronizedXXX 와 unmodifiableXXX 를 함께 Decorator 사례로 드는데(refactoring.guru — Decorator in Java), 물음 2 를 적용하면 둘은 구분돼요. 최소 조건 3번이 요구하는 "모든 호출이 대상에 전달된다"가 unmodifiableList 에서는 성립하지 않습니다.

Rust 쪽에서도 이름을 조심해야 합니다. 표준 라이브러리 문서가 "iterator adapters" 라고 부르는 map·filter·take 는 Iterator 를 받아 Iterator 를 돌려줍니다. 인터페이스가 그대로이고 전달하면서 일을 더하니, 물음 1 과 물음 2 로 판정하면 Adapter 가 아니라 Decorator 쪽이에요. 표준 라이브러리가 쓰는 adapter 라는 낱말과 GoF 의 Adapter 는 같은 말이 아닙니다. BufReader 도 같은 모양이고, 이쪽은 문서가 스스로 "버퍼링을 더한다"고 적어 헷갈릴 여지가 적어요.

스스로 점검하기

  1. 아래 TimestampNotifier 는 Decorator 인가요? 최소 조건 1~5번을 차례로 적용해 판정하고, 빠진 조건이 있으면 그 조건이 요구하는 것이 코드의 어디에 없는지 적어 보세요.

    final class TimestampNotifier implements Notifier {
    private final SmsNotifier inner = new SmsNotifier();

    @Override
    public String send(String body) {
        return inner.send("[09:00] " + body);
    }
}
    풀이 보기

    풀이 — Decorator 가 아닙니다. 빠진 조건은 2번과 4번이에요. TimestampNotifier 는 Notifier 를 구현해 send 를 그대로 제공하니 1번을 만족하고, 받은 요청을 inner.send 로 빠짐없이 넘기며 그 앞에 시각을 붙이니 3번도 만족합니다. 동일성에 기대는 코드도 없으니 5번도 걸리지 않아요. 그런데 참조 필드의 타입이 Notifier 가 아니라 구체 클래스 SmsNotifier 라서 그 자리에 다른 층을 넣을 수 없고(2번 — 시나리오 3 의 2단계와 같은 모양), 감쌀 대상을 생성자로 받지 않고 필드 초기화에서 new SmsNotifier() 로 스스로 만들어 무엇을 감쌀지 고를 길이 바깥에 없습니다(4번). 필드를 private final Notifier inner; 로 바꾸고 생성자 TimestampNotifier(Notifier inner) 로 받게 하면 두 조건이 함께 채워져요.

  2. 아래 두 클래스는 각각 Adapter · Decorator · Proxy 중 무엇인가요? 비교 절의 물음 1 과 물음 2 를 순서대로 적용해 답하고, 물음 1 만으로 구분되는지 물음 2 까지 내려가야 하는지도 밝혀 주세요. 이어서 LazyNotifier 의 send 가 inner 를 만들기만 하고 부르지는 않도록 바뀌면 판정이 어떻게 달라지는지도 적어 보세요.

    final class RetryingNotifier extends NotifierDecorator {
    RetryingNotifier(Notifier inner) {
        super(inner);
    }

    @Override
    public String send(String body) {
        try {
            return inner.send(body);
        } catch (RuntimeException e) {
            return inner.send(body);
        }
    }
}

final class LazyNotifier implements Notifier {
    private final Supplier<Notifier> factory;
    private Notifier inner;

    LazyNotifier(Supplier<Notifier> factory) {
        this.factory = factory;
    }

    @Override
    public String send(String body) {
        if (inner == null) {
            inner = factory.get();
        }
        return inner.send(body);
    }
}
    풀이 보기

    풀이 — RetryingNotifier 는 Decorator, LazyNotifier 는 Proxy 이고, 둘 다 물음 2 까지 내려가야 구분됩니다. 두 클래스 모두 Notifier 를 감싸 Notifier 를 제공하니 물음 1 에서는 "같다" 쪽이에요(비교 절의 물음 셋). 물음 2 에서 갈립니다. RetryingNotifier 는 받은 요청을 늘 inner.send 로 넘기고 실패하면 한 번 더 넘기는 책임을 더하니 Decorator 이고, 감쌀 대상도 생성자로 받아요(최소 조건 4번). LazyNotifier 는 대상을 첫 호출까지 만들지 않고 스스로 만들어 관리하니, 「Proxy 와의 차이」가 든 지연 생성이라는 접근 통제예요. send 가 inner 를 만들기만 하고 부르지 않게 바뀌면 어떤 호출도 대상에 전달되지 않습니다. 선언된 타입은 그대로라 물음 1 의 답은 바뀌지 않아요. 달라지는 것은 물음 2 입니다. 「Proxy 와의 차이」가 든 접근 통제(지연 생성 · 보호 · 원격 · 참조 관리)는 모두 대상에 가는 호출을 언제 어떻게 넘길지 정하는 일이고, 보호 프록시도 넘기지 않는 것은 「어떤 호출」이지 전부가 아니에요. 넘기는 호출이 하나도 없으면 통제할 접근이 남지 않아 Proxy 로 읽을 근거가 없고, 최소 조건 3번으로 보면 Decorator 도 아닙니다. 남는 것은 Notifier 를 구현했지만 대상을 쓰지 않는 별개의 구현체예요. 무엇을 돌려주든 발송기에는 아무것도 도착하지 않으므로, 바깥에 감사 층 같은 층이 있으면 시나리오 3 의 4단계처럼 바깥의 기록과 실제 발송이 어긋납니다.

  3. 구현 절의 코드에서 AuditNotifier.send 가 횟수를 세는 일을 전달 뒤로 옮긴다고 해 봅시다. 안쪽에서 영수증을 먼저 받고, 그다음 횟수를 올려 번호를 붙이는 순서예요(시나리오 1 의 2단계를 7단계 자리로). 실행 출력 2·3·4번 줄 가운데 무엇이 달라지고 무엇은 그대로인가요? 그리고 안쪽 층이 예외를 던지는 경우를 더하면 어느 줄이 어떻게 어긋나는지 단계로 적어 보세요.

    풀이 보기

    풀이 — 정상 경로에서는 2·3·4번 줄이 모두 그대로입니다. Java 만 그렇게 고쳐 실행해 보니 여덟 줄이 기대 출력과 글자까지 같았어요(직접 실행해 확인). 영수증을 받자마자 횟수를 올리고 그 값을 붙이니, 붙는 번호와 count() 가 원래와 같습니다. 어긋남은 안쪽이 예외를 던질 때 생겨요. 세 요청 가운데 둘째에서 안쪽이 예외를 던지는 발송기로 실행해 보면 이렇습니다(직접 실행해 확인).

    1. 첫 요청은 안쪽이 영수증을 돌려주고 횟수가 1 이 되어 +audit#1 이 붙습니다. 원래 코드와 같아요.
    2. 둘째 요청에서 안쪽이 예외를 던집니다. 원래 코드는 전달 앞에서 이미 횟수를 2 로 올렸지만, 바뀐 코드는 횟수를 올리기 전에 예외가 빠져나가 1 에 머물러요.
    3. 셋째 요청은 성공하고, 원래 코드는 +audit#3, 바뀐 코드는 +audit#2 를 붙입니다. 마지막 count() 도 원래는 3, 바뀐 코드는 2 예요.
    4. 바뀐 코드의 감사 기록에서는 실패한 요청 하나가 빠졌습니다. 시나리오 1 의 2단계가 횟수를 전달 앞에 둔 이유 — 세는 대상이 「요청이 들어왔다」는 사실이라 실패한 요청도 잡혀야 한다 — 를 어긴 결과예요.
