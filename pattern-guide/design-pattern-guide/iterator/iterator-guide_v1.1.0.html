한눈에 보는 개요

물류 창고의 컨베이어가 상자를 스캔하고, 그 기록을 최근 다섯 건만 보관하는 기록함에 넣는다고 해 봅시다. 기록함 안쪽은 칸이 다섯 개인 배열이고, 여섯 번째 기록이 들어오면 첫 칸을 덮어씁니다. SCN-01 부터 SCN-07 까지 일곱 건을 넣으면 배열은 SCN-06 · SCN-07 · SCN-03 · SCN-04 · SCN-05 순서로 채워져 있어요. 그런데 보고서를 찍는 쪽이 기록함에게 배열을 달라고 해서 for (int i = 0; i < raw.length; i++) 로 순회하면, 찍히는 순서가 배열에 놓인 순서 그대로입니다. 실제로 실행해 보면 SCN-06 SCN-07 SCN-03 SCN-04 SCN-05 가 나와요. 오래된 것부터 보고 싶었는데 중간부터 시작한 셈이죠.

Iterator 의 해법은 「지금 어디까지 봤는가」를 가지고 있는 객체를 따로 두고, 그 객체를 집합이 만들어 주는 것입니다. 보고서 쪽은 배열도 칸 번호도 모른 채 「다음 것 주세요」만 되풀이하고, 칸 번호를 순환시키는 계산은 그 객체 안에 한 번만 적혀요. 순서를 바꾸고 싶으면 다른 객체를 받아 가면 됩니다.

Before : 부르는 쪽이 기록함의 배열을 받아 칸 번호로 순회한다

  기록함.slots()  ──▶  [SCN-06][SCN-07][SCN-03][SCN-04][SCN-05]
                        i=0     i=1     i=2     i=3     i=4
  보고서   for i in 0..4   →  SCN-06 SCN-07 SCN-03 SCN-04 SCN-05   (틀린 순서)
  알람     같은 다섯 줄을 복사해서 한 번 더
  정산     같은 다섯 줄을 복사해서 한 번 더

After : 기록함이 「어디까지 봤는지」를 가진 순회자를 만들어 준다

  보고서 ──▶ 기록함.oldestFirst() ──▶ 순회자(step=0) ─┐
                                                     │ step 번째 칸이 어디인지는
  보고서 ──▶ 순회자.hasNext() / next() ───────────────┘ 순회자만 계산한다
             →  SCN-03 SCN-04 SCN-05 SCN-06 SCN-07   (들어온 순서)

  기록함.newestFirst() ──▶ 다른 순회자 ──▶ SCN-07 SCN-06 SCN-05 SCN-04 SCN-03
             기록함의 저장 코드는 한 줄도 안 바뀐다

이 패턴의 분류는 행위 패턴이고 다른 이름은 Cursor 예요. 함께 쓰는 패턴은 Composite · Factory Method · Memento 입니다.

이 글은 시나리오 셋을 따라갑니다. 기록 다섯 건이 들어온 순서대로 나오는 길, 최신 우선 순회가 더해지고 두 순회가 동시에 진행될 때, 순회 위치를 기록함 안으로 들였을 때 어디서 어긋나는가. 끝까지 읽으면 어떤 코드를 Iterator 라고 불러도 되는지 필수 조건 셋으로 판정할 수 있고, Composite 나 색인 루프와도 구분할 수 있게 됩니다.

시나리오 1 — 스캔 기록 일곱 건 중 남은 다섯 건이 들어온 순서대로 나오는 길

기록함 RingScanLog 는 칸이 다섯인 배열을 가지고 있고, 오늘 SCN-01 부터 SCN-07 까지 일곱 건이 들어왔습니다. 여섯 번째부터는 앞 칸을 덮어썼으니 남아 있는 것은 SCN-03(7건) · SCN-04(21건) · SCN-05(9건) · SCN-06(15건) · SCN-07(4건) 다섯이고, 배열에는 SCN-06 · SCN-07 · SCN-03 · SCN-04 · SCN-05 순으로 놓여 있어요. 보고서가 받아야 할 것은 들어온 순서대로 줄지은 SCN-03 SCN-04 SCN-05 SCN-06 SCN-07 한 줄입니다. 이 장면에는 넷이 등장해요. 기록을 담아 둔 기록함 RingScanLog(패턴에서는 ConcreteAggregate 라고 부르는 역할), 어디까지 봤는지를 가지고 있는 OldestFirst(ConcreteIterator), 순회자들이 공통으로 따르는 연산 모양 hasNext()·next() 를 선언한 ScanCursor(Iterator), 그리고 기록함에 순회자를 청해 한 줄을 만드는 보고서 코드(Client)입니다. 이름은 여기서 한 번씩만 소개하고 정식 정의는 개념 정리에서 해요.

  1. 보고서가 RingScanLog 에게 oldestFirst() 로 순회자를 청합니다. 보고서가 순회자를 직접 만들지 않고 기록함에게 청하는 이유는, 어느 순회자가 이 기록함의 저장 구조에 맞는지는 기록함만 알기 때문이에요. 보고서가 만들려면 칸이 배열인지 연결된 마디인지를 알아야 하고, 그 순간 개요의 Before 로 돌아갑니다.
  2. RingScanLog 가 자기 구조에 맞는 OldestFirst 를 만들어 돌려줍니다. 새로 만든 순회자의 step 은 0 이에요. 이 단계가 새 객체를 만드는 단계인 이유는 순회가 시작될 때마다 위치가 0 부터여야 해서예요. 기록함이 순회자 하나를 만들어 두고 다시 쓰면 두 번째 보고서가 끝난 자리에서 시작합니다.
  3. 보고서가 받은 것을 ScanCursor 타입으로 가지고 있습니다. OldestFirst 라는 이름으로 받지 않는 이유는, 그 이름을 받는 순간 기록함이 다른 순회자를 돌려주도록 바뀌면 보고서도 함께 바뀌기 때문이에요. 4단계에서 부를 연산은 ScanCursor 가 선언한 둘뿐입니다.
  4. 보고서가 hasNext() 로 더 남았는지 묻습니다. 남았다는 답을 먼저 받고 next() 를 부르는 이유는, 끝을 아는 쪽이 순회자이기 때문이에요. 보고서가 기록함에게 크기를 물어 자기 셈으로 다섯 번 반복하면 칸 수가 여덟로 늘 때 보고서도 고쳐야 합니다.
  5. next() 를 받은 OldestFirst 가 자기 step 번째 칸이 배열의 어디인지를 기록함에게 묻습니다. 시작 칸이 2 번이라 step 0 은 배열의 2 번 칸이에요. 이 셈을 순회자가 하고 보고서가 하지 않는 이유는, 칸 번호가 순환하는 규칙이 기록함의 저장 방식이지 보고서의 일이 아니어서입니다.
  6. 기록함이 그 칸의 SCN-03 을 돌려주고, OldestFirst 가 step 을 1 로 올린 뒤 보고서에 SCN-03 을 건넵니다. 올리는 일을 next() 안에서 하는 이유는 「값을 주는 일」과 「한 칸 나아가는 일」이 한 번의 요청으로 묶여야 해서예요. 보고서가 따로 advance() 를 불러 주게 하면 그것을 잊은 호출부에서 같은 값이 다섯 번 나옵니다.
  7. 보고서가 4~6단계를 되풀이해 SCN-04·SCN-05·SCN-06·SCN-07 을 차례로 받고, step 이 5 가 되면 hasNext() 가 false 를 돌려줍니다. 끝났다는 신호가 순회자에게서 오기 때문에 보고서에는 다섯이라는 수가 한 번도 적히지 않아요. 기록함의 칸 수를 여덟로 바꿔도 보고서는 그대로입니다.

0 번 칸입니다. 시작 칸 2 에 3 을 더하면 5 이고, 칸이 다섯이니 5 를 다섯으로 나눈 나머지 0 이에요. 그래서 SCN-06 이 나옵니다. 이 「더하고 나머지를 취하는」 두 줄이 순회자 안에 한 번만 있으면, 보고서·알람·정산 세 곳이 같은 계산을 복사해 갖지 않아도 돼요.

이 시나리오가 보여 준 것은 역할 넷과 그 사이의 호출 방향입니다. 순회자를 만드는 일(1·2단계)은 집합이, 어디까지 봤는지를 유지하고 전진시키는 일(5·6단계)과 끝을 알리는 일(7단계)은 순회자가, 원소를 받아 쓰는 일(3·4단계)은 Client 가 맡아요. Client 가 아는 이름은 집합과 ScanCursor 둘뿐이고, 배열이라는 낱말은 한 번도 나오지 않습니다.

같은 뼈대에서 다르게 짤 수 있는 자리가 하나 있어요. 이 글의 순회자는 위치만 가지고, 그 위치가 배열의 몇 번 칸인지는 5단계처럼 기록함 쪽 조회 연산에 묻습니다. 순회자가 배열을 직접 가지고 칸 번호까지 계산하는 모양도 같은 패턴이에요. 어느 쪽이든 「어디까지 봤는가」는 순회자에 있으니까요.

  2. RingScanLog 에 newestFirst() 한 줄이 늘어납니다. 늘어난 것은 그 한 줄뿐이고, 기록을 넣는 add·칸 수 계산·칸 번호를 순환시키는 at 은 한 글자도 바뀌지 않아요. 새 순회 방식이 저장 방식을 건드리지 않는 이유는, 순회자가 기록함에게 묻는 것이 언제나 「몇 번째 칸」 하나이기 때문입니다.
  3. OldestFirst 도 바뀌지 않습니다. 두 순회자는 서로를 모르고 각자 자기 step 만 가지고 있어서, 하나를 더하거나 지울 때 다른 쪽 코드를 열 일이 없어요. 순서를 정하는 규칙이 순회자마다 따로 있기 때문에 생기는 성질입니다.
  4. 점검 화면이 oldestFirst() 와 newestFirst() 를 각각 불러 순회자 둘을 받습니다. 둘은 서로 다른 객체이고 step 도 따로예요. 이 자리가 짝 맞추기가 성립하는 이유입니다. 위치가 기록함 하나에 있었다면 한쪽이 전진시킨 값을 다른 쪽이 이어받아, 다섯 쌍이 아니라 세 쌍이 나옵니다. 시나리오 3 에서 그 수를 직접 세어 봅니다.
  5. 점검 화면이 두 순회자에게 번갈아 next() 를 불러 다섯 쌍을 만듭니다. 가운데 쌍이 SCN-05/SCN-05 인 것은 다섯 칸의 한가운데에서 두 순회자가 만나기 때문이에요. 두 순회가 같은 기록함을 읽기만 하고 아무것도 쓰지 않아서, 읽는 순서를 바꿔도 결과가 같습니다. 순회 도중에 누가 기록함에 쓰면 사정이 달라져요. 보고서가 들어온 순서로 순회하면서 원소를 하나 받을 때마다 같은 기록 SCN-08 을 넣으면, 받은 다섯 건이 SCN-03 SCN-05 SCN-07 SCN-08 SCN-08 로 값을 건너뛰고도 아무 오류 없이 끝납니다(Java 로 직접 실행해 확인). 넣을 때마다 시작 칸이 한 칸씩 옮겨 가서, step 이 한 칸 나아갈 때 읽는 칸은 두 칸씩 나아가 한 칸을 건너뛰기 때문이에요.

이 시나리오가 보여 준 것은 변화의 범위와 겹친 순회입니다. 새 순회 방식이 들어올 때 바뀌는 곳은 새 순회자 클래스 하나와 그것을 내주는 한 줄이고, 저장 코드와 기존 순회자는 그대로예요(1~3단계). 그리고 순회자마다 자기 위치를 갖기 때문에 한 집합에서 순회 둘을 동시에 진행할 수 있습니다(4·5단계). 이 두 가지가 순회 위치를 집합 밖으로 꺼내서 얻는 것이에요.

시나리오 3 — 순회 위치를 기록함 안으로 들이면 어디서 어긋나는가

같은 창고의 다른 코드베이스는 기록함을 조금 다르게 짰습니다. RingScanLog 에 cursor 필드를 두고 hasNext()·next() 를 기록함 자신이 제공해요. 순회자 클래스가 없으니 코드가 짧아 보이고, 한 번 순회할 때는 시나리오 1 과 똑같은 다섯 줄이 나옵니다. 여기에 시나리오 2 의 요구(두 번 순회하기·짝 맞추기)가 들어오고, 별도로 보고서 코드가 기록함에게 배열을 달라고 하기 시작해요. 아래 결과는 Java 21 로 실제로 컴파일해 실행한 것입니다.

  1. 보고서가 while (log.hasNext()) log.next() 로 한 번 순회합니다. 결과는 SCN-03 SCN-04 SCN-05 SCN-06 SCN-07 이고 시나리오 1 과 같아요. 이렇게 짜는 이유는 대개 편의입니다. 클래스를 하나 덜 만들어도 되니까요. 그 대가로 「어디까지 봤는가」가 기록함이라는 한 곳에만 있게 됩니다.
  2. 같은 기록함에 알람 화면이 한 번 더 순회합니다. 이번에는 아무것도 나오지 않아요. 실행하면 (none) 입니다. cursor 가 이미 5 에 가 있어서 hasNext() 가 처음부터 false 이기 때문이에요. 되돌리려면 reset() 같은 연산을 두고 두 화면이 순서를 지켜 불러야 하는데, 그 순서를 아는 코드가 화면마다 생깁니다.
  3. 점검 화면이 짝 맞추기를 시도합니다. reset() 으로 cursor 를 0 으로 되돌린 뒤 같은 기록함을 왼쪽·오른쪽으로 넘겨 번갈아 next() 를 부르면 다섯 쌍이 아니라 SCN-03/SCN-04 SCN-05/SCN-06 SCN-07/SCN-03 세 쌍이 나와요. 한쪽이 전진시킨 cursor 를 다른 쪽이 이어받기 때문입니다. 마지막 쌍의 SCN-03 은 cursor 가 5 가 된 뒤 칸 번호가 순환해 다시 읽힌 값이라, 있지도 않은 기록이 짝으로 찍힌 것이에요.
  4. 갈래를 하나 더 봅니다. 보고서 코드가 기록함에게 slots() 로 배열을 받아 for (int i = 0; i < raw.length; i++) 로 순회합니다. 찍히는 줄은 SCN-06 SCN-07 SCN-03 SCN-04 SCN-05 예요. 시작 칸이 2 라는 사실이 기록함 안에만 있는데 보고서는 0 부터 세었기 때문입니다. 개요의 Before 그림이 이 자리예요.

개념 정리

패턴의 참여자 넷과 Client 를 정식으로 정의합니다. Client 는 참여자 밖에서 순회자를 청해 쓰는 쪽인데, 시나리오와 구현에 늘 나오므로 함께 정의해요. 넷 가운데 Aggregate 는 시나리오에 이름이 나오지 않았는데, 기록함 RingScanLog 가 구현하는 추상 타입이라 여기서 처음 소개합니다.

  • Iterator — 원소에 접근하고 순회를 진행시키는 연산을 선언합니다. Client 는 이 선언만 보고 부르고(시나리오 1 의 3·4단계), ConcreteIterator 가 이 선언을 구현해요. 기록함 예에서는 hasNext() 와 next() 를 선언한 ScanCursor 가 Iterator 입니다. 「다음 것이 있는가」와 「다음 것을 달라」를 한 연산으로 합쳐 「없음」을 뜻하는 값을 돌려주는 모양도 같은 역할이에요.
  • ConcreteIterator — Iterator 가 선언한 연산을 실제 순회로 구현하고, 순회의 현재 위치를 자기 필드에 둡니다. 한 집합 위에 이 객체를 여럿 두면 순회 여럿이 동시에 진행될 수 있어요(시나리오 2 의 4·5단계). 기록함 예에서는 step 을 가진 OldestFirst·NewestFirst·FromHead 가 각각 ConcreteIterator 입니다.
  • Aggregate — 원소를 담고 있는 집합의 추상 타입이고, 자기 순회자를 내주는 연산을 선언합니다(시나리오 1 의 1단계). 이 타입으로 참조하는 코드는 안쪽이 배열인지 연결된 마디인지 몰라도 순회를 시작할 수 있어요. 기록함 예에서는 oldestFirst() 를 선언한 ScanArchive 가 Aggregate 입니다.
  • ConcreteAggregate — Aggregate 를 구현해 원소를 실제로 담아 두고, 자기 저장 구조에 맞는 ConcreteIterator 를 만들어 돌려줍니다(시나리오 1 의 2단계). 기록함 예에서는 다섯 칸 배열을 순환해 쓰는 RingScanLog 와 마디를 이어 붙이는 ChainScanLog 가 각각 ConcreteAggregate 예요. 같은 ScanArchive 를 구현하므로 Client 코드는 둘을 구분하지 않습니다.
  • Client — Aggregate 에게 순회자를 청해(시나리오 1 의 1단계) Iterator 타입으로 참조하며 원소를 받아 씁니다(3·4단계). 기록함 예에서는 한 줄을 만드는 walk·pair 함수와 진입점이 Client 예요. Client 가 집합 안쪽을 다루는 코드를 한 줄도 갖지 않는 것이 이 패턴이 겨냥하는 상태입니다.

그림에서 position 이 적힌 칸이 ConcreteIterator 쪽이라는 점을 봐 두세요. 같은 이름이 ConcreteAggregate 칸으로 옮겨 적히면 그 그림은 시나리오 3 의 모양이고, 최소 조건 1번에서 빠집니다. ConcreteAggregate 에서 나가는 점선은 순회자를 만드는 자리이고, ConcreteIterator 에서 ConcreteAggregate 로 들어가는 실선은 시나리오 1 의 5단계에서 칸을 물어본 그 선이에요.

집합은 순회자를 만들어 주고, 순회자는 어디까지 봤는지를 가진다.

사용 목적

Iterator 가 필요할 때는 코드나 요구에서 보이는 단서가 있습니다. 셋을 차례로 봅시다.

단서 1 — 같은 순회 코드가 호출부마다 복제돼 있습니다

기록함의 시작 칸을 구하고 칸 수로 나머지를 취하는 다섯 줄이 보고서·알람·정산 세 파일에 그대로 복사돼 있으면 신호예요. 칸 수를 5 에서 8 로 바꾸는 변경 하나에 세 파일이 함께 수정 목록에 오릅니다. 시나리오 1 의 5단계가 그 다섯 줄을 한 곳으로 모은 자리였어요.

단서 2 — 집합이 자기 저장 구조를 그대로 내주는 조회 연산을 갖고 있습니다

slots()·getItems()·getNodes() 처럼 안쪽 배열이나 마디를 돌려주고, 부르는 쪽이 그 위에서 직접 루프를 실행하는 모양이에요. 시나리오 3 의 4·5단계에서 본 대로 순서가 틀리거나 밖에서 내용을 고칠 수 있게 됩니다. 코드에서는 돌려주는 타입이 집합의 필드 타입과 똑같은 조회 연산으로 보여요.

단서 3 — 같은 집합을 두 가지 순서로 순회해야 하고, 두 순회가 동시에 진행됩니다

알람은 최신부터, 보고서는 오래된 것부터 보고, 점검 화면은 둘을 짝지어 봅니다. 순회 상태가 집합 안에 하나뿐이면 시나리오 3 의 2·3단계처럼 두 번째 순회가 원소 없이 끝나거나 답이 틀려요. 요구 문서에서는 「같은 목록을 정렬 방향만 바꿔 보여 준다」, 「앞뒤를 맞대어 비교한다」 같은 말로 나타납니다.

쓰지 말아야 할 경우

비슷한 단서에서 다른 것을 골라야 하는 경우가 둘 있습니다. 집합이 트리이고 순회 순서가 늘 한 가지라면 노드 자신이 재귀로 순회하는 Composite 쪽이 간단하고, 원소 타입마다 할 일이 달라진다면 순회만으로는 모자라 Visitor 가 필요해요. 둘과의 차이는 다음 절에서 풉니다. 그리고 아래 상황에서는 Iterator 를 쓰면 얻는 것보다 잃는 것이 큽니다.

어떤 코드를 Iterator 라고 불러도 되는지 가르는 기준입니다. [필수] 가 하나라도 빠지면 Iterator 가 아니고, [선택] 은 갖추면 좋은 구조예요. 조건은 언어와 상관없이 코드에서 확인할 수 있는 모양(타입 선언·참조 보유·호출 방향·생성 위치)으로 적었고, 조건마다 그것을 보여 준 시나리오의 단계를 가리킵니다. 근거 괄호의 GoF 는 Gang of Four 의 줄임말로, 1994년에 나온 Design Patterns 의 저자 네 명을 함께 부르는 이름이에요.

판정 단위를 먼저 정해 둘게요. 판정 대상은 「원소를 담고 있는 집합 타입 하나와 그 집합을 차례로 읽는 순회자 타입」의 짝입니다. 타입 하나만 떼어 놓고는 답이 나오지 않아요. 원전의 조건 문장들이 Iterator·ConcreteIterator·Aggregate·ConcreteAggregate 넷을 각각 주어로 삼고 있어서, 어느 타입이 어느 주어 자리인지 정해야 조건을 댈 수 있기 때문입니다.

    • 코드에 나타나는 모양: 시나리오 1 의 2단계에서 그 필드가 0 으로 생기고 6단계에서 1 로 오르는 자리예요.
    • 빠지면: 시나리오 3 의 1~3단계입니다. cursor 를 기록함 필드로 두면 한 번은 제대로 동작하지만 두 번째 순회가 (none) 으로 끝나고, 같은 기록함을 두 자리에 넘겨 짝을 맞추면 다섯 쌍이 아니라 세 쌍이 나옵니다. 마지막 쌍 SCN-07/SCN-03 은 cursor 가 5 를 넘긴 뒤 칸 번호가 순환해 다시 읽힌 값이에요. 직접 컴파일해 실행한 결과입니다.
    • 근거가 받쳐 주는 범위: 위 괄호가 대는 것은 위치를 누가 가지고 누가 전진시키는가까지입니다. 그 위치를 색인으로 둘지 마디 참조로 둘지, 필드 이름을 무엇으로 할지는 원전이 정하지 않았어요.
  2. [필수] 원소를 얻는 코드는 집합의 저장 구조를 직접 다루지 않음 — 원소는 순회자가 선언한 연산으로만 들어오고, 부르는 쪽은 그 반환값으로 집합에 담긴 원소에 접근합니다. 시나리오 1 의 3·4단계 (근거: GoF 원서 Iterator 절 Intent — 집합 객체의 내부 표현을 드러내지 않으면서 그 원소들에 차례로 접근하는 방법을 준다 · Applicability — 집합 객체의 내부 표현을 노출하지 않고 그 내용에 접근하려 할 때)
    • 코드에 나타나는 모양: 부르는 쪽 코드에 배열 색인 계산, 마디의 다음 연결 필드 따라가기, 집합의 내부 컬렉션을 그대로 받아 순회하는 자리가 없습니다. 시나리오 1 의 3·4단계가 그 통로이고, 시나리오 3 의 4·5단계가 그 통로를 건너뛴 모양이에요.
    • 빠지면: 시나리오 3 의 4단계입니다. slots() 로 배열을 받아 0 번 칸부터 순회하면 SCN-06 SCN-07 SCN-03 SCN-04 SCN-05 가 찍혀 순서가 틀리고, 5단계처럼 받은 배열의 0 번 칸에 값을 쓰면 기록함 안의 기록도 함께 바뀝니다. 둘 다 직접 컴파일해 실행해 확인했어요.
    • 근거가 받쳐 주는 범위: 위 괄호가 대는 것은 부르는 쪽이 집합의 내부 표현에 접근하지 않는다와 부르는 쪽이 그 반환값으로 접근하는 것이 그 집합의 원소다까지입니다. 뒤쪽은 원전이 「집합 객체의 원소들에 차례로 접근하는 방법」이라고 적었으니 접근하는 대상이 원소라는 뜻이 근거 안에 들어 있어요. 어떤 연산 이름을 쓸지, 원소를 값으로 줄지 참조로 줄지는 원전이 정하지 않았습니다.
    • 경계 사례: 반환값의 겉모양은 조건이 아닙니다. 원소를 그대로 돌려주든, 「없음」까지 함께 담는 값으로 감싸 돌려주든 그 값으로 원소에 접근하면 이 조건을 만족해요. 빠지는 것은 원소에 아예 접근하지 못하는 경우입니다. 원소가 아니라 계산 결과만 돌려주면 그 자리예요. 투표지 묶음을 순회하는 커서가 표 하나가 아니라 여태까지의 찬성 누계를 돌려준다면, 위치도 순회자에 있고 순회 연산도 순회자에 선언돼 있지만 부르는 쪽은 끝내 원소에 접근하지 못해요. 그런 코드는 순회자가 아니라 집계기입니다.
  3. [필수] 순회 연산은 순회자 타입에 선언되고 집합 타입에 겹치지 않음 — 원소를 읽고 순회를 진행시키는 연산을 순회자 노릇을 하는 타입이 선언하고, 집합 타입 쪽에는 「다음 원소를 달라」에 해당하는 연산이 겹쳐 있지 않습니다. 시나리오 1 의 3·4단계 (근거: GoF 원서 Iterator 절 Participants — Iterator 는 원소에 접근하고 순회하는 인터페이스를 정의한다 · Consequences — 순회자가 순회 인터페이스를 맡으므로 집합에 같은 인터페이스를 둘 필요가 없어져 집합의 인터페이스가 단순해진다)
    • 코드에 나타나는 모양: 시나리오 1 의 3·4단계에서 Client 가 부른 이름이 전부 ScanCursor 에 선언돼 있는 것이 이 모양이에요.
    • 빠지면: 시나리오 3 의 1단계입니다. hasNext()·next() 가 기록함에 붙으면 순회자 타입 자체가 없어져, 순회 방식을 하나 더하려면 기록함을 열어야 하고 2·3단계의 겹친 순회도 성립하지 않아요. 순회자 객체가 아예 없이 집합의 노드가 재귀로 순회하는 형태도 이 조건에서 빠지는데, 그 자리는 비교 절에서 Composite 로 가릅니다.
    • 근거가 받쳐 주는 범위: 위 괄호가 대는 것은 순회 인터페이스가 순회자 쪽에 있고 집합에 겹쳐 있지 않다까지입니다. 연산을 몇 개로 나눌지는 다음 조건에서 따로 다룹니다.
  4. [선택] 집합이 자기 순회자를 내주는 연산을 가짐 — 순회자를 얻는 자리가 집합의 연산이고, 구체 집합이 자기 저장 구조에 맞는 구체 순회자를 만들어 돌려줍니다. 시나리오 1 의 1·2단계 (근거: GoF 원서 Iterator 절 Participants — Aggregate 는 Iterator 객체를 만드는 인터페이스를 정의하고 ConcreteAggregate 는 그 생성 인터페이스를 구현해 알맞은 ConcreteIterator 를 돌려준다. 다만 원전은 이 연산이 필요 없게 구현한 사용 사례도 함께 적어 두었고, 다형적 순회가 필요할 때만 쓰라고 권하는 구현 선택지로 다루므로 선택에 둡니다)
    • 빠지면: Client 가 new OldestFirst(ring) 처럼 순회자를 직접 조립하는 모양이 됩니다. 1~3번은 그대로 만족하니 Iterator 이기는 한데, 어느 순회자가 어느 집합에 맞는지를 Client 가 알아야 해서 집합의 구체 클래스가 바뀔 때 Client 도 함께 바뀌어요. 집합 쪽 생성 연산 선언(ScanCursor oldestFirst();)을 지우고 컴파일하면 javac 이 3건을 냅니다 — 그 연산으로 순회자를 얻는 상위 로직 한 곳과 두 구체 집합의 재정의 두 곳이에요(직접 컴파일해 확인).
    • 겹치는 자리: 이 연산은 Factory Method 이기도 합니다. 비교 절의 「Factory Method 와 겹치는 자리」에서 따로 다뤄요.
  5. [선택] 끝을 순회자가 알림 — 더 남았는지 묻는 연산이 따로 있거나 다음 원소를 주는 연산이 「없음」을 뜻하는 값으로 끝을 알리고, 부르는 쪽이 집합에 크기를 물어 자기 셈으로 끝을 판단하지 않습니다. 시나리오 1 의 7단계 (근거: GoF 원서 Iterator 절 Implementation — 최소 인터페이스를 첫 원소로 가기·다음으로 가기·끝났는지 묻기·현재 원소 얻기 넷으로 들면서 이들을 하나로 합치는 변형도 함께 적은 구현 선택지라 선택에 둡니다)
    • 코드에 나타나는 모양: 시나리오 1 의 7단계에서 보고서에 다섯이라는 수가 한 번도 적히지 않은 것이 이 모양입니다.
  6. [선택] 저장 구조가 서로 다른 집합들을 같은 순회 인터페이스로 순회 — 순회자 타입이 하나이고, 그것을 구현한 순회자들이 서로 다른 집합에 붙습니다. 시나리오 2 의 2단계 (근거: GoF 원서 Iterator 절 Applicability — 서로 다른 집합 구조를 균일한 인터페이스로 순회하게 하려 할 때. 셋 가운데 하나라서 선택에 둡니다)
    • 코드에 나타나는 모양: 시나리오 2 의 2단계 뒤 문단이 기록함을 배열에서 연결된 마디로 바꿔도 순회자를 내주는 한 줄의 모양이 같다고 한 자리예요. 다섯 칸 배열 RingScanLog 와 마디를 이어 붙이는 ChainScanLog 가 같은 ScanCursor 를 구현한 순회자를 내주는 것이 이 모양입니다.
  7. [선택] 한 집합에 순회 방식이 둘 이상 붙음 — 같은 집합을 차례로 읽는 순회자 클래스가 둘 이상 있고, 어느 것을 쓸지는 순회자 인스턴스를 바꾸는 것으로 정해집니다. 시나리오 2 의 1~3단계 (근거: GoF 원서 Iterator 절 Consequences — 순회자 인스턴스를 바꾸는 것만으로 순회 방식을 갈아 끼울 수 있고 순회자의 하위 타입으로 새 순회를 더할 수 있다. 하나만 있어도 패턴이 성립하므로 선택에 둡니다)
  8. [선택] 순회 중에 집합이 바뀌는 일을 막거나 감지 — 순회가 진행되는 동안 집합에 원소를 더하거나 빼는 코드가 컴파일 단계에서 막히거나, 실행 중에 감지돼 예외로 알려집니다. 시나리오 2 의 5단계 (근거: 이 가이드의 정책 — 원전이 견고한 순회자를 구현 선택지로 다루고 복사 비용을 이유로 늘 권하지는 않기 때문입니다)
    • 경계 사례: 시나리오 2 의 5단계 끝에서 본 Java 판은 순회 도중에 기록함에 쓰는 코드가 컴파일도 실행도 통과하고 값을 건너뛰니 이 조건이 빠진 상태예요. 같은 편집을 Rust 판에 하면 컴파일할 때 E0502 로 막히니 이 조건이 채워진 상태입니다(둘 다 직접 실행해 확인).

필수 셋을 앞에 둔 데는 순서가 있습니다. 1번은 위치가 어디 있는지만, 2번은 부르는 쪽 코드만, 3번은 타입 선언만 보면 되어서 앞에서 걸리면 뒤는 읽지 않아도 돼요. 실제로 가장 흔하게 걸리는 것은 1번입니다.

조건 셋을 글자대로 만족해도 판정 대상이 아닌 코드가 있습니다. 아래는 난수를 끝없이 만들어 내는 코드예요.

final class SampleStream {
    private final long seed;

    SampleStream(long seed) {
        this.seed = seed;
    }

    SampleCursor cursor() {                  // 4번처럼 보이는 생성 연산
        return new SampleCursor(seed);
    }
}

final class SampleCursor {
    private long state;                      // 1번처럼 보이는 위치 필드

    SampleCursor(long seed) {
        this.state = seed;
    }

    boolean hasNext() {                      // 3번처럼 보이는 순회 인터페이스
        return true;
    }

    long next() {
        state = state * 6364136223846793005L + 1442695040888963407L;
        return state >>> 33;
    }
}

state 는 SampleCursor 에 있고(1번), 부르는 쪽은 저장 구조를 만지지 않으며(2번의 앞 절반), 순회 연산은 SampleCursor 에 선언돼 있고(3번), SampleStream.cursor() 가 그것을 내줍니다(4번). 그런데 SampleStream 안에는 순회할 원소가 하나도 없어요. 값은 호출할 때 계산돼 나옵니다. 조건들의 주어인 「집합」과 「그 집합의 원소」가 이 코드에는 없으니, 조건을 댈 자리 자체가 없는 것이지 조건을 만족한 것이 아닙니다. 판정 단위를 「원소를 담고 있는 집합과 그 순회자의 짝」으로 정해 둔 이유가 이것이에요.

같은 이유로 이 글은 Rust 의 Read::bytes() 를 사례로 싣지 않습니다. Read 는 원소를 담아 둔 집합이 아니라 바이트를 차례로 전달하는 통로이고, 그 연산이 무엇을 하는 자리인지는 Adapter 편이 이미 판정했어요. 표준 라이브러리가 「iterator adapters」라고 부르는 map·filter·take 도 이 글의 사례가 아닙니다. 그 이름의 자리는 Decorator 편이 다룹니다.

비슷한 패턴·안티패턴과의 차이

Iterator 와 구조가 닮았거나 같은 단서에서 떠오르는 대상 셋을 비교하고, 마지막에 차이가 아니라 겹침인 자리를 하나 따로 다룹니다. 먼저 같은 트리 위에서 순회를 나눠 갖는 Composite, 그다음 이 패턴으로 오해받는 색인 루프, 그리고 함께 쓰이면서 자주 혼동되는 Visitor 예요.

비교 대상구분 기준 (코드에서 보는 것)Iterator 를 고르면 얻는 것포기하는 것
Composite순회 순서를 누가 정하는가 — 집합의 노드 자신인가, 노드 밖의 순회자 객체인가순회 순서를 밖에서 고름. 순회자 클래스를 갈아 끼우면 노드는 그대로(시나리오 2 의 1~3단계)노드가 재귀로 순회하는 단순함. 순회자가 집합의 안쪽에 접근할 길이 따로 있어야 하고 타입이 둘 늘어남

Visitor원소들이 공통 타입 하나로 다뤄지는가, 원소의 구체 타입마다 할 일이 달라지는가원소를 차례로 건네는 일만 맡고 무엇을 할지는 부르는 쪽에 둠원소 타입마다 다른 연산을 골라 주는 일. 그 갈래가 필요하면 Visitor 를 따로 둠

Composite 와의 차이

구분 기준은 순회 순서를 누가 정하는지입니다. Composite 편은 이 기준을 자기 쪽에서 적었어요. 거기서는 묶음 노드가 자식 목록을 순회하는 순서가 곧 순회 순서이고, 그래서 깊이 우선 말고 너비 우선으로 바꾸려면 노드 클래스를 고쳐야 한다고 합니다. 이 글은 같은 기준을 반대 방향에서 봅니다. Iterator 는 그 순서를 정하는 책임을 집합 밖의 순회자 객체로 뺍니다. 그래서 시나리오 2 의 1~3단계처럼 순회자 클래스 하나와 그것을 내주는 한 줄만 늘고 저장 코드는 그대로예요. 코드에서 보는 자리는 「순회 순서를 정하는 코드가 어느 클래스에 있는가」 한 곳입니다.

// Composite 쪽 — 순서를 정하는 코드가 노드 안에 있다
final class GiftBox implements Component {
    private final List<Component> children = new ArrayList<>();

    public long weightInGrams() {
        long sum = packagingGrams;
        for (Component child : children) {   // 이 줄의 순서가 곧 순회 순서
            sum += child.weightInGrams();
        }
        return sum;
    }
}

// Iterator 쪽 — 순서를 정하는 코드가 순회자 안에 있다
final class NewestFirst implements ScanCursor {
    private int step = 0;

    public ScanRecord next() {
        return log.at(log.size() - 1 - step++);   // 이 줄만 바꾸면 순서가 바뀐다
    }
}

두 쪽은 배타적이지 않아요. 같은 트리에 깊이 우선 순회자와 너비 우선 순회자를 나란히 두고 부르는 쪽이 고르게 할 수 있고, 그때 노드 클래스는 하나도 안 바뀝니다. 노드가 차례를 정하고 밖의 순회자는 위치만 가지는 중간 모양도 있는데, 그 자리는 두 패턴이 포개진 것이지 어느 한쪽에 속하는 것이 아닙니다. 다만 Iterator 를 고르면 치르는 것이 있어요. 순회자가 집합의 안쪽에 접근해야 하므로 집합이 그 길을 따로 열어 줘야 하고, 타입이 순회자 인터페이스와 구현 둘만큼 늘어납니다. RingScanLog 가 순회자에게 열어 둔 조회 연산 size()·at()(시나리오 1 의 5단계에서 칸을 물은 자리)이 그 길이에요. 트리를 늘 한 가지 순서로만 순회한다면 노드가 재귀로 순회하는 쪽이 짧습니다.

색인 for 루프와의 차이

구분 기준은 부르는 쪽 코드에 집합의 저장 구조를 다루는 자리가 있는지입니다. 시나리오 3 의 4단계가 그 코드였어요. 여기서 헷갈리기 쉬운 포인트는 for 문을 썼는지 여부로 가르려는 것입니다. 기준은 문법이 아니라 부르는 쪽이 무엇을 아는가예요.

// 둘 다 for 문이지만 아는 것이 다르다
for (int i = 0; i < raw.length; i++) {       // 배열이라는 것과 0 부터 센다는 것을 안다
    System.out.println(raw[i].id());
}

ScanCursor cursor = ring.oldestFirst();      // 배열인지 마디인지 모른다
while (cursor.hasNext()) {
    System.out.println(cursor.next().id());
}

위 루프는 기록함의 칸이 배열이라는 것, 0 번부터 세면 된다는 것, 길이가 곧 개수라는 것 셋을 알고 있습니다. 그래서 셋 중 하나만 바뀌어도 이 루프가 함께 바뀌어요. 아래 루프가 아는 것은 ScanCursor 의 연산 둘뿐입니다. Iterator 를 고르면 저장 구조를 바꿔도 부르는 쪽이 그대로이고, 순회 코드가 순회자 한 곳에만 있어요. 대신 칸 번호로 곧장 하던 접근이 원소마다 호출 둘로 바뀝니다. 개수가 적고 구조가 바뀔 일이 없는 배열이라면 위 루프가 더 짧고 빠릅니다.

Visitor 와의 차이

구분 기준은 원소들이 공통 타입 하나로 다뤄지는지, 원소의 구체 타입마다 할 일이 달라지는지입니다. 이 물음은 둘 중 하나를 고르라는 것이 아니라 Iterator 만으로 끝나는 일인지를 가려요. 기록함 예에서는 원소가 전부 ScanRecord 하나라서 순회자가 차례로 건네주면 끝입니다. 만약 기록함에 스캔 기록·온도 기록·오류 기록이 공통 부모 없이 섞여 있고 종류마다 다른 계산이 필요하다면, 순회자가 원소를 건네준 뒤에도 부르는 쪽에 타입을 가르는 분기가 남아요. 그 분기를 원소 쪽으로 넘겨 각 타입이 자기에게 맞는 연산을 부르게 하는 것이 Visitor 이고, 그때도 트리를 순회하는 일은 여전히 순회자가 맡습니다. 둘은 자주 함께 쓰여요.

Factory Method 와 겹치는 자리

이것은 차이가 아닙니다. 최소 조건 4번의 「집합이 자기 순회자를 내주는 연산」은, 그 연산의 반환 타입이 추상 순회자이고 재정의할 수 있는 인스턴스 연산이라면 동시에 Factory Method 이기도 합니다. Factory Method 편이 Iterable.iterator() 와 IntoIterator::into_iter() 를 그 패턴의 최소 조건 다섯에 하나씩 대어 보고 팩토리 메서드로 판정해 두었어요. 그 판정은 원전이 순회자를 만드는 연산을 팩토리 메서드의 예로 직접 든 데서 옵니다(근거: GoF 원서 Iterator 절 Motivation — 순회자를 만드는 연산을 팩토리 메서드의 한 예로 든다). 이 글의 ScanArchive.oldestFirst() 도 같은 자리예요. 반환 타입이 인터페이스 ScanCursor 이고, 구현마다 다른 순회자를 돌려주며, ScanArchive 의 totalCount() 는 순회자를 오직 그 연산으로만 얻습니다. 두 패턴의 조건표는 서로 다른 것을 묻습니다. Iterator 는 순회 위치가 어디 있는가를 보고, Factory Method 는 그 순회자를 만드는 연산이 재정의될 수 있는가를 봐요. 그래서 한 코드가 둘 다일 수 있고, Iterable.iterator() 가 바로 그런 코드입니다.

겹친다고 같은 패턴은 아니다. 두 조건표가 서로 다른 자리를 본다.

두 판정 경로로 맞춰 보기

경로 둘로 같은 답이 나오는지 맞춰 봅시다. 경로 A 는 최소 조건의 [필수] 1~3번만으로, 경로 B 는 이 절의 구분 기준만으로 판정한 것입니다. 경로 B 의 물음은 둘입니다(겹침 판정은 이 두 물음의 소관 밖이라 Factory Method 는 경로 B 칸에 적지 않았어요) — 물음 1 「순회 순서를 집합의 노드 자신이 정하는가, 밖의 순회자 객체가 정하는가」, 물음 2 「부르는 쪽이 집합의 저장 구조를 다루는가」. 물음 1 의 「순회 순서」는 원소가 나오는 차례를 뜻하고, 칸 주소를 구하는 셈은 저장 방식이라 여기에 세지 않습니다. 시나리오 1 의 5단계에서 칸 번호를 순환시키는 계산을 기록함에 맡기고도 순서는 순회자가 정한다고 한 것이 그 구분이에요. Visitor 를 가르는 물음은 이 패턴인지가 아니라 이 패턴만으로 끝나는지를 묻는 것이라 판정에 넣지 않았습니다.

Iterable.iterator() 와 IntoIterator::into_iter() 두 줄은 이 표에서 또 다른 이유로 중요합니다. 두 경로 모두 Iterator 라고 답하고, 같은 코드가 Factory Method 의 조건 다섯도 만족해요. 두 패턴이 배타적이었다면 이 두 줄에서 두 경로의 답이 달라졌을 텐데 달라지지 않습니다. 겹치는 것이 맞기 때문이에요.

interface ScanArchive {
    ScanCursor oldestFirst();

    default long totalCount() {
        long sum = 0;
        ScanCursor cursor = oldestFirst();
        while (cursor.hasNext()) {
            sum += cursor.next().count();
        }
        return sum;

final class RingScanLog implements ScanArchive {
    private final ScanRecord[] slots;
    private int written = 0;

    RingScanLog(int capacity) {
        this.slots = new ScanRecord[capacity];
    }

    void add(ScanRecord record) {
        slots[written % slots.length] = record;
        written++;
    }

    private int size() {
        return Math.min(written, slots.length);
    }

    private ScanRecord at(int logical) {
        int start = written <= slots.length ? 0 : written % slots.length;
        return slots[(start + logical) % slots.length];
    }

    @Override
    public ScanCursor oldestFirst() {
        return new OldestFirst();
    }

    ScanCursor newestFirst() {
        return new NewestFirst();
    }

        private int step = 0;

        @Override

            return at(step++);

final class ChainScanLog implements ScanArchive {

class RingScanLog extends ScanArchive {
  private readonly slots: (ScanRecord | undefined)[];
  private written = 0;

  constructor(capacity: number) {
    super();
    this.slots = new Array<ScanRecord | undefined>(capacity).fill(undefined);
  }

  add(record: ScanRecord): void {
    this.slots[this.written % this.slots.length] = record;
    this.written += 1;
  }

  size(): number {
    return Math.min(this.written, this.slots.length);
  }

  at(logical: number): ScanRecord {
    const start = this.written <= this.slots.length ? 0 : this.written % this.slots.length;
    const record = this.slots[(start + logical) % this.slots.length];
    if (record === undefined) {
      throw new Error("empty slot");
    }
    return record;
  }

  oldestFirst(): ScanCursor {
    return new OldestFirst(this);
  }

  newestFirst(): ScanCursor {
    return new NewestFirst(this);
  }

    const node = new ChainNode(record);
    if (this.head === undefined) {
      this.head = node;
      return;

    let last = this.head;
    while (last.next !== undefined) {
      last = last.next;
    }

    return this.head;

    this.at = log.firstNode();

    if (this.at === undefined) {
      throw new Error("no node");

    this.at = this.at.next;

struct ScanRecord {
    id: &'static str,
    count: u64,
}

trait ScanCursor {
    fn has_next(&self) -> bool;
    fn next(&mut self) -> ScanRecord;
}

trait ScanArchive {
    fn oldest_first(&self) -> Box<dyn ScanCursor + '_>;

    fn total_count(&self) -> u64 {
        let mut sum = 0;
        let mut cursor = self.oldest_first();
        while cursor.has_next() {
            sum += cursor.next().count;
        }
        sum
    }
}

struct RingScanLog {
    slots: Vec<Option<ScanRecord>>,
    written: usize,
}

impl RingScanLog {
    fn new(capacity: usize) -> Self {
        RingScanLog { slots: vec![None; capacity], written: 0 }
    }

    fn add(&mut self, record: ScanRecord) {
        let at = self.written % self.slots.len();
        self.slots[at] = Some(record);
        self.written += 1;
    }

    fn size(&self) -> usize {
        self.written.min(self.slots.len())
    }

    fn at(&self, logical: usize) -> ScanRecord {
        let start = if self.written <= self.slots.len() {
            0
        } else {
            self.written % self.slots.len()
        };
        self.slots[(start + logical) % self.slots.len()].expect("empty slot")
    }

    fn newest_first(&self) -> Box<dyn ScanCursor + '_> {
        Box::new(NewestFirst { log: self, step: 0 })
    }
}

impl ScanArchive for RingScanLog {
    fn oldest_first(&self) -> Box<dyn ScanCursor + '_> {
        Box::new(OldestFirst { log: self, step: 0 })
    }
}

언어 차이는 셋만 짚습니다. 순회 인터페이스는 Java · TypeScript 가 interface, Rust 가 trait 으로 선언하고, 집합 쪽 기본 구현은 Java 가 default 메서드, Rust 가 trait 의 기본 메서드로 두는데 TypeScript 는 interface 에 본문을 둘 수 없어 abstract class 를 썼어요. TypeScript 는 구조적 타이핑이라 implements 표기를 떼도 컴파일과 출력이 그대로이고(직접 컴파일해 확인), 모양은 위 표의 셋째 줄처럼 선언된 반환 타입이 검사합니다(TypeScript Handbook — Type Compatibility). Rust 는 순회자를 Box<dyn ScanCursor + '_> 로 돌려주어 순회자가 집합을 빌린 채 살아 있으므로 순회 중 변경이 컴파일 단계에서 막히고, 두 순회자가 같은 기록함을 동시에 빌리는 188행의 짝 맞추기는 둘 다 읽기 빌림이라 성립해요.

Iterable 행이 왜 이 패턴인지는 최소 조건을 하나씩 대 보면 보입니다. 위치는 컬렉션이 아니라 컬렉션이 돌려준 순회자 객체 안에 있고(1번), 부르는 쪽은 hasNext()·next() 둘만 알면 되며(2번), 그 둘은 Iterator 에 선언돼 있고 Iterable 쪽에는 「다음 원소를 달라」가 없습니다(3번). iterator() 가 4번이고, 컬렉션마다 다른 구현을 돌려주니 6번도 채워요. Iterable 의 기본 메서드 forEach 는 부르는 쪽이 원소마다 할 일을 넘기고 진행은 라이브러리가 맡는 모양인데, 진행을 맡는 주체가 여전히 iterator() 가 돌려준 순회자라 조건 셋이 그대로 적용됩니다.

그리고 이 표의 첫 줄과 셋째 줄은 Factory Method 이기도 합니다. iterator() 와 into_iter() 는 반환 타입이 추상 타입이고 구현마다 재정의되는 인스턴스 연산이라, Factory Method 편의 최소 조건 다섯을 그대로 만족해요. 두 편이 같은 API(Application Programming Interface, 라이브러리가 바깥에 약속한 호출 규약)를 서로 다른 조건표로 읽고 둘 다 맞는 자리입니다. 다만 결합 시점은 다릅니다. 그 두 낱말의 뜻은 참고 문서 「GoF 공통 어휘」의 「컴파일 시점 결합과 실행 시점 결합」에 있어요.

java.util.Iterator 의 remove() 는 골라 구현하는 연산이고, 이 메서드 말고 다른 방법으로 순회 중에 컬렉션을 고치면 순회자의 동작이 정해져 있지 않다고 문서가 적어 둡니다. ArrayList 의 순회자는 그런 변경을 감지해 예외를 던지는데, 문서 자신이 이 감지를 보장이 아니라 최선의 노력이라고 분명히 적어 둡니다. 그러니 프로그램의 정확성을 이 예외에 의존하면 안 됩니다. 최소 조건 8번이 [선택] 인 이유가 여기 있어요. 구현 절의 RingScanLog 에는 이 감지가 없고, 그래서 순회하면서 원소를 하나 받을 때마다 같은 기록 SCN-08 을 add 로 넣으면 SCN-03 SCN-05 SCN-07 SCN-08 SCN-08 처럼 값을 건너뛴 결과가 아무 신호 없이 나옵니다.

std::iter 쪽은 자기 소개부터 「조합할 수 있는 바깥 순회」라고 적습니다. Iterator 에서 반드시 구현해야 하는 것은 next 하나이고 나머지는 제공 메서드예요. 다만 next 가 「없음」을 돌려준 뒤 다시 값을 돌려줘도 되는 것으로 정해져 있어서, 끝난 뒤의 동작을 보장하려면 fuse() 를 거쳐야 합니다. 최소 조건 5번이 말하는 「끝을 알린다」가 「끝난 뒤의 동작까지 정해 준다」는 뜻은 아니라는 것을 보여 주는 자리예요.

  1. 아래 ShiftBoard 가 Iterator 인지 최소 조건 1~3번을 하나씩 적용해 판정해 보세요. 빠진 조건이 있다면 몇 번이고, 시나리오 3 의 어느 단계와 같은 모양인가요? 그리고 보고 화면과 알람 화면이 각각 한 번씩 while (board.hasNext()) board.next() 를 실행하면 알람 화면에는 이름이 몇 개 찍히나요?

    final class ShiftBoard {
    private final String[] names = {"kim", "lee", "park", "choi"};
    private int at = 0;

    boolean hasNext() {
        return at < names.length;
    }

    String next() {
        return names[at++];
    }
}

    풀이 — 빠진 조건은 1번과 3번이고 Iterator 가 아닙니다. 위치 at 이 순회자가 아니라 집합 클래스 ShiftBoard 의 필드라 1번이 빠지고, hasNext()·next() 가 집합 타입에 붙어 있어 순회자 타입 자체가 없으니 3번도 빠져요. 부르는 쪽은 배열을 만지지 않고 두 연산만 쓰므로 2번은 만족합니다. 시나리오 3 의 1·2단계, cursor 를 단 RingScanLog 와 같은 모양이에요(교차 판정 표의 ShiftBoard 줄도 같은 답). 알람 화면에는 이름이 0 개 찍힙니다. 보고 화면이 네 이름을 다 읽고 나면 at 이 4 에 가 있어 알람 화면의 첫 hasNext() 가 4 < 4 로 false 이기 때문이에요(고쳐 실행해 확인 — 첫 순회 4개, 둘째 순회 0개). 시나리오 3 의 2단계에서 둘째 순회가 (none) 으로 끝난 것과 같은 일입니다.
