한눈에 보는 개요

도서관 연체 통지 프로그램을 하나 떠올려 봅시다. OverdueNotifier 는 대출 기록을 읽고, 오늘이 며칠인지 보고, 기한이 지난 건마다 통지를 내보냅니다. 그런데 그 셋을 통지기가 자기 생성자 안에서 직접 만들어 씁니다 — 저장소도, 시계도, 발송기도요. 통지 내용이 맞는지 확인하려고 다음 주 날짜로 한 번 실행해 보고 싶으면 방법이 없습니다. 오늘을 정하는 코드가 통지기 안에 있으니 통지기를 고쳐야 하고, 고치고 나면 그건 확인하려던 그 코드가 아니게 돼요.

Dependency Injection 의 해법은 협력 객체를 만드는 일을 통지기 밖의 조립 코드로 옮기는 것입니다. 통지기에는 "저장소가 있다 · 시계가 있다 · 발송기가 있다" 는 타입 선언만 남고, 어느 구현이 들어오는지는 조립하는 쪽만 압니다. 그래서 같은 통지기 코드에 운영용 조립과 시험용 조립을 각각 연결할 수 있어요.

Before : 통지기가 협력 객체를 스스로 만든다

  OverdueNotifier
    ├─ new InMemoryLoanRepository(...)   ← 어느 저장소를 쓸지가 통지기 안에 적힌다
    ├─ new FixedClock(120)               ← 오늘이 며칠인지도 통지기가 정한다
    └─ new ConsoleNoticeSender("ops")    ← 통지가 어디로 나가는지도
       다른 날짜로 실행해 보려면 통지기를 고쳐야 한다

After : 조립자가 만들고, 통지기는 받아서 쓴다

  assembleForOperations()                      assembleForTest()
    InMemoryLoanRepository                       InMemoryLoanRepository
    FixedClock(120)                              FixedClock(127)
    ConsoleNoticeSender("ops")                   RecordingNoticeSender
              │                                            │
              └────────────▶ OverdueNotifier ◀─────────────┘
                               loans  : LoanRepository
                               clock  : Clock
                               sender : NoticeSender     ← 한 줄도 바뀌지 않는다

이름은 Martin Fowler 의 2004년 글에서 나왔어요. 그전까지 이런 구조를 부르던 Inversion of Control(제어의 역전)이 너무 넓어서 무엇이 뒤집히는지 알려 주지 못한다고 보고, 이 구조를 쓰던 사람들과 논의해 더 좁은 이름으로 정한 거예요(Inversion of Control Containers and the Dependency Injection pattern). 분류는 GoF(Gang of Four, 1994년에 나온 Design Patterns 의 저자 네 명을 함께 부르는 이름)의 생성·구조·행위 어느 칸에도 들어가지 않고, 같이 놓고 볼 패턴은 Strategy · Singleton 입니다.

이 글은 연체 통지 시나리오 셋을 따라갑니다. 통지 한 번이 조립부터 발송까지 가는 길, 시험용 조립이 붙을 때 무엇이 안 바뀌는가, 통지기가 구현을 직접 만들거나 구체 타입으로 가지거나 등록소에서 꺼내 오면 어디서 막히고 무엇이 어긋나는가. 끝까지 읽으면 어떤 코드를 Dependency Injection 이라고 불러도 되는지 필수 조건 셋으로 판정할 수 있고, 그 조건 셋을 다 갖춘 코드가 동시에 Strategy 이기도 한 이유까지 설명할 수 있게 됩니다.

시나리오 1 — 연체 통지 한 번이 조립부터 발송까지 가는 길

도서관 대출 기록이 넷 있습니다. M-101 의 「Data Structures」(기한 118일째), M-204 의 「Operating Systems」(기한 120일째), M-101 의 「Compiler Design」(기한 125일째), M-337 의 「Discrete Math」(기한 113일째)예요. 날짜는 연·월·일 대신 도서관 개관 이후 며칠째인지를 세는 정수 하나로 둡니다 — 세 언어 표준 라이브러리만으로 같은 값을 내려는 것이고, 이 편이 보이려는 것은 날짜 계산이 아니라 그 값을 어디서 얻는가입니다. 오늘은 120일째이고, 나와야 하는 것은 기한이 지난 건마다 통지 한 줄과 요약 한 줄입니다.

  1. 조립자가 협력 구현 셋을 만듭니다. InMemoryLoanRepository(대출 넷을 담은 저장소) · FixedClock(120)(오늘을 120일째로 답하는 시계) · ConsoleNoticeSender("ops")(통지를 줄로 찍는 발송기)입니다. 여기서 조립자는 어느 구현을 쓸지 정해 만드는 바깥 코드이고, 협력 구현은 그렇게 만들어져 실제로 일을 하는 객체입니다. 왜 조립자가 맡는가 — 어느 저장소·어느 시계·어느 발송기를 쓸지는 프로그램을 어떻게 조립할지의 문제이지 통지 규칙의 문제가 아니에요. 통지기가 그것까지 정하면 조립하는 방법이 늘 때마다 통지기를 열게 됩니다.
  2. 조립자가 그 셋을 통지기의 생성자 인자로 넣습니다. new OverdueNotifier(저장소, 시계, 발송기) 한 줄이에요. 협력 객체가 들어가는 이 자리를 주입 지점이라고 부르겠습니다. 왜 생성자 자리인가 — 통지기는 셋이 다 있어야 일을 할 수 있으니, 셋 없이는 객체가 만들어지지도 않게 두는 편이 안전합니다. 이 순서를 뒤집어 객체를 먼저 만들고 나중에 채우면, 채우기 전에 통지를 청구하는 길이 열려요.
  3. 조립자가 조립된 통지기를 쓰는 쪽에 돌려줍니다. 조립자의 일은 여기서 끝납니다. 여기서 쓰는 쪽은 조립된 통지기에게 일을 시키는 코드예요. 왜 여기서 끝나는가 — 조립자가 통지까지 맡으면 "무엇으로 조립할지" 와 "무엇을 시킬지" 가 한 덩어리가 되고, 시험용으로 다르게 조립하려면 시키는 코드까지 복사하게 됩니다.
  4. 쓰는 쪽이 통지기에게 연체 통지를 청구합니다. notifyOverdue() 한 번이에요. 왜 쓰는 쪽이 구현을 몰라도 되는가 — 청구하는 연산의 모양이 어느 구현을 넣었든 같기 때문입니다. 시나리오 2 에서 발송기를 바꿀 때 이 줄이 안 바뀌는 것이 그 덕이에요.
  5. 통지기가 시계에게 오늘을 묻습니다. 돌아온 값은 120 입니다. 왜 통지기가 직접 시각을 읽지 않는가 — 직접 읽으면 오늘이 언제인지가 통지기 바깥에서 정해질 수 없고, 그러면 어제나 다음 주로 실행해 보는 일이 통지기를 고치는 일이 됩니다.
  6. 통지기가 저장소에게 대출 목록을 청구합니다. 넷이 들어온 순서 그대로 돌아옵니다. 왜 목록을 통지기가 가지고 있지 않는가 — 대출이 어디에 어떻게 쌓이는지는 통지 규칙과 상관없는 일이고, 통지기가 그것까지 알면 저장 방식이 바뀔 때 통지기가 함께 바뀝니다.
  7. 통지기가 기한이 지난 건마다 발송기에게 넘깁니다. 118일째 기한은 2일, 113일째 기한은 7일 초과라 둘이 넘어가고, 120일째 기한은 당일이라 넘어가지 않으며 125일째 기한은 아직 남았습니다. 발송기가 ops: notice M-101 "Data Structures" 2 days late 와 ops: notice M-337 "Discrete Math" 7 days late 두 줄을 찍어요. 왜 통지기가 직접 찍지 않는가 — 찍는 일을 통지기가 맡으면 통지 내용을 확인할 방법이 화면을 읽는 것뿐이 됩니다. 시나리오 2 의 5단계가 그 차이가 나타나는 자리예요.
  8. 통지기가 오늘과 보낸 건수를 담아 돌려주고, 쓰는 쪽이 그것을 찍습니다. 요약 ops: today=120 sent=2 가 이 자리입니다. 왜 통지기가 요약까지 찍지 않는가 — 통지기가 아는 발송 경로는 주입된 발송기 하나뿐이고, 요약을 어디에 낼지는 쓰는 쪽이 정할 일이에요.

이 시나리오에서 확인한 것은 다섯입니다. 협력 객체가 들어오는 자리가 통지기 밖에서 정해진다는 것, 통지기가 그 객체를 만들지도 찾지도 않는다는 것, 통지기 코드에는 협력 타입 이름만 있고 구현 이름은 없다는 것, 조립하는 코드와 시키는 코드가 서로 다른 단위라는 것, 그리고 통지기가 조립자를 부르는 곳이 한 군데도 없다는 것. 이 이름들의 정식 정의는 아래 「개념 정리」에 모았습니다.

시나리오 2 — 시험용 조립이 붙고, 통지기는 한 줄도 바뀌지 않는다

통지 내용이 맞는지 확인하고 싶습니다. 그런데 화면에 찍히면 읽어서 비교하는 수밖에 없고, 오늘이 120일째라 연체가 둘뿐이라 기한이 늦은 건까지 확인이 안 돼요. 오늘을 127일째로 두고 발송기를 통지를 쌓아 두는 것으로 바꾸면 넷이 다 걸립니다. 대출 넷은 그대로고, 나와야 하는 것은 요약 한 줄과 쌓인 통지 넷입니다.

  1. 협력 구현 하나를 새로 만듭니다. RecordingNoticeSender 는 발송기 타입을 따르되 찍는 대신 줄을 목록에 쌓고, 쌓인 것을 내주는 연산을 하나 더 갖습니다. 이때 통지기도, 저장소도, 시계도, 기존 발송기도 한 줄이 바뀌지 않아요. 왜 안 바뀌는가 — 새 구현은 발송기 타입이 선언한 연산만 맞추면 되고, 그 타입을 쓰는 쪽은 구현이 몇 개인지 모르기 때문입니다.
  2. 조립자를 하나 더 만듭니다. assembleForTest() 는 저장소는 같은 대출 넷으로 똑같이 만들고 시계를 FixedClock(127) 로, 발송기를 새 구현으로 둡니다. 왜 통지기를 고치지 않고 조립자를 늘리는가 — 무엇으로 조립할지는 조립자의 일이라고 1단계에서 갈라 두었기 때문이에요. 그렇게 갈라 두지 않았다면 여기서 통지기에 if (시험) 가 들어갔을 겁니다.
  3. 조립자가 대역을 만들어 통지기에 넣고, 조립 결과와 함께 그 대역도 돌려줍니다. 왜 대역을 같이 돌려주는가 — 통지기는 자기가 무엇을 받았는지 바깥에 알려 주지 않습니다. 쌓인 통지를 읽으려면 그 객체를 가지고 있는 쪽이 따로 있어야 하고, 만든 것이 조립자이니 조립자가 넘겨줍니다.
  4. 쓰는 쪽이 시나리오 1 과 같은 연산을 부릅니다. notifyOverdue() 입니다. 오늘이 127일째라 넷이 다 기한을 넘겨 9일 · 7일 · 2일 · 14일 초과로 나오고, 요약은 test: today=127 sent=4 예요. 왜 같은 연산인가 — 바뀐 것은 어느 구현이 들어갔는가뿐이고 통지 규칙은 그대로이기 때문입니다.
  5. 쓰는 쪽이 대역에 쌓인 통지를 읽습니다. 쌓인 건수 test: recorded 4 와 통지 넷이 이 자리예요. 왜 이것이 이제야 가능한가 — 1단계에서 발송기가 타입으로만 선언돼 있었기에 다른 구현이 그 자리에 들어갈 수 있었습니다. 통지기가 화면 출력을 직접 했다면 여기서 읽을 것이 없습니다.

주입 지점을 어디에 둘지는 고를 수 있는 경로가 셋입니다. 셋 다 "협력 객체가 바깥에서 들어온다" 는 점은 같고, 들어오는 때와 자리가 다릅니다.

시나리오 3 — 직접 만든 구현 · 구체 타입 필드 · 등록소 조회는 어디서 막히고 무엇이 어긋나는가

아래 셋은 시나리오 1·2 의 통지 코드를 정해진 자리만 고쳐 실제로 컴파일하고 실행해 본 것입니다. 도구는 javac 21.0.11 · tsc 5.9.3(Node v22.22.3) · rustc 1.95.0 이고, 아래에 적은 자리 말고는 원래 코드와 같습니다. 그 코드는 뒤의 「구현 예시」에 세 언어로 실려 있으니, 재현하려면 그것을 저장한 뒤 적힌 자리만 고치면 돼요.

  1. 통지기가 협력 구현을 직접 만들게 바꿨습니다. 고친 자리는 셋입니다 — ① 생성자를 인자 없는 것으로 바꿔 그 안에서 저장소·시계·발송기를 만들고 ② assembleForOperations 를 new OverdueNotifier() 한 줄로 줄이고 ③ 끼울 자리가 없어진 assembleForTest·TestRig(시나리오 2 의 3단계에서 통지기와 대역을 함께 담아 돌려주던 묶음)·RecordingNoticeSender 와 쓰는 쪽의 시험 부분을 지웠습니다. 결과는 컴파일 통과이고 운영 쪽 출력 세 줄은 글자까지 같았습니다(Java 로 실행해 확인). 대신 아홉 줄이던 출력이 세 줄이 됐어요 — 시험용 조립이 코드에서 사라졌으니까요. 왜 이렇게 되는가 — 통지기가 구현을 스스로 만들면 그 선택을 바꿀 자리가 통지기 안뿐이고, 밖에서 다른 것을 넣을 길이 없습니다.

Property 'tag' is missing in type 'RecordingNoticeSender' but required in type 'ConsoleNoticeSender' 1건, Rust 는 E0308 mismatched types(expected Rc<ConsoleNoticeSender>, found Rc<dyn NoticeSender>) 1건이에요. 그런데 TypeScript 가 막은 이유는 다른 언어와 다릅니다 — 진단이 가리키는 것은 이름이 아니라 모양이라, 두 클래스의 tag 필드를 공개로 맞춰 모양을 같게 하면(발송기 쪽 선언 한 줄을 고치고 기록 발송기에 같은 필드 한 줄을 보탬) 컴파일도 실행도 통과하고 출력 아홉 줄이 그대로 나왔습니다(직접 컴파일·실행해 확인). tag 를 양쪽 다 private 으로 두면 Types have separate declarations of a private property 'tag' 로 다시 막혀요. 왜 이 차이가 생기는가 — TypeScript 는 타입이 같은지를 선언한 이름이 아니라 멤버의 모양으로 가리고, 그 판정에서 private 멤버만 이름이 같은 곳에서 나왔는지를 따로 봅니다.
  3. 협력 객체를 등록소에서 꺼내 오게 바꿨습니다. 통지기의 필드와 생성자 인자를 모두 지우고, 정적 등록소 하나를 두어 ServiceLocator.clock() · ServiceLocator.loans() · ServiceLocator.sender() 로 꺼내 쓰게 했어요. 컴파일도 실행도 통과합니다. 그런데 시험용 등록을 먼저 해 두고 운영 통지기를 만들어 부르면 ops: today=127 sent=4 가 나오고, 시험용 대역에 통지 4건이 쌓였습니다(Java 로 실행해 확인). 운영 통지가 시험용 대역으로 나간 것이고, 통지기를 만드는 줄에는 인자가 하나도 없어서 그 사실을 확인할 수 있는 자리가 없습니다. 왜 이렇게 되는가 — 꺼내 오는 구조에서는 무엇을 쓰는지가 호출 순서와 전역 상태에 달리고, 그 둘은 통지기를 만드는 자리에 적히지 않습니다.

여기서 헷갈리기 쉬운 포인트는 1번입니다. 컴파일도 되고 운영 출력도 글자까지 같으니 "그럼 같은 코드 아닌가" 싶어지죠. 그런데 사라진 여섯 줄이 무엇이었는지를 보면 구분됩니다. 그 여섯 줄은 같은 통지 규칙을 다른 날짜와 다른 발송 경로로 한 번 더 실행한 결과였고, 1번 판에서는 그것을 되살릴 길이 통지기를 고치는 것뿐이에요. 출력이 같다고 두 코드가 같은 것은 아니고, 이 패턴이 효과를 내는 자리는 프로그램을 한 벌로 실행할 때가 아니라 두 벌째를 조립할 때입니다.

개념 정리

시나리오에 나온 이름 다섯을 역할 이름으로 정의합니다. 예시 코드의 타입 이름(OverdueNotifier·Clock)은 정의 대상이 아니라 「상황 설정」에서 이 역할들에 매핑하는 쪽이에요. 다섯 가운데 원전이 쓰는 이름은 Assembler 하나뿐이고 나머지 넷은 이 가이드가 붙였습니다. 원전은 주입받는 쪽을 자기 예제의 클래스 이름으로 부르고 주입되는 쪽을 component 와 service 로 부르는데, 그 두 낱말은 이 편이 가리키려는 자리보다 넓어서 역할 이름으로 그대로 쓰지 않았어요.

  • Dependent(의존 객체) — 협력 객체를 써서 자기 일을 하는 객체입니다. 협력 객체를 만들지도 찾지도 않고 주입 지점으로 받아 필드에 두고, 협력 타입이 선언한 연산만 부릅니다. 자기에게 무엇이 들어왔는지, 누가 넣어 주었는지는 모릅니다. Collaborator 와만 협력하고 Assembler 와는 협력하지 않아요 — 그 방향의 참조가 없는 것이 이 역할의 요점입니다.
  • Collaborator(협력 타입) — 의존 객체가 협력 객체를 다룰 때 쓰는 타입입니다. 의존 객체가 부를 연산을 선언하고, 그 연산을 누가 어떻게 수행하는지는 모릅니다. 인터페이스·추상 클래스·trait(Rust 에서 타입이 구현할 연산을 선언하는 문법)·함수 타입처럼 구현을 하나로 지목하지 않는 것이면 됩니다. Dependent 가 이 타입으로 필드를 선언하고, ConcreteCollaborator 가 이 타입을 구현해요.
  • ConcreteCollaborator(협력 구현) — 협력 타입이 선언한 연산을 실제로 수행하는 객체입니다. 자기가 어느 의존 객체에 들어가는지 모르고, 같은 협력 타입의 다른 구현이 있는지도 모릅니다. Assembler 가 이것을 만들어 Dependent 에 넣습니다.
  • Assembler(조립자) — 어느 협력 구현을 쓸지 정해 만들고, 그것을 의존 객체의 주입 지점에 넣는 바깥 코드입니다. 함수 하나여도 되고 클래스나 설정 파일을 읽는 모듈이어도 됩니다. 의존 객체와 협력 구현 양쪽의 구체 타입을 다 알고, 그 앎이 여기 한 곳에 모이는 것이 이 역할의 핵심이에요. Dependent 가 Assembler 를 참조하는 순간 이 구조가 아니게 됩니다.
  • Client(쓰는 쪽) — 조립된 의존 객체를 받아 일을 시키는 코드입니다. 어느 구현이 들어갔는지 모른 채 의존 객체가 공개한 연산만 부릅니다. 조립을 청구하는 쪽과 일을 시키는 쪽이 같은 코드일 수도 있지만, 갈라 두면 조립을 바꿔 가며 같은 청구를 되풀이할 수 있어요.

그림에서 눈여겨볼 것은 없는 선입니다. Assembler 에서 Dependent 로 가는 선은 있는데 되돌아오는 선이 없어요. 이 방향이 한쪽이라서 의존 객체는 자기가 어떻게 조립됐는지 모른 채로도 일을 할 수 있고, 조립 방식을 바꿔도 의존 객체 코드가 안 바뀝니다. 되돌아오는 선을 그으면, 다시 말해 의존 객체가 조립하는 쪽을 부르면 시나리오 3 의 3단계가 되고, 그 구조의 이름은 비교 절에서 따로 다룹니다. 그리고 Dependent 에서 Collaborator 로 가는 마름모 선의 수가 1..* 인 것도 읽을 자리예요. 협력 객체가 하나뿐인 의존 객체도 이 구조이고, 이 편의 예시처럼 셋이어도 같습니다.

어떤 단서가 보일 때 이 패턴이 필요한지부터 봅시다. 셋 다 코드에서 확인되는 것들이고, 단서를 만났을 때 물어볼 것은 아래 순서예요.

그 줄은 대개 생성자나 메서드 안의 생성 호출(new SystemClock() · new SmtpSender(...))이거나 전역 접근점 호출입니다. 확인하려는 규칙은 그 클래스 안에 있는데, 그 규칙을 실행하려면 실제 시각과 실제 발송이 함께 딸려 와요. 시나리오 3 의 1단계가 이 상태에서 무엇이 사라지는지 보여 줍니다.

단서 2 — 같은 클래스를 두 환경에서 다르게 조립해야 하는데, 그 차이가 클래스 안의 분기로 들어가 있습니다

단서 3 — 한 클래스가 협력 객체를 셋 이상 스스로 만들고, 그 생성 순서까지 그 안에 적혀 있습니다

저장소를 만들려면 연결 설정이 있어야 하고 그 설정은 또 어디선가 읽어야 하는 식으로 이어지면, 그 클래스의 생성자가 프로그램 조립 절차를 겸하게 됩니다.

패턴의 경계

디자인 패턴을 충족하는 최소 조건

어떤 코드를 Dependency Injection 이라고 불러도 되는지 가르는 기준입니다. [필수] 가 하나라도 빠지면 이 패턴이 아니고, [선택] 은 갖추면 좋거나 상황에 따라 고르는 구조예요. 조건은 언어와 상관없이 코드에서 확인할 수 있는 모양(타입 선언 · 참조 보유 · 호출 방향 · 생성 위치)으로 적었고, 조건마다 그것을 보여 준 시나리오의 단계를 가리킵니다. 여기서 "협력 객체" 는 1번이 정합니다 — 의존 객체가 필드나 인자로 가지고 그 연산을 부르는 객체가 협력 객체이고, 나머지 조건은 그 객체들을 가리켜요.

  1. 잠깐, 하나만 확인해 볼까요. 시나리오 3 의 1단계 판에서 생성자 안의 생성 호출 세 줄을 생성자 인자로 옮기기만 하면 필수 셋이 다 성립할까요? 1번은 필드 타입을 안 건드렸으니 그대로 만족이고, 2번도 안에서 만드는 코드가 사라지니 만족입니다. 3번은 그 세 줄이 어디로 옮겨 갔는가에 달려요. 부르는 쪽 함수 안에 그대로 남으면 조립 코드가 쓰는 코드와 한 단위라 선택 6번만 빠지고 필수 3번은 성립합니다. 반대로 통지기가 자기 안에 정적 조립 메서드를 두고 그것을 부르면, 넣는 코드가 여전히 의존 객체 타입 안이라 3번이 빠져요.

만드는 일과 쓰는 일을 다른 코드에 둔다 — 쓰는 쪽은 협력 타입만 알고, 어느 구현인지는 조립하는 쪽만 안다.

비슷한 패턴·안티패턴과의 차이

겹치는 대상 넷을 비교합니다. 앞의 둘은 구조가 닮은 정도가 아니라 같은 코드에 두 이름이 다 붙거나 한 이름만 붙는 관계라서 먼저 그 사실을 분명히 하고 시작할게요. 뒤의 둘 가운데 하나는 같은 단서에서 떠오르는 다른 선택지이고, 나머지 하나는 이 패턴으로 오해받는 코드입니다.

비교 대상구분 기준 (코드에서 보는 것)이 이름을 고르면 얻는 것포기하는 것
Strategy의존 객체가 든 협력 타입이 하나이고 그 구현들이 같은 연산의 다른 계산인가, 여럿이고 각자 다른 일을 맡는가협력 객체가 하나든 셋이든, 구현이 하나뿐이어도 같은 이름으로 말할 수 있음「교체할 알고리즘들」이라는 좁고 분명한 뜻. 무엇이 갈아 끼워지는지가 이름에 안 실림
Service Locator협력 객체가 의존 객체 안으로 들어오는가, 의존 객체가 밖으로 나가 꺼내 오는가. 의존 객체가 등록소·접근점의 이름을 부르는 호출이 있는지를 봄의존 객체가 무엇을 쓰는지가 생성 자리에 전부 적힘. 등록소를 모르는 코드에서도 그대로 씀인자가 늘고 조립 코드가 필요함. 실행 중에 새 협력 객체를 더 얻어 올 길이 없음
Singleton협력 객체를 받는 경로가 있는가, 협력 객체 쪽이 자기 생성자를 닫고 전역 접근점을 내는가시험이나 다른 환경에서 그 자리에 다른 객체를 넣을 수 있음하나만 존재한다는 보장. 컴파일러가 두 번째 인스턴스를 막아 주지 않음
이름표를 받아 안에서 고르는 코드 (오인 코드)생성자로 들어오는 것이 협력 객체인가 이름표인가구현이 늘 때 의존 객체를 안 고침어느 구현인지 고르는 분기가 사라지지는 않고 조립 코드로 옮겨 감

Strategy 와의 차이

먼저 사실부터 적습니다. 발행된 Strategy 편의 예시 코드는 이 편의 필수 조건 셋을 전부 만족합니다. 그 편의 코드를 직접 읽어 대조했어요. Checkout 은 요금제를 ShippingPolicy 라는 인터페이스 타입 필드로 가지고 그 타입의 연산만 부르니 1번을 만족하고, 그 필드가 생성자 인자와 changePolicy 로 들어오며 Checkout 안에 요금제를 만드는 생성 호출도 찾아오는 호출도 없으니 2번을 만족하며, 구체 요금제를 만드는 choosePolicy 가 Checkout 밖에 있고 Checkout 이 그 코드를 부르지 않으니 3번을 만족합니다. 반대로 이 편의 예시 코드를 그 편의 필수 조건으로 채점하면 자리마다 답이 달라요.

Clock — 고정 시계 하나를 120일째와 127일째로 두 번만족 (그 편 1번은 같은 클래스를 필드 값으로 나눈 경우도 「한 계산 방법을 매개변수로 나눈 것」으로 쳐서 만족으로 적는다)만족부를 수 있다
LoanRepository — 메모리 저장소 하나, 두 조립이 같은 대출 넷을 넣음잴 대상 없음 (나뉜 값도 없어 「교체할 계산들」이 성립하지 않음)만족부를 수 없다

그러니 두 이름의 관계는 겹침입니다. 협력 타입이 하나이고 그 구현들이 같은 계산의 대안이면 두 이름이 다 맞고, 갈아 끼울 것이 아예 없는 자리이거나 협력 타입이 여럿이면 의존성 주입이라는 이름만 남아요. 시나리오 2 의 1단계에서 발송기 구현이 둘이 된 순간 그 자리는 Strategy 로도 읽히고, 같은 시나리오에서 시계도 120일째와 127일째로 나뉘니 그 편이 한 계산을 매개변수로 나눈 경우로 치는 자리가 됩니다. 저장소만 두 조립이 같은 값을 넣어 잴 것이 남지 않아요. 그런데도 셋 다 구현 클래스는 하나뿐이라 이 편의 최소 조건 7번은 성립하지 않습니다. 7번을 선택에 둔 이유가 바로 이것이고, 그것을 필수로 올리면 시계와 저장소가 탈락합니다.

Strategy 라는 이름을 고르면 무엇이 갈아 끼워지는지가 이름에 실리고, 대신 협력 객체가 셋이거나 구현이 하나뿐인 자리는 그 이름으로 덮이지 않습니다. 의존성 주입을 고르면 그 셋을 한 이름으로 말할 수 있고, 대신 교체할 알고리즘들을 가리키는 좁은 뜻을 포기해요. 그래서 이름을 고르는 일과 판정하는 일이 다릅니다 — 판정은 조건으로 하고, 이름은 그 코드를 읽는 사람이 무엇을 더 알게 되는가로 고릅니다.

Service Locator 와의 차이

구분 기준은 협력 객체가 의존 객체 안으로 들어오는지, 의존 객체가 밖으로 나가 꺼내 오는지입니다. 코드에서는 의존 객체가 등록소나 전역 접근점의 이름을 부르는 호출이 있는지를 보면 돼요. 시나리오 3 의 3단계가 그 호출을 넣어 본 자리입니다.

// 꺼내 오는 쪽 — 생성자 인자가 없고, 무엇을 쓰는지는 실행할 때 정해진다
static final class OverdueNotifier {
    NoticeRun notifyOverdue() {
        int today = ServiceLocator.clock().today();          // 등록소를 이름으로 부른다
        for (Loan loan : ServiceLocator.loans().allLoans()) {
            ServiceLocator.sender().send(/* … */);
        }
    }
}

// 부르는 쪽에는 이렇게만 보인다
OverdueNotifier operations = new OverdueNotifier();          // 인자가 하나도 없다

이 판을 실제로 실행해 보면 시험용 등록이 먼저 있었을 때 운영 통지가 today=127 sent=4 로 나가고 통지 4건이 시험용 대역에 쌓입니다(직접 실행해 확인). 문제가 생긴 것은 등록소가 나쁜 구조여서가 아니라, 의존 객체가 무엇을 쓰는지가 그 객체를 만드는 자리에 안 적혀 있기 때문이에요. 넣어 주는 쪽은 반대입니다 — 시나리오 1 의 2단계에서 통지기를 만드는 줄에 저장소·시계·발송기가 다 적혀 있어서, 그 줄만 보면 이 통지기가 무엇으로 조립됐는지 알 수 있습니다. 대신 인자가 늘고 조립 코드가 필요해요. 그리고 실행 중에 협력 객체를 더 얻어 올 길이 없습니다 — 주입하는 쪽으로 가는 참조가 없으니 한 번 조립된 뒤에는 더 청구할 데가 없거든요. 원전은 두 방식을 나란히 놓고 비교한 끝에 이렇게 맺습니다.

둘 사이의 선택보다 서비스의 구성을 그 사용과 분리한다는 원칙이 더 중요하다 (근거: Fowler 「Inversion of Control Containers and the Dependency Injection pattern」 Concluding Thoughts 절).

Singleton 과의 차이

구분 기준은 협력 객체를 받는 경로가 있는지, 아니면 협력 객체 쪽이 자기 생성자를 닫고 전역 접근점을 내는지입니다. 발행된 Singleton 편이 「의존성 주입 컨테이너의 단일 스코프와의 차이」를 비교 갈래로 두고 있는데, 이 편이 그 갈래의 반대쪽이에요. 같은 요구 — "이 객체는 프로그램에 하나면 된다" — 를 두 방식이 다르게 답합니다. 시계를 하나만 두고 싶다고 해 봅시다.

하나만 두려는 요구를 누가 지키는가

  Singleton          Clock.instance()          생성자가 닫혀 있어 컴파일러가 두 번째를 막는다
                                               시험에서 다른 시계를 넣을 자리가 없다

  의존성 주입        assemble() { Clock c = new FixedClock(120); … }
                                               조립자가 하나만 만들어 필요한 곳에 넣는다
                                               클래스는 몇 번이든 만들 수 있다 — 하나인 것은 조립의 약속이다

시나리오 2 의 2·3단계가 그 차이가 의미를 갖는 자리입니다. 조립자를 하나 더 만들어 시계를 FixedClock(127) 로 두었는데, 통지기는 한 줄도 안 바뀌었어요. 접근점을 부르는 구조였다면 통지기 안의 Clock.instance() 를 고쳐야 했을 겁니다. 의존성 주입을 고르면 그 자리에 다른 객체를 넣을 수 있고, 대신 하나만 존재한다는 보장을 포기합니다 — 조립 코드가 실수로 두 번 만들어도 컴파일러가 아무 말도 하지 않아요. 유일성 자체가 규칙인 자원이라면 그 편의 최소 조건 쪽이 맞습니다.

이름표를 받아 안에서 고르는 코드와의 차이

이 모양이 의존성 주입으로 가장 자주 오해받습니다. 구분 기준은 생성자로 들어오는 것이 협력 객체인지 이름표인지예요.

// 인자를 받으니 주입처럼 보이지만, 들어오는 것은 구현이 아니라 문자열이다
static final class OverdueNotifier {
    private final Clock clock;

    OverdueNotifier(String mode) {
        this.clock = switch (mode) {            // 고르는 분기가 의존 객체 안에 있다
            case "ops" -> new FixedClock(120);
            case "test" -> new FixedClock(127);
            default -> throw new IllegalArgumentException(mode);
        };
    }
}

필드 타입이 Clock 이라 1번은 만족합니다. 그런데 협력 구현을 만드는 생성 호출이 의존 객체 안에 있으니 2번이 빠지고, 고르는 코드가 밖의 별도 단위가 아니니 3번도 빠져요. 시나리오 2 의 2단계를 이 코드에 넣어 보면 차이가 납니다. 시나리오 2 에서는 조립자를 하나 더 쓰는 것으로 끝났는데, 여기서는 mode 에 case 를 더해야 하고 그러면 통지기를 다시 여는 것입니다. 시계가 아니라 발송기를 바꾸려는 요구가 오면 mode 가 두 가지를 한꺼번에 뜻하게 되고요. 의존성 주입을 고르면 구현이 늘어도 의존 객체를 안 고치고, 대신 어느 구현을 쓸지 고르는 분기는 사라지지 않고 조립 코드로 옮겨 갑니다.

조건은 다 만족하지만 이름값이 없는 코드

마지막으로 필수 셋을 다 만족하는데 이 이름을 붙여 얻을 것이 없는 코드도 확인해 둡니다. 조건이 넓다는 말을 실제 코드로 보이는 자리예요.

interface Currency { String code(); }
final class Won implements Currency { public String code() { return "KRW"; } }

final class Price {
    private final Currency currency;                  // 추상 타입으로 든다 — 1번 만족
    private final long amount;

    Price(Currency currency, long amount) {           // 바깥에서 들어온다 — 2번 만족
        this.currency = currency;
        this.amount = amount;
    }

    String label() { return amount + " " + currency.code(); }
}

Price p = new Price(new Won(), 32_000);               // 만드는 코드가 밖에 있다 — 3번 만족

셋 다 성립합니다. 그래도 이 코드를 의존성 주입이라고 불러서 읽는 사람이 알게 되는 것이 없어요. Won 을 시험용 대역으로 바꿀 이유가 없고, 갈라 둘 구성이라는 것도 없습니다. 원전이 다루는 것은 프로그램을 조립할 때 어느 구현을 넣을지 정해야 하는 서비스이고, 통화는 그런 것이 아니에요. 다만 그렇게 좁히는 기준을 코드 구조만으로 잴 방법이 없어서 조건으로 옮기지 않았습니다 — 자료를 내주는 연산과 일을 해 주는 연산은 선언만 봐서는 구분되지 않으니까요. 이것이 「Strategy 와의 차이」 끝에 적은 「판정은 조건으로 하고, 이름은 그 코드를 읽는 사람이 무엇을 더 알게 되는가로 고릅니다」의 실제 모양입니다.

두 판정 경로의 대조

두 경로로 판정했을 때 답이 달라지는지도 확인해 뒀습니다. 경로 A 는 최소 조건의 [필수] 셋만 적용한 것이고, 경로 B 는 이 절의 구분 기준만 적용한 것이에요.

시나리오 1·2 의 통지 코드의존성 주입의존성 주입 — 협력 타입 셋이 각자 다른 일을 맡는다같음

import java.util.ArrayList;
import java.util.List;

public final class OverdueNotice {

    // ── 자료 ────────────────────────────────────────────────────────────────
    record Loan(String memberId, String title, int dueDay) {
    }

    record NoticeRun(int today, int sent) {
    }

    // ── 협력 타입 — 의존 객체는 협력 객체를 이 타입으로만 안다 ──────────────
    interface LoanRepository {
        List<Loan> allLoans();
    }

    interface Clock {
        int today();
    }

    interface NoticeSender {
        void send(String memberId, String title, int daysLate);
    }

    // ── 의존 객체 — 만들지도 찾지도 않고, 받아서 쓴다 ───────────────────────
    static final class OverdueNotifier {
        private final LoanRepository loans;
        private final Clock clock;
        private final NoticeSender sender;

        OverdueNotifier(LoanRepository loans, Clock clock, NoticeSender sender) {
            this.loans = loans;
            this.clock = clock;
            this.sender = sender;
        }

        NoticeRun notifyOverdue() {
            int today = clock.today();
            int sent = 0;
            for (Loan loan : loans.allLoans()) {
                int daysLate = today - loan.dueDay();
                if (daysLate <= 0) {
                    continue;
                }
                sender.send(loan.memberId(), loan.title(), daysLate);
                sent += 1;
            }
            return new NoticeRun(today, sent);
        }
    }

    // ── 협력 구현 ───────────────────────────────────────────────────────────
    static final class InMemoryLoanRepository implements LoanRepository {
        private final List<Loan> rows;

        InMemoryLoanRepository(List<Loan> rows) {
            this.rows = List.copyOf(rows);
        }

        @Override
        public List<Loan> allLoans() {
            return rows;
        }
    }

    static final class FixedClock implements Clock {
        private final int day;

        FixedClock(int day) {
            this.day = day;
        }

        @Override
        public int today() {
            return day;
        }
    }

    static final class ConsoleNoticeSender implements NoticeSender {
        private final String tag;

        ConsoleNoticeSender(String tag) {
            this.tag = tag;
        }

        @Override
        public void send(String memberId, String title, int daysLate) {
            System.out.println(tag + ": notice " + line(memberId, title, daysLate));
        }
    }

    static final class RecordingNoticeSender implements NoticeSender {
        private final List<String> lines = new ArrayList<>();

        @Override
        public void send(String memberId, String title, int daysLate) {
            lines.add(line(memberId, title, daysLate));
        }

        List<String> recorded() {
            return List.copyOf(lines);
        }
    }

    static String line(String memberId, String title, int daysLate) {
        return memberId + " \"" + title + "\" " + daysLate + " days late";
    }

    // ── 조립자 — 어느 구현을 쓸지 여기서만 정한다 ───────────────────────────

    }

    static List<Loan> loanRows() {
        return List.of(
                new Loan("M-101", "Data Structures", 118),
                new Loan("M-204", "Operating Systems", 120),
                new Loan("M-101", "Compiler Design", 125),
                new Loan("M-337", "Discrete Math", 113));
    }

    static OverdueNotifier assembleForOperations() {

                new ConsoleNoticeSender("ops"));
    }

    static TestRig assembleForTest() {
        RecordingNoticeSender recorder = new RecordingNoticeSender();
        OverdueNotifier notifier = new OverdueNotifier(
                new InMemoryLoanRepository(loanRows()),
                new FixedClock(127),
                recorder);
        return new TestRig(notifier, recorder);
    }

    // ── 쓰는 쪽 — 조립된 것을 받아 일을 시킨다 ──────────────────────────────
    public static void main(String[] args) {
        OverdueNotifier operations = assembleForOperations();
        NoticeRun opsRun = operations.notifyOverdue();
        System.out.println("ops: today=" + opsRun.today() + " sent=" + opsRun.sent());

        TestRig rig = assembleForTest();
        NoticeRun testRun = rig.notifier().notifyOverdue();
        System.out.println("test: today=" + testRun.today() + " sent=" + testRun.sent());

        System.out.println("test: recorded " + recorded.size());
        for (String entry : recorded) {
            System.out.println("test: log " + entry);
        }
    }
}

여기서 가장 중요한 줄은 통지기의 필드 선언 셋입니다. Java 28~30행, TypeScript 28~30행, Rust 32~34행이에요. 세 줄에 적힌 타입이 LoanRepository · Clock · NoticeSender 뿐이고 구현 이름은 하나도 없습니다. 이 셋으로 최소 조건 1번이 성립하고, 같은 이름이 생성자 인자에 다시 나와 2번이 성립해요. 이 세 줄 가운데 하나라도 구체 구현 타입으로 바꾸면 시나리오 3 의 2단계가 되고, 대신 생성자 본문에서 그 필드를 new 로 채우면 시나리오 3 의 1단계가 됩니다. 조건 1번과 2번이 같은 자리를 다른 각도로 보는 것이라는 말이 이 세 줄에 그대로 있어요.

언어 차이는 두 자리만 짚습니다. Java 와 TypeScript 는 협력 객체를 그냥 참조로 가지지만, Rust 는 Rc<dyn Trait> 로 가집니다. Rc 는 참조를 세어 한 값을 여럿이 나눠 갖게 하는 표준 라이브러리 타입이고, dyn 은 어느 구현인지 실행할 때 정해진다는 표시예요. 그래서 시험 조립은 같은 기록 발송기를 조립자와 통지기가 함께 가지도록 recorder.clone() 으로 참조를 하나 더 만든 뒤 협력 타입 자리에 넣습니다(Rust 140~141행 — Java 130행·TypeScript 130행의 변수 하나에 해당). 기록 발송기가 목록에 쓰는 일은 Rust 만 RefCell(빌림 검사를 컴파일할 때가 아니라 실행 중으로 미루는 상자)로 감싸 처리해요(Rust 93행·107~108행). 협력 타입이 선언한 연산이 &self(자기 자신을 빌려만 오는 매개변수)를 받기 때문이고, 그것을 &mut self(자기 자신을 고칠 수 있게 빌리는 매개변수)로 바꾸면 Rc 로 나눠 가진 값에서는 그 연산을 부를 수 없게 되므로 쓰기가 필요한 구현 하나가 안쪽에서 해결하는 편이 나머지 구현에 짐을 지우지 않습니다.

실제 라이브러리에서

널리 쓰이는 프레임워크에 이 구조가 그대로 있습니다. 둘 다 링크로 확인한 것만 적었어요.

  • Spring Framework 의 컨테이너 — ApplicationContext 가 Assembler 입니다. 빈으로 등록된 클래스가 Dependent 이고, 그 클래스의 생성자 매개변수가 주입 지점이에요. 어느 구현을 넣을지는 @Configuration 클래스의 @Bean 메서드나 @Component 선언이 정하고, 컨테이너가 생성자를 부르면서 그 자리를 채웁니다(Dependency Injection — Spring Framework). 이 문서는 필수 협력 객체는 생성자로, 선택 협력 객체는 설치 연산으로 받으라는 기준을 제시하는데, 최소 조건 4번에서 생성자 경로를 선택으로 둔 이유와 같은 갈래예요. 다만 컨테이너를 쓰면 유일 인스턴스 이야기가 따라옵니다 — 그 갈래는 Singleton 편의 비교 절에 있습니다.
  • JUnit 의 매개변수 해석 — 테스트 클래스가 Dependent 이고 그 생성자와 테스트 메서드의 매개변수가 주입 지점입니다. ParameterResolver 가 Assembler 쪽 역할을 맡아, supportsParameter 로 그 자리를 자기가 채울지 정하고 resolveParameter 로 실제 객체를 만들어 넘겨요. TestInfoParameterResolver 처럼 내장된 것도 있고 사용자가 등록한 것도 같은 규약을 따릅니다(Parameter Resolution — JUnit User Guide). 여기서 내장 해석기가 넘기는 TestInfo 는 일을 해 주는 협력 객체라기보다 자료에 가까운데, 비교 절에서 본 Price 의 통화와 같은 자리예요. 사용자가 등록한 해석기가 저장소나 대역을 넘길 때 이 구조가 효과를 냅니다.

스스로 점검하기

  1. 경계 판정. 아래 코드를 최소 조건 1~3번으로 판정해 보세요. 의존성 주입입니까? 아니라면 몇 번에서 걸리고, 그 자리를 어떻게 고치면 통과합니까?

    final class ReportMailer {
    private final MailSender sender;
    private final ReportStore store;

    ReportMailer(MailSender sender) {
        this.sender = sender;
        this.store = ReportStore.getInstance();
    }

    void sendDaily(String reportId) {
        sender.send(store.find(reportId));
    }
}
    풀이 보기

    풀이 — 의존성 주입이 아닙니다. sender 는 생성자로 들어오니 이 협력 객체만 보면 조건을 만족하지만, store 가 2번과 3번을 어겨요. 생성자 안에서 ReportStore.getInstance() 라는 전역 접근점을 불러 협력 객체를 찾아오니 2번이 빠지고(최소 조건 2번의 「빠지면(찾아오는 쪽)」 — 「하나라도」 안에서 찾아오면 빠짐), 구현을 내주는 단위인 ReportStore 의 이름이 의존 객체의 호출에 나오니 3번도 빠집니다. 1번은 ReportStore 가 무엇이냐에 달려요. getInstance() 로 자기 인스턴스를 내주는 클래스라면 구체 타입이라 1번도 빠집니다(비교 절 「Singleton 과의 차이」의 접근점을 부르는 모양). 인터페이스에 정적 접근점을 붙인 모양이라면 필드 타입은 추상이라 1번은 만족하지만, 2번과 3번만으로도 판정은 같습니다. 고치려면 ReportMailer(MailSender sender, ReportStore store) 로 store 도 생성자로 받고, getInstance() 를 부르는 일은 조립 코드로 옮기며, ReportStore 를 인터페이스로 두면 됩니다.

  2. 비교 판별. 어떤 팀이 interface RetryPolicy { boolean shouldRetry(int attempt); } 를 만들고 세 구현을 두어 재시도 규칙을 갈아 끼웁니다. 다른 팀은 interface AuditLog { void record(String event); } 를 만들어 감사 기록 한 구현을 서비스 클래스에 넣습니다. 둘 중 어느 쪽을 Strategy 라고도 부를 수 있고, 어느 쪽은 의존성 주입이라고만 부를 수 있습니까? 판단의 근거가 되는 최소 조건 번호와 비교 절의 구분 기준을 대세요.

    풀이 보기

    풀이 — RetryPolicy 쪽은 Strategy 라고도 부를 수 있고, AuditLog 쪽은 의존성 주입이라고만 부릅니다(두 쪽 다 서비스 밖에서 만들어 넣는다고 할 때). 판정은 둘 다 최소 조건 1~3번으로 의존성 주입이에요. 갈리는 곳은 비교 절 「Strategy 와의 차이」의 구분 기준입니다. RetryPolicy 는 협력 타입이 하나이고 세 구현이 「다시 시도할까」라는 같은 판단의 다른 규칙이라 Strategy 의 「교체할 계산들」이 성립하고, 이 편의 선택 7번(한 협력 타입에 구현이 둘 이상)도 성립합니다. AuditLog 는 구현이 하나뿐이라 갈아 끼울 것이 없어 선택 7번이 빠지고, 통지 코드의 LoanRepository 처럼 의존성 주입이라는 이름만 남아요.

  3. 책임·순서. 시나리오 1 의 3단계에서 조립자가 하는 일을 쓰는 쪽으로 옮긴다고 해 봅시다. main 안에서 구현 셋을 직접 만들어 통지기 생성자에 넣는 식입니다. 이때 최소 조건 1~3번 가운데 빠지는 것이 있습니까? 없다면, 그래도 시나리오 2 의 2단계를 이 코드에 넣을 때 무엇이 달라지는지 한 문장으로 적으세요.

    풀이 보기

    풀이 — 필수 셋은 빠지지 않습니다. 통지기의 필드 타입은 그대로라 1번을 만족하고, 통지기 안에서 만드는 코드가 없으니 2번, 구현을 넣는 코드가 통지기 밖의 main 에 있고 통지기가 main 을 모르니 3번도 만족해요. 빠지는 것은 조립하는 코드와 쓰는 코드가 한 함수에 섞였다는 선택 6번뿐입니다(최소 조건 절 끝의 「잠깐, 하나만 확인해 볼까요」와 같은 판정). 달라지는 것은 시나리오 2 의 2단계예요 — 조립자 하나를 더 쓰는 대신 main 의 조립 줄과 청구 줄을 함께 복사해 시험용 진입점을 따로 써야 합니다. 시나리오 1 의 3단계가 조립자의 일을 거기서 끝낸 이유가 이것이었어요.
