한눈에 보는 개요

경비 청구를 받아 결재선에 올리는 코드를 하나 떠올려 봅시다. ExpenseDesk.submit(request) 가 금액을 보고 결재자를 고르는데, 10만 원 이하는 팀장, 100만 원 이하는 부서장, 1,000만 원 이하는 재무이사예요. 이 if 사슬을 한 곳에만 두면 다행인데 실제로는 영수증 화면·정산 배치·모바일 앱이 각자 같은 분기를 가지고 있습니다. 결재 한도가 바뀌거나 단계가 하나 늘면 그 세 곳을 함께 고쳐야 하고, 한 곳을 빠뜨리면 같은 청구가 화면마다 다른 사람에게 갑니다.

Chain of Responsibility 의 해법은 고르는 일을 없애고, 후보들을 한 줄로 세워 요청을 차례로 넘기는 것입니다. 요청을 내는 쪽은 줄의 맨 앞에게만 건네고, 각 후보가 「내가 맡을 일인가」를 스스로 보고 맡거나 다음으로 넘겨요. 누가 맡을지 고르던 분기는 어느 코드에도 남지 않고, 각 후보 안의 「내 한도인가」 한 줄로 흩어집니다.

Before : 요청을 내는 쪽마다 누가 맡을지 고르는 분기를 가지고 있음

  submit(request)
    if      (금액 ≤ 100,000)    팀장.approve(request)
    else if (금액 ≤ 1,000,000)  부서장.approve(request)
    else if (금액 ≤ 10,000,000) 재무이사.approve(request)
    else                        throw
  ← 같은 분기가 영수증 화면 · 정산 배치 · 모바일 앱에 복제돼 있다

After : 후보를 한 줄로 세우고, 맡을 수 있는 쪽이 맡는다

  submit(request) ──▶ [영수증 검사] ──▶ [팀장] ──▶ [부서장] ──▶ [재무이사] ──▶ (끝)
                          │               │           │             │            │
                       못 맡으면        못 맡으면    맡는다!      여기까지        아무도
                       다음으로         다음으로    → 멈춘다     오지 않음       안 맡으면
                                                                               처리 안 됨

분류는 행위 패턴이고 줄여서 CoR 이라고도 씁니다. 함께 쓰는 패턴은 Composite(근거: GoF Chain of Responsibility 절 Related Patterns — GoF 는 Gang of Four 의 줄임말로, 1994년에 나온 Design Patterns 의 저자 네 명을 함께 부르는 이름) 와 Command(refactoring.guru — Chain of Responsibility) 예요.

이 글은 시나리오 셋을 따라갑니다. 청구 하나가 결재선을 타고 내려가다 어디선가 멈추는 길, 새 규정이 더해질 때 어디에 끼우느냐가 결과를 어떻게 바꾸는가, 맡고도 넘기거나 부르는 쪽이 고르거나 다음 자리를 좁히면 어디서 어긋나는가. 끝까지 읽으면 어떤 코드를 Chain of Responsibility 라고 불러도 되는지 필수 조건 다섯으로 판정할 수 있고, 구조가 거의 같은 Decorator 코드와도 구분할 수 있게 됩니다.

시나리오 1 — 청구 하나가 결재선을 타고 내려가다 멈추는 길

경비 청구 R2 가 들어왔습니다. 금액은 700,000원이고 영수증은 첨부돼 있어요. 이 회사의 결재선은 셋입니다. 팀장은 100,000원까지, 부서장은 1,000,000원까지, 재무이사는 10,000,000원까지 결재해요. 나와야 하는 것은 「부서장이 승인했다」 한 줄입니다. 이 장면에는 넷이 등장해요. 청구를 만들어 결재선에 올리는 조립 코드(패턴에서는 Client 라고 부르는 역할), 차례로 이어진 결재 담당 셋(각각 ConcreteHandler), 그리고 그 셋이 공통으로 따르는 처리 연산의 모양 handle(청구)(Handler)입니다. 이름은 여기서 한 번씩만 소개하고 정식 정의는 개념 정리에서 해요.

  1. 조립 코드가 팀장 → 부서장 → 재무이사 순서로 셋을 이어 사슬 하나를 만듭니다. 순서를 정하는 일을 조립 코드가 맡는 이유는 결재선이 사내 규정이고, 규정을 아는 쪽만 누가 앞이고 누가 뒤인지 판단할 수 있어서예요. 이 순서를 결재 담당 자신이 정하게 하면 팀장이 부서장을 이름으로 알아야 하고, 규정이 바뀔 때마다 결재 담당 클래스를 열게 됩니다.
  2. 조립 코드가 사슬의 첫 후보에게만 청구 R2 를 건넵니다. 첫 후보에게만 건네는 이유는 이 코드가 누가 맡을지 모른 채로 요청할 수 있어야 해서예요. 여기서 금액을 보고 부서장을 직접 부르면 개요의 Before 그림에 있던 if 사슬이 그대로 돌아옵니다.
  3. 팀장이 청구를 받아 700,000원과 자기 한도 100,000원을 견줍니다. 넘으므로 맡지 않고, 받은 그 청구를 그대로 다음 후보에게 넘겨요. 한도 판단을 팀장 안에 두는 이유는 그 한도가 팀장의 권한이라서입니다. 판단을 밖으로 빼면 다시 2단계에서 없앤 분기가 생기고, 청구를 바꿔서 넘기면 뒤 후보가 다른 사실을 보고 판단하게 됩니다.
  4. 부서장이 같은 청구를 받아 700,000원과 자기 한도 1,000,000원을 견줍니다. 이번에는 한도 안이라 자기 일로 보고 승인해요. 3단계와 4단계가 같은 청구에 다른 답을 낸 것이 이 패턴의 핵심입니다. 부르는 쪽은 아무것도 고르지 않았는데 답이 달라졌어요.
  5. 부서장은 승인한 뒤 다음 후보를 부르지 않습니다. 여기서 멈추지 않으면 재무이사도 같은 청구를 받아 자기 한도 안이라며 또 승인하고, 전표가 둘이 됩니다. 시나리오 3 의 첫 갈래에서 그 상태를 실제로 실행해 봐요.
  6. 승인 결과가 조립 코드로 돌아옵니다. 결과를 받는 자리가 진입점 하나인 이유는 2단계에서 건넨 곳이 거기뿐이기 때문이에요. 누가 맡았는지는 결과 문자열에 담겨 오고, 조립 코드는 그 이름을 미리 알 필요가 없습니다.

영수증 검사가 없는 이 사슬에 청구 다섯을 넣고 Java 21 로 실제로 실행한 결과입니다. seen= 칸이 그 청구를 실제로 본 후보를 순서대로 적은 것이에요.

R1 80000 seen=TeamLead -> TeamLead approved
R2 700000 seen=TeamLead>DeptHead -> DeptHead approved
R3 5000000 seen=TeamLead>DeptHead>Finance -> Finance approved
R4 30000000 seen=TeamLead>DeptHead>Finance -> unhandled
R5 80000 seen=TeamLead -> TeamLead approved

잠깐, 확인 하나만 해 볼까요? R1(80,000원)의 seen= 칸에 왜 DeptHead 와 Finance 가 없을까요?

팀장이 3단계 자리에서 바로 맡고 멈췄기 때문입니다. 부서장과 재무이사는 R1 이라는 청구가 있었다는 사실조차 모르고, 그래서 둘의 코드를 아무리 읽어도 R1 이 어떻게 처리됐는지 알 수 없어요. 반대로 R4 는 seen= 에 셋이 다 있는데 결과는 unhandled 입니다. 「끝까지 갔다」와 「처리됐다」가 다른 말이라는 것이 이 두 줄에 같이 들어 있어요.

R430,000,000팀장 · 부서장 · 재무이사처리 안 됨마지막 후보가 다음이 없어서 끝냄

이 시나리오가 보여 준 것은 역할 셋과 요청이 전달되는 방향입니다. 사슬을 잇고 첫 후보에게 건네는 일(1·2단계)은 Client 가, 맡을지 말지 판단하고 맡거나 넘기는 일(3·4단계)은 ConcreteHandler 가 하고, 그 판단을 밖에서 부를 수 있게 해 주는 것이 Handler 라는 공통 연산 모양이에요. 그리고 이 사슬이 끝나는 길은 둘입니다 — 누군가 맡아서 멈추거나(5단계), 아무도 맡지 않은 채 끝에 이르거나(R4). 두 번째 길이 있다는 것이 「수신 보장 없음」이라는 대가의 실체입니다.

위 출력에서 따로 봐 둘 청구가 둘 있습니다. R4(30,000,000원)는 세 한도를 모두 넘어, 마지막 후보인 재무이사가 다음 후보가 없는 것을 보고 그대로 끝내요. 이렇게 아무도 맡지 않은 채 사슬 끝에 이르는 것을 이 글에서는 처리되지 않은 끝이라고 부릅니다. 오류가 아니라 이 사슬의 정상 종료예요(근거: GoF Chain of Responsibility 절 Consequences). R5(80,000원)는 영수증이 없는데, 지금 사슬에는 그것을 볼 후보가 없어서 팀장이 금액만 보고 승인해 버립니다. 이 빠진 부분을 채우는 것이 시나리오 2 예요.

시나리오 2 — 영수증 규정이 더해질 때, 어디에 끼우느냐가 답을 바꾼다

감사에서 지적이 하나 나왔습니다. 영수증이 첨부되지 않은 청구가 승인된 건이 있다는 거예요. 새 규정은 「영수증이 없으면 금액과 상관없이 결재선에 올리지 않고 그 자리에서 반려한다」 한 줄입니다. 시험할 청구는 R5, 금액 80,000원에 영수증 없음이고, 지금 사슬에 넣으면 시나리오 1 에서 본 R5 줄처럼 TeamLead approved 가 나옵니다. 나와야 하는 것은 rejected(no-receipt) 예요.

  1. 개발자가 영수증 검사 후보 클래스를 하나 새로 씁니다. 처리 연산의 모양은 시나리오 1 의 handle(청구) 그대로이고, 안에 든 판단만 「영수증이 없으면 내가 맡아 반려하고, 있으면 다음으로 넘긴다」예요. 연산 모양을 바꾸지 않는 이유는 그 모양이 사슬에 놓인 모든 후보와 부르는 쪽 사이의 계약이라서입니다. 모양이 바뀌면 기존 결재 담당 셋과 조립 코드가 전부 따라 바뀌어요.
  2. 조립 코드에서 사슬을 잇는 줄 하나를 고쳐 새 후보를 맨 앞에 끼웁니다. 맨 앞인 이유는 이 규정이 「결재선에 올리기 전에」 걸러야 하는 것이기 때문이에요. 이 한 줄 말고는 아무것도 바뀌지 않습니다.
  3. 기존 결재 담당 셋과 Handler 선언, 그리고 청구를 내는 코드는 한 줄도 바뀌지 않습니다. 결재 담당들이 서로를 이름으로 알지 않고 「다음 후보」라는 공통 타입으로만 알기 때문이에요. 시나리오 1 의 1단계에서 순서를 조립 코드가 맡은 것이 여기서 효과를 냅니다.
  4. R5 를 넣으면 맨 앞의 영수증 검사가 맡아 반려하고 멈춥니다. 여기서 「맡았다」는 것이 「승인했다」는 뜻이 아니라는 점을 봐 두세요. 맡는다는 것은 이 요청에 대한 답을 내가 낸다는 뜻이고, 그 답이 반려일 수도 있습니다.
  5. 같은 후보를 팀장 뒤에 끼우면 R5 의 답이 달라집니다. 팀장이 먼저 80,000원을 보고 자기 한도 안이라며 승인한 뒤 멈추므로, 영수증 검사는 불리지도 않아요. 시나리오 1 의 5단계에서 본 「맡으면 멈춘다」가 여기서는 검사를 건너뛰게 만듭니다. 사슬의 순서는 취향이 아니라 결과를 정하는 설계예요.

두 배치를 각각 Java 21 로 컴파일해 실행한 결과입니다. 바꾼 곳은 조립 코드에서 사슬을 잇는 네 줄뿐이고 후보 클래스는 손대지 않았어요.

여기서 헷갈리기 쉬운 포인트는 사슬에 후보를 더하는 일이 늘 안전하다고 믿는 것입니다. 새 후보를 더하는 것 자체는 기존 코드를 건드리지 않지만, 그 자리에 따라 기존 후보가 보던 요청이 사라질 수 있어요. 위 두 번째 출력의 R2 줄을 보면 영수증 검사가 팀장과 부서장 사이에 들어가면서 부서장이 청구를 받기 전에 한 단계가 더 생겼습니다. 이번에는 통과했지만, 영수증 검사가 맡아 버리는 청구였다면 부서장은 그 청구를 못 봤을 거예요. 사슬에 후보를 끼우는 것은 목록에 항목을 더하는 일이 아니라 요청이 지나는 길을 바꾸는 일입니다.

이 시나리오가 보여 준 것은 변화의 범위와 순서의 무게입니다. 새 규정이 들어올 때 바뀌는 곳은 새 ConcreteHandler 하나와 조립 코드에서 사슬을 잇는 줄이고, 기존 후보와 Handler 선언과 요청을 내는 코드는 그대로예요(1~3단계). 대신 그 한 줄이 어디에 놓이느냐가 같은 입력에 다른 답을 냅니다(5단계). Strategy 에서는 새 구현을 더해도 기존 구현의 동작이 바뀌지 않지만, 사슬에서는 앞에 놓인 후보가 뒤에 놓인 후보의 입력을 가로챌 수 있어요.

시나리오 3 — 맡고도 넘기거나, 부르는 쪽이 고르거나, 다음 자리를 좁히면 어디서 어긋나는가

같은 회사의 다른 코드베이스는 결재선을 조금 다르게 짰습니다. 세 갈래를 차례로 따라가 볼게요. 청구는 시나리오 1 과 같은 R1(80,000원)·R2(700,000원)이고, 아래 결과는 전부 실제로 컴파일하거나 실행해 받은 것입니다(실행은 Java 21, 5단계의 진단은 세 언어의 컴파일러).

  1. 첫 갈래는 결재 담당이 승인한 뒤에도 다음 후보를 계속 부르게 한 코드입니다. 「어차피 위 결재자도 알아야 하니까」라는 이유로 그렇게 짜는 일이 실제로 있어요. 시나리오 1 의 5단계에서 멈춘 그 호출을 분기 밖으로 꺼내 늘 실행되게 하면 됩니다.
  2. 그 코드에 R1(80,000원)을 넣으면 팀장·부서장·재무이사가 전부 승인합니다. 출력이 TeamLead approved+DeptHead approved+Finance approved+unhandled 예요. 전표를 만드는 코드가 이 결과를 받으면 8만 원짜리 청구에 결재 도장이 셋 찍힙니다. 어긋나는 자리는 「승인한다」가 아니라 「멈춘다」였어요 — 각 후보의 판단은 멀쩡히 실행됐는데 멈출 권한을 쓰지 않은 것만으로 틀린 결과가 나옵니다.
  3. 둘째 갈래는 조립 코드가 금액을 보고 결재자를 직접 고르는 코드입니다. 개요의 Before 그림 그대로예요. 컴파일도 되고 R1·R2 의 결과도 맞습니다. 문제가 생기는 것은 시나리오 2 가 들어올 때예요 — 영수증 검사는 금액으로 고를 수 있는 후보가 아니라서 이 if 사슬에 끼울 자리가 없고, 결국 모든 호출부의 분기 앞에 영수증 검사 한 줄을 각각 더하게 됩니다.
  4. 셋째 갈래는 사슬을 잇는 자리의 타입을 공통 선언이 아니라 구체 클래스로 좁힌 코드입니다. 「어차피 결재자만 들어오니까」라며 다음 후보의 타입을 LimitApprover 로 적어 두는 경우예요. 이 코드는 지금은 그대로 컴파일되고 실행 결과도 같습니다. 최소 조건으로 재도 [필수] 1~5번은 그대로 만족하고 [선택] 6번만 빠지므로, 앞의 두 갈래와 달리 「이 패턴이 아니게 되는」 코드는 아니에요. 문제는 시나리오 2 의 2단계를 하려고 할 때 나타납니다.
  5. 좁힌 타입에 영수증 검사를 끼우려 하면 Java 는 incompatible types: ReceiptCheck cannot be converted to LimitApprover 로 1건, TypeScript 는 error TS2345: Argument of type 'ReceiptCheck' is not assignable to parameter of type 'LimitApprover' 로 1건, Rust 는 error[E0308]: mismatched types 로 1건 멈춥니다. 셋 다 사슬을 잇는 그 줄 하나에서 나요. 타입을 좁힌 시점이 아니라 새 종류의 후보를 끼우려는 시점에 걸린다는 것이 이 갈래의 교훈입니다.

세 갈래가 각각 무엇을 어겼고 어디서 나타나는지 모으면 이렇습니다.

갈래            무엇을 한 코드인가              나타나는 곳
──────────────  ────────────────────────────  ──────────────────────────────────────
1·2단계         맡은 뒤에 멈추지 않음           R1 에 승인이 셋 (실행 결과)
3단계           고르는 판단이 부르는 쪽에 있음   새 종류의 후보를 끼울 자리가 없음
4·5단계         다음 자리를 구체 타입으로 좁힘   새 후보를 끼울 때 컴파일이 막음

이 시나리오가 보여 준 것은 문제가 나타나는 시점과 무게가 저마다 다르다는 것입니다. 멈추지 않는 코드는 실행 결과가 바로 틀리고(2단계), 부르는 쪽이 고르는 코드는 지금은 맞지만 다음 변경에서 막히고(3단계), 타입을 좁힌 코드는 [필수] 를 어기지 않는 대신 새 후보를 끼우려는 순간 컴파일러가 잡아 줍니다(5단계). 앞 둘은 이 패턴이 아니게 되는 코드이고, 타입을 좁힌 쪽은 이 패턴이되 넓히지 못하는 코드예요. 셋 중 가장 위험한 것은 둘째입니다. 컴파일도 되고 결과도 맞아서 코드 리뷰를 그냥 통과하는데, 그 분기가 복제된 호출부가 늘어난 뒤에야 비용이 나타납니다.

개념 정리

시나리오에 나온 역할 셋을 정식으로 정의합니다. Handler 와 ConcreteHandler 는 이 패턴의 참여자이고, Client 는 사슬을 만들고 요청을 건네는 쪽이라 참여자 목록에 함께 실려요(근거: GoF Chain of Responsibility 절 Participants).

  • Handler — 사슬에 놓일 수 있는 모든 후보가 따르는 요청 처리 연산을 선언합니다. 요청을 내는 쪽과 앞선 후보는 이 선언만 보고 부르므로, 뒤에 어떤 후보가 있는지 몰라도 돼요(시나리오 1 의 2·3단계). 다음 후보를 가리키는 링크를 여기에 둘 수도 있지만 그것은 선택입니다 — 최소 조건 6번에서 다뤄요. 경비 예에서는 청구를 받아 결과 문자열을 돌려주는 연산 handle(청구) 하나를 선언한 ApprovalHandler 가 Handler 입니다.
  • ConcreteHandler — Handler 가 선언한 연산을 구현해, 받은 요청이 자기 책임인지 판단하고 맡거나 다음 후보에게 넘깁니다(시나리오 1 의 3·4단계). 다음 후보에게 가는 길을 알고 있지만 그 후보가 누구인지는 공통 타입으로만 압니다. 같은 사슬에 놓인 다른 ConcreteHandler 들과 서로를 알지 않아요. 경비 예에서는 영수증 검사 ReceiptCheck 와 한도 결재자 LimitApprover 가 ConcreteHandler 이고, 팀장·부서장·재무이사는 한도만 다른 LimitApprover 세 인스턴스예요.
  • Client — 후보들을 순서대로 이어 사슬을 만들고(시나리오 1 의 1단계), 사슬의 진입점에만 요청을 건넵니다(2단계). 어느 후보가 맡을지는 지정하지 않고 알지도 못해요. 경비 예에서는 사슬을 잇는 buildChain 과 청구를 넣고 결과를 찍는 submit, 그리고 진입점이 Client 입니다.

그림에서 ConcreteHandler 에서 Handler 로 화살표가 두 개 나간다는 점을 봐 두세요. 하나는 「나는 이 연산 모양을 구현한다」이고 다른 하나는 「나는 이 타입의 다음 후보를 가진다」입니다. 한 칸이 두 관계를 함께 가지기 때문에 후보 뒤에 다른 후보가 오고, 그 뒤에 또 다른 후보가 올 수 있어요. 다음을 가리키는 쪽의 0..1 은 다음이 없을 수도 있다는 뜻이고, 그 자리가 시나리오 1 의 R4 가 처리되지 않은 끝에 이르던 지점입니다. 후보들이 요청을 서로에게 넘긴다는 관계를 이르는 말이 위임인데, 그 정의는 참고 문서 「GoF 공통 어휘」의 「위임」 항목에 있어요.

다음이 누구인지는 몰라도 되고, 다음이 없어도 된다. 없으면 요청은 처리되지 않은 채 끝난다.

사용 목적

Chain of Responsibility 가 필요할 때는 코드나 요구에서 보이는 단서가 있습니다. 넷을 차례로 봅시다.

단서 1 — 같은 if … else if … 사슬이 여러 호출부에 복제돼 있고, 조건이 하나 늘 때마다 그것을 전부 고칩니다

개요의 Before 그림이 그 모양이에요. 코드에서는 같은 조건식이 파일 셋 이상에 나타나고, 변경 이력에서 그 셋이 늘 한 커밋에 함께 오르는 것으로 보입니다. 요청을 처리할 수 있는 객체가 여럿이고 누가 처리할지를 부르는 쪽이 미리 알 필요가 없을 때가 이 패턴이 겨냥하는 자리예요(근거: GoF Chain of Responsibility 절 Applicability).

변경 이력                        수정된 곳
──────────────────────────────   ──────────────────────────────────────
부서장 한도 100만 → 300만         ExpenseDesk · ReceiptScreen · MobileApi
본부장 결재 단계 신설             ExpenseDesk · ReceiptScreen · MobileApi
접대비 전용 결재선 추가           ExpenseDesk · ReceiptScreen · MobileApi

단서 2 — 요청을 받을 대상과 그 순서가 설정이나 배포마다 다르고, 운영 중에 바뀌어야 합니다

회사마다 결재선이 다르고 조직 개편 때마다 단계가 늘고 줄어드는 상황이 그것이에요. 코드에서는 처리 대상을 고르는 분기가 설정 파일 값에 따라 갈리고, 그 설정 값의 가짓수가 계속 늘어나는 모양으로 보입니다. 사슬은 실행 중에 이어 붙이고 끊을 수 있으므로 이 변화를 조립 코드 한 곳에서 처리합니다(근거: GoF Chain of Responsibility 절 Applicability).

단서 3 — 정해진 순서로 여러 검사를 지나야 하고, 앞 검사가 뒤 단계로 가지 못하게 막을 수 있어야 합니다

인증 → 권한 → 한도 → 실제 처리 같은 흐름이에요. 여기서 중요한 것은 「순서대로 지난다」가 아니라 「막을 수 있다」 입니다. 막을 필요가 없고 모든 단계가 항상 실행돼야 한다면 그것은 사슬이 아니라 겹겹이 감싼 층이고, 경계 절에서 Decorator 와 가르는 자리가 바로 여기예요.

화면 위젯이 부모 위젯을 알고, 트리 노드가 부모 노드를 아는 경우예요. 이때는 후보를 잇는 링크를 새로 만들 필요가 없습니다. 이미 있는 부모 참조가 그대로 다음 후보를 가리키는 링크가 되거든요(근거: GoF Chain of Responsibility 절 Implementation). 비교 절의 Composite 항목에서 이 겹침을 따로 다룹니다.

쓰지 말아야 할 경우

비슷한 단서에서 다른 패턴을 골라야 하는 경우가 셋 있습니다. 모든 층이 반드시 실행돼야 하면 Decorator 를, 등록된 모두가 같은 사건에 각자 반응해야 하면 Observer 를, 여러 객체 사이의 협력 규칙 자체를 한 곳에 모아야 하면 Mediator 를 먼저 검토하세요. 셋과의 차이는 「비슷한 패턴·안티패턴과의 차이」에서 풉니다. 그리고 아래 상황에서는 이 패턴을 쓰면 얻는 것보다 잃는 것이 커요.

쓰지 말아야 할 상황쓰면 잃는 것
요청이 반드시 처리돼야 하는데 사슬 끝에 늘 맡는 후보를 둘 수 없음처리된다는 보장. 시나리오 1 의 R4 처럼 아무도 맡지 않으면 요청이 조용히 끝나고, 부른 쪽은 그것을 결과로 구분해 내야 함(근거: GoF Chain of Responsibility 절 Consequences)
처리자가 늘 하나로 정해져 있음읽기 쉬움. 후보가 하나뿐이면 사슬을 만들 이유가 없고, 공통 타입·다음 참조·넘기는 코드만 늘어남
누가 처리했는지 호출 한 번으로 추적해야 함흐름을 한곳에서 읽는 일. 시나리오 1 에서 실행한 결과에 seen= 칸을 따로 둔 이유가 이것이고, 그 칸이 없으면 어느 후보가 맡았는지 알려면 후보를 전부 읽어야 함
등록된 모두가 같은 사건에 반응해야 함전원 통지. 하나가 맡고 멈추면 뒤 후보는 그 요청을 아예 못 봄 → Observer 가 맡을 자리

패턴의 경계

디자인 패턴을 충족하는 최소 조건

어떤 코드를 Chain of Responsibility 라고 불러도 되는지 가르는 기준입니다. [필수] 가 하나라도 빠지면 이 패턴이 아니고, [선택] 은 갖추면 좋거나 상황에 따라 고르는 구조예요. 조건은 언어와 상관없이 코드에서 확인할 수 있는 모양(타입 선언·참조 보유·호출 방향·생성 위치)으로 적었고, 조건마다 그것을 보여 준 시나리오의 단계를 가리킵니다. [필수] 마다 근거가 받치는 범위: 줄에 그 근거가 어디까지 받쳐 주는지를 따로 적었어요 — 근거가 받치지 않는 부분을 필수로 올리면 원전 기준으로는 이 패턴인 코드가 「아님」으로 잘립니다.

  1. [필수] 같은 연산 모양을 따르는 후보 둘 이상과 정해진 순서 — 후보들이 공통 선언이 정한 처리 연산을 구현하고, 누가 먼저이고 누가 다음인지가 코드에 고정돼 있습니다. 시나리오 1 의 1단계 (근거: GoF Chain of Responsibility 절 Intent — 둘 이상의 객체에 요청을 처리할 기회를 주고 받는 객체들을 사슬로 엮는다 / Participants — Handler 가 요청 처리 인터페이스를 정의하고 ConcreteHandler 들이 그것을 구현한다)
    • 코드에 나타나는 모양: 공통 선언은 인터페이스·추상 클래스·trait(Rust 에서 타입이 구현할 연산을 선언하는 문법)·함수 타입이고, 순서는 다음 후보를 가리키는 참조의 연결 순서이거나 후보를 담은 목록의 순서입니다.
    • 근거가 받치는 범위: 위 근거 괄호가 받쳐 주는 것은 「후보가 둘 이상이다」·「공통 연산 모양이 있다」·「사슬로 엮여 순서가 있다」까지입니다. 그 순서를 무엇으로 표현하는지(후보가 가진 참조냐 목록이냐)도, 다음 후보를 가지는 자리의 타입이 무엇이어야 하는지도 근거가 정하지 않아요. 원전은 다음 후보로 가는 링크를 두는 것 자체를 선택으로 적었으니, 그 링크의 타입을 묻는 일은 더더욱 이 조건의 몫이 아닙니다. 둘 다 6번으로 내렸어요.
    • 빠지면: 후보가 늘 하나면 사슬이 아니라 단순 위임입니다. 공통 연산 모양이 없으면 부르는 쪽이 후보마다 다른 메서드 이름을 알아야 해서 5번도 함께 성립하지 않아요. 시나리오 2 의 1단계에서 새 후보가 기존 후보와 같은 연산 모양으로 들어온 것이 이 조건을 지킨 자리입니다.
  2. [필수] 맡을지는 후보가 스스로 정함 — 「내가 맡는가」를 가르는 분기가 후보의 처리 연산 안에 있고, 그 판단에 쓰는 기준(한도·권한·요청 종류)을 후보가 자기 안에 가지고 있습니다. 시나리오 1 의 3·4단계 (근거: GoF Chain of Responsibility 절 Participants — ConcreteHandler 는 자기가 책임질 수 있는 요청을 처리하고 그렇지 못하면 다음으로 넘긴다)
    • 코드에 나타나는 모양: 시나리오 1 의 3단계와 4단계가 같은 청구에 다른 답을 낸 것은 이 분기가 후보마다 따로 있기 때문입니다.
    • 근거가 받치는 범위: 위 근거 괄호가 받쳐 주는 것은 「맡을지 말지의 판단이 후보 안에 있다」까지입니다. 부르는 쪽에 그 판단이 없어야 한다는 것은 5번이 따로 받아요 — 근거가 다릅니다.
    • 빠지면: 후보들이 판단 없이 시키는 일만 하면 그것은 사슬이 아니라 일꾼 목록이고, 고르는 쪽이 디스패처입니다. 시나리오 3 의 3단계가 그 모양이에요.
  3. [필수] 맡지 않으면 요청이 다음 후보로 이어짐 — 맡지 않은 경로에 다음 후보로 가는 길이 있고, 맡지도 넘기지도 않고 조용히 끝나는 길이 없습니다. 시나리오 1 의 3단계 (근거: GoF Chain of Responsibility 절 Participants — 처리할 수 없으면 다음 후보에게 전달한다 / Collaborations — 요청은 어떤 ConcreteHandler 가 책임을 맡을 때까지 사슬을 따라 전파된다)
    • 코드에 나타나는 모양: 넘기는 일을 후보가 직접 하든(다음 참조를 호출) 사슬을 대표하는 객체나 순회가 하든 같습니다.
    • 근거가 받치는 범위: 위 근거 괄호가 받쳐 주는 것은 「맡지 않으면 다음으로 간다」와 「사슬을 따라 전파되는 것이 그 요청이다」까지입니다. 그 넘김을 누가 부르는가는 근거가 정하지 않아요 — 원전 스스로 다음 참조를 후보가 보유하는 것을 선택으로 적었기 때문에, 순회가 다음 차례로 넘어가는 형태도 이 조건을 만족합니다.
    • 빠지면: 맡지도 않고 넘기지도 않는 후보가 하나 있으면 요청이 그 자리에서 사라집니다. 부르는 쪽은 「아무도 맡지 않음」과 구분할 수 없어서 시나리오 1 의 R4 와 같은 처리되지 않은 끝을 받고, 뒤에 있는 후보는 영영 불리지 않아요.
  4. [필수] 한 후보가 맡으면 뒤 후보는 같은 요청을 받지 않음 — 다음 후보를 부르는 호출이 분기 아래에 있어 실행되지 않는 길이 코드에 있거나, 순회에 조기 종료가 있습니다. 시나리오 1 의 5단계 (근거: GoF Chain of Responsibility 절 Intent — 어떤 객체가 요청을 처리할 때까지 사슬을 따라 넘긴다 / Participants — 처리할 수 있으면 처리하고 그렇지 않으면 넘긴다는 둘 중 하나다)
    • 코드에 나타나는 모양: 모든 후보가 무조건 다음을 부르는 코드에는 그 길이 없어요. 시나리오 1 에서 실행한 R1 의 seen= 칸에 팀장 하나만 찍힌 것이 그 길이 실행된 증거입니다.
    • 근거가 받치는 범위: 위 근거 괄호가 받쳐 주는 것은 「처리될 때까지 넘긴다」와 「처리 아니면 전달」까지입니다. 맡은 후보가 답을 낸 뒤에 기록 같은 부가 작업을 더 해도 되는지는 근거가 말하지 않아서 조건이 묻지 않아요. 다만 「맡고도 계속 넘기는」 변형은 이 조건이 걸러 냅니다 — 아래에서 따로 다룹니다.
    • 빠지면: 모든 층이 무조건 다음을 부르면 그것은 Decorator 이거나 그냥 파이프라인입니다. 시나리오 3 의 1·2단계가 그 상태이고, R1 한 건에 승인이 셋 찍혔어요.
  5. [필수] 요청을 내는 쪽은 진입점만 알고 누가 맡을지 지정하지 않음 — 요청을 내는 코드의 호출 자리에 후보의 구체 타입 이름이 나오지 않고, 호출이 진입점 하나(첫 후보이거나 사슬을 대표하는 객체)에만 갑니다. 시나리오 1 의 2·6단계 (근거: GoF Chain of Responsibility 절 Intent — 요청을 보내는 쪽과 받는 쪽의 결합을 피한다 / Participants — Client 는 사슬 위의 ConcreteHandler 에게 요청을 개시한다 / Consequences — 결합이 느슨해져 보내는 쪽도 받는 쪽도 서로를 명시적으로 알지 않아도 된다)
    • 근거가 받치는 범위: 위 근거 괄호가 받쳐 주는 것은 「보내는 쪽이 받는 쪽을 명시하지 않는다」와 「요청은 사슬 위의 한 후보에게 개시된다」까지입니다. 그 진입점이 반드시 첫 후보여야 하는지는 근거가 정하지 않아서, 사슬을 대표하는 객체를 두고 그것에 요청을 건네는 형태도 이 조건을 만족해요.
    • 빠지면: 부르는 쪽이 금액을 보고 결재자를 골라 직접 부르면 그것은 사슬이 아니라 디스패처입니다. 시나리오 3 의 3단계가 그 모양이고, 새 종류의 후보를 더할 자리가 없어 분기가 호출부마다 복제돼요.
  6. [선택] 다음 후보 참조를 공통 타입 필드로 보유 — 후보 안에 1번의 공통 선언 타입으로 적힌 필드가 하나 있고, 그 값을 만들거나 설치하는 자리가 조립 코드입니다. 시나리오 1 의 1단계 (근거: GoF Chain of Responsibility 절 Participants — 다음 후보로 가는 링크를 Handler 가 구현하는 것을 선택으로 적었다 / Implementation — 링크를 새로 만들지 않고 이미 있는 링크(Composite 의 부모 참조 같은)를 쓰는 길도 든다)
    • 빠지면: 이 필드의 타입을 구체 클래스로 좁히면(시나리오 3 의 4·5단계) 1~5번은 그대로 만족하지만 이 항목이 빠지고, 그 대가로 새 종류의 후보를 사슬에 끼울 수 없게 됩니다.
    • 경계 사례: 컨테이너가 넘겨주는 사슬 객체로 다음을 부르는 형태나, 목록을 따라가는 순회가 다음 차례로 넘기는 형태도 1·3번을 만족하므로 이 항목이 없어도 패턴입니다.
  7. [선택] 공통 기본 구현이 판단 없이 다음으로 넘김 — 추상 클래스나 기본 구현에 넘기는 코드를 한 번만 써 두어, 관심 없는 후보는 그 연산을 다시 쓰지 않아도 됩니다. 시나리오 2 의 1단계 (근거: GoF Chain of Responsibility 절 Implementation — 기본 전달 동작을 Handler 에 두면 관심 없는 서브클래스가 재정의하지 않아도 된다)
    • 코드에 나타나는 모양: 시나리오 2 의 1단계에서 새 후보가 「다음으로 넘긴다」를 다시 짜지 않고 판단만 새로 쓴 것이 이 모양이에요.
  8. [선택] 사슬 끝에 늘 맡는 기본 후보 — 마지막 자리에 조건 없이 맡는 후보를 하나 두면 요청이 처리되지 않고 끝나는 일이 없어집니다. 시나리오 1 의 R4 (근거: 이 가이드의 정책 — 원전이 든 대가 「수신 보장 없음」을 줄이는 수단이지 패턴의 성립 요건은 아니라서 선택에 둡니다)
    • 빠지면: 시나리오 1 의 R4 처럼 처리되지 않은 끝에 이를 수 있습니다.
  9. [선택] 요청을 객체 하나로 표현 — 처리 연산이 값 여럿을 따로 받지 않고 요청 객체 하나를 받으면, 새 후보가 필요로 하는 정보를 더할 때 사슬 전체의 연산 모양을 바꾸지 않아도 됩니다. 시나리오 2 의 1단계 (근거: GoF Chain of Responsibility 절 Implementation — 요청을 표현하는 방식으로 고정된 연산 호출, 요청 코드와 조건 분기, 별도 요청 객체 셋을 들고 마지막이 가장 확장적이라고 적는다)
    • 코드에 나타나는 모양: 시나리오 2 의 1단계에서 영수증 여부를 새 후보가 읽을 수 있었던 것이 이 덕분이에요.
  10. [선택] 사슬은 유한하고 자기 자신을 다시 가리키지 않음 — 조립 코드가 만든 연결을 따라가면 반드시 끝에 이르고, 같은 후보를 두 번 지나지 않습니다. 시나리오 1 의 R4 (근거: 이 가이드의 정책 — 원전은 이 불변식을 따로 적지 않지만, 순환하는 사슬에서는 아무도 맡지 않는 요청이 끝나지 않고 돌아 5번이 보장하려던 「요청을 걸면 답이 온다」가 성립하지 않습니다)
    • 경계 사례: 시나리오 1 의 R4 가 사슬 끝에 이르러 끝날 수 있었던 것은 연결이 유한했기 때문입니다.

4번이 가장 자주 틀리는 자리라 조금 더 봅시다. 「맡았다」와 「계속 넘긴다」를 함께 하는 변형이 실무에 흔하기 때문이에요. Java 표준 라이브러리의 java.util.logging.Logger 가 그 예인데, 기본 설정에서 로거는 자기 핸들러로 기록을 내보낸 뒤에도 부모 로거로 계속 올려 보냅니다(Java SE(Standard Edition) 21 — Logger). 멈출지 말지는 setUseParentHandlers 로 로거마다 한 번 정하는 설정이고, 기록 한 건을 보고 내리는 판단이 아니에요. 그래서 이 가이드의 4번으로 재면 기본 설정의 로거 전파는 「맡으면 멈춘다」가 아니라 「전부 거쳐 간다」이고, 사슬이 아니라 겹겹이 쌓인 층에 가깝습니다. refactoring.guru 는 이 API(Application Programming Interface, 라이브러리가 밖으로 내놓은 호출 규약)를 이 패턴의 Java 사례로 들지만(refactoring.guru — Chain of Responsibility in Java), 이름을 붙인 출처가 있다는 것과 판정 기준을 통과한다는 것은 다른 말이에요.

// 사슬처럼 생겼지만 멈추지 않는다 — 조건 4번이 빠진다
@Override
public String handle(ExpenseRequest request) {
    request.visited(title);
    String rest = passToNext(request);                 // 늘 불린다
    if (request.amount() <= limit) {
        return title + " approved+" + rest;            // 맡고도 계속 넘겼다
    }
    return rest;
}

위 코드로 바꾸고 실제로 실행하면 R1(80,000원)의 결과가 TeamLead approved+DeptHead approved+Finance approved+unhandled 로 나옵니다(직접 컴파일해 확인). 각 후보의 한도 판단은 멀쩡히 실행됐는데도 8만 원짜리 청구에 결재가 셋 찍혔어요. 반대로 다섯 조건을 전부 만족하는 코드는 이름이 무엇이든 이 패턴입니다. 예를 들어 검증기 다섯을 순서대로 실행하다 첫 실패에서 멈추고 나머지를 부르지 않는 「검증 파이프라인」은 1~5번을 모두 통과하므로 이 가이드는 그것을 Chain of Responsibility 로 판정해요. 아무도 실패를 잡지 않고 끝나는 경우가 시나리오 1 의 R4 와 같은 처리되지 않은 끝이고, 그것이 곧 「전부 통과」라는 뜻일 뿐입니다.

부르는 쪽이 금액으로 결재자를 고르는 코드만족할 수 있음빠짐해당 없음 (넘기지 않음)해당 없음빠짐아님 — 디스패처
결재자 하나에게 늘 넘기는 코드빠짐 (후보가 하나)만족할 수 있음해당 없음해당 없음만족아님 — 단순 위임
맡지도 넘기지도 않는 후보가 낀 사슬만족만족빠짐만족만족아님 — 사슬이 끊김

[필수] 는 하나만 빠져도 판정이 끝나므로 1번부터 차례로 봅니다. 1번은 후보 쪽 타입 선언만, 2번은 후보의 처리 연산 안만, 3·4번은 다음을 부르는 호출이 어떤 분기 아래에 있는지만, 5번은 요청을 내는 코드만 보면 되어서 앞 조건에서 멈추면 뒤는 읽지 않아도 돼요. 표의 두 번째 줄과 세 번째 줄이 이 조건들의 성격을 잘 보여 줍니다. 둘 다 다음 후보 참조가 아예 없는데 판정은 이 패턴이에요 — 6번이 [선택] 이기 때문이고, 그 근거는 원전이 링크 보유를 선택으로 적은 자리입니다.

맡을 수 있는가는 후보가 정하고, 누가 먼저인가는 조립 코드가 정하고, 맡으면 멈춘다.

비슷한 패턴·안티패턴과의 차이

이 패턴과 구조가 닮았거나 같은 단서에서 떠오르는 대상 여섯을 비교합니다. Decorator 는 구조가 거의 같아 가장 먼저 보고, Observer 는 「여럿에게 차례로 보낸다」는 모양이 같아 그다음에 보며, Mediator 와 Command 는 보내는 쪽과 받는 쪽을 떼어 놓는 다른 방식이라 한 물음으로 묶습니다. Composite 는 경쟁 상대가 아니라 겹치는 관계라 따로 두고, 마지막으로 이 패턴으로 오해받는 디스패처 코드를 봐요.

비교 대상구분 기준 (코드에서 보는 것)이 패턴을 고르면 얻는 것포기하는 것
Decorator층이 전달을 멈출 수 있는가 — 다음 후보로 가는 호출이 실행되지 않는 길이 있는가(후보 안의 분기든, 순회의 조기 종료든)맡을 수 있는 하나가 처리하고 끝내는 흐름. 뒤 후보는 그 요청을 아예 안 봄모든 층이 반드시 실행된다는 보장. 바깥 층이 기록한 일이 안쪽에서 안 일어날 수 있음
Observer목록을 끝까지 순회하는가, 하나가 처리하면 멈추는가 — 루프에 조기 종료가 있는지, 연산이 「내가 처리했다」는 답을 돌려주는지「누군가 하나가 맡는다」는 모양. 뒤 후보를 부르지 않아 중복 처리가 없음전원 통지. 등록된 모두가 각자 반응하는 일은 사슬이 해 주지 않음
Mediator부른 쪽과 일하는 쪽 사이에 무엇을 끼워 넣어 떼어 놓는가 — 후보들의 줄인가, 제삼의 중재자인가후보를 실행 중에 이어 붙이고 끊는 일. 후보끼리 서로를 모름사건 하나에 여러 수신자를 각기 다르게 움직이는 조율
Command같은 물음 — 후보들의 줄인가, 수행할 요청을 담은 객체인가요청 하나를 맡을 수 있는 첫 후보가 받는 모양요청을 값으로 보관하며 미루고 쌓고 되돌리는 일
Composite배타 관계가 아님 — 트리의 부모 참조가 그대로 다음 후보 링크가 됨링크를 새로 만들지 않고 이미 있는 계층을 사슬로 씀없음. 둘은 함께 쓰인다
디스패처 (오해받는 코드)맡을지 말지의 판단이 후보의 답인가 부르는 쪽의 조건문인가새 종류의 후보를 더할 때 부르는 쪽을 열지 않음한 곳에서 읽히던 흐름. 누가 맡았는지 알려면 후보를 따라가야 함

표의 기준과 최소 조건은 답하는 물음이 다릅니다. 이 절의 기준은 「이 협력이 어느 갈래인가」를 가르고, 그 코드가 「유효한 사슬인가」는 최소 조건이 따로 봐요. 둘을 한 물음에 섞으면 엉뚱한 답이 나옵니다 — 예를 들어 맡지도 넘기지도 않는 후보가 하나 낀 사슬은 이 표의 Decorator 기준으로는 「멈출 수 있으니 이쪽」이지만, 최소 조건 3번으로 재면 사슬이 끊겨 있어 이 패턴이 아니에요. 표로 갈래를 고르고, 최소 조건으로 성립을 확인하세요.

Decorator 와의 차이

구분 기준은 층이 전달을 멈출 수 있는가, 곧 다음 후보로 가는 호출이 실행되지 않는 길이 있는가입니다. Decorator 가이드가 세운 기준을 반대 방향에서 그대로 받은 것이고, 그 가이드는 같은 물음으로 「조건을 보고 전달을 멈추는 층」을 자기 쪽이 아니라 이쪽이라고 판정합니다. 구조는 거의 같아요 — 같은 인터페이스를 구현한 객체들이 다음을 하나씩 가지고 한 줄로 이어져 있으니까요. 다른 점은 권한입니다. 데코레이터에게는 요청 흐름을 끊을 권한이 없고, 이쪽 후보는 맡으면 거기서 끝내는 것이 정상 동작이에요. 최소 조건 4번이 그 권한을 코드에서 확인하는 자리이고, Decorator 가이드의 최소 조건 3번은 정확히 그 반대(어떤 호출도 대상에 전달되지 않고 끝나는 일이 없음)를 요구합니다.

// Decorator — 다음을 부르는 호출이 분기 밖에 있다. 안 불리는 길이 없다
@Override
public String handle(ExpenseRequest request) {
    audit.record(request);                 // 앞에 붙인 책임
    return next.handle(request);           // 늘 불린다
}

// Chain of Responsibility — 다음을 부르는 호출이 분기 아래에 있다
@Override
public String handle(ExpenseRequest request) {
    if (request.amount() <= limit) {
        return title + " approved";        // 맡았다. next.handle 은 불리지 않는다
    }
    return passToNext(request);
}

두 코드를 놓고 보면 다른 줄이 하나입니다. 다음을 부르는 호출이 if 밖에 있느냐 안에 있느냐예요. 시나리오 1 의 5단계가 위쪽 모양이었다면 R1 의 seen= 칸에 세 결재자가 다 찍혔을 것이고, 실제로 시나리오 3 의 2단계에서 그렇게 됐습니다. 이 패턴을 고르면 맡을 수 있는 하나가 처리하고 끝내는 흐름을 얻고, 모든 층이 반드시 실행된다는 보장을 포기해요. Decorator 가이드가 「바깥 층이 이미 한 일과 안쪽에서 일어나지 않은 일이 어긋난다」고 적은 그 위험을 이쪽은 정상 동작으로 받아들이는 것이고, 그래서 사슬에서는 맡은 후보가 앞선 후보의 기록과 어긋나지 않도록 순서를 설계해야 합니다(시나리오 2 의 5단계).

Observer 와의 차이

구분 기준은 목록을 끝까지 순회하는지, 하나가 처리하면 멈추는지입니다. Observer 가이드가 고정한 코드 표식을 그대로 씁니다 — 통지 루프에 조기 종료가 있는지, 그리고 갱신 연산이 「내가 처리했다」는 답을 돌려주는지예요. 둘 다 보내는 쪽과 받는 쪽을 떼어 놓지만, 이쪽은 후보들 사이로 요청을 넘기다 하나가 맡으면 끝냅니다(근거: GoF 5장 행위 패턴 토론 — 잠재적 수신자들의 사슬을 따라 요청을 넘겨 보내는 쪽과 받는 쪽을 분리한다).

// Observer 의 순회 — 끝까지 돈다
void notifyObservers(ExpenseRequest request) {
    for (ExpenseObserver observer : observers) {
        observer.updated(request);           // 반환값이 없고 멈추지 않는다
    }
}

// Chain of Responsibility 의 순회 — 처리되면 멈춘다
String dispatch(List<ApprovalHandler> chain, ExpenseRequest request) {
    for (ApprovalHandler handler : chain) {
        String verdict = handler.tryHandle(request);   // 맡았는지를 답으로 받고
        if (verdict != null) {
            return verdict;                            // 하나가 맡으면 끝낸다
        }
    }
    return "unhandled";
}

아래쪽 모양을 실제로 짜서 실행해 봤습니다. 후보 넷을 List 에 담고 위 dispatch 로 R1~R5 를 넣은 프로그램이, 다음 후보 참조로 이은 시나리오 2 의 사슬과 글자 단위로 같은 다섯 줄을 냈어요(직접 컴파일·실행해 확인). 다음 후보 참조가 아예 없는데도 최소 조건 1~5번을 그대로 만족하고, 그래서 판정도 같습니다 — 최소 조건 6번이 [선택] 인 이유가 여기 있어요. 시나리오 1 의 5단계에서 부서장이 맡고 멈춘 것이 위 return verdict 자리이고, 그 if 를 지우면 그대로 Observer 의 순회가 됩니다. 이 패턴을 고르면 중복 처리가 없다는 것을 얻고, 등록된 전부가 각자 반응하는 전원 통지를 포기해요. 반대로 통지가 「알림」이지 「처리 요청」이 아니라면 사슬은 잘못된 도구입니다.

Mediator 와의 차이

이 패턴과 Mediator, 그리고 바로 뒤에서 볼 Command 는 모두 부른 쪽과 실제로 일하는 쪽을 떼어 놓습니다. Mediator 가이드와 Command 가이드가 함께 정한 물음을 이쪽에 적용하면 구분 기준은 이렇게 돼요 — 무엇을 끼워 넣어 떼어 놓는가.

부른 쪽 ──▶ [ 무엇을 끼웠나 ] ──▶ 일하는 쪽

  Chain of Responsibility   처리 후보들을 이은 줄       요청 하나를 처리할 수 있는 첫 후보가 받는다
  Mediator                  중재자라는 제삼의 객체      사건 하나에 여러 수신자를 각기 다르게 움직인다
  Command                   수행할 요청을 담은 객체     요청 하나를 담아 두었다가 실행하거나 되돌린다

시나리오 1 의 2단계로 보면 차이가 또렷합니다. 조립 코드는 진입점 하나에 청구를 건네고 그 뒤에 무엇이 있는지 모르는데, 끼워 넣은 것이 줄이라서 답은 그 줄 위의 어느 한 후보에게서 옵니다. 중재자를 끼웠다면 중재자 하나가 여러 동료를 각기 다르게 움직였을 거예요. 이 패턴을 고르면 후보를 실행 중에 이어 붙이고 끊는 일을 얻고, 사건 하나로 여러 수신자를 조율하는 일을 포기해요.

Command 와의 차이

구분 기준은 위와 같은 물음입니다. 끼워 넣은 것이 처리 후보들의 줄인가, 수행할 요청을 담은 객체인가예요. 시나리오 1 의 2단계에 커맨드를 끼웠다면 그 객체 안에 이미 받을 대상이 묶여 있었을 거예요. Command 의 세 역할(Invoker · Receiver · Command 객체)은 참고 문서 「GoF 공통 어휘」의 「Invoker · Receiver · Command 객체」에 정의가 있습니다. 이 패턴을 고르면 요청 하나를 맡을 수 있는 첫 후보가 받는 모양을 얻고, 요청을 값으로 쌓아 두고 미루거나 되돌리는 일을 포기해요.

셋은 배타적인 선택지가 아닙니다. 사슬을 타고 넘어가는 요청 자체를 커맨드 객체로 만들거나, 사슬에 놓인 후보를 커맨드로 구현하는 조합이 실제로 쓰여요(refactoring.guru — Chain of Responsibility). 최소 조건 9번이 바로 그 자리입니다 — 요청을 객체 하나로 표현하면 새 후보가 필요로 하는 정보를 더할 때 사슬 전체의 연산 모양을 바꾸지 않아도 되거든요. 중재자와도 겹칠 수 있습니다. 중재자가 받은 사건을 스스로 처리하지 않고 후보들의 줄로 넘기면 한 시스템 안에 둘이 함께 쓰여요. 그래서 위 물음은 「이 코드가 어느 패턴인가」를 가르는 것이지 「둘 중 하나만 써야 한다」는 뜻이 아닙니다.

겹쳐 쓰는 모양                                     이 가이드의 최소 조건으로 보면
─────────────────────────────────────────────    ────────────────────────────────────
사슬을 타고 넘어가는 요청을 커맨드 객체로 만든다      9번까지 갖춘 사슬 — 1~5번은 그대로
사슬에 놓인 후보를 커맨드로 구현한다                 후보의 속이 커맨드일 뿐 1~5번은 그대로
중재자가 받은 사건을 후보들의 줄로 넘긴다            중재자 안쪽에 사슬이 하나 생긴다

Composite 와의 차이

이쪽은 아예 경쟁 관계가 아니라 겹치는 관계예요. Composite 가이드가 개요에서 「자식이 부모를 거슬러 올라가며 요청을 넘기면 Chain of Responsibility 가 된다」고 적은 그 자리입니다(근거: GoF Composite 절 Related Patterns). 트리에서 자식 노드가 부모 노드를 알고 있으면 그 부모 참조가 그대로 다음 후보를 가리키는 링크가 되고, 링크를 새로 만들 필요가 없어요. 최소 조건 6번이 [선택] 인 두 번째 이유가 이것입니다.

Composite 트리                          같은 트리를 사슬로 읽으면

  Window                                  Window          ← 마지막 후보
    └ Panel                                 ↑ 부모 참조
        └ Button                          Panel           ← 두 번째 후보
                                            ↑ 부모 참조
  Button.parent = Panel                   Button          ← 첫 후보 (여기서 요청이 시작)
  Panel.parent  = Window

겹친다고 해서 최소 조건이 느슨해지지는 않습니다. 트리 구조가 있다는 것만으로는 이 패턴이 아니고, 요청을 받은 노드가 스스로 맡을지 판단하고(2번) 맡으면 부모를 부르지 않아야(4번) 이쪽입니다. 부모의 답을 늘 받아다 합치는 트리 순회는 Composite 의 집계이지 사슬이 아니에요. 시나리오 1 의 4·5단계가 그 차이를 보여 준 자리입니다.

디스패처와의 차이

구분 기준은 맡을지 말지의 판단이 후보의 답인지, 부르는 쪽의 조건문인지입니다. 같은 파일에 무엇이 들어 있는지나 클래스 이름에 Handler 가 붙었는지는 기준이 아니에요.

// Handler 라는 이름이 붙었지만 판단이 부르는 쪽에 있다 — 최소 조건 2·5번이 빠진다
final class ExpenseDesk {
    private final ApprovalHandler teamLead;
    private final ApprovalHandler deptHead;
    private final ApprovalHandler finance;

    String submit(ExpenseRequest request) {
        if (request.amount() <= 100_000) {            // 고르는 분기가 여기 있다
            return teamLead.handle(request);
        } else if (request.amount() <= 1_000_000) {
            return deptHead.handle(request);
        }
        return finance.handle(request);
    }
}

이 코드는 컴파일도 되고 R1·R2 의 결과도 시나리오 1 과 같습니다. 차이가 나는 것은 시나리오 2 가 들어올 때예요 — 영수증 검사는 금액으로 고를 수 있는 후보가 아니라서 이 if 사슬에 끼울 자리가 없고, 결국 분기 앞에 검사 한 줄을 따로 더하게 됩니다. 그 코드가 복제된 호출부만큼요. 이 패턴을 고르면 새 종류의 후보를 더할 때 부르는 쪽을 열지 않는 것을 얻고, 한 곳에서 읽히던 흐름을 포기해요. 누가 맡았는지 알려면 사슬을 따라가야 하므로, 시나리오 1 의 seen= 칸 같은 기록을 따로 두지 않으면 추적이 어려워집니다.

시나리오 1·2 의 경비 결재 장면을 세 언어로 똑같이 구현합니다. 청구 하나가 사슬을 타고 내려가 어느 후보에게서 답을 받거나 아무에게도 받지 못하는 것이 이 프로그램이 하는 일이에요.

  • 고정되는 것: 처리 연산의 모양(청구를 받아 결과 문자열을 반환함), 청구 데이터의 모양(청구 번호 · 원 단위 금액 · 영수증 첨부 여부 · 실제로 본 후보의 기록), 사슬을 잇는 방향(앞에서 뒤로 한 방향)
  • 바뀌는 것: 사슬에 놓이는 후보의 종류와 순서(영수증 검사 · 한도 결재자 셋)와 각 한도 값
  • 입력 범위: 금액은 0 이상의 정수이고 세 언어의 수 타입(Java long · TypeScript number · Rust u64)이 모두 정확히 담는 크기만 씀. 청구 번호와 후보 이름은 ASCII(American Standard Code for Information Interchange, 영문자·숫자·기호 128자) 로 고정 — 세 언어의 문자열 색인 단위가 다르기 때문인데, 이 코드는 문자열을 색인으로 다루지 않으므로 그 차이가 결과에 영향을 주지 않음
  • 진입점이 실행하는 순서: 영수증 검사 → 팀장(100,000) → 부서장(1,000,000) → 재무이사(10,000,000) 로 사슬을 만들고, 청구 다섯을 차례로 넣어 한 줄씩 출력. R1(80,000·영수증 있음) · R2(700,000·있음) · R3(5,000,000·있음) · R4(30,000,000·있음) · R5(80,000·없음)
  • 시나리오 3 의 반례들은 정본 코드에 넣지 않고, 정본의 어느 줄을 어떻게 바꾼 것인지로 구현 해설에서 따로 컴파일·실행한 결과로 보임

손으로 따져 본 값은 이렇습니다. R1 은 영수증이 있어 검사를 통과하고 팀장 한도 안이라 팀장이 맡아요. R2 는 팀장을 넘어 부서장이, R3 은 부서장을 넘어 재무이사가 맡습니다. R4 는 셋 다 넘겨 아무도 맡지 못하고, R5 는 영수증이 없어 첫 후보가 반려합니다.

    private final long amount;

    String handle(ExpenseRequest request);

    private final ApprovalHandler next;

    BaseHandler(ApprovalHandler next) {
        this.next = next;
    }

    protected String passToNext(ExpenseRequest request) {
        if (next == null) {
            return "unhandled";

    }
}

final class ReceiptCheck extends BaseHandler {
    ReceiptCheck(ApprovalHandler next) {
        super(next);
    }

    @Override
    public String handle(ExpenseRequest request) {
        request.visited("ReceiptCheck");
        if (!request.hasReceipt()) {
            return "rejected(no-receipt)";
        }
        return passToNext(request);
    }
}

    private final String title;
    private final long limit;

        super(next);
        this.title = title;
        this.limit = limit;

struct ExpenseRequest {
    id: &'static str,
    amount: u64,
    has_receipt: bool,
    trail: Vec<&'static str>,
}

impl ExpenseRequest {
    fn new(id: &'static str, amount: u64, has_receipt: bool) -> ExpenseRequest {
        ExpenseRequest {
            id,
            amount,
            has_receipt,
            trail: Vec::new(),
        }
    }

    fn visited(&mut self, who: &'static str) {
        self.trail.push(who);
    }

    fn trail_text(&self) -> String {
        self.trail.join(">")
    }
}

trait ApprovalHandler {
    fn handle(&self, request: &mut ExpenseRequest) -> String;
}

fn pass_to_next(next: &Option<Box<dyn ApprovalHandler>>, request: &mut ExpenseRequest) -> String {
    match next {
        Some(handler) => handler.handle(request),
        None => String::from("unhandled"),
    }
}

struct ReceiptCheck {
    next: Option<Box<dyn ApprovalHandler>>,
}

impl ApprovalHandler for ReceiptCheck {
    fn handle(&self, request: &mut ExpenseRequest) -> String {
        request.visited("ReceiptCheck");
        if !request.has_receipt {
            return String::from("rejected(no-receipt)");
        }
        pass_to_next(&self.next, request)
    }
}

struct LimitApprover {
    title: &'static str,
    limit: u64,
    next: Option<Box<dyn ApprovalHandler>>,
}

impl ApprovalHandler for LimitApprover {
    fn handle(&self, request: &mut ExpenseRequest) -> String {
        request.visited(self.title);
        if request.amount <= self.limit {
            return format!("{} approved", self.title);
        }
        pass_to_next(&self.next, request)
    }
}

fn build_chain() -> Box<dyn ApprovalHandler> {
    Box::new(ReceiptCheck {
        next: Some(Box::new(LimitApprover {
            title: "TeamLead",
            limit: 100_000,

                next: Some(Box::new(LimitApprover {
                    title: "Finance",
                    limit: 10_000_000,
                    next: None,
                })),
            })),
        })),
    })
}

    println!(
        "{} {} seen={} -> {}",
        request.id,
        request.amount,
        request.trail_text(),
        verdict
    );
}

첫 행을 최소 조건과 맞춰 보면 이 패턴의 조건들이 실제 API 에서 어떻게 보이는지 알 수 있습니다. 필터는 다음 후보 참조를 자기 필드로 갖지 않아요 — 컨테이너가 매 호출마다 FilterChain 객체를 넘겨주고, 필터는 그것으로 다음을 부릅니다. 그래서 6번은 없지만 1·3번은 만족하고, chain.doFilter 를 부르지 않는 길이 코드에 있으니 4번도 만족해요. refactoring.guru 가 이 API 를 이 패턴의 Java 사례로 드는 곳이 Chain of Responsibility in Java 페이지입니다.

네 행에 공통으로 보이는 것이 하나 있어요. 멈추는 길이 「다음을 부르는 코드를 실행하지 않는 것」으로 표현된다는 점입니다. 서블릿 필터는 chain.doFilter 를 부르지 않고, Express 미들웨어는 next() 를 부르지 않고, DOM 은 stopPropagation() 으로 브라우저가 부모로 올려 보내는 일을 막아요. 최소 조건 4번이 「다음을 부르는 호출이 실행되지 않는 길이 코드에 있는가」로 적힌 이유가 이것이고, 네 사용처 모두 그 길을 API 의 정상 기능으로 열어 두고 있습니다.

스스로 점검하기

  1. 아래 두 클래스가 Chain of Responsibility 인지 최소 조건 1~4번을 하나씩 적용해 판정해 보세요(5번은 요청을 내는 코드가 여기 없어서 잴 수 없습니다 — 왜 그런지도 한 줄로 적어 보세요). 빠진 조건이 있다면 몇 번이고, 시나리오 3 의 어느 단계와 같은 모양이며, 어느 줄을 어떻게 바꾸면 채워지나요?

    interface Stage {
    String process(Order order);
}

final class TaxStage implements Stage {
    private final Stage next;

    TaxStage(Stage next) {
        this.next = next;
    }

    public String process(Order order) {
        order.addTax();
        return next.process(order);
    }
}

final class ShipStage implements Stage {
    private final Stage next;

    ShipStage(Stage next) {
        this.next = next;
    }

    public String process(Order order) {
        order.addShipping();
        return next.process(order);
    }
}
    풀이 보기

    풀이 — 빠진 조건은 2번과 4번입니다. 두 클래스가 공통 선언 Stage 의 process 를 구현하고 next 로 순서가 이어지니 1번은 만족하고, 늘 다음을 부르니 맡지 않고 조용히 끝나는 길이 없어 3번도 만족해요. 그런데 「내가 맡는가」를 가르는 분기가 어느 process 에도 없어 2번이 빠지고, return next.process(order); 가 분기 밖에 있어 뒤 후보를 부르지 않는 길이 없으니 4번도 빠집니다. 시나리오 3 의 1·2단계(맡고도 늘 다음을 부름)와 같은 모양이고, 거기서 맡을지 판단하는 일마저 없는 쪽이라 최소 조건 4번의 빠지면: 이 말한 파이프라인이에요. 채우려면 각 process 에 「이 주문이 내 일인가」를 보는 if 를 두고, 맡는 쪽에서는 결과를 돌려준 뒤 next.process(order) 를 부르지 않게 그 호출을 분기 아래로 옮깁니다. 5번을 잴 수 없는 이유는 process 를 처음 거는 코드, 곧 요청을 내는 쪽이 여기 없어서 그 코드가 진입점만 아는지 볼 자리가 없기 때문입니다.

  2. 아래 AlertBus 는 Chain of Responsibility 와 Observer 중 어느 쪽인가요? 비교 절의 구분 기준으로 답해 보세요. 이어서 Listener.onAlert 가 boolean 을 돌려주게 바꾸고 dispatch 안의 호출을 if (listener.onAlert(alert)) { return; } 로 고치면 판정이 바뀌는지, 그리고 그때 최소 조건 몇 번이 새로 만족되는지도 적어 보세요.

    interface Listener {
    void onAlert(Alert alert);
}

final class AlertBus {
    private final List<Listener> listeners = new ArrayList<>();

    void register(Listener listener) {
        listeners.add(listener);
    }

    void dispatch(Alert alert) {
        for (Listener listener : listeners) {
            listener.onAlert(alert);
        }
    }
}
    풀이 보기

    풀이 — 지금은 Observer 입니다. dispatch 가 등록된 목록을 끝까지 순회하고 onAlert 가 아무 답도 돌려주지 않아요(「Observer 와의 차이」의 구분 기준 — 목록을 끝까지 순회하는가, 하나가 처리하면 멈추는가). 고친 뒤에는 Chain of Responsibility 쪽으로 판정이 바뀝니다. onAlert 가 「내가 처리했다」를 boolean 으로 답하니 맡을지를 리스너가 스스로 정하게 되어 2번이 새로 만족되고, true 가 오면 return 으로 순회를 끝내니 맡은 뒤의 리스너가 같은 경보를 받지 않아 4번도 새로 만족돼요. 최소 조건 절 표의 「등록된 전부를 끝까지 순회하는 통지 루프」 줄에서 빠졌던 두 칸이 이 둘입니다. 다음 후보 참조가 없어도 판정이 같은 이유는 6번이 [선택] 이기 때문이에요.

  3. 구현 절의 코드에서 buildChain 의 사슬 순서를 영수증 검사 → 재무이사 → 부서장 → 팀장으로 뒤집었다고 해 봅시다. 연산 모양은 그대로라서 세 언어 모두 컴파일은 통과합니다. 이때 R1(80,000원)과 R2(700,000원)의 출력 줄은 각각 어떻게 바뀌고, seen= 칸에는 무엇이 찍히나요? 최소 조건 1~5번 가운데 이 변경으로 성립하지 않게 되는 것이 있는지, 그리고 시나리오 2 의 5단계가 말한 「순서는 결과를 정하는 설계」가 여기서 어떤 모습으로 나타나는지도 짚어 보세요.
