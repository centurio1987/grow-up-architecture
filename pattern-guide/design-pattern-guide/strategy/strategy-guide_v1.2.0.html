한눈에 보는 개요

온라인 상점의 결제 코드를 하나 떠올려 봅시다. Checkout.total() 은 상품 금액에 배송비를 더해 총액을 내는데, 배송비를 매기는 방법이 정액·일정 금액 이상 무료·무게별 요금으로 셋이에요. 세 방법을 switch 하나에 넣어 두면 방법이 늘 때마다 결제 클래스를 열어 case 를 더해야 합니다. 총액만 내면 되는 클래스가 배송비 규칙을 전부 알고 있는 셈이죠.

Strategy 의 해법은 바뀌는 계산을 같은 모양의 객체로 떼어 내는 것입니다. 결제 클래스는 받아 둔 객체에 배송비 계산을 맡기기만 하고, 어느 객체를 넣을지는 결제 클래스 바깥에서 정해요. 방법이 하나 늘면 클래스가 하나 늘 뿐 결제 클래스는 열지 않습니다.

Before : 결제 클래스가 배송비 규칙을 모두 안고 있음

  Checkout.total(order)
    switch (plan)
      "flat"      → 3,000원
      "free-over" → 상품 금액 50,000원 이상이면 0원, 아니면 3,000원
      "weight"    → 무게를 kg 단위로 올림 × 1,500원
      새 방법      → 이 switch 를 열어 case 추가

After : 배송비 계산을 객체로 떼어 내고, 어느 객체를 쓸지는 바깥에서 넣어 줌

  바깥 코드 ── 고른 배송비 객체를 넣어 줌 ──▶ Checkout
                                              total(order)
                                                배송비 객체.fee(상품 금액, 무게)
                                                  ├─ FlatRate
                                                  ├─ FreeOverThreshold
                                                  ├─ ByWeight
                                                  └─ 새 방법 = 새 클래스 (Checkout 은 그대로)

분류는 행위 패턴이고 다른 이름은 Policy 예요(근거: GoF Strategy 절 Also Known As — GoF 는 Gang of Four 의 줄임말로, 1994년에 나온 Design Patterns 의 저자 네 명을 함께 부르는 이름). 함께 쓰는 패턴은 Flyweight 입니다.

이 글은 시나리오 셋을 따라갑니다. 주문 하나가 총액이 되는 길, 요금제가 더해질 때 무엇이 안 바뀌는가, 고르는 일을 결제 클래스 안으로 들이면 어디서 어긋나는가. 끝까지 읽으면 어떤 코드를 Strategy 라고 불러도 되는지 필수 조건 셋으로 판정할 수 있고, 구조가 닮은 State·Template Method 코드와도 구분할 수 있게 됩니다.

시나리오 1 — 주문 하나의 총액이 정액 요금제로 계산되는 길

주문 A 가 들어왔습니다. 상품 금액 32,000원에 무게 2,300g 이고, 이 상점의 요금제 설정은 정액 3,000원("flat")이에요. 나와야 하는 것은 총액 35,000원 하나입니다. 이 장면에는 넷이 등장해요. 총액을 내는 결제 객체 Checkout(패턴에서는 Context 라고 부르는 역할), 배송비만 계산하는 객체 FlatRate(ConcreteStrategy), 그 객체들이 공통으로 따르는 연산 모양 fee(상품 금액, 무게) 를 선언한 ShippingPolicy(Strategy), 그리고 요금제 설정을 읽어 어느 배송비 객체를 쓸지 정하는 조립 코드(Client)입니다. 이름은 여기서 한 번씩만 소개하고 정식 정의는 개념 정리에서 해요.

  1. Client 가 요금제 설정 "flat" 을 읽고 FlatRate(3,000) 을 만듭니다. 이 일을 Client 가 맡는 이유는 요금제나 프로모션 같은 요구를 아는 쪽만 어떤 계산이 맞는지 판단할 수 있어서예요. 이 판단을 Checkout 이 하면 고르는 조건문이 Checkout 안에 남고, 방법이 늘 때마다 Checkout 을 고치게 됩니다(시나리오 3 이 그 모양을 따라갑니다).
  2. Client 가 만든 객체를 Checkout 의 생성자로 넘겨 설치합니다. Checkout 은 ShippingPolicy 타입으로 받으니 정액인지 무게별인지 몰라도 돼요. 이 단계가 3단계보다 늦으면 요청이 왔을 때 위임할 대상이 없습니다.
  3. 설치가 끝나면 Client 는 Checkout 에게 주문 A 의 총액을 요청합니다. Checkout 에게만 요청하는 이유는 총액 규칙(상품 금액에 배송비를 더함)이 Checkout 안에 한 곳으로 있어야 해서예요. Client 가 FlatRate 를 직접 부르면 그 덧셈을 Client 마다 다시 써야 합니다.
  4. Checkout 은 총액을 내다가 배송비 자리에서 설치된 전략에게 fee(32,000, 2,300) 을 부릅니다. Checkout 이 아는 것은 무엇을 계산할지(총액)까지이고 배송비를 어떻게 매길지는 몰라요. 모르는 채로 부를 수 있게 해 주는 장치가 ShippingPolicy 타입입니다. 계산에 필요한 값은 Checkout 이 꺼내 인자로 넘겨요. 그래서 전략은 Checkout 을 몰라도 됩니다.
  5. FlatRate 가 3,000 을 돌려줍니다. 받은 상품 금액과 무게는 둘 다 쓰지 않았고, 어디에도 적어 두지 않았어요. 받은 값을 필드에 남기지 않기 때문에 이 객체를 결제 객체 여럿이 같이 써도 앞 호출이 뒤 호출의 답을 바꾸지 못합니다. 모든 전략이 같은 연산 모양을 공유하니 단순한 전략은 받은 값을 버리게 되고, 이것이 이 패턴이 치르는 통신 부담입니다(근거: GoF Strategy 절 Consequences).
  6. Checkout 이 32,000 + 3,000 = 35,000 을 Client 에 돌려줍니다. 더하는 일을 전략으로 옮기지 않는 이유는 그 규칙이 요금제와 무관하게 늘 같아서예요. 전략마다 덧셈을 갖게 하면 같은 덧셈이 전략 수만큼 복제됩니다.
단계   부르는 쪽 → 받는 쪽          넘기는 것                 돌아오는 것
 1     Client → (new)             "flat"                    FlatRate(3,000)
 2     Client → Checkout          FlatRate 객체              —
 3     Client → Checkout          주문 A                     (6단계에서 35,000)
 4     Checkout → ShippingPolicy   32,000 · 2,300            —
 5     FlatRate → Checkout        —                         3,000
 6     Checkout → Client          —                         32,000 + 3,000 = 35,000

잠깐, 확인 하나만 해 볼까요? 4단계에서 같은 fee(32,000, 2,300) 을 받았을 때 50,000원 이상 무료 전략은 어느 값을 쓰고 무게별 전략은 어느 값을 쓸까요?

앞은 상품 금액만, 뒤는 무게만 씁니다. 정액 전략은 둘 다 쓰지 않고요. 세 전략이 한 연산 모양을 나눠 쓰는 대신 각자 필요 없는 값을 받게 되는 것이 5단계의 통신 부담이고, 시나리오 2 에서 새 전략 둘이 들어올 때 이 표의 줄이 어떻게 늘어나는지 다시 봅니다.

전략                      넘겨받는 값            계산에 실제로 쓰는 값
정액 전략                  상품 금액 · 무게        없음
50,000원 이상 무료 전략     상품 금액 · 무게        상품 금액
무게별 전략                상품 금액 · 무게        무게

이 시나리오가 보여 준 것은 역할 넷과 그 사이의 호출 방향입니다. 고르고 만드는 일(1단계)과 설치(2단계)는 Client 가, 요청 처리와 총액 규칙(3·6단계)은 Context 가, 배송비 계산(5단계)은 ConcreteStrategy 가 맡고, Context 는 Strategy 타입 하나로만 전략을 부릅니다(4단계).

같은 뼈대 위에서 다르게 짤 수 있는 자리가 셋 있어요. 이 글의 코드는 각 줄의 첫째를 씁니다. 설치 시점은 생성자로 한 번 넣거나, list.sort(comparator) 처럼 요청 메서드의 인자로 넘겨 설치와 요청을 한 호출로 합칠 수 있어요. 전략이 비었을 때는 Client 가 늘 넣게 하거나, Checkout 이 정액 3,000원 같은 기본 전략을 쓰게 둘 수 있습니다. 이 둘째를 기본 전략이라고 부르고, 그러면 Client 는 기본이 마음에 들지 않을 때만 설치해요(근거: GoF Strategy 절 Implementation 3). 전략이 값을 얻는 길은 인자로 받기 · Checkout 자신을 받아 필요한 값을 묻기 · Checkout 참조를 미리 들고 있기 셋이에요(근거: GoF Strategy 절 Implementation 1). 뒤의 둘은 전략마다 필요한 값만 가져가는 대신 Checkout 이 조회 연산을 공개해야 해서 둘이 더 단단히 묶입니다.

자리                이 글의 코드                     다른 선택지
설치 시점           생성자로 한 번 (2단계)            요청 메서드의 인자로 — 2·3단계가 한 호출
전략이 없을 때       Client 가 늘 넣음                 기본 전략 — Context 가 정한 기본값
값을 얻는 길         인자로 받음 (4단계)               Context 를 받아 물음 · Context 참조를 미리 가짐

시나리오 2 — 50,000원 이상 무료 요금제가 더해질 때

상점이 요금제를 하나 더 도입하기로 했습니다. 상품 금액이 50,000원 이상이면 배송비가 0원이고 아니면 3,000원인 요금제("free-over")예요. 시험할 주문은 B, 상품 금액 58,000원에 무게 5,100g 입니다. 정액이면 61,000원, 새 요금제면 58,000원이 나와야 해요. 얼마 뒤에는 무게를 kg 단위로 올림해 kg 당 1,500원을 받는 요금제("weight")도 들어옵니다. 그때 주문 A 는 36,500원, 주문 B 는 67,000원이 나와야 합니다.

  1. 개발자가 FreeOverThreshold 클래스를 새로 씁니다. 연산 모양은 시나리오 1 의 fee(상품 금액, 무게) 그대로이고 본문만 "상품 금액이 기준 이상이면 0, 아니면 정액" 이에요. 모양을 바꾸지 않는 이유는 그 모양이 Checkout 과 모든 전략 사이의 계약이라서, 모양이 바뀌면 Checkout 의 호출 줄과 기존 전략이 전부 따라 바뀌기 때문입니다.
  2. Client 의 조립 코드 choosePolicy(요금제 이름을 받아 배송비 객체를 만들어 돌려주는 함수)에 "free-over" 를 FreeOverThreshold(50,000, 3,000) 으로 잇는 한 줄을 더합니다. 이 줄이 Client 쪽에 있는 이유는 시나리오 1 의 1단계와 같아요. 요금제 이름과 계산의 대응을 아는 쪽은 요구를 아는 쪽입니다.
  3. Checkout 은 한 줄도 바뀌지 않습니다. Checkout 에 적힌 배송비 관련 이름은 ShippingPolicy 와 fee 뿐이라 새 클래스 이름이 들어갈 자리가 없어서예요. 이것이 조건문을 없앤다는 이 패턴의 결과이고, 없어진 것이 아니라 Client 의 조립 코드 한 곳으로 모인 것입니다(근거: GoF Strategy 절 Consequences).
  4. Client 가 같은 Checkout 객체에 두 요금제를 차례로 설치하며 주문 B 를 넣어 봅니다. 정액을 설치하고 총액을 물으면 61,000, changePolicy 로 새 전략을 갈아 끼우고 다시 물으면 58,000 이에요. 갈아 끼우는 연산이 있어서 Checkout 을 새로 만들지 않아도 되지만, 이 연산이 없어도 요금제마다 Checkout 을 새로 만들면 같은 결과가 납니다. 그래서 실행 중 교체는 패턴의 필수가 아니라 선택이에요.
  5. 무게별 요금제가 들어오면 ByWeight 클래스 하나와 조립 코드 한 줄이 늘고 Checkout 은 그대로입니다. 두 번째 요금제 때와 드는 품이 같은 이유는 Checkout 이 배송비 계산을 이름으로 부르지 않고 연산 모양으로만 부르기 때문이에요. 이름을 불렀다면 요금제가 늘 때마다 그 이름을 아는 자리도 함께 늘었을 겁니다. 이번 전략은 무게만 쓰고 상품 금액은 버립니다. 주문 A 는 2,300g 을 올림해 3kg 이니 32,000 + 4,500 = 36,500, 주문 B 는 5,100g 이 6kg 이니 58,000 + 9,000 = 67,000 입니다.
변화                    바뀐 곳                                        안 바뀐 곳
free-over 추가          FreeOverThreshold 클래스 (새로 씀)               Checkout 전체
                        choosePolicy 의 "free-over" 한 줄               ShippingPolicy 의 연산 모양
                                                                       FlatRate
weight 추가             ByWeight 클래스 (새로 씀)                        Checkout 전체
                        choosePolicy 의 "weight" 한 줄                  ShippingPolicy · FlatRate · FreeOverThreshold

두 변화를 들인 뒤 주문 A·B 의 총액을 요금제마다 셈하면 이렇습니다.

요금제주문 A (32,000원 · 2,300g)주문 B (58,000원 · 5,100g)
flat32,000 + 3,000 = 35,00058,000 + 3,000 = 61,000
free-over32,000 < 50,000 이라 32,000 + 3,000 = 35,00058,000 ≥ 50,000 이라 58,000 + 0 = 58,000
weight올림 3kg × 1,500 = 4,500 → 36,500올림 6kg × 1,500 = 9,000 → 67,000

여기서 헷갈리기 쉬운 포인트는 전략이 정해지는 때가 실행 중이어야 한다고 믿는 것입니다. 4단계의 changePolicy 는 편의일 뿐이고, 생성자로 한 번만 받는 Checkout 도 이 시나리오의 1~3단계를 똑같이 지나요. 한 걸음 더 가면 전략을 타입 매개변수로 받아 컴파일할 때 고정하는 변형도 있습니다(근거: GoF Strategy 절 Implementation 2). 그때는 같은 Checkout 객체가 다른 전략으로 바뀌지는 못하지만, 새 전략을 더할 때 Checkout 이 안 바뀐다는 3단계는 그대로예요. 두 변형이 서로 다른 점은 결합 시점(컴파일 시점 결합과 실행 시점 결합)인데, 그 용어는 참고 문서 「GoF 공통 어휘」의 「컴파일 시점 결합과 실행 시점 결합」이 정의합니다.

이 시나리오가 보여 준 것은 변화의 범위입니다. 새 종류가 들어올 때 바뀌는 곳은 새 ConcreteStrategy 하나와 Client 의 조립 코드 한 줄이고, Context 와 기존 전략은 그대로예요(1~3단계). 전략끼리 서로를 모르기 때문에 하나를 더하거나 지울 때 다른 전략 코드를 볼 일이 없고, 새 전략마다 받은 값 중 다른 것을 버리는 통신 부담이 한 줄씩 늘어납니다(5단계). 실행 중 교체(4단계)는 뼈대가 아니라 선택지예요.

시나리오 3 — 고르는 일을 Checkout 안으로 들이면 어디서 어긋나는가

같은 상점의 다른 코드베이스는 Checkout 을 조금 다르게 짰습니다. 생성자가 요금제 이름 문자열을 받고, 그 안에서 switch 로 FlatRate(3,000) 을 만들어 필드에 넣어요. 필드 타입은 ShippingPolicy 라 겉보기엔 시나리오 1 과 같습니다. 여기에 시나리오 2 의 변화("free-over" 추가)가 그대로 들어오고, 별도로 영수증을 찍는 코드가 배송비를 직접 계산하기 시작해요. 아래 결과는 Java 21 로 실제로 컴파일해 실행한 것입니다.

  1. Checkout 생성자가 plan 문자열을 switch 로 분기해 FlatRate(3,000) 을 만들고, 모르는 이름이면 예외를 던집니다. 이렇게 짜는 이유는 대개 편의예요. Client 가 객체를 만들 필요 없이 이름만 넘기면 되니까요. 그 대가로 요금제 이름과 계산의 대응이 Checkout 안에 들어갑니다.
  2. 개발자가 시나리오 2 의 1단계대로 FreeOverThreshold 클래스를 새로 쓰고, Client 가 new Checkout("free-over") 를 만들어 주문 B 의 총액을 묻습니다. 결과는 IllegalArgumentException: unknown plan: free-over 예요. 새 클래스는 있는데 Checkout 이 그 이름을 모르기 때문입니다. 시나리오 2 의 2단계가 넣을 자리(Client 의 조립 코드)가 이 코드에는 없어요.
  3. 고치려면 Checkout 생성자의 switch 에 case "free-over" 를 더해야 합니다. 시나리오 2 의 3단계(Checkout 무변경)가 성립하지 않는 자리가 바로 여기예요. 요금제가 늘 때마다 Checkout 을 열게 되니, 개요의 Before 그림에서 switch 가 total() 안에 있던 것과 자리만 다를 뿐 같은 코드입니다. 조건문이 사라진 것이 아니라 생성자로 옮겨진 것이죠.
  4. 갈래 하나를 더 봅니다. 영수증 코드가 Checkout 을 거치지 않고 ByWeight(1,500) 의 fee(32,000, 2,300) 을 직접 불러 배송비 4,500 을 찍고, 상품 금액을 더하는 줄을 잊었어요. 같은 주문 A 를 Checkout.total() 로 물으면 36,500 인데 영수증에는 4,500 이 찍힙니다. 시나리오 1 의 3단계가 Client 는 Context 에게만 요청한다고 한 이유가 이것이에요. 총액 규칙이 한 곳에 있어야 부르는 쪽마다 규칙을 다시 쓰지 않습니다.
  5. 두 갈래를 되돌리는 길은 서로 다릅니다. 앞은 switch 를 Checkout 밖의 조립 코드로 옮기고 생성자가 ShippingPolicy 를 받게 하는 것이고, 뒤는 영수증 코드가 Checkout.total() 을 부르게 하는 것이에요. 앞은 Checkout 의 선언을 고치는 일이고 뒤는 호출하는 쪽을 고치는 일이라, 둘은 서로 다른 규칙에 해당합니다.

개념 정리

시나리오에 나온 역할 넷을 정식으로 정의합니다. 셋은 패턴의 참여자이고 Client 는 참여자 목록 밖에서 전략을 골라 넣는 쪽인데, 시나리오와 구현에 늘 나오므로 함께 정의해요(근거: GoF Strategy 절 Participants·Collaborations).

  • Strategy — 같은 목적의 알고리즘들이 모두 따르는 연산을 선언합니다. Context 는 이 선언만 보고 호출하고(시나리오 1 의 4단계), ConcreteStrategy 는 이 선언을 구현해요. 배송비 예에서는 상품 금액과 무게를 받아 배송비를 돌려주는 연산 fee 하나를 선언한 ShippingPolicy 가 Strategy 입니다.
  • ConcreteStrategy — Strategy 가 선언한 연산을 실제 알고리즘으로 구현합니다. 같은 Strategy 를 따르는 ConcreteStrategy 들이 알고리즘 군(family)을 이루고, 서로를 몰라도 각자 동작해요(시나리오 2 의 1단계). Client 가 만들고 Context 가 호출합니다. 배송비 예에서는 FlatRate·FreeOverThreshold·ByWeight 가 각각 ConcreteStrategy 예요.
  • Context — Client 의 요청을 받는 객체입니다. ConcreteStrategy 하나를 Strategy 타입 참조로 받아 두고, 요청을 처리하다 바뀌는 계산이 나오면 그 참조에 넘겨요(시나리오 1 의 2·4단계). 이렇게 일을 넘기는 것이 위임이고 Strategy 타입으로만 참조하는 것이 인터페이스에 프로그래밍한다는 원칙인데, 두 말의 정의는 참고 문서 「GoF 공통 어휘」에 있습니다. 전략을 받아 두는 일을 이 글에서는 설치라고 불러요. 배송비 예에서는 Checkout 이 Context 입니다.
  • Client — ConcreteStrategy 군에서 하나를 골라 만들고(시나리오 1 의 1단계), Context 에 설치한 뒤에는 Context 에게만 요청합니다(3단계). 배송비 예에서는 요금제 설정을 읽어 어떤 배송비 객체를 넣을지 정하는 조립 코드 choosePolicy 와 진입점이 Client 예요.

그림에서 Context 의 화살표가 Strategy 로만 향하고 ConcreteStrategy 를 직접 가리키지 않는다는 점을 봐 두세요. ConcreteStrategy 로 들어가는 화살표는 Client 에서 내려온 것 하나뿐입니다 — 그것을 만드는 쪽이 Client 이기 때문이에요. Context 쪽 화살표는 최소 조건 2·3번이, ConcreteStrategy 를 만드는 쪽 화살표는 4번이 코드에서 확인해요.

무엇을 계산할지는 Context 가, 어떻게 계산할지는 ConcreteStrategy 가, 어느 것을 쓸지는 Client 가 정한다.

사용 목적

Strategy 가 필요할 때는 코드나 요구에서 보이는 단서가 있습니다. 셋을 차례로 봅시다.

단서 1 — 계산 메서드 안의 분기가 방법이 늘 때마다 커집니다

배송비 방법을 하나 더하는 변경마다 같은 결제 클래스의 같은 메서드가 수정 목록에 오르면 신호예요. 시나리오 3 의 3단계가 정확히 이 모양이었습니다. 연산 하나 안에 여러 갈래 조건문으로 행동이 나뉘어 있는 클래스가 이 패턴이 겨냥하는 첫 대상이에요(근거: GoF Strategy 절 Applicability).

변경 이력                       수정된 곳
─────────────────────────────   ─────────────────────────────
무게별 배송비 추가               Checkout.total() 의 switch
50,000원 이상 무료 추가          Checkout.total() 의 switch
도서 산간 추가 요금 추가          Checkout.total() 의 switch

단서 2 — 계산 방법만 다른 하위 클래스가 생깁니다

FlatShippingCheckout·WeightShippingCheckout 처럼 결제 클래스를 상속해 배송비 메서드만 바꾼 클래스들이 보이는 경우예요. 행동만 다른 관련 클래스가 여럿인 상황이 두 번째 대상인데(근거: GoF Strategy 절 Applicability), 이 모양은 바뀌는 곳이 하나 더 생기면 빠르게 불어납니다. 할인 방법까지 하위 클래스로 나누면 조합마다 클래스가 필요해요.

방식전체 타입 수m = 3, n = 2 일 때배송비 방법 하나를 더하면 늘어나는 수
하위 클래스로 조합상위 클래스 1 + 조합 m × n1 + 6 = 7n (할인 방법마다 하나)
계산을 객체로 떼어 냄결제 클래스 1 + 인터페이스 2 + m + n1 + 2 + 5 = 81

배송비 방법이 m 개, 할인 방법이 n 개일 때의 셈이에요. 이 크기에서는 떼어 낸 쪽이 오히려 하나 많습니다. 단서가 되는 것은 총량이 아니라 늘어나는 속도예요. 배송비 방법을 하나 더할 때 하위 클래스 쪽은 n 개, 떼어 낸 쪽은 1 개가 늘어 차가 n − 1 씩 벌어집니다. 그래서 이 단서는 바뀌는 곳이 배송비와 할인처럼 둘 이상일 때 들어맞아요.

단서 3 — 계산 하나만 쓰는 데이터가 결제 클래스에 있습니다

알고리즘이 쓰는 자료구조를 알고리즘을 쓰는 쪽에 드러내고 싶지 않을 때가 세 번째 대상이에요(근거: GoF Strategy 절 Applicability). 코드에서는 결제 클래스의 필드 중 switch 의 한 case 안에서만 읽히는 필드로 보입니다.

Java 와 Rust 는 구현을 고치기 전까지 컴파일러가 막고, TypeScript 는 공통 연산만 넓히고 구현을 그대로 둬도 strict 모드에서 통과하니 직접 맞춰야 합니다(직접 컴파일해 확인). 매개변수가 적은 함수를 많은 쪽 자리에 넣어도 받아 주는 타입 호환 규칙 때문이에요(TypeScript Handbook: Type Compatibility). 코드에서는 이렇게 구현마다 쓰는 매개변수를 세어 대부분의 구현이 대부분을 버리는지 확인해요. 그렇다면 시나리오 1 뒤에서 본 「Context 를 받아 물음」처럼 전략이 필요한 값만 묻게 해 연산 모양을 좁히거나(대신 결합이 커짐), 이 계산들을 공통 연산 하나로 묶는 것 자체를 다시 검토합니다.

패턴의 경계

디자인 패턴을 충족하는 최소 조건

어떤 코드를 Strategy 라고 불러도 되는지 가르는 기준입니다. [필수] 가 하나라도 빠지면 Strategy 가 아니고, [선택] 은 갖추면 좋은 구조예요. 조건은 언어와 상관없이 코드에서 확인할 수 있는 모양(타입 선언·참조 보유·호출 방향·생성 위치)으로 적었고, 조건마다 그것을 보여 준 시나리오의 단계를 가리킵니다.

  1. [필수] 같은 연산 모양을 따르는 계산 방법별 구현 — 같은 목적의 계산들이 이름·매개변수·반환 형태가 같은 연산을 구현하고, 계산 방법마다 그 연산을 구현한 별도 단위가 있으며, 한 구현 안에 계산 방법을 고르는 분기가 없습니다. 시나리오 2 의 1단계 (근거: GoF Strategy 절 Participants — Strategy 가 모든 알고리즘에 공통인 인터페이스를 선언하고 ConcreteStrategy 가 그것으로 알고리즘을 구현한다)
    • 코드에 나타나는 모양: 연산 모양은 인터페이스·추상 클래스·trait(Rust 에서 타입이 구현할 연산을 선언하는 문법)·함수 타입 같은 선언이나, 타입 매개변수가 요구하는 연산으로 보입니다. 별도 단위는 클래스나 함수 값이에요.
    • 빠지면: 첫 모양은 계산 방법이 Context 안의 private 메서드 flatFee()·weightFee() 로만 있고 switch 가 그중 하나를 부르는 코드입니다. 메서드로 뽑았을 뿐 조건 분기라서, 방법을 하나 더하려면 Context 의 계산 코드에 새 case 를 더해야 해요.
    • 빠지면: 또 하나는 공통 인터페이스는 있지만 구현이 AnyPlan(String plan) 하나뿐이고, 그 fee 안에서 switch (plan) 으로 정액과 무게별을 고르는 코드입니다. 분기가 Context 에서 전략 클래스 안으로 옮겨 갔을 뿐이라 방법을 더하려면 AnyPlan 의 switch 를 고쳐야 해요. 아래에서 실행해 봅니다.
    • 경계 사례: 같은 클래스의 객체 여럿이 필드 값만 다르고 계산 코드는 같다면(FlatRate(3_000) 과 FlatRate(5_000)) 한 계산 방법을 매개변수로 나눈 것이라 만족합니다. 공통 상위 타입 없이 타입 매개변수가 연산을 요구하는 형태(컴파일 시점에 전략이 고정되는 변형)도 만족해요.
  2. [필수] Context 는 전략을 그 연산 모양으로만 보유하고 호출 — Context 가 전략을 1번의 공통 타입(또는 그 연산을 요구하는 타입 매개변수)으로 받아 두고, 요청을 처리할 때 그 연산을 불러 계산을 넘기며, 구체 전략 타입에 따라 분기하지 않습니다. 시나리오 1 의 2단계(설치)와 4단계(호출) (근거: GoF Strategy 절 Participants·Collaborations — Context 는 Strategy 참조를 유지하고 Strategy 인터페이스로 알고리즘을 호출해 클라이언트의 요청을 자기 전략에 전달한다)
    • 코드에 나타나는 모양: Context 의 필드·생성자 인자·메서드 인자·타입 매개변수에 적힌 전략 타입이 공통 타입이고, 타입 검사나 다운캐스트(상위 타입으로 받은 값을 하위 타입으로 바꾸는 변환)가 Context 에 없습니다.
    • 빠지면: 필드가 ByWeight policy 처럼 구체 타입이면 다른 계산을 넣을 수 없어서 도우미 클래스 하나에 일을 넘기는 단순 위임에 그칩니다. 필드와 생성자 인자의 타입을 ByWeight 로 좁혀 컴파일하면, 요금제마다 다른 배송비 객체를 넘기는 호출에서 Java 는 incompatible types: ShippingPolicy cannot be converted to ByWeight, Rust 는 E0308 mismatched types 로 멈춰요(직접 컴파일해 확인). if (policy instanceof ByWeight) 처럼 종류를 확인하면 1번에서 없앤 분기가 Context 로 돌아옵니다.
  3. [필수] 고르는 분기는 Context 밖, Context 는 전략을 받는 경로를 가짐 — 요금제 값이나 설정을 보고 어느 계산을 쓸지 가르는 분기가 Context 에 없고, 쓸 전략이 밖에서 정해져 들어오는 경로가 있습니다. 시나리오 3 의 1~3단계 (근거: GoF Strategy 절 Consequences·Intent — 전략을 고르던 조건문이 Context 에서 사라지고 알고리즘이 그것을 쓰는 클라이언트와 독립적으로 바뀐다)
    • 코드에 나타나는 모양: 들어오는 경로는 생성자 인자·설치 연산·요청 메서드의 인자·타입 인자 가운데 하나입니다.
    • 빠지면: Context 생성자가 요금제 문자열을 받아 switch 로 전략을 직접 고르면 필드 타입이 공통 타입이어도 방법을 하나 더할 때마다 그 switch 를 고쳐야 하고, 새 클래스만 더한 채 new Checkout("free-over") 를 부르면 unknown plan: free-over 예외가 납니다(직접 실행해 확인).
    • 경계 사례: 인자를 생략했을 때 쓸 기본 전략 하나를 Context 가 정해 두는 것(시나리오 1 뒤의 기본 전략)은 고르는 분기가 아니므로 만족합니다.
  4. [선택] ConcreteStrategy 를 만드는 코드는 Context 밖 — 전략 객체를 만드는 자리(생성자 호출·함수 값 작성·타입 인자 지정)가 Client·설정·조립 코드에 있고 Context 는 만들어진 것을 받기만 합니다. 시나리오 1 의 1단계 (근거: GoF Strategy 절 Collaborations — Client 가 보통 ConcreteStrategy 를 만들어 넘긴다고 적어, "보통" 인 자리라 필수로 올리지 않았다)
    • 경계 사례: Context 가 기본 전략 객체를 스스로 만들더라도 고르는 분기가 없으면 3번은 그대로 만족합니다.
  5. [선택] 전략을 다시 설치하는 연산 — setter(필드 값을 바꾸는 메서드) 같은 연산으로 실행 중에 설치된 전략을 다른 전략으로 바꿀 수 있습니다. 시나리오 2 의 4단계 (근거: 이 가이드의 정책 — 컴파일할 때 전략을 고정하는 타입 매개변수 변형도 Strategy 로 보므로, GoF Strategy 절 Implementation 2)
    • 경계 사례: 시나리오 2 의 4단계는 이 연산을 쓰지만 없어도 같은 결과가 났습니다. 이 연산이 없어도 1~3번을 만족하면 Strategy 예요.
  6. [선택] 공유되는 전략은 호출 사이에 값을 남기지 않음 — 정적 필드나 싱글턴(인스턴스를 하나만 두고 함께 쓰는 방식)으로 한 ConcreteStrategy 인스턴스를 여러 Context 가 함께 참조한다면, 그 전략의 연산이 자기 필드나 필드가 가리키는 가변 객체에 값을 쓰지 않습니다. 시나리오 1 의 5단계 (근거: GoF Strategy 절 Consequences — 공유되는 전략은 호출 사이에 상태를 유지하면 안 된다)
    • 경계 사례: 생성할 때 정한 뒤 바뀌지 않는 필드(FlatRate 의 amount)는 두어도 됩니다. 두어도 되는 값과 안 되는 값을 가르는 어휘가 참고 문서 「GoF 공통 어휘」의 내재 상태와 외재 상태예요.
    • 어기면: 공유된 무게별 전략이 처음 계산한 kg 값을 필드에 남겨 두고 다음 호출에서 그 값을 다시 쓰면, 결제 객체 둘이 그 전략을 같이 쓸 때 주문 A(2,300g)를 먼저 계산한 뒤 주문 B(5,100g)의 총액이 67,000 이 아니라 3kg 요금을 더한 62,500 으로 나옵니다(직접 실행해 확인).

1번이 맨 앞인 데는 이유가 있습니다. 1번만 빠지고 2·3번은 만족하는 코드가 실제로 있어서, 1번을 보지 않으면 그런 코드가 Strategy 로 통과해요. 1번의 두 번째 반례인 AnyPlan 을 코드로 봅시다.

final class AnyPlan implements ShippingPolicy {
    private final String plan;

    AnyPlan(String plan) {
        this.plan = plan;
    }

    @Override
    public long fee(long subtotal, long weightGrams) {
        return switch (plan) {                    // 계산 방법을 고르는 분기가 구현 안에 있다
            case "flat" -> 3_000;
            case "weight" -> Math.ceilDiv(weightGrams, 1_000) * 1_500;
            default -> throw new IllegalArgumentException(plan);
        };
    }
}

// Checkout 은 시나리오 1 과 같다: 필드는 ShippingPolicy, Client 가 new AnyPlan("weight") 를 만들어 넘긴다

Checkout 은 전략을 ShippingPolicy 타입으로 보유하고 타입 검사 없이 fee 를 부르니 2번을 만족하고, Checkout 안에 계산 방법을 고르는 분기가 없고 전략을 받는 경로가 있으니 3번도 만족합니다. 주문 A 를 넣으면 "flat" 으로 35,000, "weight" 로 36,500 이 나와 시나리오 2 의 표와 같아요. 여기까지는 멀쩡해 보이죠. 그런데 시나리오 2 의 변화를 넣어 new AnyPlan("free-over") 를 만들면 IllegalArgumentException: free-over 가 나고(직접 실행해 확인), 고치려면 AnyPlan.fee 의 switch 에 case 를 더해야 합니다. 시나리오 3 의 3단계와 같은 일이 Context 가 아니라 전략 클래스 안에서 일어나는 것이죠.

[필수] 는 하나만 빠져도 판정이 끝나므로 1번부터 차례로 봅니다. 1번은 전략 쪽 코드만, 2번은 Context 의 선언과 호출만, 3번은 Context 안에 고르는 분기가 있는지만 보면 되어서 앞 조건에서 멈추면 뒤는 읽지 않아도 돼요. 다만 필수 셋을 다 갖췄다고 판정이 끝나는 것은 아니에요. 구현 객체들이 같은 계산의 대안이 아니라 도메인의 상태를 나타낸다면 비교 절의 기준으로 State 쪽인지 함께 봅니다.

여기서 헷갈리기 쉬운 포인트는 5번 실행 중 교체가 필수처럼 보인다는 점입니다. refactoring.guru 의 Java 예제 페이지도 실제 일을 안쪽 객체에 맡기는 메서드와 그 객체를 바꾸는 setter 를 이 패턴을 알아보는 단서로 들어요(refactoring.guru — Strategy in Java). 하지만 시나리오 2 의 4단계에서 본 대로 changePolicy 없이 Checkout 을 새로 만들어도 결과는 같고, 컴파일할 때 전략을 고정하는 타입 매개변수 변형도 Strategy 입니다(근거: GoF Strategy 절 Implementation 2). 그래서 이 가이드는 전략이 정해지는 때를 필수로 두지 않고, 고르는 분기가 Context 안에 남아 있는지를 필수로 봅니다. 아래 세 설치 방식은 모두 1~3번을 만족해요.

비슷한 패턴·안티패턴과의 차이

Strategy 와 구조가 닮았거나 같은 단서에서 떠오르는 대상 넷을 비교합니다. State 와 Template Method 는 개요에서 이름만 꺼냈고, Command 는 요청 하나를 객체로 만들어 호출하는 쪽이 그 객체의 실행 연산만 부르게 하는 패턴이에요. 나머지 하나는 분기를 메서드로 뽑아 놓고 Strategy 로 오해받는 코드입니다. 표에 기준을 먼저 모으고, 대상마다 코드와 시나리오로 풀어 볼게요.

비교 대상구분 기준Strategy 를 고르면 얻는 것포기하는 것
State구현 객체가 같은 계산의 대안인가, 객체가 오가는 상태인가. 코드에서는 요청을 처리한 결과로 다음 구현 객체가 정해지는 코드가 있는지부터 봄요청 처리 흐름에 전이 코드가 없어, 전략을 더하거나 지울 때 다른 전략 코드를 볼 일이 없음(시나리오 2)Strategy 자체는 상태 전이 모델을 주지 않음. 전이가 필요하면 Context 나 별도 상태 모델에 따로 둬야 함
Template Method바뀌는 계산이 하위 클래스의 재정의로 들어오는가, 받은 객체의 연산 호출로 들어오는가계산 조합마다 하위 클래스를 만들지 않음. 설치 연산을 두면 실행 중 교체도 가능(최소 조건 5번)하위 클래스가 상위 클래스의 필드와 protected 연산을 바로 쓰던 내부 접근. 전략은 Context 가 넘긴 값이나 공개한 조회 연산으로만 데이터를 얻음
Command구현 객체가 Context 의 요청 처리 중 한 단계를 같은 목적의 다른 방법으로 맡는가, 수행할 요청 하나를 객체로 담고 있는가Context 가 요청 처리 흐름과 넘길 데이터를 정하고 전략의 결과나 동작을 그 자리에서 이어받음둘은 함께 쓸 수 있어 맡는 범위의 차이에 가까움. 요청을 객체로 만들어 큐·이력에 두는 일은 Strategy 가 해 주지 않으니 필요하면 Command 를 따로 둠
분기를 메서드로 뽑은 코드 (Strategy 로 오해받는 코드)새 계산 방법을 더할 때 Context 의 계산 코드에 새 방법의 이름(case 값·메서드 이름)을 더해야 하는가새 방법이 새 클래스로 들어오고 방법마다 따로 테스트한 곳에서 보이던 흐름이 여러 타입으로 나뉘고, 고르는 분기는 Client 쪽에 남음

State 와의 차이

구분 기준은 구현 객체들이 같은 계산의 대안인지, 객체가 오가는 상태인지입니다. 코드에서는 요청을 처리한 결과로 다음에 쓸 구현 객체가 정해지는 코드가 있는지부터 봐요. 그 구현들이 서로 다른 상태(받아들이는 요청과 반응이 다른 자리)를 나타내면 State 입니다. 두 패턴은 클래스 그림이 거의 같아서 코드의 한 곳을 봐야 구분돼요. State 로 주문의 결제 흐름을 짠 코드를 봅시다. 결제 대기 상태에서 결제 요청을 받으면 결제 완료 상태로 넘어갑니다.

interface OrderState {
    OrderState pay(Order order);
}

final class AwaitingPayment implements OrderState {
    public OrderState pay(Order order) {
        order.charge();
        return new Paid();              // 다음 상태를 상태 객체가 정한다
    }
}

final class Order {
    private OrderState state = new AwaitingPayment();

    void pay() {
        state = state.pay(this);        // 요청을 처리한 결과로 필드가 바뀐다
    }
}

Order.pay() 는 요청을 처리하면서 state 필드에 새 객체를 넣습니다. AwaitingPayment 와 Paid 는 같은 계산을 다르게 하는 대안이 아니라, 결제 요청이 다시 왔을 때 반응이 달라야 하는 주문의 상태예요. 반면 시나리오 2 의 4단계에서 Checkout 의 전략을 바꾼 것은 요청 처리 흐름이 아니라 Client 였고, Checkout.total() 은 policy 를 읽기만 합니다. 이 차이는 최소 조건이 아니라 이 절의 기준으로 가려요. 요청 처리가 다음 구현을 정하느냐는 두 패턴을 가르는 선이 아니어서 Strategy 의 필수 조건으로 올리지 않았습니다.

여기서 헷갈리기 쉬운 포인트는 다음 객체를 누가 정하는지만 보고 가르려는 것입니다. 위 코드에서 상태 객체가 다음 상태를 돌려주지 않게 바꾸고 Order.pay() 안에서 state = new Paid() 로 전이를 정해도 여전히 State 예요. 다음 상태를 정하는 쪽으로 Context 와 상태 객체 어느 쪽이든 허용되기 때문입니다(근거: GoF State 절 Collaborations). 전이를 누가 정하든 State 예요. 반대로 요청 결과에 따라 Context 가 다음 알고리즘을 고르기만 하고 그 구현들이 상태를 나타내지 않는다면 State 는 아닙니다. 그런 코드는 고르는 분기를 Context 에 두지 말라는 최소 조건 3번에 걸려 Strategy 로도 판정하지 않아요.

                       Strategy (Checkout)          State (Order)
구현 객체가 나타내는 것  같은 계산의 대안               주문이 오가는 상태 (분기하거나 되돌아가도 됨)
구현 객체를 바꾸는 곳    Client 의 설치 코드           대개 요청 처리 흐름 안 (상태 객체 또는 Context)
구현 객체끼리           서로 모름 (시나리오 2 의 1단계)   다음 상태를 알 수도 있음 (Context 가 전이를 정하면 모름)

구현 객체끼리 서로를 아는지도 함께 봅니다. refactoring.guru 는 상태 객체는 서로를 알고 전이를 시작할 수 있지만 전략 객체는 서로를 거의 모른다고 구분해요(refactoring.guru — State). Strategy 를 고르면 요청 처리 흐름에 전이 코드가 없어서, ByWeight 를 지우거나 새 정책을 더할 때 다른 정책 코드는 볼 일이 없습니다. 대신 Strategy 자체는 상태 전이 모델을 주지 않아요. 도메인에 실제 상태 전이가 있다면 그 규칙을 Context 나 별도 상태 모델에 따로 둬야 하고, 그러지 않으면 Client 가 순서를 기억해 매번 알맞은 전략을 설치하게 되어 규칙이 Client 코드 여러 곳에 흩어집니다.

전략은 서로 모르는 대안이고, 상태는 요청에 따라 옮겨 가는 자리다.

Template Method 와의 차이

구분 기준은 바뀌는 계산이 하위 클래스의 재정의로 들어오는지, 필드나 인자로 받은 객체의 연산 호출로 들어오는지입니다. 앞은 상속으로 알고리즘의 일부를 바꾸고 뒤는 위임으로 알고리즘 전체를 바꿔요(근거: GoF Template Method 절 Related Patterns). 상속으로 맺는 관계와 객체로 맺는 관계가 어떻게 다른지는 참고 문서 「GoF 공통 어휘」의 「위임」 항목, 그리고 「클래스 패턴과 객체 패턴」 항목에 있습니다.

abstract class Checkout {
    final long total(Order order) {
        return order.subtotal() + shippingFee(order);   // 계산 순서는 상위 클래스가 고정
    }

    protected abstract long shippingFee(Order order);    // 이 한 단계만 하위 클래스가 채움
}

final class WeightShippingCheckout extends Checkout {
    protected long shippingFee(Order order) {
        return Math.ceilDiv(order.weightGrams(), 1_000) * 1_500;
    }
}

이 코드에서 무게별 배송비로 결제하는 객체는 만들어지는 순간 WeightShippingCheckout 으로 정해지고, 그 객체를 정액 배송비로 바꿀 방법이 없습니다. 클래스가 곧 계산 방법이니까요. 시나리오 2 의 1~3단계를 이 코드에 넣으면 새 요금제는 새 하위 클래스가 되고, 사용 목적의 단서 2 에서 센 대로 할인까지 나뉘면 조합마다 클래스가 생겨요. 계산 순서는 두 쪽 다 고정돼요. Template Method 는 (이 예제에서는) 상위 클래스의 final 메서드가, Strategy 는 시나리오 1 의 Checkout.total() 처럼 Context 메서드가 순서를 정합니다. 달라지는 것은 끼우는 단위예요. 하위 클래스가 상위 클래스의 필드와 protected 연산(하위 클래스에서만 부를 수 있게 열어 둔 메서드)을 바로 쓰던 내부 접근이 사라지고, 전략은 Context 가 넘긴 값이나 공개한 조회 연산으로만 데이터를 얻습니다. 시나리오 1 의 4단계에서 본 통신 부담을 떠안게 되는 거죠.

Command 와의 차이

구분 기준은 구현 객체가 Context 의 요청 처리 중 한 단계를 같은 목적의 다른 방법으로 맡는지, 수행할 요청 하나를 객체로 담고 있는지입니다. 반환값은 기준이 아니에요. 앞쪽이면 구현 객체는 그 요청 처리 흐름 안에서 불리고, 돌려주는 값이 없어도 Strategy 입니다. 뒤쪽이면 요청 객체가 요청 하나를 대표하고, 호출하는 쪽은 그 일이 무엇인지 모른 채 실행 연산만 부릅니다. Command 의 세 역할(Invoker · Receiver · Command 객체)과 Receiver 없이 명령이 스스로 일을 다 하는 모양도 허용된다는 점은 참고 문서 「GoF 공통 어휘」의 「Invoker · Receiver · Command 객체」에 있고, 그래서 필드 모양은 기준으로 쓰지 않아요. refactoring.guru 도 두 패턴이 객체를 어떤 동작으로 매개변수화한다는 점은 같고 목적이 다르다고 봅니다. Command 는 연산 자체를 객체로 바꿔(연산의 매개변수가 객체의 필드가 됨) 실행 지연·큐잉·이력·원격 실행을 가능하게 하고, Strategy 는 같은 일을 하는 다른 방법을 바꿔 끼웁니다(refactoring.guru — Strategy).

Strategy : Context 의 요청 처리 중 한 단계를 같은 목적의 다른 방법으로 맡음 (시나리오 1 의 4·5단계)
  checkout.total(order) 안에서       policy.fee(32000, 2300)               → 3000 또는 4500 을 반환함
  pool.execute(task) 가 거절될 때     handler.rejectedExecution(task, pool)  → 예외 · 그 자리 실행 · 버림 (void)

Command : 요청 하나를 대표하는 객체 (받을 객체 document 를 안에 묶어 둠)
  new PasteCommand(document)         execute() 가 인자 없이 document.paste() 를 부름
  메뉴 항목은 무슨 명령인지 모른 채 execute() 만 부름 (바로 부르든 큐·이력에 두었다 부르든)

Strategy 를 고르면 Context 가 요청 처리 흐름과 넘길 데이터를 정하고 전략의 결과나 동작을 그 자리에서 이어받으므로, 데이터 흐름이 total() 한 메서드 안에서 보입니다. 두 패턴은 서로를 대신하는 선택지라기보다 맡는 범위가 달라서 함께 쓸 수 있어요. 요청 자체를 객체로 만들어 큐에 넣거나 이력으로 남기는 일은 Strategy 가 해 주지 않으니, 그런 요구가 있으면 Command 를 따로 둡니다.

분기를 메서드로 뽑은 코드와의 차이

구분 기준은 새 계산 방법을 더할 때 Context 의 계산 코드에 새 방법의 이름(case 값·메서드 이름)을 더해야 하는지입니다. 같은 파일에 무엇이 들어 있는지는 기준이 아니에요. 새 이름을 더해야 하는 코드라면 계산을 메서드로 나눠 담았을 뿐 Strategy 가 아닙니다.

final class Checkout {
    private final String plan;

    Checkout(String plan) {
        this.plan = plan;
    }

    long total(Order order) {
        long fee = switch (plan) {                 // 방법이 늘면 이 switch 를 고친다
            case "flat" -> flatFee();
            case "weight" -> weightFee(order.weightGrams());
            default -> throw new IllegalArgumentException(plan);
        };
        return order.subtotal() + fee;
    }

    private long flatFee() {
        return 3_000;
    }

    private long weightFee(long weightGrams) {
        return Math.ceilDiv(weightGrams, 1_000) * 1_500;
    }
}

최소 조건으로 보면 flatFee·weightFee 는 공통 연산 모양을 따르는 별도 단위가 아니라 한 클래스의 private 메서드라서 1번부터 빠집니다. 시나리오 3 의 3단계에서 생성자에 일어난 일이 여기서는 total() 안에서 일어나요. 방법이 두어 개로 고정된 코드라면 이 모양이 오히려 읽기 쉽다는 점은 사용 목적의 표와 같습니다. 방법이 계속 늘어나는 코드에서 Strategy 를 고르면 새 방법이 새 클래스로 들어오고, 방법마다 Checkout 없이 따로 테스트할 수 있어요. 대신 한 곳에서 보이던 흐름이 여러 타입으로 나뉩니다. 요금제 문자열을 전략 객체로 바꾸는 분기도 사라지지는 않고, 시나리오 2 의 choosePolicy 처럼 Client 쪽 한 곳으로 모일 뿐이에요.

trait ShippingPolicy {
    fn fee(&self, subtotal: u64, weight_grams: u64) -> u64;
}

struct FlatRate {
    amount: u64,
}

impl ShippingPolicy for FlatRate {
    fn fee(&self, _subtotal: u64, _weight_grams: u64) -> u64 {
        self.amount
    }
}

struct FreeOverThreshold {
    threshold: u64,
    amount: u64,
}

impl ShippingPolicy for FreeOverThreshold {
    fn fee(&self, subtotal: u64, _weight_grams: u64) -> u64 {
        if subtotal >= self.threshold {
            0
        } else {
            self.amount
        }
    }
}

struct ByWeight {
    per_kg: u64,
}

impl ShippingPolicy for ByWeight {
    fn fee(&self, _subtotal: u64, weight_grams: u64) -> u64 {
        weight_grams.div_ceil(1_000) * self.per_kg
    }
}

        Checkout { policy }

        order.subtotal + self.policy.fee(order.subtotal, order.weight_grams)
    }
}

fn choose_policy(plan: &str) -> Box<dyn ShippingPolicy> {

        return ZstdCodec.encode(data);
    }
}

final class Archiver {
    private final Compression compression;

    Archiver(String format) {
        this.compression = format.equals("zstd") ? new Zstd() : new Gzip();
    }

    byte[] pack(byte[] data) {
        return compression.compress(data);
    }
}
    풀이 보기

    풀이 — 빠진 조건은 3번입니다. Compression 을 Gzip·Zstd 가 따로 구현하니 1번을 만족하고, Archiver 가 Compression 타입 필드로 받아 compress 만 부르니 2번도 만족해요. 그런데 생성자가 형식 이름 format 을 받아 그 안에서 Zstd 와 Gzip 중 하나를 고르므로, 고르는 분기가 Context 안에 있습니다. 시나리오 3 의 1단계(생성자가 이름을 받아 고름)와 같은 모양이고, 새 형식이 오면 3단계처럼 Archiver 를 열어야 해요. 생성자를 Archiver(Compression compression) 으로 바꾸고 format.equals("zstd") ? new Zstd() : new Gzip() 를 부르는 쪽 조립 코드로 옮기면 채워집니다.

  2. 아래 Lamp 는 Strategy 와 State 중 어느 쪽인가요? 비교 절의 구분 기준으로 답해 보세요. 이어서 Light.press 가 다음 객체를 돌려주지 않게 고치고 Lamp.press() 안에서 light = (light instanceof Off) ? new On() : new Off(); 로 전이를 정하면 판정이 바뀌는지도 적어 보세요.

    interface Light {
    Light press(Lamp lamp);
}

final class Off implements Light {
    public Light press(Lamp lamp) {
        lamp.powerOn();
        return new On();
    }
}

final class On implements Light {
    public Light press(Lamp lamp) {
        lamp.powerOff();
        return new Off();
    }
}

final class Lamp {
    private Light light = new Off();

    void press() {
        light = light.press(this);
    }

    void powerOn() {
        System.out.println("on");
    }

    void powerOff() {
        System.out.println("off");
    }
}
    풀이 보기

    풀이 — State 입니다. Lamp.press() 가 요청을 처리한 결과로 light 필드에 다음 객체를 넣고, Off·On 은 같은 계산의 대안이 아니라 버튼을 다시 눌렀을 때 반응이 달라지는 램프의 상태예요(「State 와의 차이」의 구분 기준). 전이를 Lamp.press() 안에서 정하도록 고쳐도 판정은 그대로 State 입니다. 다음 상태를 Context 가 정하든 상태 객체가 정하든 State 이기 때문이에요. 다만 instanceof 로 종류를 확인하는 그 코드는 Strategy 로 보면 최소 조건 2번에도 걸립니다.

  3. 이 글의 결제 코드에서 상품 금액을 더하는 일을 Checkout.total() 에서 빼고, 각 ConcreteStrategy 의 fee 가 총액을 돌려주도록 옮겼다고 해 봅시다. 연산의 모양은 그대로라서 세 언어 모두 컴파일은 통과합니다. 그다음 누군가 FreeOverThreshold 를 고치면서 무료 조건일 때 예전처럼 0 을 돌려주게 두면, free-over 줄에서 주문 B 의 출력은 몇 원이 되나요? 시나리오 1 의 6단계가 덧셈을 Context 에 둔 이유 중 무엇을 어긴 결과인지도 짚어 보세요.

    풀이 보기

    풀이 — 0원입니다. 덧셈이 Checkout.total() 에서 빠졌으니 free-over 줄의 주문 B 는 FreeOverThreshold 가 돌려준 값이 그대로 총액이 되고, 58,000 ≥ 50,000 이라 그 값이 0 이에요(출력 줄은 free-over: A=35000 B=0). 시나리오 1 의 6단계가 덧셈을 Context 에 둔 이유는 그 규칙이 요금제와 무관하게 늘 같아서 한 곳에 있어야 한다는 것이었습니다. 전략마다 덧셈을 복제하자 한 전략이 덧셈을 빠뜨렸고, 연산 모양은 그대로라 컴파일러도 막지 못했어요.
