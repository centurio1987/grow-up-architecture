- **2) 비교 — Command를 ‘Receiver와 인자를 필드에 보관하는 객체’로 한정했습니다.** GoF는 Command가 별도 Receiver 없이 작업 전체를 수행하거나 Receiver를 실행 시점에 찾는 구현도 허용합니다. 따라서 필드 보유 여부나 호출 시 데이터 전달 여부로 두 패턴을 확정할 수 없습니다. `PasteCommand`는 대표 사례로 유지하되, 그 구조를 Command 전체의 최소 조건처럼 설명하지 마세요. [GoF Command, Implementation 1 원문](https://www.javier8a.com/itc/bd1/articulo.pdf)

- **3) 구현 일치 — 입력 범위만으로 세 언어의 결과 동일성을 보장할 수 없습니다.** 상품 금액 `9,007,199,254,740,991`, 무게 `0`은 세 타입 모두 정확히 표현합니다. 그런데 정액 배송비를 더하면 Java·Rust의 정확한 결과는 `9,007,199,254,743,991`이고, TypeScript `number`는 `9,007,199,254,743,992`가 됩니다. 해당 JavaScript 덧셈을 직접 확인했습니다. “입력뿐 아니라 배송비·총액·중간 계산도 정확한 표현 범위 안”이라는 전제가 필요합니다. 제시된 두 주문에서는 문제가 없습니다.

- **1) 패턴 정의 — 데이터 전달 방식에서 원전의 한 가지 변형을 빠뜨렸습니다.** “필요한 데이터를 호출에 실어 건넨다”와 4-a·4-b만으로 설명하면, **전략이 Context 참조를 미리 저장하고 호출 때 조회하는 방식**이 제외됩니다. GoF 구현 쟁점 1은 이 방식도 명시합니다. “호출할 때 데이터나 Context를 반드시 전달한다”는 설명을 완화해야 합니다. [GoF Strategy, Implementation 1](https://courses.cs.duke.edu/spring12/cps108/classwork/class10/Strategy_Pattern.pdf)

- **1) 패턴 정의 — 정적 타입 검사를 패턴 성립 조건과 혼동했습니다.** `any`로 바꿔도 실제로 같은 `fee` 계약을 지키는 객체를 주입하고 위임한다면 런타임 협력 구조는 그대로입니다. 잘못된 객체를 넣을 수 있다는 것은 타입 안전성이 약해졌다는 증거이지, 곧바로 Strategy가 사라졌다는 증거는 아닙니다. **추정:** GoF를 TypeScript에 적용한 해석이므로, 정적 선언 요구는 “이 가이드의 구현 규칙”으로 분리하는 편이 정확합니다.

- **3) 구현 설명 — Java `Object`에서 호출하려면 `instanceof` 분기가 필요하다는 설명은 틀렸습니다.** `((ShippingPolicy) policy).fee(...)`처럼 공통 인터페이스로 한 번 캐스팅해 호출할 수 있습니다. 구체 전략별 분기는 필요하지 않습니다. 안전한 설계라는 뜻은 아니지만, 제시된 컴파일 오류가 증명하는 것은 “`Object`에는 `fee` 선언이 없다”까지입니다.

- **2) 비교 — ‘계산 순서는 같고 한 단계만 다르면 Template Method’는 이 글의 Strategy 예제에도 해당합니다.** `Checkout.total()`도 총액 계산 순서를 고정하고 배송비 한 단계만 바꿉니다. 따라서 단계 수는 선택 기준이 아닙니다. 뒤에서 제시한 **상속과 재정의인지, 합성과 위임인지**를 앞부분에서도 기준으로 사용해야 합니다.

- **2) 비교 — State 대비 득실이 실제보다 배타적입니다.** “Strategy를 고르면 상태 전이 규칙을 담을 자리가 없다”는 표현은 부정확합니다. Context나 별도 상태 모델에 전이를 두고 배송비에는 Strategy를 함께 사용할 수 있습니다. “Strategy 자체는 상태 전이 모델을 제공하지 않는다”로 고치세요. State 객체끼리 서로 모르게 전이를 중앙화할 수도 있으므로, 독립적인 구현 추가·삭제 역시 Strategy만의 이점으로 단정하면 안 됩니다.

### 1) 패턴 정의의 정확성 (GoF 1994 원전 기준)

- **원전에 없는 제약을 `[필수]` 최소 조건(3번)으로 단정하여 패턴의 범위를 자의적으로 왜곡함**
  - 본문은 최소 조건 3번에서 *"어떤 전략을 쓸지는 Context 밖에서 정해지고 요청 처리가 그 선택을 바꾸지 않습니다... 여러 전략 중 하나를 고르는 분기가 Context 안에 없고"*를 필수 조건으로 못 박았습니다.
  - **원전 대조**: GoF 원전(p.316, Applicability)은 *"Instead of many conditionals, move related conditional branches into their own Strategy class"*라고 하여 Context의 **비즈니스 연산(operations) 내부**에 얽힌 알고리즘 분기를 캡슐화하라고 했지, Context 내부의 전략 팩토리 메서드나 기본 전략 분기 생성 자체를 전면 금지하지 않았습니다. 원전 Collaborations(p.320)에서도 *"A client **usually** creates and passes a ConcreteStrategy..."*라며 '보통(usually)' 클라이언트가 주입한다고 완화해 표현합니다.
  - 데이터 크기·캐시·런타임 부하에 따라 Context가 요청 처리 중 최적의 전략으로 내부 전환하는 동적 적응형 전략(Adaptive Strategy) 역시 실무와 문헌에서 널리 쓰이는 형태인데, 본문은 이를 "3번이 빠져 Strategy에 못 미친 코드"로 규정하여 원전보다 좁은 자의적 규칙을 만들었습니다.

- **Context와 Strategy 간의 협력 방식에서 원전이 제시한 제3의 통신 경로를 누락함**
  - 본문 동작 절차 4단계는 데이터를 전달하는 경로로 '값 인자 전달(갈래 4-a)'과 'Context 자체를 인자로 전달(갈래 4-b)'의 두 가지만 설명합니다.
  - **원전 대조**: GoF 원전(p.320, Implementation 1)은 *"Alternatively, the strategy can keep a reference to its context, eliminating the need to pass anything at all"*이라 하여, Strategy 객체가 생성 시 Context의 참조를 필드로 유지해 매 호출마다 인자를 넘기지 않고 필요한 데이터를 직접 조회하는 방식을 명시적 대안으로 설명합니다. 본문은 이를 누락하여 통신 모델을 불완전하게 전달하고 있습니다.

- **Flyweight 패턴과의 연계 설명에서 '내재적/외재적 상태' 개념을 왜곡하고 단순화함**
  - 본문 개요 및 최소 조건 5번은 Flyweight 적용 조건을 *"호출 사이에 값을 필드에 남기지 않는"*, *"그 전략의 연산이 자기 필드나 필드가 가리키는 가변 객체에 값을 쓰지 않습니다"*라며 오직 '가변 상태 미보유(호출 간 무상태)'로만 한정했습니다.
  - **원전 대조**: GoF 원전(p.323, Related Patterns; p.195)에서 Strategy가 Flyweight가 되는 핵심은 **내재적 상태(Intrinsic State, 공유 가능한 전략 고유의 불변 설정값)와 외재적 상태(Extrinsic State, 호출 시 Context가 넘기는 데이터)의 분리**입니다. 본문 예제의 `FlatRate(amount)`, `FreeOverThreshold(threshold, amount)`, `ByWeight(perKg)` 역시 내부에 불변 필드(내재적 상태)를 갖고 있습니다. 본문의 표현은 독자에게 "필드가 아예 없는 무상태 객체여야 한다"는 오해를 낳습니다.

- **단서 2(클래스 폭발)에서 Strategy 단독이 아닌 다중 축 합성(Bridge적 상황)을 끌어들여 수식을 도출함 [추정]**
  - 본문은 클래스 폭발의 대수식으로 배송비($m$)와 할인($n$)의 조합을 끌어들여 $(m-1)(n-1)-3$이라는 식을 제시했습니다.
  - 그러나 배송비와 할인이라는 두 개의 직교하는 변량 축은 다중 합성이나 Bridge 패턴에 가까운 논점입니다. 순수한 단일 축 Strategy 패턴에서는 서브클래싱 시 $1+m$개, Strategy 적용 시 $Context(1) + Strategy(1) + m$개로 Strategy를 쓸 때 타입 수가 항상 1개 더 많습니다. 단일 축 패턴의 비용 분석에 굳이 2개 축의 조합 곱을 끌어들인 것은 설명의 전제가 부자연스럽습니다.

### 2) 비교의 타당성 (유사 패턴·안티패턴과의 구분 기준)

- **State 패턴과의 구분을 '의도'가 아닌 '전이 코드 위치'로 기계화하여 비정상적인 판정을 초래함**
  - 본문은 State와의 구분 기준으로 *"요청을 처리한 결과로 다음 구현 객체가 정해지는 코드가 있는지부터 봄"*을 내세우며, Context가 요청 결과에 따라 다음 알고리즘을 바꾸면 "State도 아니고 Strategy에도 못 미친 코드"라고 규정했습니다.
  - **비판**: GoF에서 두 패턴의 근본적 차이는 **의도(Intent)**입니다. State는 '상태 변화에 따른 객체 전체 행동의 변화'이고, Strategy는 '동일 작업에 대한 상호 교체 가능한 알고리즘 군'입니다. State 패턴에서도 Context가 고정 테이블을 통해 상태를 직접 바꿀 수 있고(GoF State Implementation 1), Strategy에서도 성능/환경에 따라 내부 전환이 일어날 수 있습니다. 본문은 기계적 전이 코드 유무만 따지다 보니 정상적인 동적 알고리즘 전환 코드마저 미완성 결함 코드로 몰아세우는 오류를 범합니다.
  - 또한 본문 표에서 State 객체는 *"다음 상태를 알 수 있음"*이라고 단정했으나, Context가 전이를 중앙 제어하는 State 구현에서는 상태 객체들이 서로의 존재를 전혀 모릅니다.

- **Command 패턴과의 비교에서 범주가 다른 트레이드오프(대체재 오인)를 제시함**
  - 본문 비교 표에서 Strategy를 택할 때 '포기하는 것'으로 *"요청 자체를 객체로 만들어 큐·이력에 두는 구조는 따로 주지 않음"*을 들었습니다.
  - **비판**: Command는 '요청(수신자+매개변수+작업)'을 캡슐화하고, Strategy는 '알고리즘의 구현'을 캡슐화합니다. 두 패턴은 상호 배타적인 대체재가 아닙니다. Strategy를 썼다고 해서 요청 큐잉이나 Undo 기능을 잃어버렸다고 서술하는 것은 범주 오류(Category mistake)이며 독자에게 양자택일의 관계라는 착각을 줍니다.

- **Template Method와의 비교에서 핵심 트레이드오프를 누락함**
  - 본문 표에서 Strategy를 택할 때 포기하는 것으로 *"하위 클래스가 상위 클래스의 필드와 protected 연산을 바로 쓰던 접근"*만을 언급했습니다.
  - **비판**: Template Method의 본질적 가치는 상위 클래스가 전체 제어 흐름(스켈레톤)의 불변성을 프레임워크 수준에서 강제(헐리우드 원칙)하는 데 있습니다. Strategy를 택함으로써 실제로 포기하게 되는 것은 '알고리즘 골격에 대한 강력한 제어 통제권'이지, 단순한 `protected` 멤버 접근 권한 수준의 사소한 구현 상세가 아닙니다.

- **단순 분기 코드(안티패턴/오인 코드)를 공식 디자인 패턴과 대등한 층위로 비교 배치함**
  - State, Template Method, Command는 아키텍처적 트레이드오프를 따지는 디자인 패턴인 반면, "분기를 메서드로 뽑은 코드"는 Extract Method 수준의 미완성 리팩터링 상태입니다. 이를 같은 표에 나란히 올려놓아 개념적 층위의 혼선을 유발합니다.

### 3) 구현과 설명의 일치

- **클래스 다이어그램과 본문 설명·구현 코드의 명백한 불일치**
  - 클래스 다이어그램의 `Context`에는 `+request()`만 존재하고 전략 교체/설치 메서드가 전혀 없습니다.
  - 그러나 본문 동작 절차(2단계), 최소 조건 4번, 그리고 3개 언어 구현 코드 전반에서는 `changePolicy(policy)`를 Context의 핵심 API로 정의하고 반복 호출하고 있습니다.
  - 또한 다이어그램의 Strategy는 `+algorithm(data)`로 단일 인자 형태이나, 실제 본문 설명과 구현 코드는 모두 `fee(subtotal, weightGrams)`로 2개의 인자를 전달(갈래 4-a)하고 있어 다이어그램과 구현 코드가 어긋납니다.

- **시퀀스 다이어그램과 본문 시나리오 실행 흐름의 불일치**
  - 시퀀스 다이어그램은 "1회 생성 -> 1회 설치 -> 1회 요청 -> 위임 -> 반환"의 단발성 호출 흐름만을 표현합니다.
  - 하지만 본문 상황 설정과 실제 3개 언어 `main` 코드는 단일 `Checkout` 인스턴스를 유지한 채 `changePolicy`를 호출해 전략을 3회 연속 런타임 교체하며 총 6회의 계산 출력을 실행하는 동적 시나리오입니다. 다이어그램이 실제 시나리오를 제대로 표현하지 못합니다.

- **Client의 입력 처리 구조에서 언어 간 비일관성**
  - Java와 Rust 구현은 `choosePolicy`가 동적 문자열(`String`, `&str`)을 받아 런타임 예외(`IllegalArgumentException`, `panic!`)를 던지는 방어적 분기 구조입니다.
  - 반면 TypeScript 구현은 `type Plan = "flat" | "free-over" | "weight"`라는 정적 유니온 타입을 정의하여 컴파일 타임에 분기를 닫아두었고 `default` 처리조차 없습니다. "세 언어로 똑같이 구현합니다"라는 상황 설정 전제와 달리 언어별 Client 설계 구조가 상이합니다.
