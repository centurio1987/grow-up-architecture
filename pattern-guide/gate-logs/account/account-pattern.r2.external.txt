### 1) 패턴 정의의 정확성

* **[가장 중요] `Account` 패턴의 핵심 Participant인 `Account`의 요약 책임(잔액 계산) 박탈 및 역할 전도**
  * **원전 대조(Fowler, 1996 AP §6.1 / eaaDev [Account]):** Fowler가 정의한 Account 패턴의 의도(Intent)는 "관련된 회계 Entry를 모으고 요약 동작(`balance()`)을 제공하는 컨테이너"다. 원전 다이어그램(그림 6.1)에서도 `Account`가 `Entry[*]`를 연관으로 가지며 `balance(): Quantity` 메서드를 소유하는 주체다.
  * **왜곡:** 본 문서는 이를 'Account 패턴 가이드'라 표방하면서, 정작 코드의 `Account` 클래스에서 `Entry` 목록은 물론 `balance()` 메서드까지 완전히 제거했다. 잔액 계산 책임을 외부 서비스(`GeneralLedger.balanceAsOf`)와 별개 읽기 모델(`AccountBalance`)로 외주화하고, `Entry`의 소유권은 Fowler §6.2의 `Transaction`에 넘겼다. 이는 Account 패턴의 참여자 역할을 껍데기(단순 메타데이터 및 `checkPostable` 검증기)로 전락시키고, 사실상 **Transaction 패턴 중심의 이벤트 소싱 원장**을 다루면서 이름만 Account 패턴이라 붙인 본말전도다.
* **독립된 별개 패턴(Quantity)의 조건을 Account 패턴의 [필수] 조건 4로 규정한 오류**
  * **원전 대조(Fowler, 1996 AP 3장·6장):** `Quantity`(단위를 가진 수량)와 `Money`는 분석 패턴 3장에서 다루는 독립된 패턴이다. Account 패턴(6장)에서 금액의 단위나 Money 객체 사용은 권장되는 협력 관계일 뿐, 단일 통화 도메인에서 기본 정수(`long`)로 Entry를 기록하더라도 "잔액을 저장하지 않고 Entry의 합으로 유도한다"는 Account 패턴의 최소 조건은 성립한다.
  * **왜곡:** 본문 스스로 서두에서 "함께 쓰는 패턴은 Quantity"라고 협력 관계임을 밝혀놓고서, 정작 패턴의 최소 조건 4에서는 이를 `[필수]`로 못박았다. 다른 독립 패턴의 최소 조건을 본 패턴의 필수 정의로 오염시켰다.
* **도메인 감사·복식부기 규칙을 Account 패턴의 [필수] 조건 3으로 일반화 및 단정**
  * **원전 대조(Fowler, eaaDev [Accounting Entry]):** Fowler는 확정(booked) 전에는 Entry 변경을 허용하는 시스템이 흔하다고 서술하며, 비회계 도메인(재고, 단순 포인트)에서는 역분개가 아닌 수정/취소를 허용하기도 한다.
  * **왜곡:** 확정 후 불변 및 역분개(Reversal)를 통한 정정은 복식부기 감사 추적의 규칙이지, 일반화된 분석 패턴으로서의 Account 패턴 자체의 불변 조건이 아니다. 본문 스스로 "정정 방식을 역분개로 정한 것은 이 가이드의 정책"이라고 인정했으므로, 조건 3은 `[선택]` 또는 도메인 제약으로 분류해야 마땅하다.
* **원전에 없는 제약 단정: '순서 무관 합산(덧셈의 교환법칙)'을 Account 성립 조건으로 규정**
  * **원전 대조:** Fowler 원서 그림 6.1의 Entry는 `whenCharged`와 `whenBooked`라는 두 개의 시간 좌표를 갖는다. 실제 금융/회계에서 잔액 계산은 당좌대월 수수료, 날짜별 이자 계산, 마감 시점 등 **시간 순서(ordering)가 필수적으로 관여하는 누적 함수**인 경우가 많다.
  * **왜곡:** 본문 "사용 목적"에서 "순서를 바꿔 더해도 결과가 같아야 Account 후보... 순서대로 적용해야 결과가 나오는 기록은 변경 이력"이라 단정했다. 단순 덧셈의 수학적 성질을 원전에도 없는 Account 패턴의 절대적 판정 기준으로 격상시켰다.

### 2) 비교의 타당성

* **[가장 중요] 대체 관계가 아닌 협력 패턴(`Transaction`)을 양자택일 비교 표에 배치한 범주 오류**
  * 본문 스스로 `Transaction`을 "(함께 쓰는 짝)", "둘은 대체 관계가 아니라 함께 쓰는 관계"라고 인정하면서, "Account를 고르면 얻는 것 / 포기하는 것"이라는 택일적 트레이드오프 비교 표의 한 행으로 배치했다.
  * 표에서 Transaction에 대해 "포기하는 것: Account만 쓰면 짝을 맞추는 검증은 없음"이라고 적었는데, 이는 Account를 선택해서 포기하는 기회비용이 아니라 **단지 Transaction 패턴을 결합하지 않았을 때 결여되는 기능**일 뿐이다. 비교의 전제와 표의 형식이 정면으로 충돌하여 독자에게 양자택일의 오인을 준다.
* **"필드가 원천인 잔액 모델(안티패턴)"과의 구분 기준이 실제 제공한 구현 코드와 모순**
  * 본문은 구분 기준으로 "잔액과 기록이 어긋날 때 무엇을 고치는가 — 기록으로 잔액을 다시 계산하면 Account, 필드를 기준으로 두면 이 모델"이라 정의하고, `CashAccount` 안티패턴을 "원천은 필드이고 로그는 부산물"이라고 비판했다.
  * 그러나 본문이 구현한 `AccountBalance` 읽기 모델은 이벤트가 올 때마다 `balance = next.plus(...)`로 필드를 가산 갱신할 뿐, **잔액 필드가 어긋났을 때 Entry들을 기반으로 재계산(Replay/Recalculate)하는 복구 로직이 코드 어디에도 없다.** 비판 대상인 `CashAccount`의 `balance += amount`와 구조적으로 동일한 델타 누적 방식을 취하고 있어, 본문이 제시한 구분 기준을 코드 스스로 입증하지 못한다.
* **`Event Sourcing`과의 구분 기준 불명확 및 아키텍처 혼선**
  * 구분 기준으로 "상태 변경 전체의 권위 있는 이력인가 vs 금액 결과를 계정별로 모아 더하는가"를 들었으나, 본문의 예제는 `TransactionPosted` 도메인 이벤트를 발행하고 프로젝션(`AccountBalance`)이 이를 구독하는 **전형적인 Event Sourcing + CQRS 아키텍처**다.
  * 본문 스스로도 "겹쳐 쓸 수 있다"고 언급하듯이, 이것이 단순 Account 패턴인지 Event Sourcing 시스템인지 코드 구조상 분별할 수 있는 명확한 경계를 제시하지 못했다("의도가 좁다"는 식의 주관적 서술에 의존).
* **`Temporal Property`와의 비교에서 득실(Trade-off) 서술의 비대칭성**
  * Temporal Property 행에서 "Account를 고르면 포기하는 것"으로 "값을 더할 수 있어야 한다는 전제, 모든 변화를 기록으로 남기는 저장"을 적었다.
  * 이는 패턴 채택의 기회비용이 아니라 **도메인의 전제조건(Prerequisite)과 저장 비용**이다. 반면 Temporal Property를 채택했을 때 얻는 단순함이나 포기해야 하는 내역 추적 불가의 대가는 누락되어 비교가 비대칭적이다.

### 3) 구현과 설명의 일치

* **[가장 중요] Mermaid 클래스 다이어그램과 실제 구현 코드(Java/TS/Rust)의 구조적 전면 불일치**
  * **다이어그램:** `Account` 클래스가 `/balance(기준 시점) Money` 속성/책임을 가지며, `Account "1" -- "*" Entry : 모은다`라는 직접 연관을 맺고 있다.
  * **실제 코드:** Java, TypeScript, Rust 세 언어 모두 `Account` 클래스에는 `Entry` 참조나 컬렉션이 전혀 없고, `/balance` 메서드조차 존재하지 않는다.
  * 잔액 계산은 다이어그램에 없는 `GeneralLedger.balanceAsOf`와 별도 클래스 `AccountBalance`에 흩어져 있다. 클래스 다이어그램의 정적 구조와 실제 구현 코드가 완전히 딴판이다.
* **최소 조건 1([필수])을 코드가 스스로 위반하는 실행 결과 노출**
  * 최소 조건 1: "[필수] 잔액은 Entry 의 합으로 정의됩니다 — 어느 시점의 잔액이든 그 시점까지 확정된 Entry 가운데 그 Account 에 속한 것의 금액 합과 같아요."
  * 그러나 실제 코드 실행 결과:
    `T1 전기 직후 현금: 읽기 모델 0 KRW / Entry 합 100000 KRW`
  * `post()` 호출 직후 `ledger.balance(cash)`를 조회하면 0 KRW가 반환되며, 이는 최소 조건 1의 불변식을 정면으로 위반한다. 결과적 일관성이라는 구현상의 타협 때문에 자신이 세운 `[필수]` 조건을 코드 스스로 깨뜨리고 있다.
* **이벤트 배달 로직(`deliverEvents`)의 복합 분개(Compound Entry) 처리 결함 및 기형적 디스패치**
  * 세 언어 공통: `deliverEvents`에서 `for (const line of event.lines)` 루프를 돌며 라인마다 `apply(event)`를 호출한다.
  * 만약 한 Transaction 내에 동일 계정이 2개 이상의 Entry로 참여하는 복합 분개(예: 수수료와 원금이 분리된 차변 분개)가 발생할 경우, 첫 번째 라인 처리 시 `apply(event)` 내부 루프가 해당 계정의 모든 라인을 합산하고 `lastAppliedSeq = event.position`을 기록한다.
  * 두 번째 동일 계정 라인 처리 시에는 `position <= lastAppliedSeq` 검사에 걸려 조기 리턴(return)된다. 합계는 우연히 맞을지 몰라도, **"라인 루프 안에서 이벤트 전체를 중복 전달하고 내부 플래그로 억제"하는 기형적이고 불안정한 디스패치 구조**다.
* **세 언어(Java, TypeScript, Rust) 간의 불변성 및 안전성 구현 편차**
  * **날짜 비교 안전성:** Java는 `LocalDate.isAfter()`를 통해 날짜 도메인 불변식을 지키지만, TypeScript와 Rust는 날짜를 단순 문자열(`string`, `&'static str`) 사전식 비교(`tx.date > date`)에 의존하며 형식 검증이 없다.
  * **불변성 캡슐화 누수:** Java(`record`, `List.copyOf`)와 Rust(`Vec` 값 복사)는 `Transaction.lines()`의 불변성을 엄격히 보장하지만, TypeScript는 `Entry` 내부의 `AccountAmount` 객체 참조를 그대로 노출하여 외부 변조 위험이 남아 있다.
* **라이프사이클 절차 설명과 코드 실행 순서의 불일치**
  * 본문 7단계 절차 설명에서는 "7. Account 닫기 — 닫힌 계정은 3단계에서 새 Entry를 거절합니다"로 계정 정상 운영 후의 마감 라이프사이클을 서술했다.
  * 그러나 세 언어의 `main()` 예제 코드에서는 `suspense` 계정을 생성하자마자 4번째 줄에서 `close()`를 호출해 미리 닫아버린다. 절차적 설명의 흐름과 예제 코드의 셋업 맥락이 어긋난다.

### 4) DDD 일관성 (분석 패턴 가이드 전용)

* **[가장 중요] 불변식 ③(계정 유효성)과 트랜잭션 경계의 불일치로 인한 동시성 불변식 파괴 취약점**
  * **상황 설정 표:** "③ Entry 가 속할 Account 가 있고 열려 있으며 통화가 같음 → 전기 서비스가 저장 전에 `Account` root 의 `checkPostable` 을 호출, 동기"
  * **비판:** Evans(2003) DDD에서 Aggregate는 불변식을 원자적으로 보장하는 트랜잭션 일관성 경계다. 그러나 본 구현에서 `Account`는 단지 조회되어 `checkPostable`만 호출당할 뿐 변경되거나 락이 걸리지 않으며, 트랜잭션 저장 대상은 오직 `Transaction` Aggregate뿐이다.
  * 멀티스레드/분산 환경에서 스레드 A가 `checkPostable`을 통과한 직후 스레드 B가 `account.close()`를 커밋하면, 스레드 A는 닫힌 계정에 거래를 전기하게 된다. 표에서 "경합은 허용"이라고 주석을 달았으나, 이는 Aggregate를 분리함으로써 발생한 불변식 보장 실패를 무책임하게 방치한 허위 경계(False Boundary)에 불과하다.
* **`Account` Aggregate Root의 도메인 로직 빈곤화(Anemic Model) 및 정체성 상실**
  * **상황 설정 표:** `Account = aggregate root (식별자·이름·계정 종류 id·통화·열림/닫힘만, Entry 목록과 잔액 필드 없음)`
  * DDD에서 Aggregate Root는 도메인의 핵심 비즈니스 행위와 상태 변경을 캡슐화해야 한다. 그러나 본 모델의 `Account`는 `close()`라는 boolean 플래그 변경 외에는 아무런 도메인 행위가 없는 극단적인 빈혈 모델(Anemic Model)이다.
  * 회계의 핵심인 전기, 잔액 계산, 분개 유효성 검증은 모두 `Transaction`과 `GeneralLedger`가 수행한다. DDD 모델링 관점에서는 완벽하게 **Transaction Aggregate Root 중심의 시스템**인데, 본문은 이를 억지로 'Account 패턴'이라 부르며 주객을 전도시키고 있다.
* **불변식 ④(잔액 정의)가 Aggregate 경계 밖으로 완전히 유출됨**
  * **상황 설정 표:** "④ 잔액 = 그 Account 에 속한 Entry 금액의 합 → aggregate 경계 밖의 `AccountBalance` 읽기 모델이 ... 갱신"
  * DDD에서 핵심 도메인 규칙이나 파생 속성은 Aggregate 내부나 엄밀한 도메인 서비스에서 관리되어야 한다. 잔액을 "aggregate 경계 밖의 읽기 모델"로 추방함으로써 도메인 모델 내 어떤 Aggregate도 잔액의 일관성을 보증하지 못한다.
  * 리포지토리인 `GeneralLedger`에 `balanceAsOf`를 두어 트랜잭션 전체를 풀스캔하여 잔액을 구하는 임시 쿼리로 때운 것은, 도메인 모델의 캡슐화 실패를 인프라/리포지토리에 전가한 전형적인 모델링 결함이다.
* **상황 설정 표의 ID 참조 원칙과 도메인 이벤트(`TransactionPosted`) 설계의 불일치**
  * **상황 설정 표:** "타 aggregate 참조 방식: id 참조 ... `Entry` → `Account`는 `AccountId`"
  * 그러나 도메인 이벤트인 `TransactionPosted(long position, List<AccountAmount> lines)`에는 정작 **이벤트의 발생 원천인 `TransactionId`가 누락**되어 있다.
  * DDD에서 도메인 이벤트는 발생한 사실의 완전한 식별 컨텍스트를 제공해야 하며, 역분개 추적이나 이벤트 중복 방지(멱등성)를 위해서는 Aggregate Root 식별자가 필수적이다. 표에서는 엄격한 ID 참조를 표방하면서 정작 핵심 도메인 이벤트에서 루트 ID를 누락했다.
