[Q3] 답변: 상대적으로 설명이 얇은 ③ 계정 존재·열림·통화 조건을 고른다. Account root가 수용 조건을 검사하고 전기 서비스가 저장 전에 호출하지만, Transaction과 별도 경계여서 확인 직후의 계정 닫기까지 막지는 않는다. 두 root를 원장 전체 aggregate로 합치면 이 경합을 막는 대신, T2 전기와 무관한 가수금 닫기도 같은 변경 단위를 두고 충돌한다.
[Q3] 인용: “③ Entry 가 속할 Account 가 있고 열려 있으며 통화가 같음 → 전기 서비스가 저장 전에 `Account` root 의 `checkPostable` 을 호출, 동기 (계정 닫기와 같은 순간에 일어난 전기의 경합은 허용, 통화가 다른 금액의 덧셈은 `Money` 가 거절)” / “| ③ 계정 존재 · 열림 · 통화 | 이 가이드 그대로 | `checkPostable` 통과 직후 다른 요청이 가수금을 닫음 | 닫힌 가수금에 전기가 확정될 수 있음. 확정안 I5 가 허용한 경합이고, 막으려면 아래 두 행이나 위 합친 행의 비용을 치러야 함 |” / “| ① · ③ | Account 와 Transaction 을 한 aggregate(원장 전체)로 합침 | T2 전기와 가수금 닫기가 같은 순간에 옴 | 합 0 과 계정 열림은 한 경계에서 함께 지켜지지만, 서로 관계없는 두 요청이 같은 aggregate 를 고쳐 한쪽은 충돌 후 다시 시도. 모든 전기와 계정 변경이 한 줄로 늘어섬 |”

[Q4] 답변: 비교 설명이 상대적으로 얇은 Event Sourcing을 고른다. 본문의 Account 구현은 계정의 현재 상태를 저장하고 금액만 Entry 합으로 구하므로 이름 변경 이력을 답하지 못한다. 대비 사례는 계정 개설·이름 변경·닫기까지 이벤트로 저장하고 순서대로 적용하여 Account 상태를 복원한다. 구분 기준은 현재 상태를 직접 저장하는지, 이벤트에서 복원하는지다.
[Q4] 인용: “계정 이름 이력     물을 수 없음. 이름을 바꾸면 현재 값만 남음” / “저장소에 있는 것   AccountOpened(1010, 현금) · AccountRenamed(1010, 보통예금)” / “Account 객체       이벤트를 순서대로 적용해 이름·열림/닫힘·잔액을 모두 다시 만듦” / “저장된 원천이 무엇인가 — 계정 이름·열림/닫힘 같은 현재 상태까지 이벤트에서 다시 만들면 Event Sourcing, 현재 상태는 그대로 저장하고 금액 결과만 Entry 로 모아 더하면 Account”

[Q1] 답변: 
(a) 출발점: 계정마다 잔액 숫자 필드 하나를 두고 돈이 오갈 때마다 그 숫자를 고쳐 쓰는 모델(`Before — 잔액을 숫자 하나로 고쳐 쓰는 모델`).
(b) 무너지는 지점: 4/5에 임대료 30,000원을 지급했다가 실제 금액이 25,000원임이 밝혀져 4/6에 담당자가 5,000원을 더해 잔액 75,000원으로 맞추는 정정 상황에서, 시스템에는 75,000원 숫자만 남아 4/5 마감 때의 현금이 얼마였는지 계산할 재료가 없고 4/6의 +5,000원의 출처를 설명할 기록이 사라지며 75,000원이 맞는 값인지 확인할 기준조차 없어 모델이 무너진다.
[Q1] 인용: 
(a) "작은 회사의 회계 프로그램이 계정마다 잔액 숫자 하나를 두고, 돈이 오갈 때마다 그 숫자를 고쳐 쓴다고 해 봅시다. 4월 1일에 매출 100,000원이 현금으로 들어왔고 4월 5일에 임대료 30,000원을 냈어요. 그런데 실제 임대료는 25,000원이어서, 담당자가 4월 6일에 현금 잔액에 5,000원을 더해 맞췄습니다."
(b) "시스템에 남는 것: 현금 잔액 = 75,000   (왼쪽 줄들은 어디에도 없음)
  "4/5 마감 때 현금은 얼마였나요?"   → 계산할 재료가 없음
  "4/6 의 +5,000 은 무엇이었나요?"    → 설명할 기록이 없음

마감 보고서를 다시 뽑거나 감사에서 5,000원의 출처를 물으면 숫자 하나로는 답할 수 없어요. 75,000 이 맞는 값인지 확인할 기준조차 없습니다."

[Q2] 답변: 
문제를 푸는 결정적 구조는 "잔액을 저장해 두는 값으로 보지 않고 확정된 Entry 기록을 남기며, 잔액은 특정 시점까지 계정에 속한 Entry 금액의 합으로 계산하고 정정 시에도 부호가 반대인 역분개 Entry를 새로 더하는 구조"이며, 분석 층위의 `Account`(계정) 개념이 Entry를 모으고 그 합인 잔액에 답하는 책임을 진다.
[Q2] 인용: 
(i) 개념 정의: "- **Account**(계정) — 금액 기록을 모으고 그 합을 알려 주는 개념입니다.
  - 기본 책임(원서 그림 6.1 · eaaDev Account): 자기에게 속한 Entry 를 모으는 기준이 되어, 그 합인 잔액에 답합니다. 그러려면 식별자로 자기를 구별하고, 받을 금액의 통화를 정해야 해요."
(ii) 무너짐을 막는 이유: "6. **틀린 기록을 역분개로 정정.** T2 금액이 틀렸다는 걸 알게 돼도 T2 는 그대로 둡니다. T2 의 Entry 부호를 뒤집은 T3(역분개)과 올바른 금액의 T4 를 새로 만들어 3·4단계를 다시 거쳐요.
   - 결과: 4/6 현금 = 70,000(4/5 까지의 합) + 30,000(T3 #2) − 25,000(T4 #2) = 75,000 입니다. 4/5 현금은 여전히 70,000 이에요. T3·T4 의 날짜가 4/6 이라 4/5 까지의 합에 들어가지 않으니까요.
   - 왜 고치지 않는가: T2 #2 의 −30,000 을 −25,000 으로 고치면 4/5 현금이 75,000 으로 바뀝니다. 4/5 에 70,000 으로 이미 낸 보고서와 지금 계산이 어긋나는데, 어느 쪽이 맞는지 보여 줄 기록이 남지 않아요."

[Q3] 답변: 
본문 설명이 가장 얇은 불변식은 "전기된 Entry는 불변"(불변식 ②)이다. 이 불변식은 `Transaction` aggregate root 경계 안에서 지켜진다(생성 뒤 상태를 바꾸는 메서드를 두지 않고 Entry 객체 대신 값만 내보냄). 만약 경계를 바꾸어 Entry가 홀로 존재하는 크기 1의 별도 aggregate가 되면, 전기가 끝난 T2에 속한다는 Entry를 나중에 한 건 더 저장하는 동작이 일어날 때 T2라는 묶음이 닫혔음을 지킬 root가 없어져, 4/7에 T2 소속 현금 −5,000원을 추가 저장할 경우 4/5 현금이 65,000원으로 바뀌고 T2 합도 −5,000원이 되어 불변식 ②와 거래 균형(불변식 ①)이 깨진다.
[Q3] 인용: 
"② 전기된 Entry 는 불변 → `Transaction` root, 생성 뒤 상태를 바꾸는 메서드가 없고 Entry 객체를 밖으로 내보내지 않음"
"전기가 끝난 T2 에 속한다는 Entry 를 나중에 한 건 더 저장 | 각 Entry 는 스스로 바뀌지 않아도, T2 라는 묶음이 닫혔다는 것을 지킬 root 가 없어 막을 곳이 없음. 4/7 에 T2 소속 현금 −5,000 을 더하면 4/5 현금이 65,000 으로 바뀌고 T2 합은 −5,000. 역분개도 T2 의 다리를 조회로 모으므로 언제 모으느냐에 따라 다른 T3 이 만들어짐"

[Q4] 답변: 
본문 설명이 가장 얇은 반례는 "현재 값만 필요할 때의 게시글 조회수"이다. 본문은 이를 `Post { viewCount } · view() 가 viewCount 에 1 을 더함`이라는 구체 모델 형태로 제시한다. Account 패턴과 가르는 기준은 현재 값이 한 계정에 속한 기록들의 합으로 정의되는지 여부이며, 모델에서는 "기록 값 타입에 단위를 확인하는 덧셈과 0이 있는지, 조회 코드가 기록을 더하는지 아니면 과거 값이나 변경 한 건을 묻지 않고 필드 하나만 읽는지"로 확인한다.
[Q4] 인용: 
"현재 값만 필요할 때. 게시글 조회수처럼 지금 몇인지만 묻는 값은 필드 하나로 충분하다고 Fowler 도 적었습니다. Account 로 만들면 증가 한 번마다 Entry 가 쌓이고 조회 때 합산이나 캐시 동기화를 챙겨야 하는데, 그렇게 해서 새로 답할 수 있는 질문은 없어요."
"조회수 — 필드로 충분
  모양      Post { viewCount } · view() 가 viewCount 에 1 을 더함
  묻는 것   지금 몇인가 → 필드 하나로 답이 끝남. 과거 값이나 변경 한 건을 묻는 코드가 없음"
"넷을 가르는 질문은 하나예요. 현재 값이 한 계정에 속한 기록들의 합으로 정의되는가. 조회수는 합을 물을 과거가 없고... 모델에서는 기록 값 타입에 단위를 확인하는 덧셈과 0 이 있는지, 조회 코드가 기록을 더하는지 아니면 기간을 찾거나 순서대로 적용하는지를 보면 됩니다."

[Q5] 답변:
