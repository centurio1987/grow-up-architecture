- **[2] Temporal Property와 Account를 ‘기간 검색 대 합산’으로 배타적으로 가르는 기준은 부정확합니다.**

Account의 잔액을 시간에 따라 조회하는 인터페이스와 함께 사용할 수도 있습니다. “조회 코드가 더하면 Account, 기간을 찾으면 Temporal Property”는 **이 글의 두 예제 구현을 구분하는 관찰**로 제한해야 합니다. [Fowler, Temporal Property](https://martinfowler.com/eaaDev/TemporalProperty.html)

- **[1 / 추정] ‘원전이 성립 요건으로 적은 것만 `[필수]`’이라는 선언은 제시한 근거보다 강합니다.**

[Fowler, Account](https://martinfowler.com/eaaDev/Account.html)

Rust의 `&mut GeneralLedger`는 같은 인스턴스의 변경을 직렬화하고, TypeScript의 해당 메서드는 동기 실행이며, Java는 동기화가 없습니다. **공통된 순차 예제와 향후 저장소의 동시성 정책을 구분**해야 합니다.

- **[2·4] id 참조가 최신 조회와 덮어쓰기 방지를 보장한다는 결론은 과장입니다.**  
  “id로만 가리키면 필요할 때마다 지금 값을 새로 읽어야 한다”는 보장은 없습니다. 저장소가 캐시나 오래된 스냅숏을 반환할 수도 있고, 조회 직후 상태가 바뀔 수도 있습니다. 반대로 객체 참조도 cascade 저장을 하지 않으면 제시한 덮어쓰기를 일으키지 않습니다. 문서가 처음에는 “그래프를 함께 저장한다”는 조건을 붙였지만, 마지막에는 그 조건을 잊고 id 자체의 보장처럼 결론 냅니다. 코드의 id 참조는 상황 설정과 일치하되, **정합성 보장은 저장·동시성 정책의 몫**입니다. [Vernon, Effective Aggregate Design Part II](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf)

- **[1·2] ‘확정 Entry 불변’이 감사·과거 보고에 반드시 필요하다는 설명도 지나칩니다.**  
  선택 조건 3에서는 감사 요구가 생기면 이 조건이 필요하다고 하고, 없으면 과거를 묻는 질문에 답하지 못한다고 단정합니다. 그러나 변경 전 버전이나 별도 변경 이력을 보존하는 설계도 가능합니다. 반대로 이 예제처럼 소급 전기를 허용하면 Entry 불변만으로 당시 보고서가 재현되지 않습니다. 정확한 설명은 **“이 예제는 수정 이력을 별도로 보존하지 않으므로, 삭제·덮어쓰기를 하면 이전 기록을 잃는다”**입니다. Fowler의 후속 글도 Entry 변경 가능 시점을 설계 질문과 흔한 규칙으로 다룹니다. [Fowler, Accounting Entry](https://martinfowler.com/eaaDev/AccountingEntry.html)

- **[3] `balance()`는 설명에서 말하는 ‘현재 잔액’의 캐시가 아닙니다.**  
  미래 날짜의 거래도 전기되면 즉시 읽기 모델에 더해지므로, 이벤트 전달을 마쳐도 `balance()`와 `balanceAsOf(today)`는 다를 수 있습니다. 이 차이는 반영 지연이 아니라 **집계 대상 자체의 차이**입니다. 본문에 주의문은 있지만 “현재 잔액 캐시”, “Entry 합과 같음”이라는 명칭은 계속 혼동을 유발합니다. `postedTotal`처럼 의미를 드러내거나, 현재일 기준 잔액과 전기 완료분 총합을 별도 API로 나누는 편이 정확합니다.

- **[3·4] Entry의 식별 규칙은 설명보다 구현이 약합니다.**  
  표는 식별자를 `거래 id + seq`라고 하지만 Java `equals`, TypeScript `sameAs`, Rust `PartialEq`는 `seq`만 비교합니다. 따라서 서로 다른 거래의 첫 Entry도 비교에 넣으면 같다고 나옵니다. 현재 캡슐화된 경로에서는 거래 간 비교가 발생하지 않아 즉시 잔액 오류로 이어지지는 않습니다. 그래도 “같은 거래 안에서만 비교한다”는 것은 구현이 강제하는 조건이 아닙니다. 거래 범위를 받는 비교로 제한하거나 소유 거래 id를 포함해야 합니다.

- **[2] 비교 표의 ‘얻는 것·포기하는 것’이 일관된 비교가 아닙니다.**  
  “조회 때 합산 비용”, “변화를 모두 Entry로 남기는 저장”은 포기하는 기능이 아니라 추가 비용입니다. Transaction 행은 함께 쓸 때와 생략할 때를 비교하고, 다른 행은 대체 모델을 비교합니다. “대안 대비 이점 / 추가 비용·제약 / 함께 사용 가능 여부”로 나누면 혼동이 줄어듭니다. Temporal Property가 더 단순하다는 일반화 역시 근거가 약합니다. Fowler도 Account가 더 복잡한지는 확신하지 않는다고 적었습니다. [Fowler, Account](https://martinfowler.com/eaaDev/Account.html)
