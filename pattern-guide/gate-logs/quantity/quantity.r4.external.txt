핵심 환산 절차와 주 시나리오의 재고 검사 순서는 일치합니다. 다만 **원전의 정의와 이 가이드의 구현 규약을 섞어 패턴 충족 여부를 단정하는 부분**은 수정이 필요합니다.

- **1) 패턴 정의 — [추정] `[필수] 3`을 Quantity의 보편적 판정 기준으로 삼을 근거가 부족합니다.** Figure 3.2의 `=`와 2016년 Value Object 글만으로 “명시적인 값 비교 수단이 없으면 Quantity가 아니다”까지 도출하기는 어렵습니다. 특히 문제 1의 탈락 판정과 문제 2의 “역직렬화해야 비로소 Quantity”라는 결론은 분석 모델의 개념과 구현 완성도를 혼동합니다. “이 가이드가 요구하는 Quantity 구현 조건”으로 범위를 좁히세요. 확인한 도해는 초판 자체가 아니라 **1999년 UML 번역 자료**이므로, 초판의 필수 조건이라고 단정하려면 본문 근거가 더 필요합니다. [Fowler 도해](https://martinfowler.com/apsupp/apchap3.pdf), [Value Object](https://martinfowler.com/bliki/ValueObject.html)

- **3) 구현과 설명 — 문제 1은 `[필수] 2` 적용이 일관되지 않습니다.** 최소 조건은 “더하기·빼기와 크기 비교”를 요구하지만 `Amount`에는 `plus`만 있습니다. 그런데 풀이에서는 조건 2를 충족하고 `equals`만 추가하면 된다고 합니다. 연산 제공 자체가 필수인지, **제공하는 연산에만 단위 안전성을 요구하는지**를 먼저 정해야 합니다. 후자라면 최소 조건의 문구를 바꾸세요.

- **2) 비교 — “상대의 단위를 읽는가”는 일반적인 구분 기준으로 너무 좁습니다.** `Weight<Kg>`처럼 타입으로 단위를 제한하거나, 생성 시 모든 값을 g로 정규화한 타입은 연산에서 `other.unit`을 읽지 않아도 안전합니다. 제시한 `Weight(double, String)`의 오류는 맞지만, 이를 모든 구현의 판정 기준으로 확장하면 정상적인 Quantity를 탈락시킵니다. 기준은 **호환되지 않는 단위의 산술을 방지하는가**여야 합니다.

- **4) DDD 일관성 — TypeScript만 실행 시점에 root를 우회할 수 있습니다.** `IngredientStock`의 `private onHandValue`는 JavaScript로 변환하면 일반 속성입니다. JavaScript 호출자는 `stock.onHandValue = Quantity.of("-1", Unit.G)`로 음수 재고를 직접 넣을 수 있고, `readonly id`도 재대입할 수 있습니다. 본문은 VO와 상수 표에 대해서는 런타임 우회까지 차단하면서 root에는 같은 보장을 적용하지 않았습니다. 타입 검사된 호출만 전제한다고 명시하거나, `#onHandValue`와 식별자 접근자를 사용해야 합니다. 정적 TypeScript 사용만 전제한다면 이 지적은 해당하지 않습니다.

- **3) 구현과 설명 — Rust에는 단순한 표현 범위 차이 이상의 입출력 비대칭이 있습니다.** `Quantity::of("-9223372036854775.808", Unit::G)`는 내부 값이 정확히 `i64::MIN`이라 표현 가능하지만, 양수 `magnitude`를 먼저 만들기 때문에 실패합니다. 반면 `Quantity::of("-9223372036854775.807", Unit::G)?.minus(Quantity::of("0.001", Unit::G)?)`는 그 값을 만들 수 있습니다. 즉 **연산으로 만든 값을 출력한 뒤 다시 읽으면 실패**합니다. 음수 최솟값을 처리하도록 파서를 고쳐야 합니다. 이미 설명한 일반적인 오버플로 차이와는 별개입니다.

- **1) 패턴 정의 — Conversion Ratio와 Quantity의 책임 경계가 앞뒤에서 달라집니다.** 개념 정의는 “단위가 다르면 ConversionRatio를 찾아 협력”한다고 단정하지만, 최소 조건 5에서는 선택이고 확장 시나리오에서는 도메인 서비스가 환산합니다. 앞 문장을 “이 예제에서는”으로 제한해야 합니다. Fowler의 후속 설명도 다른 단위의 연산을 거부하는 구현과 별도 변환 객체를 허용합니다. [Fowler, Quantity](https://martinfowler.com/eaaDev/Quantity.html)

- **2) 비교 — Money의 식별 기준에 반올림 정책을 필수처럼 끼워 넣었습니다.** “단위가 통화이고 통화별 자릿수·반올림 규칙이 붙는가”라고 쓰면, 정수 원화만 더하고 빼는 Money가 제외됩니다. 금전적 값을 나타내는 것이 핵심이고, 반올림·배분은 제공하는 연산과 업무에 따라 필요한 정책입니다. 최소 조건 6의 “통화의 최소 단위가 이 규칙”도 부정확합니다. 최소 단위만으로 반올림 시점·방식·잔여액 배분은 결정되지 않습니다. [Fowler, Money](https://martinfowler.com/eaaCatalog/money.html)

- **4) DDD 일관성 — 경계 변경의 위험을 설명하면서 현재 예제에 없는 전제를 사용합니다.** 재료 객체 참조의 반례는 “포대 무게 변경이 다음 입고 환산을 바꾼다”고 하지만, 현재 코드는 카탈로그의 포장 비율을 조회하지 않습니다. 이는 확장 시나리오에서만 성립합니다. 또한 다른 aggregate의 **root 객체를 참조한다는 사실만으로** 불변식 우회가 발생하지는 않습니다. 이 예제의 id 참조 정책 위반과, 가변 객체 접근·복수 aggregate 변경이 만드는 위험을 분리하세요.

- **2) 비교 — 규칙 배치를 바꾼 반례들이 변경 자체와 잘못된 구현을 섞습니다.** root가 수치·단위를 두 필드로 가져도 함께 검증·갱신할 수 있고, 재고마다 환산 표를 주입해도 동일한 불변 표를 사용할 수 있습니다. “수치만 수정한다”, “비율 100을 잘못 넣는다”는 추가 실수가 있어야 제시한 장애가 발생합니다. 현재 표는 대안의 필연적인 결함처럼 읽힙니다. 중복 검증이나 설정 불일치 **가능성이 늘어난다**는 수준으로 고쳐야 합니다.

제공된 `quantity-model.png`는 실제 이미지가 없어 관계·다중도와 코드의 일치 여부를 판정할 수 없습니다. 원전 초판 전문도 확인하지 못했으므로, 위의 원전 필수 조건 관련 지적은 표시한 대로 추정입니다.
