가장 큰 약점은 **예제에서 선택한 동일성 규칙을 패턴의 필수 조건으로 올린 것**입니다. 원전 본문 전체를 직접 대조하지 못한 판단은 아래에 ‘추정’으로 표시했습니다.

- **1) 패턴 정의 — `[필수] 3`의 “2.5 kg과 2500 g은 같은 값이 아니다”는 근거가 부족합니다.** Figure 3.2에 `=`가 있다는 사실은 동등성 연산을 뒷받침하지만, 그것이 반드시 *환산하지 않은 수치·단위 쌍의 동일성*이어야 한다는 뜻은 아닙니다. 두 값을 환산해 동등하게 보는 구현을 패턴 밖으로 밀어낼 이유가 제시되지 않았습니다. **표현 동등성과 양의 동등성을 구분하는 것은 이 예제의 정책**으로 내려야 합니다. **추정:** 이를 Fowler 원전의 필수 조건으로 제시하는 것은 과도한 해석입니다. [Fowler의 보충 도식](https://martinfowler.com/apsupp/apchap3.pdf), [Value Object](https://martinfowler.com/bliki/ValueObject.html)

- **1) 패턴 정의 — 곱셈·나눗셈에서 “새 단위가 나온다”는 설명은 지나치게 단정적입니다.** `2 m / 1 m`은 무차원 값이고, `2 m/s × 3 s`는 기존 단위인 m으로 단순화됩니다. 합성 단위 객체가 반드시 새로 필요한 것이 아닙니다. `[필수] 2`는 “차원과 단위를 계산하고 약분·무차원 결과를 처리한다”로, `[선택] 6`은 “그 표현에 CompoundUnit을 사용한다”로 구분해야 합니다.

- **1) 패턴 정의 — ConversionRatio가 필수 참여자인 것처럼 시작했다가 뒤에서 선택으로 바뀝니다.** 개념 정의의 “단위가 다르면 ConversionRatio를 찾아 협력”과 동작 절차는 특정 구현의 협력을 일반 정의처럼 서술합니다. 그런데 최소 조건에서는 환산 없이 거부해도 Quantity라고 합니다. 정의에는 “환산을 지원한다면”이라는 조건이 필요합니다. Fowler의 후속 설명도 단위가 다르면 거부하고 호출자에게 환산을 맡기는 구현을 허용합니다. [Fowler, Quantity](https://martinfowler.com/eaaDev/Quantity.html)

- **2) 비교의 타당성 — Money를 가르는 기준에 반올림 구현 여부를 넣으면 오분류합니다.** “통화이고 통화별 자릿수·반올림 규칙이 붙는가”를 판정 기준으로 쓰면, 정수 원화만 보관하고 더하기·빼기만 제공하는 Money는 제외됩니다. 핵심 기준은 **금전적 가치를 표현하는가**이고, 자릿수·반올림·배분은 제공하는 연산과 업무에 따라 필요한 책임입니다. 또한 “Money에서는 통화의 최소 단위가 이 규칙”이라는 표현도 보관 정밀도와 지급 시 반올림 단위를 혼동합니다. [Fowler, Money](https://martinfowler.com/eaaCatalog/money.html)

- **2) 비교의 타당성 — “원시 숫자 필드(Primitive Obsession)”와 “래퍼는 틀린 합을 낸다”는 비교가 상대를 과장합니다.** 본문 스스로 조회수에는 원시 정수가 적합하다고 했으므로 원시 숫자 필드 자체를 안티패턴과 동일시하면 모순입니다. 또한 연산을 제공하지 않는 단위 래퍼는 틀린 합을 내지 않습니다. 제시한 `Weight`의 문제는 **연산이 없다는 것보다 잘못된 연산을 제공한다는 것**입니다. 비교 대상을 “단위 처리가 필요한데 원시 수치로 계산하는 설계”와 “상대 단위를 무시하는 산술 구현”으로 좁혀야 합니다.

- **3) 구현과 설명 — 문제 1의 “값 비교 수단 하나만 더하면 조건 셋을 갖춘다”는 최소 조건 2와 맞지 않습니다.** `Amount`에는 `plus`만 있고 크기 비교가 없습니다. 조건 2에서 크기 비교 제공까지 필수로 요구한다면 `equals`만 추가해서는 부족합니다. 반대로 *제공하는 연산에 대해서만* 단위 확인을 요구한다면 최소 조건을 그렇게 명시해야 합니다. 현재는 필수 기능 목록과 구현된 기능의 올바름을 섞어 판정합니다.

- **3) 구현과 설명 — TypeScript 공유 환산표의 “실행 중에 바꿀 수 없다”는 보장은 불완전합니다.** `Object.freeze([...])`는 배열을 얼리지만, `ConversionRatio.ALL`이라는 정적 속성의 재할당까지 막지는 않습니다. JavaScript 실행 환경에서는 `ConversionRatio.ALL = []`로 표를 교체할 수 있습니다. `readonly`는 런타임 보호가 아닙니다. 배열 내용 변경 방지와 표 자체의 교체 방지를 구분하거나, 클래스의 정적 속성도 보호해야 합니다. [TypeScript 클래스 문서](https://www.typescriptlang.org/docs/handbook/2/classes.html)

- **4) DDD 일관성 — “재료 하나마다 재고 기록 하나”라는 전제를 코드가 보장하지 않습니다.** 서로 다른 `StockId`에 동일한 `IngredientId`를 넣어 재고 두 개를 만들 수 있습니다. 이는 개별 root의 음수 방지와 달리 여러 aggregate에 걸친 유일성 조건입니다. 저장소·DB의 유일성 제약이나 생성 정책이 담당한다고 밝히거나, 예제 밖의 전제라고 명시해야 합니다.

- **4) DDD 일관성 — 배치 변경의 반례가 실제 설정과 다른 상황을 끌어옵니다.** 재료 객체 참조의 위험을 설명하면서 “포대 무게 변경이 다음 입고 환산을 바꾼다”고 하지만, 현재 코드는 카탈로그의 포장 비율을 사용하지 않습니다. 비율을 root에 주입하는 반례 역시 `0.3 kg` 입고가 즉시 g으로 저장된다고 설명하지만, 현재 코드는 같은 단위끼리 계산하면 kg을 유지합니다. 두 반례 모두 **새 상황·새 호출 조건이 추가되어야 성립**하므로, 기존 경계 변경만으로 발생하는 결과처럼 쓰면 안 됩니다.

인정할 부분: 제시된 기본 시나리오의 환산 방향, 음수 검사 후 보유량 교체, 다른 aggregate의 ID 참조는 세 구현에서 일관됩니다.

### 4) DDD 일관성

* **Aggregate Root가 내부 상태 단위의 일관성을 통제하지 못하고 VO에 휘둘림 [가장 치명적]**
  * **내용**: 상황 설정 표는 `IngredientStock`을 보유량 불변식을 지키는 Aggregate Root로 배정했고, 생성자에서 `Unit.KG`를 받아 `0 kg`으로 초기화합니다. 하지만 `consume(Quantity.of("50", Unit.G).times(2))`를 호출하는 순간, `onHand`의 내부 저장 단위가 `kg`에서 `g`로 영구 전환됩니다(출력 3행: `보유 200 g`).
  * **문제점**: Aggregate Root의 존재 이유는 내부 상태와 불변식(Invariant)의 일관성을 캡슐화하여 보호하는 것입니다. 그러나 현재 코드는 외부에서 어떤 단위의 인자가 들어오느냐에 따라 Root 내부의 핵심 속성 단위가 제멋대로 바뀝니다. 본문은 "어느 단위로 적어 두는지는 요구 전제가 아니라서 크기만 맞으면 된다"고 변명하지만, Aggregate Root가 자신의 기준 단위조차 통제하지 못하고 VO 연산의 공통 단위 선택 로직(`to` 우선)에 내부 표현을 내맡긴 것은 Evans DDD가 정의한 Aggregate Root의 경계 보호 책임과 어긋납니다.
* **`ConversionRatio.ALL`을 '불변 VO'로 분류했으나 실제로는 전역 레지스트리로 동작함**
  * **내용**: 상황 설정 표에서는 `ConversionRatio`를 "어느 aggregate에도 속하지 않는 불변 VO"라고 명시했습니다. 하지만 실제 코드에서 `Quantity`의 모든 사칙연산과 비교 메서드는 전역 정적 상수인 `ConversionRatio.ALL`을 직접 조회합니다.
  * **문제점**: Evans DDD에서 Value Object의 연산은 외부 전역 상태나 외부 저장소에 의존하지 않고 전달받은 인자만으로 닫혀 있는 '부작용 없는 순수 함수(Side-Effect-Free Functions)'여야 합니다. VO 내부에서 전역 컬렉션(`ALL`)을 직접 결합해 조회하는 구조는 순수 VO가 아니라 사실상 전역 인메모리 리포지토리/서비스에 강결합된 안티패턴입니다.

### 1) 패턴 정의의 정확성

* **원전에 없는 제약을 `[필수]` 조건으로 단정 (Quantity 동치성 정의의 왜곡)**
  * **내용**: 본문은 `[필수] 3`에서 "2.5 kg 과 2500 g 은 같은 양이어도 같은 값은 아니에요"라며, 수치와 단위가 모두 물리적으로 일치해야만 값으로 다루는 것(`equals`)이고 환산 비교는 크기 비교(`compareTo`)의 몫이라고 단정했습니다.
  * **원전 대조**: Fowler의 『Analysis Patterns』 §3.1(p.37) 원전에는 *"We would expect two quantities to be equal if their amounts and units are equal. In addition, we might say that two quantities are equal if we have a conversion ratio between their units and the converted amount is equal (e.g., 500g = 0.5kg)."* 라고 명시되어 있습니다. 즉, 환산 가능한 동일 양을 equal(`=`)로 취급하는 모델링 역시 원전이 공식 인정한 유효한 정의입니다. Java `BigDecimal`의 `equals`(scale까지 일치 요구)라는 특정 언어 구현체의 특성을 패턴의 원전 필수 조건인 것처럼 단정한 것은 오류입니다.
* **다이어그램의 `Quantity <|-- Money` 상속 관계는 Analysis Patterns 원전 구조와 어긋남**
  * **내용**: 본문 Mermaid 다이어그램은 `Quantity <|-- Money` 일반화(상속) 화살표를 그리고 있습니다.
  * **원전 대조**: 본문이 다루는 주 원전인 『Analysis Patterns』 3장(Figure 3.2, 3.3, 3.4)에는 `Money` 패턴 자체가 존재하지 않습니다(Money는 훗날 PoEAA 18장에 독립 패턴으로 등장). 튜토리얼 슬라이드의 개념적 설명을 근거로 들었으나, Analysis Patterns 3장의 정규 클래스 모델에 타 서적의 패턴을 상속 관계로 편입시킨 것은 원전 다이어그램과 일치하지 않으며 독자에게 구조적 오해를 부릅니다.

### 3) 구현과 설명의 일치

* **클래스 다이어그램과 세 언어 구현 코드의 필드명 및 타입 구조 불일치**
  * **속성명 불일치**: Mermaid 다이어그램의 `ConversionRatio`는 원서 속성명을 따라 `number : Number`로 표기되어 있으나, Java·TS·Rust 실제 코드는 모두 `factor`(`long`, `bigint`, `i64`)를 사용합니다.
  * **타입 구조 불일치**: 다이어그램은 `Unit <|-- CompoundUnit` 상속 구조로 그렸으나, 실제 코드는 Java `enum`, TS 객체 리터럴 유니온, Rust `enum`으로 작성되어 있습니다. 세 언어 모두 상속이나 하위 타입 확장이 원천적으로 불가능한 닫힌 타입을 사용했으므로, 다이어그램의 구조와 구현 코드가 모순됩니다.
* **Java `Quantity`의 `Comparable<Quantity>` 인터페이스 구현 누락**
  * **내용**: Java 코드에 `int compareTo(Quantity other)` 메서드를 정의하고 본문에서도 `BigDecimal`의 `compareTo`와 비교하며 상세히 설명하지만, 클래스 선언부에 `implements Comparable<Quantity>`가 빠져 있습니다.
  * **문제점**: 인터페이스 구현이 누락되어 Java 표준 정렬 컬렉션(`TreeSet`, `TreeMap`)이나 `Collections.sort()`, Stream의 `.sorted()` 등 Java 표준 라이브러리 생태계에서 전혀 동작하지 않는 '이름만 compareTo인 불완전한 메서드'로 남아 있습니다.
* **Java `convertTo`의 `divide` 호출 시 무한소수 예외 취약성 [추정]**
  * **내용**: Java `Quantity.convertTo`에서 `amount.divide(factor)`를 호출할 때 `RoundingMode`나 `MathContext`를 지정하지 않습니다.
  * **문제점**: 현재 예제는 `factor = 1000`(소인수 2와 5)이라 우연히 유한소수로 떨어져 동작하지만, 단위가 확장되어 3이나 7 같은 비율(예: 3 ft = 1 yd)이 추가되는 순간 즉시 `ArithmeticException: Non-terminating decimal expansion`이 발생합니다. TS와 Rust가 `% ratio.factor != 0`으로 사전 검증하는 것과 비교할 때 Java 구현만 예외 안전성이 결여되어 있습니다.

### 2) 비교의 타당성

* **'단위를 들고만 있는 래퍼'와의 구분 기준이 모순되어 독자 혼란 유발**
  * **내용**: 비교 표에서는 구분 기준을 "연산이 상대의 단위를 읽고 판단하는가"로 정의했습니다. 그러나 바로 아래 본문에서는 "단위 다를 때 거부만 하고 환산은 못 해도 조건 2는 갖춘 것"이라 서술하고, [문제 1]의 풀이에서도 환산 없이 단위 불일치 시 throw만 하는 `Amount`에 대해 "조건 2는 충족하며 equals만 더하면 Quantity"라고 판정합니다.
  * **문제점**: 이 기준에 따르면 "환산 기능 없이 단위 확인 후 거부만 하는 불변 객체"는 래퍼입니까, Quantity입니까? 본문 설명과 문제 풀이가 충돌하여 독자는 환산 기능이 필수인지 단순 검사만으로 충분한지 경계를 가를 수 없게 됩니다.
* **Money 비교 표의 득실 서술 관점 역전**
  * **내용**: 비교 표의 다른 행(원시 필드, 래퍼, Measurement)은 "해당 대상 대신 Quantity를 택했을 때의 득실"을 적고 있습니다. 반면 Money 행은 "질량·부피·금액이 같은 연산 규칙을 공유한다(얻는 것)", "통화의 최소 단위 반올림 규칙은 따로 얹어야 한다(포기하는 것)"로 기술되어 있습니다.
  * **문제점**: 이는 비교 대상인 Money를 골랐을 때의 득실이 아니라, 'Money 대신 범용 Quantity 하나로 금액까지 퉁쳤을 때의 득실'을 적은 것입니다. 표 전체의 비교 관점(대칭성)이 Money 행에서만 거꾸로 뒤집혀 있어 서술의 일관성을 해칩니다.
