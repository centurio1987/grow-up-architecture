# 파일럿 회고 — Strategy · Account · Quantity (KAN-001.3 S4)

> 작성 2026-09-17. 파일럿 세 편을 `gof-guide`·`analysis-guide` 1.0.0 으로 3라운드씩 돌린 실측과, 그것으로 정한 spec 1.1 · 게이트 수정 · 배치 크기를 적는다.
> 게이트 원자료는 이 폴더의 `strategy/` · `account/` · `quantity/` 에 라운드별로 있다(이해 게이트 `*.gate.txt`, 외부 검토 `*.external.txt`, 품질 채점 `*.score*.md`).

## 2. 세 편에 공통으로 나온 결함 — 예제 정책을 `[필수]` 최소 조건으로 올렸다

| 편 | 조건 | 원전이 말하는 것 | 결과 |
| --- | --- | --- | --- |
| Strategy | 조건 3 뒷절 "요청 처리가 그 선택을 바꾸지 않는다" | GoF 원서에 없는 이 가이드의 확장 | 채점 워커 지적 |
| Quantity | 조건 3 "수치와 단위가 둘 다 같아야 같은 값" | 원서 그림 3.2 는 연산 `=` 만 둔다. 환산 후 비교를 배제하지 않는다 | 3라운드 외부 검토 두 모델 공통 지적 |
| Account | 조건 3 "확정된 Entry 를 고치지 않는다" | eaaDev Account 의 필수 성질은 "Entry 모음 · 요약 제공" 둘뿐이고, 확정 뒤 불변은 "Often" 붙은 흔한 규칙이다 | 3라운드 외부 검토 두 모델 + 채점 E2 |

`[필수]` 는 analyzer 가 "패턴 아님"으로 읽는 표기라, 예제 정책이 여기 들어가면 원전 기준으로는 그 패턴인 사용자 코드를 오판한다.
spec 에는 "빠지면 그 패턴이 아니게 되는 것만 `[필수]`"라는 문장이 있었지만 근거를 대라는 요구가 없어서 세 워커가 모두 같은 방향으로 넘었다.

**처리(spec 1.1)**: PG27(MUST) — `[필수]` 조건마다 `(근거: 원전의 자리)` 괄호, 원전이 흔한 규칙·선택지로 적은 것과 예제 정책은 `[선택]`.
강제 지점은 `scripts/check-guides.py` 최소 조건 검사(근거 괄호 없음 · 근거가 "이 가이드"로 시작하면 실패)와 두 캔버스의 집필 지시다.
1.1 로 다시 검사하면 Strategy·Quantity 는 `[필수]` 3개씩 근거 괄호가 없어 기계 검사에서 떨어지고, Account 는 괄호는 있지만 조건 3 내용이 채점에서 떨어진다.

## 3. 이해 게이트 — 판정이 실행마다 흔들린다

### 3.1 실측

| 실험 | 파일 | 결과 |
| --- | --- | --- |
| 3라운드 원 실행 | Strategy r3 | codex PASS · agy FAIL(Q2 · Q3 · Q4 · Q5) |
| 같은 파일 재실행 | Strategy r3 | agy FAIL(Q4 만) — codex 는 사용량 한도로 응답 없음 |
| 규칙 6 을 "대상 전부 검사"로 바꾼 사본 | Strategy r3 | agy PASS |
| 3라운드 원 실행 | Quantity r3 | codex FAIL(Q3) · agy PASS |
| 같은 파일 재실행 | Quantity r3 | agy PASS |
| 규칙 6 을 "대상 전부 검사"로 바꾼 사본 | Quantity r3 | agy FAIL(Q5 — 상황 설정 표의 bounded context 행을 코드와 잇지 못함) |

- **같은 모델 · 같은 파일에서 FAIL 네 개가 한 개로 바뀌었다.** 재실행에서도 남은 것은 Strategy 의 Q4(Command 와의 구분 기준이 "목적이 다르다")뿐이다. 모델 간 편차라고 보던 것의 상당 부분이 실행 간 편차다.
- **규칙 6("본문 설명이 가장 얇은 대상을 고른다")** 은 채점 모델마다 다른 대상을 고르게 해 라운드마다 표적이 옮겨 간다. 전수 검사 사본은 편차를 없애지 못했고 새로운 실패(값 객체의 bounded context 행)를 만들었다.
- **spec 과 게이트의 충돌**: spec PG20 은 세 언어 해설을 한 번만 쓰라고 하는데, 게이트 Q5 는 "본문이 가장 적게 설명한 줄, 한 언어를 골라도 된다"라서 agy 가 해설이 적은 TypeScript 줄을 골라 FAIL 을 냈다(Strategy r3).
- 실험은 codex 사용량 한도(오후 7시 46분 해제 예정) 때문에 agy 한 모델로만 돌았다. codex 쪽 재현성은 확인 안 함.

### 3.2 고친 것 — 결함

- **한 모델만 응답해도 PASS(종료코드 0)가 나왔다.** 위 실험에서 codex 가 한도로 빠진 채 agy 단독 PASS 가 0 으로 끝났다. 플랜의 전제("두 모델 모두 필요")와 어긋나는 결함이라 `scripts/comprehension-gate.sh` 를 고쳤다 — 한 모델이라도 응답이 없고 FAIL 도 없으면 미완료(2).
- codex 사용량 한도를 "인증 만료"로 오진하던 문구도 고쳤다.
- 회귀 테스트 `scripts/test-comprehension-gate.sh`: 가짜 codex·agy 로 응답 조합 7건. 수정 전 스크립트는 "한도 + PASS" 조합에서 0 을 냈다.
- 파일럿 18회(3편 × 3라운드 × 이해 게이트·외부 검토)는 모두 두 모델이 응답해 기록에 영향이 없다.

### 3.3 유저 결정으로 올린 것

게이트의 통과 기준을 바꾸는 일이라 적용하지 않았다. .3 검토서 판단 항목에 추천과 함께 있다.

1. **FAIL 재확인** — FAIL 이 나면 한 번 더 돌려 같은 질문이 다시 FAIL 일 때만 확정한다. 추가 비용은 FAIL 때만 든다.
2. **Q5 와 PG20 충돌** — Q5 문구에 "해설은 세 언어 공통으로 한 번 쓰는 것이 규약이므로 언어별 설명이 적은 것은 FAIL 사유가 아니다"를 넣는다.
3. **규칙 6** — 유지(전수 검사로 바꿔도 편차가 줄지 않았다).

## 4. 품질 채점 — 마지막 라운드 외부 검토가 채점에서 빠졌다

- 라운드 순서가 "게이트·외부 검토 실행 → 채점 → 집필 보완"이라, 3라운드 외부 검토는 보완할 집필 라운드가 없고 채점보다 늦게 끝나면 판정에도 들어가지 않는다.
- Quantity 는 채점(16:39:01)이 외부 검토(16:39:07)보다 먼저 끝나 그 지적이 채점에 들어가지 않았다. Strategy 3라운드 채점이 외부 검토를 봤는지는 채점 보고에 언급이 없어 확인 안 함.
- Account 는 채점이 끝난 뒤 외부 검토를 따로 전달했다. 첫 채점도 조건 3 으로 FAIL 이었고, 외부 검토 대조로 참 6건이 미흡에 더해졌다.
- Strategy·Quantity 는 이해 게이트에서 이미 FAIL 이라 최종 판정은 같다. 지적 원문은 각 `*.r3.external.txt` 에 있다.
- **처리(spec 1.1 공유 블록 「채점 규약」)**: 마지막 라운드 외부 검토는 채점 입력이다. 채점이 먼저 끝나도 닫지 않는다.
- 산문 연속 상한(voice V1)은 채점자가 손으로 세면 도식·표·코드를 끊김으로 치는지가 갈렸다. `golden.py measure` 의 `max_prose_run_without_visual` 로 고정했다. voice 파라미터 `max_prose_run=2` 는 그대로 두고, 세 편 모두 그 값이 2 였다.

## 5. 값 객체 계열 상황 설정 표 — 유지

Quantity 채점 워커의 칸별 관찰(3라운드)을 근거로 **4행 표를 MUST 로 유지**하고 경계 반례 표(AG13, SHOULD)를 더했다.

| 칸 | 표만 있을 때 | 경계 반례 표를 붙인 뒤 |
| --- | --- | --- |
| bounded context | 정보량 낮음 | 여전히 낮음 — 한 줄 유지, 코드가 그 경계를 드러내는 곳을 한 줄 덧붙이면 충분 |
| 불변식의 위치 | 값 객체 몫과 root 몫을 갈라 정보량 가장 높음 | 불변식 9행 표로 더 높아짐 |
| root·entity·VO 배정 | 자명 | "비율을 재고마다 들면 분점에 30 g" 반례로 뜻을 가짐 |
| 타 aggregate 참조 방식 | 자명 | 카탈로그 객체 보유 · 가변 공유 두 반례로 뜻을 가짐 |

IF-APPLICABLE 로 내리지 않은 이유는 값 객체도 코드에는 반드시 그것을 품는 aggregate 가 나오고, root 가 불변식을 한 번 더 지는지가 독자가 가장 자주 틀린 자리였기 때문이다.

## 6. 비용과 배치 크기 — 2

| 워커 | 최대 컨텍스트 | 출력 토큰 합 | API 호출 |
| --- | --- | --- | --- |
| Strategy 집필 | 590,321 | 286,232 | 188 |
| Account 집필 | 695,173 | 317,538 | 209 |
| Quantity 집필 | 511,027 | 275,273 | 162 |
| Strategy 채점 | 342,440 | 112,196 | 92 |
| Account 채점 | 467,635 | 161,264 | 146 |
| Quantity 채점 | 363,405 | 113,008 | 154 |

- 벽시계: 세 편 병렬로 15:25 ~ 16:50(약 85분).
- 편당 출력 토큰(집필 + 채점)은 약 39만 ~ 48만. 집필 워커는 라운드마다 같은 대화를 이어 써서 3라운드 끝에 컨텍스트가 51만 ~ 70만까지 커졌다. 4라운드를 같은 워커로 이으면 더 커진다 — 라운드마다 새 워커에 게이트 보고와 파일만 넘기는 편이 안전하다.
- **codex 사용량 한도**: 편당 codex 호출은 3라운드 기준 6회(이해 게이트 3 + 외부 검토 3)다. 세 편 × 3라운드(18회) 뒤 이어서 부른 실험 4회가 한도에 걸렸다. 한도 창의 길이와 정확한 호출 수 상한은 확인 안 함.
- 세션 예산 대비 비율은 확인 안 함. 이 세션은 .1 · .2 마무리와 함께 돌았고 메인 대화 요약이 한 번 일어났다.

**결정**: `batch_size_works` = 2. 세 편 모두 3라운드를 소진했고 한 한도 창에 세 편이 들어가지 않았다. .4 11배치 · .5 5배치 · .6 2배치로 배치 문서를 만들었다. 비교 쌍이 배치를 넘는 곳은 뒤 배치 워커에게 앞 배치 확정본을 입력으로 준다.

## 8. 하지 않은 것과 이유

- **exemplars 등록 없음** — 게이트를 통과한 편이 없다. 형식이 spec id 하나에 파일 하나라 계획의 "3건"은 애초에 불가능했다(검증 절 정정).
- **파일럿 보완 없음** — 3라운드 상한을 넘기는 보완이나 1.1 기준 새 사이클은 비용이 크고 게이트 판정 방식(3.3)이 먼저 정해져야 한다. 유저 결정으로 올렸다.
- **Strategy·Quantity 3라운드 외부 검토 지적 반영 없음** — 같은 이유. Quantity 에서 코드로 확인할 수 있는 지적(TypeScript `ConversionRatio.ALL` 정적 필드 재할당 가능, Java `divide` 의 비종료 소수 가능성, 다이어그램 필드명 `number` 와 코드 `factor` 불일치)은 확인 안 함.

## 9. 새 파이프라인에서의 재사이클 (2026-09-20)

유저 결정으로 게이트에서 정성 판정을 빼고, 가이드 배치·버저닝·예시 코드·도식 규약을 바꾼 뒤 세 편을 다시 돌렸다. **세 편 모두 통과했고 각각 2라운드가 걸렸다.**

| 편 | 라운드 1 지적 | 라운드 2 결과 |
| --- | --- | --- |
| Strategy | 조건 3의 근거가 원문의 "usually" 를 떼고 옮김 · 도식이 본문보다 한 단계 많음 · 사실 주장 둘 | MUST 38/38 · SHOULD 0 — 조건 3을 "고르는 분기가 Context 안에 없다"로 좁히고 생성 위치는 `[선택]` 로 |
| Account | 조건 1의 시간 기준이 코드와 어긋남 · 통화 단정 · id 참조 보장 과장 | MUST 35/35 · SHOULD 0 — 거래일 기준 명시, 원전 표현대로 완화 |
| Quantity | 환산 협력의 위상이 앞뒤로 다름 · 통화 자릿수와 반올림을 섞음 · 도식이 본문 주장과 다름 | MUST 42/42 · SHOULD 0 — 도식을 다시 그려 연관선·다중도가 보이게 |

### 무엇이 달라졌나

- **판정이 흔들리지 않았다.** 이전 사이클에서 통과를 막던 것은 실행마다 바뀌는 이해 게이트였다. 이번에는 기계 검사(헤딩·플레이스홀더·문체·도식·링크·근거 괄호·세 언어 컴파일·실행 대조)가 통과 여부를 가르고, 외부 검토와 채점은 **고칠 자리를 지목하는 입력**으로만 썼다.
- **지적이 재현 가능한 것으로 바뀌었다.** 세 편의 1라운드 지적 아홉 건 중 여덟이 코드 실행이나 원문 대조로 참/거짓이 갈렸다(계정 닫기 경로, TypeScript 시그니처 확장, `ConversionRatio.ALL` 재대입, 원서의 "usually", 도식의 연관선 유무 등). 남은 하나는 문서 안의 앞뒤 모순이었다.
- **도식이 검사 대상이 됐다.** mermaid 를 쓸 때는 그림이 본문 주장과 다른 것을 아무도 잡지 못했다. 컴포넌트로 옮긴 뒤 채점자가 PNG 를 직접 열어 "연관선과 다중도가 없다"를 잡았고, 그 자리가 실제 결함이었다.
- **코드가 본문 밖 실행 파일이 되면서** 세 언어 출력 동일성과 본문 수치의 출처가 기계로 확인된다. 이전에는 워커가 임시 경로에 코드를 복사해 돌린 결과를 손으로 옮겨 적었다.

### 비용

편당 집필 워커 1명이 2라운드, 채점 워커 1명이 2회 판정했고, 외부 검토는 편당 1회(codex 응답, agy 는 사용량 한도로 빠짐)였다. 이전 사이클(편당 3라운드 + 이해 게이트 3회 + 외부 검토 3회)보다 외부 모델 호출이 편당 6회에서 1회로 줄었다.
