Node.js 비동기 작동 원리 — 개념 검토

질문에 담긴 각 주장을 하나씩 확인하고, 틀린 부분을 바로잡습니다. (Node.js 11 이상 기준)

1. 한눈에 보는 판정

#주장판정실제 동작
1콜스택이 비었을 때만 큐에서 꺼내 온다맞음JS는 run-to-completion. 실행 중인 코드가 끝나 콜스택이 비어야 다음 콜백이 들어갑니다.
2nextTick → Promise(microtask) → libuv(macro) 순대체로 맞음우선순위는 맞습니다. 단, nextTick·microtask는 libuv 콜백 하나가 끝날 때마다 끼어들어 실행됩니다.
3한 틱에 하나만 꺼내고, 콜스택이 비면 다시 꺼낸다틀림nextTick·microtask 큐는 빌 때까지 전부 비웁니다. libuv 단계(phase)도 그 단계의 큐에 쌓인 콜백을 전부(시스템 한도까지) 실행한 뒤 다음 단계로 넘어갑니다.
4Macro는 6개 큐: immediate → timer → pending → exit → system call틀림순서와 이름이 다릅니다: timers → pending callbacks → idle/prepare → poll → check(setImmediate) → close callbacks. "exit" 단계는 없습니다(close 콜백 단계가 있음).
5immediate 3개 → 하나 실행 후 끊기고, 다음 틱에 또 하나틀림check 단계에서 3개 모두 같은 루프 회차에 실행됩니다(사이사이 microtask 비우기). 단, check 실행 중에 새로 등록된 setImmediate는 다음 회차로 미뤄집니다.
6시스템 콜 여러 개 → 처음 도착한 응답 하나만 처리 후 다음 틱틀림poll 단계는 그 시점까지 완료된 I/O 이벤트를 모두 처리합니다. 한 개만 처리하고 넘어가지 않습니다.

2. 올바른 이벤트 루프 모델

① timerssetTimeout / setInterval→ ② pending지연된 일부 시스템 오류 콜백→ ③ idle/prepare내부용→ ④ pollI/O 완료 콜백, 대기→ ⑤ checksetImmediate→ ⑥ closesocket.on('close')↺
핵심 규칙
  1. 각 단계는 자기 FIFO 큐의 콜백을 모두 실행한다 (혹은 libuv 한도에 도달할 때까지).
  2. libuv 콜백 하나가 끝날 때마다(콜스택이 빌 때마다) → process.nextTick 큐 전부 → Promise microtask 큐 전부를 비운다. 비우는 도중 새로 추가된 것도 계속 처리한다.
  3. 즉 "하나씩"인 것은 macrotask 콜백 실행 단위이지, "한 틱에 하나만 꺼낸다"가 아니다.

⚠ 용어 주의: process.nextTick의 "tick"은 이벤트 루프 한 바퀴가 아니라 "현재 작업 직후"라는 뜻입니다. 루프 한 바퀴는 보통 iteration이라고 부릅니다.

3. 주장 5 검증 — setImmediate 3개

setImmediate(() => { console.log('imm1'); Promise.resolve().then(() => console.log('micro1')); });
setImmediate(() => console.log('imm2'));
setImmediate(() => {
  console.log('imm3');
  setImmediate(() => console.log('imm4 (다음 회차)'));
});
imm1
micro1            ← 콜백 하나 끝날 때마다 microtask 비움
imm2              ← 같은 check 단계에서 계속 실행
imm3
imm4 (다음 회차)  ← check 도중 등록된 건 다음 루프로

질문의 모델대로라면 imm1 다음에 루프가 끊기고 timers·poll을 한 바퀴 돈 뒤 imm2가 나와야 하지만, 실제로는 한 check 단계 안에서 연속 실행됩니다.

4. 주장 6 검증 — I/O 여러 개

  • 네트워크 I/O는 OS의 epoll/kqueue/IOCP로, 파일 I/O·DNS·crypto 일부는 libuv 스레드풀로 처리됩니다.
  • poll 단계에 들어오면 libuv는 준비된 이벤트 목록을 한 번에 받아서 각 콜백을 차례로 실행합니다(각 콜백 뒤 microtask 비움).
  • 처리 순서는 "요청한 순서"가 아니라 "완료되어 준비된 순서"입니다. 아직 완료되지 않은 I/O만 다음 회차로 넘어갑니다.
  • poll 큐가 비면: setImmediate가 있으면 check로 바로 넘어가고, 없으면 가장 가까운 타이머 만료 시점까지 대기(block)합니다.

5. 정정된 요약문

콜스택이 비면 Node는 process.nextTick 큐를 전부, 이어서 Promise microtask 큐를 전부 비운다. 그다음 libuv 이벤트 루프가 timers → pending → idle/prepare → poll → check → close 순으로 단계를 돈다. 각 단계는 해당 큐의 콜백을 모두 실행하며, 콜백 하나가 끝날 때마다 nextTick·microtask 큐를 다시 전부 비운다. setImmediate 3개는 한 check 단계에서 연속 실행되고, poll 단계는 완료된 I/O 응답을 모두 처리한다.

6. 추가 질문

Q1. immediate가 timer보다 우선순위가 높은가?

아니요. 단계는 우선순위가 아니라 순환입니다. 어느 쪽이 먼저 실행되는지는 루프의 현재 위치에 따라 달라집니다.

// 메인 모듈: 실행 순서가 비결정적
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// → 루프 진입 시 1ms가 지났으면 timeout 먼저, 아니면 immediate 먼저

// I/O 콜백 안(poll 단계): 항상 immediate가 먼저
require('fs').readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
}); // → immediate, timeout (poll 다음이 바로 check라서)
Q2. timer 3, pending 3, immediate 3이면 한 바퀴에 9개?

네, 루프 한 바퀴(iteration)에 9개 모두 실행됩니다. timers(만료된 것 3) → pending 3 → poll → check 3 순이고, 콜백 하나가 끝날 때마다 nextTick·microtask 큐를 비웁니다.

조건: 타이머는 이미 만료된 것만 실행되고, 해당 단계 실행 중에 새로 등록된 timer/immediate는 다음 바퀴로 넘어갑니다. pending 단계는 사용자 코드가 직접 채우는 큐가 아니라, 지연된 일부 TCP 오류 콜백 같은 내부용 큐입니다.

Q3. poll은 아직 응답이 오지 않은 요청까지 기다렸다가 처리하나?

아니요. poll은 타임아웃을 정해 두고 기다립니다(epoll_wait(timeout)).

  • 타임아웃 = 가장 가까운 타이머의 만료 시점까지 남은 시간. setImmediate가 대기 중이면 0(기다리지 않음). 타이머가 없고 활성 핸들만 있으면 무한대.
  • 이벤트가 하나라도 준비되거나 타임아웃이 되면 깨어나서, 그 순간 준비된 이벤트 묶음을 처리하고 다음 단계로 넘어갑니다.
  • 남은 요청은 다음 바퀴의 poll에서 처리합니다.

모든 요청을 기다리는 방식이라면, 1초 걸리는 HTTP 요청 하나 때문에 그동안 만료된 타이머나 setImmediate가 전부 막힙니다. server.listen()처럼 끝나지 않는 소켓이 있으면 루프가 영영 다음 단계로 넘어가지 못합니다.

setTimeout(() => console.log('timer 10ms'), 10);
require('https').get('https://example.com', () => console.log('http 응답'));
// → timer 10ms 먼저 (poll이 10ms 타임아웃으로 깨어나 timers로 돌아감), 그 뒤 http 응답
