# 디자인 패턴 부합도 분석 Skill

이 skill 은 사용자가 작성한 코드를 읽고, 사용자가 의도한 디자인 패턴의 최소 충족 조건과 비교해 부합도를 판정한다.

산출물은 두 개다.
1. **채팅 요약** — 조건별 ✅/⚠️/❌ 와 종합 판정, 최우선 권장 조치 1~2개.
2. **분석 리포트 파일** — `analysis/<pattern>-<filename>-<YYYYMMDD-HHMM>.md` 에 풀 리포트 저장.

## 작성 절차

### 1. 입력 식별
- **대상 파일**: 사용자가 명시한 경로, 첨부 파일, 또는 `python/` `typescript/` `rust/` `java/` 안의 파일 중 사용자가 가리킨 것.
  - 경로 모호하면 `ls` 로 후보를 추려서 사용자에게 한 번 확인.
- **대상 패턴**: 사용자 메시지에서 추출. 명확하지 않으면 짧게 한 번 묻는다.
- **언어**: 파일 확장자로 판정 (`.py` `.ts` `.rs` `.java`). 그 외 확장자면 사용자에게 확인.

### 2. 평가 기준 로드 (우선순위 순)
1. 프로젝트 루트에 `<pattern>-pattern.md` (예: `singleton-pattern.md`) 가 있으면 그 문서의 **"## 디자인 패턴을 충족하는 최소 조건"** 섹션을 평가 기준으로 사용한다. (가장 우선)
2. 사용자가 별도 기준 문서를 제시했으면 그것을 사용.
3. 위 두 가지 모두 없으면 같은 폴더의 `checklist.md` 의 해당 패턴 항목을 사용한다.

평가 기준의 출처(파일 경로 또는 "내장 checklist.md")를 리포트 메타에 반드시 명시한다.

### 3. 정적 분석
Read 도구로 대상 파일을 읽고, 각 최소 조건마다 다음을 수행한다.

- **조건 진술**: 기준 문서의 원문을 그대로 인용.
- **판정**: ✅ 충족 / ⚠️ 부분 충족 / ❌ 미충족 / ❓ 판정 불가 — 4값 중 하나.
- **근거 인용**: 파일 경로 + 라인 범위 + 5~12 라인의 코드 발췌.
- **해설**: 왜 그렇게 판정했는지 1~3 문장. 미충족이면 무엇이 빠졌는지 구체적으로.

판정이 흔들리는 경우 (코드 단편만으로 판단이 어려움) 는 반드시 ❓ 로 처리하고 "판정 보류" 사유를 적는다. 추측으로 ❌ 를 남발하지 않는다.

추가로 `checklist.md` 의 **자동 시그널** 패턴(정규식·키워드)을 grep 으로 확인해 1차 시그널을 빠르게 잡는다. 단, 시그널 부재만으로 미충족 판정을 내리지 않는다 — 실제 코드 의미를 확인한다.

### 4. (선택) 안전한 실행 검증

다음 조건이 **모두** 충족될 때만 코드를 실행한다.

- 파일이 자기-완결적 진입점을 가짐 (`if __name__ == "__main__"`, `main()`, `fn main()`, `public static void main`).
- 네트워크 호출, 파일 시스템 변경, 외부 명령(subprocess/exec) 호출이 없음.
- 프로젝트의 `Makefile` 에 해당 패턴/파일에 대응하는 타깃이 존재 (`make py PATTERN=...` 등).

실행은 다음 명령을 사용한다.
- Python: `cd /Users/centurio/design-pattern-guide && make py PATTERN={module}`
- TypeScript: `cd /Users/centurio/design-pattern-guide && make ts PATTERN={basename}`
- Rust: `cd /Users/centurio/design-pattern-guide && make rs PATTERN={example_name}`
- Java: `cd /Users/centurio/design-pattern-guide && make java PATTERN={ClassName}`

실행 출력은 리포트의 "테스트 / 동작 검증" 섹션에 발췌 첨부한다. 출력이 조건(예: Singleton 의 인스턴스 동일성)을 입증/반증하는지 한 줄로 결론짓는다.

위 조건 중 하나라도 안 맞으면 실행 단계를 생략하고 "정적 분석만 수행" 으로 표기한다.

### 5. 종합 판정

조건별 결과를 다음 규칙으로 묶는다.

| 결과 분포 | 종합 판정 |
| --- | --- |
| 모든 필수 조건이 ✅ | **정통 패턴** |
| 필수 조건은 모두 ✅, 선택 조건만 ⚠️/❌ | **정통 패턴 (선택 조건 보강 권장)** |
| 필수 조건 중 1개가 ⚠️ 이고 나머지 ✅ | **변형 패턴** |
| 필수 조건 중 ❌ 가 1개 이상 | **패턴 아님** |
| ❓ 가 핵심 조건에 포함 | **판정 보류** — 추가 정보 요청 |

"필수"와 "선택"의 구분은 기준 문서의 표기를 따른다. 표기가 없으면 첫 3개 조건을 필수로 본다.

### 6. 리포트 작성

같은 폴더의 `report-template.md` 의 구조를 그대로 따른다. 파일명 규칙:

```
analysis/<pattern>-<filename_stem>-<YYYYMMDD-HHMM>.md
```

예: `analysis/singleton-singleton-20260529-1430.md`

`analysis/` 디렉토리가 없으면 만든다.

### 7. 채팅 요약 출력

다음 형식으로 짧게:

```
[패턴명] {파일경로}
종합 판정: {정통/변형/아님/보류}
조건: ✅ N개 / ⚠️ M개 / ❌ K개 / ❓ L개
최우선 조치: {한 줄}

리포트: analysis/...md
```

리포트 파일은 반드시 `mcp__cowork__present_files` 로 사용자에게 공유한다.

## 톤 & 스타일

- 한국어. 패턴/역할 용어는 영문 원어 병기.
- 추측 금지. 코드에 없는 사실을 단정하지 않는다. 보이지 않으면 ❓.
- "이 코드는 좋다/나쁘다" 류의 가치 평가는 피하고, "조건 N 미충족: 이유" 처럼 사실 기반 서술.
- 권장 조치는 항상 before/after 짝 코드로 보여준다.

## 하지 말 것

- 평가 기준을 임의로 새로 만들지 않는다. 반드시 (1) 가이드 문서 또는 (2) 내장 `checklist.md` 에서 가져온다.
- 코드를 실행할 때 "안전한 실행 조건" 4개를 1개라도 어기지 않는다.
- ❌ 판정만 잔뜩 나열하지 말고, 정확히 어떤 라인의 어떤 코드가 어떤 조건을 어떻게 위반하는지 짝지어 적는다.
- 사용자가 작성한 코드를 마음대로 고치지 않는다. 권장 조치 코드 스니펫은 리포트 안에만 둔다.
